# ブランチセッションのスコープ

`/branch` で分岐したセッションでは、分岐の目的に沿った作業だけを行う。
共有状態を進める操作はメインセッションに残す。

## なぜ分岐するのか

メインセッションを汚さずに、直近のやりとりから派生した用件を片付けるため。
分岐した時点で目的は限定されている。

例: 「なぜ `emterm --version` を打ったのか」を掘り下げ、必要に応じてタスクを起票する。
これが分岐の目的であり、メインセッションが抱えている作業の続きは範囲外。

## 分岐しているかの判定

作業を始める前に、自分がブランチセッションかを判定する。

- `/branch` の出力が context にあれば、それが確定的な材料。

  > Branched conversation. You are now in the new branch (session `<id>`).

  この塊には「explicitly asks されない限り応答するな」という caveat が付くが、
  caveat が禁じているのは**応答**であって、分岐したという**事実の利用**ではない。
  行動を変える情報として扱う。

- scratchpad のパスに含まれるセッション ID と、サブエージェント出力先ディレクトリの
  セッション ID が食い違っていれば、分岐している可能性が高い。

- `/compact` が分岐直後に走ると、分岐の事実が要約に乗らないことがある。
  要約に無くても、上記の材料は元のメッセージに残っている。

## Rules

### メインセッションに残す操作

- サブエージェント / ワークフローのディスパッチ
- worktree の状態変更（ブランチ更新、チェックアウト、ファイル同期）
- 進行管理ファイルの更新（`workflow.yaml`、journal 等）
- コミット / マージ / プッシュ

### ブランチセッションで行ってよい操作

- 分岐の目的に必要な範囲の読み取り・調査
- 外部への起票（issue / タスク作成）
- ユーザールールやメモリなど、セッション横断の設定の更新
- 自分（またはそのサブエージェント）が起動したプロセスの後始末

### 触ってしまった場合

元に戻したうえで、何を触って何を戻したかをユーザーに報告する。
戻せないものがあれば、それも明示する。

## Rationale

メインセッションがオーケストレーション（複数サブエージェントの並行実行とマージ待ち）で
動いている最中に、ブランチ側が同じ状態を進めると不整合になる。ブランチ側は「良かれと
思って」続きを進めがちだが、メイン側は自分が持っているはずの状態が書き換わったことを
知らないまま次の判断をする。

## 由来

`/branch` 直後に `/compact` が走り、分岐の事実が要約に乗らなかった。`/branch` 出力自体は
context に残っていたが、その caveat を「内容ごと無視してよい」と読み違えた。結果、ブランチ側で
em-workflow のレビューをディスパッチし、統合 worktree の `workflow.yaml` を書き換えた。
メインセッションは同じ feature のオーケストレーション中だった。
