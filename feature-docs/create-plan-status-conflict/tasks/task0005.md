### The rule that separates a rewrite from a deletion

Failures 1-4 guard something that still exists in a changed form: re-express
the assertion against the current text and keep the guard. Failure 5 guards
behaviour that no longer exists at all: it is the only case where the original
claim is retired, and it is retired by **substitution** — the replacement
assertion covers the behaviour that took the old one's place, so the file's
coverage of Step A does not shrink to nothing.

No case is resolved by deleting a test, skipping it, or weakening it into a
check that cannot fail.

## Test Notes

- This task's deliverable IS test code, so the usual TDD order is inverted in
  form but not in substance: for each of the five, first observe the assertion
  failing for the stated reason, then retarget it, then observe it passing —
  and confirm it fails again when the guarded production text is perturbed
  locally (do not commit the perturbation). That perturbation check is how
  AC-6 is demonstrated per assertion.
- Read the current production text before rewriting an assertion. The failure
  messages quoted in this plan identify the cause, not the replacement
  wording; the replacement literal must be taken from the file itself.
- Prefer structural relationships over one long literal where the document is
  prose (failures 3 and 5): a section slice plus the concepts it must contain
  survives a wording tweak that a full-sentence literal would not.
- AC-1 is the criterion the verify phase re-runs. Run the full suite, not only
  the four modified files — retargeting an assertion in one file must not
  perturb another file's expectations.
- Requirement coverage: AC-1 → TS-5; AC-2 … AC-7 → TS-7.
