# Task Plan: task0002 — Interrupt recovery in create-plan-phase §3, and the phase-state consistency fix

## Goal

`em-workflow/references/phases/create-plan-phase.md` §3 states the recovery
rule for a create-plan step interrupted at `in_progress` (reset to `pending`
before dispatch when the proposed patch has not been applied; no reset when it
has), and `em-workflow/references/phase-state.md` no longer describes Step B
in a way that contradicts the create-plan exemption — both pinned by their
paired test files.

## Design

### §3 "Reconcile on entry" — the rule to add

§3 currently tells the orchestrator to apply the Resume decision table from
`references/phase-state.md` against a fixed ordered list of inputs. Add one
rule that resolves the case where the create-plan step in `workflow.yaml` is
`in_progress` on entry (see IMPLEMENTATION.md S2 for the contract):

1. **Patch not applied** (the interrupted run never got to applying the
   proposed patch): reset the create-plan step to `pending` **before**
   dispatching the planner, and commit that reset with the phase's normal
   documentation-commit mechanism (`commit-docs.sh`), following the commit
   discipline Step B owns. Dispatch happens only after the reset is committed.
2. **Patch already applied**: perform no reset. Only the transition to
   `completed` is carried out, following this document's existing completion
   section and the Resume decision table row for an already-applied patch in
   `references/phase-state.md`.

Both branches must be readable from §3 alone — a maintainer resuming an
interrupted feature must not have to reconstruct the procedure from elsewhere
(US2/AC4). Cite the owning documents for the underlying tables and for the
`replace_all` permission conditions instead of restating them
(IMPLEMENTATION.md S3, NFR3): this document is already required by its tests
not to restate workflow-patch.md's application-rule text or the question
packet's internal fields, and that must remain true afterwards.

Structural constraints for this document:

- Its section titles and their order are asserted against the design source;
  add the rule **inside** the existing §3 rather than as a new numbered
  section, and do not rename or reorder any section.
- The document is English; write the new text in English.

### `phase-state.md` — the FR7 fix

The `project.design_system backfill` section describes Step B's normal
sequence as "select the first incomplete step → set it `in_progress` →
execute the phase", and its numbered procedure ends by telling the reader to
proceed to set the step `in_progress` and execute the phase. `create-plan` is
one of the two backfill-target steps, so as written this contradicts the
create-plan exemption (IMPLEMENTATION.md S1/D4).

Required outcome: the section no longer asserts the `in_progress` update as
unconditional for its target steps — it either scopes that description to the
steps that do take it, or notes that create-plan is exempt — and it points at
`skills/develop/SKILL.md` Step B as the owner of that discipline instead of
re-deciding it here. Do not copy the exemption's rationale text from Step B
(single ownership); a pointer plus the minimum qualifier is enough.

Preservation constraints, all currently asserted by
`tests/test_phase_state_doc.py`:

- the section heading stays;
- the section still mentions Step B and still presents its placement as a
  numbered sequence of at least four steps;
- the placement rationale ("why the backfill runs before the status update")
  and the interrupted-backfill paragraph stay;
- the section still reaches the cross-product handling by reference, without
  reproducing the owning table's rows as markdown table syntax.

Also confirm — and state nothing new unless a contradiction is found — that
the legacy-compatibility table row for a create-plan that is
`in_progress` / `pending` with no phase-state still lands on the same
conclusion as the new §3 rule (restart that phase, i.e. re-run from
`pending`). Planning found these consistent; if the implementer finds
otherwise, that is a reportable deviation.

### Explicitly not part of this task

mirrored there.
