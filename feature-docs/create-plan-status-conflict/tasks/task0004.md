# Task Plan: task0004 — Step B stop-condition 3: generalize the carve-out to protocol-prescribed automatic re-entry

## Provenance

- `source`: review
- `source_ids`: [`cmp-stopcond3-universal-claim`]
- `review_round`: 1

Round-1 finding `cmp-stopcond3-universal-claim` (high, comprehensive,
`em-workflow/skills/develop/SKILL.md:240`): the carve-out paragraph added to
Step B during round 1's auto-fix loop closes with the universal claim that
stop condition 3's "`needs_update` requiring user intervention" means *steps
other than create-plan*. That sentence makes the rework spec-change
transition's create-spec re-entry unreachable — the transition sets
`create-spec` to `needs_update` and requires the develop state machine to
re-enter there, but Step B selects `create-spec` as the first incomplete step
and the universal claim fires stop condition 3, producing a deadlock that no
re-run of `/em-workflow:develop` can leave.

## Design

See IMPLEMENTATION.md **S4 (automatic-re-entry carve-out)** for the normative
statement this task renders, and **D6** for why this task modifies the

### What Step B must say after this task

One labelled block inside Step B, replacing the current
「**停止条件 3 との優先関係**」 paragraph's final universal sentence, stating:

1. **Evaluation point (retained, unchanged in meaning).** Stop condition 3 is
   evaluated once, against the `failed` / `needs_update` status of the step
   Step B has just selected. It does not re-fire on a status that is
   deliberately held during that step's own phase execution.
2. **The generalized carve-out.** A `needs_update` that a phase protocol's
   prescribed transition set *in order to have that phase re-entered
   automatically* is not a stop reason. The phase is executed with that status
   unchanged. The status is not rewritten to `pending` first — the entry
   status is what the phase is entered with.
3. **The exhaustive enumeration.** Exactly two transitions qualify today, each
   named together with the document that owns it:
   - the create-plan **route back to planning** —
     `references/implement-phase.md` (I.2.c), which sets `create-plan` to
     `needs_update`;
   - the rework **spec-change transition** —
     `references/rework-task-synthesis.md` §10 and
     `references/contracts/rework-planner-contract.md`'s
     Specification-change transition, which sets `create-spec` to
     `needs_update` and requires the develop state machine to re-enter at
     `create-spec`.
   The enumeration is exhaustive by construction: a transition joins it only
   when the owning SSOT itself states that the phase is re-entered
   automatically. Nothing else qualifies.
4. **The negative case, stated explicitly.** The `needs_update` that
   `create-spec.stalled` option 3 (abort create-spec as `needs_update`) sets is
   a genuine wait for user intervention. Stop condition 3 still fires on it.
   The two create-spec `needs_update` states are indistinguishable in
   `workflow.yaml` alone, so the block must say which evidence separates them.
5. **The discriminator for the create-spec case.** The spec-change transition
   is required by its owning SSOT to record the interruption reason and the
   finding's `stable_id` in `phase-state/rework.yaml`. The carve-out therefore
   applies to a create-spec `needs_update` only while such a record is present
   and unconsumed; absent that record, Step B stops. The record is consumed by
   the create-spec run it caused — a `needs_update` set after that run reached
   `completed` is not covered by it.
6. **The universal claim is gone.** The sentence
   「停止条件 3 が意味する「ユーザー介入が必要な `needs_update`」は create-plan
   以外の step を指す」 is removed, not merely qualified.

Stop condition 3's bullet in the "ターンを終わらせていい唯一の条件" list
(currently naming the create-plan exemption specifically) is restated in the
same generalized terms and points at this block for the detail.

### Placement and form

- The block lives inside Step B, after the create-plan `in_progress` exemption
  block and before the commit-per-write discipline paragraph, carrying its own
  bold label — distinct from both existing labels in that section
  (「**`in_progress` へ先に更新しない理由**」 for the backfill, and
  「**create-plan が `in_progress` を経ない理由**」 for the exemption), so the
  three blocks can never be confused for one another by an assertion.
- The document is Japanese; write the new text in Japanese, matching the
  surrounding style.
- Every pre-existing assertion in `tests/test_develop_skill_rewiring.py` must
  still pass unchanged. Note in particular that the existing exemption-section
  slice runs from the exemption marker to the commit-discipline paragraph, so
  the new block falls inside it: it must not introduce any of
  `workflow-patch.md`'s copied permission-condition sentences, and must not
  reuse the backfill rationale label.

### Consistency constraints

- **The `in_progress` exemption stays create-plan-only** (IMPLEMENTATION.md
  S1). This task generalizes a different axis — which `needs_update` values
  stop the loop. Nothing in the new text may suggest that a second step is
  exempt from the pre-dispatch `in_progress` update.
- **Cite, never restate** (NFR3, IMPLEMENTATION.md S3). Name
  `references/rework-task-synthesis.md` / `rework-planner-contract.md` as the
  owners of the spec-change transition; do not reproduce the transition's
  five steps or its per-step status assignments in Step B. Likewise keep
  citing `references/implement-phase.md` for the route-back transition rather
  than describing it.
- **The referenced documents are frozen here** (NFR1).
  `references/rework-task-synthesis.md` in particular must not be changed at
  all; this task makes SKILL.md consistent with it, never the reverse. The
  same applies to `references/contracts/rework-planner-contract.md`,
  `references/implement-phase.md`, `references/phases/create-spec-phase.md`,
  `references/phase-state.md`, `references/workflow-patch.md` and
  `em-workflow/scripts/validate-worker-output.py`.
- **No phase-state schema change.** The discriminator is expressed against
  what `references/phase-state.md` and the spec-change transition already
  require to exist (`phase-state/rework.yaml` recording the interruption
  reason and the finding's `stable_id`). Concluding that a new phase-state
  field is required is a reportable plan deviation, not licence to edit
  `references/phase-state.md`.
- **`workflow.yaml` remains the sole basis for step selection and status.**
  The phase-state record is consulted only to tell the two meanings of a
  create-spec `needs_update` apart — the same pattern Step B already uses when
  it delegates create-plan's interrupt recovery to
  `phase-state/create-plan.yaml`. The new text must not read as introducing a
  second source of truth for status.
