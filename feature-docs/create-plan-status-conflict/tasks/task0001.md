# Task Plan: task0001 — Step B: create-plan exemption from the pre-dispatch `in_progress` update

## Goal

`em-workflow/skills/develop/SKILL.md` Step B states that create-plan is the
sole exception to the "set the step `in_progress` before executing it" rule,
preserves the step's entry status into planner dispatch, and carries the
rationale for the exception — with the change pinned by assertions in the
test file already paired with this document.

## Requirements

## Design

### What Step B must say after this task

Three statements, all inside the Step B section (see IMPLEMENTATION.md S1 for
the contract they render):

1. **The exception itself.** create-plan is the only step that does not have
   its status updated to `in_progress` before the step is executed. It is
   dispatched with the status it was entered with, and it advances directly to
   `completed` (with `completed_at_commit`, rule R2) once the phase has
   finished — meaning the proposed patch was applied and the commit succeeded.
   If either fails, the status is not advanced.
2. **Entry-status preservation.** The exception never overwrites the entry
   status: entering as `pending` dispatches the planner while `pending`;
   entering as `needs_update` dispatches while `needs_update`. Both branches
   the permission conditions allow are therefore actually reachable.
3. **The rationale**, carrying two reasons:
   - a `replace_all` patch is only permitted while create-plan is in one of
     those two entry statuses — stated by **citing**
     `references/workflow-patch.md`'s `replace_all` permission conditions /
     application rule 5, never by repeating the condition text
     (IMPLEMENTATION.md S3 / NFR3);
   - create-plan's interrupt recovery is carried by
     `phase-state/create-plan.yaml`, so no `in_progress` marker is needed to
     make an interrupted run recoverable.

### Placement and form

- The exemption block goes **after** the existing generic sentence that
  instructs the orchestrator to set a step `in_progress` before executing it,
  narrowing that sentence rather than replacing it (IMPLEMENTATION.md D2).
  Keep that sentence's wording intact; an existing assertion in this task's
  own test file locates it by exact substring, and the design-system backfill
  section must still be described before it.
- Use the same layout as the existing design-system backfill rationale block
  in this section: a bold label introducing the reasons, then the reasons.
  Two adjacent "why we do not set `in_progress` first" explanations now exist
  (backfill, create-plan); make clear which is which so neither reads as a
  restatement of the other.
- The document is Japanese; write the new text in Japanese.

### Consistency constraints

- Do not contradict IMPLEMENTATION.md S2 (interrupt normalization). Step B
  may mention that an interrupted `in_progress` create-plan is normalized on
  phase entry, but the procedure itself is owned by
  `references/phases/create-plan-phase.md` and is written there by another
  task — cite, do not describe it in full.
- Do not change any other Step B rule: the design-system backfill branch, the
  `completed_at_commit` normative wording, the commit-per-write discipline and
  the exit-4 recovery all stay exactly as they are.
- Do not touch `references/workflow-patch.md` or
  `em-workflow/scripts/validate-worker-output.py` (IMPLEMENTATION.md D1) and
  do not edit any test file other than the one listed above (D3).
