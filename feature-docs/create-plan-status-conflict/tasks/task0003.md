## Design

### What is frozen

`em-workflow/references/workflow-patch.md` and
`em-workflow/scripts/validate-worker-output.py` must end this feature
byte-identical to how they start (IMPLEMENTATION.md D1: the contradiction is
resolved on the producer side). This task adds tests **around** them; it never
edits them. The same applies to everything on the rework path — the
`append_rework` permission conditions, the validator's append branch, and
`references/rework-task-synthesis.md` (NFR1).

### Document pinning (FR4)

`tests/test_workflow_patch_doc.py` already asserts that the `replace_all`
permission-conditions section exists and mentions both entry statuses. Extend
it so the pin is unambiguous rather than incidental:

- the section still enumerates exactly the two permitted create-plan entry
  statuses, and no third one;
- the first condition (tasks empty, or every existing task `pending`) is still
  present — the security floor must not silently widen;
- application rule 5 still points at those permission conditions.

Assertions must be scoped to the permission-conditions section and to the
application-rule list, so an occurrence of the same words elsewhere in the
document cannot satisfy them.

### Validator regression (FR5, FR2's reachability claim)

The validator's dry-run application path rejects a `replace_all` patch unless
the create-plan step is in one of the two permitted entry statuses, reporting
the `replace-all-not-permitted` identifier. That behaviour already matches the
updated specification, so the task's job is to make an accidental future
relaxation fail loudly.

Fixture-driven regression, following the existing fixture layout (the test
module discovers case directories by kind/group/outcome from the directory
names, so a directory whose name starts with `invalid-` is expected to exit
non-zero and one starting with `valid-` to exit zero):

| Case | create-plan status | tasks | Expected |
|---|---|---|---|
| new `invalid-replace-all-create-plan-in-progress` | `in_progress` | empty | exit 1, `replace-all-not-permitted`, message naming the create-plan step status |
| new `valid-replace-all-create-plan-needs-update` | `needs_update` | empty | exit 0 |
| existing `valid-dry-run-apply` | `pending` | empty | exit 0 (assert explicitly for this scenario, do not rely on the generic sweep alone) |

Design constraints for the new fixtures:

- The **only** defect in the `in_progress` case must be the step status: the
  staleness anchors must agree with the accompanying workflow and digest
  source, the task entries must satisfy every vocabulary rule, and no task may
  be non-`pending`. Otherwise the test would pass for the wrong reason.
  Mirror the existing valid dry-run-apply case and change only what the
  scenario requires.
- The digest anchor in the patch is derived from the accompanying digest
  source; regenerate it for each new case rather than copying a value from
  another case.
- The assertions check the specific error identifier and that the failure is
  attributed to the create-plan step status — not merely a non-zero exit.

### Version bump (FR9)

`em-workflow/.claude-plugin/plugin.json` `version` becomes 0.1.35. The root
`.claude-plugin/marketplace.json` has no `version` field for this plugin and
must not be touched. Existing version assertions compare against a fixed
pre-feature baseline (strictly greater), so no test needs updating for the
bump itself.

## Test Notes

- The regression is deliberately fixture-driven rather than inline: the fixture
  discovery mechanism already gives every new case directory a second,
  independent check via the generic sweep, and the per-group coverage test
  expects each group to hold both valid and invalid cases.
- AC-5 is the "test can fail for the right reason" guard. Assert on the set of
  reported error identifiers, not just their count.
- The existing `pending` case is exercised today only as part of a combined
  both-operations test; AC-4 wants a scenario-named assertion so a future
  change to that combined test cannot silently drop the `pending` branch.
- Keep the new fixtures minimal — one task entry at most, no phase-state
  companion (the idempotency check is a different scenario), no registries
  directory unless the vocabulary checks require it.
- Requirement coverage: AC-2 → TS-3; AC-3/AC-4/AC-5 → TS-4; AC-1/AC-6/AC-7 →
  TS-5.
