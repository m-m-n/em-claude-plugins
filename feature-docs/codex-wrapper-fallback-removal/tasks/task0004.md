## Design

### The bump

Both plugins changed under this feature, so both are bumped, and each value is
written identically in the plugin's own manifest and in the marketplace entry
for that plugin. The marketplace entry is located by its name field; entry
order in the registry is not a contract.

Bumping is not optional housekeeping here: an installed plugin is cached by
version, so a version left standing means the shipped code never reaches
users' caches even though the repository is correct.

### The ripple (IMPLEMENTATION.md D5)

Four existing test modules assert the em-review marketplace version equals a
literal that was current when each of them was written — the value this
feature moves. They fail the moment em-review is bumped, and no amount of care
in the other three tasks prevents it.

Each of those assertions was written to prove "my feature's bump did not spill
into the neighbouring plugin". That intent cannot survive literally once a
later feature bumps em-review on purpose, so the repair restates it in the
form that does survive: the neighbouring plugin's version is not below the
baseline that module captured, compared on parsed numeric components rather
than on the raw string. Re-pinning the new literal is prohibited — it
reproduces exactly this breakage at the next em-review bump, which is the
failure mode the repository already recorded once.

Where a module derives forged samples from the pinned value to prove its
matcher rejects a drifted version, the forged sample must stay outside the
accepted range after the repair, otherwise the negative proof becomes vacuous.

The em-workflow side needs no repair: every em-workflow version assertion in
the suite is already baseline-relative and keeps passing across this bump.

### New module design

The new module asserts, for each plugin independently: the manifest version
parses as three numeric components; it is strictly greater than that plugin's
pre-feature baseline at the patch component with major and minor unchanged;
and the marketplace entry located by name carries the identical string. It
also asserts the name-based lookup fails loudly when the entry is absent, and
keeps a negative proof per matcher against forged data plus a well-formedness
guard on the forged sample.

## Test Notes

- Every criterion is a static assertion over two JSON files plus the four
  repaired modules; the suite run itself is AC-6.
- Write AC-4's repairs before performing the bump: with the repairs in place
  the four modules pass both before and after the bump, which is the cleanest
  demonstration that the repair is a generalization rather than a re-pin.
- Comparison is on parsed numeric components, never on the raw string: a naive
  string comparison orders a two-digit patch component wrongly, and this
  feature's em-workflow value is exactly the kind of value that exposes it.
- Edge case worth covering: a forged entry whose name matches but whose
  version is malformed must fail the parse assertion rather than silently
  satisfying an equality check.
