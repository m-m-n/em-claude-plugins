# Task Plan: task0003 — Batch protocol docs: drop the fallback-provider audit item

## Goal

The batch reporting list and the audit-record obligation stop requiring a run
to record whether a fallback provider answered, while every description of the
orchestrator's chain walk, the routing table and the Opus escalation stays
exactly as it is.

## Design

### What is removed and what is not

The clause being removed appears in both documents as one item in a list of
things a batch run must report or persist about an autonomous resolution. It
is removed because it asks a question that has no answer once the wrapper
launches one process: there is no fallback provider to have answered.

Each of the surrounding clauses — the gate, the option chosen, the options not
chosen, the discussion's key points, whether Codex was consulted, and whether
the Opus escalation ran with its reasoning — stays. The list keeps its item
structure: the removed clause lives inside one item's parenthetical, so the
number of items, the item order, and the source map that pairs each item with
its persisted location are all unaffected.

Also untouched, in every document this task reads: the orchestrator's chain
walk over the reviewer registry, the `rate_limited` / `budget_exhausted` /
`harness_unavailable` routing table, and the Opus escalation prose
(IMPLEMENTATION.md, Removed-phrase vocabulary).

### The superseded SPEC

`feature-docs/batch-codex-autonomous-decisions/SPEC.md` records a decision that
this feature reverses. It is left exactly as it is — no edit, and specifically
no note saying it has been superseded. The cost of that choice is that a later
reader may mistake it for current requirements; the choice is deliberate
(SPEC A4). This task owns the guard that the file stays untouched
(IMPLEMENTATION.md D6): a positive assertion that its superseded requirement
and test-scenario entries are still present, plus an assertion that it
contains no reference to this feature's name (which is what a supersession
note would introduce).

### Test module design

Static text checks, section-scoped rather than whole-file:

1. In each owned document, the removed clause is absent from the section that
   carried it, and the surviving clauses of the same list are all present —
   asserted individually, so a bulk deletion that takes a neighbour with it
   fails here.
2. The routing-table rows and the chain-walk description are present with
   their existing wording.
3. The superseded SPEC still carries its own requirement and test-scenario
   entries, and does not mention this feature's name.
4. No provider or model identifier and no usage-limit detection description
   appears in either owned document.

Every matcher gets a negative proof against forged text, and the forged sample
is itself shown to be well-formed so the proof exercises the comparison rather
than a parse failure.

## Test Notes

- All criteria are static text assertions over repository files; no subprocess
  and no stub is needed.
- TDD-awkward point: AC-2 and AC-4 are preservation criteria, which pass
  trivially before the edit. Their value is as regression guards for the edit
  itself, so write them together with AC-1 and confirm AC-1 is red first —
  that red state proves the section slicing actually reaches the clause.
- The reporting sentence is asserted in a whitespace-normalized form because
  the source file wraps it across lines; keep that normalization when updating
  the constant, or the update will look correct and fail on the line break.
- Edge case: the word "fallback" occurs legitimately in both owned documents
  (the unlisted-gate fallback, the Claude fallback). AC-1 must be scoped to
  the removed clause's own wording, never to the bare word.
