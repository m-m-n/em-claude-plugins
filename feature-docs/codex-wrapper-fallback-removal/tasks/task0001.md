# Task Plan: task0001 — Wrapper: one invocation, no provider chain

## Goal

`em-workflow/scripts/run_codex_exec.sh` launches `codex exec` exactly once on
every outcome, passing through that single run's exit code and output
unchanged, with the superseded chain test module replaced by one that pins the
no-fallback contract.

## Requirements

FR1, FR2, FR3, FR6, FR7, NFR1, NFR2, NFR3, NFR5

## Scope

### Files to Create
- `tests/test_codex_wrapper_single_invocation.py` — the replacement wrapper
  test module: records every launch of a stubbed external command and pins the
  single-invocation contract, the output ordering, and the timeout path.

### Files to Modify
- `em-workflow/scripts/run_codex_exec.sh` — delete the provider chain and
  every construct that exists only to serve it, including the header comment
  blocks that describe it; keep every other behaviour byte-equivalent.
- `tests/test_codex_wrapper_provider_fallback.py` — delete this file. It makes
  the chain's existence its contract, so it cannot be repaired in place.

## Design

### What the wrapper must be after this task

Read the Wrapper caller-facing contract row in IMPLEMENTATION.md Shared
Components; that row is the contract, and this section only names what is
removed and what is preserved in reaching it.

**Removed** — every construct below exists only to serve the chain, and none
of them has a caller once the chain is gone:

| Existing construct | Why it goes |
|---|---|
| The second and third entry-argument arrays and their provider-name constants | There are no further entries to launch |
| The fallback profile path constant and the prerequisite predicate | Nothing gates an entry that no longer exists |
| The usage-limit and provider-error response recognizers | Response shape is no longer a control-flow input at all (NFR3) |
| The answering-entry variable and every branch reading it | There is exactly one launch, so it has nothing to distinguish |
| Both marker emissions (the "a later entry answered" line and the "not configured" line) | Neither event can occur |
| The header comment blocks describing the chain, the switch-shape stream, the environment prerequisites, and the entry-1 marker rule | They describe removed behaviour (FR7's wrapper share) |

**Preserved, behaviour-for-behaviour** — the temporary-file pair and its
cleanup on exit, the separate redirection of the single launch's stdout and
stderr into them, the final concatenation in stdout-then-stderr order, the
timeout diagnostic line and its exit code 124, exit-code pass-through, the
redirection of stdin from the null device, the guard that keeps a non-zero
exit from terminating the script before the diagnostic is written, every
pass-through flag the launch already carries, and the whole argument-handling
surface including its usage and error messages.

Whether the single launch keeps living inside a helper or is inlined is the
implementer's choice; the contract constrains observable behaviour, not
structure. The chain's removal must not turn into a rewrite of the argument
parser.

### Processing flow after this task

1. Read the configured timeout from the configuration file next to the script.
2. Validate the mode argument; derive the sandbox selection, the reasoning
   effort selection, and the prompt constraint text from it.
3. Consume the optional working-directory and output-schema flags; reject an
   unknown flag or a flag missing its argument with the existing message.
4. Take the remaining argument as the prompt; prepend the mode's constraint
   text when the mode defines one.
5. Launch the external command exactly once under the timeout, with stdin from
   the null device, stdout captured to one temporary file and stderr to the
   other; record its exit status without letting a non-zero status terminate
   the script.
6. When the status is the timeout status: concatenate both captures to the
   caller, write the timeout diagnostic naming the configured timeout to
   stderr, and exit with the timeout status.
7. Otherwise: concatenate both captures to the caller and exit with the
   recorded status.

There is no step that reads either capture to decide what to do next. That
absence is the task's point.

### Test module design

The module drives the real script as a subprocess with a stubbed external
command first on `PATH`, an isolated `HOME`, and an append-only log the stub
writes one record per launch into. The stub's behaviour per run is selected
through the environment, covering: a usage-limit diagnostic on stderr with a
non-zero exit, a provider-error diagnostic on stderr with a non-zero exit, the
same switch-shaped text on stdout only, a schema-shaped reply on stdout with a
multi-line banner on stderr, an unrelated non-zero exit, and a run that
outlives the configured timeout.

Two constraints follow from IMPLEMENTATION.md:

- **Configured-timeout read rule**: the timeout case must not wait for the
  production value and must not assert a hard-coded number. Exercise it
  against an isolated copy of the script paired with a reduced configured
  value, and assert the diagnostic names exactly that reduced value; assert
  separately that the diagnostic's wording is the one the production script
  emits. The literal production value belongs to task0002, not here.
- **Non-vacuity**: each matcher gets a negative proof — in particular, the
  launch-count matcher must be shown to fail against a forged two-launch log,
  otherwise "exactly one launch" could pass on a broken reading of the log.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, NFR2): with the stub emitting a usage-limit diagnostic on
      stderr and exiting non-zero, the launch log holds exactly one record,
      the wrapper exits with the stub's own exit code, and the stub's stderr
      text reaches the caller verbatim.
- [ ] AC-2 (FR1): the same holds with a provider-error diagnostic, and also
      with a usage-limit diagnostic while the former prerequisites (the proxy
      credential in the environment and the profile file under the isolated
      `HOME`) are both present — the prerequisite gate no longer exists and
      configuring it changes nothing.
- [ ] AC-3 (FR1, NFR3): under every stub behaviour above, no output line
      begins with either fallback marker prefix, and neither prefix string
      occurs anywhere in the script's text. A switch-shaped text present only
      on the stub's stdout produces exactly one launch and an outcome
      identical to the unrelated-error case.
- [ ] AC-4 (FR2): with a schema-shaped reply on stdout and a multi-line banner
      on stderr, every byte of the stdout content precedes every byte of the
      stderr content in the wrapper's combined output, and the script's text
      contains no combined-stream redirection on the launch.
- [ ] AC-5 (FR3): a stub that outlives the configured timeout produces exit
      code 124 and a stderr diagnostic naming the configured timeout in
      seconds; an unrelated non-zero exit surfaces with its own exit code and
      its own output, with no diagnostic added.
- [ ] AC-6 (FR3): the argument-handling surface is unchanged — invalid mode,
      missing prompt, unknown flag, and each optional flag missing its
      argument each produce the same message and non-zero exit as before this
      task, and the accepted flag set on the launch is unchanged.
- [ ] AC-7 (FR6): `tests/test_codex_wrapper_provider_fallback.py` no longer
      exists, and the replacement module covers AC-1 through AC-5.
- [ ] AC-8 (NFR5): both project test commands pass in this worktree, and the
      new module imports only the standard library and touches no network, no
      real provider, and no location outside its own temporary directories.

## Test Notes

- AC-1 / AC-2 / AC-3 / AC-4 / AC-5 / AC-6 are subprocess-level integration
  tests against the real script — they are the only honest way to pin a shell
  script's observable contract. AC-7 is a file-existence assertion. AC-8 is a
  static import check plus the suite run.
- TDD-awkward point: the timeout case. Waiting the production timeout is not
  an option, and asserting a literal would couple this task to task0002's
  value. Resolve it with the isolated-copy-plus-reduced-value approach in the
  Design above, which keeps the assertion behavioural rather than numeric.
- Write the tests first: the replacement module should be red against the
  current chain-carrying script (it will record three launches where it
  expects one), then green after the removal. That red state is the proof the
  module actually tests the chain's absence.
- Edge case worth covering: a stub that writes to stdout AND exits non-zero
  must still deliver the stdout content to the caller — the failure path is
  not permitted to discard the capture.
