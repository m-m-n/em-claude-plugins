## Design

### Cause

`TestPerTargetCaseTable.test_the_cases_come_after_every_other_case` asserts
that the positions of the cases labelled `mixed-rm-self-config-deny TS-` are
exactly the positions from the first such case to the last case of the table.
A later feature (`mcp-bridge-exec-tool-rescan`) appended its cases after that
run, as the table's append-only rule asks, so the run is no longer the end of
the table and the assertion fails. The failure reproduces at
`implement.base_commit` and on `main`; it does not come from this feature's
diff. The case table itself is correct and is not changed.

### Ordering check (module level)

| Item | Contract |
|---|---|
| Input | A case table (a list of cases, each with its label as the second element), the label prefix of the per-target feature, the label prefix of the earlier feature (`FEATURE`), and the count of cases that existed before the earlier feature (`PRE_EXISTING_CASE_COUNT`). All are parameters, so the check runs on small synthetic tables as well as on the real table |
| Selection | A case is a per-target case when its label begins with `mixed-rm-self-config-deny TS-`; a case is an earlier-feature case when its label begins with the earlier feature's name and one space, the selection `feature_case_positions` already makes |
| Conditions | (1) at least one per-target case exists; (2) the per-target positions are consecutive, one run; (3) the first per-target position is at or after the pre-existing count; (4) the first per-target position is after every earlier-feature position |
| Not a condition | What follows the run. Any number of cases with other labels may come after the last per-target case |
| Output | The list of violated conditions, each naming its condition number and the positions involved; empty when every condition holds |

`TestPerTargetCaseTable`'s ordering test applies this check to the real table
and asserts that no condition is violated, with the violations as the failure
message. The class docstring describes the cases as one run after the earlier
feature's cases, not as the last cases of the table.

### What stays

Every other test method of the module keeps its assertions, including
`test_none_of_the_cases_joins_the_earlier_features_run`,
`test_the_earlier_features_ts_15_case_is_changed_in_place` and the
`TestCaseTable` checks of the earlier feature. The hook, the runner and the
case table are not touched; `.claude/rules/hook-tests.md` forbids removing an
existing deny / ask case, and this task removes, reorders and edits no case.

## Test Notes

AC-1 to AC-3 are unit tests of the ordering check over small in-memory
tables; build the labels from the same prefixes the module already defines so
the selection is exercised, and pass a small pre-existing count. Write them
first: AC-2 and AC-3 must fail against a check that is not yet written, and
AC-1 must fail against the current "run reaches the end of the table"
condition, which is the negative proof that the old condition rejected a
legitimate table. AC-4 is the real-table test. AC-5 can be confirmed with a
read-only git diff against `implement.base_commit`. The full suite runs hook
subprocesses already; do not add repetition or load to it.
