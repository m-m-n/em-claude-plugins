# Task Plan: task0002 — Behavior test of the derived plan path against a backslash decoy

## Goal

A new unittest module shows, against the unchanged validator, that the plan
path derived as IMPLEMENTATION.md's "Plan path resolution" states is the file
the validator's `_resolve_contained_relative_path` reads, for both backslash
spellings of the plan value, and is never a decoy whose literal name is
`\task0003.md`.

## Requirements

FR1, FR4, NFR2, NFR3

## Scope

### Files to Create
- `tests/test_plan_path_backslash_binding.py` — behavior test of the attack scenario (SPEC.md AC-4) and of the spellings the validator binds (FR4)

### Files to Modify

None.

## Design

### Components of the test module

| Component | Responsibility | Contract |
|---|---|---|
| Validator loader | Makes the validator's functions available to the tests | Loads `em-workflow/scripts/validate-worker-output.py` by file path, in the way `tests/test_final_path_correction.py` loads it, and leaves no compiled file under `em-workflow/` |
| Documented derivation | Encodes IMPLEMENTATION.md's "Plan path resolution" | Input: a feature directory and a stored plan value. Output: the feature directory joined in order with each segment the validator's `path_segments` returns for the value. It does not call `_resolve_contained_relative_path`, so the comparison is between two independent computations |
| Pre-fix derivation | The negative-proof sample | Input as above. Output: the feature directory joined with the stored string as-is |
| Decoy fixture | The attack scenario of SPEC.md AC-4 | In a fresh temporary directory, `feature-docs/{feature}/tasks/` holds `task0003.md` with the text the validator's `canonical_correction_plan` renders for task0003 (one file, one correction), and a regular file whose literal name is `\task0003.md` with different, instruction-like text |

### Flow of the main case

1. Build the decoy fixture.
2. For each backslash plan value (`tasks/\task0003.md` and `tasks\task0003.md`,
   each holding one literal backslash character), compute the documented
   derivation and ask `_resolve_contained_relative_path` to resolve the same
   value under the same feature directory.
3. The validator admits the value (no rejection message), the two paths are
   equal, the path names the same file as `tasks/task0003.md`, reading it
   gives the canonical text, and it does not name the decoy.

### Negative proof

The pre-fix derivation of `tasks/\task0003.md` names the decoy and reads the
decoy text; the pre-fix derivation of `tasks\task0003.md` names an entry that
does not exist. The checks of the main case, applied to the pre-fix
derivation, report a failure, which shows the main case can detect the attack.

### Spellings the validator binds (FR4)

For `tasks/task0003.md`, `./tasks/task0003.md`, `tasks//task0003.md`,
`tasks/./task0003.md` and both backslash spellings, the documented derivation
equals the validator's resolution, and `_plan_is_bound_to_task_md` reports the
value bound for task0003. This records that the fix does not narrow what the
validator binds.

### Platform

A literal backslash in a file name is possible where backslash is not a path
separator (Linux, macOS). Where it is a separator, the cases that need the
decoy skip with a stated reason; the other cases still run.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TM-1, SPEC.md AC-4): With the decoy fixture and plan value `tasks/\task0003.md`, the documented derivation equals the path `_resolve_contained_relative_path` returns for that value under the same feature directory (which admits it), names the same file as `tasks/task0003.md`, reads the canonical text, and does not name the decoy.
- [ ] AC-2 (TM-1, SPEC.md AC-4): With the decoy fixture and plan value `tasks\task0003.md`, the documented derivation equals the validator's resolution, names an existing regular file that is `tasks/task0003.md`, reads the canonical text, and does not name the decoy.
- [ ] AC-3 (TM-1): The pre-fix derivation of `tasks/\task0003.md` names the decoy and reads its text, the pre-fix derivation of `tasks\task0003.md` names no existing entry, and the checks of AC-1 and AC-2 applied to the pre-fix derivation report a failure.
- [ ] AC-4 (FR4): For `tasks/task0003.md`, `./tasks/task0003.md`, `tasks//task0003.md`, `tasks/./task0003.md`, `tasks/\task0003.md` and `tasks\task0003.md`, the documented derivation equals the validator's resolution, and `_plan_is_bound_to_task_md` reports each value bound for task0003.
- [ ] AC-5 (NFR2): The module imports only standard-library modules, creates every file inside a temporary directory that is removed after the test, leaves no compiled file under `em-workflow/`, and skips the decoy cases with a stated reason on a platform where backslash is a path separator.
- [ ] AC-6 (NFR2, FR4): `python3 -m unittest discover -s tests` passes in full, and `em-workflow/scripts/validate-worker-output.py` and `tests/test_final_path_correction.py` are unchanged.

## Test Notes

AC-1 to AC-4 are integration tests over a temporary directory. AC-3 is the
negative proof of AC-1 and AC-2; keep the main-case checks in one helper so
the same helper is applied to both derivations. File identity is checked as
"same file on disk", not only as equal path text. The stdlib-only part of
AC-5 can be pinned by a test that parses the module's own imports, the way
`tests/test_final_path_correction_docs.py` pins its own. Write the tests
first; they should pass against the unchanged validator once the documented
derivation helper exists, and the negative proof should fail when the main
helper is pointed at the pre-fix derivation.

## Out of Scope

- The phase documents and their docs tests.
- Any change to the validator, including any rule that rejects a
  non-canonical spelling.
- Edits to existing test modules, and every other file outside the Scope
  lists.
