# Task Plan: task0001 — Read task status from direct-child keys only

## Goal

The Stop hook's status reader takes each task's status only from a `status:` key at the task block's direct-child indentation, so lines inside block-scalar bodies (including the untrusted `notes` text) and inside nested mappings can no longer set the status the hook acts on.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create
- `tests/test_queue_stop_guard_task_status_direct_key.py` — new tests for this task's acceptance criteria (subprocess runs of the Stop hook and direct calls of the status reader)

### Files to Modify
- `em-workflow/hooks/queue_stop_guard.py` — restrict the task status reader to direct-child keys

## Design

### Changed contract: `task_statuses_from_workflow`

- **Signature and result shape**: unchanged — it takes the workflow.yaml text it takes today and returns a mapping from task id to status string.
- **Input lines**: the task block lines produced by `iter_task_block_lines`, which this task does not modify (NFR5, A3).
- **Postconditions**:
  1. The direct-child indentation of a task block is the indentation of the first line in that block that is neither blank nor a comment line (A1). A comment line placed before the first key therefore never shifts it.
  2. Only lines whose indentation equals the direct-child indentation exactly are status candidates. Deeper lines — block-scalar bodies of every header form (literal or folded, with or without chomping and indentation indicators) and the lines of nested mappings — are never candidates, whether the direct `status:` key comes before them, after them, or not at all (FR1, FR2, FR3).
  3. The first direct-child line carrying the status key decides the task's status (FR4, A5).
  4. A task with no direct-child status key, or whose direct status value cannot be extracted, is omitted from the result (FR4, A5).
  5. Any task-block content, however malformed, is handled without an uncaught exception; content the reader cannot interpret yields no status for that task (NFR2, TM-1 and TM-2 in THREAT-MODEL.md).

### Processing flow (per task block)

1. Take the block's lines from the unchanged block iterator.
2. Find the first line that is neither blank nor a comment; its indentation is the direct-child indentation. When no such line exists, the task has no status and is omitted.
3. Scan the block's lines in order, skipping every line whose indentation differs from the direct-child indentation.
4. At the first remaining line that carries the status key, extract its value. Record it when extractable; otherwise omit the task. Stop scanning the block either way.
5. Return the mapping. `evaluate_feature` consumes it unchanged, and its three-condition exclusion is not altered (FR4).

### Constraints

- Keep the names `task_statuses_from_workflow`, `TASK_STATUS_RE` and `TASKS_SECTION_RE` (NFR3). If the pattern held by `TASK_STATUS_RE` changes, confirm that every other reader of it keeps its current behaviour (NFR5).
- Leave `iter_task_block_lines` and `task_routeback_records_from_workflow` unmodified (NFR5, A3).
- Import standard-library modules only; no YAML library (NFR1).
- Keep the module docstring wording pinned by the existing module-docstring test (NFR4).
- Keep the hook fail-open: unreadable or garbled workflow.yaml / journal input ends with exit code 0 and no traceback (NFR2).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR2, TM-1): Fixture — a task block carrying `routeback_failed_journal_line: 1` and a `notes` block scalar whose body contains `status: pending` indented deeper than the direct keys, with no direct-child `status:` key; journal line 1 is that task's `failed` event. For each block-scalar header form `|`, `>`, `|-`, `|+` and `|2`, running the Stop hook as a subprocess ends with exit code 0 with no BLOCK on stderr, and `task_statuses_from_workflow` omits the task.
- [ ] AC-2 (FR1, FR2): The AC-1 fixture (`|` form) plus a direct-child `status: failed` placed after the notes block scalar makes the Stop hook end with exit code 0, and `task_statuses_from_workflow` returns `failed` for that task.
- [ ] AC-3 (FR3): A task block with no direct-child `status:` key and a nested mapping under a direct key (for example a `meta` key) whose child line is `status: pending` is omitted by `task_statuses_from_workflow`; with the AC-1 route-back record and journal, the Stop hook ends with exit code 0.
- [ ] AC-4 (FR1, FR4, TM-1): With the AC-1 route-back record and journal and a notes body containing `status: failed`, a direct-child `status: pending` placed before the notes block scalar, and separately one placed after it, each makes the Stop hook end with exit code 2 and name the task in its `launch=` output. A comment line placed before the block's first key, at an indentation different from the direct keys, does not change this: `task_statuses_from_workflow` still returns `pending` for the task.
- [ ] AC-5 (NFR2, TM-2): For task blocks with crafted content and no direct-child `status:` key — a block made only of blank and comment lines, a block whose first key is itself a `notes` block-scalar header, a block-scalar header followed by unexpected trailing characters, and a block-scalar body that reaches the end of the file without a final newline — the Stop hook ends with exit code 0 and writes no traceback to stderr, and `task_statuses_from_workflow` returns without raising and omits the task.
- [ ] AC-6 (FR4, NFR1, NFR3, NFR4, NFR5): `tests/test_queue_stop_guard.py`, `tests/test_queue_stop_guard_routeback_record.py` and `tests/test_queue_hook_status_read_pin.py` pass without modification under `python3 -m unittest discover -s tests`; the hook still imports only standard-library modules; the three identifiers named in Constraints keep their names; `iter_task_block_lines` and `task_routeback_records_from_workflow` are unmodified.
- [ ] AC-7 (FR1, FR2, FR3): The tests for AC-1 to AC-5 live in `tests/test_queue_stop_guard_task_status_direct_key.py` and are collected by `python3 -m unittest discover -s tests`; the tests for AC-1 (`|` form), AC-2 and AC-3 fail when run against the base revision's hook.
