# Task Plan: task0004 — R4/R5 triage timing: no auto-apply, once per phase

## Goal

`review-phase.md` states that dependency updates are never auto-applied, and
that turning unresolved `vulnerability` findings into human-triageable tasks
happens exactly once per review phase — immediately before the final round's
R5 — with the "final round" determined by a deterministic signal that can
neither drop the filing after an abnormal termination nor fire in a
non-final round.

## Design

All edits are additive (IMPLEMENTATION.md, Conventions → "Protocol edits are
additive").

### R4 — `vulnerability` is never auto-applicable (FR10)

The classification section states that a `vulnerability` finding is never
classified auto-applicable and always lands on the needs-judgment side. Two
independent reasons are stated, so neither alone is load-bearing: the
protocol forbids it, and axis 2's `suggestion` is prose by contract
(IMPLEMENTATION.md D4), which the existing shape probe already routes to the
needs-judgment path. No dependency update, lockfile edit or package
installation is ever dispatched to an editor.

### R4 → R5 boundary — triage filing, once per review phase (FR11, FR24)

A new sub-section placed immediately before Phase R5 states:

1. **What runs**: the orchestrator invokes the filing subcommand of
   `em-workflow/scripts/scan-dependencies.py` (IMPLEMENTATION.md, Shared
   Components "`file-tasks` subcommand"), passing the project root, the
   feature, the unresolved `vulnerability` findings, and the
   notion-task-dispatch entry point IF R0's probe found one. Selecting which
   findings are "unresolved" is the orchestrator's job (resolution other than
   fixed, category `vulnerability`); the script never re-decides it.
2. **When it runs**: exactly once per review phase, immediately before the
   final round's R5. The deterministic signal is the round's closing
   disposition, defined in IMPLEMENTATION.md D3 and restated here in protocol
   terms: computed after R4's loop termination and before the round record is
   written, from values the orchestrator already holds (residual
   critical/high count, the report-only flag, the loop termination reason,
   the batch rework counter). Filing runs iff the disposition is not
   "another round".
3. **Why neither failure mode can arise**: a non-final round always yields
   the "another round" disposition, so filing cannot fire early; a run that
   dies before R5 wrote no round record, so the resumed round recomputes the
   same disposition and files then — safely, because the filing path is
   idempotent under its own package-name duplicate detection.
4. **The receipt**: Phase R5's round record gains a root field recording
   whether triage filing ran this round, which branch was taken (external
   task system or report), and the packages filed / appended to / suppressed
   as duplicates, plus the report path when the report branch ran. The field
   is present and empty when the disposition was "another round". This is
   disclosure and audit only: it introduces no new gate identifier and never
   affects the completion gate.

The branch between filing and report is decided mechanically from R0's probe
result — no question is put to the user, in either interactive or batch mode.
