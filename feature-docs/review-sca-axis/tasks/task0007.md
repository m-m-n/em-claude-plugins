listing with zero tasks files, only a genuinely unobtainable listing degrades
to the report — and neither one malformed finding nor a mid-batch external
failure destroys the rest of the run's work or the record of what it already
did.

## Design

### The listing outcome is three-valued, not two

Today a successful listing carrying zero valid entries and a listing that
could not be obtained both collapse to the same "no listing" value, and the
caller reads any such value as unavailable. Zero tasks is the NORMAL first-run
state and must reach the filing branch.

The listing call returns an outcome that distinguishes:

- **available** — the entry point ran, exited successfully and produced a JSON
  array. The validated entry set may be empty; empty is a legitimate value,
  not an error. Entries dropped item-wise by validation while others survive do
  not make the listing unavailable; the dropped count is carried on the outcome
  and surfaced in the summary.
- **unavailable** — one of exactly the conditions IMPLEMENTATION.md D6 already
  names: the entry point fails its validity check, the process cannot be
  launched, it exits non-zero, its stdout is not JSON, or the JSON is not an
  array. Each condition carries its own machine-stable reason.

D6 is unchanged by this task: `unavailable` still degrades to the report
branch and still says so in the report. What changes is that `available` with
an empty set no longer takes that path.

### Poison-finding policy: skip and record

Grouping isolates each finding. A finding whose title violates the
IMPLEMENTATION.md "Finding text-encoding contract" is skipped, recorded with
its position in the input and a machine-stable reason, and never aborts the
grouping of the remaining findings. The recorded set travels on the returned
summary, and into the report body when the report branch runs. A batch in
which EVERY finding is malformed still returns the documented summary — with
empty filed / appended / suppressed sets and a non-empty malformed set — never
an exception.

The malformed reason string is derived from this script's own contract text,
never from the offending title: advisory-sourced text stays inside the
truncation discipline and never becomes part of a reason identifier (NFR4).

### Partial progress survives a mid-batch failure

The per-package loop records each package's outcome as it completes. When the
external task system fails on a package, the loop stops there but the function
still returns the documented summary dict, carrying the packages already filed
and appended before the failure, a machine-stable failure reason, and the
package the failure occurred on. Every key the summary already documents
(`branch`, `filed_packages`, `appended_packages`, `suppressed`, `report_path`,
`degraded`, `degraded_reason`) keeps its name and meaning — new keys are ADDED,
never substituted — so the round record's triage-filing receipt mapping still
holds (IMPLEMENTATION.md D8).

A run that produced a summary object exits 0, as the script's existing error
policy requires for a produced result; the human-readable failure reason also
goes to stderr. A retry after a partial failure re-derives what is still
outstanding from the listing, so packages already filed are suppressed by the
existing duplicate detection rather than re-filed (FR15/FR16).
