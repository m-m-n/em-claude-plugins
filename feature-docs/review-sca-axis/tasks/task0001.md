# Task Plan: task0001 — Scanner registry, scan/normalize path, and the result-schema contract

## Goal

Axis 2 can detect known vulnerabilities in the reviewed change's dependency
ecosystems and emit them as one schema-conforming review-result object — with
a machine-stable skip when the ecosystem's tool is not installed — and the
review-result schema admits that object's `tool` source and `vulnerability`
category.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR21, FR22, NFR2, NFR3, NFR4, NFR7

## Scope

- `em-workflow/scripts/scan-dependencies.py` — co-owned with task0005; this

- `tests/test_reviewer_roles_protocol.py` — the FROZEN_SOURCE_ENUM pin
  update, one line.

## Design

### Registry (`vuln-scanners.yaml`)

Data only, no conditionals. Follows `reviewers.yaml`'s SSOT conventions: a
header comment stating the responsibility split (this file owns WHICH tool
serves which manifest and WHERE the threshold sits; the script owns HOW to
run it and how to normalize), and a top-level `version` key. Per ecosystem it
carries: the manifest filenames that select it, the executable name to look
for on PATH, the argument form that produces machine-readable output while
only READING the existing lockfile, the mapping from that tool's severity
vocabulary onto the schema's `critical` / `high` (everything else is below
threshold), and the two threshold facts (direct dependencies only, severity
high and above). Ecosystems covered: npm, cargo, pip, go.

### Result-schema contract

This task owns `review-output-schema.json` and the frozen pin that guards it.
The edit is additive and byte-scoped:

- the root `source` enum gains `tool`, appended after `litellm`;
- the finding `category` enum gains `vulnerability`, appended after
  `license`;
- nothing else in the schema document changes — both `required` lists, both
  `additionalProperties: false` flags and the `severity` enum stay
  byte-identical.

The existing frozen pin asserts exact equality against the three-value source
enum and therefore fails the moment the schema changes; it becomes the
four-value list in the same change. The category-side pin in that module is a
membership assertion and needs no edit; no other assertion in that module
changes.

The new pin module states the invariance side explicitly, so a later widening
of the schema cannot pass unnoticed: the two enums must contain the new
values AND the untouched parts must still match their pre-change content.

### `scan` flow

1. Reduce the caller's changed-file list to the set of manifests the registry
   recognises; from that, the set of ecosystems to scan. No manifest in the
   change ⇒ nothing to scan ⇒ an empty, non-skipped result.
2. For each selected ecosystem, resolve its executable on PATH. Not
   resolvable ⇒ this run is a SKIP: `skipped` true, a machine-stable
   `skip_reason` identifying the missing tool, `findings` empty. No model is
   consulted, no substitute is attempted, no package is installed (FR3, FR8).
3. Run the registry's command form against the existing lockfile from the
   project root. Nothing on this path writes inside the project root: no
   install, no lockfile rewrite, no formatter (NFR2).
4. Normalize each advisory the tool reports: apply the threshold FIRST
   (direct dependency, severity high or above — IMPLEMENTATION.md D5), then
   build a finding per IMPLEMENTATION.md "Finding text-encoding contract".
   `suggestion` is prose and never diff-shaped (D4). Every advisory-sourced
   string passes through the truncation helper (untrusted discipline).
5. Emit exactly one object with `source: "tool"`, every finding
   `category: "vulnerability"`.

Tool-execution failure that is not "tool absent" (non-zero exit with
unparseable output, unparseable machine-readable output) is reported as a
skip with its own machine-stable reason — never as an empty successful scan,
which would silently claim the ecosystem is clean.

### Co-ownership

`scan-dependencies.py` is created by this task AND by task0005. Register both
subcommand names; implement `scan` fully; supply `file-tasks` as the
clearly-marked placeholder IMPLEMENTATION.md's "Module co-ownership skeleton"
defines, and honour the symmetric merge duty stated there. That skeleton is
the ONLY shared-file arrangement in this task — the schema and the frozen pin
have no second writer.

## Test Notes

- Unit-level: AC-1 through AC-7 are all reachable without any SCA tool
  installed — the tool's output samples are fixtures embedded in the test
  module, and the execution boundary is exercised by pointing PATH at a
  temporary directory (empty for AC-5, holding a stand-in executable that
  prints a fixture for AC-3/AC-4).
- AC-8 and AC-9 are pure document assertions in their own module. AC-9's
  "unchanged" is asserted against the literal expected structures rather than
  a hash of the whole file, so a legitimate enum addition does not make the
  assertion useless while a change to `required` / `additionalProperties` /
  `severity` still fails. One negative case is worth writing: an input where
  `tool` was added by REPLACING an existing value must fail AC-8, which means
  asserting full expected membership rather than just the presence of `tool`.
- The scan test module loads the script by file path (its name contains a
  hyphen); every new module's own imports stay standard-library only. Schema
  conformance in the test is a structural assertion written against the
  schema document, not a third-party validator.
- AC-7's "leaves the file state unchanged" is checked by comparing the
  porcelain status of a disposable temporary repository before and after.
- TDD-awkward: the real network-touching tools are never invoked by the
  suite. That is deliberate — determinism (NFR3) is a property of the
  normalization path, which is what the tests pin.

## Out of Scope

- The `file-tasks` subcommand's behaviour (task0005).
- Any protocol text in `review-phase.md` (task0003 / task0004) — this task
  states nothing about WHEN it runs.
- Adding `vulnerability` to `reviewers.yaml` (explicitly forbidden, FR8).
- Widening `severity`, `required` or `additionalProperties` for any reason.
- SAST or any non-dependency scanner; ecosystems beyond npm / cargo / pip /
  go; auto-applying or proposing dependency upgrades as diffs.
