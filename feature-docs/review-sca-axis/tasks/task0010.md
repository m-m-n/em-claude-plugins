## Goal

The pip ecosystem's registry entry carries the argument form the plan and the
existing test pins already fix, so pip command assembly and pip scan-job
construction produce their pinned argument vectors again and
`python3 -m unittest discover -s tests` exits 0.

FR1, FR4, FR20, NFR2

Rework task. `origin_kind: verify`, `origin_id`: `AC-22`, `TS-26`, `TS-1`.

nine suite failures are comparisons against those two tokens.

## Design

### What the pinned form is, and where the drift entered

FR1 names the pip command as `pip-audit --format json`. The registry's `args`
are appended AFTER the `target_flag`'s value (the registry header states this
ordering), so the constructed pip job's argument vector is
`<absolute pip-audit> -r <changed requirements path> --format json` for a
changed requirements file and `<absolute pip-audit> <target directory>
--format json` for a changed `pyproject.toml` or lockfile — the two forms
task0008's AC-1 fixed and TS-26 exercises.

The pip entry's `args` currently carries two further tokens beyond that form.
Every one of the nine failures is a comparison against them: the ecosystem/
command-assembly pin in `tests/test_sca_scan_normalization.py`, the per-manifest
target pins in `tests/test_sca_scan_invocation.py`, and that module's
no-install / no-resolution-artifact pin, whose forbidden-token list names one of
the two.

### The restore is data-only

`em-workflow/scripts/scan-dependencies.py` assembles the command from the
registry; it needs no change, because it already produces the pinned vector for
the pinned `args`. No test module is touched either: the assertions that fail
today are exactly the assertions that must pass, and weakening any of them is
not this task's resolution. The change is one value in one registry entry, plus
the plugin version bump that any change under `em-workflow/` requires.

### Why the pinned form stays pinned here

- FR1 states the command form, and AC-4 (FR4) requires the registry to hold
  that command mapping.
- NFR2's read-only discipline is about the working tree: no automatic package
  installation, no lockfile rewrite, no formatter run. It does not require any
  resolution-disabling flag, and TS-19 verifies it by observing the project
  root's file state across a run.
- The registry's single `args` list is shared by BOTH pip target forms, so any
  flag placed there also lands on the directory-target form. Changing the
  command form is therefore a specification-and-pins decision spanning
  `vuln-scanners.yaml` and `tests/test_sca_scan_invocation.py` together, not a
  registry-only edit.

### The version bump

The changed registry file lives under `em-workflow/`, so the plugin version
rises once, at one value, in `em-workflow/.claude-plugin/plugin.json` and in
`.claude-plugin/marketplace.json`'s em-workflow entry (IMPLEMENTATION.md D8's
one-bump-per-round rule; this round has a single task, so this task owns the
bump). No other plugin's version moves.

## Test Notes

- No new test module and no test edit. The existing pins ARE the contract for
  this task; adding a parallel assertion of the same registry value would
  duplicate `test_command_assembled_from_registry_tool_and_args`, which already
  reads the shipped registry rather than a fixture — which is why it caught the
  drift.
- The TDD step is inverted in the usual sense but still red-then-green: run the
  suite first and record the nine failures (they are the pre-existing red this
  task owns), make the single data change, then run it again and confirm zero
  failures and that the failing set went to empty rather than merely shrinking.
- AC-4's "strictly greater than the pre-task value" is verified against the two
  files' pre-change values (the suite's own version assertion only pins the
  agreement of the two files and a lower baseline).
- AC-1's "no other entry changed" and AC-3's "no test file modified" are both
  verified from this task's own diff, so the restore cannot be widened
  silently.
