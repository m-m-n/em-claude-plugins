# Task Plan: task0008 — Bind each scanner invocation to the reviewed project and off repository-controlled dispatch

## Goal

Every selected ecosystem's scanner runs as a trusted binary against the
REVIEWED project's own dependency set, with no path by which a file inside the
reviewed repository chooses the executable or the package-registry endpoint —
and the Python path reports the advisories `pip-audit` actually emits instead
of discarding all of them.

## Design

### The scan job (IMPLEMENTATION.md D8)

Turning the registry into something executable becomes one pure function of
(registry, changed files, project root), producing one **scan job** per
(ecosystem, selected manifest) pair, as D8 pins it: ecosystem name, the
project-relative manifest that selected it, the ABSOLUTE resolved executable
path, the full argument vector, the working directory, and the explicit child
environment. Constructing a job launches nothing, so every claim below about a
command is assertable without running a scanner.

Executing a job is the sibling task's half; this task calls the same
`execute` contract D8 states and does not change its body.

### Trusted binary, never a multiplexer subcommand

The registry names the scanner binary ITSELF. A command whose first element is
a package-manager front end and whose second element is a subcommand that the
front end resolves through configuration read from the reviewed project is not
an acceptable form: the reviewed repository can define that subcommand, so the
dispatch happens inside the front end and an argument-list (non-shell)
invocation does not prevent it. The cargo entry therefore names the standalone
audit binary, and the executable allowlist is updated in the SAME change so
the registry and the allowlist agree — a registry the allowlist rejects would
silently skip the whole ecosystem.

Resolution produces an absolute path on PATH; that absolute path is what the
job carries. When the trusted binary is not resolvable, the ecosystem skips
with its existing machine-stable reason (FR3's path, unchanged) and NO other
command form is attempted as a fallback.

### Configuration isolation

The child environment is built explicitly rather than inherited wholesale, so
that configuration files inside the reviewed project cannot redirect the
executable, the package-registry endpoint, or the build. For each ecosystem
this means pinning, through the tool's own documented environment variables
or flags, where it may read configuration from — and keeping the reviewed
project's own configuration out of that set. The reviewed project's tree is
still the working directory: it is the thing being audited, and NFR2's
read-only discipline is unchanged (no install, no lockfile rewrite, no
resolution that writes into the tree).

### The pip job audits the reviewed project, not the ambient environment

`pip-audit` with no target audits whatever Python environment happens to be
active; the working directory does not select a project. So the target is
carried in the arguments, per changed manifest:

- a changed requirements file ⇒ that file is the audited input;
- a changed `pyproject.toml` ⇒ that project directory (or its locked input)
  is the audited target.

Both forms stay read-only, and the argument vector must not contain any form
that installs or writes a resolution artifact into the reviewed tree.

### The pip normalizer's real input contract

`pip-audit --format json` emits, per dependency, a name, a version and a list
of vulnerabilities each carrying an identifier, fix versions, aliases and a
description. It emits NEITHER a per-dependency directness flag NOR a
per-advisory severity string. Gating on those two absent fields is what
discards every real advisory today.

- **Directness** is resolved from the reviewed manifest's own declared
  dependency set — the same shape of resolution the cargo path already
  performs against `Cargo.toml`, reusing the existing project-relative path
  confinement helper so a changed-file entry can never open a file outside the
  project root. Directness is never read from a tool-supplied field.
- **Severity** is taken from advisory metadata actually present in the tool's
  output. When an advisory's severity cannot be determined from that output,
  it is NOT silently treated as below threshold: the run contributes a
  machine-stable reason to its skip surface (the same surface the sibling
  rework task aggregates) and the summary states HOW MANY advisories were
  affected. Counts only — no advisory-sourced text is spliced into the summary
  (NFR4).

The shipped pip fixture is replaced by captured real `pip-audit --format json`
output. A fixture that invents fields is what let this defect pass the suite;
the replacement must carry no field the tool does not emit.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: for a changed requirements file the constructed pip job's argument
      vector audits THAT file; for a changed `pyproject.toml` it audits THAT
      project's directory or locked input; in neither case does the vector
      contain an install or write-resolution form, and in neither case does
      the audited target default to the ambient environment. (TS-26)
- [ ] AC-2: every constructed job's first argument-vector element is an
      absolute path to an allowlisted scanner binary, and no constructed
      vector has the multiplexer-front-end + subcommand form. The registry and
      the executable allowlist agree for every registered ecosystem, asserted
      directly against both files. (TS-26, TS-1)
- [ ] AC-3: when the trusted binary is absent from PATH the ecosystem yields
      its machine-stable tool-absent skip and no alternative command form is
      constructed for it. (TS-26, TS-4)
- [ ] AC-4: against a reviewed-project fixture containing a hostile alias
      definition in the cargo configuration file and a hostile registry line in
      the npm configuration file, the constructed job's executable path and the
      child environment's configuration/registry selection are identical to
      those constructed from the same fixture without those two files. (TS-26)
- [ ] AC-5: the pip fixture used by the normalization tests is captured
      `pip-audit --format json` output and contains no per-dependency
      directness field and no per-advisory severity string; the previously
      fabricated fields are gone from the test module. (TS-27, TS-2)
- [ ] AC-6: against that fixture, an advisory on a package declared in the
      reviewed manifest is classified direct and reaches `findings` when its
      severity is at or above the registry threshold, while one reachable only
      transitively is dropped; directness is never read from a tool-supplied
      field. (TS-27, TS-3)
- [ ] AC-7: an advisory whose severity cannot be determined from the tool's
      output is not counted as below threshold — the result's machine-readable
      skip surface carries a stable reason for it and the summary states the
      affected count, with no advisory-sourced text in either. (TS-27)
- [ ] AC-8: in this task's worktree, `python3 -m unittest discover -s tests`
      exits 0 and `python3 em-workflow/scripts/check-plugin-invariants.py
      <repo-root>` exits 0. (TS-21, TS-22)

## Test Notes

- No real scanner is ever executed. AC-1 to AC-4 assert on the CONSTRUCTED
  job (argument vector, executable path, working directory, environment), which
  is why construction is a pure function; binary resolution is exercised by
  placing an executable stub on a temporary PATH.
- AC-4's fixture is a temporary directory holding the two hostile
  configuration files plus a manifest — nothing in it is ever executed, so the
  test is safe even if the isolation regresses.
- AC-2's registry/allowlist agreement is a cross-file assertion; the registry
  is read with the module-local restricted YAML parser convention this
  repository's test modules already use, not with a third-party import.
- AC-5's captured output goes in as a fixture constant with a comment naming
  the tool version it came from, so a later reader can tell a capture from an
  invention.
- AC-7 needs a fixture advisory with no determinable severity alongside one
  that has one, to show the two are handled differently.
