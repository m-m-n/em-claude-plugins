# Task Plan: task0003 — Axis 2's placement in review-phase.md R0–R3b

## Goal

`review-phase.md` states, end to end and without any model invocation, how
axis 2 is probed for, selected, run as an R2 peer, excluded from LLM chain
walking, and merged into the R3a evaluation and the R3b gates — while
`review-protocol.md`, `reviewers.yaml`, `batch-policies.yaml` and
`batch-mode.md` stay untouched.

## Requirements

FR6, FR7, FR8, FR9, FR22, FR23, NFR1, NFR5, NFR6

## Scope

### Files to Create
- `tests/test_sca_axis_review_phase_r0_r3.py` — document and registry pins
  for this task's statements (stdlib only).

### Files to Modify
- `em-workflow/references/review-phase.md` — Phases R0, R1, R2, R2b, R3a and
  R3b ONLY. Phases R4, R5 and R6 belong to task0004; do not touch them.

## Design

All edits are additive: new steps, new rows, new sentences. Sentences already
pinned by existing test modules are not reworded or reflowed
(IMPLEMENTATION.md, Conventions → "Protocol edits are additive").

### R0 — notion-task-dispatch availability probe (FR6)

One new step in the same shape as the existing "Probe codex" and "Probe
litellm" steps. Its subject is the notion-task-dispatch entry point located
by a glob over the plugin cache that does NOT hard-code the marketplace name
and picks the newest when several versions are installed. The step's wording
distinguishes it from R0 step 1's fail-closed SSOT resolution: this is an
availability probe whose negative result is an ordinary, supported state, not
an abort. Its result is an input the orchestrator later hands to axis 2's
filing path — nothing here decides the filing branch by itself.

### R1 — `vulnerability` rides along the Mandatory Layer-2 check (FR7)

The existing "Mandatory Layer-2 check — license" trigger (a diff touching a
dependency manifest or lockfile) additionally adds `vulnerability` to the
selected set. The `license` behaviour is unchanged, and the same trigger
list serves both. `vulnerability` is never in the mechanical floor.

### R2 — axis 2 as a peer of the fan-out set (FR8, FR9, FR23)

`vulnerability` is served by axis 2: the orchestrator itself executes the
scan subcommand of `em-workflow/scripts/scan-dependencies.py`
(IMPLEMENTATION.md, Shared Components "`scan` subcommand") as a deterministic
step in the same phase, NOT as a Task dispatch and with no model anywhere on
its path. The text states that reachability and attack-scenario judgement is
the R3a evaluator's, which is why axis 2 needs no LLM of its own and why
`vulnerability` is absent from `reviewers.yaml`.

The run is recorded exactly as IMPLEMENTATION.md's "Axis-2 run identity"
pins it, and that row is what enters `perspectives_dispatched` /
`reviewer_outputs` for R3a.

Exclusions stated explicitly at the places they apply (FR23): a
`source: tool` run is never looked up in the reviewer registry, never walks
a `primary_chain`, never consumes an R2b fallback hop, never triggers the
Claude fallback dispatch, and never appears in `unreviewed_perspectives`. A
skipped axis-2 run (tool absent) is a recorded skip, not a retryable
`skip_reason` for the chain walk.

### R3a / R3b — downstream merge (FR9)

R3a's input carries the axis-2 run and its output like any other run. R3b's
step 3 category cross-check resolves a `vulnerability` finding against that
run's recorded perspective, and the evaluator accountability floor covers its
critical/high sites, so a tool-reported critical/high cannot be silently
dropped by the evaluator. The registry-owned threshold (direct dependencies
only, severity high and above) is named as living in `vuln-scanners.yaml`,
not restated as a protocol rule.

### Invariance (NFR1, NFR5, NFR6)

`review-protocol.md`'s Read-only Constraint is not edited — wording included.
Axis 2 is presented as a separate, non-LLM stage rather than as an exception
to that constraint. No new gate identifier is introduced, so
`batch-policies.yaml` and `batch-mode.md`'s Non-packet gates table are not
edited either.

## Test Notes

- Every criterion is a document assertion. The new module anchors on literal
  headings ("Phase R0", "Phase R1", …) and asserts phrase presence within the
  sliced section, so a statement landing in the wrong phase fails.
- AC-6's invariance side is the stronger half: assert the Read-only
  Constraint section's content matches its pre-change bytes, and assert the
  gate-identifier set extracted from `batch-policies.yaml` and
  `batch-mode.md` is unchanged. A negative case (a forged section) is worth
  one test so the assertion is known to be able to fail.
- `reviewers.yaml` is read with a hand-rolled restricted-subset parser local
  to the test module (repository convention).
- Whitespace normalization before phrase matching keeps the assertions
  robust against the document's ~79-column reflowing.
