# Task Plan: task0005 — Triage filing and report path in scan-dependencies.py

## Goal

Unresolved `vulnerability` findings become human-triageable artifacts —
one task per package in the external task system when it is available, a
report under the main working tree's `tmp/` when it is not — without ever
filing the same package twice against an incomplete task.

## Requirements

FR12, FR13, FR14, FR15, FR16, FR17, FR18, FR22, NFR2, NFR4, NFR7

## Scope

### Files to Create
- `em-workflow/scripts/scan-dependencies.py` — co-owned with task0001; this
  task implements the `file-tasks` subcommand.
- `tests/test_sca_task_filing.py` — this task's tests (stdlib only).

## Design

The subcommand's inputs and outputs are pinned in IMPLEMENTATION.md, Shared
Components "`file-tasks` subcommand". The external task system's entry point
is always an INPUT — the script never probes for it (that is R0's job), which
is also what makes the whole path testable with a stand-in executable.

### Report destination resolution (FR13)

The destination is `tmp/` directly under the root of the FIRST entry of the
porcelain worktree listing taken against the project root — the main working
tree. The top-level-resolution command is never used: under review it returns
the integration worktree, which is the wrong tree. The report filename
carries the feature name and a timestamp. `tmp/` is already ignored by the
repository, so nothing is committed.

### Branch (FR12)

Entry point supplied ⇒ file into the external task system with the security
type argument. Entry point absent ⇒ write the report. Entry point supplied
but its incomplete-task listing cannot be obtained ⇒ IMPLEMENTATION.md D6:
degrade to the report branch and say so in the report, rather than filing
without duplicate detection. Neither branch asks the user anything.

### Grouping and content (FR14, FR18)

Findings are grouped by package: one task per package, regardless of how many
advisories it carries. Every advisory for that package becomes one line in
the 「参照」 field, each line carrying the advisory identifier and the
severity as a recorded FACT. The priority property is set to its initial
value 「高」 and is never derived from severity — a human moves it during
triage. Every advisory-sourced string passes through the truncation helper
(4096-byte discipline) before it reaches a filed field or the report.

### Duplicate detection (FR15, FR16, FR17)

Two stages:

- **Task identity** = package name. An INCOMPLETE task already existing for
  that package suppresses a new task; the advisories not yet recorded on it
  are appended instead.
- **Entry identity** = advisory identifier (CVE / GHSA / …). An advisory
  already present on that task is neither re-appended nor duplicated.

Matching considers incomplete tasks ONLY: when every task for a package is
complete or discarded, a NEW task is filed — a fresh advisory on a discarded
package is a separate matter deserving a fresh judgement.

The duplicate-detection key is built by exactly ONE function, and every call
site obtains its key from that function alone. No call site knows the key's
composition, so a later widening to "package name + major version" changes
that function and nothing else.

Package and advisory identities are recovered from a finding through the one
recovery function IMPLEMENTATION.md's "Finding text-encoding contract"
requires; no call site parses a finding's text itself.

clearly-marked placeholder IMPLEMENTATION.md's "Module co-ownership skeleton"

## Test Notes

- The external task system is never contacted: the entry point is an input,
  so every filing test points it at a stand-in executable created under a
  temporary directory that records the arguments it received and replies with
  a scripted listing. Listing failure (AC-1's third branch) is the same
  stand-in exiting non-zero.
- AC-2 is the one criterion that needs a real repository: create one under a
  temporary directory, add a second worktree, and assert the destination
  resolves to the first entry's root in BOTH orderings.
- AC-4's "incomplete only" needs the listing stand-in to return a mix of
  incomplete, complete and discarded tasks in one run.
- The test module loads the script by file path; its own imports stay
  standard-library only.
- Idempotency (IMPLEMENTATION.md D3's recovery guarantee) is worth one direct
  test: run the subcommand twice over the same findings against the same
  listing state and assert the second run files nothing new.
