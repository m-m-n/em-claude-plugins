# Task Plan: task0002 — Forged marker with an unparsable index must not crash the hook

## Provenance

- source: review
- source_ids: [9d315d6486b00e4d]
- review_round: 1

## Goal

A command carrying a forged internal marker whose index cannot be converted to an integer gets the same verdict and rule id as on the base hook (94875785), instead of the hook dying with an uncaught exception and producing no decision (fail-open).

## Requirements

FR5, FR6, NFR2

## Scope

### Files to Create

### Files to Modify
- `em-workflow/hooks/destructive-guard.py` — marker-position registration added by task0001 tolerates a marker whose index is not a parsable integer
- `tests/test_destructive_guard_rm_reason_positions.py` — regression cases for forged markers with an oversized index

## Design

Feature-wide rules (reason-text hygiene, test conventions) are in IMPLEMENTATION.md "Conventions"; they are referenced here, not restated.

### Defect

task0001 added a step that, before markers are removed from a token, reads every marker in the token and converts its index to an integer. The conversion is unguarded. A marker forged in the command text (NUL, then more digits than the interpreter's integer-from-string digit limit, then STX) raises a conversion error. The error propagates out of statement enumeration and out of the hook's entry point, the hook exits with an error status and emits no decision. A single forged marker anywhere in the command suppresses every rm judgment of that command. The pre-existing unresolved-mark stripping step already guards the same conversion.

### Contract

- **Precondition.** A token may contain any byte sequence, including NUL / STX sequences that look like markers but were not produced by the hook.
- **Postcondition.** Marker-position registration never raises on any token content. A marker whose index cannot be converted is not registered and is skipped, exactly as the unresolved-mark stripping step skips it. The marker's text is then handled by the existing downstream steps exactly as on the base hook.
- **Every conversion of a marker index that task0001 introduced follows the same rule**, not only the one named in the finding. No exception from marker-index parsing may reach statement enumeration's caller.
- The integer-from-string digit limit of the interpreter is not raised or disabled. Skipping the unparsable marker is the fix.

### Unchanged

- Verdict and rule id for every command (FR5).
- Numbering, designations and the combined reason for every command that contains no unparsable marker.
- The destructive-guard cases file is not extended (SPEC A6, IMPLEMENTATION.md "Conventions", VERIFICATION.md TS-7). The regression cases live in the feature's own unittest module. The cases file pins behaviour relative to the base hook, which already denies these commands; the defect exists only in this feature's unmerged change.

## Acceptance Criteria (MANDATORY)

Below, `<FORGED:k:d>` means NUL, then the digit `d` repeated `k` times, then STX. Every case passes HOME and PATH explicitly and runs the hook as a child process with PreToolUse JSON on standard input.

- [ ] AC-1 (FR5): For each command below, the hook's exit status, decision and rule id equal the values recorded from the base hook (94875785) for the same input before editing. The expected recorded values are deny / rm-recursive for all of them. A recorded value that differs is a finding to report, not something to adjust silently.
  - `rm -rf /var/x<FORGED:5000:1>` (forged marker inside the rm target)
  - `echo <FORGED:5000:9>; rm -rf /var/x` (forged marker in an earlier, non-rm statement)
  - `rm -rf /var/x; echo <FORGED:5000:9>` (forged marker in a later statement)
  - `echo "$(echo <FORGED:5000:9>)"; rm -rf /var/x` (forged marker inside a command-substitution body)
  - `bash -c 'echo <FORGED:5000:9>'; rm -rf /var/x` (forged marker inside a `-c` payload)
- [ ] AC-2 (FR5): For every AC-1 command, the hook's stderr contains no `Traceback` and the hook's stdout is a single parsable decision object.
- [ ] AC-3 (NFR2): For every AC-1 command, the hook's stdout contains no raw control character (a character below 0x20, or 0x7F), apart from the line terminator at the end of the output. NUL and STX in particular do not occur.
- [ ] AC-4 (FR5, FR6): `python3 em-workflow/hooks/tests/run-destructive-guard.py` passes with its cases file unchanged, and `python3 -m unittest discover -s tests` passes, including every task0001 case in `tests/test_destructive_guard_rm_reason_positions.py` unchanged in its expectations.

## Test Notes

- Write the AC-1 to AC-3 cases first and confirm that at least the first two fail (no decision, traceback on stderr) against the current integration hook before fixing.
- Pin AC-1's expected values by running each command against the base hook (94875785) first, as task0001 did for its own pins.
- Build the forged strings in the test code (character escapes for NUL and STX, string repetition for the digits); do not embed raw control characters in the test source.
- Keep each command as its own subtest so a failure names the position of the forged marker.
- Use the existing module's helpers for driving the hook and reading decision / rule id.

## Out of Scope

- Adding cases to the destructive-guard cases file (SPEC A6).
- Raising or disabling the interpreter's integer digit limit.
- The plugin manifest and the marketplace file (NFR4).
