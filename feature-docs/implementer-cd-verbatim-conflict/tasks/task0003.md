## Design

説明する内容は IMPLEMENTATION.md の C1 と C2 に従う。D3 のとおり、「コマンド全体で cd は 1 つ」とは書かない。

### command-execution-protocol.md の Verbatim execution rule 節

- 規則を役割ごとに分けて書く。
- オーケストレーター（メインセッション）: 今の規則を残す。`cd {dir} && …` を前置せず、単独の `cd` で先に移動する（メインセッションでは cwd が Bash の呼び出し間で残る）。実行後は単独の `cd` でプロジェクトルートへ戻り、cwd が worktree の中のまま次のステップや別の worktree へ進まない。
- implementer（例外）: サブエージェントでは cwd が Bash の呼び出し間で残らない。承認文字列は `cd "{worktree_path}" && <承認文字列>` の 1 回の Bash 呼び出しで実行し、`&&` より後ろは承認文字列そのままにする。hook がこの形を allow する条件を要約して書く（二重引用符で囲んだ絶対パス 1 つ、`cd` にオプションなし、閉じ引用符と最初の `&&` の間は空白だけ、パスの realpath がメイン作業ツリー直下の `.claude/worktrees/em-workflow/` より深い既存ディレクトリ、残りが承認文字列と完全一致）。
- どの役割でも、環境変数の代入の前置は禁止のまま。分割・結合・引用で包む・「改善」する、の禁止と、変形した文字列は承認と一致しなくなるという説明は残す。

### command-execution-protocol.md の Runtime enforcement 判定表

- cd 前置形の行を足し、判定を allow とする。置く位置は禁止パターンの行の後、「承認済みと完全一致」の行の前。
- 禁止パターンの行は、cd 前置形にもコマンド全体で当たり、承認済みでも deny であることが読み取れるようにする。
- 条件を満たさない cd 前置形は、文字列全体として残りの行で判定される（多くは判定なし）と書き添える。
- deny 時の対応（On a deny for an unapproved command）の 2 項目は変えない。

### README.md と workflow-schema.md

- README.md の「実行時強制」の項目にある判定の列挙に、implementer の `cd "{worktree_path}" && <承認文字列>` の形の例外を書き足す。日本語で、詳細は command-execution-protocol.md に委ねる。
- workflow-schema.md の Command approval store 節の hook の説明（approved exact string → allow、declared-but-unapproved → deny）に、同じ例外を英語で書き足す。「Details: `references/command-execution-protocol.md`.」の参照は残す。

### 文書全体の制約

- command-execution-protocol.md の `AskUserQuestion` の出現数を増やさない（`tests/test_muse_consent_no_new_questions.py` の上限は 8）。
- Approval gate 節、Refusal cases 節、Fallback 節、Reporting 節は変えない。
