# Task Plan: task0001 — bash_guard: worktree への cd 前置形の許可と deny 時の案内の書き分け

## Goal

`em-workflow/hooks/bash_guard.py` の hook が、IMPLEMENTATION.md の C1 を満たす `cd "<P>" && <承認文字列>` に allow を返すようにする。C1 の候補でないコマンドの判定は変えない。未承認で deny するときの案内を、オーケストレーター向けと implementer 向けに書き分ける。

## Design

### 判定の流れ（hook mode）

1. 入力の読み取り、Bash 以外や空コマンドの扱い、cwd の決め方、宣言済みコマンドの収集は変えない。
2. 承認済み文字列の集合を読んだ後で、コマンドが C1 の候補かを判定する（下の 3 つの部品）。
3. コマンドが「宣言済み」「承認済み」「C1 の候補」のどれでもなければ、判定なしで終える（変更前と同じ）。
4. 禁止パターンの判定をコマンド全体に当て、一致したら deny（既存の理由文と案内のまま）。
5. 文字列全体が承認済み、または C1 の候補なら allow。C1 の候補で allow するときの理由文は、全体一致の allow と区別できる文にする。
6. それ以外（宣言済みで未承認）は deny。案内は下の「deny 時の案内」に従う。

承認ストアのファイルが無く、文字列全体も宣言されていないときに判定なしで早く終える既存の分岐は残してよい（C1 の候補は承認済み文字列を必要とするため、結果は変わらない）。

### 部品 1: 前置部の分解

- 入力: 前後の空白を取り除いたコマンド文字列。
- 出力: C1 の構文条件 1〜4 をすべて満たすときだけ、パス P と残りの組。満たさないときは「該当なし」。
- 事後条件: 該当なしのとき、コマンドは C1 の候補にならない。分割に使う `&&` は、閉じ引用符の後にある最初の `&&`。P の中の文字はどれも分割に使わない。

### 部品 2: worktree 領域の判定

- 入力: P と hook の cwd。
- 出力: C1 のパス条件 5〜7 を満たすときだけ真。
- 事前条件: P は部品 1 を通ったもの。
- 事後条件: git common dir を求められないとき、基準の場所を求められないとき、P の realpath が存在するディレクトリでないときは偽。基準の場所そのもの、基準と名前が前方一致するだけの兄弟ディレクトリ（例: `em-workflow-x`）の配下は偽。git の問い合わせは cwd に対してだけ行い、P を作業ディレクトリや引数にした子プロセスは起動しない。

### 部品 3: 残りの照合

- 入力: 残りと、project_key(cwd) の承認済み文字列の集合。
- 出力: 残りの前後の空白を取り除いた文字列が集合のどれかと完全一致するとき真。
- 事後条件: 残りが空、または前後に文字を足した形は偽。

### deny 時の案内（FR7）

宣言済みで未承認のコマンドを deny するときの additionalContext に、次の 3 つを別々の文として書く。

- オーケストレーター向け: 承認ゲートを実行してから、単独の `cd` で作業ディレクトリへ移動し、承認された文字列をそのまま実行する。
- implementer 向け: 承認された文字列は `cd "{worktree_path}" && <承認文字列>` の 1 回の Bash 呼び出しで実行する。
- AskUserQuestion を持たないサブエージェント向け: deny された後は再試行せず、実行を諦めて notes で報告する。

あわせて、環境変数の前置などで承認文字列そのものを変形しない旨を残す。禁止パターンで deny するときの理由文と案内は変えない。

### 実装上の制約

- 標準ライブラリだけを使う（NFR1）。判定は文字列と realpath だけで決め、LLM や外部サービスを使わない。
- コメントと docstring を除く実行コードに、部分文字列 `status` を含めない（NFR3、`tests/test_hook_classification_pin.py`）。変数名・関数名・文字列リテラルのどれにも含めない。
- CLI モード（`--record` / `--remove` / `--list`）の挙動は変えない。

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR9): 一時 git リポジトリの `.claude/worktrees/em-workflow/` より深い既存ディレクトリ P と、承認ストアに記録した文字列 X について、`cd "P" && X` は allow になる。X が環境変数の代入で始まる文字列（例: `CARGO_TARGET_DIR=src-tauri/target cargo test --manifest-path src-tauri/Cargo.toml --lib`）でも、X が `&&` を含む文字列（例: `a && b`）でも allow になる。hook 入力の cwd がメイン作業ツリーのときも、git の worktree 追加で作った worktree の中のときも、判定は同じになる。

- [ ] AC-3 (FR1, FR3, FR9, TM-2): パス条件を満たさない次の形は allow にならず、出力なし（変更前の判定と同じ）になる。worktree 領域の外の既存ディレクトリ、別の一時リポジトリの `.claude/worktrees/em-workflow/` 配下、`..` を含み realpath が領域の外になるパス、領域の中に置いたシンボリックリンクで realpath が領域の外を指すパス、`.claude/worktrees/em-workflow` そのもの、名前が前方一致する兄弟ディレクトリ（`.claude/worktrees/em-workflow-x/` 配下）、存在しないパス。

- [ ] AC-5 (FR3, FR9, NFR2): `cd` を前置しないコマンドの判定は変わらない。承認済み → allow、一時リポジトリの workflow.yaml に宣言済みで未承認 → deny、どちらでもない → 出力なし。`cd "P" && <宣言済みで未承認の文字列>` は出力なしになる（新しい deny を返さない）。
- [ ] AC-6 (FR7): 宣言済みで未承認のコマンドを deny したときの additionalContext に、オーケストレーター向けの単独 `cd` の案内、implementer 向けの `cd "{worktree_path}" && ` の形の案内、AskUserQuestion を持たないサブエージェントが再試行せず notes で報告する指示が含まれる。環境変数の前置で文字列を変形しない旨も含まれる。

## Test Notes

- テストはすべて `tests/test_bash_guard_cd_prefix.py` に置き、hook を subprocess で起動して JSON を標準入力で渡し、標準出力の JSON（または出力なし）を判定する。期待する判定は allow / deny / 出力なしの 3 種類。
- ケースは「期待する判定・ラベル・コマンドの組」を並べた表にして、1 ケースずつ subTest で回す（リポジトリの hook テストの並べ方に合わせる）。コマンドは一時ディレクトリのパスを後から埋め込む形にする。
- 一時 git リポジトリは一時ディレクトリに作り、比較に使うパスは realpath で求める（一時ディレクトリがシンボリックリンク経由の環境に備える）。コミットを作るときは、利用者の git 設定に依存しないよう作者情報をテスト側で与える。
- 承認は `bash_guard.py --record --project-dir <一時リポジトリ>` で記録する。`--record` は禁止パターンを拒むので、AC-4 だけは承認ストアの JSON を直接書く。そのときのキーは git が返す git common dir の絶対パスにする。
- subprocess の環境では `EM_WORKFLOW_APPROVALS` を一時ファイルに向け、`CLAUDE_PROJECT_DIR` を取り除く（または一時リポジトリに向ける）。実在の承認ストアと実リポジトリの workflow.yaml を読ませない。
- AC-1 の cwd を worktree にするケースは、最初のコミットを作った後に `.claude/worktrees/em-workflow/` 配下へ worktree を追加し、その中を hook 入力の cwd にする。
- AC-3 の別リポジトリのケースは、2 つ目の一時 git リポジトリに同じ構成を作り、hook 入力の cwd は 1 つ目のリポジトリにする。
- AC-5・AC-6 の宣言済みコマンドは、一時リポジトリの `feature-docs/<任意>/workflow.yaml` に `test_command` の 1 行として置く。
- 赤の確認: AC-1・AC-4・AC-6 は実装前に失敗する（AC-1・AC-4 は出力なし、AC-6 は implementer 向けの案内が無い）。AC-2・AC-3・AC-5 は変更前から成り立つ回帰の確認なので、実装前に通るものは red_confirmed: false とし、理由に「変更前から成り立つ挙動の固定」と書く。
