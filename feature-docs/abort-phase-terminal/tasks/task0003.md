## Design

### Why the implementation side, not the specification side

Two directions could restore containment: amend SPEC.md's Declared Change Set,
or bring the actual change set back inside it. SPEC.md and REQUIREMENTS.md are
never edited by rework synthesis, and no requirement forces the assertions to
live in their own module:

- FR7 constrains only `em-workflow/references/batch-mode.md`'s row content and
  requires that `tests/test_batch_policies.py` keep matching — it says nothing
  about which module asserts the row.
- NFR4 already describes the change set as "prose plus the three test modules
  plus the two version manifests", and SPEC.md's TS-10 uses the same count.
  Both become accurate again once the fourth module is gone; neither needs an
  edit.
- `tests/test_implement_routeback_gate.py` is inside the Declared Change Set,
  is already modified by this feature (task0001), and already carries
  cross-document contract assertions over `implement-phase.md`,
  `commit-docs.sh`, `skills/develop/SKILL.md` and the two version manifests.
  Adding the `batch-mode.md` row keeps SC-1's two restatement sites (the
  implement-phase.md terminal and the batch-mode.md row) asserted in one
  module, which is what NFR6 is about.

The alternative host modules named by finding b06cb0bd27bf9dbd
(`tests/test_recycled_task_id_consistency.py`) and
`tests/test_routeback_reset_scope_consistency.py` are equally declared; this
task picks `tests/test_implement_routeback_gate.py` for the reason above and
must not spread the assertions across more than that one module.

### Contract of the relocation (pre/post)

**Pre**: `tests/test_abort_phase_terminal_batch_mode.py` holds ten test methods
in three classes, reads only `em-workflow/references/batch-mode.md`, imports no
sibling test module, and uses the standard library only.

**Post**, all of the following hold simultaneously:

1. Every one of those ten assertions is exercised from
   `tests/test_implement_routeback_gate.py`, over the same target: the single
   line of `em-workflow/references/batch-mode.md` that contains the gate id
   `implement.failed-task`, located by asserting that exactly one such line
   exists.
2. The three checks the relocated assertions make are unchanged in substance:
   (a) the row states the write-and-commit terminal, (b) the row retains its
   gate id, its retry clause, its route-back-never-automatic clause and its
   Full-detail pointer, (c) the removed phrase's absence is paired with a
   regression proof against a verbatim capture of the pre-change row, a
   non-vacuity guard on that capture, and a proof that the new-wording matcher
   also fails against it.
3. `tests/test_abort_phase_terminal_batch_mode.py` no longer exists.
4. Nothing already in `tests/test_implement_routeback_gate.py` is removed,
   renamed, weakened or skipped — in particular the byte-pin constant
   `PRE_CHANGE_BATCH_MODE_PARAGRAPH` and its equality assertion, and
   `TestPluginVersionBumpedInLockstep`, stay exactly as they are.

### Name collisions to resolve during the move

`tests/test_implement_routeback_gate.py` already defines a class named
`TestValidationDetectsRegressions` and a constant whose value is close to the
relocated `REMOVED_PHRASE`. The move therefore requires:

- the relocated regression proofs to be folded into the existing
  `TestValidationDetectsRegressions` class, or placed in a class with a
  distinct name — never a second class of the same name (the second definition
  would silently shadow the first and drop its tests from discovery);
- the relocated module-level constants to carry batch-mode-specific names so
  none of them rebinds an existing constant of that module;
- a new path constant for `em-workflow/references/batch-mode.md` (the module
  currently resolves `implement-phase.md`, `commit-docs.sh`,
  `skills/develop/SKILL.md` and the two manifests only).

Shared cross-task contracts (SC-1 abort terminal, SC-2 byte pins, SC-3 version
lockstep, SC-4 file ownership) are IMPLEMENTATION.md's; this task introduces no
new one and restates none of them. Note that SC-4's ownership map and the Layer
Structure table's "plus one new module for the batch-mode.md row" describe the
first implement wave and are not rewritten by this task.

## Test Notes

- The relocated assertions ARE this task's tests; there is no separate
  production artifact. The TDD order that still applies: move the assertions
  first and watch them run green against the already-correct `batch-mode.md`
  row, then delete the old module and re-run the whole suite — a drop in the
  collected count is the signal that the move lost a test (AC-5, AC-6).
- AC-5's count check is the guard against the silent-shadowing failure mode
  named in Design: a duplicate class name compiles and runs, and only the count
  reveals the loss.
- AC-1's deletion half and AC-7's byte-identity half are inspected on the diff
  (`git status --porcelain` / `git diff --name-only` against the task branch
  base), not by a committed checker — the same treatment VERIFICATION.md's
  TS-10 already gives change-set containment.
- No new assertion beyond the ten relocated ones is wanted. The batch-mode row's
  content is already correct and already verified; this task changes only where
  the verification lives.
