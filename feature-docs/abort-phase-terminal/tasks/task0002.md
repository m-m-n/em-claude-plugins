# Task Plan: task0002 — batch-mode.md gate row synchronization and version bump

## Goal

Restate `em-workflow/references/batch-mode.md`'s `implement.failed-task`
Non-packet gate row so it describes the abort terminal of IMPLEMENTATION.md
SC-1 (the `implement: failed` write plus its commit) instead of asserting a
status no write produces, cover it with a new test module, and move the
plugin version to `0.1.44` in both manifests.

## Design

### The row's Batch behavior cell

The cell currently ends the second-failure branch with a parenthetical
asserting that `implement` "stays `failed`", which is false: no write
produces that status on the abort path. Restate the second-failure branch to
IMPLEMENTATION.md SC-1's terminal — the `implement` step's `status` is WRITTEN
to `failed` and exactly that write is committed — in row-sized wording. SC-1
is the contract; read it there. This row does not need to match
implement-phase.md byte for byte and must not try to: it is a summary whose
detail pointer already delegates to the owning document. What it must not do
is contradict SC-1 (NFR6), and it must not claim `implement` reaches `failed`
without naming the write that produces it.

Elements of the row that MUST survive unchanged in substance:

- the gate id `implement.failed-task` and the row's left-hand
  interactive-behavior cell;
- `Auto-select **retry** once per task (kept worktree, I.2.a resume guard)`;
- `Route-back-to-planning is never taken automatically`;
- the pointer `` Full detail: `references/implement-phase.md` Step I.2.c ``.

The existing batch-policy test asserts, for this row, both the gate-id string
and a (description, keyword) pairing keyed on `implement.failed-task`; it must
stay green without being modified. The row also stays a single table row —
the table's shape (one row per gate, two columns) is unchanged, and no row is
added or removed.

### The version bump

Both manifests currently read `0.1.43`; both move to `0.1.44` (SC-3). The
values must never diverge. The durable lockstep assertion (equality,
`(major, minor) == (0, 1)`, patch strictly greater than 42) already exists in
a module this task does not own and already accepts `0.1.44`, so no test
change is needed for it — and per that module's own recorded convention, the
literal version must NOT be pinned in a test, because that goes red on the
next unrelated bump.

### The new test module

One module under `tests/`, named `test_*.py` so discovery picks it up, using
the standard library only. It reads batch-mode.md, locates the single row
containing the gate id, and asserts on that row's text. It reads no other
document and imports no sibling test module.

  absence assertion is provably about that exact pre-change text, matching

  reading both manifests and by running the existing lockstep test. Do not
  add a test pinning the literal `0.1.44`.

  module.
