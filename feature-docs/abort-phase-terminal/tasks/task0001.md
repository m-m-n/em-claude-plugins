## Design

### The terminal to write

The procedure is IMPLEMENTATION.md SC-1 — read it there; it is not restated
here. Both abort call sites in this section describe that same procedure.
Per SPEC.md assumption A4 the two call sites MAY share one description via an
explicit cross-reference inside Step I.2.c rather than duplicating the
command sequence, provided each path's terminal is fully readable without
leaving the section.

The rejected path already in the section (the branch opened by
`When the gate does not hold`) is the template: it refreshes, captures the
tip, sets the `implement` step's `status` to `failed` as the single write it
makes, commits exactly that write through `commit-docs.sh` with the captured
tip as third argument, states that the terminal status write and its own
commit are the ONLY side effect, and returns control via develop's stop
condition 3 firing on the next Step B iteration. That branch's own sentences
are NOT edited by this task — they are the reference the abort paths are
brought into line with.

### Edit site 1 — the exit-4 recovery bullet (Branch & Worktree Model)

The bullet introduces its call-site list with `for example`, so the list is
open and admits one more entry: the abort terminal status commit. Constraints:

- The three currently named entries — `Step I.1's baseline commit`,
  `Step I.2.b's wake-phase commit`, `Step I.2.c's rejected-path terminal
  status commit` — all survive.
- The single carve-out stays exactly Step I.2.c's route-back commit; the
  abort call site is never described as carved out.
- No claim fixing the NUMBER of exit-4-capable call sites is introduced; in
  particular the withdrawn literal `` the three `commit-docs.sh` call sites
  in this phase where exit 4 can occur `` must not come back.

### Edit site 2 — the `- **abort phase**` option

The option currently reads as a status assertion with no write behind it
(`` leave `implement` as `failed` for manual handling ``). Replace that with
the SC-1 terminal. Constraints:

- The bullet still opens with the exact literal `- **abort phase**` (two
  test modules use it as a slice anchor).
- The removed phrase `` leave `implement` as `failed` for manual handling ``
  appears nowhere in the section afterwards.
- The bullet states the bounded side-effect set and names develop's stop
  condition 3 with the "fires on the next Step B iteration reading
  `implement: failed`" formulation.

### Edit site 3 — the closing batch-mode paragraph

The paragraph currently asserts `implement stays `failed`, report and stop`,
which no write produces. Restate it to the SC-1 terminal. Constraints:

- It keeps naming batch-mode.md's Non-packet gates table and the
  `implement.failed-task` gate id, keeps the auto-retry-once-per-task rule,
  keeps `Route-back-to-planning is never taken automatically`, and keeps the

- It remains the FINAL content of the section: nothing follows it before the
  `### Supporting cast` heading, and exactly one blank line separates them.
- The phrase `implement stays `failed`, report and stop` is gone.

### Byte pins (SC-2)

against the section slice that starts at the marker
`` Batch mode (`references/batch-mode.md` `` and runs to the end of the

## Test Notes

- All criteria are document-contract assertions: read the target file, slice
  the section between its heading and `### Supporting cast`, normalize
  whitespace for multi-word phrase checks, and keep the raw text for the
  byte-identity and section-position checks. The three target modules already
  contain section-slice and whitespace-normalizing helpers; reuse them rather
  than adding new ones.
- Write the assertions first (they will fail against the current document),
  then edit the prose until they pass — the paragraph literals are the one
  exception to test-first ordering: they can only be finalized once the
  prose is final, so derive them from the document at that point and treat
  the equality assertion as the check that the derivation is faithful.
- Each absence assertion (AC-1's removed phrase, AC-2's removed phrase,
  AC-5's withdrawn claim) deserves its paired negative proof, following the
  regression-guard pattern the modules already use: the removed literal is
  kept as a named constant so the assertion is provably about that exact
  text.
- AC-6's negative proof is a manual, non-committed experiment: revert one
  literal, observe exactly one module fail, restore it. Do not leave a
  mutation-testing harness behind.
- No new test module is created by this task.
