# Task Plan: task0001 — Align reason code conditions and the merge skill result table

## Goal

The `verification_failed`, `git_failed` and `remote_unresolved` Conditions in
`em-workflow/references/merge-result.md` cover every emission site in
`em-workflow/skills/merge/SKILL.md`, the skill's 結果の値 section names
`merge-result.md` as the owner of the conditions, and tests in
`tests/test_merge_skill_doc.py` detect drift between the two documents.

## Requirements

FR1, FR2, FR3, FR4, FR6, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/references/merge-result.md` — the three Condition cells of the
  Reason codes table
- `em-workflow/skills/merge/SKILL.md` — the 結果の値 section: the ownership
  statement, and the `git_failed` and `verification_failed` rows
- `tests/test_merge_skill_doc.py` — drift detection for FR6 (a) and (b), plus
  the excluded paths

## Design

### Condition cells in `merge-result.md`

Rules for all three cells:

- Conditions are written in terms of operations. No Condition cell carries a
  step number. The step numbers in this plan identify emission sites in
  `SKILL.md` only.
- Rows stay at 3 cells, and a cell body contains no pipe character.
- A cell states only what the code covers. A failure excluded below is not
  named in the cell, not even as a negative clause, so that its absence is
  checkable.

`verification_failed` states all of the following. Emitted by stays
`the skill, merge-git integrate`.

| Item | Condition | Emission site |
|------|-----------|---------------|
| (a) | A build / test / e2e command failed or timed out | step 10 |
| (b) | Before integration, the HEAD of the integration worktree differs from the expected tip (`head_sha` on a retry) | step 8, `merge-git integrate` |
| (c) | After the verification commands, tracked files have uncommitted changes | step 10 |
| (d) | After the verification commands, HEAD differs from the verified `head_sha` | step 10 |
| (e) | Immediately before the local merge, the tip of the integration branch differs from the verified `head_sha` | step 13.3 |

Item (b) keeps the literal `HEAD before integration differs from the expected`.

`git_failed` states all of the following.

| Item | Condition | Emission site |
|------|-----------|---------------|
| (a) | A failure with which a `merge-git` subcommand stopped as `git_failed`, including a git command failure, a launch failure, a timeout, and reaching the script-wide time limit. This covers `route` reading remote / config, `merged` reading the tip and the ancestor check, `main-tree`, `worktree-state` running worktree list / git-path / status, `integrate` running fetch and a non-conflict merge failure, and `base-check` | steps 3, 4, 6, 7, 8, 9, 12 |
| (b) | `git worktree add` failed | step 7 |
| (c) | `git merge --abort` failed for `merge_in_progress`, or for the unattributable case | steps 7, 9 |
| (d) | `worktree-state` after the add / abort is neither `clean` nor `stop` | steps 7, 9 |
| (e) | The conflict-resolution `git commit` failed | step 9 |
| (f) | `git status` / `git rev-parse HEAD` failed after verification | step 10 |
| (g) | `git rev-parse` of the integration tip failed immediately before the local merge | step 13.3 |

Not part of `git_failed`:

- Git failures in step 2, the failure to read the tip on the PR route in step
  6.4, and an invalid value from the post-commit rev-parse in step 9 (each is
  `internal_error`).
- `main-tree` not being ready in step 13.3 (`main_tree_not_ready`).
- `git merge --abort` failing after a merge failure in step 13.3 (the result is
  `merge_failed`).
- Reads after a successful merge and step 15 failures (the result stays
  `merged` / `already_merged`).

`remote_unresolved` keeps the two existing conditions (no remote can be chosen,
the remote name is unsafe) and adds the following from `merge-pr repo`. Emitted
by stays `merge-git route, merge-pr repo`.

| Item | Condition |
|------|-----------|
| (a) | The remote does not exist |
| (b) | The gh default repository cannot be determined |
| (c) | On either the remote side or the default side, the host of the URL gh reported is malformed |
| (d) | The default repository and the remote differ in host or owner/name (case-insensitive) |

Not part of `remote_unresolved`:

- Zero remotes (the local route).
- The gh default repository query output not being JSON, and `url` being missing
  or not a string (`internal_error`).

### 結果の値 section in `SKILL.md`

- The section states that the owner of each reason's condition is Reason codes
  in `references/merge-result.md`.
- The table keeps its columns (reason / 出どころ / 手順 / detail) and its 28 rows.
  No row or column is removed, and no condition column is added.
- The `git_failed` row's 手順 becomes 3, 4, 6, 7, 8, 9, 10, 12, 13.
- The `verification_failed` row's detail gains the step 10 uncommitted changes
  and HEAD mismatch. The row keeps 4 cells, its 手順 stays 8, 10, 13, its 出どころ
  keeps `merge-git integrate`, and its detail keeps `component.field`,
  `integration branch moved after preflight` and
  `integration branch moved after verification`.
- Rows stay at 4 cells, and a cell body contains no pipe character.

### Tests in `tests/test_merge_skill_doc.py`

A step's body is the text from its step heading up to the next step heading. The
結果の値 section is not a step body. A sub-step such as 13.3 counts as its parent
step in the 手順 column comparison.

| Scenario | Check |
|----------|-------|
| TS-1 | For `verification_failed` and `remote_unresolved`, the steps whose body contains the code equal the row's 手順: {8, 10, 13} and {3, 5}. For `git_failed`, the steps whose body contains the code are contained in the 手順 {3, 4, 6, 7, 8, 9, 10, 12, 13}, and the column also contains the pass-through steps {3, 4, 6, 7, 8, 9, 12}, each of whose bodies names `merge-git` |
| TS-2 | Each of the three Condition cells is read from a row of exactly 3 cells and contains the terms of its items, with at least one term per item. A forged row with one condition removed makes the check fire, for each of the three codes |
| TS-3 | Step 2, the tip read on the PR route in step 6.4 and the rev-parse in step 9 stay `internal_error`. `main-tree` in step 13.3 stays `main_tree_not_ready`. A merge failure in step 13.3 stays `merge_failed` |
| TS-4 | The 結果の値 section names `references/merge-result.md` as the owner of the conditions, and the table has each of the 28 codes exactly once |

## Test Notes

- TS-1 is the red state for this task: against the table before this change it
  fails, because the `git_failed` row lacks 3, 4, 6 and 10.
- Term lists come from the text written into the cells, at least one literal term
  per lettered item.
- Absence matchers use phrases only an excluded failure would carry. Positive
  items overlap in wording with excluded ones: `git merge --abort` (item (c) of
  `git_failed` and the abort after a merge failure), `git rev-parse` (items (f)
  and (g) and the post-commit rev-parse), and "no remote can be chosen" and zero
  remotes. A matcher on the shared words alone would fire on correct text.
- A check that no Condition cell carries a step number is an assertion of absence
  and gets its own forged-text case.
- Existing pins in this test file stay true. An assertion that pins the old
  `git_failed` 手順 is updated to the new set.
