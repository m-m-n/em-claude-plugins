# Task Plan: task0003 — Create the --litellm launch home outside the temporary directory

## Goal

On em-workflow's `--litellm` route, `run_codex_exec.sh` creates the
launch-dedicated Codex home in a per-user cache directory instead of the
temporary directory, so that Codex can create its sandbox helper binaries there
and commands run inside the sandbox on that route. Everything else about the
launch home (its content, its isolation from the user's real Codex home, its
removal after the launch) stays as it is.

## Design

### Launch home location
- Cache base: the value of `XDG_CACHE_HOME` when it is set and is an absolute
  path; otherwise `HOME` followed by `/.cache`, when `HOME` is set and
  non-empty.
- Parent: the directory `em-workflow` under the cache base. The wrapper creates
  the parent (and any missing directory above it) when it does not exist.
- Launch home: a new uniquely named directory created directly under the
  parent, accessible to the owner only. It is created per launch, exactly as
  today, and removed when the wrapper exits on every path that removes it today.
- The temporary directory (`TMPDIR`, or `/tmp` when unset) is no longer used for
  the launch home.
- When no cache base can be determined (`HOME` unset or empty, and
  `XDG_CACHE_HOME` not an absolute path), the wrapper writes one diagnostic line
  to standard error and exits with a non-zero status without launching codex.
  This is a new error condition; no existing usage text or error message changes.

### Unchanged
- The launch home's content: a copy of the user's `litellm.config.toml` when it
  exists, and a `config.toml` that marks the working directory, in each
  spelling, and every directory above it as `untrusted`. The user's real Codex
  home is never written, and the launch home is never inside it.
- The default route (no `--litellm`) neither sets `CODEX_HOME` nor creates
  anything under the cache base.
- em-review's wrapper (it has no `--litellm` route).
- IMPLEMENTATION.md D1: the launch home is prepared before the codex launch;
  the wrapper still starts no other process that lives at the same time as the
  launch.
- The wrapper contract of NFR3, and the Stop and PreToolUse registrations.

### Comment block
The "Launch home on the --litellm route" comment states the new location and
that Codex refuses to create its helper binaries under the temporary directory,
which is why the launch home is not placed there.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: On the `--litellm` route, readonly and readwrite, with
  `XDG_CACHE_HOME` set to an absolute directory, the `CODEX_HOME` that the
  stub codex sees is a directory directly under `XDG_CACHE_HOME`'s `em-workflow`
  directory. With `XDG_CACHE_HOME` unset, or set to a relative path, it is
  directly under `HOME`'s `.cache/em-workflow` directory. In every case it is
  not under the `TMPDIR` given to the wrapper and not under the user's Codex
  home.
- [ ] AC-2: During the launch the launch home exists, its permission bits allow
  access to the owner only, and it holds exactly the files the wrapper puts
  there today: `config.toml`, plus `litellm.config.toml` byte-identical to the
  user's copy when the user's Codex home has one. `config.toml` parses as TOML,
  and every project entry in it has `trust_level` equal to `untrusted`,
  including one for the working directory.
- [ ] AC-3: After the wrapper exits, both when the stub codex exits 0 and when
  it exits non-zero, the launch home of that run no longer exists, and nothing
  of the run is left under `TMPDIR`. The user's Codex home is unchanged.
- [ ] AC-4: With `HOME` empty and `XDG_CACHE_HOME` unset, the `--litellm` route
  writes one diagnostic line to standard error, exits non-zero, and does not
  invoke the stub codex.
- [ ] AC-5: On the default route, readonly and readwrite, the stub codex sees no
  `CODEX_HOME` (the test removes it from the inherited environment), and nothing
  is created under the cache base.
- [ ] AC-6 (NFR3): `python3 -m unittest tests.test_codex_hook_wrapper_args`
  passes unchanged, and each `--litellm` run in the new module invokes the stub
  codex exactly once.
- [ ] AC-7 (NFR4): The new module imports only standard-library modules. Every
  wrapper run uses a stub `codex` first on `PATH` and its own `HOME`,
  `XDG_CACHE_HOME` (or none) and `TMPDIR`, all inside a temporary directory the
  test owns, so the user's real cache, Codex home and temporary directory are
  never written.

## Test Notes

- All criteria are subprocess unit tests of the em-workflow wrapper with a stub
  codex. The stub records, while the launch is in progress, the `CODEX_HOME` it
  sees and that directory's permission bits, file listing and file contents,
  because the launch home is removed when the wrapper exits.
- Remove `XDG_CACHE_HOME` and `CODEX_HOME` from the inherited environment in the
  harness, and set `TMPDIR` to a directory separate from the test's `HOME` and
  `XDG_CACHE_HOME`, so that "not under `TMPDIR`" is a meaningful check even
  though the test's own directories are temporary.
- For AC-1, cover the case where the parent `em-workflow` directory does not
  exist yet and the case where it already exists.
- The launch home's content checks (AC-2) are part of this module only to show
  that relocation kept them; the existing behaviour is not redesigned.
- If an existing test outside this task's files observes the launch home under
  `TMPDIR`, that is a plan deviation to report, not a file to change silently.
