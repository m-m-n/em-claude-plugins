# Task Plan: task0002 — em-workflow plugin version bump

## Goal

The em-workflow plugin version moves one patch step in both places that carry
it, so that an installed plugin cache stops serving the pre-change hook set and
picks up this feature's guard.

## Requirements

FR9

## Scope

### Files to Create

None — this task creates no file.

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — the plugin's own version field moves
  to the value pinned in IMPLEMENTATION.md Shared Components.
- `.claude-plugin/marketplace.json` — the em-workflow entry's version field moves
  to the same value; no other plugin entry changes.

## Design

The version value, its starting point and the invariant that both files carry
the identical string are pinned in IMPLEMENTATION.md Shared Components ("Plugin
version value") and are not restated here.

This task changes nothing else. It does not touch the hook registration file,
any hook program, or any test, and it introduces no new field in either
manifest. The repository's own rule on plugin version bumps — one patch step for
a behavioural fix, the same value in both files, no other plugin's version moved
— is the whole content of this task.

The repository already carries a parity check over these two files in its test
suite, so the correctness of this change is observable from the standard test
command without adding a test.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The plugin manifest's version field reads the new value pinned in
      IMPLEMENTATION.md, and no other field of that file changes.
- [ ] AC-2: The marketplace manifest's em-workflow entry reads the identical
      value; no other plugin entry's version, and no other field of that file,
      changes.
- [ ] AC-3: The two values are byte-identical to each other, and the move from
      the previous value is exactly one patch step.
- [ ] AC-4: `python3 -m unittest discover -s tests` passes in full in this
      worktree, including the existing plugin version parity check.

## Test Notes

- No new test file. AC-1 through AC-3 are pinned by the existing version parity
  check in the repository's test suite, which AC-4 runs.
- If the existing parity check turns out not to compare these two files, report
  it as a plan deviation rather than silently adding a new test file — the SPEC's
  declared file structure does not include one for this task.
- There is nothing TDD-shaped here: the change is two literal values in two
  manifests, and the assertion that binds them already exists.

## Out of Scope

- Everything in the guard itself: the hook program, its tests and its
  registration (task0001). Do not edit the hook registration file or any file
  under the plugin's hooks directory.
- Bumping any other plugin's version.
- Adding a per-feature version-bump test file.
- Refreshing the installed plugin cache or restarting Claude Code; that is an
  operator action reported at feature completion, not a code change.
