# Task Plan: task0002 — heredoc stdin guard: correct the emitted output shape, its assertions, and the version baseline

## Goal

The object the guard places on standard output carries the event-name member the
runtime requires, so the rewrite it returns is actually applied instead of being
discarded; the contract tests assert that corrected shape against a single
in-repo schema fixture instead of a hand-written member list; and the plugin
version moves one further patch step in both manifests with its regression
baseline re-anchored so the move cannot be skipped silently.

## Requirements

FR1, FR3, FR5, FR8, FR9, NFR5, NFR6

## Scope

### Files to Create

None. Every file this task touches already exists in the tree.

### Files to Modify

- `em-workflow/hooks/heredoc-stdin-guard.py` — the single place that builds the
  emitted object: add the event-name member to the hook-specific output, with the
  PreToolUse event name as its value. Nothing else in the guard changes — not the
  detection reading, not the idempotency rule, not the rewritten-command shape,
  not the fail-open paths, not the exit status.
- `tests/test_heredoc_stdin_guard.py` — introduce the hook-output schema fixture
  as one module-level declaration; rewrite the shared rewrite-assertion helper to
  check the guard's parsed standard output against that fixture instead of
  against a hand-written member list; add the dedicated schema-conformance case.
  The existing cases keep their payloads and their expectations otherwise.
- `tests/test_heredoc_stdin_guard_version_bump.py` — raise the baseline patch so
  the pre-change value fails, and re-anchor the forged pre-bump sample to the
  value the baseline must now reject. Structure, matchers, negative proofs and
  non-vacuity guards are otherwise unchanged.
- `em-workflow/.claude-plugin/plugin.json` — em-workflow version one patch step
  up from the value the tree currently holds, to the value pinned in
  IMPLEMENTATION.md Shared Components; no other field changes.
- `.claude-plugin/marketplace.json` — the em-workflow entry's version to the same
  value, identical to the plugin manifest; no other entry and no other field
  changes.

## Design

See IMPLEMENTATION.md for the PreToolUse decision contract, the hook-output
schema fixture contract, the rewritten-command shape, the plugin version value
and the version baseline assertion — they are pinned there and are not restated
here. D9 (why this is one task), D10 (why the event-name member), D11 (the
automated/manual boundary and the no-installed-binary constraint) and D12 (the
version re-anchoring) are the decisions this task implements.

### What is being corrected, and what must not move

The guard's decision logic is correct and stays untouched. The defect is
entirely in the envelope the decision is delivered in: the hook-specific output
object was emitted without the member that names the event it belongs to, so the
runtime's output validator rejected it and the updated input was never applied.
The guard therefore passed every test while having no effect at all.

Three things must not change while fixing it:

1. **No permission-decision member is introduced.** The guard's two outcomes stay
   "one updated-input object" and "nothing" (IMPLEMENTATION.md D4).
2. **The rewritten command text is untouched.** Same cut-off token, same newline,
   same original command text byte-for-byte.
3. **Every fail-open path stays silent and exits 0.** The correction is on the
   success path only; no failure path gains an output.

### Test-layer correction

The existing shared rewrite-assertion helper asserts an exact member set over
the hook-specific output object, built from a member list written by hand. That
list omitted the event-name member, so the helper does not merely fail to detect
the defect — it pins it, and goes red against the correct output. The correction
is not to loosen the assertion:

- The exact member-set assertion is KEPT. It is what pins "no permission-decision
  member is ever emitted" (NFR5), and loosening it to a membership check would
  silently give that property up.
- The set it asserts is taken from ONE declaration — the schema fixture — rather
  than being restated at the call site. One declaration is the difference between
  a fixture that can be reviewed against the runtime's documented schema and a
  list that can drift unnoticed.

The dedicated schema-conformance case then checks a rewrite-target output
against the fixture as a whole: the required top-level member is present, the
hook-specific output's member set is exactly the required set, the event-name
member holds the required event name, and the updated-input member is present
with the expected command. That case is the one that would have caught this
defect.

### Fixture sourcing constraint

The fixture is a literal declaration written into the test module. It is NEVER
derived by reading an installed Claude Code build — not its binary, not its
bundled documentation, not any path under the user's home directory. A test that
reads an installed build depends on that build being present, on its version, and
on a private file layout, and stops being deterministic. What the runtime
actually does with a conformant output is confirmed once by hand, as the verify
phase's manual scenario (IMPLEMENTATION.md D11); it is not this task's concern.

### Version bump and its baseline

Both manifests move together to the single value pinned in IMPLEMENTATION.md
Shared Components. The per-feature version-bump module's baseline is raised so
that the value the tree held before this task fails it, and its forged pre-bump
sample is re-anchored to that same now-rejected value so the negative proof keeps
exercising the comparison rather than a parse failure. The module's matchers, its
equality assertion, its two negative proofs, its two non-vacuity guards and its
untouched-neighbour regression guards are all kept as they are — this is a
re-anchoring, not a rewrite.

Write the baseline change BEFORE editing the manifests, so the module is observed
red first. That red is the whole point of choosing the baseline this way
(IMPLEMENTATION.md D12).

## Test Notes

- Every test stays in the two existing modules. No new test file is created —
  the schema fixture and the conformance case belong in the guard contract-test
  module, next to the helper that consumes the fixture.
- Order of work: change the assertion helper and add the conformance case FIRST,
  observe them red against the current guard, then correct the guard. The red is
  the proof that the assertion actually reaches the defect; correcting the guard
  first turns this into an unverifiable claim.
- Same order for the version half: re-anchor the baseline, observe the module
  red, then edit the two manifests.
- AC-7 is a regression criterion, not new coverage. Re-run the existing cases as
  they are; do not rewrite their payloads while touching the helper they share.
- Do not add a test that reads an installed Claude Code build, its binary, its
  bundled schema help, or anything under the user's home directory. The fixture
  is a literal in this repository (IMPLEMENTATION.md D11).
- Do not add a test that requires the stdin-reading CLI named in the SPEC, or a
  restarted Claude Code. That confirmation is a verify-phase manual item
  (IMPLEMENTATION.md D7, D11).
- TDD-awkward: "the runtime accepts this output" is not provable from a test
  process. The planned handling is the schema fixture as the automated proxy plus
  the manual verify-phase scenario; do not build a harness that launches Claude
  Code to chase completeness.

## Out of Scope

- Changing the guard's detection reading, its idempotency rule, its rewritten
  command text, its fail-open paths or its exit status.
- Changing the hook registration file: the array, its order, its seventh entry's
  command, timeout or status message all stay as task0001 left them.
- Adding a permission-decision member of any value to the emitted object.
- Changing the repository-wide plugin version parity check's own floor, or any
  other feature's version-bump module baseline.
- Bumping any plugin other than em-workflow.
- Investigating or remedying the downstream permission-prefix matching effect
  recorded in IMPLEMENTATION.md's Risk Assessment; it is a verify-phase
  observation item, and any remedy is a separate issue.
- Correcting the stale version literal in SPEC.md; that is an open question for a
  later phase, not a change this task makes.
