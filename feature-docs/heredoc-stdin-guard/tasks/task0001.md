# Task Plan: task0001 — heredoc stdin guard: program, contract tests, registration, version bump

## Goal

A PreToolUse guard exists in the em-workflow plugin that, for a Bash command
containing a heredoc and no head-position stdin redirection, returns the same
command with a stdin cut-off prepended; it is registered as the last entry of
the PreToolUse Bash matcher so that no other guard's input changes; and the
plugin version is bumped in both manifests in the same change, with a test that
goes red if the bump is missing.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR9, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Design

See IMPLEMENTATION.md for the decision contract, the rewritten-command shape,
the invocation form, the plugin version value, the version baseline assertion and
the fail-open policy — they are pinned there and are not restated here.

### Decision flow (the guard's own logic)

1. Read everything available on standard input and interpret it as one event
   object. Anything that prevents that — no input, input that is not one
   well-formed object — ends the run with no output.
2. If the tool name is not exactly the Bash tool's name, end with no output.
3. Take the command from the tool input mapping. If it is absent, not a text
   value, or empty, end with no output.
4. Decide whether a heredoc operator is present: a run of exactly two
   consecutive less-than characters, optionally followed by the dash form,
   occurring where the shell would read it as a redirection operator. A run of
   three consecutive less-than characters is a here-string and is never counted.
   Text inside a heredoc body already opened earlier in the command is not
   scanned for further operators.
5. Decide whether standard input is already redirected at the head of the
   command: the first command of the script either is a redirection-only
   statement that redirects standard input, or itself carries a standard-input
   redirection. The exact token this guard inserts is one instance of that case,
   which is what makes a second application impossible.
6. Rewrite only when step 4 says yes and step 5 says no. Otherwise end with no
   output.
7. Build the result by copying the whole tool input mapping and replacing only
   the command with the rewritten-command shape from IMPLEMENTATION.md. Emit one
   object carrying that mapping under the hook-specific output member.
8. Any unexpected failure anywhere above is caught and ends the run exactly like
   step 1 does: no output, exit status 0.

### Precision boundary

The reading in step 4 does not need to be a complete shell parser. When the
command text cannot be settled — an unterminated quote, a construct the reader
does not model — the guard treats the command as undecidable and ends with no
output (FR6). Over-detection is acceptable and under-detection is safe, because
the only effect of a rewrite is a closed standard input (IMPLEMENTATION.md D4).

### Registration

The seventh entry of the PreToolUse Bash matcher, built to the invocation form
pinned in IMPLEMENTATION.md Shared Components. The existing six entries keep
their order, their commands, their timeouts and their status messages.

### Version bump and its baseline module

The two manifests move together to the single value pinned in IMPLEMENTATION.md
Shared Components. The new baseline module follows the shape the sixteen existing
per-feature version-bump modules in this repository already use — read it from a
recent one (for example the exit4-tip-argument or muse-consent module) and mirror
its structure rather than inventing a new one:

- Both manifests are parsed as JSON; the marketplace entry is located by its
  name field, never by array position.
- The version assertion is a durable baseline, not a fixed literal: major and
  minor are `0` and `1`, and the patch number is strictly greater than 72. A
  literal equality against `0.1.73` would go stale at the next unrelated bump.
- The same baseline assertion is applied to both manifests, and a second
  assertion requires the two version strings to be identical.
- Each matcher carries a negative proof (a forged pre-bump value is rejected, two
  forged differing values are rejected) plus a non-vacuity guard showing the
  forged samples are themselves well-formed, so the proof exercises the
  comparison rather than a parse failure.
- Untouched neighbouring fields (the plugin manifest's name, the other
  marketplace entry) are asserted as plain regression guards and need no negative
  proof.

Baseline choice: 72, because both manifests read `0.1.72` before this task's
edit. Choosing 72 is what makes the module red on the un-bumped tree — the
repository-wide parity check's floor of `0.1.50` and the newest existing
per-feature module's floor of 71 both stay green there, so this module is the
only thing that detects a forgotten bump (IMPLEMENTATION.md D8).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: For a Bash event whose command contains a heredoc and no
      head-position stdin redirection, standard output is exactly one object
      whose updated-input command equals the cut-off token, a newline, then the
      original command text unchanged; every other field of the tool input
      mapping is reproduced with its original value and type; exit status is 0.
      Covers FR2, FR3, FR5.
- [ ] AC-2: A command with no heredoc operator, and a command whose only
      candidate operator is a here-string, each produce empty standard output and
      exit status 0. Covers FR2.
- [ ] AC-3: A command whose standard input is already redirected at its head —
      including a command that already begins with the cut-off token this guard
      inserts — produces empty standard output; feeding the guard its own output
      a second time never yields a command carrying the token twice. Covers FR4.
- [ ] AC-4: Input that is not well-formed, an event with no command, an empty
      command, a command that is not a text value, and an event whose tool name
      is not the Bash tool each produce empty standard output and exit status 0.
      Covers FR6.
- [ ] AC-5: Executing a rewritten command in a real shell against a temporary
      directory writes the heredoc body byte-for-byte identical to the body in
      the original command — content, interior newlines and terminator intact —
      and no file outside that temporary directory is touched. Covers FR3.
- [ ] AC-6: Across every case in the new guard test file, the guard's standard
      output never contains a permission-decision member and its exit status is
      always 0. Covers NFR5.
- [ ] AC-7: The guard imports only Python standard-library modules, and its
      decision path starts no other process, opens no network connection, writes
      no file and writes nothing to standard error. Covers NFR1, NFR2.
- [ ] AC-8: The PreToolUse Bash matcher holds exactly seven entries; the seventh
      invokes the guard in the pinned invocation form with a 10-second timeout;
      the first six are unchanged in order, command, timeout and status message —
      pinned by an assertion in the registration test so a later reordering
      fails. Covers FR7, NFR3, NFR4.
- [ ] AC-9: Both manifests carry em-workflow version `0.1.73`; the plugin
      manifest's name field and every other field of both files are unchanged, and
      no other plugin's version in the marketplace manifest moves. Covers FR9.
- [ ] AC-10: The new version-bump module is discovered by the suite, parses both
      manifests as JSON, asserts in each that the version is `0.1.<patch>` with
      patch strictly greater than 72, asserts the two version strings are
      identical, and carries a negative proof plus a non-vacuity guard for each of
      those two matchers. Reverting only the two manifest edits makes this module
      fail. Covers FR9.
- [ ] AC-11: `python3 -m unittest discover -s tests` passes in full in this
      worktree and includes both new test files, and
      `python3 em-workflow/hooks/tests/run-destructive-guard.py` still passes.
      Covers FR8, NFR4.
- [ ] AC-12: No file outside the em-workflow plugin directory, the
      repository-root marketplace manifest and the repository-root test directory
      is modified; no reference to the undocumented feature flag named in SPEC.md
      is introduced. Covers NFR6.

## Test Notes

- Unit (contract) tests, all in the new guard test file, all launching the guard
  as a separate process: AC-1 (two payload variants — a bare heredoc write, and a
  heredoc followed by a stdin-reading command stood in for by a harmless
  placeholder), AC-2, AC-3, AC-4 (five payload variants), AC-6 (assert over the
  whole case corpus rather than per case).
- Integration test, same file: AC-5 runs the rewritten command in a real shell
  with a temporary directory as its target and compares the written bytes against
  the original heredoc body. Never writes outside that temporary directory.
- Static assertion, same file: AC-7's import check reads the guard's own source
  text and asserts every imported module resolves to the standard library. The
  "no process, no network, no file write" half is a code-review item as well as a
  source-text assertion; it is not provable by execution alone.
- Registration assertion: AC-8 belongs in the registration test file, not in the
  new guard test file — FR8 scopes the new guard test file to detection and
  execution tests.
- Version assertions: AC-9 and AC-10 live together in
  `tests/test_heredoc_stdin_guard_version_bump.py`, not in the guard test file.
  Write that module BEFORE editing the manifests so it is observed red first —
  that red is the whole point of the chosen baseline.
- AC-12 is verified by reading the task's own diff; it needs no test of its own,
  and no test should be invented to police it.
- TDD-awkward: AC-7's negative properties (nothing is started, nothing is
  written) cannot be proven exhaustively by a test. The planned handling is the
  source-text assertion above plus the security review perspective; do not invent
  a sandbox to chase completeness.
- Do not add a test that requires the codex CLI or a restarted Claude Code — that
  confirmation is a verify-phase manual item (IMPLEMENTATION.md D7).
