# Task Plan: task0001 — pip routes audit only a prepared pinned inventory

## Goal

Every pip scan unit is audited by starting pip-audit only on prepared requirements files that hold statically extracted, validated pins. The target flag and arguments come from a per-target-form table in the registry. A unit with excluded or no auditable items reports a fixed `skip_reason` token, and every test pin that encodes the old shape is updated in the same change.

## Design

Cross-task contracts (target form, extraction, prepared-file scope, job construction, skip tokens) and decisions D1-D7 are in IMPLEMENTATION.md. This section covers only the per-task detail.

### 1. Registry

- The pip entry's top-level `args` and `target_flag` are replaced by `target_forms`.
- `target_forms` is a block-style nested mapping. It holds exactly one form, `prepared_requirements`, with `target_flag` `-r` and `args` `--no-deps`, `--disable-pip`, `--format`, `json`, in that order.
- `manifests`, `executable`, `severity_map` and `threshold` keep their values.
- The header comment:
  - documents `target_forms` and the form;
  - no longer describes a pip top-level `args` / `target_flag`;
  - keeps its ownership phrases (which tool serves each manifest; the script owns how to run and how to normalize);
  - keeps the cargo sentence on where its arguments go.
- The npm, cargo and go entries stay byte-identical.

### 2. Target-form validation (D4)

- `validate_ecosystem_entry` checks `target_forms` whenever an entry carries it. It must be a non-empty mapping. Each form is a mapping with:
  - a non-empty string `target_flag` that passes the same token rule as `args`;
  - a list `args` whose every item passes that rule.
- A pip entry must carry the form `prepared_requirements`.
- Any failure returns `<ecosystem>_target_forms_invalid`. The checks that exist today keep their order and reasons.

### 3. pip job construction

- For every pip manifest kind (requirements, root or nested pyproject, poetry.lock, Pipfile.lock), `build_scan_job` builds the IMPLEMENTATION.md form.
- It reads the flag and arguments from the form and writes neither flag literally.
- `_pip_target` and every other path to the directory form or the reviewed-file form are removed.
- The npm, cargo and go branches, the target-path validation, the cwd rules and the environment are unchanged.
- `build_command` keeps its contract (D5).

### 4. Extraction component: requirements files

The walk is the same walk the requirements direct-name resolver uses:
- the existing logical lines and option splitting;
- includes resolved through the existing confinement, each file opened at most once;
- `-c` and the value-only options consumed and never opened.

**Pin rule.** A requirement line is a pin when, after its `--hash` options are removed (both the separated form and the `=` form), the rest consists of exactly these parts:
- a name;
- optionally one extras group in square brackets (dropped);
- the operator `==`, with optional whitespace around it;
- a version.

The version is made only of letters, digits and the characters `.`, `+`, `!`, `-`, `_`. This excludes wildcards, `===`, other operators, commas, markers and direct references. The pair (canonical name, version) must also pass `_pip_pin_is_valid`. The same pin rule serves `[project].dependencies` items.

**Excluded count.** Each of the following adds one:
- a non-option line that is not a pin;
- an editable item;
- an undetermined (abbreviated) option item;
- an option line that cannot be split;
- an include that may not be opened (URL, outside the root, unresolvable, empty);
- a file in the walk that cannot be read, starting file included (missing, a directory, non-UTF-8, unreadable, outside the root).

The following add nothing:
- constraint options;
- value-only options;
- an include of an already-visited file.

### 5. Extraction component: pyproject.toml

Pins are read from the tables the direct-name resolver reads (as-pyproject-pin-sources).
- **`[project].dependencies`:** each string item goes through the pin rule.
- **Poetry tables:** `[tool.poetry.dependencies]` and `[tool.poetry.dev-dependencies]`, with `python` ignored. An entry is a pin only when its value is a string made of `==` followed by a version that passes the pin rule. Every other value adds one excluded item: a bare version, `^`, `~`, `*`, a range or a table.
- **Shapes and dynamic declarations:** a non-string list item, a non-list `dependencies` or a non-mapping poetry table each adds one excluded item. So does a `[project].dynamic` that lists `dependencies` without a static list.
- **Tables never read:** optional dependencies, dependency groups and poetry group tables. They contribute nothing.
- **Unusable file:** a file that cannot be confined, read or parsed gives no pins and an excluded count of one.
- **No declaration:** valid TOML with no declaration gives no pins and a count of zero.

### 6. Manifest route (`_scan_pip_group`, non-lockfile target)

1. The existing TOML-parser check runs first (D7).
2. Extract pins from the unit's target.
3. No pins: add `pip_manifest_unpinnable` and stop. Nothing is launched, and the unit does not complete.
4. Otherwise, group the pins with `_group_pip_pins`. Inside the existing prepared-file scope, run one job per prepared file, in group order.
5. Each completed run is normalized with the reviewed manifest as its label.
6. A run that does not complete adds its reason once, and the other runs continue. The unit completes when at least one run completed.
7. When the excluded count is at least one, add `pip_manifest_entries_unpinnable`. The findings are kept.
8. The unit's `excluded` stays zero (D3).

### 7. Lockfile route

- Conversion, the declaration check, the reasons, the lockfile note and the prepared-file scope (including its file-name prefix) are unchanged.
- Its jobs come from the same form, so its argv is unchanged.

### 8. Test pins (FR7)

**Restricted parsers.** The parsers in the invocation and normalization modules learn the nested `target_forms` block and stay standard-library only.

**Unpinned fixtures.** A fixture that expected an unpinned or partly pinned manifest to complete takes one of two updates:
- it is pinned, when the test is about directness;
- it expects the new token, when the test is about completion.

**Directness.** Direct-name expectations do not change.

**Shared expectations that stay unedited.**
- The `forbidden_tokens` tuple.
- The executable allowlist, the lockfile sets and the pip environment-pin expectations.
- The lockfile suite.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR5; TS-6): the loaded pip entry has no top-level `args` or `target_flag`. Its `target_forms` holds exactly `prepared_requirements`, with `target_flag` `-r` and `args` `--no-deps`, `--disable-pip`, `--format`, `json`, asserted through both restricted parsers and the script's loader against literals. The header comment names `target_forms` and keeps its ownership phrases. The npm, cargo and go entry texts equal their pinned literal texts.
- [ ] AC-2 (FR5; TS-6): `validate_ecosystem_entry` returns None for the shipped pip entry. It returns `pip_target_forms_invalid` for each of the following:
  - a missing `target_forms`, a missing `prepared_requirements`, or a non-mapping form;
  - a missing, empty or non-string `target_flag`;
  - a non-list `args`;
  - a token containing a shell metacharacter or starting with a path separator.

  With such a registry, `run_scan` reports `pip_target_forms_invalid` once and starts no scanner. The validation reasons of the npm, cargo and go entries are unchanged.
- [ ] AC-3 (FR1, FR4, FR5, NFR1; TS-1; TM-1): the following targets are each given a prepared file outside the project root: `requirements.txt`, `x/requirements.txt`, `pyproject.toml`, `svc/pyproject.toml`, `poetry.lock` and `Pipfile.lock`. For each, the pip job's argv equals the executable path, `-r`, the prepared file, `--no-deps`, `--disable-pip`, `--format`, `json`, and its cwd is the project root. No argv element contains the project root or the reviewed file. Without a prepared file, every one of these targets raises `JobConstructionError`. An in-memory entry whose form arguments differ produces argv that follows that entry. Neither `--no-deps` nor `--disable-pip` appears in the source text of `build_scan_job`, and `_pip_target` no longer exists.
- [ ] AC-4 (FR2, NFR1; TS-2; TM-2, TM-3, TM-4): for a requirements fixture, extraction returns exactly the pins of these lines:
  - an exact pin with extras;
  - an exact pin with spaces around `==` and `--hash` options;
  - an exact pin in an in-root include.

  Names are in canonical form. The excluded count equals the number of lines of these kinds: `-e .`, `--editable=./x`, a local path, a URL, a VCS reference, a marker, `==1.*`, `===`, a range, a compatible-release specifier, a bare name, an abbreviated option, an unsplittable option line, and includes that leave the root, are URLs, or are missing. The open-recorder observes the following:
  - a `-c` file and every out-of-root file are never opened;
  - every opened file lies inside the root and is opened once (an include cycle ends);
  - no file is written and no process starts.

  Random and malformed content (non-UTF-8 bytes, a byte-order mark, a directory as target) never raises.
- [ ] AC-5 (FR2; TS-2; TM-2, TM-3, TM-4): for pyproject fixtures, `[project].dependencies` items follow the same pin rule. Poetry entries count as pins only for `'==<version>'` string values, and the bare version, `^`, `~`, `*`, range and table values are each counted as excluded. `python` is ignored, and optional-dependency and group tables contribute nothing. The following each give no pins and never raise:
  - a dynamic-only declaration;
  - no declaration;
  - invalid TOML;
  - non-UTF-8 content;
  - a file symlinked outside the root.
- [ ] AC-6 (FR1, FR3, FR6; TS-3, TS-4; TM-1, TM-2): `run_scan` is run with the recording stub.
  - A fully pinned requirements unit launches once. The recorded `-r` file holds exactly the sorted canonical pin lines, and the result has `skipped` false and no reason.
  - A mixed unit launches on the pins and keeps the stub's findings. Its `skip_reason` contains `pip_manifest_entries_unpinnable`, `skipped` is true, and pip is still counted as scanned.
  - A unit with no auditable item, for both requirements and pyproject, never starts the stub. Its pip reason is exactly `pip_manifest_unpinnable`, never together with `pip_manifest_entries_unpinnable`.
  - `pip_lockfile_entries_unpinnable` never appears for a manifest unit.
- [ ] AC-7 (FR3, NFR4, NFR5; TS-2, TS-3, TS-8; TM-6): one name at two versions across a requirements file and its include gives two prepared files and two launches, in group order, each file holding that name once. Scanning the same input twice gives byte-identical result JSON and identical recorded file contents. With fixtures that carry distinctive package names and paths, neither `skip_reason` nor `summary` contains any of those names, those paths or the project root.
- [ ] AC-8 (NFR2; TS-7; TM-7): the process temporary directory points at a test-owned directory outside the project root. Every prepared file the stub recorded is owner-only and is absent after the scan in each of these cases:
  - normal completion;
  - a launch that does not complete;
  - an exception injected into the execution step, which propagates.

  A byte snapshot of the project tree is identical before and after each case.
- [ ] AC-9 (FR4, NFR3; TS-5; TM-5): `tests/test_sca_pip_lockfile_audit.py` passes without edits. The lockfile argv, reasons and `pip_lockfile_entries_unpinnable` note expectations elsewhere keep their values. The pip child-environment pins, the executable allowlist and absolute-path resolution expectations pass without changes to their expected values.
- [ ] AC-10 (FR7, NFR6; TS-9): every test that encoded the old pip shape is updated, and the `forbidden_tokens` tuple is unchanged. Every new or changed test module imports only the standard library, and no test starts a real scanner. `python3 -m unittest discover -s tests` exits 0.
