# Task Plan: task0006 — Evaluator handoff and reporting of both coverage fields

## Goal

The evaluator receives `unreviewed_perspectives` and
`partially_reviewed_perspectives`, and the Phase R6 report and the batch final
result show both, so an unreviewed range is never presented as a clean review.

## Requirements

FR15, FR16, FR18

## Scope

### Files to Create

### Files to Modify

- `em-workflow/references/review-evaluation-contract.md` — the Input Block and the Independent Inspection Duty

## Design

Cross-task rules: IMPLEMENTATION.md Shared Components (coverage fields), D5
(reason tokens), D9 (failure handling), D10 (this task owns Phase R3a and Phase
R6), D11 (where the fields surface).

**Phase R3a.** The `unreviewed_perspectives` input bullet keeps "the same list
Phase R5 records at the round-record root" and "present and empty when there are
none", and drops the definition through the Claude fallback. Both fields are
computed by the `coverage` operation over the loop-0 pass right after Phase R2b,
before the evaluator dispatch. A failure aborts as D9 states. A new bullet
`partially_reviewed_perspectives` follows: same source, same empty rule. The
Independent Inspection Duty does not apply to a perspective in
`unreviewed_perspectives` and still applies to a perspective in
`partially_reviewed_perspectives`.

**Evaluation contract and evaluator.**
- The contract's Input Block gains `partially_reviewed_perspectives`: entries
  with `perspective`, `unreviewed_files` and `reason`.
- The contract's Independent Inspection Duty states the same exemption split as
  Phase R3a. A partially reviewed perspective is inspected like any other, and
  its unreviewed files may be among those the evaluator reads.
- The evaluator's Step 3 keeps its exemption for `unreviewed_perspectives` and
  states that a perspective in `partially_reviewed_perspectives` is inspected.
- Neither file restates the retryable `skip_reason` strings (an existing test
  forbids it).

**Phase R6.** The report renders, from the round record, each perspective of
`unreviewed_perspectives`, and each entry of `partially_reviewed_perspectives`
with its reason and its full unreviewed file list. This is disclosure only and
affects no gate. The batch final result carries the same content through
batch-mode.md's Reporting item list.

**batch-mode.md.**
- The Reporting item list gains one item, placed after the autonomous
  fail-closed-route item and immediately before "every review round whose triage
  filing was incomplete": every review round's `unreviewed_perspectives` and
  `partially_reviewed_perspectives`, with each partial entry's reason and
  unreviewed files.
- The audit-item source map gains one row, placed immediately before the
  triage-filing row. It maps that item to
  `feature-docs/{feature}/reviews/roundN.yaml` `unreviewed_perspectives` /
  `partially_reviewed_perspectives`, citing `references/review-phase.md` Phase R5.
  The kept-branch row stays last, the triage row second to last.
- The section names no provider or model (no Muse, Vertex, GPT or GLM) and no
  usage-limit wording. It holds none of "processing order", "malformed",
  "automatic retry" or "duplicate detection". The level-2 heading list and the
  `gate_id` count of the file stay the same.

**Pin updates.** `REPORTING_ITEM_LIST_SENTENCE` and `SOURCE_MAP_EXPECTATIONS` in
`tests/test_batch_quiet_output_discipline.py` take the new item and row. The four
source-map row counts of 8 (in the audit-persistence, audit-record-contract,
wrapper-fallback and triage-receipt modules) become 9. No other assertion of
those modules changes.
