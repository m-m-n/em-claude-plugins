# Task Plan: task0001 — bash_guard.py: exclude top-level operators from the cd prefix allow

## Goal

The hook allows `cd "{worktree_path}" && <approved string>` only when the
whole approved string runs in the worktree: a remainder that IMPLEMENTATION.md
C1 excludes gets the decision of the unchanged table instead, and the module
docstring states the new condition.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR9, FR10, NFR1, NFR2, NFR3, NFR4, NFR7

## Scope

### Files to Create
- `tests/test_bash_guard_cd_prefix_operators.py` — hook cases for FR1 to FR5 and the docstring check for FR9

### Files to Modify
- `em-workflow/hooks/bash_guard.py` — cd prefix allow narrowed by rule C1, decision order per C2, module docstring cd prefix conditions extended

## Design

### Exclusion check (implements IMPLEMENTATION.md C1)

- One deterministic check that takes R (the trimmed remainder — the same
  string compared with the approval store) and answers excluded / not
  excluded by the scan model and rules E1–E10 of C1.
- A hand-written left-to-right character scan. Do not use a general-purpose
  tokenizer whose quoting rules differ from Bash.
- No file read, no child process; the path of the cd prefix is not involved.

### Decision order (implements IMPLEMENTATION.md C2)

- The existing cd prefix candidate determination (syntax, approved
  remainder, path below the worktree area — currently the function that
  checks the cd-prefixed approved form) stays as it is and keeps deciding
  workflow relevance (C2 step 2).
- The cd prefix allow (C2 step 6) additionally needs "not excluded".
- The unapproved deny (C2 step 7) is given only when the whole command is
  declared; an excluded candidate that is neither approved nor declared
  gives no decision (C2 step 8).
- Every decision reason and additional-context string stays as it is,
  `UNAPPROVED_GUIDANCE` included (SPEC A6). The CLI modes do not change.

### Module docstring (FR9)

- The bullet list under "cd prefix:" gains the C1 condition: no lone `&`,
  `;`, `||` or line break at the top level of the remainder, outside quotes
  and backslash escapes, with the recognized tokens `&&`, `|&`, `>&`, `<&`,
  `&>`, `&>>` not counted; and the safe-side exclusions E5–E10 with their
  positions.
- The existing statements stay: a command that fails a condition is judged
  as if it had no cd prefix (never a new deny), and the refusal patterns are
  applied to the whole command first. Add that the refusal check does not
  depend on the operator condition.

### Constraints

- NFR2: no identifier and no string literal in the executable text (outside
  comments and docstrings) contains the substring `status`.
- NFR1: standard library only.
- NFR3: `em-workflow/hooks/queue_launch_guard.py`,
  `em-workflow/scripts/merge-task.sh` and `em-workflow/hooks/hooks.json` are
  not edited.
- `tests/test_bash_guard_cd_prefix.py` is not edited.

## Test Notes

- Follow the hook-test method of IMPLEMENTATION.md Conventions. The fixture
  of `tests/test_bash_guard_cd_prefix.py` is the model; the new module builds
  its own fixture rather than importing from that module.
- The record CLI stores one string per line and refuses refusal patterns, so
  the line-feed strings (AC-1) and the refusal strings (AC-5) go into the
  store file directly. Unclosed quotes and trailing backslashes can go
  through the record CLI.
- AC-4's declared cd prefix string is written into a temporary
  `feature-docs/<name>/workflow.yaml` as a `test_command` line after the
  temporary path is known. Keep `#` out of declared values.
- AC-1 to AC-3 are table-driven like the existing module (expected decision,
  label, command template).
- Every allow case asserts the cd prefix reason, so a case that passes only
  through the exact-match branch is caught.
