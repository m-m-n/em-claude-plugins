# Task Plan: task0003 — planner contract, create-plan dispatch and the TASK.md append permission

## Goal

The planner contract and the create-plan phase protocol admit THREAT-MODEL.md
as a planner input and output, and define the single permitted minimal-tier
write to TASK.md, without adding any phase, step, gate or write_policy action.

## Requirements

FR5, FR6, NFR2

## Design

### planner-contract.md (owner of SC-3 and of the planner-side shapes)

- **Responsibility**: the produced artifacts include THREAT-MODEL.md.
- **planning_inputs**: the field listing gains `threat_model_template` (the
  absolute path of `references/templates/threat-model.md`).
- **write_policy paragraph**: THREAT-MODEL.md is a target with the same
  action rule as IMPLEMENTATION.md (`create` on a first pass, `replace_own`
  on a same-phase rewrite; the existing re-plan authorization path applies
  unchanged). At the minimal tier, TASK.md is an `extend_only` target with
  its dispatch-time `expect_digest`.
- **New `###` subsection inside the planning_inputs section** (before the
  Question packet bundling rule heading), owning SC-3 in full: when it
  applies, the exact-prefix rule, the no-heading rule, the final-section
  precondition and its `blocked` outcome, written_artifacts listing only
  when appended, and that this is the Markdown counterpart of the
  extend_only key-comparison rule owned by spec-writer-contract.md.
- **digest_inputs**: adds the existing THREAT-MODEL.md (alongside the
  existing IMPLEMENTATION.md / VERIFICATION.md / tasks/ entry) and
  `references/templates/threat-model.md`.
- **completed payload**: the written_artifacts comment lists THREAT-MODEL.md
  and TASK.md (minimal tier, only when appended). The payload triple itself
  is unchanged.
- Existing test anchors stay intact: the Question packet bundling rule,
  digest_inputs, completed payload, Prohibited fields and Task
  decomposition headings keep their exact text and their required phrases;
  the complexity-criteria wording is not copied in.

### create-plan-phase.md

- **Section 1**: the planner's outputs include THREAT-MODEL.md; the pass
  runs at every tier.
- **Section 4 (dispatch)**: the registry/template path list gains
  `references/templates/threat-model.md`, passed as
  `planning_inputs.threat_model_template`; `write_policy` names the
  THREAT-MODEL.md target and, at the minimal tier, the TASK.md
  `extend_only` target (cited to planner-contract.md).
- **Scope-check delta**: stated here as a delta on create-spec-phase.md's
  Scope verification (cited, not repeated): at the minimal tier the
  pre-dispatch snapshot keeps TASK.md's full content, and the post-dispatch
  check applies planner-contract.md's append rule to it.
- **Section 7**: the written artifacts list gains THREAT-MODEL.md and TASK.md
  (minimal tier, only when appended).
- **Section 9**: the human-review list gains "every TM-n of a
  `threats-identified` model is reflected per the plan-writing reflection
  rules", as an invariant the validator script does not implement.
- Section 2a's pinned trigger sentence, the section 3 and section 4
  headings, and the citation of create-spec-phase.md stay; the document
  never gains the literal hashing command or trash command that existing
  tests forbid.

### spec-writer-contract.md

- One pointer inside the `extend_only` key-comparison rule: besides
  `design-system/tokens.yaml`, the planner's minimal-tier TASK.md append
  uses `extend_only` under the Markdown rule owned by planner-contract.md.
  The six-action set and the action table are unchanged.
