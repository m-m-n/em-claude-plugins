# Task Plan: task0002 — implementation-planner threat-modeling step and mitigation carriage

## Goal

The implementation-planner prompt runs the threat-modeling pass on every
dispatch, writes THREAT-MODEL.md, and carries each TM-n into the task ACs and
VERIFICATION.md (TASK.md's Expected Result at the minimal tier).

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR10, NFR1, NFR2

## Scope

### Files to Create
- `tests/test_threat_model_planner_agent.py` — document-contract tests for the planner prompt changes

### Files to Modify
- `em-workflow/agents/implementation-planner.md` — new threat-modeling step, mitigation carriage in the existing steps, inputs, outputs and report
- `em-workflow/.claude-plugin/plugin.json` — version field only, and only when the commit guard rejects this task's commit (IMPLEMENTATION.md SC-6)
- `.claude-plugin/marketplace.json` — em-workflow entry's version field only, same condition and same value as plugin.json (SC-6)

## Design

The prompt owns WHEN the pass runs and WHAT the planner writes and reports;
the format belongs to the template (SC-1), the judgment criteria and
reflection rules to plan-writing, the TASK.md append rule to
planner-contract.md. The prompt cites those by path and restates none of
them.

- **Inputs paragraph**: the parenthesized list of `planning_inputs` fields
  gains `threat_model_template` (SC-1). The LESSONS.md paragraph and the
  worktree paragraph stay byte-identical.
- **New step**: a `### 2a.` step between step 2 (TBD detection) and step 3
  (cross-task design decisions), marked MANDATORY. It states: after reading
  SPEC.md / REQUIREMENTS.md / DESIGN.md (TASK.md at the minimal tier, per
  create-plan-phase.md's single-task shape), identify trust boundaries and
  analyze them with STRIDE on every dispatch, at every tier (full / reduced
  / minimal); nothing in domains, complexity or tier skips it; the four
  domains only set depth (D1); follow the plan-writing threat-modeling
  section and the template read from `planning_inputs.threat_model_template`;
  write `feature-docs/{feature}/THREAT-MODEL.md`; use the short form for the
  two short verdicts and invent no mitigation; keep SPEC Security
  Considerations and THREAT-MODEL.md apart (FR10). The Implemented by /
  Verified by columns are completed after steps 4 and 5.
- **Step 4** (task decomposition): for `threats-identified` at the full or
  reduced tier, the implementing task of each TM-n carries at least one AC
  naming that TM-n; the D1 consistency re-check runs after domains are
  assigned. At the minimal tier the TM-n line is appended to TASK.md's
  Expected Result under the append rule owned by planner-contract.md (cited,
  not restated), including its `blocked` outcome. Numbering and headings of
  steps 4, 5 and 6 do not change.
- **Step 5** (VERIFICATION.md): one Performance / Security Verification item
  per TM-n, keyed by the TM-n, counted in the Verification Summary.
- **Step 7** (existing files): an existing THREAT-MODEL.md joins
  IMPLEMENTATION.md / tasks/ in the same existing-files decision under the
  existing `create-plan.existing-files` gate (D3). The Questions table and
  the Gate option vocabulary table are unchanged.
- **Step 8 / Output**: THREAT-MODEL.md is saved inside the integration
  worktree with the other artifacts and listed in `written_artifacts`;
  TASK.md is listed only when appended. The Japanese report adds the
  verdict and the TM-n count.
- **Frontmatter description**: mentions THREAT-MODEL.md among the produced
  documents; every other frontmatter line is unchanged.
- Wording constraints from existing tests: the whole prompt never contains
  "untracked", "AskUserQuestion", "auto-select", "scripts/commit-docs.sh",
  the re-entry field names, or a phrase in which "every task" is followed
  within one sentence by "entries"; the step 4 section never contains
  "needs_update" or the phrase stating that create-plan is pending.
