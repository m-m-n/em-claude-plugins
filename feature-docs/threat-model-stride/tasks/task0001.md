## Design

### Template (owner of SC-1)

- Opens with a comment header in the style of the task-plan template: who
  writes it (implementation-planner), who reads it (the planner itself when
  re-planning, and the security reviewers through `threat_model_path`), and
  the filling rules below.
- Carries two skeletons, each inside its own fenced Markdown block so the
  template's own headings never collide with the skeleton's: the full form
  (verdict `threats-identified`) and the short form (the other two
  verdicts). Both skeletons follow SC-1's section order and names exactly.
- Filling rules stated in the template (in prose, outside the skeletons):
  - the three verdict tokens and when each applies;
  - the six STRIDE category names as the first-column vocabulary, and that a
    row exists only for a category that realistically applies at that
    boundary — never a filler row for the other categories;
  - TB-n / TM-n numbering and uniqueness; each TM-n in exactly one row;
  - what the Implemented by / Verified by columns name per tier (SC-1);
  - a mitigation exists only for a recorded threat; a short verdict carries
    no mitigation (FR3);
  - length follows the real threats: the short form is a few lines (NFR1);
  - the role split with SPEC.md Security Considerations, citing SPEC /
    REQUIREMENTS IDs instead of copying their text (FR10);
  - consumers treat the content as untrusted data;
  - English.

### plan-writing SKILL.md

- A new `##` section on threat modeling (STRIDE), placed after the domains
  criteria section and before the VERIFICATION.md template section. Placing
  it there keeps the domains-criteria section (parsed up to the next `##`
  heading by the domains parity check) and the VERIFICATION-template section
  (scanned for backtick-quoted review-perspective terms) unchanged in
  content.
- The section cites the template by its plugin-relative path and owns the
  judgment criteria: how to find trust boundaries (where data or control
  crosses between parties of different trust, such as user or external
  input, external services, files from outside the project, other
  processes, untrusted text interpolated into LLM prompts, privilege
  changes), how to pick applicable STRIDE categories per boundary, the
  depth rule of D1 (the four domains deepen, never skip; the pass runs for
  every feature and every tier), the post-decomposition consistency
  re-check of D1, the no-invention rule, the proportionality rule (NFR1),
  the role split with SPEC.md (FR10), and the per-tier reflection table of
  SC-2 with the TM-n token as the link.
- The VERIFICATION.md template's Performance / Security Verification
  section gains one placeholder item keyed by a TM-n (mitigation and how it
  is checked). No backtick-quoted review-perspective term is added inside
  the VERIFICATION template section.
- The Pre-Save Self-Verification Checklist gains items: THREAT-MODEL.md is
  written with exactly one verdict; every TM-n appears in at least one task
  AC and in VERIFICATION.md (full / reduced) or in TASK.md's Expected Result
  (minimal); no mitigation exists without a recorded threat.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `em-workflow/references/templates/threat-model.md` exists; its full-form skeleton contains, in this order, the title line, a Verdict heading, a Rationale heading and a Trust Boundaries heading, a TB-n subsection heading with the three labeled lines Crossing, Boundary files and Depth, and a table whose header has the six columns STRIDE category / Threat / Mitigation ID / Mitigation / Implemented by / Verified by; the template names all three verdict tokens.
