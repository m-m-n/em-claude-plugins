# Task Plan: task0001 — Keep temp-file deletion errors from overriding filing results

## Goal

A failed deletion of the temporary references file no longer changes the
outcome of a file-tasks filing. The outcome of each package is decided only
by the entry-point launch result and its exit status; the deletion error is
reported on stderr and nowhere else.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/scripts/scan-dependencies.py` — make the references-file deletion in the cleanup of _run_entry_point_with_references catch OS errors and report them on stderr; update the docstrings of _run_entry_point_with_references and create_security_task
- `tests/test_sca_file_tasks_oserror.py` — rewrite the existing deletion-failure helper test, update the module and class docstrings, and add file_tasks-level and error-precedence tests

## Design

### Current behavior (the defect)

The cleanup step of `_run_entry_point_with_references` always deletes the
temporary references file after the entry-point launch. An OS error raised
by that deletion escapes the cleanup step and replaces whatever the launch
produced: a completed result or an earlier launch error.
`create_security_task` / `append_security_task_references` then turn it into
`EntryPointError`, and `file_tasks` records the package as
`failed_package`, puts it at the head of `unattempted_packages`, and stops,
even though the task was filed.

### Target contract of `_run_entry_point_with_references`

- Precondition: the references file was created by this process and its path
  is known to the function.
- Postcondition, launch returned: the completed-process result is returned
  unchanged, whether or not the deletion succeeded (FR3).
- Postcondition, launch raised an OS error: that same launch error reaches
  the caller; a deletion error never replaces it (FR4).
- Deletion behavior:
  1. Deletion is attempted exactly once; no retry (A-2). A file that cannot
     be deleted is allowed to remain.
  2. A file that is already absent is accepted silently, as today: no
     exception and no stderr output (A-4).
  3. Any other OS error raised by the deletion is caught and not raised to
     the caller (FR1). One output containing that error's message text is
     written to stderr per failed deletion (FR2). The wording and any prefix
     are free (A-1).
  4. Exceptions other than OS errors keep their current handling (A-4).
- The deletion error text never reaches stdout, any file-tasks summary key,
  or any `EntryPointError` message (FR2, NFR2).

### Helpers and `file_tasks`

No logic change is expected in `create_security_task`,
`append_security_task_references` or `file_tasks`: once the cleanup no
longer raises, their existing rules give the required outcomes, and this
task pins them with tests.

| Launch outcome | Deletion outcome | Helper outcome |
|---|---|---|
| exit 0 | OS error | returns normally; `file_tasks` records the package as filed / appended and moves to the next package |
| non-zero exit | OS error | existing non-zero-exit `EntryPointError`: message contains the entry point's stderr, no chained cause |
| launch OS error | OS error | `EntryPointError` whose chained cause is the launch OS error |

### Docstrings (FR5)

- `_run_entry_point_with_references` and `create_security_task`: remove every
  statement that a deletion OS error propagates or is converted into
  `EntryPointError`; state that a deletion error is reported on stderr only
  and does not change the result.
- `append_security_task_references`: change only if its text contradicts the
  updated `create_security_task` docstring (A-7).

### Tests in `tests/test_sca_file_tasks_oserror.py`

- `TestFilingHelpersConvertOsErrors.test_temp_file_removal_failure_becomes_entry_point_error`:
  rewrite its body to assert the new behavior (FR6). Keep the method
  identifier unchanged: its test ID may be referenced by `test-docs` records
  of an earlier feature, and those records are outside this task's file set
  (A-5 permits but does not require a rename). Update its docstring, the
  `TestFilingHelpersConvertOsErrors` class docstring and the module docstring
  so none of them says a deletion error becomes `EntryPointError` (A-6).
- Add a `file_tasks`-level test covering the create path and the append path
  (FR7), and helper-level tests for the error-precedence rows of the table
  above (FR4) and for the already-absent file (A-4).

### Unchanged

- The write-failure cleanup of `_write_references_tempfile` (A-3).
- The em-workflow version: neither `em-workflow/.claude-plugin/plugin.json`
  nor `.claude-plugin/marketplace.json` is modified (NFR4).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR3, FR7): With the references-file deletion failing with an OS error (EIO), `file_tasks` run over three packages against a stand-in entry point that exits 0 records all three packages in `filed_packages` on the create path and in `appended_packages` on the append path; on both paths `failed_package` and `failure_reason` are None and `unattempted_packages` is empty.
- [ ] AC-2 (FR1, FR2, FR3, FR6): With the deletion failing, `create_security_task` and `append_security_task_references` against an exit-0 stand-in return without raising; captured stderr contains the injected deletion error's message text and captured stdout does not. This is asserted by the rewritten `test_temp_file_removal_failure_becomes_entry_point_error` (identifier unchanged), and that method's docstring, the `TestFilingHelpersConvertOsErrors` class docstring and the module docstring no longer say a deletion error becomes `EntryPointError`.
- [ ] AC-3 (FR4): When the entry-point launch raises an OS error and the deletion raises a different OS error, each helper raises `EntryPointError` whose `__cause__` is the launch error object, not the deletion error.
- [ ] AC-4 (FR2, FR4): When the stand-in exits non-zero and the deletion raises an OS error, each helper raises the existing non-zero-exit `EntryPointError`: its message contains the entry point's stderr and does not contain the deletion error text, and its `__cause__` is None.
- [ ] AC-5 (FR1, SPEC A-4): When the references file is already absent at deletion time, the helper returns normally and nothing about the deletion is written to stderr.
- [ ] AC-6 (FR5): The docstrings of `_run_entry_point_with_references` and `create_security_task` contain no statement that a deletion OS error propagates or is converted into `EntryPointError`, and each states that a deletion error is reported on stderr only and leaves the result unchanged; the `append_security_task_references` docstring does not contradict them.
- [ ] AC-7 (NFR1, NFR2, NFR3, NFR4): `python3 -m unittest discover -s tests` passes in full, including `TestDocstringAndModuleDiscipline.test_only_standard_library_imports` and the existing file-tasks stdout-shape tests; the task modifies neither `em-workflow/.claude-plugin/plugin.json` nor `.claude-plugin/marketplace.json`, and leaves the write-failure cleanup of `_write_references_tempfile` unchanged.

## Test Notes

- Mapping: AC-1 is an integration test through `file_tasks`; AC-2 to AC-5
  are helper-level unit tests; AC-6 is checked by reading the docstrings (a
  docstring-introspection test is optional); AC-7 is the full-suite run plus
  a diff check on the two version files.
- Failure injection: make the deletion fail by replacing the OS-level unlink
  operation that the path deletion goes through, scoped to the call under
  test so the test's own cleanup is not affected. For AC-3, the launch is
  replaced so it raises one OS error instance and the deletion raises
  another, and the test checks the chained cause by identity. For AC-5, the
  OS-level unlink reports the file as not found.
- Leftover files: with the deletion disabled, the references files remain in
  the temporary directory; remove them with the real deletion in test
  cleanup.
- Stream capture: capture the process-level stderr and stdout around the
  helper call so the assertions see exactly what the helper wrote.
- Stand-in entry point: reuse the test module's existing stand-in mechanism
  (configurable exit status and stderr) rather than adding a new one.
- TDD order: AC-1 to AC-4 fail on the current code (the deletion error
  escapes and replaces the result or the earlier error); AC-5 passes on the
  current code and stays as a regression guard.
