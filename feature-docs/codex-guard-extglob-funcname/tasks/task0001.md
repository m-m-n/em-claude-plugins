# Task Plan: task0001 — Treat words ending in an extglob operator as non-function names in codex-hook-interactive-guard

## Goal

Both copies of codex-hook-interactive-guard.py stop reading a word that ends
in an extglob operator character (`?` `*` `+` `@` `!`) as a function name, so
the group after its `()` is evaluated and an interactive launch inside that
group is denied. The case table and the documentation tests pin the new rule.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/scripts/codex-hook-interactive-guard.py` — the parser's function-name judgment (the _names_function method of _Parser), the module docstring's procedure step 4, the head description of _Group, and the _names_function docstring
- `em-review/scripts/codex-hook-interactive-guard.py` — the same change, kept byte-identical to the em-workflow copy
- `tests/test_codex_hook_interactive_guard.py` — new deny cases in CASES and new markers in TestGuardDocumentation

## Design

### Function-name judgment (FR1, FR2, FR4)

Contract of the parser's function-name judgment (_names_function):

- **Precondition** (unchanged): it receives the words that precede a `()`.
- **Kept behavior**: leading reserved words and the `function` keyword are
  removed, and the existing logic selects the candidate name word — including
  the case where the whole head is one reserved word (`then`).
- **New rule**: when the candidate name word's content ends in one of the five
  extglob operator characters, the judgment returns "not a function name"
  (False). This is an extra rejection applied to the candidate the existing
  logic already selects. It never changes which word is selected and never
  turns a head that is currently not a function name into one.
- **Text basis (SPEC.md A1)**: only the last character of the word's content
  after quote removal is examined. A final operator character that is
  single-quoted, double-quoted or backslash-escaped counts the same, and
  whitespace between the word and `(` does not change the result.
- **Reserved-word-only head (SPEC.md A3)**: when the single remaining word is
  itself a reserved word ending in an operator character (`!`), the new rule
  applies and it is not a function name.
- **Postcondition**: when the judgment returns "not a function name", the
  `()` does not open a function definition, and the following group —
  parenthesized or braced, on the same line or after a newline — is
  evaluated like any other command group, so an interactive launch inside it
  yields deny.
- **Independence (NFR2, SPEC.md A2)**: the judgment depends on the command
  string only. It does not check whether extglob is enabled; a head that Bash
  would accept as a function name with extglob off is still not exempted, so
  its body is evaluated.

### Nested bash -c strings (FR3)

The guard already evaluates the string passed to `bash -c`. The rule above
holds inside that string as well; the outer `-O extglob` option changes
nothing in the judgment. If the nested evaluation reaches the same judgment,
no separate change is needed; if it does not, the nested path applies the
same rule. AC-1 verifies the outcome either way.

### Documentation (FR5)

The FR1 rule is stated in three places of the guard: the module docstring's
procedure step 4, the description of _Group's head, and the _names_function
docstring. TestGuardDocumentation gains markers that fail when any of these
three statements is missing.

### Two copies (NFR1)

The change is made once and reproduced byte-for-byte in the other copy in the
same commit. TestCopies is the check.

## Acceptance Criteria (MANDATORY)

Command strings below write a newline as `\n`.

- [ ] AC-1 (FR1, FR2, FR3, FR6, TM-1): CASES gains deny cases in the `bash -O extglob -c '<string>'` form, both with a reserved word (`bash -O extglob -c 'time /bin/true?()\n(python3 -i)'`) and without one (`bash -O extglob -c 'f?()\n(python3 -i)'`), and both copies of the guard return deny for each.
- [ ] AC-2 (FR1, FR2, TM-1): these top-level forms return deny on both copies: `if true; then f?()\n(python3 -i)\nfi`, `time -p f?()\n(python3 -i)`, and `function f?()\n{ python3 -i; }`.
- [ ] AC-3 (FR1, TM-1): for each of `*`, `+`, `@` and `!`, a word ending in that character followed by `()`, a newline and `(python3 -i)` (`f*()\n(python3 -i)` and so on) returns deny on both copies — one case per character; `?` is covered by AC-1 and AC-2.
- [ ] AC-4 (FR1, TM-1): the SPEC.md A1 / A3 forms return deny on both copies: `'f?'()\n(python3 -i)`, `f\?()\n(python3 -i)`, `f? ()\n(python3 -i)` and `!()\n(python3 -i)`.
- [ ] AC-5 (FR4): every existing CASES entry keeps its label, command and expected decision and passes on both copies — including the existing silent function-definition cases such as `foo()\n(python3 -i)`, `then()\n(python3 -i)` and `time f() { python3 -i; }`; no existing entry is removed or changed, and `python3 -m unittest tests.test_codex_hook_interactive_guard` passes.
- [ ] AC-6 (FR5): the module docstring's procedure step 4, the _Group head description and the _names_function docstring each state the FR1 rule, and TestGuardDocumentation has markers that fail if any of the three statements is removed.
- [ ] AC-7 (NFR1, NFR2, NFR3): TestCopies passes (the two copies are byte-identical), TestStaticConstraints passes, `python3 -m unittest discover -s tests` and `python3 em-workflow/scripts/check-plugin-invariants.py .` exit 0, and the task changes no file under either plugin other than the two guard copies — in particular neither plugin's plugin.json nor the root marketplace.json.

## Test Notes

- Every criterion is a unit test in tests/test_codex_hook_interactive_guard.py.
  The existing harness runs CASES against both copies, so each new case covers
  both copies without extra test code.
- TDD order: add the AC-1 to AC-4 cases first and confirm they come back
  silent on the unchanged guard (this proves each case reaches the bypass),
  then add the AC-6 markers and confirm they fail, then change the judgment
  and the docstrings until everything passes.
- New cases use the existing (expected decision, label, command) tuple shape,
  with a label distinct from every existing label that names the form covered.
- AC-4's quoted and escaped forms depend on the judgment reading the word's
  content after quote removal. A form that stays silent after the change
  signals that the judgment is looking at the raw text.
- If a new case stays silent for a reason other than the function-name
  judgment (a different parsing branch), report it as a plan deviation rather
  than widening the change beyond Scope.
- Run `python3 -m unittest tests.test_codex_hook_interactive_guard` after every
  change to either guard copy (repository hook-tests rule).
