# Task Plan: task0002 — Non-fast-forward ruleset definition for main and its creation procedure

## Goal

The repository holds a GitHub ruleset definition that forbids non-fast-forward updates of main with no bypass, a document that tells a maintainer how to create it with gh api and confirm it, and a test that pins the definition's content.

## Requirements

FR7, FR8, FR10, NFR3, NFR4, NFR5

FR8 is covered here for its part (a) only; FR10 for the ruleset content check only. NFR5 holds for this plan: it and its criteria carry no concrete version value.

## Scope

### Files to Create
- `.github/rulesets/main-non-fast-forward.json` — the ruleset definition in the shape of the GitHub REST API repository ruleset creation payload (FR7)
- `.github/rulesets/README.md` — post-merge procedure (a): create the ruleset with gh api and confirm it (FR8 (a))
- `tests/test_main_non_fast_forward_ruleset.py` — reads the definition and checks its content (TS-3)

## Design

This task implements Shared Component C2 and part (a) of C3 of IMPLEMENTATION.md, following decision D2. Tests follow C4.

### Definition
The file holds the creation payload for a repository ruleset with exactly these settings (C2):
- name main-non-fast-forward, distinct from the existing ruleset named main;
- target branch;
- enforcement active;
- bypass_actors an empty list;
- a ref-name condition whose include list holds exactly refs/heads/main and whose exclude list is empty;
- rules holding exactly one rule, of type non_fast_forward, with no parameters.

No other rule is added. The existing main ruleset is not touched (A9).

### Procedure document (a)
Written in the language of the repository's root README.md. In order:
1. Preconditions: this feature's pull request is merged, and gh is authenticated with permission to administer the repository's rulesets.
2. Check that no ruleset with the same name exists yet, so the creation does not make a duplicate.
3. Create the ruleset with one gh api call that posts the definition file as the request body to the repository rulesets endpoint.
4. Confirm: list the repository's rulesets, show the new one, and check its name, enforcement active, empty bypass list, target main, and its single non_fast_forward rule.
5. Confirm that the existing main ruleset is unchanged.

### Test
Reads the definition file through a path built from the test module's own location, parses it as JSON, and checks every item of the definition above. It uses no git, no network and nothing under `~/.claude`.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The definition parses as JSON and has name main-non-fast-forward, target branch, enforcement active, bypass_actors an empty list, a ref-name condition including exactly refs/heads/main and excluding nothing, and exactly one rule whose type is non_fast_forward; the test asserts each of these (TS-3, TM-5).
- [ ] AC-2: `.github/rulesets/README.md` contains the gh api command that creates the ruleset from the definition file, a check for an existing ruleset of the same name before creating, and confirmation steps that inspect the created ruleset's name, enforcement, bypass list, target and rules (TS-20).
- [ ] AC-3: `.github/rulesets/README.md` states that the existing main ruleset is not changed and includes a step confirming it is unchanged after the creation (TS-20).
- [ ] AC-4: The test module follows the C4 isolation rules (TS-19) and `python3 -m unittest discover -s tests` exits 0.
- [ ] AC-5: This task changes no version field in any plugin.json or in .claude-plugin/marketplace.json (TS-22).
