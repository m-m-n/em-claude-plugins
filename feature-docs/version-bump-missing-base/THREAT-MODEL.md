# Threat Model: version-bump-missing-base

## Verdict
threats-identified

## Rationale
Inspected: SPEC.md and REQUIREMENTS.md (FR1-FR10, NFR1-NFR5, Security Considerations), tier `full`, no DESIGN.md (design step skipped). The feature's inputs are the push event values (BEFORE, AFTER), the two workflow_dispatch inputs (`plugin`, `min_version`) and the selected ref, the single fetch from origin, the repository's JSON files, and the pushes that update main on GitHub.

Depth: task0001 declares `input-handling` and `external-io`, so TB-1 is analysed deep; task0002 declares `auth`, so TB-2 is analysed deep.

Considered and not recorded as threats:
- BEFORE and AFTER are generated by GitHub, not chosen by the pusher. FR1 already requires the 40-hex / not-all-zero check before BEFORE is used as a git argument, and TM-1 covers how event values reach the script. No separate row.
- The single fetch from origin talks only to the repository's own origin with the job's own credentials; its failure is the FR1 fallback, not a security event.
- plugin.json and marketplace.json are repository files that reached main through review; they are data, not a boundary.
- The tests (NFR3) run git only inside temporary directories against local bare repositories; no external party is involved.

Domain consistency: task0001's workflow and template files appear in TB-1, and task0002's ruleset definition and its procedure document appear in TB-2. The test modules of task0001 and task0002 (`tests/test_plugin_version_bump_workflow.py`, `tests/test_main_non_fast_forward_ruleset.py`) appear in no `Boundary files` line because they only read repository files and operate on temporary repositories. task0003 declares none of the four depth domains.

## Trust Boundaries

### TB-1: workflow_dispatch request to the version-update job
Crossing: a person allowed to dispatch the workflow supplies the free-text inputs `plugin` and `min_version` and chooses the ref; these enter a job that rewrites plugin.json and marketplace.json, writes GITHUB_OUTPUT, and opens and merges a pull request into main with the workflow token.
Boundary files: `.github/workflows/plugin-version-bump.yml`, `plugin-dev/skills/plugin-dev/templates/plugin-version-bump.yml`
Depth: deep (input-handling, external-io)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
|---|---|---|---|---|---|
| Elevation of privilege | A dispatch input holding shell or script syntax, if the Actions expression engine expands it into the step's script text, runs as code with the job's token, which can open and merge pull requests into main (FR4, FR5) | TM-1 | The dispatch inputs and the event values reach the heredoc only through the step's environment variables; the heredoc body contains no Actions expression | task0001 AC-7 | VERIFICATION.md TM-1 (TS-17) |
| Tampering | A `plugin` value that is not a registered name, such as one shaped like a relative path, makes the script read or rewrite a JSON file outside the registered plugins (FR4) | TM-2 | `plugin` must equal a name registered in marketplace.json exactly before it is used to locate any file; otherwise the script exits non-zero with no file changed | task0001 AC-6 | VERIFICATION.md TM-2 (TS-13) |
| Tampering | A `min_version` carrying extra text, such as a line break or trailing characters, is carried into the written version or into the `bumped` line of GITHUB_OUTPUT, adding or altering step outputs that steer the pull request step (FR4, FR5) | TM-3 | `min_version` must fully match three dot-separated non-negative integers before use; otherwise the script exits non-zero with no file changed and no `bumped` value written | task0001 AC-6 | VERIFICATION.md TM-3 (TS-13) |
| Tampering | A dispatch on a ref other than main computes versions from that ref's tree and opens a version-update pull request into main (FR4) | TM-4 | Under workflow_dispatch the version-update step runs only when the ref is main. This guards the workflow definition as it stands on main; a ref that carries an edited definition is outside this mitigation, and its pull request still meets the repository's rules | task0001 AC-7 | VERIFICATION.md TM-4 (TS-15) |

### TB-2: pushes that update main on GitHub
Crossing: a push from a maintainer's local clone, or from any process holding push rights, updates the main ref on GitHub, where Actions may already have added its version-update commit.
Boundary files: `.github/rulesets/main-non-fast-forward.json`, `.github/rulesets/README.md`
Depth: deep (auth)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
|---|---|---|---|---|---|
| Tampering | A non-fast-forward push replaces origin/main with history that lacks the Actions version-update commit and discards that bump; the existing main ruleset's admin bypass lets such a push through (FR7, A9) | TM-5 | A separate ruleset definition holding only the non_fast_forward rule, targeting main, with enforcement active and an empty bypass list, created by the post-merge procedure (FR8 (a)); the existing main ruleset stays unchanged. The protection takes effect on GitHub only once that procedure is run (A7) | task0002 AC-1 | VERIFICATION.md TM-5 (TS-3) |
