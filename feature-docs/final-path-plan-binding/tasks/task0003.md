# Task Plan: task0003 — Resolve the implementer's plan from tasks.{T}.plan behind a fail-closed Plan-path check

## Goal

The implement phase gives each implementer the plan document that
`tasks.{T}.plan` names, and before any launch prompt is built it checks that
value for every selected task and aborts the phase on any failure. A batch
run reports that stop as `step_needs_intervention`.

## Design

### 1. Payload line (FR2)

In Step I.2.a's "Prompt payload per task" block, the `task_plan_path` line
becomes: the absolute path of the integration worktree's
`feature-docs/{feature}/` joined with the stored `tasks.{T}.plan` value, the
value the Plan-path check admitted. It stays one line, before the
`## Untrusted data` label, in its current position among the trusted fields.
No text of the payload block names `tasks/{T}.md`.

### 2. Plan-path check paragraph (FR3)

A new paragraph labelled "**Plan-path check**" directly after the whole
Control-character check paragraph and before the approval-gate paragraph
("Before launching, verify every ..."). It states:

- **When and for which tasks.** Once the Control-character check has passed,
  and before any implementer launch prompt is built, the check runs over the
  stored `tasks.{T}.plan` value of each task selected in this entry, not only
  the first one.
- **Rules, one bullet each, every bullet a sentence of its own:**
  1. The stored value is a string that is a safe relative path in the sense
     of `is_safe_relative_path` of `scripts/validate-worker-output.py` (cited,
     not restated) and names at least one segment once `path_segments`
     normalization is applied.
  2. Joined to the integration worktree's `feature-docs/{feature}` directory,
     no component of the path, intermediate ones included, is a symlink.
  3. The realpath of the joined path lies inside the realpath of
     `feature-docs/{feature}`.
  4. Neither the stored value nor the resolved absolute path holds a
     character of Unicode category Cc, U+2028 or U+2029, the set the
     Control-character check above rejects.
- **Why it sits in the trusted part.** `task_plan_path` is derived from
  `workflow.yaml` yet is placed before the untrusted-data label; it reaches
  the payload only after this check passes.
- **Abort.** When the value of one or more selected tasks fails, the phase
  aborts with the terminal handling of the Control-character check above,
  cited and not restated as commands: report the IDs of the failing tasks,
  build no launch prompt for any selected task and launch no implementer,
  make one write that sets the `implement` step's `status` to `failed` with
  `failed_kind` valued `decision`, committed with `commit-docs.sh`. Nothing is
  repaired, stripped or replaced, and nothing falls back to `tasks/{T}.md`.
  Tasks launched by an earlier refill are not waited for, not cancelled and
  not rolled back. Control returns through develop's stop condition 3.

Wording constraints, from the neighbouring pinned tests of Step I.2.a:

- The new paragraph does not contain "Unicode general category Cc" (the
  locator of the Control-character check paragraph must stay unique), "strict
  realpath", "every task selected in this entry into Step I.2.a", "each of
  those tasks, not only the first or the current one" or "ABORT the
  implement phase".
- No sentence or bullet holds three or more of: "strictly below", "existing
  directory", "realpath", the backticked `..`, "empty component", "link
  component", "symbolic link". Write "symlink", never "symlink component"
  (it contains "link component") and never "symbolic link".
- It contains none of the launch-order anchors of
  `tests/test_prelaunch_inprogress_launch_order.py` (the approval-gate and
  launch-loop openings, the journal re-read phrase, the launch tip capture,
  the refresh command, the in-progress write, the launch-state commit call,
  the end-of-turn phrase), and no uppercase "EVERY" or "ALL".

### 3. Section 2a of create-plan-phase.md (FR2)

The sentence that says the registered entry's `plan` points at the task
document is reworded so that it states separately: the stored `tasks.{T}.plan`
value is relative to `feature-docs/{feature}` (`TASK.md` at the `minimal`
tier, `tasks/taskNNNN.md` otherwise), and the implement phase resolves it to
the absolute path of the integration worktree's `feature-docs/{feature}/`
joined with that value, behind the Plan-path check of
`references/implement-phase.md` (cited). These phrases stay: "exactly one task
entry", "task document", "the plan value's final path segment equals the task
document's file name", "every mandatory field", "including its `complexity`
value", "`requirements` list may be empty", "merge into the integration
branch".

### 4. Batch stop binding (FR6)

A new paragraph in `## Stop point coverage` of `batch-terminal-line.md`,
directly after the "Precedence rule:" paragraph and before the paragraph on
the Same-cause write rejection. The "Precedence rule:" paragraph stays
byte-identical. The new paragraph states:

- The batch stop raised by the Plan-path check of Step I.2.a in
  `references/implement-phase.md` is a second named exception to the
  `stop-condition-3` row's current-run exclusion, on the same terms as the
  Control-character check's exception in the paragraph above.
- In the current run that check writes `implement: failed` /
  `failed_kind: decision`, the stop has no phase-specific row, and control
  returns through develop's stop condition 3.
- The stop binds to the `stop-condition-3` row, `step_needs_intervention`,
  and not to `unmapped_stop`.
- The exception covers this one stop only; the table gains no row and no
  code.

The new paragraph does not contain "The batch abort that", does not repeat
the Control-character check's own naming phrase, and binds nothing
affirmatively to `unmapped_stop`.

### 5. Write-path count (consistency of FR3)

The Plan-path check stop is one more write path that sets the `implement`
step's `status` to `failed`. In `references/workflow-schema.md`, section
`failed_kind`, paragraph "Required-ness", the count of write paths becomes
five; nothing else in that section changes. In
`tests/test_workflow_schema_journal_readers_doc_contract.py`, the captured
section constant is updated in place to the new text, and its comment gains
a sentence naming this feature and the reason, in the same way the comment
already records the earlier change from three to four. The comparison stays
byte-identical.
