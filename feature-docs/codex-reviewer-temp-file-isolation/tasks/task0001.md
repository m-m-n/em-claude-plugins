# Task Plan: task0001 — codex-reviewer temp-file discipline in both plugins

## Goal

Both plugins' `codex-reviewer` agent definitions carry a temp-file uniqueness
rule that removes the parallel-reviewer overwrite window, and a structural test
holds that rule in place.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3

## Scope

### Files to Modify

## Design

### The discipline section

Add one short section to each agent definition, positioned immediately before
the existing "Execute Codex" step (see IMPLEMENTATION.md Conventions). It must
convey all of the following, in whatever prose reads naturally:

1. **When it applies**: only when the agent writes a temp file into the session
   scratchpad — assembling the prompt as a shell variable and passing it
   straight to the wrapper needs no file and is fine (FR6).
2. **The hazard being avoided**: parallel `codex-reviewer` instances started in
   one message share the scratchpad directory, so a fixed name lets a sibling
   overwrite the file between the write and the read, and the reviewer then
   sends another perspective's prompt to Codex and labels the result with its
   own perspective.
3. **The mechanism**: allocate the path with `mktemp` using a template whose
   random part is the `XXXXXX` placeholder. Name the reason it beats computing
   a name from PID or `$RANDOM`: `mktemp` creates the file while allocating the
   name, so a path is never handed out twice (FR3).
4. **The prohibition**: fixed names (`prompt.txt`) and perspective-derived names
   (`security-prompt.txt`) are forbidden; uniqueness is per invocation, so even
   a retry of the same perspective gets a fresh path (FR4).
5. **The failure route**: if allocation fails, return the agent's standard skip
   object — the same shape used elsewhere in the file, with `skipped` true and
   `source` `codex` — rather than falling back to a shared path (FR5).

The two files' sections differ only in plugin-identifying wording.

### The structural test

A `unittest` module that reads both agent definitions as text and asserts the
required elements above are present in each. Follow the style of
`tests/test_review_implement_develop_lock_contracts.py` and
`tests/test_planner_designer_worktree_docs.py`: locate files relative to the
test file's own path, assert on required elements rather than whole sentences,
and give each assertion a message naming the acceptance criterion it covers.

Also assert the wrapper invocation is untouched: each file still invokes
`run_codex_exec.sh` with the mode, working-directory, output-schema and prompt
arguments it had before, and no prompt-file flag was introduced (NFR1).

### Version bumps

Patch-level bump on both plugin manifests (IMPLEMENTATION.md D4).

## Test Notes

The deliverable is prose, so the tests are structural checks over markdown text
— the pattern this repository already uses for documentation tasks. Write the
test first: it will fail against the current files (neither mentions temp files
at all), then pass once both sections are added, which is a genuine red-green
cycle rather than a formality.

Edge cases worth an assertion: the prohibition must be present in BOTH files
(a one-sided edit is the realistic regression), and the wrapper invocation
check must fail if a prompt-file flag is ever introduced.

Avoid asserting on exact sentences — assert that the required tokens and
concepts appear, so later rewording does not break the suite (IMPLEMENTATION.md
Risk Assessment).
