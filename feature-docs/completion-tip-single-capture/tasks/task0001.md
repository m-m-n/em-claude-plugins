# Task Plan: task0001 — Pin completed_at_commit to the step-1 COMPLETION_TIP capture in Step I.3

## Goal

Step I.3 of `em-workflow/references/implement-phase.md` names the step-1
`$COMPLETION_TIP` capture as the single source of the `completed_at_commit`
value in the command sequence itself, including on an exit-4 retry. A new
standard-library unittest detects any later change that brings back a
second, independent capture as the source of `completed_at_commit`.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3

## Scope

### Files to Create
- `tests/test_completion_tip_single_capture.py` — regression tests for the
  single value source of `completed_at_commit` (TS1-TS4 in VERIFICATION.md),
  including the negative proof against the pre-change step 3 wording and its
  non-vacuity guard.

### Files to Modify
- `em-workflow/references/implement-phase.md` — Step I.3: step 3 wording that
  binds `completed_at_commit` to step 1's `$COMPLETION_TIP`; exit-4 retry
  wording; optionally the closing invariant paragraph.

## Design

### Current state
Step I.3 step 1 captures the integration tip into `$COMPLETION_TIP`. The
completion sentence pinned byte-for-byte by
`tests/test_rework_synthesis_contract.py`
`test_completed_at_commit_wording_is_unchanged` writes `completed_at_commit`
as an inline command substitution on the integration branch, and step 3 only
says that the `status = completed` and `completed_at_commit` "set above" are
committed. An agent following the text literally evaluates a second,
independent capture, so the closing paragraph's claim that both values
derive from the same step-1 capture does not follow from the commands.

### Step 3 change (FR1)
- The phrase "on the worktree just refreshed" stays in step 3 unchanged. It is
  the write anchor used by `tests/test_exit4_tip_argument_consistency.py` and
  by this task's TS1/TS2 matchers.
- Between that anchor and step 4's `commit-docs.sh` invocation, new wording
  states both of the following:
  1. The `completed_at_commit` value written to `workflow.yaml` is the value
     of `$COMPLETION_TIP` captured in step 1.
  2. The command substitution shown in the pinned sentence above is not
     evaluated as a separate command; its value is the one step 1 captured.
- Lexical constraints on step 3 (whitespace-normalized):
  - Step 3 as a whole contains no "rev-parse" string and no "$(git" string.
    The pinned sentence's expression is referred to descriptively (for
    example "the command substitution in the pinned sentence above"), never
    quoted.
  - No "commit-docs.sh" occurs between the anchor and the binding wording, so
    the first "commit-docs.sh" after the anchor remains step 4's invocation.

### Exit-4 retry wording (FR2)
- Step I.3 states that on an exit-4 retry (Branch & Worktree Model's exit-4
  recovery) `completed_at_commit` is re-written with the freshly re-captured
  `$COMPLETION_TIP`, the same value passed as `commit-docs.sh`'s third
  argument on that retry, so the two values still name the same commit across
  retries.
- This wording sits outside the step 3 span above: at or after step 4's
  `commit-docs.sh` invocation, next to Step I.3's existing exit-4 handling.
- It is one sentence (or one paragraph) that contains an exit-4 reference,
  `completed_at_commit` and `$COMPLETION_TIP` together, so TS3 matches it as
  a single unit.

### Closing invariant paragraph (SPEC A2)
The paragraph asserting that both values are derived from the same step-1
capture may stay as written or be reworded to point at step 3 as the place
where the single source is stated. No test asserts its wording. Either way it
obeys the section-wide constraints below.

### Section-wide constraints (FR3, NFR2)
- The pinned sentence stays byte-identical, including its internal newline.
  Every new word goes strictly after it: nothing is inserted inside the
  pinned span and its lines are not re-wrapped.
- New wording anywhere in Step I.3 contains no `COMPLETION_TIP=$(git` string,
  no "reset --hard" string, and no hard reset onto `$COMPLETION_TIP`
  (`tests/test_tip_capture_idiom_uniformity.py` takes the first match of the
  capture idiom and of "reset --hard" inside the section).
- New wording does not repeat the anchor phrase "on the worktree just
  refreshed" anywhere in Step I.3.
- Every existing assertion on the Step I.3 section in
  `tests/test_exit4_tip_argument_consistency.py` keeps passing.
- The meaning of `completed_at_commit` (the integration tip when every task
  is merged, before the completion docs commit) and the order of Step I.3's
  steps do not change (SPEC A4).

### Test module (FR4)
- Section isolation: read `em-workflow/references/implement-phase.md`,
  extract the Step I.3 section and collapse whitespace runs to single spaces
  before matching. The existing Step I.3 tests in
  `tests/test_exit4_tip_argument_consistency.py` are the pattern reference;
  the extraction is re-implemented inside the new module, which imports no
  other test module.
- TS1 matcher: from the first "on the worktree just refreshed" in the
  section, take the text up to the next "commit-docs.sh". It matches when
  that span contains both `completed_at_commit` and `$COMPLETION_TIP`.
- TS2 matcher: the same span contains neither "rev-parse" nor "$(git".
- Both matchers fail explicitly when the anchor or the following
  "commit-docs.sh" is not found; a missing anchor never passes vacuously.
- TS3: the section contains one sentence (or paragraph) that refers to the
  exit-4 retry and contains `completed_at_commit` and `$COMPLETION_TIP`,
  stating that `completed_at_commit` is re-written from the re-captured
  value.
- TS4 negative proof: the module holds a verbatim sample of the pre-change
  step 3 text, copied from the base revision before editing. The sample
  contains "`status = completed` and `completed_at_commit` set above". The
  TS1 matcher applied to the sample yields no match. A non-vacuity guard
  asserts the sample is non-empty and contains `completed_at_commit`. This
  follows the negative-proof and non-vacuity pattern already in
  `tests/test_exit4_tip_argument_consistency.py`.
- Imports: Python standard library only.
