# Task Plan: task0001 — Escaped-pipe unsupported notice in classification table parser

## Goal

When `parse_classification_table()` meets a non-separator row that does not split into two cells and contains `\|`, the `ClassificationTableError` it raises states that `\|` escapes are not supported, so the cause is readable from the message; tests in `TestParseClassificationTableFailureModes` pin that behavior.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `tests/test_hook_classification_pin.py` — parser column-count-mismatch message branch, parser docstring (Raises), three added failure-mode tests

## Design

Cross-task decisions D1-D3 in IMPLEMENTATION.md apply; they are not restated here.

### Parser flow for one non-separator table row (FR1, FR2)

1. Split the row line into cells exactly as today (unchanged).
2. Two cells: continue with the existing classification-vocabulary and path-resolution validation (unchanged).
3. Not two cells:
   1. The row line, as held before splitting, contains the two-character substring backslash + pipe: raise `ClassificationTableError` whose message carries the existing content (the two-column expectation and the repr of the offending row) plus an English notice that `\|` escapes are not supported by this parser. The notice itself contains the literal `\|` and the phrase "not supported".
   2. Otherwise: raise `ClassificationTableError` with the existing message, textually unchanged.

Detection is a plain substring check on the row line. Escaped backslashes are not analysed (a `\\|` sequence also matches). A row whose split yields exactly two cells never reaches step 3.

### Contract of `parse_classification_table()` after the change

- **Input**: unchanged.
- **Postcondition (success)**: every input that parsed before returns the same rows.
- **Postcondition (failure)**: every input that raised before still raises `ClassificationTableError` at the same row. The only difference is the message for a column-count-mismatch row containing `\|`, which gains the unsupported notice.

### Docstring (FR4)

The Raises description for a malformed row states that `\|` escapes are not interpreted, and that a row containing `\|` which fails the two-column check raises `ClassificationTableError` with a message noting that the escape is not supported.

### Added tests (FR3)

Added to `TestParseClassificationTableFailureModes`; existing tests stay untouched. Each input is a one-row table built the same way the existing failure-mode tests in that class build theirs.

- **Case A**: hook cell `` `em-workflow/hooks/queue\|stop_guard.py` ``, classification cell the canonical READS_STATUS value. Expected: raises, notice present.
- **Case B**: hook cell `` `em-workflow/hooks/queue_stop_guard.py` ``, classification cell ``reads `tasks.{T}.status` \| `journal` `` (the reproduction value). Expected: raises, notice present.
- **Case C**: the single-cell row `| only-one-column |`. Expected: raises, no notice.

## Test Notes

- AC-1 to AC-4 are unit tests in `TestParseClassificationTableFailureModes`. Case A and Case B fail before the change (the message lacks "not supported"), which gives the TDD red step. Case C already passes before the change; it guards the unchanged branch.
- Pitfall (AC-1, AC-2): repr of a row line holding one backslash shows that backslash doubled, and the doubled form still contains the backslash + pipe substring. A whole-message substring check for `\|` therefore passes even without the notice. Verify the literal within the notice independently of the embedded row repr, for example by checking the message after removing the offending row's repr.
- Pitfall (test inputs): the inputs must hold exactly one backslash character followed by a pipe. Use a string form that yields that without relying on an unrecognized escape sequence, which emits a warning on current Python.
- AC-3: check that the Case A / Case B messages include the repr of the offending row and the same two-column expectation wording the existing mismatch message uses.
- AC-5 is TDD-awkward (docstring content). Planned handling: verified by inspection in review / verify (VERIFICATION.md TS-5); no dedicated test is required.
- AC-6: covered by the existing real-document test (4 rows), the existing failure-mode tests and a full-suite run (VERIFICATION.md TS-4); "unchanged" is confirmed by diff inspection (VERIFICATION.md TS-6).
- AC-7: diff inspection (VERIFICATION.md TS-7).
