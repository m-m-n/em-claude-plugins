Seven review round 1 findings land on the same document,
`em-workflow/references/batch-terminal-line.md`, and on the same root cause:
the SSOT states rules an emitter must satisfy but leaves the rule's own
boundary conditions to another document or to nothing at all. They are one
task because they share one file — the SSOT is rewritten by exactly one task
at a time (IMPLEMENTATION.md D1) — and because their fixes interact inside
the same two sections.

## Design

The canonical statement of every rule below is IMPLEMENTATION.md SC11; this
section states how each lands in the document.

### (a) Confidentiality: `beyond paths` restored (`d790c24d9d29f3e8`, NFR5)

`## Responsibility boundary` currently says `detail`, `resume_conditions`,
`branch` and `pr_url` "carry no confidential information". SPEC NFR5's rule
is "no confidential information BEYOND PATHS", widened in field scope only.
The words `beyond paths` are restored, so the sentence again permits the
paths every one of these four values is made of.

### (b) The in-full loading rule gets its owner (`d790c24d9d29f3e8`, FR1, FR17)

`batch-mode.md`'s `## Reporting` says "Per `references/batch-terminal-line.md`,
every item above is carried in full inside the result's human-facing
description value" — a citation of a rule the cited document does not state.
The SSOT states it, in `## Field values`:

- Every audit item `batch-mode.md`'s `## Reporting` enumerates is carried in
  full inside `detail`; the stop-recovery guidance in full inside
  `resume_conditions`. A count alone, or a pointer alone, satisfies neither.
  The ITEM LIST stays `batch-mode.md`'s to own and is not reproduced here —
  the SSOT names the section, not its contents.
- One named exception, and only one: where an item's text carries a secret,
  exactly that portion is replaced by a fixed placeholder. This is the
  confidentiality rule of (a) taking precedence over the in-full rule; it is
  a redaction, never a count or a pointer substitution, and it never applies
  to a path.

### (c) `detail` carries several items on one line (`6e738eeb10be06d5`, FR7)

`detail`'s normalization collapses CR/LF/TAB to spaces, so items assembled
into it lose their boundaries and a carried command string loses its internal
whitespace. The normalization itself is FR7's and is NOT changed. The bullet
instead states the two consequences explicitly:

- Items carried in `detail` are separated by a fixed textual delimiter that
  survives normalization, so their boundaries remain readable in the single
  collapsed line.
- `detail` is not a byte-verbatim record: whitespace inside a carried command
  string is normalized. The verbatim record stays in the persisted audit
  source `batch-mode.md`'s Audit-item source map already names. Stating this
  is a disclosure, not a licence to replace an item with that pointer.

### (d) The 64 KiB / in-full collision has one defined outcome (`aa806983e2dde5ac`)

`## Consumer constraints` says an emitter that cannot satisfy both the 64 KiB
bound and the in-full requirement "has a reportable condition for the run",
without saying what that emitter actually outputs. The paragraph is completed
so exactly one outcome is legal:

- Nothing is dropped, summarized, replaced by a count or replaced by a
  pointer — unchanged.
- The bound is hard: an oversize result is never emitted.
- Therefore that run emits NO result, and `## Purpose`'s absence signal
  applies to it: a consumer that sees no result reads an abnormal outcome.
  The paragraph states that consequence explicitly, so the outcome is a
  chosen fail-closed behaviour rather than an emitter improvising.
- The assembled content is not lost: it remains in the persisted audit
  sources.

No stop reason code is added and no row is added to `## Stop point
coverage`: SPEC FR15 fixes the domain at twelve documented values with eleven
coverage rows and one named exception, and TS7 asserts exactly those counts.
A dedicated reason code for this condition would be a SPEC change and is
deliberately NOT taken here; the exclusion is recorded so a later round can
revisit it as a specification decision rather than rediscover it.

### (e) `feature`'s slug pattern is named (`6684af2e09a0c2b1`, FR9)

The `feature` bullet says "when a supplied name matches the slug pattern"
with neither the pattern literal nor a named owner, while the `step` bullet
in the same list names its domain's owner explicitly. The bullet gains the
pattern literal `^[a-z0-9][a-z0-9-]*$`, or a named reference to the document
that defines it in exactly the form the `step` bullet uses. The string
`slug pattern` stays in the bullet, so the existing binding assertion that
looks for it stays green.

### (f) `resume_conditions` presence rule matches FR12 (`d0c6daaf5c1bc6b9`)

The bullet's `non-empty whenever `state` is `stopped`` becomes
non-whitespace — never empty AND never whitespace-only — matching SPEC FR12
and AC-5 and the behaviour
`tests/test_structured_result_derivation.py` already verifies. The pin in
`tests/test_batch_stop_contract.py` that binds the old wording moves in the
same change (FR22).

### (g) Control code points in the values that carry foreign text (`945001897c8ae4b6`)

Constraints 3 and 4 reject a line terminator or a terminal-control code point
in `branch` and `pr_url` after parsing. `detail` and `resume_conditions` are
the values that actually carry attacker-influenceable text and have no such
rule. The SSOT states the same rule for both of them, in the same form and
with the same "escaping does not help" note.

It is stated as em-workflow's OWN emitter obligation and rejection rule, in a
part of `## Consumer constraints` labelled as such — NOT as a constraint
carried over from the external consumer. FR14's carried-over set (the five
numbered constraints) is unchanged, so the document claims nothing about the
external consumer's implementation that this repository cannot verify.

`detail`'s normalization rule (FR7) and `resume_conditions`' exemption from
it (FR8) are unchanged: this is an additional obligation on the value, in the
same shape as the existing `branch` / `pr_url` obligations, not an edit to
the normalization step.

### (h) Shape defences that fire only when escaping has already failed (`15cef915894f6e83`)

Under the same "em-workflow's own hardening rules" label as (g),
`## Consumer constraints` gains three checks, each stated as a rule that
cannot fire while `## Escaping` is honoured:

1. The top-level mapping's key sequence is exactly the eight keys of
   `## Result format`, in that order — a result with a missing, extra or
   reordered key is rejected.
2. A key appearing more than once is rejected BEFORE any parser's
   last-wins resolution; equivalently, a result that is not exactly eight
   physical lines is rejected on shape alone.
3. A `state`, `step` or `reason` value outside its documented domain is
   rejected.

These are defence in depth for the case the review names: an unescaped
newline inside a value followed by a line that looks like another key.

### Guard moves (FR22, NFR4, D5)

- `tests/test_batch_stop_contract.py` is this document's binding module: it
  gains assertions that the real SSOT carries (a)-(h), each new matcher with
  a negative proof and a non-vacuity guard, and its `resume_conditions`
  presence pin is updated to the new wording.
- `tests/test_structured_result_derivation.py` binds its local
  `SLUG_PATTERN` to the pattern the SSOT states (e), and keeps its existing
  whitespace-only presence case, now also justified by the SSOT's own words
  (f).
- `## Escaping` and `## Result format` must come out of this task
  BYTE-IDENTICAL to their pre-change text. task0009 binds its executable
  escaping copies to `## Escaping` and depends on that invariance
  (IMPLEMENTATION.md SC12).
