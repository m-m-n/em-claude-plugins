# Task Plan: task0004 — Conformance suite for the structured result's shape and escaping

## Goal

Two new test modules prove, against a real YAML parser, that the canonical
document shape and the canonical escaping rule produce a single eight-key
mapping of eight string values for every adversarial input, and that the
consumer's rejected combinations are detectable.

## Requirements

FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR14, FR22, NFR2, NFR3, NFR4

## Scope

### Files to Create

- `tests/test_structured_result_conformance.py` — TS1, TS2, TS3: document
  shape, escaping conformance over the 14 adversarial cases, and the
  normalization-versus-escaping distinction.
- `tests/test_structured_result_consumer_constraints.py` — TS5: the rejected
  combinations, the `branch` / `pr_url` character constraints after parsing,
  and the 64 KiB boundary.

### Files to Modify

None.

## Design

### What is under test

There is no runtime component: the result is text a model writes (NFR2). What
these modules verify is that the RULE, as IMPLEMENTATION.md states it
canonically, is sound — i.e. applying SC3's escaping to an arbitrary source
value and assembling SC1's eight lines yields a document a real YAML parser
loads back into the original values. Per IMPLEMENTATION.md D5, the modules
declare SC1 and SC3 independently as canonical constants and never read
`batch-terminal-line.md`; task0001 owns the single binding assertion that the
SSOT states the same rule.

### Module-local reference applier

Each module carries one small reference applier that turns a mapping of eight
source strings into the document SC1 describes, applying SC3 character by
character. It is a test fixture, not a shipped component: it lives under
`tests/`, is exercised only by these modules, and its purpose is to make the
documented rule executable so a parser can judge it. It must be written
directly from SC3's table and residual ranges, with no reliance on any
language-provided string-escaping helper — a helper's own escaping rules would
substitute for the rule under test and make the conformance vacuous.

### The parser (D6)

The YAML parser is imported under a guard. When it is unavailable the module
skips with a message naming the missing package; VERIFICATION.md treats such a
skip as a failed verification item, so the skip is a signal, never a pass. The
guarded import is the single permitted departure from the stdlib-only
convention, and the module's own stdlib-only self-check is written to allow
exactly that one module name and no other.

### Scenario coverage

| Scenario | What it asserts |
|---|---|
| TS1 (FR2, FR3, FR4, FR6) | For a representative source mapping per `state` value, the assembled document loads to exactly one mapping; its keys equal SC1's set; its key order as written equals SC1's order; every loaded value is a string; the document is exactly eight physical lines; and nothing precedes or follows the mapping |
| TS2 (FR5, NFR3) | Each of the 14 adversarial source values, placed in each of the eight positions, round-trips to a value equal to the source, character for character. The 14: empty string; `null`; `true`; `0`; a value beginning with a colon and a space; a value beginning with a hyphen and a space; a value beginning with a hash; a value containing a colon-space-hash sequence; embedded LF; embedded CRLF; embedded TAB; embedded double quotes and backslashes; a non-BMP emoji; and a string built from C0, C1, line-separator and noncharacter code points |
| TS3 (FR7, FR8) | A `detail` source containing CR, LF, TAB and runs of spaces normalizes (whitespace to a single space, runs collapsed, result trimmed, fixed non-empty placeholder when the normalized value is empty) and only THEN escapes — so the emitted `detail` carries no newline escape. A `resume_conditions` source containing newlines, indentation and trailing spaces is escaped only, so its emitted value DOES carry newline escapes and preserves indentation and trailing spaces through the round trip |
| TS5 (FR14) | `stopped` together with the no-reason value is rejected; `phase_done` without the no-reason value is rejected; `phase_done` with a non-empty `resume_conditions` is rejected; a `branch` or `pr_url` carrying a line terminator or a terminal-control code point is rejected AFTER parsing (escaping does not rescue it); and a document at, just below, and just above 64 KiB encoded UTF-8 falls on the expected side of the bound |

### Non-vacuity

Every matcher these modules introduce carries a negative proof and a
non-vacuity guard (NFR4). Specifically: the escaping applier must be shown to
reject a deliberately wrong mapping (e.g. one that emits a literal newline
instead of its escape) by failing the round trip; the constraint checkers must
each reject a forged conforming-looking sample; and the adversarial case list
must be asserted to have exactly 14 members so a silently-dropped case fails.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: for each `state` value, an assembled representative document loads
      under a strict YAML load to exactly one mapping whose keys equal SC1's
      set, whose written key order equals SC1's order, whose eight values are
      all strings, and which is exactly eight physical lines with nothing
      before or after it.
- [ ] AC-2: all 14 adversarial source values round-trip to values equal to the
      source, in every one of the eight key positions; the case list is
      asserted to hold exactly 14 members.
- [ ] AC-3: a reference applier that emits a literal newline instead of its
      escape fails the round-trip assertion — proving the round trip is doing
      work rather than passing trivially.
- [ ] AC-4: a `detail` source containing CR / LF / TAB and space runs yields an
      emitted value with no newline escape and no repeated space; an empty
      normalized `detail` yields the fixed non-empty placeholder.
- [ ] AC-5: a `resume_conditions` source containing newlines, indentation and
      trailing spaces yields an emitted value carrying newline escapes, and
      round-trips with its indentation and trailing spaces intact.
- [ ] AC-6: each of FR14's five constraints has both an accepting case and a
      rejecting case, with the `branch` / `pr_url` rejection applied to the
      PARSED value rather than to the emitted text.
- [ ] AC-7: both modules are discovered by `python3 -m unittest discover -s
      tests`, run with zero skipped tests when the YAML parser is installed,
      and import no third-party module other than that parser — enforced by
      each module's own stdlib-only self-check.

## Test Notes

- These are pure unit tests: no repository document is read, so the modules are
  green inside this task's own worktree regardless of the other tasks'
  progress (IMPLEMENTATION.md D5).
- The 14-case matrix times 8 positions is 112 round trips; drive it
  table-style with subtests so a single failing combination is identifiable.
- Edge case: the noncharacter and line-separator code points must survive the
  round trip as the SAME code points — a parser that normalizes them would
  make the assertion misleading, so assert code-point equality, not visual
  equality.
- Edge case: the 64 KiB bound is on the ENCODED UTF-8 byte length of the whole
  document, not on the character count of any one value; the boundary cases
  must be constructed in bytes.
- Edge case: a source value that is already an escape sequence in text form
  (e.g. a backslash followed by `n`) must emit a doubled backslash and survive
  the round trip unchanged — this is the "never re-process a generated escape"
  rule, and it deserves its own case beyond the 14.
- TDD order: write the assertions and the adversarial table first, then the
  reference applier until green.
