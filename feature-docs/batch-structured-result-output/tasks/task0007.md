## Design

### The rule this task gives an owner (IMPLEMENTATION.md SC10)

No document currently owns how many assistant messages a terminal batch turn
has and which one carries what. `batch-mode.md` now states it for two
occasions (a stop turn, Step C) and SKILL.md states it for one run kind (the
cap-reached run). Everywhere else SKILL.md says only 「対話時と同じ内容を
全文報告する」, which a reader can satisfy inside the final message —
and a final message carrying prose plus the result fails the SSOT's
"exactly one bare YAML mapping and nothing else" rule, which NFR6 then makes
a consumer read as an abnormal outcome for a run that in fact succeeded.

SC10 is the canonical statement; this task writes it into SKILL.md as a
single general rule and binds it.

### 「## バッチ構造化結果」 (FR2, SC10)

The section gains one general rule covering EVERY turn on which the run
reaches a terminal state — normal completion, a `--once` phase boundary, and
every stop point the SSOT's coverage table binds:

1. That turn's LAST assistant message is the structured result and nothing
   else.
2. Every prose report the turn owes — the stop's cause, the affected paths,
   the recovery guidance, Step C's completion report, the audit items'
   human-readable narration — is emitted in the message(s) BEFORE that last
   one.
3. One result per run, unchanged.

The section's existing cap-reached-run paragraph is RETAINED and restated as
an instance of this general rule rather than as the rule's only carrier. Its
pinned sentences (`構造化結果は 1 走行につき 1 件出力し`, and the Step C
report / result ordering sentence) stay in the file, so
`tests/test_verify_cap_run_continuation.py`'s existing assertions keep their
subject; that module gains one assertion for the general rule.

### 「## 停止時の報告（停止条件 2-4 のみ）」 (FR17, NFR6)

The batch exception paragraph keeps naming every stop/abort site it names
today and keeps requiring the same content as interactive. It gains two
statements:

- WHICH message carries it: the messages preceding the turn's final one, per
  the general rule above.
- That the stop's cause, affected paths and recovery guidance are ALSO
  carried in full inside the result's own values — the cause and affected
  paths in `detail`, the recovery guidance in `resume_conditions` — so a
  consumer that reads only the result still has them (FR17). The prose report
  is an addition, never a substitute, and never a count or a pointer.

The section's three existing bullets (スタック / 中断 / YAML エラー) are
unchanged.

### Step C（完了処理）の終了報告 (FR17)

Item 3's audit-item sentence 「これらの監査項目は、この報告に続けて出す
構造化結果の値の中に全文で運ぶ」 is retained verbatim — it is pinned by
`tests/test_batch_stop_contract_skill_wiring.py` and it already agrees with
the general rule. Only a cross-reference to the general rule is added if the
implementer judges one necessary.

citation, no `state` value, no `step` value or sentinel, no reason code, no
removed prefix. Backticked `detail` / `resume_conditions` as prose references
to the SSOT's own bullets are the form the file already uses and stay
admissible; the existing whole-file absence guards are the arbiter.
