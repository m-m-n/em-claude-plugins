## Design

### SKILL.md's 終端行 section (FR20, NFR1)

The section is renamed to name the structured result (構造化結果) rather than
a line, and keeps its single job: stating WHEN the result is emitted. It
continues to:

- name `references/batch-terminal-line.md` as the sole SSOT of the format,
- instruct a Read of the SSOT immediately before emitting and use of the key
  set, ordering and value domains defined there as-is,
- enumerate the occasions (Step C completion, `--once` phase boundary, and
  every terminating stop condition it already lists) as occasions on which the
  emission condition holds,
- state that a turn which has not reached a terminal state emits no result,
  naming stop condition 5 and the implement launch / wake turns,
- state the cap-reached run's asymmetry: it reaches Step C, completes worktree
  cleanup and the final report, and is then reported as a stop rather than a
  normal completion, with the executed step being verify and the description
  value saying that Step C was reached and cleanup and reporting completed,
- state that exactly one result is emitted per run, and that on a cap-reached
  run it follows the Step C completion report.

It restates no SC5 literal. Every place that currently says 「終端行を1行出力
する」 or similar, and every place that describes the result as the LAST LINE
of the message, changes: the result is now the WHOLE final assistant message
(FR2), so the "appended after the report" wording for Step C must be restated
as the report being emitted first and the result being the message that
follows it, per the SSOT.

The completion-report instruction that requires the batch audit items
(自動承認コマンド / 記録した仮定 / rework 消費 / deferred findings) is
retargeted to IMPLEMENTATION.md SC7: those items are carried in full inside
the result's values, with the source map in `batch-mode.md` remaining the
place they are assembled from.

### implement-phase.md's citation (FR20)

The one sentence citing the SSOT for why the implement second-failure stop
takes precedence over the generic stop condition is left semantically
unchanged; only wording that names a "line" is restated. This file must remain
free of SC5 literals — it is currently used by another module as the
real-prose non-vacuity grounding for a false-positive proof, so its ordinary
use of the words `completed` / `skipped` / `stopped` must be preserved.

### Guard retargeting (FR22, NFR4, D3)

- `tests/test_batch_stop_contract_skill_wiring.py` and
  `tests/test_batch_quiet_output_skill_wiring.py`: the forbidden-literal sets
  become SC5; the prefix constant becomes a literal proved absent rather than
  a literal expected somewhere.
- `tests/test_verify_cap_run_continuation.py`: its section-heading constant
  and its three pinned Japanese fragments are updated to the renamed section
  and its new sentences, keeping the same underlying guarantees (the no-result
  rule, the Read-the-SSOT instruction, the stop-not-completion rule for a
  cap-reached run).
- `tests/test_failed_kind_stop_condition.py`: the pinned 自動再開 sentence is
  updated so it still asserts that an automatic resume emits no result and
  adds no new stop reason code.
- `tests/test_develop_once_option.py`: its SKILL.md `state`-literal guard is
  retargeted to SC5, keeping its existing forged-sample negative proof and its
  false-positive proof over ordinary step-status vocabulary.

Every NEW matcher carries a negative proof plus a non-vacuity guard. A matcher
that only changes its pinned Japanese sentence is a pure regression guard over
retained-meaning wording and is exempt.
