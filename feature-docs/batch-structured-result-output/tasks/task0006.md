# Task Plan: task0006 — Bump the em-workflow plugin version in both manifests

## Goal

The em-workflow version is raised past `0.1.82` to the same value in
`em-workflow/.claude-plugin/plugin.json` and in the `em-workflow` entry of
`.claude-plugin/marketplace.json`, with a new per-feature guard pinning the
baseline and leaving the `em-review` entry untouched.

## Requirements

FR21, FR22, NFR7

## Scope

### Files to Create

- `tests/test_batch_structured_result_output_version_bump.py` — TS10: the two
  manifests agree, the value is strictly past this feature's baseline, and the
  `em-review` entry is unchanged.

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — the version field.
- `.claude-plugin/marketplace.json` — the version of the entry whose name
  field is em-workflow.

## Design

Per `.claude/rules/core-plugin-version-bump.md`, a change under
`em-workflow/` must raise the version in both places, to the same value, in
the same change. This feature changes three documents under `em-workflow/`
(task0001, task0002, task0003), so the bump is required.

IMPLEMENTATION.md D9 fixes the bump size: a patch bump from `0.1.82`.
IMPLEMENTATION.md SC8 makes this task the only owner of both manifests, so no
other task can conflict on them.

The new guard module follows the repository's existing per-feature
`test_*_version_bump.py` convention rather than editing the generic
`tests/test_plugin_version_parity.py` (IMPLEMENTATION.md D4): it declares this
feature's own baseline (`0.1.82`), compares versions as dot-separated numeric
tuples rather than as whole strings, and looks the marketplace entry up by its
`name` field rather than by array position.

The `em-review` entry's identity fields and its version are asserted to be
unchanged in shape and value relative to the pre-change file, so a stray edit
there fails.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `em-workflow/.claude-plugin/plugin.json` and the marketplace entry
      whose `name` is `em-workflow` carry the same version string.
- [ ] AC-2: that version compares strictly greater than `0.1.82` under
      dot-separated numeric comparison, and the new guard demonstrates that a
      naive whole-string comparison would get a two-digit component wrong,
      proving the comparison is numeric.
- [ ] AC-3: the marketplace entry is located by its `name` field; a forged
      marketplace document missing that entry is rejected.
- [ ] AC-4: the `em-review` entry's `name`, `author`, `category`, `source` and
      `version` are unchanged from their pre-change values.
- [ ] AC-5: both manifests still parse as JSON, and every other key of each
      file is unchanged.
- [ ] AC-6: the new module is discovered by `python3 -m unittest discover -s
      tests`, imports the Python standard library only, and carries a negative
      proof for each matcher it introduces (versions disagreeing; version at
      the baseline; version below the baseline; malformed version shape).
- [ ] AC-7: nothing is added under `em-workflow/` beyond the version value
      itself (NFR7) — the new test module lives under `tests/`.

## Test Notes

- This is a unit-level guard over two JSON files; no runtime behaviour is
  involved and no other task's edits are needed for it to be green.
- Edge case: the `em-review` version must be pinned by exact value here, not
  merely by shape — this feature's requirement is that it is NOT touched, and
  a shape-only assertion would not detect a bump.
- Edge case: comparing `0.1.9` against `0.1.10` as whole strings gets the
  order wrong; the module must demonstrate this explicitly so a future reader
  cannot "simplify" the comparison back to a string compare.
- TDD order: write the guard with the new baseline first (it fails against
  `0.1.82`), then bump both manifests until green.
