# Task Plan: task0001 — Stop treating rm operands that `..` folds out of the protected area as protected self-config paths

## Goal

In destructive-guard's rm handling, an operand whose raw form matches
SELF_CONFIG but whose `..`-folded form leaves the protected area is no longer
treated as a protected self-config path, so its recursive deletion is decided
as deny / rm-recursive instead of being absorbed by the self-modification ask.
Operands that stay inside the protected area, and the behaviour for a HOME
outside /home (previous feature mixed-rm-self-config-deny, FR2 and A1), keep
their current decisions.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_destructive_guard_parent_ref.py` — unittest that runs the hook in a subprocess with HOME replaced by a value outside /home (TS-6, TS-12)

### Files to Modify

## Design

### The defect being fixed

`rm_protected_operand_numbers()` treats an rm operand as a protected
self-config path when either its raw form or its `normalize_candidate()` form
matches SELF_CONFIG. The raw form of `~/.claude/skills/../../valuable` matches,
so that operand is taken out of the recursive-delete deny pool although it
names `~/valuable`, and the statement ends with only the self-modification
ask (SPEC.md FR1).

### Three forms per operand

1. **Raw form** — the operand exactly as the function receives it today.
2. **Folded form** — the raw form with `.` and `..` segments folded
   lexically: empty and `.` segments are dropped and each `..` removes the
   segment before it. `~` and `$HOME` are not expanded; a leading `~` or
   `$HOME` segment stays as the anchor of the form. Computed from the string
   alone, with no filesystem access (NFR2).
   - **Anchor rule**: when a `..` segment consumes that leading `~` or
     `$HOME` anchor, the folded form has left the protected area and is
     treated as not matching SELF_CONFIG, whatever segments follow. A later
     literal `~` or `$HOME` segment therefore cannot rebuild a home-anchored
     form.
   - The anchor rule is a create-plan refinement of the folded form of
     SPEC.md FR1 and A2. It only makes more operands unprotected, so it moves
     decisions in the ask-to-deny direction only (NFR1).
3. **Normalized form** — the result of `normalize_candidate()` (HOME expanded,
   then folded). Unchanged by this task, and the anchor rule does not apply
   to it.

### Protected-operand rule

| Raw form matches SELF_CONFIG | Folded form matches | Normalized form matches | Protected |
|---|---|---|---|
| yes | yes | any | yes |
| yes | no | yes | yes |
| yes | no | no | no |
| no | not consulted | yes | yes |
| no | not consulted | no | no |

"Folded form matches" is "no" whenever the anchor rule applies. Stated as one
condition: an operand is protected when (the raw form matches AND the folded
form matches) OR the normalized form matches.

- The rule keeps the "raw or normalized" structure of the previous feature's
  FR2; it does not switch to judging the normalized form alone. That is what
  keeps `~/.claude/skills/foo` protected when HOME is not under /home (its
  normalized form does not match there, its raw and folded forms do).
- Examples (SPEC.md FR1): `~/.claude/skills/../../valuable` is not protected
  (folded `~/valuable`, normalized form outside too);
  `~/.claude/skills/../hooks/x` stays protected (folded
  `~/.claude/hooks/x` matches).
- Anchor-rule example: in `~/.claude/skills/../../../~/.claude/hooks/x` the
  third `..` consumes the leading `~`, so the folded form does not match and
  only the normalized form can protect the operand. With HOME under /home
  (for example /home/user) the normalized form `/home/~/.claude/hooks/x`
  still matches SELF_CONFIG, so the decision stays ask / self-modification;
  with HOME outside /home (for example /srv/user) it does not, and the
  operand gives deny / rm-recursive.
- TS-10 is unaffected: its folded form also consumes the anchor, but its
  normalized target is a safe deletion area, so no rm-recursive record
  arises and the self-modification ask remains.

### Call sites (FR3)

The function has two callers: the plain rm path and the path where a command
substitution leads the statement (the caller that passes the shaped words from
the skip index on). The new rule lives only inside the function, so both
callers get it without being edited. The exclusion condition (the statement's
`self_modification_asked`) and the per-operand unit of exclusion do not change.

### Docstring (FR4)

The docstring currently says the function matches the raw form or the
normalized form the same way `check_self_modification()` does. Rewrite that
passage to state the rule above: a raw-form match counts only when the folded
form also matches, and the folded form does not match once a `..` consumes the
leading `~` / `$HOME` anchor; a normalized-form match counts as before; and
`check_self_modification()` itself keeps matching on the raw or normalized
form.

### Unchanged

- `check_self_modification()` and its decision.
- The statement-level exclusion condition and its per-operand unit.
- `.claude/rules/hook-tests.md` (its precedence bullets stay correct) and the
  previous feature's SPEC.md.

### Unit test (TS-6, TS-12)

A new unittest module under `tests/`, picked up by
`python3 -m unittest discover -s tests`. It starts the hook as a subprocess,
handing it a Bash tool payload on standard input the same way the case-table
runner does, with:

- HOME set to a placeholder absolute path that is not under /home, not under
  any area `safe_delete_target()` treats as a safe deletion target (confirm
  against that function; the system temp directory is such an area), and
  whose last segment is not a literal `~`. The path need not exist.
- `CLAUDE_BATCH` removed from the environment.

It asserts the decision and the reason ID (the `[destructive-guard/<rule>]`
prefix of permissionDecisionReason) for three commands:

| Scenario | Command | Expected decision / rule |
|---|---|---|

| TS-6 | `rm -rf ~/.claude/skills/../../valuable` | deny / rm-recursive |
| TS-12 | `rm -rf ~/.claude/skills/../../../~/.claude/hooks/x` | deny / rm-recursive |

## Test Notes

- Write the new cases (AC-1 to AC-3, AC-5) and the unittest (AC-4) first. Run
  against the unchanged hook: TS-1, TS-2, TS-3, TS-5 and TS-9 are expected to
  fail there (they give ask / self-modification before the change), and so
  are the `..` command of TS-6 and TS-12; TS-4, TS-8, TS-10 and TS-11 are
  expected to pass both before and after the change.
- TS-12 exercises the anchor rule. Without that rule a plain lexical fold
  turns its operand back into `~/.claude/hooks/x`, which matches, and the
  decision stays ask / self-modification; a TS-12 failure after the change
  therefore points at the anchor rule.
- TS-7 is pinned to the observed output. Because the rule lives in the shared
  function, the `..` operand is expected to stay in the deny pool on this path
  too, so deny / rm-recursive is the expected observation. If the observed
  output differs, pin it as observed and state in the implementation report
  which check decides it.
- TS-11: run the base-commit hook once to read its decision and reason ID, and
  pin that pair.
- The case-table runner cannot replace HOME, so AC-4 is the only place the
  HOME-outside-/home behaviour is checked. Do not choose a HOME under the
  system temp directory: `..` targets would then land in a safe deletion area
  and give no rm-recursive record.
- A test under `tests/` pins a digest of the leading part of the case table
  (previous feature, A6). Appending at the end keeps it valid; if it fails,
  the edit touched the leading part.
- AC-6 is checked by reading the diff (docstring text, no filesystem query in
  the new rule).
