# Task Plan: task0001 — Launch guard git-common-dir fallback rules, tests and content pin

## Goal

On the launch guard's segment-free path, a correct launch is no longer denied
when the git common dir is not a `.git` directory, when the derived root does
not contain the worktree path, or when the project root is a linked worktree;
the standard linked layout keeps its denials, and the hook's content pin
matches the changed file.

## Design

Cross-task conventions (fail-open, containment vocabulary, content-pin rule,
test determinism) and the hook function contracts are in IMPLEMENTATION.md
(Conventions, Shared Components, D2). This section covers this task only.

### Decision flow of the cwd check

1. A missing or non-string cwd: no denial, before any process (unchanged).
2. Project-root determination:
   1. The normalized worktree path contains the segment: the root is the
      prefix before its last occurrence; a segment at the very start leaves the
      root undetermined (unchanged, FR5).
   2. Otherwise, the one existing git-common-dir call runs with the worktree
      path as its working directory and the existing timeout (NFR3). Every
      existing failure (cannot start, timeout, non-zero exit, empty or
      non-absolute output, invalid value) leaves the root undetermined
      (unchanged).
   3. The stripped output is lexically normalized (SPEC.md A1). When its last
      path element is not exactly `.git`, the root is undetermined (FR1).
   4. The candidate root is the parent of the normalized common dir — the same
      value the hook reports today and names in a denial.
   5. When the candidate root does not contain the worktree path (both
      resolved to real paths), the root is undetermined (FR2). This is decided
      before the cwd's toplevel is looked up, so no show-toplevel call runs in
      this case.
3. Root undetermined: no denial.
4. The cwd's toplevel comes from the existing show-toplevel call;
   unresolvable: no denial (unchanged).
5. Real toplevel equal to real root: no denial (unchanged).
6. Segment-free path only: when the root contains the toplevel and the
   toplevel strictly contains the worktree path, no denial (FR3).
7. Otherwise: denial naming the root, with the existing message, before the
   journal is touched (unchanged).

Steps 2.3, 2.5 and 6 use only the results of the two existing git calls and
the worktree path (FR4). None of them adds a denial.

### Placement

- Step 2.3 belongs to the fallback call's result handling
  (`git_common_dir_root`), so the root is undetermined exactly as for the
  existing call failures.
- Step 2.5 belongs to the project-root determination (`project_root_for`), so
  FR1 and FR2 share the documented statement that an undetermined root skips
  the cwd check.
- Step 6 belongs to the cwd check (`cwd_outside_project_root`), the only place
  that sees the toplevel. It tells the segment-free path apart by re-checking
  the worktree path for the segment, which starts no process.
- The function docstrings of these three functions describe the new
  behaviour.

### No new exception path (NFR2)

The comparisons in steps 2.5 and 6 receive absolute paths the earlier steps
already accepted (the worktree path served as the git call's working directory;
the toplevel already went through real-path resolution in step 5). If any
comparison still cannot be computed, the outcome is no denial; nothing new may
escape the hook's entry point.

### Module docstring (FR6)

The Project root paragraph gains three statements: the parent of the common
dir is taken only when the normalized common dir's last element is `.git`,
otherwise the root is undetermined; a root that does not contain the worktree
path is undetermined; on the segment-free path, the cwd check does not deny
when the root contains the cwd's toplevel and that toplevel strictly contains
the worktree path. The three statements TestHookDocstring pins (segment,
fallback, fail-open) stay present after whitespace normalization (SPEC.md A2).
The outside-layout statement TestHookDocstring checks for absence stays
absent.

### Content pin (FR8, A5)

`EXPECTED_LAUNCH_GUARD_SHA256` is set to the sha256 of the hook file's final
bytes in this change. The comment before it and the docstring of
TestNeverModifiedFilesAreByteIdentical stop saying the hook is unmodified;
they describe a content pin that follows the hook and name this feature's
task as having set it, in the style of the neighbouring merge-task.sh pin
comment. The test id `test_launch_guard_untouched` keeps its name.

### Fixtures (FR7)

- `TestFallbackCallShape.CANONICAL_PATH` and `TestFallbackFailures.WORKTREE_PATH`
  become segment-free paths under `/proj` (for example a store directory
  directly below `/proj`), so the derived root `/proj` contains them and the
  existing assertions hold under FR2.
- The real-git layouts: a main worktree M; a linked worktree L added from M
  and used as the project root; inside L a link placement whose target is
  inside L (as the existing placements do), through which an integration and a
  task worktree are added from L, so the canonical task path has no segment.
  Two placements of L: a sibling of M (outside M), and a directory below M
  (inside M). With L outside M, the allow comes from step 2.5 (M does not
  contain the task path); with L inside M, it comes from step 6.

## Test Notes

- AC-1 to AC-3: unit tests on the hook module loaded the way the existing
  classes load it, with the module's RecordingRunner standing in for the
  process runner. A RecordingRunner with no toplevel outcome fails on any
  show-toplevel call, which is how AC-2's "no show-toplevel call" is observed.
- AC-4: follows the existing hook-entry test in TestFallbackFailures (stdin and
  stdout replaced, a temporary directory for the worktree path).
- AC-5: real git through the module's run-git helper and git environment
  isolation; the hook runs as a subprocess, as in the existing linked-layout
  classes. Assert that the canonical task path lacks the segment, as the
  existing classes do.
- AC-3's ancestor case: choose paths so that the toplevel is a proper ancestor
  of the root; the expected outcome is a denial, which shows that FR3 needs the
  root to contain the toplevel and not only the toplevel to contain the
  worktree path.
- New test classes carry docstrings that name this task's AC labels; the
  module docstring's coverage list may gain them.
- Compute the content pin last, after the final hook edit, and re-compute it
  after any later edit to the hook within this task.
- Run the focused set first:
  `python3 -m unittest tests.test_queue_launch_guard_linked_layout tests.test_queue_launch_guard tests.test_merge_unverified_exit_doc_contract`,
  then the full suite.
