# Task Plan: task0001 — Move the I.2.a launch-state commit behind the approval gate and launch loop

## Goal

Step I.2.a commits `in_progress` only for tasks whose launch the re-read
journal confirms, after the `project_commands` approval gate and the `Task()`
launch loop, and the launch turn ends after that commit (or its omission). A new
document-contract test module fails on the old order.

## Requirements

FR1, FR2, FR3, FR4, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_prelaunch_inprogress_launch_order.py` — document-contract tests for TS1–TS4 over Region L and the Step I.2 intro, plus the TS6 negative proofs

### Files to Modify
- `em-workflow/references/implement-phase.md` — Region L of Step I.2.a and the Step I.2 intro (IMPLEMENTATION.md Shared Components); nothing else in the file

## Design

Region boundaries, the shared term "launch-state commit", the protected
sections and the test conventions are fixed in IMPLEMENTATION.md (Shared
Components, Conventions, D1–D3) and are not restated here.

### Target order of Region L

The paragraphs of Region L end up in this order. Content not named as changed
moves unchanged.

1. **Worktree creation** — the "For each selected task T" paragraph, the
   worktree-creation block, the "Branch point = …" sentence, and the
   **Resume guard** paragraph. The "Write the launch state …" sentence that
   currently follows "Branch point" moves out of this position.
2. **Approval gate** — the paragraph opening "Before launching, verify every
   `project_commands`", unchanged.
3. **Launch loop** — the BACKGROUND launch paragraph, the prompt payload, the
   "Do NOT inline" paragraph and the `tests_yaml_path` paragraph, unchanged;
   then the launch-guard sentence (the guard records each allowed launch as a
   `launched` journal event and denies double launches), kept with its
   current line break after "records".
4. **Journal re-read and write set** (new) — after the launch loop, re-read the
   latest journal. The write set is the tasks selected in this entry whose
   journal last event is `launched`:
   - no event for the task (stopped at the approval gate, denied by the launch
     guard, or `Task()` never issued) → not in the write set; the task stays
     `pending` in workflow.yaml;
   - last event `merged` or `failed` (terminal) → not in the write set; never
     written `in_progress`.
   A partial launch still yields exactly one write set and one commit.
5. **Sequence** — the existing capture / refresh / write / commit list, stated
   "in this normative order", with the four numbered lead-ins kept
   ("1. **capture**", "2. **refresh** the integration worktree to the branch",
   "3. **write**,", "4. **commit**"). Changes inside it:
   - write: `tasks.{T}.status = in_progress` and `tasks.{T}.branch` for every
     task in the write set (not every selected task) — one write set;
   - commit: named the launch-state commit; its message names every task in
     the write set; the third argument stays `"$LAUNCH_TIP"` in the same code
     span as `commit-docs.sh`; the exit-4 parenthetical keeps citing
     "exit-4 recovery: Branch & Worktree Model above".
   The rationale paragraph ("Capture precedes refresh …") and the **Idiom
   split** paragraph follow unchanged. The **Refill** paragraph keeps its
   statement that the sequence runs ONCE per entry into Step I.2.a, including
   the refill re-entry from Step I.2.b step 5, and that `$RECONCILE_TIP` is
   never reused; its coverage wording changes from every selected task to the
   write set, with at most one write set and one commit per entry.
6. **Empty write set** (new, FR3) — when the write set is empty (no confirmed
   launch, or every confirmed task already terminal at the re-read), the write
   and the commit are omitted.
7. **exit 4** (new, FR4) — the bounded recovery is the Branch & Worktree
   Model's, cited. Applied here: on the retry, the journal is re-read again
   after the re-capture and refresh, and the write set is re-derived the same
   way (terminal tasks excluded; an empty re-derived write set means no retry
   commit). A second exit 4 stops the phase with a report naming the call site
   (Step I.2.a's launch-state commit) and the tasks in the write set; the stop
   keeps the journal's launch records and the tasks' worktrees and branches —
   nothing is deleted or rolled back. Those tasks then read `pending` with
   journal last event `launched` and are in-flight under the in-flight rule in
   Region P (cited, not restated).
8. **End of turn** — the turn ends after the launch-state commit, or after its
   omission — no polling, no synchronous wait. The existing `--batch`
   marker-line sentence follows here and occurs exactly once in I.2.a.

### Step I.2 intro

The phrase stating that the launch phase's turn ends immediately after
launching is replaced by a statement that it ends after the launches and the
launch-state commit that follows them (or its omission). The rest of the intro
is unchanged.
