# Task Plan: task0005 — Align queue_stop_guard.py with the record-match classification

## Goal

The Stop hook classifies a `pending` + `failed` task exactly as the
orchestrator does. The task is unlaunched (the hook blocks to request a
refill) only when its last `failed` journal event is on the physical line
recorded in `tasks.{T}.routeback_failed_journal_line`. Otherwise the task
is failed, and the hook lets the turn end for that feature.

## Design

The record's contract (line counting, canonical form, absent / null) and
the three-condition match rule are pinned in IMPLEMENTATION.md Shared
Components. This task implements them in the hook.

**Journal replay.**

- For each task, keep the last event and the 1-based physical line it came
  from.
- Lines are split on LF only. A CR never starts a new line, so the file is
  not read with newline translation. A final non-empty segment without LF
  counts as a line.
- These lines advance the line counter but never become a task's event:
  - blank lines;
  - malformed lines;
  - lines with an unknown event;
  - lines with an invalid task id.

**Record lookup.**

- Read the record only from the task's own `taskNNNN:` block. Use the same
  scoping `task_statuses_from_workflow` uses for `status`. A
  `routeback_failed_journal_line:` line inside another task's block or at
  step level is never this task's record.
- Within the task's block, the first occurrence wins.
- Accept only the canonical form: an unquoted run of ASCII digits whose
  first digit is 1–9, optionally followed by trailing whitespace.
- Treat anything else as no record. That includes: `null`, `~`, empty,
  `0`, a negative number, a non-integer, a quoted value, a leading zero, an
  inline comment and any other trailing text.

**Classification (`evaluate_feature`).**

- A `pending` task whose last event is `failed` is unlaunched only when
  that event's line equals the record.
- Otherwise it is failed. A failed reconciled state means the hook does not
  block for that feature (exit 0), as the existing rule already does for
  failed tasks.
- No-event, `launched` and `merged` classifications are unchanged.
- workflow.yaml is still read lazily, only when the classification needs
  it.

**Docstring.**

- State the three-condition classification and the failed outcome.
- Keep "the task's own id, returned from `failed` to `pending` by
  route-back".
- Do not introduce "a recycled task id left behind by a route-back
  re-plan".

**Constraints (NFR5).**

- Standard library only.
- No YAML library. Reading stays line-based.
- The source never contains "subprocess", "rev-parse", "show-toplevel" or
  "find_project_root".
- Any unexpected state, including a read or parse error, ends with exit 0
  (fail-open).
- The executable text, with docstrings stripped, still contains both
  "workflow.yaml" and "status". `tests/test_hook_classification_pin.py`
  relies on that co-occurrence.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR9, TM-2): For a `pending` task whose journal last event is
  `failed`, invoked as a subprocess:
  - (a) a record equal to that event's line gives exit 2, and the task is
    named for launch;
  - (b) no record gives exit 0;
  - (c) `null` gives exit 0;
  - (d) a different line gives exit 0. This includes a task relaunched and
    failed again on a later line.
- [ ] AC-2 (FR9, TM-2): Non-canonical record values give exit 0 for an
  otherwise matching task: `0`, a negative number, a non-integer, a quoted
  number, an empty value and a leading-zero number.
  - (g) A matching-looking record placed in another task's block or on a
    step-level line is not read as this task's record.
- [ ] AC-3 (FR9, TM-3): (f) Blank lines, malformed lines, unknown-event
  lines and invalid-task lines before the target `failed` line are
  counted.
  - The correct physical line gives exit 2.
  - The line number obtained by skipping those lines gives exit 0.
  - A CR inside a line does not shift the count.
- [ ] AC-4 (FR9, NFR3): No-event, `launched` and `merged` classifications
  are unchanged. Every existing case in `tests/test_queue_stop_guard.py` is
  kept. The three recycled-task-id tests carry a matching record in their

  - `test_consecutive_block_cap_still_works_with_reclassified_task`

  The Layer 2 pending fixture in `tests/test_queue_hook_status_read_pin.py`
  carries a matching record and keeps its expectation.
- [ ] AC-5 (FR9): The module docstring states the three-condition
