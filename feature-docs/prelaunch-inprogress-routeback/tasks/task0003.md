# Task Plan: task0003 — Record already-failed launches in the I.2.a launch-state commit

## Goal

Step I.2.a's launch-state commit also records, as `failed`, a task that
launched in this entry and had already failed by the time the journal is
re-read. Such a task is never left `pending`, so it cannot later be mistaken
for a route-back reset and relaunched automatically.

## Requirements

FR2, FR3, FR4, FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_prelaunch_failed_launch_state.py` — document-contract tests for the FR7 write-set rule in Region L, with negative proofs

### Files to Modify
- `em-workflow/references/implement-phase.md` — Region L only: the journal re-read and write-set paragraph, the write step, the empty-write-set paragraph and the exit-4 paragraph

## Design

Edit region: Region L only (IMPLEMENTATION.md Shared Components, "Edit
regions in implement-phase.md"). Region P, I.2.b, I.2.c, the Supporting cast
and the Branch & Worktree Model are not touched.

**Write-set rule after the change.** The journal is re-read after the launch
loop, as now. The single write set of this entry then has two parts:

1. **in_progress part** — tasks selected in this entry whose re-read
   journal last event is `launched`. Write `tasks.{T}.status = in_progress`
   and `tasks.{T}.branch` for each. This part is unchanged.
2. **failed part** — tasks selected in this entry that meet two
   conditions. First, a `launched` event for the task appears in the
   re-read journal after the extent replayed at selection time (the replay
   at the top of I.2.a). Second, the re-read last event is `failed`. Write
   `tasks.{T}.status = failed` and `tasks.{T}.branch` for each, in the same
   write set and the same launch-state commit. Never write `in_progress`
   for such a task.

**Selected tasks that are not written:**

- No `launched` appended after the selection-time replay. This covers:
  - a task stopped at the approval gate;
  - a task denied by the launch guard;
  - a task whose `Task()` was never issued;
  - a task that was already `pending` + `failed` at selection and did not
    launch this time.

  Such a task stays `pending`.
- Last event `merged`. It is left to I.2.b.

**The record.** The launch-state write never sets or changes
`tasks.{T}.routeback_failed_journal_line`. The record's contract is in
IMPLEMENTATION.md Shared Components. Name it here only as a field this
write leaves alone.

**Commit message.** The commit message still names every task in the write
set, both parts.

**Empty write set.** The write set is empty only when both parts are empty.
In that case the write and the commit are omitted, and the turn still ends
after that omission.

**exit-4 retry.** The journal is re-read again after the re-capture and
refresh. Both parts of the write set are re-derived by the same rule. The
same rule also applies to a task that reached `failed` between the first
attempt and the retry. An empty re-derived set means no retry commit. The
second-exit-4 stop text is unchanged in substance. The exit-4 recovery
bullet is still cited, not restated.

**Literals that must remain in Region L.** They are pinned by
`tests/test_prelaunch_inprogress_launch_order.py`, which this task must not
edit:

- "re-read the latest journal" — its first occurrence must precede the
  write-set definition;
- "The write set is the tasks selected in this entry whose journal last
  event is `launched`" — it may be extended after this phrase;
- "stopped at the approval gate", "denied by the launch guard",
  "`Task()` never issued", "the task stays `pending` in workflow.yaml";
- "A partial launch still yields exactly one write set and one commit";
- "naming every task in the write set";
- "when the write set is empty", "the write and the commit are omitted";
- "on the retry, the journal is re-read again after the re-capture and
  refresh", "the write set is re-derived the same way";
- "last event `merged` or `failed`", "never written `in_progress`";
- the second-exit-4 phrases, and "Step I.2.a's launch-state commit";
- "**End the turn** after the launch-state commit, or after its omission";
- the `tasks.{T}.status = in_progress` write literal, the `LAUNCH_TIP`
  capture and refresh lines, and the `commit-docs.sh` call with
  `"$LAUNCH_TIP"`. They keep their order: gate → background launch →
  re-read → capture → refresh → write → commit → end of turn.

**Other Region L constraints:**

- The `--batch` marker sentence occurs exactly once.
- The exit-4 bullet's own phrases ("RE-CAPTURE the tip from the branch
  ref", "never loop unbounded", "re-apply the SAME intended state
  transition") are not restated.
- The literal term "launch-state commit" stays.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR7, FR2): Region L defines both parts of the single write set.
  - The in_progress part is tasks selected in this entry whose re-read
    last event is `launched`.
  - The failed part is tasks selected in this entry whose `launched` event
    was appended after the selection-time replay and whose re-read last
    event is `failed`.
  - The failed part gets `tasks.{T}.status = failed` and `tasks.{T}.branch`
    in the same write set and the same launch-state commit, and is never
    written `in_progress`.
- [ ] AC-2 (FR7): Region L states that a selected task with no `launched`
  appended after the selection-time replay is not written, naming the case
  of a task already `pending` + `failed` at selection that did not launch.
  It also states that the launch-state write does not change
  `tasks.{T}.routeback_failed_journal_line`.
- [ ] AC-3 (FR2, FR3): The commit names every task in the write set, both
  parts. A partial launch still yields one write set and one commit. The
  write and the commit are omitted only when both parts are empty, and the
  turn ends after the commit or its omission.
- [ ] AC-4 (FR4): A last event `merged` is never written and is left to
  I.2.b. No terminal task is written `in_progress`. On the exit-4 retry,
  both parts are re-derived from the journal re-read after the re-capture
  and refresh. The second exit 4 still stops the phase, keeping the launch
  records, worktrees and branches.
- [ ] AC-5 (FR6, NFR4): `tests/test_prelaunch_failed_launch_state.py` has a
  positive test for each of AC-1 to AC-4. Each matcher fails against a

  changes. Everything outside Region L is byte-identical to the base
