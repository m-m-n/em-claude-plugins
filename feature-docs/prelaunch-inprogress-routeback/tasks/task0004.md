# Task Plan: task0004 — Limit the recycled-task-id carve-out to the route-back record

## Goal

`implement-phase.md` reclassifies a `pending` + `failed` task as unlaunched
only when its last `failed` journal event is the one route-back reset.
Route-back records that event as `tasks.{T}.routeback_failed_journal_line`.
Every other `pending` + `failed` task goes through I.2.c's failure handling
instead of being relaunched automatically.

## Requirements

FR5, FR6, FR8, FR9, FR10, NFR1, NFR2, NFR3, NFR4

### Files to Modify

## Design

Edit regions follow IMPLEMENTATION.md Shared Components, "Edit regions in
implement-phase.md". Region L is not touched. The record's contract and the
three-condition match rule are pinned in IMPLEMENTATION.md Shared
Components. This document applies them to the protocol text. It cites
`references/workflow-schema.md` for the record's definition and does not
restate the line-counting or canonical-form rules.

**1. Region P — carve-out definition (FR8 (2)).**

- Rewrite the "Recycled task id" rule. A task is unlaunched only when all
  three conditions hold:
  - its status is `pending`;
  - its journal last event is `failed`;
  - that event's physical line equals the record.
- State the outcome for a `pending` + `failed` task that fails the match:
  - The match fails when the record is absent, null, not in canonical form,
    or names a different line.
  - Such a task is `failed`. It goes to I.2.c's failure handling (batch:
    `implement.failed-task` in `references/batch-policies.yaml`, cited).
  - This includes a task route-backed before this change that carries no
    record.
- State that nothing clears the record: a re-launched task that fails
  again has its last `failed` event on a new line, so it no longer matches.
- These pinned phrases must survive:
  - "This carve-out is deliberately scoped to `failed` only" — exactly once
    in raw text;
  - "The carve-out reclassifies only a task whose journal last event is
    `failed` and whose workflow.yaml `status` is `pending`" — text may be
    appended after "`pending`";
  - the two-parties phrase naming `queue_stop_guard.py`;
  - the in-flight sentence.

**2. Region P — Reason sentence (FR10).**

- Replace the claim that the `pending` + `failed` combination "arises only
  from I.2.c's own reset". The sentence names two origins:
  - a route-back reset;
  - a launched task that failed without reaching the launch-state commit,
    whether through an interruption or after a second exit 4.
- It states that the record match tells the two apart.
- Keep the citation of the allocation rule. It must contain "allocation
  rule" and must not contain "task0001" or "renumber".
- I.2.a must not contain "task0001" anywhere.

**3. Region P — FR5 addition.**

- Add: a task whose launch-state commit was not reached and which later
  fails becomes `pending` + `failed`. Its `failed` event does not match the
  record, so the carve-out does not apply and the task is `failed`.
- Place it so that these spans stay byte-identical:
  - the replacement sentence, from "Given I.2.c's route-back precondition
    below" to "the recycled-task-id carve-out above does not apply to it.";
  - the whitespace between that sentence and "Because Step I.2.c's
    route-back gate below";
  - the premise span, with exactly one "Because " and one " so ".
- Do not insert between the replacement sentence and "Because". Insert
  elsewhere, for example next to the rewritten Reason sentence or after the
  carve-out definition.
- No "never arise" / "never arises" claim is introduced.

**4. Region P — divergence paragraph.** Update the mention of
`queue_stop_guard.py` to say that its carve-out also requires the record
match. Do not introduce "fail-open" anywhere in that paragraph.

**5. I.2.b step 1.**

- Keep "the recycled-task-id rule in I.2.a above" and the no-event note.

**6. I.2.c route-back write set (FR8 (1), NFR1).**

Add exactly one item to the existing ordered write set. For each task in
the reset target set that has a journal event, set
`tasks.{T}.routeback_failed_journal_line` to the physical line of that
task's last `failed` event. The line comes from the same journal replay
used for the gate and the reset-set decision. A task with no journal event
gets no record. The item is committed by the existing
"docs({feature}): implement route back to planning" commit. No new write
and no new commit are introduced.

Insertion constraints:

- Put the item after "set `tasks.{T}.status` back to `pending` for every
  task in that set" and before " — the gate above already established". As
  a fallback, put it between "`tasks.{T}.notes`," and " and set".
- Do not split the raw span from "clear `failed_kind`" through "— record"
  plus its trailing line break and indentation.
- The first `tasks.{T}.status` in I.2.c must still have "pending" within 60
  characters after it.
- The added item contains neither "rework" nor "append".
- Nothing else in I.2.c changes. That covers the gate's three conditions,
  the reset set, the cleanup targets, the residual sentence ending "already
  cover" and the batch-mode tail paragraph.
