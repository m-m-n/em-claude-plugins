# Task Plan: task0001 — Refresh the version-bump test baseline and align the task0002 test record

## Goal

`tests/test_exit4_tip_argument_version_bump.py` actually guards the
exit4-tip-argument em-workflow version bump: it goes red on a tree whose
em-workflow registries read the real pre-bump value at that feature's diff
base, a new stdlib-only test detects drift between the baseline constant and
the forged pre-bump sample, and the module text plus the AC-1/AC-2/AC-3
`red_reason` values of `test-docs/exit4-tip-argument/task0002.tests.yaml`
describe the new baseline.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

- `test-docs/exit4-tip-argument/task0002.tests.yaml` — the red_reason values of AC-1, AC-2 and AC-3 only

## Design

This feature has a single task; no IMPLEMENTATION.md exists for it. Every
decision this task needs is stated here.

### Current state (facts the task starts from)

- The module's baseline matcher parses a version string into a
  (major, minor, patch) integer triple with the module's own
  `_parse_version` helper and requires it to be strictly greater than
  (0, 1, `BASELINE_PATCH`) under per-component numeric comparison.
- `BASELINE_PATCH` reads 44 and
  `TestValidationDetectsRegressions.FORGED_PRE_BUMP_VERSION` reads
  `"0.1.44"`. At exit4-tip-argument's diff base (`02aff93`) both registries
  carried em-workflow `0.1.68`, so an un-bumped tree currently passes the
  baseline tests.
- The module locates both registries relative to its own file location
  (repository root = parent of the `tests/` directory).

### Change 1 — Baseline constant (FR1)

`BASELINE_PATCH` becomes 68: the em-workflow patch level both registries
carried at exit4-tip-argument's diff base `02aff93`. The comment above the
constant states that pre-bump fact (both registries read `0.1.68` at that
diff base) instead of the old `0.1.44` statement.

### Change 2 — Forged pre-bump sample (FR2)

`FORGED_PRE_BUMP_VERSION` becomes `"0.1.68"`. The negative proof
(`test_baseline_matcher_rejects_forged_pre_bump_version`) and its
non-vacuity guard (`test_forged_pre_bump_version_is_well_formed`) keep
their structure and run against the new value. `FORGED_VERSION_A` /
`FORGED_VERSION_B` stay unchanged: they are an arbitrary differing pair for
the equality matcher.

### Change 3 — Baseline/sample tie test (FR4)

One new test method in `TestValidationDetectsRegressions`.

| Aspect | Contract |
|---|---|
| Precondition | None (reads no file; uses only the two class/module constants) |
| Postcondition (pass) | `FORGED_PRE_BUMP_VERSION` parses through `_parse_version` into a triple whose major/minor are (0, 1) and whose patch equals `BASELINE_PATCH` |
| Postcondition (fail) | Any other outcome fails the test: the sample does not parse, major/minor differ from (0, 1), or the patch differs from `BASELINE_PATCH` |
| Constraints | Standard library only; reuses the existing `_parse_version`; no git invocation; no new import |
| Naming | Follows `test/README.md`'s `test_<condition>_<expected_result>` convention; the exact name is not load-bearing |

The test carries a docstring stating which drift it detects (a change to
either constant without the other). The module-level matcher inventory is
not otherwise restructured.

### Change 4 — Module text alignment (FR3)

Every docstring and comment that states the old baseline is rewritten to the
new one:

| Current location | Current wording | Rewritten to |
|---|---|---|
| line 2 | "strictly greater than 44" | the new baseline patch |
| lines 8-9 | "major/minor `0.1` and patch strictly greater than 44" | a description of the per-component comparison against (0, 1, `BASELINE_PATCH`) — later minor or major bumps stay green — rather than a `0.1` pin (SPEC A6) |
| line 18 | "patch > 44" | the new baseline patch |
| lines 27-29 | "raising the baseline patch to 44 ... un-bumped `0.1.44` tree" | the new baseline and its source (the pre-bump value at exit4-tip-argument's diff base), with the module going red on an un-bumped `0.1.68` tree |
| line 56 comment | "both registries read 0.1.44" | covered by Change 1 |

After the change, no text in the module presents `44` or `0.1.44` as the
baseline. The AC-2 docstring's "still carries no `version` key" wording is
left untouched (NFR5, out of scope).

### Change 5 — Per-task test record alignment (FR5)

In `test-docs/exit4-tip-argument/task0002.tests.yaml`, only the
`red_reason` values of AC-1, AC-2 and AC-3 change:

- Each names the new baseline (patch 68 / pre-bump `0.1.68`) instead of
  44 / `0.1.44`.
- Each quotes the `AssertionError` text actually observed in the red run
  below. The baseline matcher compares triples, so the observed message has
  the form "(0, 1, 68) not greater than (0, 1, 68)", not
  "68 not greater than 68"; record what the run prints, never a
  reconstructed message.
- AC-2's trailing em-review clause (the retention checks were already green
  pre-bump since that entry is untouched) is kept unchanged.
- AC-3 keeps its other claims (the module did not exist before task0002;
  standard-library-only imports and no other test module), with its
  baseline wording and quoted failure updated.
- Every other field of the file is byte-for-byte unchanged, including
  `task_id`, `baseline_failures`, `final_failures`, every `tests` list (the
  stale AC-2 entry `test_em_review_entry_has_no_version_key` included,
  NFR5), every `red_confirmed` flag, and the AC-4 / AC-5 entries.

### Red-run flow (FR5, NFR1)

1. With Changes 1 and 2 applied, build a throwaway tree outside the
   repository working tree (a temporary directory). Because the module
   locates registries relative to itself, a minimal tree holding the module
   and the two registry files at their repository-relative paths is
   sufficient.
2. In the throwaway tree only, set the em-workflow version in both
   registries (the plugin manifest and the em-workflow marketplace entry) to
   the pre-bump value `0.1.68`.
3. Run the module against the throwaway tree. The baseline tests for
   AC-1 (`test_version_is_past_baseline`) and AC-2
   (`test_em_workflow_entry_version_is_past_baseline`) must fail; capture
   their exact `AssertionError` lines.
4. Copy the captured text into the three `red_reason` values (Change 5).
   The throwaway tree is never committed and the repository's registry files
   are never edited.

This task changes no plugin version: it touches no file under a plugin
directory, and the throwaway tree in step 2 is a test fixture outside the
repository.
