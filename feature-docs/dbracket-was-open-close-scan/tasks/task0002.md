# Task Plan: task0002 — Keep reading the words after the closer except redirection targets

## Goal

In the `was_open` branch of `_args_json_conditional_step()` in destructive-guard,
the words after the valid closer `]]` of a continuation statement are read
again, except the redirection targets. A new `[[` after `then` / `do` right
after the closer makes the chunk uncertain again (deny), while the `>=~` /
`>-eq` redirection forms keep the exclusion of the notion call (allow). The
comment, the docstring and the regression tests follow the revised reading.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

## Design

No IMPLEMENTATION.md is written for this feature (reduced tier; this is the
only task left to implement). This plan is self-contained.

### Current state of the code

- The `was_open` branch reads the statement's non-operator words in order. A
  word before the closer goes through the two uncertain checks (`_unsettled()`,
  and membership of its restored text, `_args_json_declaration_word()`, in
  `_ARGS_JSON_DOUBLE_BRACKET_WORDS`); either makes the result (true, true) at
  once. The closer is the first word written exactly `]]`
  (`_args_json_word_source()`) with no stripped trailing carriage return. At
  the closer the branch stops: no word after it is read.
- A comment above that loop states that Bash accepts only redirections (and
  the `)` of an enclosing group) after the closer in the same statement.
- The docstring's paragraph on the opener statement ends with "Words before
  the opener and words after the closer are not read here. In a later
  statement that holds the closer, the words up to just before the closer are
  read and the words after the closer are not read here."
- TestDbracketWasOpenCloseScan in `tests/test_destructive_guard_args_json.py`
  pins this reading: READ_PAST (`[[ true && true ]] >=~`,
  `[[ true && true ]] >-eq`), KEEP_DENY (`[[ true && true =~ true ]]`,
  `[[ true && true -eq 0 ]]`), the closer-operand forms, the docstring
  sentences (NEW_SENTENCE, OLD_SENTENCE) and a row set of exactly six case
  rows under the label prefix `dbracket-was-open-close-scan` (four allow, two
  deny).

### The defect

lex_segments() ends a statement only at `;`, `&`, `&&`, `||`, a pipe or a
newline; `then` and `do` end none. Bash accepts `then` / `do` directly after
`]]` with no separator, and a new `[[` after them. In
`if [[ true && true ]] then [[ 0 -eq SID=1 ]]; fi` the statement after `&&` is
`true ]] then [[ 0 -eq SID=1 ]]`. The branch stops at its first `]]`, and the
command-level reading sees the allowlisted command name `true`, so `-eq` is
read nowhere: the notion call after it turns from KIND_INSPECTED / deny into
KIND_NOTHING / allow. `while [[ true && true ]] do [[ -v x ]]; done` is the same
with `-v`. The assumption behind the stop (only redirections follow the closer)
is wrong.

### Contract of the changed branch

- Precondition: `was_open` is true. The inputs (the marked chunk, the
  statement's tokens, its simple commands, its separator, `was_open`) and the
  result shape (UNCERTAIN, OPEN) are unchanged.
- Processing flow:
  1. Read the statement's tokens in their order of appearance, operator tokens
     included, so the reading can tell which word directly follows a
     redirection operator. Operators are recognized on the tokens after the
     fused-closer split that the scan already applies to the same statement
     (`_split_fused_closer_redirects()`), so a fused `)>` counts as `)`
     followed by `>`.
  2. Before the closer, each non-operator word is handled as now: the closer
     test first; otherwise, when `_unsettled()` holds for the word or its
     restored text is in `_ARGS_JSON_DOUBLE_BRACKET_WORDS`, the result is
     (true, true) at once. A word after a `<` or `>` before the closer is read
     too (inside the conditional those compare strings). A `]]` written with a
     backslash, a quote or a line continuation, and a `]]` with a stripped
     trailing carriage return, are not closers and are read past, as now.
  3. The closer closes the conditional, and the reading continues with the
     next token.
  4. After the closer, a non-operator word that directly follows a redirection
     operator token is that operator's target and is not read. Every other
     non-operator word after the closer (`then`, `do` and the other reserved
     words, a new `[[`, its operands and operator words, a later `]]`) goes
     through the same two checks, and either makes the result (true, true) at
     once.
  5. A redirection operator is a token the lexer marked as an operator whose
     whole text has the redirection-operator shape that `split_redirects()`
     recognizes (the module's REDIRECT shape). A quoted or escaped `>` or `<` is
     a word, not an operator, so the word after it is read. An operator token
     without that shape (`)`, `(`) is not a redirection operator, and the word
     after it is read.
  6. OPEN after the statement is false when a closer was met and true
     otherwise, as now. The tail of the function is unchanged: an open
     conditional whose statement ends at a `;` or a lone `&` is (true, true);
     otherwise the result is (false, OPEN).
- Postconditions and invariants:
  - The opener-statement branch (`was_open` false) is not changed.
  - The only caller stays `_args_json_nameref_scan()`; its other readings
    (redirection-variable subscript, deferred evaluation, the command-level
    reading of each simple command) are unchanged.
  - Static analysis only: the function launches nothing, reads no file, builds
    no decision and names no `destructive-guard/` reason ID (NFR2, NFR3); its
    source keeps passing the existing forbidden-name tests. A helper factored
    out for the redirection test, if any, is called only from this function
    and follows the same rules.
- Why the existing rows keep their decision (NFR1): the changed branch reads a
  subset of the words the branch read at the merge base with `main` (every word
  of the statement), since it skips only redirection targets after the closer,
  and a superset of the words it reads now, since it no longer skips the other
  words after the closer. A row that passed at the merge base as allow stays
  allow, a deny row that passes now stays deny, and the four rows whose word
  after the closer is a redirection target stay allow because that word is
  skipped.

### Comment and docstring (FR4)

- The comment that states Bash accepts only redirections after the closer is
  removed or rewritten, so the source of the function no longer holds the
  phrase "accepts only redirections".
- In the docstring, the sentence "In a later statement that holds the closer,
  the words up to just before the closer are read and the words after the
  closer are not read here." is replaced by this sentence, which AC-5 pins
  verbatim after whitespace normalization:

  "In a later statement that holds the closer, the words up to just before the
  closer are read; after the closer, the redirection targets are not read
  here, and the other words, such as a new `[[` after `then` or `do`, are
  still read."

- The opener-statement sentence "Words before the opener and words after the
  closer are not read here." stays.

  when its first word is not an allowlisted name. The scan-level "reads false"
  assertions of AC-4 therefore keep a continuation statement led by `true`.
- The then / do forms are judged without the array assignment (SPEC AC-6); the
  KEEP_DENY forms keep theirs.
- Several other test modules iterate every case-table row (for example the
  stage-agreement test of `tests/test_destructive_guard_lexer_agreement.py`),
  so run the whole `unittest discover`, not only the changed class.
