# Threat Model: verify-cap-worktree-cleanup

## Verdict
threats-identified

## Rationale

**What was inspected.** SPEC.md and REQUIREMENTS.md, at tier full. The
feature relaxes a guardrail hook. For a new excluded state of workflow.yaml, the
hook stops denying S1 (`git worktree remove`) and S3 (`gh pr create`).

**The hook's inputs.**

- The PreToolUse Bash payload. Its command string is generated by the agent and
  can be steered by injected content.
- The target feature's workflow.yaml. It is untrusted (NFR3). Its free-text
  fields, such as `goal`, carry text from an external task description.

**Analysis depth.** Both boundaries are analyzed at deep depth, driven by
task0001's domains:

- `auth`: the hook is a permission decision point.
- `input-handling`: the hook parses the payload and workflow.yaml.

**Scope of the threats recorded.** Threats are recorded only where the new
exclusion path widens what passes the guard. The following behaviors are
unchanged by this feature, so they get no row:

- fail-open on an unreadable workflow.yaml or a missing PyYAML (NFR4)
- target-path resolution
- the content of deny reasons
- the fact that an actor able to rewrite step statuses freely can already make
  any feature look healthy

**Tasks outside the boundaries.** task0002 changes only README prose and
touches no trust boundary.

## Trust Boundaries

### TB-1: workflow.yaml content → excluded-state decision
Crossing: the target feature's workflow.yaml reaches the hook. The orchestrator
and workers write it inside the feature worktree, and its free-text fields come
from an external task description. The hook parses it, and the parsed content
now decides whether S1 / S3 get a deny or no decision.
Boundary files: `em-workflow/hooks/failed-run-cleanup-guard.py`
Depth: deep (auth, input-handling)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
|---|---|---|---|---|---|
| Tampering | A malformed or type-confused cap record is read as a reached cap. Examples: `rounds` given as a string or a boolean, `failed_id_counts` given as a list, a `failed_id_counts` value of true. A failed run that never hit the cap then passes as excluded, and S1 / S3 lose their deny (FR2, FR3) | TM-1 | Strict typing per FR3. A boolean is never read as an integer. A `batch`, `verify_rework` or `failed_id_counts` that is not a mapping never yields exclusion. A present member of the wrong type invalidates the whole cap record | task0001 AC-3 | VERIFICATION.md Performance / Security Verification, TM-1 (TS-5) |
| Tampering | Free-text fields such as `goal` carry text shaped like step statuses or cap values, and that text sways the exclusion decision (NFR3) | TM-2 | The decision reads only two things from the parsed structure: the top-level steps' id and status, and `batch.verify_rework`'s `rounds` and `failed_id_counts`. No other field and no raw text is consulted | task0001 AC-4 | VERIFICATION.md Performance / Security Verification, TM-2 (TS-11) |
| Elevation of privilege | An unexpected value shape makes the new exclusion evaluation raise. The exception lands in the hook's fail-open path (NFR4). A failed run that is not in the excluded state then gets no decision instead of today's deny (FR6) | TM-3 | The excluded-state classification is total. For any parsed shape it cannot classify, it returns "not excluded" instead of raising, so the existing deny path is reached | task0001 AC-3 | VERIFICATION.md Performance / Security Verification, TM-3 (TS-5) |

### TB-2: Bash command payload → per-shape decision for unresolvable targets
Crossing: the agent-generated command string reaches the hook, and
prompt-injected content can steer it. The string selects the command shapes and
their targets. When a target cannot be resolved statically, the hook aggregates
over the worktrees it can enumerate.
Boundary files: `em-workflow/hooks/failed-run-cleanup-guard.py`
Depth: deep (auth, input-handling)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
|---|---|---|---|---|---|
| Elevation of privilege | One payload chains an unresolvable S1 and an unresolvable S2. Memoization lets the S1 aggregate, which counts excluded worktrees as healthy, be reused for S2. S2 then gets no decision for an excluded feature's branch instead of ask, or deny under CLAUDE_BATCH (FR4, FR5) | TM-4 | The unresolvable-target aggregate is memoized separately for each command shape. S2 always counts excluded-state worktrees as failed | task0001 AC-5 | VERIFICATION.md Performance / Security Verification, TM-4 (TS-9) |
