# Task Plan: task0001 — Excluded state for verify cap-out runs in failed-run-cleanup-guard

## Goal

For a feature in the excluded state, failed-run-cleanup-guard emits no decision
for S1 and S3. S2, and every failed state that is not the excluded state, keep
today's behavior. Regression tests pin this, and the module docstring states the
judgment model.

## Requirements

## Design

The judgment model is defined in IMPLEMENTATION.md, Cross-task Design Decisions,
D1. This task implements it. This section states only the parts that belong to
this task.

### Excluded-state classification (one feature)

- Input: the workflow.yaml content already loaded for one target. It is
  untrusted and may have any shape.
- Output: excluded or not excluded.
- Precondition: none.
- Postcondition: the result is "excluded" only when D1's conditions (a)–(d) hold
  under D1's cap-record reading. The classification never raises for any parsed
  value (THREAT-MODEL.md TM-3). In these cases it returns "not excluded":
    - a step entry that is not a mapping
    - a step entry whose id or status is missing or is not a string
    - a cap-record member of an invalid type
    - any other shape it cannot classify
- Fields consulted: only the top-level steps' id and status, and
  `batch.verify_rework`'s `rounds` and `failed_id_counts`. Free-text fields such
  as `goal` and notes are never consulted (NFR3, THREAT-MODEL.md TM-2).
- The two thresholds (2 for the lineage cap, 3 for the hard cap) are each defined
  once in the hook and match develop SKILL.md's lineage-cap definition (NFR5).

### Targeted commands

Flow for a resolved target whose feature has a failed step:

1. Classify the feature from the already-loaded content. Do not read the file
   again (NFR2).
2. S1 or S3 with an excluded result: emit nothing and exit 0.
3. Every other case: take today's deny path unchanged. This covers S2 for any
   failed feature and S1 / S3 for a feature that is not excluded. The reason
   wording is unchanged (FR4, FR6).

### Unresolvable targets

- Classify each enumerated worktree once per payload: healthy, failed and
  excluded, or failed and not excluded. Each worktree's workflow.yaml is read at
  most once, even when one payload holds both an S1 and an S2 (NFR2).
- The per-worktree classification does not depend on the shape, so it may be
  shared between shapes.
- The aggregate of the two shapes differs:
    - S1 counts failed and excluded as healthy.
    - S2 counts it as failed.
- Memoize the aggregate separately for each shape. A result computed for S1 is
  never returned for S2, and an S2 result is never returned for S1 (FR5,
  THREAT-MODEL.md TM-4).
- The ask when no worktree can be enumerated, and the CLAUDE_BATCH demotion,
  stay as they are today.

### Module docstring

Rewrite the docstring's judgment model to state D1:

- the excluded-state conditions (a)–(d) and the cap-record reading
- the per-shape outcome table
- per-shape counting for unresolvable targets
- the unchanged invariants: no allow, no subprocess, no file write, fail-open

## Test Notes

- **How tests run.** Drive every criterion through the hook's real entry point:
  a JSON payload on stdin, as the existing tests in this file do. Build fixtures
  in tempfile trees laid out the way this file's existing fixtures lay out an
  integration worktree, and reuse its fixture helpers.
- **Check existing cases first.** Before writing new cases, look for any existing
  case whose fixture already satisfies the excluded state while expecting a
  deny. Such a case contradicts FR1. Change it so that one exclusion condition
  breaks and its deny expectation stays, and say so in the task report.
- **Table-driven cases.** AC-3 and AC-4 are table-driven: one table row per case,
  with each row reported as its own sub-case. Each AC-3 case asserts on the deny
  reason's wording, not only on the decision.
- **Read count (AC-5).** Load the hook as a module and count calls to its
  workflow-loading routine. If this file already has a read-count harness,
  reuse it.
- **Static invariants (AC-6).** If existing tests already pin the hook's static
  invariants (no subprocess, no allow), rely on them. Otherwise add a test. Do
  not assert on a bare "allow" substring of the source, because the docstring
  legitimately mentions it.
- **AC-7** is checked by inspection in verify. No test is required.
- Run no real git command and no load-generating loop.
