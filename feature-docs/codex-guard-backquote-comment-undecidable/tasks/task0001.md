### 1. Checkpoint (reader)

A checkpoint is a newline that the reader itself reads at the top level, at which all of these
hold (FR2):

1. No group is open: the stack of open groups is empty.
2. No pipe is pending: no `|` or `|&` is still waiting for its right side.
3. No list continuation is pending: the list has not been left open by a trailing `&&` or `||`.
4. The heredoc bodies registered on that line have been read through their terminators.

How the reader records it:

- The reader keeps the last checkpoint as two counts: the number of simple commands and the number
  of groups recorded so far. Only these two numbers are stored, never a copy of a list, so each
  newline costs constant time (NFR1).
- The counts are updated in the reader's newline handling, after the newline has finished the
  simple command in progress and after that line's heredoc bodies have been read. An unterminated
  heredoc body raises before this point, so condition 4 needs no separate check. A line
  `python3 -i <<EOF` followed by the line `print(1)` and nothing else therefore has no checkpoint.
- New reader state, "list continuation pending":
  - it is set when the reader reads `&&` or `||`;
  - it is cleared when a simple command with words is finalized, or when a group opens;
  - a newline that ends an empty command (a blank line or a comment-only line) and a heredoc body
    leave it as it was.
- The existing pending-pipe state already persists in the same way and is reused unchanged.
- Only the main reading loop's own newline can be a checkpoint. A newline inside quotes, a
  substitution chunk, an argument range or a heredoc body never is, and neither is a
  backslash-newline pair. `;` and `&` are never checkpoints, so a launch before an undecidable
  fragment on the same line stays silent.

### 2. Carrying the checkpoint commands (decision for A3)

Chosen form: an attribute on the `_Undecidable` exception.

- `_Undecidable` keeps its name. Every existing raise site keeps raising it as it does today, with
  a reason text.
- `_Undecidable` gains one attribute that holds the checkpoint commands. Its value is an empty
  sequence unless the reader sets it.
- When an `_Undecidable` raised while reading leaves the reader's parse method, that method:
  1. settles connection and skip for the groups opened before the last checkpoint;
  2. attaches the first N simple commands to the same exception, where N is the command count of
     the last checkpoint (an empty sequence when there is no checkpoint);
  3. re-raises the same exception.
- Postcondition: every attached command takes its group's connected and skipped values exactly as
  a full read would set them.
  - The pass visits the groups opened before the checkpoint once each, in the order they opened,
    and applies the same rule as the final pass of a full read.
  - Prefer one definition of that rule shared by both paths, so they cannot drift.
  - The pass is correct because, at a checkpoint, no group is open and every attribute that feeds
    connection and skip is already final: pipe, stdin redirect after the close, head stdin, and
    the function-body mark.
- The reader neither catches nor alters any exception other than `_Undecidable`.
- On success, the module-level parse function and the reader's parse method keep their signatures
  and their return values.

Why this form: no raise site changes, the success path keeps its return shape, and the walk keeps
exactly one try statement around the nested parse call.

### 3. Walk

- **Nested strings (_scan)**:
  - The handler for `_Undecidable` takes the exception's checkpoint commands as the commands of
    that string. It adds them to the work list exactly as it adds the commands of a fully read
    string: same inherited connection, level one higher. An empty sequence leaves nothing to judge.
  - The string's length still counts toward NESTED_READ_LIMIT before it is parsed, so an
    undecidable string counts at its full length.
  - The handler for the general exception class is unchanged: it skips the string and neither
    returns nor raises.
  - _scan keeps exactly one try statement around the nested parse call, and that statement
    catches both `_Undecidable` and the general exception class (NFR2).
- **Hook command (find_deny)**:
  - When the top-level parse raises `_Undecidable`, the walk runs over the exception's checkpoint
    commands.
  - Any other exception reaches main as it does today, so there is no output.
  - find_deny keeps its single `command` parameter and still calls _scan.

## Test Notes

- **Test first**: add the TS1 to TS3 rows first. They fail against the current code, which is
  silent for all of them, and they pass once Design sections 1 to 3 are in place.
- **Silent rows**: write the TS4 rows before the implementation too. Most of them already pass
  against the current code. They pin the four checkpoint conditions and the full-read settlement
  of connection and skip, so an implementation that drops one condition, or skips the settlement
  pass, fails at least one of them. For example, the connected group and the function-body rows
  fail when the settlement pass is missing.
- **Documentation test**: add the marker test first. It fails until the docstrings are rewritten.
- **Deep-input shape**: a natural home is TestMalformedAndDeepInput. The expected verdict is deny,
  because the last line before the unbalanced quote is a launch.
- **Edge cases from SPEC.md**:
  - the comment-exception edge case is pinned by the extra deny row;
  - an unterminated heredoc on the launch line is a TS4 row;
  - `cat <<EOF` followed by `python3 -i` is an existing silent row;
  - an error other than `_Undecidable` is covered by TestNestedParseErrorContainment on the syntax
    tree.
- **Copies**: run the whole suite after the copies are synchronised. The byte-identity test fails
  if they drift.
