# Task Plan: task0001 — Release the held ID after a tab line in the tests-block parser

## Goal

In the record check's tests-block parser, a tab line at or shallower than the
items' depth no longer leaves the preceding ID "held". A deeper line that
follows such a tab line therefore no longer takes back the readable ID written
before the tab line. That ID reaches resolution again, and the record's single
failure lists every extraction and resolution error together. Regression tests
pin both reproduction records from the ticket.

## Requirements

## Scope

### Files to Modify

## Design

### Terms

- **Tab line**: a line whose first character after its leading spaces is a
  tab.
- **Items' depth**: the indentation of the first item line without a tab, as
  fixed by the existing pre-item scan (unchanged).
- **Held ID**: the state the item loop tracks with its held-ID flag
  (`last_is_id`). It is set while the most recent element is a readable
  one-line scalar kept in the ID list, so that a deeper line following it
  can take that ID back as the first-line fragment of a multi-line value.

### Item-loop tab-line rule (FR1, FR2)

The tab-line branch of the item loop in `_RecordParser.parse_tests` behaves as
follows for every tab line:

1. Report the line once as `tab in indentation`. This is unchanged and happens
   at every depth.
2. Take the held ID back out of the ID list only when both of these hold: the
   line is deeper than the items' depth, and an ID is currently held.
3. In every case (deeper, same depth or shallower), leave the loop with no ID
   held before moving on to the next line.

Postcondition: right after any tab line, no ID is held. A deeper line that
follows a tab line therefore takes nothing back:

- A deeper tab line is reported only as a tab error (rule 1).
- A deeper line without a tab keeps its existing handling. It is reported once
  as `tests item continues or nests on a deeper line (multi-line or nested
  value)`, the deeper lines after it are skipped as today, and no ID is
  removed.

The branch for deeper lines without a tab and the item-line branch are not
changed.

### Behaviors that must not change (NFR1)

These existing behaviors stay exactly as they are, and the existing tests that
pin them pass unmodified:

- A tab line deeper than the items, directly after a readable ID, takes that
  ID back and is reported only as a tab error.
- Consecutive deeper tab lines take the held ID back once and are each
  reported.
- A deeper tab line after an element that is not an ID (a mapping item, for
  example) takes nothing back.
- Lines without a tab after a deeper tab line keep their existing handling.
- A tab line at the items' depth or shallower keeps the IDs before and after
  it.
- Tab lines before the first item, blocks made only of tab lines, and the
  resumption of the field loop are unchanged.

### Comments and docstring (FR5)

- The comment in the item loop's tab-line branch no longer says that the held
  state stays after a tab line at the items' depth or shallower. It states
  rules 1 to 3 above.
- The tab-line part of the method docstring states the same rules. Only a tab
  line deeper than the items, directly after a readable ID, takes that ID
  back. After any tab line no ID is held, so a deeper line that follows a tab
  line takes back nothing.
- The comment on the held-ID flag stays consistent with this: a tab line
  counts as an element that leaves no ID held.

denotes one tab character. In test code it is written as an escape sequence
inside the string literal, never as a raw tab (NFR3), following the existing
record helper of the tab-line test class.
