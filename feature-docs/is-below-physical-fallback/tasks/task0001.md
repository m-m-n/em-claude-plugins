# Task Plan: task0001 — Physical-path fallback in the cd-prefix path check

## Goal

The Bash guard's cd-prefix path check allows a path that Bash reaches through its physical-path fallback. That is the case where the logical path is not an existing directory and the physical path is an existing directory strictly below the area. Every form whose logical destination lies outside the area stays not allowed. The two written statements of the path condition are updated to the new rule.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

## Design

### Terms

- **Path**: the directory operand of the cd prefix, as written in the command.
- **Logical path**: the canonical, symlink-resolved form of the lexically normalized path. Each `..` is first collapsed against the written component before it, and only then are symbolic links resolved. This models Bash's default logical cd. (SPEC calls this the logical path.)
- **Physical path**: the canonical, symlink-resolved form of the path exactly as written. Symbolic links are resolved component by component, and each `..` applies to the directory already resolved. This models the kernel resolution that Bash falls back to when the logical move fails. (SPEC calls this the physical path.)
- **Strictly below the area**: compared by path components against the same area value the existing check uses. The area itself is not below it, and neither is a sibling that only shares a name prefix (for example the `em-workflow-x` directory next to the area).

### Judgment rule (the contract of the path check)

Precondition: the existing cd-prefix syntax check has extracted the path. The area is determined exactly as today.
Postcondition: the check returns True only in the rows marked True below; every other outcome is False.

| Logical path | Physical path | Result |
|---|---|---|
| Existing directory strictly below the area | Existing directory strictly below the area | True (unchanged, FR2) |
| Existing directory strictly below the area | Anything else | False (unchanged, FR2) |
| Existing directory not strictly below the area | Anything | False (unchanged, FR2, FR4) |
| Not an existing directory (absent, or a file) | Existing directory strictly below the area | True (new, FR1) |
| Not an existing directory (absent, or a file) | Absent, a file, the area itself, outside the area, or a prefix-only sibling | False (FR5) |
| Resolution or comparison raises OSError or ValueError | - | False (NFR4) |

Processing flow:
1. Compute the logical path and the physical path.
2. If the logical path is an existing directory, return the existing two-sided result: both paths are existing directories and both are strictly below the area.
3. Otherwise, return whether the physical path is an existing directory strictly below the area.
4. An OSError or ValueError raised anywhere in steps 1-3 makes the result False.

### Constraints

- Only the path check changes. These stay as they are: the cd-prefix syntax and approval conditions, the forbidden-pattern deny, the exact-match allow, the declared-but-unapproved deny, and the absence of output for unrelated commands (FR6). When the path check returns False, the command keeps today's consequence: it is treated as having no cd prefix, so no new deny arises.
- Both branches use the existing path-component comparison for "strictly below". Do not add a string-prefix comparison.
- The judgment is pure in-process path resolution. Never imitate Bash's cd by running a shell or any other child process. Never give the path to a child process as a working directory or an argument (NFR3, TM-3).
- Import only standard-library modules (NFR1).
- No new identifier or string literal in the hook's executable text may contain the substring `status` (NFR2). This applies to local names and messages too.
- On every path the hook still exits 0 and writes nothing to stderr (NFR4).

### Path-condition wording (FR7)

The hook's module docstring and the protocol's Verbatim execution rule both state the same rule in prose. If the logical path is an existing directory, the logical path and the physical path must both be existing directories strictly below the area. Otherwise the physical path alone must be an existing directory strictly below the area. Each place defines the two terms in one short phrase, as in "Terms" above. This replaces the current single-realpath wording in both places. The docstring keeps its existing description of the rest of the cd-prefix form.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Let P be `/proc/self/root/..` followed by the absolute path of an existing worktree directory inside the area. A cd-prefixed approved string with P receives allow, from both Fixture working-directory kinds (the plain repository and a git worktree). When `/proc/self/root` is not a directory, the case is skipped, not failed. (FR3, FR8)
- [ ] AC-2: A symbolic link L outside the area points at a deep existing directory inside the area. A cd-prefixed approved string with path L, then `..`, then the name of an existing directory under the target's parent receives allow. In this form the logical path does not exist and the physical path is an existing directory inside the area. A second case also receives allow: the logical path is an existing file while the physical path is an existing directory strictly below the area. (FR1, FR8)
- [ ] AC-3 (TM-1): A symbolic link inside the area is followed by `..`. The logical path is an existing directory outside the area, and the physical path is an existing directory inside the area. This form produces no output: the hook does not allow it. (FR2, FR4, FR8)
- [ ] AC-4 (TM-2): The logical path is not an existing directory. Each of the following physical paths produces no output: an existing directory outside the area, the area itself, a directory under a sibling that only shares a name prefix with the area, a path that does not exist, and an existing file. (FR5, FR8)

The full suite passes under the workflow.yaml test command. The new tests import only standard-library modules, use the existing Fixture isolation, and read neither the real user approval store nor the real repository's workflow.yaml. (FR6, NFR1, NFR2, NFR3, NFR5)
- [ ] AC-7: The hook's module docstring and the Verbatim execution rule in `em-workflow/references/command-execution-protocol.md` both state the rule given under "Path-condition wording". Neither still states the single-realpath condition. (FR7)

## Test Notes

- AC-1 to AC-4 are hook-level cases in `tests/test_bash_guard_cd_prefix.py`, built on the existing Fixture: its area, its inside directory, its root, and the `em-workflow-x` sibling. Where the SPEC names it, the new forms go into the existing `PATH_CASES` table (AC-4 in particular). Symbolic links and files go only under the Fixture's temporary root.
- AC-1 builds P from the Fixture's inside directory. It covers both working-directory kinds the Fixture already provides. The skip condition is `/proc/self/root` not being a directory.
- AC-2 is the /proc-independent reproduction. The SPEC example is a link named hop at the Fixture root that points at the area's task0001/sub directory, with the path hop, then `..`, then sub. The file variant places an existing file where the logical path lands, while the physical path lands on a directory.
- AC-3 needs an existing directory at the logical destination outside the area (for example under the prefix-only sibling) and an existing directory at the physical destination inside the area.
- AC-5 can be checked on the path check directly and also end to end through the hook. If the hook's command parsing rejects the NUL input before the path check runs, keep the direct check, and keep the end-to-end check only for the observable exit code, stderr and decision.
- "No output" means the hook prints no decision, which is the existing convention of this test file for "not allowed by the cd-prefix rule".
- Run the full suite with the workflow.yaml test command. AC-6 and AC-7 are partly confirmed in review: the docstring and protocol wording, and the isolation of the new tests.
