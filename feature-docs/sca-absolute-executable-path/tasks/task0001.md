# Task Plan: task0001 — Absolute-only executable resolution for scan jobs

## Goal

`resolve_executable` searches only the absolute entries of the search list.
Every SCA scan job then launches its scanner by an absolute path, whatever the
job's working directory, and a scanner reachable only through relative or
empty entries is reported as not found.

## Requirements

FR1, FR2, FR3, FR5, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_sca_absolute_executable_resolution.py` — unit and run_scan integration tests for this task's Acceptance Criteria

### Files to Modify
- `em-workflow/scripts/scan-dependencies.py` — absolute-only resolution and its docstring, plus the FR5 updates to the Scan job construction section comment and the build_scan_jobs docstring

## Design

### Resolution (FR1)
Implements the `resolve_executable(name)` contract and the absolute-entry rule
pinned in IMPLEMENTATION.md Shared Components.

1. Take the search list. If the process PATH is present, use it (an empty
   value counts as present). Otherwise use the platform default search path
   that SPEC FR1 names (`os.defpath`), read at call time so that a test can
   substitute it.
2. Keep only the absolute entries, per the rule. Empty and relative entries
   (`tools`, `./node_modules/.bin`, `.`, `~/bin`) are skipped. Nothing is
   expanded, and no implicit current-directory entry is searched on any
   platform.
3. Walk the kept entries in their original order. The first entry that holds
   an existing, non-directory file named `name` that the current user may
   execute wins. This is the same executable test the previous resolution
   applied.
4. Return that entry joined with `name`, unnormalized. The result is an
   absolute path. Return none when no entry qualifies.

Postcondition: the return value is either none or an absolute path. The
signature (one argument) is unchanged.

### Not found (FR2)
`build_scan_jobs` keeps its existing branch: when resolution returns none, the
ecosystem gets `<ecosystem>_tool_not_found` once, with no plan and no
fallback. Nothing changes here except what resolution returns. No new reason
is added.

### argv[0] (FR3)
`build_scan_job` and `run_scan` do not change (IMPLEMENTATION.md D3): argv[0]
is the plan's executable. Because of resolution's postcondition, the launched
file is the same absolute file whatever the job's cwd: the project root, a
nested go project directory, or an npm / cargo isolation directory.

### Comments (FR5; IMPLEMENTATION.md D2)
- `resolve_executable`: add a docstring that states the contract above.
- "Scan job construction" section comment: resolution searches only PATH's
  absolute entries (the default search path when PATH is unset) and never
  relative or empty entries.
- `build_scan_jobs` docstring: the same, plus the fact that a scanner found
  only under relative or empty entries produces the existing tool-not-found
  reason.

Do not edit the comment above `CHILD_ENV_BASE_KEYS` or `build_child_env`.
Both belong to the sibling child-PATH change (IMPLEMENTATION.md D2).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, TM-1): Set the process cwd to a temporary directory and set PATH to the relative entries `tools`, `./node_modules/.bin`, `.` and an empty entry, followed by one absolute stub directory. Each relative entry (resolved against that cwd) and the stub directory hold an executable `npm`. Resolving `npm` returns the stub directory entry joined with `npm`, exactly as written. That is an absolute path and never a path under a relative entry.
- [ ] AC-2 (FR1): Remove PATH from the process environment and substitute the default search path with a mix of relative / empty entries and an absolute stub directory, each holding an executable `npm`. Resolving `npm` returns the stub's absolute path.
- [ ] AC-3 (FR1, FR2, TM-1): Set PATH to only `tools`, `./node_modules/.bin`, `.`, an empty entry and `~/bin`, with an executable `npm` under each of them relative to the process cwd. Resolving `npm` returns none. Planning a change of `package.json` and `package-lock.json` returns zero plans and exactly the skip reasons `["npm_tool_not_found"]`.
- [ ] AC-4 (FR1): Among several absolute entries, an entry holding a directory named `npm`, or a non-executable file named `npm`, is passed over, and the first later absolute entry holding an executable `npm` is returned.
- [ ] AC-5 (FR3, TM-1): Run the attack scenario through run_scan. The reviewed project has `services/api/package.json`, `services/api/package-lock.json` and an executable `services/api/tools/npm`, and the process cwd holds an executable `tools/npm`. Both planted files leave a marker file when launched. PATH is `tools`, then the platform path-list separator, then the recording-stub directory. The single recorded npm launch's launch path is the stub's absolute path, and neither marker file exists.
- [ ] AC-6 (FR3): Run run_scan for a nested go project (`services/api/go.mod`, cwd `<root>/services/api`), a root go project, a pip requirements file (cwd the root), an npm project and a cargo project (cwd the isolation directory). Every recorded launch path is absolute and equals the value that resolution returns for that ecosystem's executable under the same PATH.
- [ ] AC-7 (FR5): The `resolve_executable` docstring, the Scan job construction section comment and the `build_scan_jobs` docstring state two things: only absolute entries are searched (the default search path when PATH is unset), and a scanner found only under relative or empty entries produces the existing tool-not-found reason. None of them describes resolution as a plain PATH lookup. Verified by inspection.
- [ ] AC-8 (NFR1, NFR2, NFR3): `python3 -m unittest discover -s tests` passes, and this task modifies no existing test file. The script still imports only standard-library modules. `ALLOWED_EXECUTABLES` and the skip-reason tokens are unchanged.

## Test Notes

- Put the tests in the new module `tests/test_sca_absolute_executable_resolution.py`.
  It loads the script by file path and owns its harness. Follow the shape of
  `ScanHarness` in `tests/test_sca_scan_unchanged_surfaces.py`: a project
  tree, a stub directory, a record file, a temp parent outside the project
  (through the temp-directory setting) and a reviewer HOME. Copy that shape
  rather than importing it.
- The recording stub must record the path it was launched through (the
  interpreter's view of its own argv[0]) in addition to argv, cwd and env. The
  existing stubs record only argv[1:]. Stubs use the absolute path of the
  current interpreter in their shebang.
- AC-1, AC-3 and AC-5 need a controlled process cwd, because relative entries
  resolve against it. Change into a temporary directory (for AC-5, the project
  root is the realistic choice) and restore the cwd in cleanup. AC-5's marker
  stubs write the marker to an absolute path outside the scanned tree.
- AC-2: substitute the default search path module-wide for the duration of
  the test and remove PATH from the environment, then restore both.
- AC-3 `~/bin`: create a literal `~` directory under the cwd. Nothing expands
  it.
- AC-1 to AC-4 are unit tests on resolution and planning. AC-5 and AC-6 are
  integration tests through run_scan.
- Before the change, these tests fail: AC-1 and AC-5 get a relative
  `tools/npm`, AC-2 searches the system default path instead of the
  substituted list, and AC-3 finds a relative entry.
- Do not assert the child environment's PATH (IMPLEMENTATION.md Conventions,
  cross-task test independence).
- AC-7 is verified by inspection. AC-8 is the full-suite run.
