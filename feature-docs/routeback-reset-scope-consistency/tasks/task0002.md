## Goal

Move both plugin version registries from `0.1.38` to `0.1.39` in this change,
so the installed-plugin cache picks up task0001's protocol edit, and pin that
with a test module whose baseline goes red on an un-bumped tree.

## Design

### The version change

Both registries carry the em-workflow plugin version and must always agree —
an installed plugin is cached per version, so a protocol edit shipped without
a bump keeps serving stale files. The bump is a patch step (`0.1.38` →
`0.1.39`, SPEC.md A-3). Only the `version` value changes in each file: key
order, formatting, indentation and every other field stay as they are, and
both files must still parse as JSON afterwards.

### The new test module

`tests/test_routeback_reset_scope_version_bump.py`, following
IMPLEMENTATION.md's "Test conventions" and D8:

| Scenario | Asserts |
|---|---|
| TS-9 | `em-workflow/.claude-plugin/plugin.json` parses as JSON, its `name` is still `em-workflow`, and its `version` is on the `0.1.x` line with a patch number strictly greater than 38; the `em-workflow` entry of `.claude-plugin/marketplace.json` parses as JSON and reports exactly the same version string; the `em-review` entry's `source` is still `./em-review` |

Two design points, both deliberate:

- **Durable baseline, not a fixed literal.** The version assertion is
  expressed as "major.minor == 0.1 AND patch > 38", the pattern the existing
  version-bump module uses. A hard-coded `0.1.39` would go stale on the very
  next unrelated bump; the baseline form stays true afterwards while still
  going red on the un-bumped `0.1.38` tree (IMPLEMENTATION.md, D6).
- **No assertion about `implement-phase.md`.** The whole-file bare-git-line
  invariant belongs to task0001 (NFR6 / TS-7) and is already covered by two
  existing modules; duplicating it here would make this module's result depend
  on a file it does not own (D6, D7).

Both files are parsed as JSON rather than pattern-matched, so a malformed edit
fails with a clear message instead of a silent mismatch.

## Test Notes

  runtime behaviour to integration-test.
- TDD order that actually produces a red: write the module first and run it
  against the un-bumped tree — the baseline assertion fails on `0.1.38` — then
  edit the two JSON files. Record that observed red per criterion in the
  tests.yaml record.
- `tests/test_recycled_task_id_version_bump.py` asserts the same two files
  against baseline 37 and must stay green; that is a check on this task's
  edit, not a file to modify.
- The edit is two single-value replacements. Reformatting either JSON file, or
  reordering its keys, is a defect even when the parsed value is unchanged.
