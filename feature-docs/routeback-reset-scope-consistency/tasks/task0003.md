## Design

### Why this is one task

The three failed items land in one file, and two of them in one bullet of one
section. They also share one root cause: task0001 moved the derivation source
of the route-back path without re-deriving the three statements that hang off
it — the write set's postcondition (MANUAL-1), the cleanup's not-merged claim
(MANUAL-2) and I.2.a's pointer back at the gate (MANUAL-3). Splitting them
across worktrees would guarantee a merge conflict in `implement-phase.md` and
in the single document-contract module that pins its wording, and would let one
task's edit silently break an ordering or containment anchor another task
asserts (IMPLEMENTATION.md D3). One owner, one worktree.

### The anchor-preservation contract still governs every edit

IMPLEMENTATION.md D3 applies to this task exactly as it applied to task0001,
and every literal task0001's module already asserts is now ALSO a
precondition. Two of its constraints are the likely way this task breaks:

  `append_merged_event`, may not say "journal append" or "appended", and may

### Site A — the reset target set covers both `failed` sources (MANUAL-1)

Present state (route-back bullet): the ordered write set runs over "the reset
target set — every task whose Step I.2.b step 1 reconciled state is `failed`",
and the sentence that follows concludes "the result is that no task is left
`merged` or `in_progress` or `failed`, which is exactly what makes the
planner's `replace_planning` operation admissible on re-entry".

The defect: the postcondition and `references/workflow-patch.md`'s
`replace_all` permission conditions are evaluated over workflow.yaml's own
`tasks.{T}.status` values, but the target set is now defined over the
reconciled state. The two sets can diverge — Step I.2.b step 3 writes
`status: failed` for a task "whose report is `failed`/malformed" even when the
journal carries no event for that task, and such a task's reconciled state is
unlaunched, not `failed`. Nothing in the gate covers workflow.yaml `failed`.
A diverged task is then left `failed` after the write set, and the re-plan hits
the `replace_all` protocol error.

Required after the edit:

- The reset target set is stated as covering BOTH sources: every task whose
  Step I.2.b step 1 reconciled state is `failed`, AND every task workflow.yaml
  reports `status: failed`. Same union vocabulary the gate's two halves already
  use (IMPLEMENTATION.md D2: either member puts a task in the set; neither
  replaces the other).
- The literal `` every task whose Step I.2.b step 1 reconciled state is
  `failed` `` survives verbatim and stays the leading member of that phrase —
  the existing TS-2 matcher reads it as one contiguous string.
- One sentence states WHY both are named: the two sets can diverge (cite Step
  I.2.b step 3 as the owning rule for the workflow.yaml write, do not restate
  it — D5), and the postcondition together with `replace_all`'s permission
  conditions are read off workflow.yaml's own statuses, so covering both is
  what makes the postcondition true rather than assumed.
- The four write instructions and their order, the `replace_planning` /
  `replace_all` citation and the postcondition sentence are otherwise
  unchanged; the pre-change workflow.yaml-`status`-only phrasing
  (`` **every** failed task's `tasks.{T}.status` back to `pending` ``) stays
  absent.

### Site B — the cleanup sentence is a consequence of the gate, not a second filter (MANUAL-1, finding 5a9c94c87a6f7c4f)

Required after the edit:

- The literal "a task whose reconciled state is `merged` is never a cleanup
  target, whatever workflow.yaml says" survives (the existing TS-3 matcher), as
  does "clean up worktrees and branches for exactly the tasks the write set
  just reset".

### Site C — the not-merged claim is weakened to what is verified, and the residual is recorded (MANUAL-2)

Present state: the cleanup targets are described as "confirmed not merged"
without qualification. Nothing on this path runs `git merge-base
--is-ancestor` against a cleanup candidate: that check applies in Step I.2.b
step 1 only to tasks that CLAIM `merged`. `merge-task.sh` advances the
integration branch with `git update-ref` and only afterwards writes the
`merged` journal event, and a failure of that write is a warning that does not
fail the script. An implementer stopping in that window, with no completion
report, leaves the failure net writing `failed`, a reconciled state of
`failed`, a gate that does not block — and an already-merged branch deleted by
`git branch -D`.

Required after the edit:

- The unqualified "confirmed not merged" is replaced by the claim the document
  actually establishes: not merged under the two sources this path reads —
  workflow.yaml `status` and Step I.2.b step 1's reconciled state.
- A residual-state sentence, written in the same shape as the existing
  leftover-state sentence and placed after it, records what those two sources
  cannot see: a task whose merge already advanced the integration branch while
  its `merged` event never reached the journal (the window inside
  `merge-task.sh` between the ref update and its journal write, whose failure
  the script reports without failing) is indistinguishable from a failed task
  here, so route-back can still delete such a branch. State it as a known
  residual of this gate, not as something the gate closes.
- No new verification step, no new command and no behaviour change is
  introduced on this path: the reviewer's option (a) — an ancestor check per
  cleanup candidate — is NOT taken (IMPLEMENTATION.md D9, item 3, records
  why).
- The commit-before-cleanup order, the leftover-state sentence and the single
  `git branch -D` occurrence survive.

Required after the edit:

- One added sentence gives the ownership chain (I.2.a carve-out ← I.2.c gate ←

  carve-out applies only when the journal's last event is `failed`, so Step
  I.2.b step 1's `merged` classification never consults it and the chain is not
  circular.
- Placement: inside the recycled-task-id paragraph, after the existing
  recursion-invariant sentence, i.e. after the "can never arise." terminal —
