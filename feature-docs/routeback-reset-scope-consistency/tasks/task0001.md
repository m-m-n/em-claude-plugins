## Design

### Why this is one task

Every prose requirement edits `implement-phase.md`, and FR1–FR4 edit one
bullet of one section of it. Splitting them across tasks would guarantee a
merge conflict on every parallel run and would separate the wording from the
assertions that pin that exact wording, so the document and its
document-contract module are one owner's responsibility (IMPLEMENTATION.md,
D1). The eight acceptance criteria below are the consequence of that
indivisibility, not of scope creep.

### Site 1 — I.2.c gate: the `merged` conjunct becomes a two-source union (FR1)

Present state: the gate sentence states the conjunction "no task has status
`merged`, and no task has status `in_progress`", both re-read from
workflow.yaml; a following sentence widens ONLY the `in_progress` half into a
union of two independent sources, citing Step I.2.b's last-event-per-task rule
as owner.

Required after the edit:

- The `merged` conjunct is stated as a union of two independent sources,
  either of which blocks: workflow.yaml reporting a task `merged`, OR Step
  I.2.b step 1's reconciled state reporting a task `merged` (journal last
  event `merged`, verified by `git merge-base --is-ancestor` as that step
  already requires).
- Step I.2.b is CITED as the owning rule and never restated
  (IMPLEMENTATION.md, D5).
- Union semantics, not replacement: workflow.yaml `status: merged` with no
  `merged` journal event still blocks (SPEC.md EC-6), and a `merged` claim
  that fails the ancestor check is NOT merged and does not block (EC-3).
- The existing literal `` "no task has status `merged`" `` survives; the union
  is added around it, not substituted for it.

Placement (IMPLEMENTATION.md D3 constraint 5): the new sentence goes AFTER the
sentence that joins the two retained gate literals — never between them, and
never in a position that would make an earlier occurrence of
`` "no task has status `merged`" `` the first one. The normalized text between
the two retained literals must still contain no sentence break.

### Site 2 — I.2.c write set: reset target defined by the reconciled state (FR2)

Present state: the ordered write set resets "**every** failed task's
`tasks.{T}.status` back to `pending`", i.e. keyed off workflow.yaml's status.

Required after the edit:

- The reset target set is every task whose Step I.2.b step 1 reconciled state
  is `failed`. The workflow.yaml-`status: failed`-only basis is gone.
- The four write instructions and their order are unchanged: `create-plan` to
  `needs_update`; the `implement` step back to `pending`; each such task's
  failure reason into `tasks.{T}.notes`; `tasks.{T}.status` back to `pending`.
- The `replace_planning` / `replace_all` citation of
  `references/workflow-patch.md` stays a citation (D5).

Placement hazard (IMPLEMENTATION.md D3 constraints 1 and 2): the phrase
`` `tasks.{T}.status` back to `pending` `` must stay contiguous, and the FIRST
occurrence of `tasks.{T}.status` in the normalized section must still have
`pending` within the following 60 characters. Wording that puts the
reconciled-state qualifier BEFORE the token (or after `pending`) satisfies
both; wording that inserts the qualifier between `tasks.{T}.status` and
`pending` breaks the 60-character window. Do not introduce any earlier mention
of `tasks.{T}.status` anywhere in the section.

### Site 3 — I.2.c cleanup: only tasks confirmed not merged (FR3)

Present state: after the commit, cleanup runs `git worktree remove --force`
and `git branch -D` "for every {T} just reset".

Required after the edit:

- The cleanup targets are exactly the tasks the write set just reset, and the
  text states in so many words that those are tasks confirmed NOT merged — a
  task whose reconciled state is `merged` is never a cleanup target, whatever
  workflow.yaml says (SPEC.md AC-2, AC-3, EC-1).
- `git branch -D` occurs only inside that scoped sentence; the I.2.c section
  contains no other occurrence of it.
- The commit-before-cleanup order and the leftover-state sentence ("this
  order's one residual leftover state is the commit succeeding and the cleanup
  not yet running…", with its pointer to Step I.2.a's resume guard and
  recycled-task-id rule) are preserved.

### Site 4 — I.2.c rejected path: the new blocker is enumerated (FR4)

Present state: "When the gate does not hold — because a task has status
`merged`, because a task has status `in_progress`, or because Step I.2.b's
last-event-per-task rule reports a task in-flight — …".

Required after the edit:

- The enumeration additionally names Site 1's source: a task the reconciled
  state reports `merged` even though workflow.yaml does not. EC-2's scenario
  (journal `merged` + workflow.yaml `in_progress`) must find a reason in this
  enumeration that is true of it.
- The terminal is unchanged: `create-plan` is NOT set to `needs_update`;
  refresh, `TERMINAL_TIP`, `implement` set to `failed` as the single write,
  committed as exactly that write; control back via develop's stop condition
  3, the same terminal as "abort phase". No retry loop, no alternative
  recovery, no degraded route back.
- Containment (IMPLEMENTATION.md D3 constraint 7) survives: the normalized
  text after "When the gate does not hold" contains none of "make one ordered
  workflow.yaml write set", "git worktree remove --force", "ROUTEBACK_TIP",
  and the strings "rework" and "append" occur nowhere in the I.2.c section.

### Site 5 — I.2.a: route-back's own recursion invariant (FR6)

Required addition to the recycled-task-id paragraph, placed AFTER the existing
unreachability sentence's terminal "can never arise." (IMPLEMENTATION.md D4 —
placing it there leaves both the protected Step I.2.a wrap literal and the
existing sentence's slice anchors untouched):

- A statement of why Site 1 cannot deadlock a later route-back through a
  recycled id: route-back proceeds only when no task is `merged` under EITHER
  source, so no retired id can leave a `merged` last event behind for a
  renumbered task to inherit; therefore the recycled-task-id carve-out stays
  correctly scoped to `failed` only (SPEC.md EC-5).
- The existing sentence "This carve-out is deliberately scoped to `failed`
  only…" and the retained in-flight sentence ("A task whose journal last event
  is `launched` is always in-flight, regardless of workflow.yaml `status`…")
  survive unchanged.

### Site 6 — Cross-references that describe the gate stay true (FR5)

- **Branch & Worktree Model, exit-4 recovery bullet**: the sentence beginning
  "The widened I.2.c gate's union rule — blocked when workflow.yaml reports a
  task `in_progress` OR …" must, after Site 1, identify WHICH union rule it
  invokes, because the gate now has two. The exit-4 unreachability proof rests
  on the `in_progress` union alone (no implementer can be running), so the
  sentence names that union specifically. Everything else in the bullet is
  unchanged — in particular the enumeration of ref-advancing paths, the
  single carve-out naming Step I.2.c's route-back commit, the residual
  assumption and its covering terminal.
- **Step I.2.a unreachability sentence**: "Given I.2.c's route-back
  precondition below, which admits only tasks with a terminal journal last
  event, …" stays present and stays true; the sentence added at Site 5
  strengthens it rather than replacing it. Do not restructure the sentence or
  its "can never arise." terminal — an existing protected module slices on
  both anchors.

## Test Notes

- Every criterion is a unit-level document-contract assertion; the change is
  documentation-only, so there is no runtime behaviour to integration-test.
- TDD order that actually produces a red: write TS-1 .. TS-6 first — they fail
  against the current document because the new wording is absent — then edit
  the document site by site. TS-7 is a regression guard that is GREEN before
  the edit; its value is that it turns red the moment an edit reflows a
  protected literal, moves the batch-mode tail or reorders the I.2.c section,
  so run the FULL suite after every individual document edit, not only at the
  end. Record the observed red per criterion in the tests.yaml record.
- Capture every pre-change sample (D8 point 2) BEFORE editing the document —
  after the edit the verbatim text is no longer available in the worktree.
- Assert prose against a whitespace-normalized copy; assert byte identity and
  line-wrap survival against the raw text. Mixing the two is the known source
  of both false passes and false failures in this suite.
- SPEC.md's EC-1 .. EC-6 are the reading test for the new wording: each edge
  case must be decidable from the edited paragraph alone. EC-1 (journal
  `merged` + workflow.yaml `failed`) is the live bug and must come out blocked
  by Site 1 and excluded from cleanup by Site 3.
