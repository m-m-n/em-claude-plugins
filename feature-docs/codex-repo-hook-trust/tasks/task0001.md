# Task Plan: task0001 — Probe working-directory Codex hooks on every wrapper route and close the gap

## Goal

Establish on Codex 0.160.0 whether repository hooks execute under each launch
route of the em-workflow and em-review Codex wrappers, record the evidence,
and leave the feature in one closed state: every executing route now launches
Codex so that repository hooks do not run (pinned by tests), or
codex-interactive-guard-hook TB-3 records that no route executes them.

## Design

Vocabulary (route, working directory, repository hook, executing route,
Branch E / Branch N, protective specification, findings record) and the
cross-cutting conventions (Codex home isolation, credentials, wrapper parity,
evidence over absence, bounded launches) are defined in IMPLEMENTATION.md.

### 1. Probe conditions (FR1)

| ID | Wrapper | Route | Working directory trusted in the user config |
|----|---------|-------|----------------------------------------------|
| P1 | em-workflow | default | not applicable (user config ignored) |
| P2 | em-workflow | --litellm MODEL | trusted |
| P3 | em-workflow | --litellm MODEL | not trusted |
| P4 | em-review | default | not applicable (user config ignored) |

- Each probe launches Codex through the wrapper itself, so the argv is the
  wrapper's own (hook-trust bypass, --ignore-rules, the wrapper's own
  PreToolUse registration, plus the route's options). Any difference a probe
  needs from the wrapper's argv is listed in the record.
- Each condition is probed in both wrapper modes (readonly, readwrite). The
  observation that a hook ran must not depend on the sandbox permitting the
  hook's own effect; where it could, the readwrite result decides and the
  record says so.
- The user config needed for P2 and P3 (the trust entry, the litellm profile)
  and any credential live only in the temporary CODEX_HOME. Credentials enter
  only through environment variables or a login step that writes into the
  temporary CODEX_HOME — never by copying from the user's real Codex home.

### 2. Hook definitions under test (A2)

- Locations: every location Codex 0.160.0 reads hook definitions from that a
  repository under review controls — at least the hook tables of the
  working directory's Codex configuration file, plus any separate
  hook-definition file that version reads. The record states how the list
  was established (documentation, help output or observation for 0.160.0).
- Events: every hook event Codex 0.160.0 supports, not only PreToolUse.
- Each location × event gets its own hook whose only effect is a distinct
  marker, so each observation is attributable.
- Same-key override: the record states whether the wrapper's own PreToolUse
  registration replaces, merges with, or is replaced by a repository
  PreToolUse definition.
- Positive control: a "not executed" verdict for a location × event stands
  only if the same definition demonstrably runs in a control launch in the
  same environment where Codex is known to load it (for example the same
  definition in the temporary user config on a launch that reads user
  config, or the working directory trusted on a launch that honours trust).
  A location × event whose control never fires is "unobservable" with the
  reason.

### 3. Classification and branch

- A probe condition is executing when any repository hook ran in it; a route
  is executing when any of its conditions is (IMPLEMENTATION.md D2).
- Branch E: sections 4, 5 and 6 apply. Branch N: the launch composition of
  both wrappers stays as it is, section 6 applies, and no new test module is
  created.
- Stop and report a plan deviation instead of choosing a branch when the
  installed codex does not report 0.160.0, or when a route has no observable
  location × event at all.

### 4. Protective specification (Branch E; FR3, A1)

- Contract: on each executing route, each wrapper that has the route hands
  codex a protective specification. The means (a Codex option, a
  configuration override, a launch-dedicated configuration home, or another
  means) is chosen from the FR1 evidence and recorded in the findings record
  with its rationale.
- Observability: the specification is visible in the argv or the
  environment the wrapper hands to codex, so a stub can detect it.
- Preserved on every route: the wrapper's own interactive-guard PreToolUse
  registration, --ignore-rules, --ignore-user-config on the default route,
  -p litellm -m MODEL on the --litellm route, and the NFR3 wrapper contract.
- Parity: when the default route is executing, both wrappers receive the
  same means in this change.
- Post-change probe: the changed launch is probed again with the same hook
  definitions; the record shows that no repository hook ran and whether the
  wrapper's own guard still fires. Where both cannot hold, the route keeps
  the specification (A1) and TB-3 records that the guard does not fire on
  that route.
- Routes that are not executing keep their current launch composition.

### 5. Tests (Branch E; FR5)

New test module, Python standard library only (NFR2), following the
stub-codex approach of the existing wrapper test modules in tests/.

TS1 (always runs):
- For every changed route × {readonly, readwrite}: a stub codex first on
  PATH captures argv and environment; HOME and CODEX_HOME are temporary
  directories.
- Checks: the protective specification is present; the wrapper's own guard
  registration is present; the environment the stub saw points HOME and
  CODEX_HOME at the temporary directories.
- Non-vacuity: the same check applied to a fabricated argv/environment that
  differs only by lacking the specification reports failure.
- Credentials: the credential variable carries a sentinel value; the
  sentinel is absent from the wrapper's captured stdout and stderr. Failure
  diagnostics name variables, never their values.

TS2 (real Codex, may skip):
- Skips when codex is not on PATH or does not report 0.160.0.
- A temporary repository whose working-directory configuration carries a
  marker-writing repository hook, using a location × event FR1 observed
  executing on that route.
- For every changed route × mode: a control launch with the pre-change
  composition (no specification) must create the marker — when it does not
  (no credentials, unreachable backend, event not fired) the case skips with
  that reason and never passes; the launch through the wrapper must leave no
  marker.
- Same Codex home isolation and launch time bounds as the probes.

TS3: the four existing wrapper test modules keep passing; their expected
fixed values change only where section 4 changed the launch.

### 6. Records (both branches; FR2, FR4, FR6)

Findings record (English): environment (Codex version as reported, the
temporary home layout, how credentials were provisioned — by name only);
the location and event list and its source; the hook definitions; the probe
command per condition (credentials as variable names); the result matrix
condition × mode × location × event → executed / not executed /
unobservable (with reason) and the positive control behind each "not
executed"; the same-key override observation; the per-route verdict and the
branch taken; in Branch E, the means chosen, its rationale and the
post-change probe.

codex-interactive-guard-hook TB-3 (that feature's SPEC.md stays unchanged,
A5):
- Both branches: cites the findings record, the Codex version and the
  per-route verdicts; the Rationale's item on configuration layers the
  wrapper does not author is no longer stated as unresolved
  (IMPLEMENTATION.md D3).
- Branch N: states that no route executes repository hooks (FR4) and lists
  any unobservable events.
- Branch E: names the changed routes and the means, and any route on which
  the wrapper's guard no longer fires (A1).

Wrapper comments (FR6): the Interactive-guard hook section comment of each
wrapper (em-workflow around lines 151–156, em-review around lines 124–129)
states the FR1 result for that wrapper's routes and describes the launch as
it is after this task.

## Test Notes

- AC-5 and AC-6 are automated in the new module. Write TS1 first and see it
  fail against the current wrapper before changing the launch.
- AC-4 is pinned by the existing wrapper test modules together with TS1.
- AC-1, AC-2, AC-7 and the comment part of AC-8 are document checks by
  inspection; no test parses the Markdown records. The post-change probe
  part of AC-3 is likewise checked in the findings record.
- FR1 is exploratory: run the probes, write the findings record, then decide
  the branch (section 3), then write the Branch E tests before the launch
  change.
- In Branch N, AC-5 and AC-6 do not apply; the findings record says so, and
  no new test module is created.
- Every real Codex launch, in the probes and in TS2, is bounded in
  wall-clock time.
