# Task Plan: task0002 — Read a here-document after a subscript closed on a later line, and line continuations inside a name, as bash 5.3 does

## Goal

A `<<` after an assignment-word subscript whose `]` comes on a later line is
read as a real here-document operator, so no quote or `${` of its body takes
the close line and the following lines into a region (finding
5753be9288beab27). A `NAME[` whose name holds line continuations opens a
subscript, so the `<<` inside it is no operator and no whole-word delimiter
swallows the following lines (finding e25427e2a8b1dddf).

## Requirements

FR1, FR4, FR9, FR10, FR11, NFR1, NFR4, NFR5, NFR6, NFR7

### FR1: here-document after a subscript closed on a later line (SPEC A5)

- First add the six cases and run them. If all six are already deny and the
  lexical expectations of AC-2 already hold, no hook code changes for FR1.
- Otherwise the reading to reach: the array-subscript region opened at `[`
  runs across the newline to its matching `]`; the word ends as an
  assignment word; the next `<<` on the line or on a later line is a
  here-document operator whose body starts at the line after the operator's
  line; the pending-operator bookkeeping is not disturbed by the newline
  inside the subscript (it is not a line start for here-document bodies,
  as a newline inside any other region is not).
- No tail start is set by these forms: the subscript is closed, so nothing
  is settled.

### FR4: line continuations inside the name (SPEC FR4, F4)

- The `NAME[` test runs on the word's leading characters with every
  backslash-newline pair removed, at exactly the positions where it runs
  today (assignment positions and declaration-builtin arguments). The
  subscript opens at the original offset of the `[`, and the word's
  original start offset is the one compared with the tail start.
- A continuation inside the subscript, right before its `]`, or between the
  `]` and the `=` keeps today's reading (the subscript is already read
  across a continuation); these forms are pinned, and code changes only if
  one of them is not deny.
- A subscript whose `]` never comes still raises the unmatched-subscript
  condition, so the hook asks (deny under `CLAUDE_BATCH`), as today.
- The removal must not make the detection rescan the word: a word with many
  continuation pairs is read in work proportional to its length (NFR1).

### Cases (FR9)

Commands in the case table's JSON string notation (`\n` is a newline, `\\`
a backslash). Labels begin with the stable_id, then `round2-deferred`, then
the tag.

FR1, stable_id 5753be9288beab27, tags `FR1.1` to `FR1.6`, all deny:

1. `a[1\n]=x\ncat <<E\n'\nE\nrm -rf /home/sakura/valuable\n'`
2. `a[1\n]=x\ncat <<E\n\"\nE\nrm -rf /home/sakura/valuable\n\"`
3. `a[1\n]=x\ncat <<E\n${\nE\nrm -rf /home/sakura/valuable\n}`
4. `a[1\n]=x; cat <<E\n'\nE\nrm -rf /home/sakura/valuable\n'`
5. `a[$(echo 1\n)]=x\ncat <<E\n'\nE\nrm -rf /home/sakura/valuable\n'`
6. `a[b[1\n]]=x\ncat <<E\n'\nE\nrm -rf /home/sakura/valuable\n'`

FR4, stable_id e25427e2a8b1dddf, tags `FR4.1` to `FR4.6`:

1. deny: `a\\\n[1<<2]=x\nrm -rf /home/sakura/valuable\n2]=x`
2. deny: `ab\\\nc[1<<2]=x\nrm -rf /home/sakura/valuable\n2]=x`
3. deny: `a[1\\\n<<2]=x\nrm -rf /home/sakura/valuable\n2]=x`
4. deny: `a[1<<2\\\n]=x\nrm -rf /home/sakura/valuable\n2]=x`
5. deny: `a[1<<2]\\\n=x\nrm -rf /home/sakura/valuable\n2]=x`
6. ask: `a\\\n[1<<2\nrm -rf /home/sakura/valuable`

The labels of FR4.3 to FR4.5 say, in Japanese, that a form the subscript
detection misses combines with the whole-word delimiter `2]=x` and turns
into allow. FR4.6 keeps an existing conservative verdict (unmatched
subscript), so it needs no bash confirmation.
