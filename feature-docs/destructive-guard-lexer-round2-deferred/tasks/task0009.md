# Task Plan: task0009 — Bring the hook evaluation of deeply nested unclosed `${ ` inputs back under the 10-second bound

## Goal

One hook evaluation of a ~60 KB input made of nested unclosed command forms
(`${ ` repeated, alone or mixed with other unclosed openers) and a following
destructive line finishes within the 10-second hook timeout with a decision
other than allow, and the cost of that evaluation grows in proportion to the
input length instead of faster (verify failed items under Provenance).

## Requirements

FR7, FR10, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6, NFR7

## Provenance

- source: verify
- source_ids: TS-13, TS-14, TS-10

The verify run of the integrated tree measured these three tests of
`tests/test_destructive_guard_lexer_agreement.py` past their 10-second hook
bound, each with the correct non-allow decision:

- `TestUnclosedOpeners.test_bulk_unclosed_openers_get_a_non_allow_decision_in_time`
  (opener `${`: `"${ "` repeated 20000 times, then `\nrm -rf /home/sakura/valuable\n`): 10.8 s
- `TestUnclosedOpeners.test_mixed_bulk_openers_get_a_non_allow_decision_in_time`
  (the unit `"${ $(( $[ (( $' "` repeated to ~60 KB, then the destructive line): 10.6 s
- `TestBraceCommandSubstitution.test_nested_unclosed_forms_followed_by_a_destructive_line_are_never_allow`
  (`"${ "` repeated 20000 times, then `\n`, the destructive line and `\n`): 11.1 s

The hook at the end of the first implement pass (commit ebb8b700) took the
same time, so the cost came in with the command form of `${` (task0005), not
with review rework. Every other test passes and the case-table runner passes
all 846 cases. The three failures are one root cause: the cost of handling
20000 nested unclosed command forms.

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/hooks/destructive-guard.py` — the step (or steps) whose cost grows faster than the input length on nested unclosed command forms, located by measurement (see Design).
- `tests/test_destructive_guard_lexer_agreement.py` — a new class for the doubled-length inputs (Design → Tests); the three failing tests are not edited.

## Design

Cross-task rules that apply here (IMPLEMENTATION.md): the `lex_shell()` row
(work bound, budget-exceeded answer, determinism, no file read, nothing
evaluated), the substitution regions downstream row (its observable contract
is kept, below), the lexer internals row (existing call shapes keep their
meaning), the fail-safe direction, the existing-cases convention, the
existing-agreement-test-expectations convention, test runs and file scope.

### Locate first

- Before changing the hook, measure where one evaluation of the three inputs
  above spends its time (lexing, the structure scan, extracting and queueing
  the inner text of each unclosed command form, inspecting the queued chunks,
  statement shaping, the scan-budget check). The task report names the
  dominating step and how its cost grew with the nesting depth before the
  change.
- The lexer's counted work for `${ ` repeated 20000 times is already linear
  (TS-9); a counted-work bound that holds does not show that wall time is
  linear.

### Contract to reach

- The cost of one hook evaluation over nested unclosed command forms grows in
  proportion to the input length: doubling the nesting depth at most roughly
  doubles the time, so the ~60 KB inputs finish well inside 10 seconds rather
  than just under it.
- The content of every unclosed command form is still inspected as commands
  (SPEC F7, the substitution regions downstream row): a destructive command
  inside any one of the nested forms, or on the line after them, is never
  allowed. Content that two nested forms share may be inspected once rather
  than once per level, as long as no form's content goes uninspected.
- When the work or scan bound is exceeded, the answer stays the scan-budget
  ask (deny under `CLAUDE_BATCH`), never allow (NFR3); the bound is checked
  before the work it limits is done, so reaching it costs time in proportion
  to the bound, not to everything queued past it.
- A budget value is changed only if every existing case-table entry and every
  existing test keeps its verdict; the change aims at the superlinear step,
  not at a lower threshold.
- Lexical maps, region lists, UNOPENED and tail starts are unchanged for
  every input; the change is in cost only.

### Tests

- The three failing tests are the TDD red tests: they fail before the change
  and pass after it, with their inputs, their 10-second bound and their
  assertions unchanged.
- A new class, directly after the classes task0005 added after
  `TestUnclosedOpeners` (the command-form class and its stage-agreement
  subclass), runs the doubled-length inputs of AC-3 through the hook the way
  the three failing tests do.

### Not touched

The hook timeout in `hooks.json`, the case table, every reading of the
lexer (task0001 to task0008), and the three failing tests themselves.

## Acceptance Criteria (MANDATORY)

Commands use the case table's JSON string notation. RM is
`rm -rf /home/sakura/valuable`. "Both modes" means without `CLAUDE_BATCH`
and with `CLAUDE_BATCH=1`. "One hook evaluation" means one run of the hook
through its stdin / stdout contract, as the three failing tests run it.

- [ ] AC-1 (NFR2, NFR3): `TestUnclosedOpeners.test_bulk_unclosed_openers_get_a_non_allow_decision_in_time`, `TestUnclosedOpeners.test_mixed_bulk_openers_get_a_non_allow_decision_in_time` and `TestBraceCommandSubstitution.test_nested_unclosed_forms_followed_by_a_destructive_line_are_never_allow` pass, each in two consecutive runs of `python3 -m unittest discover -s tests`, with no change to their inputs, their 10-second bound or their assertions.
- [ ] AC-2 (NFR3, FR7): `"${ "` repeated 20000 times followed by `\nRM\n` gets ask or deny without `CLAUDE_BATCH` and deny with it; the bulk `${` input and the mixed bulk input each get a decision other than allow in both modes.
- [ ] AC-3 (NFR2, NFR1): `"${ "` repeated 40000 times followed by `\nRM\n` (~120 KB) gets, in one hook evaluation, ask or deny without `CLAUDE_BATCH` and deny with it, and the unit `"${ $(( $[ (( $' "` repeated to ~120 KB followed by `\nRM\n` gets a decision other than allow in both modes; each evaluation finishes within 20 seconds.
- [ ] AC-4 (FR7, NFR6): `echo ${ RM`, `echo ${ echo x ${ RM`, and `"${ "` repeated 3 times followed by `RM` (the destructive command inside the innermost unclosed form) each deny in both modes, so every nested unclosed form's content is still inspected.
- [ ] AC-5 (NFR1, NFR4): The linearity tests of TS-9 pass unchanged (`${ ` repeated 20000 times included); each input of AC-2 and AC-3 gets the same decision on two consecutive evaluations, the second after clearing the lexer cache.
- [ ] AC-6 (FR10, NFR5, NFR7): No case-table entry is added, removed, edited or reordered and every case keeps its verdict; no existing test is removed, skipped or has its bound loosened; `python3 em-workflow/hooks/tests/run-destructive-guard.py`, `python3 -m unittest tests.test_destructive_guard_lexer_agreement` and `python3 -m unittest discover -s tests` all pass, including `TestModuleContract` and `TestStageAgreement`.
