# Task Plan: task0002 — Bucket descriptions and Codex fact fields in tier-rules.yaml

## Goal

The rule table's `question_set` defines the four bucket descriptions that both
Jev calls receive, with a rule addition plus a test addition placed in bucket
1, and `codex_output_schema` gains seven fact fields with value vocabularies
while keeping every existing field.

## Requirements

FR6, FR7, NFR3

## Scope

### Files to Create
- `tests/test_tier_rules_buckets_codex_facts.py` — conformance tests for the question_set and codex_output_schema sections

### Files to Modify
- `em-workflow/references/tier-rules.yaml` — only the question_set and codex_output_schema sections, per IMPLEMENTATION.md SC-5

## Design

Section ownership and the bucket keys are pinned in IMPLEMENTATION.md (SC-5,
SC-2) and are not restated.

### `question_set` bucket descriptions

Meaning each description must convey. Wording is written fresh, in the
file's own language and voice:

| Bucket | Meaning |
|--------|---------|
| 0 | Only wording or rule-text changes; no new logic and no test change |
| 1 | A rule addition combined with a test addition, or a small change in a few files together with a small test change |
| 2 | New logic, a change spanning several modules, or a change to an external contract |
| 3 | A broad cross-cutting change, new files / modules / dependencies, or an architecture change |

- Keys are `"0"` to `"3"`, the same keys the evaluator validates.
- The section comment that currently assigns the question wording to external
  skills is rewritten: the bucket descriptions are defined here and are
  passed to both Jev calls (the description-only call and the final call).
- No sentence is copied from the jev or typesafe-ai skill documents.

### `codex_output_schema` additions

Every existing field stays as it is, including whether it is required. The new
fields follow the same required/optional convention and the same notation the
section already uses.

| Field | Fact reported | Values |
|-------|---------------|--------|
| `test_change_kind` | Whether the test change only adds cases one-to-one to existing checks, or writes tests for new behavior | `none` / `extend_existing_one_to_one` / `new_behavior_tests` |
| `added_test_cases_approx` | Approximate number of added test cases | non-negative integer |
| `body_change_kind` | Whether the body change is wording or a rule addition, or new logic | `wording_or_rule_addition` / `new_logic` |
| `change_containment` | How far the change is contained | `single_function` / `single_module` / `multiple_modules` |
| `caller_and_dependency_count` | Number of callers of, and dependencies of, the changed places | non-negative integer |
| `changes_external_contract` | Whether an external contract (arguments, return values, file formats, configuration keys and similar) changes | boolean |
| `changes_behavior` | Whether observable behavior changes | boolean |

- Each field's description states the fact it reports. The section states
  that Codex reports facts only and makes no size or tier judgment.
