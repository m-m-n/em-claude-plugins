# Task Plan: task0003 — unresolved-substitution evidence survives the payload re-scan and is reported truthfully

## Provenance

- source: review
- review_round: 1
- source_ids: bd7710d1b20046e5, 63705cbaaa5891ed, 91320984c3e74bc0

All three findings sit on one root cause: the evidence that a delete target
came from a command substitution is either destroyed before the shell-payload
re-scan can use it (first finding), or carried into a verdict whose reason
text then describes something that is not true of the input (second finding),
while the test that was supposed to pin the payload path asserts a shape that
never exercised it (third finding). They share the file set, the marker/flag
contract between the lexing boundary and the recursive-delete check, and the
same Acceptance Criteria, so they are one task.

## Requirements

FR1, FR2, FR3, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6, NFR7

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/hooks/destructive-guard.py` — the ORDER in which the statement
  extraction stage removes marker residue relative to extracting a shell
  payload for re-scanning, and the reason text the recursive-delete check
  produces for a target that carries unresolved-substitution evidence.
- `em-workflow/hooks/tests/destructive-guard-cases.json` — new entries for the
  payload-carried substitution-only delete target and for the safe-root
  boundary forms whose verdict this feature already moved but never pinned.
- `tests/test_destructive_guard_command_substitution.py` — replace the
  payload-path assertion that used a literal path with one that uses a
  substitution, and add the reason-text assertions for the safe-root boundary
  form.

## Design

Read together with IMPLEMENTATION.md: D4 states the feature-level behavioural
contract, and the Conventions section states the reason-text, sentinel,
filesystem and case-table rules that apply throughout. This task adds no rule
id, no tier and no new vocabulary to either.

### Part 1 — evidence must reach the shell-payload re-scan

The statement extraction stage does two things to a token stream that must not
be ordered as they are today: it converts marker residue into a per-token
"evidence lost" flag (which erases the residue from the token TEXT), and it
extracts the payload of a shell-invoking statement (`-c` form, `eval` form,
here-string form) as a fresh command string to re-scan as its own statement.

Because the flag conversion runs first, a payload token that mixes real text
with a substitution loses the substitution's textual trace before the payload
string is taken. The re-scanned statement then contains a delete with no
target at all, and the recursive-delete check returns early with zero targets
— the exact zero-target early return this feature exists to close, reachable
again by prefixing one shell invocation.

Required contract after the change:

- The string handed to the payload re-scan still carries the substitution
  trace, so the re-scan's own conversion pass produces the same per-token flag
  (and the same whole-word stand-in from task0001) it would produce for the
  identical command written directly. Both spellings behave alike.
- The verdict, rule id and rendered target for a delete carried inside a
  payload equal those for the same delete written directly — for the
  substitution-only target, for a variable-expansion target, and for a literal
  path target alike.
- Idempotence at the boundary: a trace already converted once is not converted
  a second time by the re-scan, and the stand-in text never accumulates or
  nests.
- The existing bound on how many times a shell payload may be expanded is left
  exactly as it is (NFR3); this change alters the ORDER of two steps, not the
  number of expansions.
- The token stream of a statement that invokes no shell payload is unchanged,
  byte for byte.

### Part 2 — the deny-side reason text must be true of its input

A target whose word mixes real text with a substitution carries the "evidence
lost" flag, and that flag suppresses the safe-root exception. When the real
text of such a word does lie under a safe root, the verdict is therefore the
outside-safe-root deny, and its reason text asserts that the target lies
outside the scratch area and instructs the reader to move it aside — an
assertion that is false for that input and an instruction that does nothing
for it.

Required contract:

- **Tiers do not move.** Every verdict FR5 pins stays exactly as it is,
  including the denies for a substitution adjacent to real text. The
  suppression of the safe-root exception for a flagged target is retained: a
  substitution can still expand to a parent-directory escape, so the
  strengthening itself is correct and is not what this task changes.
- **The text changes.** For a target carrying the flag, the reason states the
  fact that holds — part of this delete target comes from a command
  substitution, so its effective range cannot be confirmed statically — and
  never asserts anything about the target's position relative to a safe root,
  because the deciding property was the unresolved part, not the position.
- The instruction that closes the sentence must be actionable for THIS input:
  it tells the reader to re-issue the delete with the substitution already
  expanded into a literal path. The existing Japanese sentence style, the rule
  id prefix and the demotion behaviour are unchanged (NFR5, NFR4).
- The rendered target is non-empty, is not whitespace only, carries no NUL and
  no other control character, and the sentinel never reaches standard output
  (NFR6).
- A target with no unresolved evidence keeps today's reason text verbatim —
  the wording change is confined to the flagged branch.

### Part 3 — the case table pins what moved

The case table is the record of what this feature changed. Two classes of
entry are missing from it:

- The payload-carried forms of Part 1: the substitution-only delete target
  inside a `-c` payload (both the `$( )` and the backtick spelling), inside an
  `eval` payload, and inside a here-string payload, each at the verdict Part 1
  makes them reach.
- The safe-root boundary forms of Part 2: a delete whose target is a path
  under a scratch root followed by a substitution at a quote boundary, and the
  variant that appends a further segment after the substitution. These already
  moved from `allow` to `deny` when task0001 landed and are pinned here at
  their CURRENT verdict, so the next edit to the boundary handling cannot move
  them silently.

No existing entry is removed, and no existing entry's expectation is changed
by this task — the table only grows.

### Part 4 — the payload test asserts the payload property

The repository-level regression module currently backs the payload scenario
with a case that puts a literal path inside the payload. That case passes
against the pre-feature guard as well, so it is evidence of nothing. It is
retained as a regression assertion, but the scenario's evidence becomes a case
whose payload carries a substitution, asserted to reach the same tier, rule id
and rendered target as the identical delete written directly.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR2): a recursive delete whose target consists solely of a
      command substitution reaches the same tier AND the same rule id as the
      identical delete written directly, when carried inside each of: a `-c`
      payload of a shell invocation, an `eval` payload, and a here-string
      payload; in both the `$( )` and the backtick spelling. None of these is
      `allow` in either attended or unattended mode, and each becomes `deny`
      when the unattended environment variable is set.
- [ ] AC-2 (FR5, FR6, NFR7): the ordering change moves nothing else — a
      payload carrying a variable-expansion target keeps its current verdict, a
      payload carrying a literal dangerous path keeps its `deny`, and the whole
      `allow` half of the case table (a delete string inside quotes, a here-doc
      body, a commit message, a `python3 -c` payload, a redirect-only
      statement, a delete under a safe root) is still `allow`. Every command
      string present in the case table before this task is still present, and
      no pre-existing entry's expected verdict changes.
- [ ] AC-3 (FR3, NFR5, NFR6): for a recursive delete whose target mixes a
      path under a scratch root with a command substitution at a quote
      boundary, the verdict is unchanged from the current tree, and its reason
      text (a) does not assert that the target lies outside the scratch area,
      (b) states that part of the target comes from a command substitution and
      therefore cannot be resolved statically, (c) ends with an instruction the
      reader can act on for this input, in the existing Japanese style, and
      (d) contains no NUL and no other control character anywhere in the
      emitted output.
- [ ] AC-4 (FR3, FR5): a recursive-delete target carrying NO unresolved
      evidence produces byte-identical reason text to the current tree — the
      wording change reaches only the flagged branch.
- [ ] AC-5 (FR7, NFR7): the case table contains entries for the
      payload-carried substitution-only target in the `-c`, `eval` and
      here-string forms and in both spellings, and for both safe-root boundary
      forms at their current verdict; `python3 em-workflow/hooks/tests/run-destructive-guard.py`
      reports every case passing, including the trailing unattended-demotion
      case.
- [ ] AC-6 (FR1, FR6): the repository-level regression module's evidence for
      the payload scenario is a case whose payload CARRIES a substitution, and
      that assertion fails against the tree as it stands before this task and
      passes after it; the literal-path payload case is retained as a separate
      regression assertion.
- [ ] AC-7 (NFR1, NFR2, NFR3, NFR4): `python3 -m unittest discover -s tests`
      passes; the same command string re-run yields the identical verdict and
      reason text; the guard's source gains no filesystem-resolution, stat or
      subprocess call; the cap on shell-payload re-expansion is unchanged and
      the kilobyte-scale case in the table still completes; a malformed payload
      still fails open with exit 0 and the unattended demotion is untouched.

## Test Notes

- **Red first, and prove it.** Every assertion this task adds must be run
  against the tree as it stands BEFORE the source change: AC-1, AC-3 and AC-6
  are expected to fail there. An assertion that is already green before the
  change is not evidence — treat it as a signal that the finding it came from
  does not reproduce as described, and report that rather than keeping the
  green assertion as proof.
- **Split by suite.** The case table (integration, TS-1) owns everything
  expressible as one command string plus one expected verdict: the payload
  forms, the safe-root boundary forms, and the whole retained `allow` half.
  The unit module (TS-2, TS-11) owns what the table cannot express: reason-text
  content and its negative assertions (no claim about position relative to a
  safe root), rule-id identity between the payload form and the direct form,
  rendered-target identity across spellings, absence of control characters in
  the complete standard-output text, determinism across repeated runs, and the
  unattended demotion for the new shapes.
- **Equality, not literals.** State the payload assertions as "same tier, same
  rule id, same rendered target as the direct form", computed by running both
  through the guard in the same test, rather than as a hard-coded expected
  string. The direct form's own verdict is already pinned by task0001's
  assertions, so the comparison cannot drift into asserting the wrong thing.
- **The tier-preservation half is the expensive half.** The second finding's
  own suggested fix (route every flagged target to the ask branch) would flip
  the denies FR5 pins for a substitution adjacent to real text; this task
  deliberately changes only the text, so the assertions that those denies still
  hold are load-bearing, not incidental.
- **TDD-awkward**: "the reason text does not claim the target is outside the
  scratch area" is a negative assertion over prose. Pin it as the absence of
  the specific claim the current text makes, together with the presence of the
  unresolved-substitution statement, rather than as a full-string match that
  any future rewording would trip.

## Out of Scope

- Moving any verdict tier. No `deny` becomes `ask`, no `ask` becomes `deny`,
  no `allow` becomes non-`allow` except through the payload path of Part 1.
- Introducing a new rule id, a new tier, or changing the unattended demotion.
- Removing or relabelling any existing case-table entry.
- The plugin version fields (`em-workflow/.claude-plugin/plugin.json` and the
  repository-root `.claude-plugin/marketplace.json`). IMPLEMENTATION.md makes
  task0002 their only writer, and the value it set ships the whole merged
  feature including this task; no second bump belongs here.
- The safe-root / build-artifact vocabulary, the root/home shape, and the
  symlink gap in target resolution — all unchanged.
- Any other hook and any change to hook registration.
