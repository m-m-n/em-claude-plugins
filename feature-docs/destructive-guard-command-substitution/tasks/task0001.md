# Task Plan: task0001 — substitution-only delete target reaches the decision

## Goal

A recursive delete whose target word is built entirely from a command
substitution is judged instead of waved through: it reaches the
recursive-delete check as a target, lands on the existing `rm-unresolvable`
branch, and is named legibly in the reason text — with the guard's existing
`deny` / `ask` / `allow` verdicts otherwise intact.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6, NFR7

## Scope

### Files to Create
- `tests/test_destructive_guard_command_substitution.py` — repository-level
  regression module for this behaviour change, driving the guard through its
  external contract (subprocess, PreToolUse JSON on standard input).

### Files to Modify
- `em-workflow/hooks/destructive-guard.py` — the lexing-boundary handling of a
  whole-word command substitution, the recursive-delete check's treatment of
  the resulting target, and the target rendering in the `rm-unresolvable`
  reason text.
- `em-workflow/hooks/tests/destructive-guard-cases.json` — expectations for
  the two entries pinned as known holes, the entry for the quoted whole-word
  form, and new entries for both substitution spellings and the edge cases
  below.

## Design

Read together with IMPLEMENTATION.md — D4 there states the feature-level
behavioural contract this task implements; the conventions section there
states the reason-text, sentinel, filesystem and case-table rules that apply
throughout.

### Part 1 — evidence survives the lexing boundary

Today the marking stage classifies each command-substitution match by its
neighbours: a match bounded on both sides by a word boundary is blanked to a
single space (the word vanishes at tokenization, which is the hole), while a
match adjacent to real text is replaced by the internal marker whose residue
the next stage converts into a per-token "evidence lost" flag.

Change the first case so evidence survives it too, while keeping the two cases
distinguishable downstream. The contract after both stages have run:

- **Whole-word case** — a word whose entire text was one or more command
  substitutions and nothing else yields exactly ONE token, in the same
  argument position the original word occupied, carrying a flag that says its
  value was never present at all. Both spellings (the parenthesised form and
  the backtick form) produce an identical token; a substitution sitting inside
  an otherwise-empty pair of quotes is the same case, because quoting is
  resolved before tokens are seen.
- **Adjacent-text case** — unchanged: the real text survives as the token, and
  the existing "evidence lost" flag is set on it.
- **No-substitution case** — unchanged, byte for byte: a command with no
  substitution in it produces exactly the tokens it produces today.
- The two flags must be tellable apart by the recursive-delete check, because
  they lead to different tiers (Part 3).
- The separate re-scan of each substitution BODY as its own statement is
  unchanged — a destructive call hidden inside a substitution is still seen.

### Part 2 — the stand-in text for a whole-word target

The whole-word token needs a text, since it is what the reason text will show.
Required properties, all of which are testable:

- Non-empty and not whitespace only (FR3, FR4).
- Identical for both substitution spellings (FR1).
- Recognizable to a reader as "this target was a command substitution", so the
  reason text identifies which delete target is the problem.
- Contains no NUL and no other control character; never carries the internal
  marker through to output (NFR6).
- Inert in every position a word can occupy: it must not read as a flag (no
  leading `-`), must not match the redirect-operator shape, must not equal or
  begin with any safe-root or build-artifact name, and must not match the
  self-config or transcript protected-path patterns — so its appearance in a
  non-delete position changes no verdict (FR6).
- Chosen so the whole-word target cannot reach the safe-root exception by any
  route.

### Part 3 — the recursive-delete check and its reason text

Per target, the existing order is preserved: the root/home shape is still
judged first on the raw token, the recursive-flag gate still gates everything
below it, and the cross-target "strongest tier wins" selection is untouched.
Added within that order:

- A whole-word-substitution target counts as a target (it must not produce the
  zero-target early return), and is judged BEFORE lexical normalization and
  before the safe-root containment step — there is no path text to normalize,
  and it must never reach the safe exception.
- Its tier is `ask` and its rule id is the existing `rm-unresolvable`; the
  existing unattended demotion turns that into `deny` with no change to the
  demotion logic (NFR4).
- Its reason text follows the existing `rm-unresolvable` sentence: it names
  the target using Part 2's rendering and keeps the closing instruction that
  tells the reader to re-issue the command with the expanded real path. The
  existing sentence already describes variable expansion AND command
  substitution; once this behaviour lands the description is accurate, so the
  sentence needs no rewrite beyond what the target rendering changes (FR3).
- The adjacent-text case keeps today's outcome: the safe exception is skipped
  and the target falls through to `deny` under `rm-recursive`, which is what
  keeps the pinned denies of FR5 unchanged.
- A delete without a recursive flag behaves exactly as before.

### Part 4 — non-delete positions must not move

Because the marking stage feeds every command, confirm by test that the
changed handling leaves these intact: the command word a statement is
classified by, the redirect-versus-word classification and the write-target
set built from it, and the destination extraction for copy / link / sync /
archive / download commands. A substitution appearing in any of those
positions still produces `allow`.

### Part 5 — case table

- The two entries pinned as known holes (`rm -rf $(mktemp -d)` and
  `rm -rf $(cat list)`) take the new verdict, and the "既知の穴(未修正)"
  wording is removed from their labels.
- The entry for the quoted whole-word form (`rm -rf "$(cat list)"`) takes the
  verdict IMPLEMENTATION.md D4 records for it, with a label that no longer
  describes an asymmetry against a known hole. The entry itself is retained.
- New entries are added for a substitution-only delete target in both
  spellings, using the observed attack shapes from the SPEC, plus the edge
  cases listed under Test Notes.
- No existing entry is removed, and no existing `allow` entry changes its
  expectation.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR2): `rm -rf $(printf /home/sakura/valuable)`, the same
      command written with the substitution in backticks, `rm -rf $(mktemp -d)`
      and `rm -rf $(cat list)` are each judged `ask` with rule id
      `rm-unresolvable`, and each becomes `deny` when the unattended
      environment variable is set. None of the four is `allow` in either mode.
- [ ] AC-2 (FR3, NFR5, NFR6): for each command in AC-1 the reason text names
      the offending delete target with a rendering that is non-empty, not
      whitespace only, identical across both spellings, and still carries the
      closing rewrite instruction in the existing Japanese style; the complete
      standard-output text of every case in this module contains no NUL and no
      other control character.
- [ ] AC-3 (FR4): `rm -rf "$(cat list)"` is never `allow`; its verdict is the
      tier IMPLEMENTATION.md D4 records, and the delete target shown in its
      reason text is not whitespace only.
- [ ] AC-4 (FR5, NFR7): every verdict FR5 lists is unchanged — `deny` for
      `rm -rf $(pwd)/build`, `rm -rf $(pwd)/../tmp/scratch`,
      `rm -rf tmp/scratch$(pwd)` and their backtick equivalents; `deny` for
      `echo $(rm -rf /home/sakura/x)` via the substitution-body re-scan; `ask`
      for `X=$(mktemp -d); rm -rf $X`; `allow` for `rm -rf /tmp/x`,
      `rm -rf node_modules`, `rm -rf ./build` and `rm -rf dist/*`.
- [ ] AC-5 (FR6, NFR4): a substitution outside a delete-target position
      changes no verdict — command-word position, redirect destination,
      copy/link/sync destination, a build invocation, a commit message, a
      `python3 -c` payload and a here-doc body all stay `allow`; a delete
      without a recursive flag is unchanged; a nested substitution stays
      `deny` and never becomes `allow`; a delete carried inside a `-c` / eval
      / here-string payload reaches the same verdict as the same delete
      written directly; and a command with unbalanced quoting (the
      parse-failure fallback) raises no exception and still exits 0.
- [ ] AC-6 (FR7, NFR7): the case table has entries for a substitution-only
      delete target in BOTH spellings; the two known-hole labels no longer
      carry the "既知の穴(未修正)" wording; every command string present in the
      table before this task is still present afterwards, and the only
      expectation changes are the three entries named in Design Part 5;
      `python3 em-workflow/hooks/tests/run-destructive-guard.py` reports every
      case passing, including the unattended-demotion case.
- [ ] AC-7 (NFR1, NFR2, NFR3): `python3 -m unittest discover -s tests` passes
      with the new module present; the module drives the guard as a subprocess
      with PreToolUse JSON on standard input and imports no third-party
      package; the guard's source gains no filesystem-resolution, stat or
      subprocess call; the same command string re-run yields the identical
      verdict and reason text; and the existing cap on shell-payload
      re-expansion is left in place, with the kilobyte-scale case in the table
      still completing.

## Test Notes

- **Write the failing expectations first.** Add the new case-table entries and
  flip the three existing expectations before changing the guard: the runner
  then reports exactly the cases this task must move, and the `allow` half
  proves it moves nothing else.
- **Split by suite.** The case table (integration, TS-1) owns verdict-level
  expectations, including every edge case that is expressible as one command
  string. The new unit module (TS-2) owns what the table cannot express:
  reason-text content and rendering, absence of control characters in the
  whole standard-output text, the unattended demotion for the new shapes,
  exit-status/fail-open behaviour, determinism across repeated runs, and a
  source-level check that no filesystem or subprocess call was introduced.
- **Edge cases to cover** (SPEC TS-3 … TS-10): nested substitution; a
  substitution in a redirect destination; a safe target mixed with a
  substitution target, and an unmistakably dangerous target mixed with one;
  a delete without a recursive flag; a substitution adjacent to real text
  inside double quotes; a delete inside a `-c` / eval / here-string payload;
  unbalanced quoting; and the complete `allow` half as regression.
- **TDD-awkward**: the source-level "no new filesystem access" check is a
  property of the file rather than of a behaviour — assert it by inspecting
  the guard's own source for the forbidden call shapes, keeping the assertion
  narrow enough that unrelated edits do not trip it.
