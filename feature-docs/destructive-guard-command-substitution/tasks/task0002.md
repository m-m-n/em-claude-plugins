# Task Plan: task0002 — plugin version bump pinned by its own regression module

## Goal

The em-workflow plugin version is raised by one patch step in both manifests
that carry it, so an installed cache picks up the fixed hook, and a new
regression module fails on any tree that skipped the bump.

## Requirements

FR8

## Scope

### Files to Create
- `tests/test_destructive_guard_command_substitution_version_bump.py` —
  regression module pinning the bump: both manifests parse as JSON, both carry
  the same version string, and that string is past the pre-change baseline.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — the plugin manifest's version
  field.
- `.claude-plugin/marketplace.json` — the version field of the em-workflow
  entry only.

## Design

Read together with IMPLEMENTATION.md — the "em-workflow plugin version" row of
its Shared Components table states the contract this task satisfies, and D2
states the value and the ownership boundary.

### Part 1 — the two manifest edits

- Both files are JSON documents edited in place: only the version value of the
  em-workflow entry changes. Every other field, and every other plugin's
  entry, keeps its current value; formatting and key order are preserved.
- The marketplace entry is located by its `name` field, never by its position
  in the array.
- The new value is one patch step above what both files currently read, per
  the version-bump rule's semantics for a behaviour fix.

### Part 2 — the regression module

Follows the shape the repository's existing per-feature version-bump modules
already use, so a reviewer reads one familiar structure:

- Both manifests are PARSED as JSON and asserted on as data; the raw file text
  is never pattern-matched for the version.
- Two matchers: a **baseline matcher** (the version is of the three-part form,
  its leading pair is unchanged, and its patch is strictly greater than the
  pre-change patch) and an **equality matcher** (the two files report the
  identical string). Expressing the baseline as "strictly greater than" rather
  than as a fixed literal keeps the module from going stale on the next
  unrelated bump while still failing on a tree that skipped this one.
- Each matcher carries a negative proof (a forged sample the matcher rejects)
  and a non-vacuity guard (the same forged sample is itself well-formed, so
  the proof exercises the comparison rather than a parse failure).
- Regression guards over untouched neighbours: the plugin manifest's own name
  field, and the sibling plugin's entry — its source, and the fact that its
  independent version was not dragged along.
- Standard library only; the module imports no sibling test module.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR8): both manifests report the identical version string, of the
      form `0.1.<patch>` with patch strictly greater than 74.
- [ ] AC-2 (FR8): both files still parse as JSON; no field other than the
      em-workflow version changes in either file; the sibling plugin's entry
      keeps its own `source` and its own, different version.
- [ ] AC-3 (FR8): the new module is discovered by
      `python3 -m unittest discover -s tests`, parses both manifests as JSON
      rather than pattern-matching their text, and looks the marketplace entry
      up by its `name` field.
- [ ] AC-4 (FR8): the module carries a negative proof and a non-vacuity guard
      for each of its two matchers, and reverting only the two manifest edits
      makes the module fail — the failure names the version comparison, not a
      parse error.
- [ ] AC-5 (FR8): `python3 -m unittest discover -s tests` passes as a whole
      with the new module present — including the repository-wide plugin
      version parity check — and
      `python3 em-workflow/scripts/check-plugin-invariants.py .` exits 0.

## Test Notes

- Write the module first: on the unedited tree it fails on the baseline
  matcher, which is exactly the state it exists to detect. Then make the two
  manifest edits and re-run.
- The negative proofs are pure in-module comparisons over forged strings; they
  need no fixture files and must not write anywhere.
- No test in this module may mutate either manifest — they are read-only
  inputs.
- The repository-wide parity check and the plugin-invariants script are the
  cross-check that the two edits agree; run both, not just the new module.

## Out of Scope

- Any change to `em-workflow/hooks/destructive-guard.py`, its case table, or
  any guard behaviour (task0001 owns those).
- The sibling plugin's version, which moves independently.
- Generating or editing the LICENSE file.
- Reinstalling or refreshing the local plugin cache; only reporting that a
  Claude Code restart is needed for the new version to take effect.
