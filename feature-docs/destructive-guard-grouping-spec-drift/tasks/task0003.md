### Facts the revised documents state

- Write-target sources: exactly (a) to (d) from IMPLEMENTATION.md "Write-target sources".
- mv: every non-flag argument is a write target, because mv unlinks each source, plus the `-t` / `--target-directory` value. So in `mv a b c dir/`, a, b, c and dir/ are all write targets.
- cp / ln: the last positional argument after value-flag stripping, or only the `-t` / `--target-directory` value when that flag is given.
- tar `-C` / `--directory` is a write target only in extract mode, per the tar extract-mode rule. The code in this task's worktree may still treat `-C` as a destination in every mode, because that change lands in parallel (D3). The documents describe the extract-mode-only behaviour and never the all-mode behaviour.
- rm: the bodies of `check_rm` and `SAFE_DELETE` are unchanged, but `head()`'s wrapper value-flag consumption (`WRAPPER_VALUE_FLAGS`) and `statements()`'s `-c` / eval / here-string payload re-scan changed the input `check_rm` receives. As a result `sudo -u root rm -rf $HOME/x`, `bash -c 'rm -rf $HOME/x'` and `eval 'rm -rf $HOME/x'` went from allow to ask (demoted to deny under `CLAUDE_BATCH`).
- Before writing, confirm the facts other than the tar mode against `em-workflow/hooks/destructive-guard.py` in this worktree (read only). If a fact differs from this plan, report a plan deviation instead of documenting the difference.
