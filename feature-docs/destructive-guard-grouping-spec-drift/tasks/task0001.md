# Task Plan: task0001 — Judge commands inside grouping and compound constructs

## Goal

A command that a grouping or compound construct places at command position gets the same verdict as the same command written alone, a closing `)` never becomes an argument of any check, and reserved words or grouping characters used as data stay allow.

## Design

This task owns statement shaping (IMPLEMENTATION.md, Layer Structure stage 2) and produces the "Shaped statement" shared component. It follows D1 (handle grouping once, upstream of every check), D4 (version target value) and D5 (case-table union) in IMPLEMENTATION.md. It does not touch the tar handling inside destination extraction.

### Constructs recognised at command position (FR2)

- Subshell opener `(`, only when it is an unquoted operator token.
- Brace-group opener `{`.
- Reserved words `if`, `then`, `elif`, `else`, `while`, `until`, `do`, and `!`.
- Case patterns: after `case WORD in`, an optional `(`, the pattern alternatives and `)`; the command after that `)` is judged. A pattern can be split across statements, by pipe splitting (`a|b)`) or by newlines (multi-line case body), so the case context must carry from one statement to the next within the same command string or payload. `;;` ends the current case item, after which a new pattern may start. `esac` ends the case context.
- Function definitions: `NAME() {`, `function NAME {`, `function NAME() {`. The body is judged as if it runs, whether or not the command also calls the function.
- The `for` / `select` header (`for NAME in WORDS`) is not a command. The words after `in` are never judged as a command; the command after `do` is.
- Closers and terminators (`)`, `}`, `fi`, `done`, `esac`, `;;`) carry no command of their own. A redirect attached to one is still a write target.
- Nested and combined forms unwrap fully, including combination with the existing VAR=value skip, the `WRAPPERS` skip, mise / asdf exec, and substitution-headed command words.

### Closer handling (FR3)

- A bare `)` operator token that closes a subshell or a case pattern is never counted among a command's arguments by any check: rm targets, write targets (cp / ln / rsync positional-last, mv / rm / chmod / chown non-flag arguments, `INPLACE_WRITERS`), git, file-destruction, external and permission checks.
- This includes a closer that directly follows the last argument (`(rm -rf /tmp/x)`, `(cp /tmp/x ~/.claude/settings.json)`).
- A closer fused with a following redirect operator (`)>`, `)>>`, `)2>` and similar) splits into the closer and a real redirect. The redirect target is judged only as a redirect target, never as the command's destination or as an rm target.
- A quoted `")"` or `"("` is an ordinary word.

### Data stays data (FR4)

- Reserved words and grouping characters count as syntax only at command position, and `(` only as an unquoted operator token.
- These stay allow: a reserved word in argument position, grouping text inside quotes, here-doc bodies not aimed at a shell sink, commit messages, the words of a for / select header, and a case pattern whose text happens to be a command name.
- A subshell's trailing `)` is never mistaken for a case-pattern terminator.
- A quoted `"{"` at command position cannot be told apart from a bare `{`; treating it as grouping is accepted (stricter direction).
- Pre-existing rows that must keep their verdicts include: `(cd /home/sakura && rm -rf ./x)` (deny); `(true; X=/tmp/safe; false)>/dev/null; rm -rf $X`, `(X=/tmp/safe; true); rm -rf $X` and the newline-separated subshell form (ask); the if/then HOME forms (deny); the for / while-read forms (ask); `find /home/sakura \( -name '*.log' \) -delete` (deny); `git push "(" --force origin main` (deny).

### Scope boundary (FR5)

- The unwrap applies to every per-statement check in `main()`: `check_rm` (rm-root / rm-recursive / rm-unresolvable), `check_git`, `check_file_destruction`, `check_external`, `check_permissions`, `check_self_modification` (self-modification and transcript-write), and the substitution-headed route.
- It applies equally to statements reached through `statements()`'s substitution-body, shell-sink here-doc and `-c` / eval / here-string payload re-scan.
- Unchanged: the deferral to failed-run-cleanup-guard (`matches_target_shape()` over `strip_grouping_prefix()` / `_deferral_head()`), so the existing `(silent)` and deferral-related allow rows keep their verdicts. `em-workflow/hooks/failed-run-cleanup-guard.py` is not modified. `head()` keeps its 2-tuple return shape.
- Documentation inside the hook: the mirror note in `head()`'s docstring states that the grouping-aware skip is local to `destructive-guard.py` (same precedent as the `substitution_only` skip). The `strip_grouping_prefix()` docstring sentence saying subshell- or brace-wrapped destructive commands stay unexamined by the other checks, and the matching `main()` comment, are rewritten to describe the new behaviour.

### Processing flow

1. Command string enters the deferral check (unchanged).
2. `statements()` produces statements, including substitution bodies, shell-sink here-docs and re-scanned payloads.
3. For each statement, with the case context carried over from the preceding statements of the same source, grouping syntax at command position is skipped (repeatedly, interleaved with the existing skips) until the real command word is reached.
4. Closer tokens are dropped from the arguments; fused closer-redirect tokens are split into a closer and a real redirect.
5. A statement that consists only of syntax (for example `fi`, `done`, `esac`, `}`) yields no command, but its redirects still count as write targets.
6. The shaped statement is handed unchanged to every per-statement check.

### Case rows to add, as one contiguous block, before any change to destructive-guard.py (FR1)

Expected verdicts are runner verdicts (`CLAUDE_BATCH` cleared).

Group (1) — ticket reproductions, each ask (same as bare `rm -rf $HOME/x`):

- `if true; then rm -rf $HOME/x; fi`
- `for f in a; do rm -rf $HOME/x; done`

Group (2) — literal-target parity, each deny (same as bare `rm -rf /home/sakura/x`):
- `( rm -rf /home/sakura/x )`
- `(rm -rf /home/sakura/x)`
- `{ rm -rf /home/sakura/x; }`
- `if true; then rm -rf /home/sakura/x; fi`
- `if false; then :; elif true; then :; else rm -rf /home/sakura/x; fi`
- `if rm -rf /home/sakura/x; then :; fi`
- `while true; do rm -rf /home/sakura/x; done`
- `until rm -rf /home/sakura/x; do :; done`
- `for f in a; do rm -rf /home/sakura/x; done`
- `! rm -rf /home/sakura/x`
- `case x in a) rm -rf /home/sakura/x;; esac`
- `case x in (a) rm -rf /home/sakura/x;; esac`
- `case x in a|b) rm -rf /home/sakura/x;; esac`
- A three-line command, lines joined by newlines:
  - line 1: `case $x in`
  - line 2: `  a) rm -rf /home/sakura/x ;;` (two leading spaces)
  - line 3: `esac`
- `f() { rm -rf /home/sakura/x; }; f`
- `function f { rm -rf /home/sakura/x; }; f`
- `( { rm -rf /home/sakura/x; } )`
- `if true; then ( sudo rm -rf /home/sakura/x ); fi`
- `bash -c '( rm -rf /home/sakura/x )'`
- `echo $(if true; then rm -rf /home/sakura/x; fi)`

Group (3) — git parity, each deny:
- `( git reset --hard HEAD~1 )`
- `{ git push --force origin main; }`
- `if true; then git clean -fdx; fi`

Group (4) — self-modification parity, each ask:
- `(cp /tmp/x ~/.claude/settings.json)`
- `(cp /tmp/x ~/.claude/settings.json)>/dev/null`
- `{ tee ~/.claude/settings.json < /tmp/x; }`

Group (5) — transcript-write parity, each deny:
- `(mv ~/.claude/projects/x/y.jsonl /tmp/y.jsonl)`

Group (6) — other per-statement checks:
- `( find /home/sakura -name '*.log' -delete )` (deny)
- `{ chmod -R 777 /home/sakura/x; }` (ask)

Group (7) — false-positive guards, each allow:
- `( rm -rf /tmp/x )`
- `(rm -rf node_modules)`
- `(rm -rf /tmp/x)>/dev/null`
- `if [ -d /tmp/x ]; then rm -rf /tmp/x; fi`

- `f() { echo hi; }; f`

## Test Notes

- The case table is the test suite for AC-1 to AC-5; the runner is the harness. Each group maps to one criterion (group (1) to AC-2, groups (2) to (6) to AC-3, the fused-closer rows to AC-4, group (7) and all pre-existing rows to AC-5).
- Red first: add the whole block, run the runner, and record which rows fail. The rows expected to fail are those whose verdict the fix changes; rows that already pass (for example several group (7) allow forms) stay in as regression guards and are not expected to go red.
- Edge cases that deserve attention while implementing: a case pattern split by pipe or by newline; the optional leading `(` of a case pattern; fused `)>` / `)>>` / `)2>` tokens; redirects attached to `done` and `}`; nesting (`( { ...; } )`, a subshell inside if/then); grouping inside `-c` / eval payloads and substitution bodies; a subshell's trailing `)` next to an existing case-free command (the pinned `(X=/tmp/safe; true); rm -rf $X` row).
- The unattended variant (deny under `CLAUDE_BATCH=1`) is covered by the runner's trailing demotion case; no separate row is added for it.
- AC-6 is checked by reading the diff; AC-7 by the unittest run; AC-8 by reading both JSON files.
