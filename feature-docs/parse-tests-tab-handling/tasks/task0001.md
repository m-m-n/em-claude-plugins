# Task Plan: task0001 — Tab-line handling in the record check's tests-block parser

## Goal

The tests-block parser of the record check (`_RecordParser.parse_tests` in
`tests/test_tests_yaml_id_resolution.py`) handles lines that carry a tab in
their indentation so that a record containing them still yields one failure
message listing both the `tab in indentation` errors and the resolution errors
of every readable ID. Regression tests pin the behaviour.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `tests/test_tests_yaml_id_resolution.py` — revised tab-line handling in the block-list branch of the record parser's tests-block method, and new regression tests for FR1 to FR4

## Design

IMPLEMENTATION.md is not produced for this feature (reduced tier, a single
task, no file declared by more than one task); every decision this task needs
is stated here.

### Terms

- **Tab line**: a non-ignorable line (neither blank nor a full-line comment,
  per the parser's existing rule) whose first character after its leading
  spaces is a tab. This is exactly the condition the parser already reports as
  `tab in indentation`; the condition itself does not change.
- **Leading space count** of a tab line: the number of spaces before that tab.
- **Item indentation**: the indentation shared by the items of the block list.
- **Held ID**: the parser's existing state "the most recent element is a
  one-line scalar kept among the IDs" (the state that lets a deeper line take
  the fragment back).

### Defects being fixed

1. When the first line after the `tests` key is a tab line, the parser reports
   it and returns no IDs right after that line. The field loop of the AC then
   reads the next dash item as a field with inconsistent indentation, so the
   following IDs are never resolved (FR1).
2. A tab line deeper than the item is reported as a tab before the
   deeper-line check runs, so a held ID (the first-line fragment of a
   multi-line value) is never taken back and gets resolved (FR3).

### Revised flow of the block-list branch

The flow-list branch and the inline-value branch of the tests parser are
unchanged.

1. **Pre-item scan.** Starting after the `tests` key line, pass over
   ignorable lines and tab lines. Report each tab line once as
   `tab in indentation` at its own line number. Remember whether at least one
   tab line was passed.
2. **Block end reached during the scan.**
   - No tab line passed: unchanged — `tests key has neither a value nor items`
     at the key line.
   - At least one tab line passed: report nothing more; return no IDs and the
     block end as the next index (FR2).
3. **First non-tab line found.** Classify it exactly as today: a dash line at
   or deeper than the key fixes the item indentation and the list is read
   (FR1); a non-dash line deeper than the key is
   `tests value is not a block sequence of scalars` (unchanged); anything else
   is the "neither" case. In the "neither" case:
   - No tab line passed: unchanged (error at the key line, return the index
     right after the key line).
   - At least one tab line passed: `neither a value nor items` is not
     reported; return no IDs and the index of that first non-tab line, so the
     field loop resumes there and never reads the consumed tab lines again
     (FR2: exactly one error per tab line).
4. **Tab line inside the item loop**, decided by comparing its leading space
   count with the item indentation:
   - **Greater (FR3)**: report only `tab in indentation` — the deeper-line
     reason (`continues or nests on a deeper line`) is not reported for this
     line. If an ID is held, remove it from the returned IDs; afterwards no ID
     is held. Advance one line; deeper non-tab lines that follow go through
     the existing deeper-line handling (A2).
   - **Equal (FR4)**: not a continuation line. Report only
     `tab in indentation`; the preceding ID stays in the returned IDs and the
     held-ID state is left as it is. Advance one line.
   - **Smaller**: unchanged (report `tab in indentation`, advance one line).
5. Every other line kind in the item loop keeps its current handling.

### Contract of the tests-block parser (shape unchanged)

- Returns the readable IDs in file order and the next index; the next index
  is strictly greater than the `tests` key line's index, as today, so the
  field loop always advances.
- Every tab line between the key line and the returned next index produces
  exactly one `tab in indentation` error for the AC (TM-1).
- An element written on a tab line never contributes an ID.
- Only the existing reason strings are used; no new reason is introduced and
  lines with a tab in their indentation stay unsupported notation (A1).
- Docstrings and comments of the parser that describe the changed behaviour
  are kept consistent with it.

### Regression tests (FR5)

- The tests live in `tests/test_tests_yaml_id_resolution.py`, either next to
  the existing extraction-error tests or in a new test case class dedicated
  to tab handling whose docstring cites this feature's FR IDs, following the
  existing classes' docstring convention. Reuse the module's existing record
  and temporary-root builders and its resolution-error-line reading.
- Write each tab as an escape sequence inside the string literal, as the
  existing `tab in indentation` case does, never as a raw tab character in
  the source file.
- In the criteria below, `<TAB>` denotes one literal tab character and ` / `
  separates the lines of the record text.

## Test Notes

- AC-1 to AC-4 and AC-6 are unit tests over the module's own extraction
  function, its per-record check and its per-record test generator, run
  against temporary roots built with the module's existing fixture builders.
  AC-5 is the integration check (both run commands, plus a review of the diff
  for removed or changed existing expectations and for the changed-file set).
- Resolution of `tests.nope.*` IDs fails in a temporary root by
  construction, so each readable ID shows up as exactly one resolution error
  line; that is how "the ID is resolved" and "the ID is not resolved" are
  observed.
- Cover the end-of-file termination of AC-2 with the record text ending right
  after the tab line.
- Write the AC-1 and AC-3 tests first and confirm they fail on the current
  parser (they reproduce the ticket), then change the parser.

## Out of Scope

- The flow-list and inline-value branches of the tests parser, the AC-level
  and record-level tab handling, and the resolver.
- Changing any reason string, or accepting tab-indented lines as supported
  notation (A1).
- Deeper non-tab lines that follow a deeper tab line keep their existing
  handling (A2).
- Any file other than `tests/test_tests_yaml_id_resolution.py` (NFR3).
