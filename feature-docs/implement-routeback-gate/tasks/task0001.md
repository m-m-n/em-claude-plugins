## Design

### Target locations

1. **Branch & Worktree Model → exit-4 recovery bullet.** It currently scopes
   itself to "every `commit-docs.sh` call site in this phase" and enumerates
   Step I.1's baseline commit and Step I.2.b's wake-phase commit. The
   enumeration gains the I.2.c route-back commit introduced below. Nothing
   else in the bullet changes — the recovery procedure sentences remain as
   they are (see IMPLEMENTATION.md D4 for the substrings that must survive).
2. **`### I.2.c: Failed handling` → "route back to planning" option.** Its
   gate sentence, its ordered write set, its commit step and its merged-task
   branch are the substance of this task.
3. The heading line itself, the "retry" option, the "abort phase" option, the
   "There is NO skip option" paragraph and the batch-mode paragraph are NOT
   edited.

### Route-back path (the corrected behaviour the text must express)

1. The failure reason is recorded in `tasks.{T}.notes` and stays there.
2. One ordered workflow.yaml write set: `create-plan` → `needs_update`; the
   `implement` step → `pending`; the failed task's `tasks.{T}.status` →
   `pending` (this last write is what makes the planner's `replace_planning`
   operation admissible on re-entry — cite
   `references/workflow-patch.md`'s `replace_all` permission conditions as
   the owner of that rule rather than restating it).
3. Cleanup of the failed task's worktree and branch, in an order stated
   unambiguously relative to step 4 (the existing `git worktree remove` /
   `git branch -D` lines stay as they are).
4. A `commit-docs.sh` commit of that write-back against the integration
   worktree, with the expected-tip third argument expressed the way the
   file's other call sites express theirs, and a pointer to the Branch &
   Worktree Model's exit-4 recovery rule.
5. The phase ends with its report; create-plan re-enters afterwards.

### Gate condition

The condition governing the automatic re-entry is the **absence of any task
with status `merged`**. The current phrasing "every existing task is still
`pending` (i.e. none has merged yet)" is falsified by the failed task itself
at decision time and is removed from the section.

### Merged-task branch (the terminal)

When at least one task has merged: automatic re-entry does not apply,
`create-plan` is not set to `needs_update`, `implement` stays `failed`, and
the phase reports and returns control to the user through develop's stop
condition 3 — the same terminal as the "abort phase" option. The existing
instruction to hand the additional scope to the rework path (`append`), and
the `replace_all`-rejection rationale sentence attached to it, are removed:
no defined trigger routes implement into rework.

### Delegation citation

The sentence currently reading "`skills/develop/SKILL.md` Step B's create-plan
exemption owns that precedence" must instead name Step B's stop-condition-3
precedence clause — the block whose auto-re-entry exclusion list enumerates
the create-plan route-back transition owned by implement-phase.md. The
create-plan `in_progress` exemption is a different Step B block and is no
longer named as the owner. implement-phase.md continues to cite, never
restate, develop's rule (IMPLEMENTATION.md Conventions).

### Test module

A new module under `tests/`, following the existing document-contract
modules' pattern (IMPLEMENTATION.md Conventions): resolve the plugin root
relative to the test file's location, read implement-phase.md once per test
class, and slice the `### I.2.c: Failed handling` section between its heading
and the next section heading. Assertions are: presence of the tokens each
criterion names, absence of the strings each criterion removes, relative
ordering by position inside the slice, and byte-identity for the batch-mode
paragraph only. Per IMPLEMENTATION.md D3, no assertion may reference the
plugin's version value.
