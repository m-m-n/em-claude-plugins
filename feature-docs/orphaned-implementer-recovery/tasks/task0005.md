## Design

### Root cause

Each of these modules was written for an earlier feature's em-workflow
version-bump task. To prove that its task touched nothing outside the
em-workflow entry, each module captured the *other* marketplace content as a
retention anchor at its own base revision — and at every one of those
revisions the `em-review` entry had no `version` key. The project rule
`.claude/rules/core-plugin-version-bump.md` requires a plugin's version to
appear in two places, the plugin's own `plugin.json` and its entry in the
root `marketplace.json`; the `em-review` entry now satisfies that rule and
carries a version. The manifest is correct and the snapshots are stale: they
encode "the shape em-review happened to have back then" as if it were an
invariant. Nothing in the manifest is to be changed by this task.

### Three assertion shapes, one correction

| Shape | Where | Correction |
|---|---|---|
| A direct "no `version` key" assertion on the em-review entry | the seven modules whose failing test is `test_em_review_entry_has_no_version_key` | Assert instead that the entry carries a `version`, and that it is a dotted numeric string. The assertion stays non-vacuous: it fails when the key is absent or malformed |
| An expected key *set* for the em-review entry | `test_goal_vs_spec_divergence_version_bump.py`, `test_rework_contract_drift_version_bump.py` | Add `version` to the expected key set. Equality against the full key set is retained, so an added or removed field still fails |
| A pinned whole-entry (or whole-other-entries) snapshot compared for equality | `test_spec_file_set_completeness_version_bump.py`, `test_batch_policy_option_id_version_bump.py` | Split the comparison: the structurally stable identity fields (name, author, category, source, and the description's stable substring anchor) stay pinned and compared exactly; the `version` field is asserted by shape — present and dotted numeric — rather than against a literal value |

### Why the version value is asserted by shape, not by literal

Pinning the current em-review version literal would reproduce the same
failure the moment em-review is next bumped — the version field is the one
field of that entry the project rule *requires* to change over time, so an
exact-value expectation over it is a staleness generator, not a guard. Every
other field of the entry keeps its exact expectation, so the property each
module was placed to hold — "this feature's task altered nothing in the
em-review entry" — is preserved for everything that is genuinely invariant,
and is stated as a shape constraint exactly where a value is legitimately
mutable.

### What must not move

The em-workflow half of every module is out of this task's reach: the
plugin.json version parse, the per-component numeric baseline comparison,
the registry-agreement check, the entry-lookup-by-name helper and every
negative proof attached to them stay exactly as they are. This task changes
only expectations about the em-review entry, plus the prose describing them.

### Version-bump rule applicability

The file set is entirely under repository-root `tests/`. No file under
`em-workflow/` (or any other plugin directory) is touched, so
`.claude/rules/core-plugin-version-bump.md` is not triggered and neither
manifest is edited by this task.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `python3 -m unittest discover -s tests`, run from the repository
      root, exits 0 with zero failures and zero errors.
- [ ] AC-2: In each of the nine modules, the em-review expectation names
      `version` as part of the entry's shape, and a test in that same module
      proves the em-review matcher still fails on a forged entry whose
      name, author, category or source is altered, and on a forged entry
      whose `version` is absent or is not a dotted numeric string.
- [ ] AC-3: No module compares the em-review version against a literal
      version value; each of the nine modules has a test showing its
      em-review matcher accepts a forged entry that differs from the real
      one only by a higher version value.
- [ ] AC-4: Every test method name present in the nine modules before the
      change is still present after it, except for em-review assertions
      whose meaning changed — each of those is a 1:1 rename whose
      replacement asserts the rule-conformant shape. No test is deleted,
      skipped, or reduced to an assertion that cannot fail.
- [ ] AC-5: Every em-workflow-side assertion in the nine modules — plugin
      manifest version parse, baseline advancement, registry agreement,
      entry lookup by name, and their negative proofs — is byte-unchanged.
- [ ] AC-6: No docstring or comment in the nine modules states that the
      em-review entry carries no version key, or otherwise contradicts the
      assertion it sits next to.
- [ ] AC-7: The change is confined to the nine declared files: no other
      file is created or modified, in particular no file under
      `em-workflow/`, `.claude-plugin/marketplace.json` or any plugin
      manifest; each modified module still imports only the standard
      library and remains at repository-root `tests/` named `test_*.py`.

## Test Notes

- Every criterion except AC-1 and AC-7 is a unit-level property of the
  modules themselves, exercised the way these modules already work: parse
  the two manifests, compare against expectations, and prove each matcher
  in the failing direction against forged in-memory samples. The forged
  samples are hermetic — they never write to the manifests.
- AC-2 and AC-3 are the negative and positive proofs of the same matcher;
  write them as a pair per module so a matcher weakened to a tautology is
  caught by the negative half.
- AC-1 is not assertable from inside a module in this suite (a suite cannot
  assert its own full-suite outcome without recursion) — follow the existing
  convention in these modules: run the discovery command and record its exit
  code and failure count in the implementer report.
- AC-4, AC-5 and AC-7 are diff properties, verified against the pre-change
  revision with the repository's own diff tooling and recorded in the
  implementer report, not encoded as tests.
- Edge case worth one test where the pinned whole-entry snapshots live
  (`test_spec_file_set_completeness_version_bump.py`,
  `test_batch_policy_option_id_version_bump.py`): the split comparison must
  still fail when a *new, unexpected* key appears on the em-review entry —
  loosening only the version field must not turn the comparison into a
  subset check.

## Out of Scope

  or any other plugin manifest. The manifests are correct; the expectations

- Bumping any plugin version. No file under a plugin directory is touched,
  so the version-bump rule does not apply to this task.
- Consolidating the nine modules' duplicated helpers into a shared test
  module. Each module is owned by the feature that created it; merging them
  is a separate decision.
- Changing any assertion about the em-workflow entry, or about any file
  other than the two manifests these modules already read.
- Touching the test modules this feature's own tasks 0001–0004 created.
