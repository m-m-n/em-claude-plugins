# Task Plan: task0002 — Journal terminal-append helper

## Goal

A single new journal writer that appends one `failed` event with reason
`orphaned` under the same exclusion discipline as the existing writers, and
does nothing at all when the task's final event is already terminal.

## Requirements

FR3, FR4, NFR1, NFR2, NFR4, NFR5

## Scope

### Files to Create

- `em-workflow/scripts/journal-append-failed.py` — the journal terminal-append
  helper (IMPLEMENTATION.md SC2).
- `tests/test_journal_append_failed.py` — unit coverage for the append, the
  idempotent no-op, the exclusion discipline, and the downstream launch.

### Files to Modify

None.

## Design

Implement SC2's contract exactly as pinned in IMPLEMENTATION.md — its
parameters, preconditions, critical section, postconditions and outcome
reporting are the contract the caller (task0003) is built against, so none
of them may be renamed or relaxed here.

**Reason validation (D5).** `--reason` is checked against a closed set whose
only member is `orphaned`. Any other value is rejected before the journal is
opened: non-zero exit, nothing written. This is what keeps the new
orchestrator-side write authority as narrow as the SSOT exception.

**Event line shape (SC4).** Read the existing `failed` writers and reuse
their field names and ordering; do not invent a shape. The change is
additive — a new value of the existing reason field.

**Exclusion discipline (NFR2).** One exclusive advisory lock on the journal
file itself, held across both the replay that determines the task's final
event and the append. Open for append without following a symbolic link.
Never create the journal file, and never create its parent directory: an
absent file or directory is an error, reported and not repaired.

**Structure for testability.** The replay decision and the append are
reachable as functions; the command-line entry point is a thin wrapper over
them, so both the decision logic and the whole invocation can be tested
(FR3's "unit-testable form").

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Given a journal whose final event for the task is `launched`,
      one invocation appends exactly one `failed` line carrying reason
      `orphaned`, and no pre-existing line in the file changes.
- [ ] AC-2: A second invocation in the resulting state appends nothing and
      reports the terminal no-op outcome; the file still holds exactly one
      `failed` line for that task (TS-2). The same holds when the final
      event is `merged`.
- [ ] AC-3: A `--reason` value outside the closed set is rejected with a
      non-zero exit and no write.
- [ ] AC-4: A journal path that is a symbolic link is refused without
      writing; an absent journal file, and an absent parent directory, are
      each reported as an error, and neither is created (TS-7).
- [ ] AC-5: Two invocations contending for the same journal produce at most
      one appended `failed` line for the task and never a partially written
      line (TS-7).
- [ ] AC-6: Outcome reporting matches SC2 — one line of JSON on stdout
      carrying the outcome, exit 0 for both decided outcomes, non-zero and
      no write for usage or internal errors, diagnostics on stderr only.
- [ ] AC-7: After this helper records `failed` with reason `orphaned`, a
      launch of the same task is permitted by the launch guard and
      `launched` is appended — it is not denied (TS-4).

## Test Notes

- Fixtures build a throwaway worktree-root directory inside a temporary
  directory, holding a journal file seeded with the event lines each case
  needs. Nothing outside the temporary directory is touched, and no real
  `~/.claude` state is read (NFR5).
- AC-5 needs genuine contention: start two invocations against the same
  journal and assert the post-state, rather than asserting that a lock was
  requested. Keep the assertion on the observable outcome so the test does
  not depend on lock internals.
- AC-7 exercises the launch guard through its documented hook interface —
  subprocess with stdin JSON, per the repository convention — against a
  journal this helper has just written. It is the downstream-convergence
  evidence for FR4; it does not re-test the guard's own rules.
- Standard library only; no third-party import anywhere in the new test file
  (NFR4).

## Out of Scope

- Deciding whether a task is an orphaned `launched` — task0003 owns every
  evidence rule, and this helper trusts its caller's decision while still
  re-checking the final event inside the lock.
- Reading the agent index, transcripts, or any current-session state.
- Widening the reason set beyond `orphaned`.
- Documentation updates and the plugin version bump (task0004 owns both).
