# Task Plan: task0006 — Bind the agent index evidence to the launch under recovery

## Goal

The orphan-recovery decision treats an `agents.jsonl` entry as evidence about
a task's CURRENT launch only when that entry can be bound to it, so a launch
whose index write was missed can never be judged by a previous launch's
recorded session identity.

## Provenance

- source: `review`
- source_ids: 1ca085e307eacd90
- review_round: 2

Review round 2 found that `recover-orphaned-task.py` feeds the LAST
`agents.jsonl` entry matching the task into the whole evidence pipeline
without correlating it with the launch the recovery is about. Index recording
is fail-open by contract (IMPLEMENTATION.md SC1: an absent or invalid session
identity omits the field, and an absent journal directory skips the append
entirely), so the newest entry for a task can describe an EARLIER launch. In
that state every evidence step can pass against a session that really has
ended while the launch actually under recovery is still running, and a
`failed(orphaned)` is appended for a live implementer — the double-launch
NFR1 and US2 exist to prevent.

## Design

### What is wrong today

The decision entry point's first evidence step accepts the last matching
`agents.jsonl` line unconditionally. Nothing in that line ties it to the
`launched` event the recovery is about, and the `launched` event itself
carries no session identity — so "the recorded identity is not the current
session and its transcript is quiet" can be true of a session that ended
BEFORE the launch under recovery even started.

### The binding rule

IMPLEMENTATION.md D7 pins the rule and the tolerance; this task implements it
and does not restate it. In flow terms:

- A new step runs immediately after "an agent index entry exists for the
  task" and BEFORE the entry's session identity is read, so an entry that is
  not evidence about this launch never has its contents trusted.
- It compares the entry's own `at` against the `at` of the LAST `launched`
  journal event recorded for the task, admitting the entry only when it is
  not older than that instant by more than D7's tolerance.
- Failure ends the run as `residual` with the SC6 reason code
  `stale-agent-entry`: no journal write, no helper invocation, no file opened
  outside the resolved transcripts directory — identical in every observable
  respect to the other residual paths.
- Data that cannot be compared at all (a missing, non-string or unparsable
  `at` on either side) is a binding FAILURE, not a pass. This is the
  Error-handling policy of IMPLEMENTATION.md's Conventions applied unchanged:
  doubt never produces a write.
- The step does not apply when the journal records no `launched` event for
  the task at all. No recovery can result from such a journal — the existing
  journal pre-check ends that run as `journal-not-launched` or
  `noop_terminal` — so applying the step there would only relabel an existing
  outcome.

### Documentation

`implement-phase.md`'s I.2.b Orphan recovery block is the single owning
section for the evidence order (IMPLEMENTATION.md Conventions, NFR7). The new
condition and its reason code are added there, in the position the pipeline
actually runs them, with the contract citation pointing at IMPLEMENTATION.md
SC3 / SC6 / D7. No other document states the rule; `workflow-schema.md` and
`em-workflow/README.md` are not touched, because neither carries the evidence
order.

### Version bump

Files under `em-workflow/` change, so `.claude/rules/core-plugin-version-bump.md`
applies: both manifests move to the same new version. This is the carve-out
IMPLEMENTATION.md's "Version bump ownership" convention now records — task0004
owned the bump for the implement round and is merged; this task owns it for
this rework round.

## Test Notes

- AC-1 through AC-6 are unit-level, built the way
  `tests/test_recover_orphaned_task.py` already builds fixtures: a temporary
  directory holding the journal, the agent index and an injected
  `--transcripts-dir`, plus the stub helper implementing SC2's outcome
  contract. Keep the stale case's two `launched` instants far apart (an hour
  is enough) so the assertion is about the rule, not about the tolerance.
- AC-4's boundary pair is the test that keeps the tolerance honest: write the
  admitted and the rejected case as one parameterised pair so a later change
  to the constant cannot silently pass only one of them.
- AC-5 is a no-regression property. Do not rewrite the existing residual
  cases; run them as they are, and add the new ones alongside. An existing
  case whose expected reason code has to change would mean the binding step
  was placed wrongly — treat that as a failure of AC-6, not as a fixture to
  update.
- AC-7 and AC-8 are the same assertion from both sides: the prose and the
  verbatim constants must move together in this one change, exactly as the
  IMPLEMENTATION.md risk table requires.
- AC-9 needs no new test module — `tests/test_plugin_version_parity.py`
  already asserts parity and baseline advancement over both manifests.
- The journal byte-identity assertions read the file's bytes before and after
  the invocation; comparing parsed events would hide a partial line.

## Out of Scope

- Recording any session identity on the `launched` journal event, or any
  other change to what `queue_launch_guard.py` writes. That is a different
  evidence source than FR2 specifies and would require a SPEC change.
- Changing `queue_agent_index.py`, its fail-open discipline, or the SC1 entry
  shape. The fail-open behaviour is the premise this task defends against,
  not a defect to remove.
- Widening or renaming any other SC6 reason code, or changing the outcome
  vocabulary of either helper.
- Changing SC2 (`journal-append-failed.py`) or its in-lock replay, which
  remains the authoritative terminal check.
- Any change to `workflow-schema.md`, `em-workflow/README.md` or the
  Supporting-cast journal bullet: none of them carries the evidence order.
