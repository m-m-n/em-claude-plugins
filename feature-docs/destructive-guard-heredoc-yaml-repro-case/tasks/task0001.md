# Task Plan: task0001 — Pin the reported heredoc reproduction in the destructive-guard expectation suite

## Goal

The reported reproduction command — a quoted-delimiter heredoc that writes a
YAML file with cat and only quotes the text `git reset --hard` in its body —
is fixed in the destructive-guard expectation suite as an allow case, next to
a contrast deny case that runs a real `git reset --hard` after the heredoc,
and the whole suite passes against the in-tree guard.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3

## Scope

### Files to Modify
- `em-workflow/hooks/tests/destructive-guard-cases.json` — add the FR1 allow case and the FR3 deny case
- `em-workflow/hooks/destructive-guard.py` — changed only when the FR1 case fails against the current guard (FR2); left byte-identical otherwise

## Design

### Reproduction command (test data, used verbatim)

The FR1 case's command is the reported command, character for character. It
consists of five lines joined by single line feeds, with no line feed after
the last line (the same form as the existing multi-line heredoc cases):

1. `cat > /tmp/example.yaml <<'YAML'`
2. `description: |`
3. Two ASCII spaces, then ``実測: `rm -rf tmp/$X` は main deny → 本ブランチ ask、``
4. Two ASCII spaces, then `` `rm -rf tmp/$X; git reset --hard HEAD~1` も main deny → ask。 ``
5. `YAML`

The backticks and `$X` in lines 3 and 4 are literal text: the delimiter is
quoted, so the shell expands nothing in the body. In the case file the line
feeds are written as JSON escapes and the Japanese text and the arrow stay
literal, the same way existing cases are encoded.

The FR3 case's command is the reproduction command above, followed by one
line feed and the line `git reset --hard HEAD~1`.

### Case form

- Both new cases use the three-element form (decision, label, command) with no
  fourth element: no working directory and no `CLAUDE_BATCH` (FR1).
- Each label is a Japanese label written in the style of the existing labels:
  it states the shape and the expected outcome, and the two labels differ from
  each other and from every existing label (NFR2).
- Both cases are placed among the existing cases that write a heredoc with cat
  and mention `git reset --hard` in the body. Placement does not affect the
  runner; it keeps related cases together.
- The project rule for this suite is `.claude/rules/hook-tests.md`: cases are
  added before any guard fix, and existing deny / ask cases are never removed.

### Processing flow

1. Add the two cases to the case file, leaving every existing case unchanged.
2. Run the runner against the in-tree guard (its default target).
3. Branch on the result for the two new cases:
   - a. Both report ok: the guard is not changed (FR2, SPEC assumption A1).
   - b. The FR1 case reports FAIL: first locate why the guard reads this body
     as commands (the report suspects the git reset --hard check is applied
     to a heredoc body that the rm -rf handling already skips), then change
     the guard so that the body of a heredoc whose delimiter is quoted and
     whose destination is cat redirecting to a file is not read as commands
     (FR2). Limits on the change:
     - Only the lines strictly between the heredoc operator line and its
       terminator line are excluded; lines after the terminator stay judged
       as commands (TM-1).
     - The exclusion does not extend to an unquoted delimiter (SPEC
       assumption A3), nor to a heredoc whose destination is an interpreter,
       a pipe into an interpreter, or a destination the guard cannot resolve
       (SPEC assumption A2, FR4) (TM-2).
     - No existing case changes its result.
   - c. The FR1 case reports ok but the FR3 case reports FAIL: this
     contradicts SPEC assumption A1, and FR2 forbids changing the guard while
     the FR1 case passes. Stop and report it as a plan deviation instead of
     changing the guard.
4. Feed the FR3 command to the guard directly, as a Bash tool payload on
   standard input, and read its permission decision reason: it begins with the
   rule tag `[destructive-guard/git-reset-hard]` (TS-2). The runner compares
   decisions only, so this tag check is a one-off direct invocation; the
   runner itself is not changed.
5. Run the runner over the whole suite again and confirm the result of AC-5.

## Test Notes

- The expectation suite is this task's test. Adding the two cases first and
  running the runner is the red/green step: a FAIL on the FR1 case is the red
  state that step 3b turns green; ok on both cases means the in-tree guard
  already satisfies FR1 to FR3.
- AC-3's reason-tag check and AC-4's comparison with the base commit are
  one-off checks run during the task (a direct guard invocation, and a
  comparison of the parsed case list at the base commit with the current
  one). They add no new test file and do not change the runner.
- AC-7 is checked from the list of files the task's commits change.
- When the guard is changed (step 3b), also run the project test command
  `python3 em-workflow/hooks/tests/run-destructive-guard.py && python3 -m unittest discover -s tests`,
  since other tests may load the guard.
- Run each suite once, as a normal foreground command; nothing here needs load
  or repetition.

## Out of Scope

- Changing the runner `run-destructive-guard.py`.
- New cases or behaviour changes for the unquoted-delimiter form (SPEC
  assumption A3) or for heredocs fed to an interpreter (SPEC assumption A2).
- Inspecting or refreshing an installed copy of the hook in the plugin cache
  (the suspected origin of the reported deny in SPEC assumption A1).
- Any plugin version change.
- Changes to other guard rules beyond what step 3b requires.
