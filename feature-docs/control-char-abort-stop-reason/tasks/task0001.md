# Task Plan: task0001 — Bind the Step I.2.a control-character stop to stop-condition-3 and pin it with a document test

## Goal

The "Precedence rule:" paragraph of
`em-workflow/references/batch-terminal-line.md` adds a named exception to the
`stop-condition-3` row's current-run exclusion. The exception states that the
batch stop raised by the Control-character check of Step I.2.a binds to
`stop-condition-3` (`step_needs_intervention`), not to `unmapped_stop`. A new
document test module pins that binding and the preserved exclusion.

### Document edit

Placement:
- Append the new text to the end of the existing "Precedence rule:"
  paragraph. Start it on a new line directly after the line that ends
  "keep their binding to `docs_commit_conflict_aborted` alone.", and before
  the blank line that closes the paragraph.
- Introduce no blank line (NFR1). Do not reword, move or delete any existing
  line of the paragraph, so the file's diff is added lines only (FR2 "not as a
  rewording of it", NFR2).
- Why the end of the paragraph: the restriction sentence ("Correspondingly,
  the `stop-condition-3` row's meaning binds ...") and the collision passage
  after it ("The one such collision: ...") stay next to each other. "such"
  keeps its referent, and every existing pin on order and anchors still holds.

Content: the appended text states all of the following.
1. It is a named exception to the `stop-condition-3` row's current-run
   exclusion stated earlier in the same paragraph. It refers to that
   exclusion and does not reword it (FR2).
2. The stop it covers: the batch stop raised by the Control-character check
   of Step I.2.a in `references/implement-phase.md`. It cites the document,
   step and check name and does not restate the check's rules.
3. Why no other row binds the stop: in the current run, the check writes
   `implement: failed` / `failed_kind: decision`. This is the pair notation
   the paragraph already uses for this write. The stop has no phase-specific
   row of its own, and control returns through develop's stop condition 3
   (FR1).
4. The binding: the stop binds to the `stop-condition-3` row,
   `step_needs_intervention`, and not to `unmapped_stop` (FR1).
5. Confinement: the exception covers this one stop only. It is not a general
   rule for other current-run routes that write `implement: failed` /
   `failed_kind: decision` (SPEC A2).

Constraints on the appended text:
- Do not use the phrase "`failed_kind` reads `decision`". That phrase is the
  anchor of the existing restriction, so name the write with the pair notation.
- `unmapped_stop` appears only in the negated binding. The paragraph never
  states an affirmative binding to `unmapped_stop`.
- Do not name `no-work-required`. Do not use the retired phrases "no
  phase-specific row covers" or "all three leave a step's status `failed`".
- Leave the exit-4 binding alone. Do not claim that the exception applies when
  the stop's terminal status commit exhausts `commit-docs.sh` exit-4 recovery.
  That case keeps `docs_commit_conflict_aborted` under the existing sentence
  (SPEC A3).
- Change no coverage-table row, no reason code, and no other paragraph or
  section of the file. This includes the `step_needs_intervention` Meaning
  cell, the Stop point coverage introduction and the Fallback rule (NFR3,
  SPEC A1). Do not edit `references/implement-phase.md`.

### Document test module

Reading and slicing:
- Read `em-workflow/references/batch-terminal-line.md` relative to the test
  module's own file. The repository root is the parent of `tests/`.
- Paragraph slicer: from the "Precedence rule:" label to the next blank line,
  the same slicing as the existing modules that slice this paragraph. It
  yields empty text when the label is absent, so assertions fail cleanly.
- Normalizer: collapse whitespace runs to one space before phrase matching.
  The blank-line guard reads the raw paragraph.

Matchers. Each takes paragraph text and raises an assertion failure when its
statement is missing.
- Binding matcher (FR1). The normalized paragraph:
  - names the Control-character check, Step I.2.a and develop's stop
    condition 3
  - binds that stop to `stop-condition-3` / `step_needs_intervention` through
    a phrase only the new text contains
  - carries the negated `unmapped_stop` binding
  - contains no affirmative binding to `unmapped_stop`
- Exception matcher (FR2): the full exclusion anchor "binds a stop at Step B's
  entry evaluation that reads a `failed` / `needs_update` status no route of
  the current run produced" is present. After it comes a phrase, found only in
  the new text, that marks the control-character binding as an exception to
  that exclusion.

Structural guards. These are regression invariants that already held before
the edit.
- Blank-line guard (NFR1): the raw paragraph is non-empty and contains no
  blank line.
- Coverage-table guard (NFR3): the `## Stop point coverage` table has exactly
  fourteen data rows. No row's stop-point key names the control-character
  check.

Negative proofs:
- Keep a verbatim pre-change paragraph constant: the "Precedence rule:"
  paragraph copied byte-for-byte from `batch-terminal-line.md` at this task's
  starting commit, before the edit. Never paraphrase or reconstruct it.
- Non-vacuity guard on the constant:
  - it begins with the "Precedence rule:" label
  - it carries "phase-specific stop point takes precedence over the generic",
    "no route of the current run produced" and "confined to that one
    collision"
  - it contains no blank line
  - it does not name the Control-character check
- The binding matcher and the exception matcher each raise an assertion
  failure on the constant.
- Each structural guard rejects a forged sample derived from the live text:
  the paragraph with a blank line inserted, and the table with a
  control-character row added. Each guard also accepts the unforged
  pre-change text, because its invariant predates the edit.
- How this task reads SPEC AC3's "each of its matchers fails against the
  verbatim pre-change paragraph": it applies to the matchers that assert the
  new statements (binding and exception). The structural guards of SPEC TS4
  assert invariants the pre-change text already meets. The forged samples
  above prove them non-vacuous instead.

## Test Notes

- Mapping: AC-1 and AC-2 run the binding and exception matchers on the live
  document. AC-3 is the negative-proof and non-vacuity classes. AC-4 is the
  structural guards and their forged-sample proofs. AC-5 is the full-suite
  run. AC-6 is a change-set criterion: it is checked by inspecting the diff
  (VERIFICATION.md TS-6), not by a unit test.
- Vacuity traps: the pre-change paragraph already contains all of these:
  - `stop-condition-3`
  - `step_needs_intervention` ("see the `step_needs_intervention` row above")
  - "Step I.2.a" ("Step I.2.a launch")
  - `implement: failed` / `failed_kind: decision`
  - the word "exception" ("abort terminal-commit exception")

  A matcher keyed on any one of these alone passes vacuously. Key each
  matcher on text that only the new statement contains, such as the check's
  name, develop's stop condition 3, `unmapped_stop`, and the exception
  phrase.
- TDD red step: write the module first. Before the edit, the live paragraph
  equals the pre-change paragraph, so the binding and exception matchers fail
  and the structural guards pass.
- `tests/test_failed_kind_batch_docs.py` checks that the first
  "`failed_kind` reads `decision`" in its slice comes after the exclusion
  anchor. End placement and the pair notation keep that true.
  `tests/test_canonical_worktree_path_docs.py` pins the unchanged Step I.2.a
  paragraph of `implement-phase.md`.
