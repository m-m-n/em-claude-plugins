# Task Plan: task0001 — static resolution of literal variable assignments in the destructive-guard hook

## Goal

The destructive-guard hook resolves plain literal `VAR=value` assignments made
in the command string it is judging and feeds the resolved literal into every
target-path judgment, so a delete or write reached through such a variable gets
exactly the verdict the literal path would get — no weaker, no stronger.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/hooks/destructive-guard.py` — the resolution stage (collection,
  scope identity, token substitution) and the wiring of resolved text into the
  target-path judgments.
- `em-workflow/hooks/tests/destructive-guard-cases.json` — new expectation

## Design

Cross-task decisions (pipeline layers, fail-closed policy, rule-identifier
reuse, expectation-case discipline, verification commands, judgment parity) are
in IMPLEMENTATION.md and are not restated here.

### A. Assignment collection

- **Precondition**: the statement stream the hook already produces for one
  command string. No filesystem access, no subprocess, no shell.
- **Postcondition**: a mapping from variable name to one literal value, plus
  the set of names excluded because they carry more than one assignment.
- **Qualifying shape**: a statement whose entire content is a single
  name-then-equals-then-value word, where the name is an ordinary shell
  variable name and the value is one token once the lexer has already resolved
  quoting.
- **Non-qualifying shapes**, each left out of the map (FR5):
  - the same word used as a prefix to a command in the same statement — the
    shell expands that command's own words before the assignment takes effect,
    so treating it as resolved would contradict shell semantics;
  - an assignment introduced by a command word (the export builtin, or any
    other command that takes assignments as arguments);
  - a value that is not a single token;
  - a value that itself references another variable — resolution is
    single-stage, with no chaining.
- **Multiplicity rule** (FR6): a name assigned two or more times anywhere in
  the command string is dropped from the map entirely and remembered as
  reassigned, so the unresolvable reason can carry the rewrite hint (item F).

### B. Scope identity

- Every collected assignment and every use site carries an identity for the
  nesting context it came from. A reference resolves only when the assignment's
  identity and the use site's identity are the same (FR7).
- Contexts that must yield a different identity from the enclosing one:
  a subshell group; a shell word's `-c` payload and the equivalent payload
  forms the hook already re-queues (the eval form and the here-string form); a
  command-substitution body; a here-doc body re-queued as script; and each
  element of a pipeline.
- **Fail-closed rule**: when the identity of a statement cannot be established
  with certainty — including the lexer's parse-failure fallback path, where
  per-token provenance is unavailable — treat it as its own distinct identity,
  so nothing resolves across it.
- The set of statements the hook yields, and their order, must not change; the
  identity travels alongside them (NFR6).

### C. Target-token resolution

- **Precondition**: one target token, the map from item A, and the scope
  identity of the statement the token came from. Pure text handling, no I/O.
- **Behaviour**: replace every reference of a mapped name — both the bare form
  and the braced form — with that name's literal value. References to unmapped
  names are left exactly as written.
- **Postcondition**: the token counts as resolved only when the resulting text
  contains no dynamic construct at all: no glob metacharacter, no command
  substitution in either spelling, and no remaining variable reference. When
  resolved, the resulting text is what the target-path judgments see for that
  token. When not resolved, the original token text is used and every existing
  judgment behaves exactly as before (NFR2).

### D. Consumption points (FR3)

Resolved text must reach **both** judgments that inspect a target path, not
only the delete one:

- the recursive-delete judgment — its root/home test, its scratch-area
  allowance, and its denial branch including the replacement-command
  suggestion, which is built from the resolved text (FR4);
- the write-target judgment — the candidate set it assembles from the
  statement's own words, its redirect targets and its destination flags is
  resolved before the Claude-Code-config test and the session-transcript test
  run against it.

### E. Judgment parity

A resolved token is judged on the same path, with the same text, as the same
literal written directly in the command. No normalization, expansion or lookup
is introduced on the resolved path that a literally-written token would not
also receive.

### F. Reassignment hint (FR6)

When a reference stays unresolvable because its name was assigned more than
once, the unresolvable reason states — in Japanese, alongside the existing
wording — that assigning the two values to separate variables makes the command
resolvable, so the calling agent can rewrite and retry.

### G. Cost shape (NFR4)

Collection is one linear pass over the statements the hook already produces.
Nothing re-lexes the command string per target, and no new expansion loop is
introduced; the existing cap on payload expansion continues to bound the
statement stream itself.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A standalone literal assignment of a scratch-area path followed, at
      the same nesting level, by a recursive delete through that variable is
      allowed. An expectation entry for it exists in the case list.
      (FR1, FR2, FR3, FR7 — TS-1)
- [ ] AC-2: The same shape aimed at a path outside the scratch area is denied
      under rule `rm-recursive`, and its reason carries the replacement-command
      suggestion built from the resolved path — not from the unexpanded
      variable reference. (FR2, FR3, FR4 — TS-2)
- [ ] AC-3: A resolved value that is the bare home shorthand, and one that is
      the filesystem root, are each denied under rule `rm-root`.
      (FR2, FR3 — TS-8)
- [ ] AC-4: A resolved value flowing into a write target under Claude Code's
      own configuration asks under rule `self-modification`; one naming a
      session transcript file is denied under rule `transcript-write`.
      (FR3 — TS-9, TS-10)
- [ ] AC-5: Each unresolvable form keeps its pre-change ask under rule
      `rm-unresolvable` — a command-prefix assignment, an assignment separated
      from its use by a subshell, an assignment separated from its use by a
      shell `-c` payload, and a name assigned twice — and the twice-assigned
      case's reason contains the split-the-variables hint.
      (FR5, FR6, FR7 — TS-3, TS-4, TS-5)
- [ ] AC-6: A value that still contains a glob metacharacter after
      substitution, and one that still contains a command substitution, each

- [ ] AC-7: `python3 em-workflow/hooks/tests/run-destructive-guard.py` exits 0

- [ ] AC-8: The resolution path adds no filesystem access, path realization,
      subprocess or shell invocation, and no import beyond the standard library

      already-produced statements. (NFR1, NFR4, NFR5)

## Test Notes

- **Order** (the project's hook-test rule): add the new expectation entries
  first and record the red run — the false-positive entry must fail before the
  resolution stage exists — then implement until the suite is green.
- **What the case list can and cannot check**: the runner compares the verdict
  only. The rule identifier and the reason substrings named in AC-2 and AC-5
  are checked by invoking the hook directly with a Bash tool payload and
  reading the emitted reason, whose leading bracketed segment carries the rule
  identifier. Record both the case-list run and these direct invocations in the
  task's test record.
- **Additional edge cases worth an entry or a direct check**, beyond the
  scenarios above:
  - a mapped reference embedded in a larger token, where the surrounding text
    is literal and the result is still fully static — must resolve;
  - a token holding both a mapped and an unmapped reference — must stay
    unresolved;
  - an assignment in one pipeline element used in another — must stay
    unresolved;
  - a value carrying a trailing separator, and a value that is the home
    shorthand followed by a path — both judged as the identical literal is;
  - a command that assigns and then only reads through the variable (no write,
    no delete) — must stay allowed, with no new judgment triggered.
- **Determinism** (NFR3): run the suite twice and confirm identical output; the
  resolution stage must not depend on ordering that varies between runs.
- **Not split into two tasks on purpose**: the resolution stage and its
  consumption points live in the same file, and a second task editing that file
  would conflict on merge without buying parallelism. The eight criteria above
  are therefore carried by one task rather than split.

## Out of Scope

- Multi-stage or chained resolution, export-form assignments, and any value
  coming from the parent process environment.
- Redefining the scratch-area allowance, the Claude-Code-config pattern, the
  session-transcript pattern or the dynamic-construct pattern (NFR6).
- Modifying the hook test runner, adding a new test module, or changing the
  three-element expectation-entry format.
- The plugin version manifests — task0002 owns those; do not edit them here.
- Introducing a new rule identifier, or restating any existing reason text
  beyond the added hint.
- Any behaviour of the hook unrelated to target-path judgment (git checks,
  external-operation checks, bypass detection, permission checks).
