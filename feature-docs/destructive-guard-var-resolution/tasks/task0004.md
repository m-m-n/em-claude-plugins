## Goal

The resolution layer's reach is narrowed to the text it actually substitutes
into: every other text a check judges is the text the hook judged before this
feature existed, so a command carrying no usable assignment — including a
command carrying no variable at all — receives its pre-feature verdict.
Alongside that narrowing, the shapes that bind a name without being recordable
as a value stop leaving a stale literal in the map.

## Design

Cross-task decisions — the pipeline layers and their allowed direction, the
fail-closed policy, rule-identifier reuse, the additions-only expectation-case
discipline, the two verification commands, and D4 judgment parity — are in
IMPLEMENTATION.md and are not restated here. This task keeps them, with the
one narrowing item D records explicitly. It introduces no new rule identifier
and redefines none of the four pattern constants (NFR6).

The whole task is one property. Review round 2 measured ten command strings
against the hook at `workflow.implement.base_commit`; nine moved in an
unintended direction, and two of those nine contain no variable at all. That
is the shape of the defect: machinery built for resolution is deciding
outcomes for text resolution never touched.

> **P**: the text a check judges differs from the text the hook at
> `workflow.implement.base_commit` would have handed that same check ONLY when
> a resolved value was substituted into it. Statement splitting, word
> boundaries, the containment decision on text nothing was substituted into,
> and the text a reason quotes are all pre-resolution behaviour, unchanged.

P is not a new requirement; it is NFR6 restated at the granularity the findings
need, and it is the property the previous round's approach — making the layer
more capable — kept breaking. Where an item below has a choice between widening
the layer and returning a decision to the pre-resolution path, it takes the
pre-resolution path.

### A. Scope delimiters are delimiters only when the lexer says so

The parenthesis handling that opens and closes a subshell scope compares
segment text, and the token type it compares is a string subclass, so a
parenthesis a user wrote inside a quoted or escaped word opens or closes a
scope exactly as an operator would.

- **Precondition**: a segment is treated as a scope delimiter only when the
  lexer's own operator-provenance marker says it is one — the same contract the
  redirection splitting already honours. The carve-out for punctuation fused to
  an adjacent word carries the same condition.
- On the parse-failure fallback path, where no provenance exists, no
  parenthesis is a scope boundary at all: that path yields the statements it
  yielded before this feature, one identity each.
- **Required outcomes, both directions**: detection that base performed on
  parenthesis-bearing commands is performed again — the file-search delete with
  escaped grouping parentheses, and the force push whose first argument is a
  quoted parenthesis, are denied by their own rules as they were at base. And
  an unclosed parenthesis inside a quoted word no longer splits the rest of the
  command into a foreign scope, so an assignment followed by such a word and
  then a delete resolves as it did before the word appeared.

### B. Substitution placeholders never leave the collector

Folding a command substitution into a placeholder is a device for reading
assignments; it currently reaches the text every judgment reads and the text
every reason quotes.

- The placeholder-bearing text is an input to assignment collection only. Each
  check receives the statement text it received at base, and a reason quotes
  the command as the user wrote it.
- **Required outcomes**: a delete whose target is a bare command substitution
  keeps its base allow; a delete whose target is a command substitution
  followed by a path segment keeps its base deny; and a reason for a delete
  through a command substitution names no identifier that is absent from the
  command string as written (the reason exists so its reader can rewrite the
  command, and an invented name misdirects that rewrite).
- The provenance the placeholder carried — "this value was never a literal" —
  is still required by task0003's item D. Carrying it beside the token rather
  than inside the judged text satisfies both.

### C. The unresolvable gate is decided before any containment decision

Lexical normalization collapses parent references without knowing what an
unexpanded component would have expanded to, so a dynamic target can be
normalized into the scratch area and never reach the gate that would have
asked about it.

- The dynamic/unresolvable determination for a target runs first. A target
  still carrying an unexpanded reference, a glob component or a substitution
  after the resolution step is decided by that gate, on the raw text, exactly
  as at base — normalization is not consulted for it at all.
- **Required outcome**: a delete whose path contains an unexpanded reference
  followed by enough parent references to climb out of the named tree stays an
  `rm-unresolvable` ask, in the reference, glob and home-shorthand spellings.
  A lexical count of segments never decides containment for a path whose real
  depth is unknown.

### D. Containment on unsubstituted text is the pre-resolution decision

Round 1 replaced the scratch-area decision's raw prefix test with a decision
taken on normalized text at path-component boundaries, and applied it to every
target. On text nothing was substituted into, that is a change to existing
behaviour (NFR6), and round 2 measured its cost: the scratch roots themselves
written in directory form, and ordinary build-output directories whose names
merely begin with a scratch name, all became denials.

- A target token nothing was substituted into is handed to the scratch-area
  decision as raw text, and that decision is the pre-resolution one. Nothing
  about the SAFE_DELETE, SELF_CONFIG, TRANSCRIPT or DYNAMIC patterns changes
  (NFR6): what changes is only which text the existing pattern is applied to,
  back to what it was.
- A target token a resolved value was substituted into keeps round 1's
  treatment — home-form expansion, lexical collapse of parent and current
  references, containment decided at path-component boundaries — because
  TS-19 states that property of a resolved target and the fail-open it closes
  is a round-1 finding. Normalization preserves the directory form: a value
  whose spelling ends in a separator is still a directory when the containment
  decision reads it.
- **Narrowing of IMPLEMENTATION.md D4, recorded here rather than silently**:
  D4 asks that a resolved token be judged as the identical literal would be.
  After this item the two agree everywhere except on a resolved value that a
  component-boundary decision refuses and a raw prefix test would have
  accepted, where the resolved side is the stricter one. The asymmetry is
  one-directional by construction — resolution can make a verdict stricter,
  never weaker (NFR2) — and it is confined to the containment decision. No
  other treatment is provenance-dependent.
- **Required outcomes**: every literal delete round 2 measured moving from
  allow to deny is allowed again — the scratch roots in directory form, and
  the build-output names that begin with a scratch name. A resolved value in
  directory form naming a scratch root is allowed. The resolved-side
  containment cases round 1 pinned still hold.

### E. Anything that can bind a name invalidates it

Recording a value and counting a binding are still decided by the same
narrow shape test in two places, so a binding written in any other shape is
invisible to both and a stale first value survives.

- **Recording stays as narrow as it is** (FR5): only a statement whose whole
  content is one bare `NAME=VALUE` word contributes a value.
- **Invalidation is wider, and is decided per token rather than per first
  token**: a statement whose leading token is not an assignment is still
  scanned, and every token in it matching an assignment shape invalidates that
  name. This covers a reassignment fused into a compound statement — after a
  conditional keyword, inside a loop body, inside a brace group, or behind an
  assignment prefix on another command.
- **Name-binding words are recognised wherever they sit in the statement**, not
  only as its first token: the loop and selection constructs bind the
  identifier that follows them, the option-parsing builtin binds its name
  argument, and the line- and array-reading builtins bind every name they are
  given. `unset` joins the binding words and removes the name.
- **A second assignment invalidates even when its value is unrecordable**: a
  value containing a variable reference, a substitution or an arithmetic
  expansion is not recorded, but the binding is still counted, so the earlier
  literal is dropped. This is the asymmetry the findings measured — one branch
  counts before it declines, the other declines before it counts — and both
  branches must count.
- Everything task0003's item B already listed stays: the command-word
  assignment forms, the append form, the formatted-output builtin's
  assign-to-variable option, and the two forms that invalidate the whole map
  from their own position onward.
- **Required outcomes**: the reassignment cases round 2 measured — fused into a
  conditional statement, carrying a chained value, self-referential, and
  followed by `unset`, `for` or a reading builtin — all return to the verdict
  the command has when the first value is not applied. The verdict does not
  depend on whether the statements were separated by `;` or by a newline
  (NFR3): a counting rule that fires for one spelling and not the other is not
  a counting rule.

### F. One place applies resolution, one place numbers statements

- Resolution is applied once, where a statement's arguments are produced, and
  the checks that consume resolved text are named in exactly one place in the
  file. FR3 fixes that set to the recursive-delete check and the write-target
  check; every other check reads the statement's own text, and the single
  declaration is what makes that a decision rather than an oversight.
- A check outside the declared set therefore returns its base verdict for a
  command that supplies its argument through a variable — that is P applied to
  the wiring question, and it is what keeps this item inside FR3 rather than
  widening it.
- The statement's ordinal is carried with the statement, from the same place
  that assigns its scope identity. No second enumeration re-derives it. Two
  independent enumerations agreeing by coincidence is a fail-open when they
  stop agreeing: an assignment written after its use would be read as
  preceding it.

### G. Resolved text is bounded, and the bound fails closed

Substituting a value of length V at R reference sites builds V×R characters
with no ceiling, and the hook is a synchronous PreToolUse check on every Bash
call with a 10-second timeout: past roughly 110KB of command the hook is
killed and no verdict is emitted at all — the one failure mode that is neither
allow, ask nor deny.

- Resolved text carries an explicit length ceiling. Exceeding it is not an
  error and not a denial: the token is simply not resolved, so the
  pre-resolution judgment path runs on it and the pre-resolution verdict stands
  (NFR2).
- The ceiling is a constant in the file, stated with the reason it exists, so
  the next reader can see what it protects.
- The constant-factor scan reductions the round's performance nit lists
  (repeated regular-expression passes over the same statements, tokens and
  argument lists) are permitted where they serve this budget and are not
  otherwise required — the reviewer records them as a borderline nit against a
  linear bound that already holds.

## Test Notes

- **Order** (the project's hook-test rule): add every expectation entry first
  and record the red run, then implement until the suite is green. Most of the
  entries this task adds record an allow that is currently a deny or an ask, so
  the red run is what distinguishes a real narrowing from a change that only
  relabels. The entries for the two restored denials (the parenthesis-bearing
  detections) start red in the other direction and must not be satisfied by
  weakening anything else.
- **AC-8's comparison is mechanical, not a judgement call**: obtain each
  pre-change verdict by running the same string through the hook as it stood at
  `workflow.implement.base_commit`, and record both verdicts in the task's test
  record so the parity claim is auditable rather than asserted. The round's
  own spot-check table is the minimum command set for that ledger.
- **What the case list cannot check**: the runner compares the verdict only.
  The rule identifiers named in AC-1, AC-3 and AC-4, and the reason content in
  AC-5, are checked by invoking the hook directly with a Bash tool payload and
  reading the emitted reason, whose leading bracketed segment carries the rule
  identifier (IMPLEMENTATION.md D3). Record those invocations too.
- **AC-6 is a measurement, not an inspection**: record the four numbers (base
  and current, at both sizes) in the test record. The point of the ceiling is
  that a command large enough to exceed it still produces a verdict; include
  one over-ceiling command in the expectation entries so the fail-closed path
  is exercised rather than argued.
- **False-positive budget**: this hook's false positives end an unattended run
  on the spot, so every tightening item E introduces needs a companion entry
  proving the ordinary shape it resembles still passes — a single assignment
  followed by a delete at the same level still allows; a statement mentioning a
  reading builtin for an unrelated name still leaves the target's name
  resolvable; an assignment followed by a conditional command still resolves.
- **If an item flips a pre-existing entry**, the pre-existing entry wins: it is
  evidence about a shape someone already relied on. Narrow the change until
  every pre-existing entry passes, and record which shape forced the narrowing.
  This applies with particular force to item D, whose whole subject is not
  moving verdicts that were never this feature's business.
- **Determinism** (NFR3): run the suite twice and confirm identical output.
  AC-4's separator-spelling requirement is part of the same property — a
  verdict that depends on how a command was punctuated is not deterministic in
  any sense the caller can use.
- **Not split into smaller tasks on purpose**: all fourteen findings name the
  one hook file, and IMPLEMENTATION.md's shared-component row makes that file's
  single writer a contract, so a split would produce conflicting edits to the
  same functions with no parallelism to show for it. The eight criteria are
  above the usual size guide for that reason and not because the work is eight
  separable pieces: items A through G all answer the same question, which text
  a check is entitled to judge.

## Out of Scope

- Redefining the SAFE_DELETE, SELF_CONFIG, TRANSCRIPT or DYNAMIC patterns
  (NFR6), including adding separator-suffixed alternatives to the scratch-area
  pattern. Item D changes which text the existing pattern reads, never the
  pattern.
- Tightening the scratch-area allowance for text nothing was substituted into.
  IMPLEMENTATION.md's open question records prefix-only matching as a
  pre-existing property this feature preserves deliberately; tightening it is a
  separate change with its own false-positive budget, and this round is the
  bill for having tightened it inside this one.
- Widening the set of checks that consume resolved text beyond FR3's two.
  Item F declares the set; it does not extend it.
- Multi-stage or chained resolution, values from the parent environment, and
  any dynamic evaluation. A name the resolver cannot settle stays unresolved.
- Introducing a new rule identifier, or rewording an existing reason beyond
  what item B's placeholder removal forces.
- Modifying the hook test runner, adding a new test module, or changing the
  three-element expectation-entry format.
- The plugin version manifests — task0002 owns those, and the feature ships as
  one release at 0.1.57. If a further bump is wanted, that is a separate task.
- Any behaviour of the hook unrelated to the text a check judges: git checks,
  external-operation checks, bypass detection and permission checks keep their
  base behaviour by item F, and are not otherwise touched.
