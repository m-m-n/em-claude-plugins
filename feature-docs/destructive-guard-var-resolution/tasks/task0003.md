## Goal

The resolution stage substitutes a value into a target only when that value is
the one the shell itself would use at that point, and the substituted text is
then judged with the same treatment a literal spelling of the same path would
receive — so resolution can no longer turn a pre-resolution ask or deny into an
allow, and no longer manufactures a deny out of a value the shell never builds.

## Design

Cross-task decisions (pipeline layers and their allowed direction, the
fail-closed policy, rule-identifier reuse, the additions-only expectation-case
discipline, the two verification commands, and D4 judgment parity) are in
IMPLEMENTATION.md and are not restated here. This task keeps every one of them;
in particular it introduces no new rule identifier and redefines none of the
four pattern constants (NFR6).

The whole task is one property, stated once and then broken into the five
places that currently break it:

> **P**: a reference is replaced only by the value the shell would use at that
> point, and replaced text is judged exactly as the same text written literally
> would be judged.

### A. Which assignments may be used at all (execution-effect model)

Today's collection walks every statement of the command string with no notion
of when — or whether — each one runs, so a value can be applied at a point the
shell never reached with it.

- **Precondition**: the statement stream the hook already produces, one linear
  pass, no filesystem, subprocess or shell (NFR1, NFR4).
- An assignment may be used at a use site only when all three hold:
  1. **It precedes the use site.** Statements carry an ordinal within their own
     scope; an assignment whose ordinal is not lower than the use site's is not
     applicable. Ordinals are comparable only among statements sharing a scope
     identity — a cross-scope pair is already refused by item C, so no ordering
     question arises between scopes.
  2. **It is unconditional.** An assignment statement introduced by a
     conditional separator (`&&` or `||`) may or may not run and is therefore
     never applicable. A statement introduced by a sequential separator, a
     newline, or the start of its scope is unconditional. The conditional test
     is about the separator PRECEDING the assignment, not the one following it:
     an assignment that always runs and is followed by a conditional command
     stays applicable.
  3. **It runs in the same shell.** A statement whose own execution is handed
     to another shell — a background job, a pipeline element, a subshell group,
     a re-queued payload — is governed by item C.
- **Fail-closed default**: an assignment whose applicability cannot be settled
  from the statement stream is not applicable. Not-applicable means the token
  is left as written and the pre-resolution judgment path runs on it (NFR2).

### B. What invalidates a name (collection / invalidation asymmetry)

Today the same shape test decides both "record this value" and "count this
binding", so any binding written in a shape the recorder does not accept is
also invisible to the counter, and a stale first value survives a rebinding.

- **Recording** stays as narrow as it is today (FR5): only a statement whose
  whole content is one bare `NAME=VALUE` word contributes a value.
- **Invalidation is deliberately wider**: any statement that could bind the
  name at all removes that name from the map, whether or not its value was
  recordable. At minimum this covers the assignment forms introduced by a
  command word (`export`, `declare`, `typeset`, `local`, `readonly`), the
  append form, the input-reading builtins that name a variable (the
  line-reading builtin and the array-reading builtins), the formatted-output
  builtin's assign-to-variable option, and the two forms that can bind
  anything at all (the string-evaluating builtin and sourcing a file) — the
  last two invalidate the entire map from their own position onward, since
  what they bind is not statically knowable.
- The existing multiplicity rule (FR6) and its rewrite hint stay: a name bound
  two or more times is dropped and remembered as reassigned, and the
  unresolvable reason keeps the split-the-variables hint. A name invalidated by
  one of the wider forms above is dropped the same way; whether it also carries
  the reassignment hint is the implementer's choice, provided the hint is never
  misleading.

### C. Where an assignment's effect stops (scope boundaries)

FR7's boundary is currently one-sided and can be lost entirely:

- **Every element of a pipeline** gets its own identity, the first element
  included. Today only what follows a pipe gets a fresh one, so the head
  element's assignments leak into the enclosing shell.
- **A statement terminated as a background job** runs in its own shell: it gets
  its own identity, and neither the background statement's assignments nor the
  enclosing shell's ordering carry across.
- **A subshell group's delimiters are delimiters, not words.** The opening
  parenthesis is not part of the first statement's token list, and the closing
  one is not part of the last statement's — the group's boundary is tracked by
  counting delimiter occurrences across the token stream rather than by testing
  whether a statement's first or last token IS a parenthesis. Two consequences
  are required outcomes, not side effects: a closing parenthesis fused with an
  adjacent redirection operator still closes the group, and a group written
  with `;` separators behaves identically to the same group written with
  newlines.
- Everything item B of task0001's plan already listed as its own identity — the
  shell `-c` payload and the equivalent re-queued payload forms, a
  command-substitution body, a here-doc body re-queued as script — stays that
  way, as does the parse-failure fallback's one-identity-per-statement rule.
- The set of statements the hook yields, and their order, still must not change
  (NFR6); only the identity and ordinal travelling with them may.

### D. Values that were never literal (dynamic provenance)

Command substitutions are flattened to whitespace before lexing, which erases
the evidence that a value is dynamic; what survives can look like a bare
assignment with an empty or truncated literal value.

- An assignment whose right-hand side contained a command substitution
  (either spelling), an arithmetic expansion, or a process substitution is not
  recordable, and its name is invalidated per item B.
- The mechanism must make that provenance survive the flattening — either by
  keeping the provenance alongside the token, or by flattening substitutions
  into a placeholder the existing dynamic-construct test already recognises, so
  the value can never be mistaken for a literal.
- This is the finding's false-positive half as much as its miss half: the
  capture-a-scratch-directory-then-delete-it idiom must land on the
  pre-resolution ask, not on a denial built from a value the shell never
  produced.

### E. How resolved text is judged (post-substitution treatment)

Substituted text is currently handed to the judgments with none of the
treatment the same text would have received had it been written literally.

1. **Word splitting.** A substituted value containing whitespace names more
   than one target once the shell is done with it. Such a token is not treated
   as one resolved target: either it stays unresolved (pre-resolution verdict),
   or every whitespace-separated word becomes an independent target and each is
   judged on its own. Preserving the reference's quoting provenance and
   splitting only unquoted references is permitted but not required; the
   required outcome is that the first word can never carry the whole token.
2. **Empty result.** A substitution producing an empty or whitespace-only text
   is not a resolution: the token stays unresolved. Independently of that, the
   replacement-command suggestion never runs on an empty path.
3. **Path normalization and containment.** Before the root/home test and the
   scratch-area allowance run, a target is put through the same lexical
   normalization the write-target path already applies — home-form expansion
   and lexical collapse of parent and current references, still with no
   filesystem access (NFR1). Containment in the scratch area is decided at path
   component boundaries, so a leading component that merely starts with a
   scratch-area name as a string prefix is not inside it. Per D4 this treatment
   is applied to the target text irrespective of whether it came from a literal
   or from a substitution, so parity with the literal spelling is preserved
   rather than traded away.
4. **Flags.** Arguments are resolved before they are separated into flags and
   targets, so a flag supplied through a variable is seen as a flag and the
   recursive-delete path runs.

### F. Reason text

Reasons stay Japanese and keep their existing rule identifiers and wording. The
only changes permitted here are the ones the items above force: no suggestion
for an empty path, and a suggestion built from the same text the judgment
actually used.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: An assignment that the shell would not have executed with that
      value at the use site never resolves the reference. Covering, each with
      its own expectation entry: the assignment written after the delete, an
      assignment reached only through a short-circuit that does not run, and an
      assignment terminated as a background job. Each command keeps its
      pre-resolution verdict — the home-directory form stays a `rm-root` deny,
      the unknown-target form stays an `rm-unresolvable` ask.
      (FR1, FR7, NFR2 — TS-13)
- [ ] AC-2: A name bound a second time through the export / declare / typeset /
      local / readonly assignment forms, the append form, the line- or
      array-reading builtins, or the formatted-output builtin's
      assign-to-variable option is excluded from resolution exactly as a
      twice-written bare assignment is, and the delete through it is an
      `rm-unresolvable` ask; a string-evaluating builtin or a sourced file
      invalidates every name from its own position onward.
      (FR1, FR5, FR6, NFR2 — TS-14)
- [ ] AC-3: An assignment whose right-hand side contains a command substitution
      is never used as a literal value: the capture-a-scratch-directory-then-
      delete-it idiom is an `rm-unresolvable` ask, and its reason carries no
      replacement-command suggestion. (FR1, FR2, NFR2 — TS-15)
- [ ] AC-4: Assignments do not cross a scope boundary in either direction —
      from the first pipeline element outward, from a later pipeline element
      outward, and from a background job outward — and a subshell group is
      recognised as one under both punctuation spellings: the closing
      parenthesis fused with a redirection operator still closes the group, and
      a group written with `;` separators produces the same verdict as the same
      group written with newlines, both for a use inside the group and for a
      use after it. (FR7, NFR2 — TS-16, TS-17)
- [ ] AC-5: Substituted text is judged as the shell's own words: a value
      containing whitespace is never allowed on the strength of its first word,
      a value substituting to empty or whitespace stays unresolved and produces
      no suggestion naming the current directory, and a recursive flag supplied
      through a variable makes the delete recursive.
      (FR2, FR3, FR4, NFR2 — TS-18, TS-20, TS-21)
- [ ] AC-6: A target that begins inside a scratch root and climbs out of it
      with parent references is not allowed, and a target whose leading
      component merely starts with a scratch-area name as a string prefix is
      not treated as inside the scratch area; the denial reason's replacement
      command names the same path the judgment used. The four pattern
      definitions are unchanged and no new rule identifier exists.
      (FR3, FR4, NFR1, NFR6 — TS-19)
- [ ] AC-7: `python3 em-workflow/hooks/tests/run-destructive-guard.py` exits 0
      with every pre-existing entry present, byte-identical and still passing —
      including the entries task0001 added — the new entries added in the fixed
      three-element form, and `python3 -m unittest discover -s tests` also
      exits 0. (FR8, NFR3, NFR6 — TS-11)
- [ ] AC-8: For every command string this task adds an entry for, the verdict
      is no weaker than the verdict the hook at `workflow.implement.base_commit`
      gives the same string: an ask may become a deny or stay, and never
      becomes an allow. Collection remains one pass over the statements the
      hook already produces, with no filesystem access, path realization,
      subprocess or shell invocation, and no import beyond the standard library
      modules the file already uses. (NFR1, NFR2, NFR4, NFR5)

## Test Notes

- **Order** (the project's hook-test rule): add the new expectation entries
  first and record the red run — every entry for a miss the round-1 findings
  demonstrated must fail before the fix — then implement until the suite is
  green. The entries for AC-3's and AC-5's false-positive halves also start red
  (they record a deny that must become an ask), which is what distinguishes a
  real fix from a fix that only tightens.
- **AC-8's comparison is mechanical, not a judgement call**: the pre-change
  verdict for each new command string is obtained by running the same string
  through the hook as it stood at the implement base commit. Record both
  verdicts in the task's test record so the no-weakening direction is auditable
  rather than asserted.
- **What the case list cannot check**: the runner compares the verdict only.
  The rule identifiers and reason contents named in AC-1, AC-2, AC-3, AC-5 and
  AC-6 are checked by invoking the hook directly with a Bash tool payload and
  reading the emitted reason, whose leading bracketed segment carries the rule
  identifier (IMPLEMENTATION.md D3). Record those invocations too.
- **False-positive budget**: this hook's false positives end an unattended run
  on the spot, so each tightening in items A, B and E needs a companion entry
  proving the ordinary shape it resembles still passes — an assignment followed
  by a delete at the same level still allows; a conditional command AFTER an
  unconditional assignment still resolves; a value with a trailing separator,
  and one that is the home shorthand followed by a path, are still judged as
  the identical literal is.
- **If item E.3's component-boundary containment flips a pre-existing entry**,
  the pre-existing entry wins: it is evidence about a shape someone already
  relied on. Narrow the containment change until every pre-existing entry
  passes again, and record which shape forced the narrowing in the test record.
- **Determinism** (NFR3): run the suite twice and confirm identical output.
  Ordinals and scope identities must not depend on anything that varies between
  runs, and the statement stream's own order must be unchanged from today.
- **Not split into smaller tasks on purpose**: all fifteen findings are in one
  file, and IMPLEMENTATION.md's shared-component row makes that file's single
  writer a contract. Items A through E also share one decision surface — what
  counts as resolved — so splitting them would produce conflicting edits to the
  same functions with no parallelism to show for it.

## Out of Scope

- Multi-stage or chained resolution, and any value coming from the parent
  process environment. A name the resolver cannot settle stays unresolved; the
  findings ask for fewer resolutions here, not more.
- Redefining the scratch-area allowance, the Claude-Code-config pattern, the
  session-transcript pattern or the dynamic-construct pattern (NFR6). Item E.3
  changes what text those patterns are applied to and where a match must end —
  never the patterns themselves.
- Introducing a new rule identifier, or rewording an existing reason beyond
  what item F permits.
- Modifying the hook test runner, adding a new test module, or changing the
  three-element expectation-entry format.
- The plugin version manifests — task0002 owns those. If the version needs
  another bump for this change, that is a separate task, not an edit here.
- Any behaviour of the hook unrelated to target-path judgment (git checks,
  external-operation checks, bypass detection, permission checks).
- Executing a shell, or any dynamic evaluation, to decide what a value is. The
  answer to "the analysis cannot tell" is always the pre-resolution verdict.
