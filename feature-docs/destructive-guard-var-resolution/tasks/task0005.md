## Goal

The destructive-guard hook stops carrying a variable-resolution layer: for
every input it answers exactly as the hook at
`1fdb27fe51de6d20e9812027d3aee603cb584173` answers — same verdict, same rule
identifier — while the expectation entries this feature contributed are kept
wherever they record what that hook actually does, so the three rounds' work
survives as detection coverage rather than as behaviour.

## Requirements

FR8, NFR5

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/hooks/destructive-guard.py` — the whole judgment path returns to
  the behaviour of the named commit. Restoring that commit's content outright
  is an acceptable way to get there; whatever is kept, the file's answers are
  that commit's answers.
- `em-workflow/hooks/tests/destructive-guard-cases.json` — entries whose
  recorded expectation disagrees with what the restored hook produces are
  removed; every other entry stays.

## Design

### Why this task is a withdrawal rather than a repair

Three review rounds produced 15, 14 and 15 findings against the same layer. The
third round's own measurement is the decisive input: eleven command strings run
against both the base hook and the merged hook, ten of which moved. Five of
those ten contain no variable at all — `rm -rf dist/*` and
`rm -rf node_modules/*` moved allow→ask (an ask is demoted to deny under
unattended execution, so those are run-stopping false positives on the most
ordinary build shape there is), and `rm -rf <(echo x) …` and
`git push <(echo x) --force …` moved deny→allow (a real target the guard no
longer sees). The one statement of repeated binding words measured 9.85s at
44KB against a 10-second hook timeout, versus 0.05s on base — past roughly
46KB the hook emits no verdict at all.

FR1-FR7 and NFR1/NFR2/NFR3/NFR4/NFR6 are recorded as `status: excluded` in
`workflow.yaml` with the reason. This task implements what remains: FR8 (the
expectation entries, per `.claude/rules/hook-tests.md`) and NFR5 (single file,
standard library only). FR9's version value is already merged and is not this
task's to touch.

### A. Behavioural equivalence is the definition of done, and it is measured

The criterion is not "the resolution code is gone" — it is "the answers are the
base commit's answers". Those are different claims, and only the second one is
checkable.

- **Postcondition**: for every command string in the differential corpus below,
  the restored hook's verdict and the bracketed rule identifier in its reason
  equal the verdict and rule identifier the hook at
  `1fdb27fe51de6d20e9812027d3aee603cb584173` produces for the same string, both
  sides run on the same machine in the same session.
- **The corpus** is fixed, not sampled: every command string in the expectation
  list as this task leaves it; every command string quoted in a finding or a
  spot-check table of review rounds 1, 2 and 3, including round 3's eleven
  verified inputs; and the two large shapes round 3 timed.
- Equivalence includes *producing an answer at all*: a shape on which the merged
  hook exceeds the hook timeout has no verdict to compare, so it is a
  difference, not a match.
- The comparison is mechanical — two runs and a diff of the recorded pairs.
  Reading the diff and judging it equivalent is not the check, and does not
  substitute for it.

### B. What the expectation list keeps, and what it loses

The entries added across task0001, task0003 and task0004 are the only part of
this feature worth keeping. They cover command shapes nobody had a case for,
and several of them are the exact regressions review found — the scratch root
in directory form, the build-output name that merely begins with a scratch
name, the glob delete under a scratch root, the file search whose grouping
parentheses are escaped, the force push whose first argument is a quoted
parenthesis.

- **Retention test, applied per entry and decided by measurement**: run the
  entry's command string through the hook at
  `1fdb27fe51de6d20e9812027d3aee603cb584173`. If the entry's recorded
  expectation equals that hook's verdict, the entry stays, unedited. Otherwise
  it goes. No entry's recorded expectation is rewritten to make it stay — an
  edited expectation is a new claim, and this task adds no claims.
- **The 58 pre-existing entries are not subject to that test**: they are present
  and byte-identical afterwards, exactly as the project's hook-test rule
  requires. The rule's "既存の deny / ask ケースは消さない" is what this task
  answers to; the entries it removes are ones this same feature added days ago,
  not entries anyone has ever relied on.
- **Entries that cannot survive by construction**: any entry that asserts the
  verdict of a value reached through a variable, and any entry that exists to
  pin the split-the-variables reason hint. Those describe a layer that no
  longer exists; keeping them would require keeping the layer.
- **Recorded deviation from IMPLEMENTATION.md's additions-only discipline**:
  that convention was written for a feature that only adds behaviour. This task
  removes entries, and the entries it removes are all this feature's own. The
  convention stands unchanged for the 58 pre-existing entries, which is the
  part of it that protects anything.

### C. Cost returns to the base shape

The layer's cost was superlinear in command length in three separate places.
Nothing replaces them; the restored hook's cost on the round's measured shapes
is the base hook's cost. This is stated as an outcome so that a restoration
that accidentally keeps a scan is caught by a number rather than by reading.

### D. Nothing else moves

The version manifests are task0002's and already read 0.1.57. The plugin
content still differs from 0.1.56 because the retained expectation entries are
part of what ships, so the merged bump remains correct and no further bump is
needed. The four pattern constants, the rule identifiers, the reason wording
and the test runner are all whatever the base commit has them be.

## Test Notes

- **The differential harness is the task's main instrument, and it is
  throwaway.** Obtain the base hook by extracting the file at
  `1fdb27fe51de6d20e9812027d3aee603cb584173` to a scratch location outside the
  repository, feed each corpus string to both copies as a Bash tool payload,
  and record `(input, base verdict, base rule, current verdict, current rule)`.
  Nothing about the harness is committed: the repository's own runner and case
  format are unchanged, and no new test module is added.
- **Order of work.** Prune the case list only after the retention test has been
  run for every added entry and its result recorded — deciding by reading which
  entries "look like resolution entries" is how a regression case gets deleted
  by mistake. The removals and the hook restoration land together; the suite is
  green at the end of the task, not at the end of each edit.
- **The suite alone does not establish AC-1.** The runner compares the verdict
  only, and the corpus is wider than the case list. Rule identifiers come from
  the leading bracketed segment of the emitted reason (IMPLEMENTATION.md D3).
- **The two directions this task can fail in are not symmetric, and both need
  evidence.** Restoring too little leaves a false positive that ends an
  unattended run; restoring in a way that also drops a retained regression entry
  loses detection the three rounds bought. AC-3's per-entry verdict pairs are
  what separates the two after the fact.
- **Determinism** is checked by the doubled run in AC-4; the differential
  ledger is recorded once but its corpus rows must be reproducible from the
  recorded inputs alone.
- **Not split into smaller tasks**: all fifteen findings name one file, the
  withdrawal is one atomic behavioural change, and the case-list pruning is only
  decidable against the restored hook. A split would leave the suite red between
  two merges.

## Out of Scope

- Any further attempt to repair, narrow or re-scope the resolution layer. The
  requirements it implemented are excluded in `workflow.yaml`; this task does
  not reintroduce them under another shape.
- Rewriting any pre-existing entry's expectation, deleting any pre-existing
  entry, or editing a retained added entry's command string or label.
- Changing the expectation-entry format, the test runner, or adding a test
  module.
- The plugin version manifests, and any further version bump. task0002 owns
  0.1.57 and the feature ships at that value.
- Redefining the scratch-area, Claude-Code-config, session-transcript or
  dynamic-construct patterns, introducing a rule identifier, or rewording a
  reason. The base commit's definitions are the target, not a starting point
  for improvement.
- Tightening any behaviour the base hook has, including the prefix-only
  scratch-area match. A shape that was a false positive at the base commit
  stays one; addressing it is a separate feature with its own budget.
- `SPEC.md` and `REQUIREMENTS.md`: the withdrawn requirements are excluded, not
  rewritten.
