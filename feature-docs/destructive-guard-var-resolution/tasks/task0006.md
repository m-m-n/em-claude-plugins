## Goal

Every entry this feature added to
`em-workflow/hooks/tests/destructive-guard-cases.json` says which judgment path
produces its verdict, marks in its own text every verdict that records a known
guard gap rather than an endorsed policy, and sits in the base revision's
layout so the diff against the base revision reads as an append. No verdict
moves and the hook is not touched.

## Design

### A. What this task is, and what it must not become

Review round 4 established the ground state by measurement, not by reading:
the hook is byte-identical to `1fdb27fe51de6d20e9812027d3aee603cb584173`, the
two suites are green (132/132 and 2830/2830), and the 58 pre-existing entries
survive in order as parsed triples. Nothing in the current diff changes what
the guard does at runtime.

All six round-4 findings are therefore about one thing: what the 73 retained
entries *assert*. The runner compares only the first element of an entry, so
the label is the only text a human ever sees when the suite speaks — and today
that text names a mechanism the feature withdrew. This task changes text and
layout in one data file. **Any edit that changes an entry's recorded verdict,
or the hook, falls outside it.**

### B. The judgment paths that actually produce these verdicts

The labels are rewritten against what the merged hook does, measured per entry.
Five paths account for every retained entry; the label names the one that
applies:

1. **Unresolvable dynamic target** — a `$X` / `${X}` / backtick / `$( )`
   fragment inside a delete target makes the recursive-delete check report the
   target as not statically decidable, and the hook asks under the
   `rm-unresolvable` rule. This is the path behind the large majority of the 70
   entries currently prefixed `変数解決:`; assignment tracking and scope
   analysis play no part in it, because neither exists in this hook.
2. **Root / home recursive delete** — the target text reaches the filesystem
   root or the home directory and the hook denies under `rm-root`.
3. **Recursive delete outside the scratch areas** — the target text is a
   concrete path outside the allowed roots and the hook denies under
   `rm-recursive`.
4. **Scratch-area allowance** — the target text matches one of the allowed
   deletion prefixes and the hook allows silently.
5. **Nothing this hook judges** — the command is not a form the hook inspects,
   or the delete carries no positional target at all after lexing, and the hook
   allows.

A label states the path and the property the entry pins. It never names a
resolution stage, an assignment map, a scope rule, a length ceiling or a reason
sentinel — none of those exist in the file under test.

### C. The three entries that claim machinery which is absent entirely

Three of the retained entries describe a check the code does not contain:

- the entry whose label calls its very long assignment token an over-ceiling
  *resolved value* — there is no such constant; what the command actually pins
  is that a kilobyte-scale token still reaches a verdict (path 1) rather than
  timing out;
- the entry whose label claims a reason-string sentinel is verified — the
  runner compares the verdict only and never sees a reason (IMPLEMENTATION.md
  D3); what its command actually pins is path 5 on a bare command substitution,
  which is a known gap (item D);
- the entry whose label says a resolution-exempt check does not consume
  resolved text — with no resolution there is no resolved text; what its
  command actually pins is that a delete-style flag passed to an unrelated tool
  is not a form this hook judges at all (path 5).

Each is either rewritten to state only the property it really pins, or removed
when it pins none. The choice is recorded per entry, so a later reader sees a
decision rather than an omission.

### D. Entries that contract a known hole, and how they must read

Fourteen retained entries record a verdict that follows from a gap in the
guard, not from a policy anyone chose:

- **Bare command substitution as the sole delete target** (2 entries:
  `rm -rf $(mktemp -d)`, `rm -rf $(cat list)`). The substitution is carved out
  into a separate segment, the outer delete reaches the check with zero
  positional targets, and the check returns early. The quoted spelling of the
  same command is judged and denies — so this is the lexer losing the target,
  not a decision about `mktemp`.
- **The trailing-slash spelling of a scratch root** (4 entries: `/tmp/`,
  `tmp/`, `.cache/`, `/var/tmp/`). Round 4 measured the counterpart: the same
  path without the trailing slash denies. One operation, two spellings, two
  verdicts.
- **The unanchored scratch-name prefix** (8 entries: `build-debug`, `dist-ssr`,
  `target-old`, `coverage.old`, `build-artifacts`, `dist-newstyle`,
  `coverage-old`, `node_modules_bak`). The allowance matches a prefix without
  requiring a path separator, which is also why `rm -rf targets` and
  `rm -rf build/../src` allow.

These fourteen stay, with their verdicts untouched: they are the false-positive
guards three review rounds bought, and deleting them would cost detection of
regressions on ordinary build shapes. What changes is that each label says
plainly that the verdict records an unfixed gap. The purpose is legibility
across time: when someone later anchors the prefix match or teaches the lexer
about bare substitutions, these entries flip, and the suite must read as
"the known gap closed" rather than as "a false positive came back".

The marker is a fixed string so it can be found mechanically rather than
recognised by tone: every such label contains `既知の穴(未修正)`.

### E. Paired counter-cases

An asymmetry is only visible when both sides are in the file. Seven entries are
appended so the suite itself shows the split:

- the quoted spelling of the bare-substitution form, beside the bare form;
- the no-trailing-slash spelling of each of the four scratch roots, beside its
  trailing-slash entry;
- `rm -rf targets` and `rm -rf build/../src`, beside the eight prefix entries,
  as the two shapes that ride the same unanchored match without being build
  output at all.

**Every appended entry's expectation is the verdict the merged hook is measured
to produce for that command string, recorded in the test record before the
entry is written.** No expectation is copied from a review finding's prose. A
finding's claim about a verdict is a claim; the harness output is the fact. An
appended entry whose measured verdict is an allow is written as an allow and
carries the known-gap marker of item D.

### F. Layout, and why the diff shape is part of the deliverable

The base revision holds one entry per line — a three-element array on a single
line. The retained work was committed as a whole-file pretty-print at one
element per line, which rewrites all 58 pre-existing lines and makes the diff
against the base revision unreadable as an append: nobody can see at a glance
which added entries survived task0005's pruning and which did not.

The file returns to the base layout, with this feature's entries appended in
that same form. The end state is that the diff against
`1fdb27fe51de6d20e9812027d3aee603cb584173` for this file contains additions
only, with one structural exception: the base file's final entry line has no
trailing comma, so continuing the list re-emits that one line with a comma
appended. That single line is the only permitted non-addition, and it differs
from its base form by exactly that comma.

Restoring the layout also restores the 58 pre-existing entries to their base
bytes, which is what task0005's AC-2 and VERIFICATION.md's manual check asked
for and what the reformat took away.

### G. Follow-up material — not this task's work

The gaps items D and E make visible are pre-existing base behaviour. They were
present before this feature started, review round 4 confirmed the hook is
byte-identical to base, and closing any of them changes what the guard allows
for every user of the plugin. They belong to a separate change with its own
false-positive budget, and are recorded here so the next reader has the list:

1. The scratch-area allowance matches on prefix without a path-separator
   anchor, so unrelated names that merely begin with an allowed name are
   allowed.
2. A delete whose only target is an unquoted command substitution reaches the
   check with no targets and returns early; the quoted spelling does not.
3. A target that begins inside a scratch root and climbs out with parent
   references is allowed on the same prefix match.
4. A scratch root with a trailing slash is allowed where the same root without
   one is denied.

IMPLEMENTATION.md's Open Questions already carries item 1 in the same terms;
this task adds nothing to that document and resolves none of the four.

## Test Notes

- **Measure first, write second.** The instrument is the same throwaway
  differential harness task0005 used: feed each command string to the hook as a
  tool payload and record the verdict together with the leading bracketed rule
  identifier of the reason (IMPLEMENTATION.md D3). Labels are written from that
  recording. Writing a label from the finding text, or from the entry's old
  label, is how a wrong claim survives a round that was called to remove one.
- **The runner does not check labels.** It compares the verdict only, so a green
  suite is evidence for AC-5 and AC-7 and for nothing else. AC-1 and AC-3 are
  checked mechanically by string search over the file (`変数解決` must not
  occur; `既知の穴(未修正)` must occur exactly on the entries items D and E
  name), and AC-2 / AC-4 by reading the test record beside the file.
- **AC-6 is checked on the diff, not on the file.** Compare the file against the
  base revision and count non-added lines; the expected count is zero or one.
  Reading the file and judging it "looks like the old format" is not the check.
- **Ordering inside the task.** Restore the layout first, then relabel, then
  append the measured pairs — a relabel done before the layout restore produces
  a diff nobody can review, which is the exact failure this task exists to undo.
- **Not split into smaller tasks.** All six findings name one file and one
  contract: what the retained entries assert. The label rewrite, the gap
  marking, the paired entries and the layout restore all land in the same file
  and are only verifiable together, against one measurement pass.
- **The suite must be green at the end of the task, not between edits.** A
  temporarily red suite mid-task is expected while entries are appended before
  their measurement is recorded; the ordering above avoids it.

## Out of Scope

- **Any change to `em-workflow/hooks/destructive-guard.py`.** The four
  weaknesses in item G are pre-existing base behaviour and stay exactly as they
  are. Anchoring the scratch-name prefix, teaching the lexer about bare command
  substitutions, denying the parent-reference escape and unifying the
  trailing-slash spelling are all follow-up material for a separate feature.
- Changing any recorded verdict, including "correcting" one of the fourteen
  known-gap entries to the verdict someone thinks the hook ought to give. The
  entries record what the hook does; a verdict change is a hook change wearing a
  data-file costume.
- Deleting, reordering or editing any of the 58 pre-existing entries. Their
  return to base bytes is a consequence of the layout restore, not an edit.
- Removing any of this feature's retained entries other than the ones AC-2
  explicitly permits, and in particular removing a known-gap entry instead of
  labelling it — that would delete a false-positive guard the earlier rounds
  bought.
- Changing the three-element entry format, the runner, or adding a test module.
- The plugin version manifests. task0002 merged `0.1.57` and the feature ships
  at that value; this task's change is part of the same unreleased feature, so
  no further bump is required by the project's version-bump rule.
- `SPEC.md` / `REQUIREMENTS.md` / `IMPLEMENTATION.md`. The withdrawn
  requirements stay excluded, and this task introduces no cross-task contract.
