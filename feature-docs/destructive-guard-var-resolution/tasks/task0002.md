# Task Plan: task0002 — plugin version bump to the next patch level

## Goal

Both plugin registries carry the em-workflow version `0.1.57`, so an installed
copy of the plugin picks up the changed hook instead of serving the cached
`0.1.56` files.

## Requirements

FR9

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — the plugin manifest's version
  value.
- `.claude-plugin/marketplace.json` — the version value of the marketplace
  entry whose plugin name is em-workflow.

## Design

The cross-task contract for this value (precondition, postcondition, and the
rule that no other task writes these files) is in IMPLEMENTATION.md's Shared
Components table and is not restated here.

Task-level details:

- The change is a data edit only: the single version value in each file. No
  other key, no formatting change, no reordering of the marketplace entry list.
- The marketplace entry is located by its plugin name. The entry list's order
  is not a contract, and one sibling entry carries no version key at all, so a
  positional or uniform-scan approach is wrong on both counts.
- The bump is a patch-level step, matching the project rule's guidance that a
  behaviour fix moves the patch component: `0.1.56` to `0.1.57`.
- Confirm the precondition before editing: both files must read `0.1.56` at the
  base revision. If either reads something else, stop and report it as a plan
  deviation rather than bumping from an assumed baseline.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The plugin manifest's version value reads exactly `0.1.57`.
- [ ] AC-2: The marketplace entry whose plugin name is em-workflow reads
      exactly `0.1.57`; the entry was located by name; no other entry gained,
      lost or changed a version key, and no other key in either file changed.
- [ ] AC-3: `python3 -m unittest discover -s tests` exits 0 — the repository's
      version-parity module reads both registries, requires them to agree, and
      requires the value to compare past its recorded baseline under
      component-wise numeric comparison.
- [ ] AC-4: `python3 em-workflow/scripts/check-plugin-invariants.py` against
      the repository root exits 0.

## Test Notes

- The postcondition already has an automated home: the repository's
  version-parity module covers agreement between the two registries and the
  past-baseline property, and it runs under the main component's test command.
  No new test module is added — the equivalent bump in the previous change to
  this hook added none either, and a second module pinned to this feature's own
  baseline would duplicate it.
- The red-then-green evidence for this task is the literal-value check of
  AC-1/AC-2: read both files before the edit (both `0.1.56`, so the criteria
  fail) and after (both `0.1.57`). Record both readings in the task's test
  record.
- Edge case to keep in mind while editing the marketplace file: the sibling
  plugin entry has no version key, so any change must not introduce one there.
- Reporting note for the completion summary: picking the new version up
  requires a Claude Code restart, per the project's version-bump rule.

## Out of Scope

- Any file under `em-workflow/hooks/` — task0001 owns the hook and its
  expectation cases.
- Bumping any other plugin's version, or editing the marketplace file's
  structure, descriptions or sources.
- Regenerating or reformatting either JSON file wholesale.
