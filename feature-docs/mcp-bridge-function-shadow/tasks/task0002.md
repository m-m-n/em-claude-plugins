# Task Plan: task0002 — Read the command word, env's child position and partly static words statically

## Goal

The notion-pair exclusion of the `--args-json` step is no longer kept, or its
call no longer missed, because a word is written in a form the guard can undo
statically. Three cases are covered. A notion call whose command name
`mcp-bridge` is written in ANSI-C quoting is still decided by the lift. A
notion call inside a `bash -c` payload reached through `env` by a path, after a
lone `-`, or after an assignment whose `=` is written in ANSI-C quoting is
still found and decided by the lift. `BASH_FUNC_`, `BASH_ALIASES` and
`BASH_CMDS` in the statically restorable part of a word that also holds an
expansion still lift the exclusion. Every reading this task adds applies only
on the notion-pair path. The `--args-json` decision for other pairs (which
statements become targets included) and `head()` for every other check stay
as they are (FR7).

## Design

### Origin

Review round 1 findings:

- 3d3e6afd38e8c4b3: a command name in ANSI-C quoting.
- 444c158592ba641c: environment-variable names in a word that also holds an
  expansion.
- 8ec945002f0cf118 and c0598deb75b9d2c7: env's child command position.

The four share one root cause. A word at or before command position, or a
word the lift matches by substring, is read in the text shlex leaves, not in
the text Bash passes on.

### Boundary (FR7)

- SPEC FR7 is read literally. For pairs other than the notion pair, the
  `--args-json` decision does not change. That includes which statements
  become targets.
- `head()`, `_skip_assignments_and_wrappers()`, `_deferral_head()` and the
  shell-payload extraction do not change. Every check other than the
  notion-pair path keeps its verdict.
- Each reading below is reached only where the notion-pair predicate
  (`_args_json_notion_pair()`) answers true for the statement it reads.

### Notion-path command word (finding 3d3e6afd38e8c4b3; FR1, FR5)

- Step 1 (Target) of `_mcp_bridge_args_json_chunks()` keeps its current
  reading first. When the command word `head()` returns is exactly
  `mcp-bridge`, nothing changes.
- When it is not, the command word is read with `_read_static_word()`. The
  statement goes on only when all of the following hold:
  - the outcome is Static and the restored text has the basename
    `mcp-bridge`;
  - the next word is `run`;
  - `_args_json_notion_pair()` answers true;
  - `_args_json_notion_lifted()` answers true.

  It then goes on to the flag reading (step 3) exactly like a lifted notion
  statement whose command word is plainly `mcp-bridge`.
- In every other case the statement is nothing to do, exactly as now:
  - a non-notion pair;
  - a notion pair that is not lifted;
  - a Not static or Unrestorable command word;
  - another basename.

  The Unrestorable outcome of the command word never sets the Unrestorable
  flag, so no command gets a new ask (`args-json-unrestorable`). This is the
  difference from the loop-3 attempt that was reverted.

### Notion-path env reading (findings 8ec945002f0cf118, c0598deb75b9d2c7; FR3, FR4, FR5)

A new reader, used only by the `--args-json` decision, reads the command
position of a statement that starts with env. `head()` and the skip loop
behind it are not changed and do not call it.

1. Name: a word whose statically restored text has the basename `env`
   (`/usr/bin/env`, `env`) is env.
2. Options: env's options are read the way the skip loop reads them: `--`
   ends them and is consumed, and the value-taking options of env take their
   value. A lone `-` also ends them and is consumed.
3. Assignments: after the options, every word whose statically restored text
   holds `=` is an assignment operand, whatever the name holds. A word that
   cannot be restored statically ends the assignments.
4. The first word after that is the child command.

The reader is used only for a statement whose `head()` command word is not
`mcp-bridge` and whose child command, read this way, differs from the word
`head()` returns (the forms `head()` misreads). It applies only when that
child is a shell taking a `-c` payload in a single static word, the payload
the shell-payload extraction would take if it had read that child.

The statements of that payload are read as a derived chunk whose enclosing
chunk is the statement's own chunk, so the lift's chain reaches the outer
chunk's words. For each `mcp-bridge run` statement of the payload that the
notion-pair predicate determines and the lift answers true for, the
decision queues what it would queue for a lifted notion statement (FR5):

- the decoded `command` strings;
- the candidate bodies.

Each is anchored at the payload word.

This route queues nothing for the following, which keep the verdict of the
hook before task0002:

- any other statement of the payload;
- a notion statement that is not lifted;
- a payload that is not a single static word.

`statements()` references no new name, and no name that holds `args_json`
(`TestStructure`).

### Partly static words in the shadow scan (finding 444c158592ba641c; FR1, FR3)

- `_args_json_shadow_scan()` is read only by the lift. It keeps its raw-text
  match and its whole-word restored match. It adds a match on the static runs
  of each word.
- A static run is a maximal run of parts of the word whose characters Bash
  passes on literally:
  - single-quote content;
  - double-quote content with no expansion;
  - a decodable ANSI-C quote;
  - unquoted literal characters.

  A run ends at every part that is not static or cannot be restored: an
  expansion, a substitution, a locale quote, or an ANSI-C quote that does not
  decode. Each run is restored on its own and matched by substring.
- The words matched on the runs are the two of
  `_ARGS_JSON_SHADOW_ENVIRONMENT_WORDS` and `BASH_CMDS`. These are the same
  words the whole-word restored match checks now.
- The following do not change: `_overrides_command_name()`, `override_seen`,
  the heredoc data decision, the masking stop and the shared vocabularies.

## Acceptance Criteria (MANDATORY)

Placeholders used below. Commands are shown as Bash receives them.

- `<notion call>`:
  `mcp-bridge run --mcp notion --tool notion-create-comment --args-json '{"command":"git branch -D example"}'`
- `<notion tail>`: the same text without its leading `mcp-bridge`.
- `<dc call>`:
  `mcp-bridge run --mcp desktop-commander --tool start_process --args-json '{"command":"git branch -D example"}'`
- `<dc tail>`: the same text without its leading `mcp-bridge`.
- `<inner notion>`: the `<notion call>` text inside a double-quoted `bash -c`
  argument with its inner `"` escaped, as in the existing TS-6 case.
- `<import>`: `'BASH_FUNC_mcp-bridge%%=() { :; }'`

The criteria:

  - `f() { :; }; $'mcp-bridge' <notion tail>`
