# Task Plan: task0001 — Place the closer of a `[[ ]]` conditional that holds a regex or an extended pattern by parenthesis depth

## Goal

`destructive-guard` no longer reads a `[[ ]]` conditional as uncertain only
because it holds a `=~` word or an extended-pattern prefix. After such a word
the closer is placed by counting the pattern's parentheses: a conditional whose
closer can be placed keeps the following canonical notion call `KIND_NOTHING`,
and one whose closer cannot be placed stays uncertain, so the call is inspected.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

  pattern by parenthesis depth and reports the parentheses it counted; the

## Design

### Root cause (as read at the base commit)

- `_unsettled()`, nested in `_args_json_conditional_step()`, is true for any
  word whose written form with line continuations removed is `=~`, and for any
  word ending in one of `?*+@!` that is followed (line continuations skipped)
  by `(`. The opener branch then reports the statement uncertain
  (`evaluates`), and the continuation branch (`was_open`) returns uncertain
  for such a word anywhere in the statement, after the closer included.
- Separately, `_args_json_nameref_scan()` splits each statement into simple
  commands at every unquoted parenthesis operator
  (`_args_json_command_boundary()`). The words inside a pattern's parentheses
  (`x` of `@(x)`, `ab` and `$` of `^(ab)$`) are then command names, outside
  the allow-list, so removing `_unsettled()` alone would still leave the
  AC-1 forms uncertain. FR4 is what makes them certain.

### Terms

- **Statement tokens**: WORDS, the statement's tokens as `lex_segments()`
  gives them, operator tokens included (not FLAT, which drops them).
- **Range**: in the statement that holds the opener, the tokens after the
  opener; in a continuation statement (WAS_OPEN true), the tokens from the
  first. The range ends at the closer, or at the end of the statement when it
  has none.
- **Pattern start**: a word of the range written exactly `=~`
  (`_args_json_word_source()`, no trailing carriage return); or a word whose
  written form, line continuations removed, ends in one of `?*+@!` and whose
  span is directly followed in the marked text by `(` (no line continuation
  between them).
- **Unsettled start**: a word of the range whose written form with line
  continuations removed is `=~` but which was written with a line
  continuation or carries a trailing carriage return; or a word ending in one
  of `?*+@!` that is followed by one or more line continuations and then `(`.
  These keep today's reading: the statement is uncertain (A3).
- **Counted parenthesis**: once a pattern start has been read in the range,
  each unquoted operator token of WORDS made only of parentheses (`(`, `)`,
  `((`, `))`, `)(`, `()`), up to the closer. It counts one step per
  character: `(` adds 1 to the depth, `)` takes 1 away. A quoted `"("` or an
  escaped `\(` is a word, never counted (FR5).
- **Closer**: a word written exactly `]]` with no trailing carriage return
  (as today). Before any pattern start, the first such word in the range is
  the closer; after a pattern start, the first such word at depth 0.

### Change 1: the depth reading in `_args_json_conditional_step()` (FR1, FR2, FR3, FR5)

The depth reading replaces `_unsettled()` and is applied the same way to the
statement that holds the opener and to a continuation statement. For one
statement, it walks the range in order:

1. Before a pattern start, nothing is counted and a parenthesis is not a
   counted parenthesis (the grouping parentheses of `[[ ( a == b ) && ... ]]`
   keep their reading).
2. An unsettled start makes the statement uncertain.
3. A pattern start begins the count at depth 0. A later pattern start in the
   same statement neither resets nor restarts it.
4. While counting:
   - a counted parenthesis changes the depth;
   - an operator token that holds a parenthesis together with any other
     character (for example a `)` fused with a redirection operator) makes the
     statement uncertain;
   - a depth below 0 makes the statement uncertain (A2, `[[ ( x =~ a ) ]]`).
5. The closer ends the range. No word after the closer is read by the depth
   reading, in either branch (so a `=~` written after the closer, as the
   target of a redirection, changes nothing).
6. At the end of a statement with no closer:
   - depth 1 or more makes the statement uncertain (FR2, `[[ x =~ (a ]]`, and
     `[[ x =~ (a|b) ]]`, which the lexer splits at `|`);
   - depth 0 leaves the conditional open, and the next statement starts with
     no count and depth 0.

Unchanged by this change:

- Opener detection through `_args_json_command_name_word()`, including the
  rule that a quoted or escaped opener makes the statement uncertain at once.
- The operator-word reading of `_ARGS_JSON_DOUBLE_BRACKET_WORDS`: in the
  opener statement, the words after the opener up to the closer (now the
  closer placed by depth); in a continuation statement, every word of the
  statement, as today. An operator word inside a pattern still makes the
  statement uncertain (A5).
- The `;` / lone `&` rule (`_args_json_separator_breaks_conditional()`) for a
  conditional still open, and the caller's end-of-chunk rule.

Result contract (signature unchanged):

- **Precondition**: as today (WORDS, COMMANDS split at every boundary, SEP,
  WAS_OPEN).
- **Postcondition**: (UNCERTAIN, OPEN, COUNTED).
  - UNCERTAIN: true when the depth reading or the unchanged readings above
    find the statement uncertain.
  - OPEN: as today, true when a conditional is open after the statement.
  - COUNTED: the counted parenthesis tokens of WORDS for this statement,
    identified by position in WORDS or by object identity, never by their
    text (every `(` token has the same text). Empty when no pattern start was
    read. The caller reads COUNTED only when UNCERTAIN is false.

Placement (NFR2): the depth reading is a function nested inside
`_args_json_conditional_step()`, as `_unsettled()` is today. SPEC's
Architecture places the new helper under `_args_json_conditional_step()`, and
NFR2 requires it to be reached only from `_args_json_nameref_scan()`. Nested
there, it has no module-level name and no caller but
`_args_json_conditional_step()`, whose only caller is
`_args_json_nameref_scan()`; its text is part of that function's source, which
the existing call-site, forbidden-name and no-decision tests read. Any
module-level function the change adds (for example one that builds the simple
commands of a statement) is referenced only inside
`_args_json_nameref_scan()`.

### Change 2: the simple-command split in `_args_json_nameref_scan()` (FR4)

- `_args_json_conditional_step()` still receives the simple commands split at
  every boundary, as today. The opener stands before any counted parenthesis,
  so its command-name position is unaffected.
- When `_args_json_conditional_step()` returns UNCERTAIN false and a non-empty
  COUNTED, the simple commands that the command-level reading
  (`_args_json_declares_nameref()`) reads for that statement are built again:
  a token derived from a counted parenthesis — the token itself, or each piece
  the fused-operator split (`_split_fused_closer_redirects()`) makes of it — is
  not a boundary and stays inside its simple command. Every other token keeps
  `_args_json_command_boundary()`'s answer.
- Effect: the words of `@(x)` and `^(ab)$` stay words of the `[[` command (or
  of the continuation's simple command), read by the `[[` rule of
  `_args_json_name_uncertain()` (operator words stay uncertain, A5) or by the
  rule for that command's first word (A6). Parentheses before a pattern
  start, before the opener, after the closer and in a statement without a
  conditional stay boundaries.
- The reading of the whole statement for a `{` / `}` argument word is
  unchanged.

### Docstrings (NFR4)

- `_args_json_conditional_step()`: the sentences stating that a word written
  exactly `=~` makes the conditional uncertain, and that a word ending in one
  of `?*+@!` followed by `(` does (8760-8766), are replaced by the depth rule
  above and the third result. Its source must not contain the strings
  `destructive-guard/` or `permissionDecision` (an existing test reads the
  whole source, docstring included).
- `_args_json_nameref_scan()`: item 4's statement that a `(` or `)` begins a
  new simple command gains the exception for the parentheses the conditional
  reading counted as a pattern's; item 5 states the depth rule briefly. Two
  existing tests pin this docstring:
  - it still names `_args_json_fd_variable_deferred()`,
    `_args_json_conditional_step()`, `_args_json_declares_nameref()`,
    `_args_json_has_brace_substitution()`,
    `_args_json_has_deferred_evaluation()` and `lex_segments()`;
  - it contains none of the whole words `declare`, `local`, `typeset`,
    `eval`, `source`, `trap`, `alias`, `mapfile`, `readarray`, `echo`,
    `mcp-bridge`, `printf` (so no example such as "the written source of a
    word", and no example command line).

### Test and case-table placement (constraints from existing tests)

- New forms go into a new test class. They are not added to the tuples of
  `TestSourceTextReadings` or `TestDbracketOpenerArithScan`, whose table
  checks look forms up by command string and require their own label prefix.
- Every new label starts with `dbracket-regex-settled`. No new label starts
  with `args-json-deferred-eval-bypass` (the count of labels starting with
  `args-json-deferred-eval-bypass TS-16:` or `TS-17:` stays at 30) or with
  `dbracket-opener-arith-scan` (that prefix's membership test stays as it is).
- Every new case's command is the array assignment
  `A=(json --mcp desktop-commander --tool start_process); `, then the form,
  then `; `, then the canonical notion call
  `mcp-bridge run --mcp notion --tool notion-create-comment --session "$SID" --args-json`
  with the payload whose `command` is `git branch -D example`. A deny case
  carries the fourth element with `rule` set to `git-branch-force-delete`; an
  allow case has three elements.
- No new command string repeats an existing case's command string or another
  new one (the existing tests key the table by command string).
- The case-table forms:
  - **allow**: `[[ x =~ a ]]`, `[[ version =~ ^v ]]`, `[[ a =~ b ]]`,
    `[[ x =~ ^(ab)$ ]]`, `[[ a == @(x) ]]`, `[[ a == ?(x) ]]`,
    `[[ a == *(x) ]]`, `[[ a == +(x) ]]`, `[[ a == !(x) ]]`,
    `[[ a == @(true) && true ]]`, `[[ a == b && true =~ ^(ab)$ ]]`,
    `[[ x == =~ ]]`, `[[ a =~ "(" ]]`;
  - **deny**: `[[ x =~ (]]) || true -eq 0 ]]`,
    `[[ a == @(]]) || true -eq 0 ]]`, `[[ x =~ (a|b) ]]`, `[[ x =~ (a ]]`,
    `[[ a == b && true == @(]]) || true -eq 0 ]]`, the form `[[ x =~ a ]]`
    with its `=~` written as `=`, a backslash, a newline and `~`, and the form
    `[[ a == @(x) ]]` with a backslash and a newline between `@` and `(`.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR2, FR4): for each of `[[ x =~ a ]]`, `[[ version =~ ^v ]]`,
  `[[ a =~ b ]]`, `[[ x =~ ^(ab)$ ]]`, `[[ a == @(x) ]]`, `[[ a == ?(x) ]]`,

  `[[ a == @(true) && true ]]`, `_args_json_nameref_scan()` returns false.
  The command made of the array assignment, the form, `; ` and the canonical

  `Spy(...).kinds()`, and the hook's decision on it is `allow`.
- [ ] AC-2 (FR2, TM-1): for `[[ x =~ (]]) || true -eq 0 ]]` and
  `[[ a == @(]]) || true -eq 0 ]]`, `_args_json_nameref_scan()` returns true,
  the AC-1 command shape gives `[KIND_INSPECTED]`, and the hook's decision is
  `deny` with the reason ID `git-branch-force-delete`.
- [ ] AC-3 (FR2, TM-1): for `[[ x =~ (a|b) ]]` and `[[ x =~ (a ]]`,
  `_args_json_nameref_scan()` returns true, the AC-1 command shape gives
  `[KIND_INSPECTED]`, and the hook's decision is `deny` with
  `git-branch-force-delete`. `_args_json_nameref_scan()` also returns true for
  `[[ ( x =~ a ) ]]` (depth below 0) and for `[[ x =~ (a)>b ]]` (a parenthesis
  fused with another operator character while counting).
- [ ] AC-4 (FR3, FR4, TM-1): for `[[ a == b && true =~ ^(ab)$ ]]`,
  `_args_json_nameref_scan()` returns false, the AC-1 command shape gives

  `[[ a == b && true == @(]]) || true -eq 0 ]]` it returns true, the command
  gives `[KIND_INSPECTED]` and the decision is `deny` with
  `git-branch-force-delete`. For `[[ a == b && true ]] >=~` it returns false

- [ ] AC-5 (FR4, FR5, TM-2): for `[[ x == =~ ]]` and `[[ a =~ "(" ]]`,
  `_args_json_nameref_scan()` returns false, the AC-1 command shape gives

  `[[ a =~ \( ]]`. For the two line-continuation deny forms of the case-table
  list it returns true, the command gives `[KIND_INSPECTED]` and the decision
  is `deny` with `git-branch-force-delete`. It returns true for `echo @(x)`

- [ ] AC-6 (FR6, NFR1): `destructive-guard-cases.json` gains the allow and

## Out of Scope

- Any change to `_ARGS_JSON_DOUBLE_BRACKET_WORDS`, the allow-list,
  `_args_json_declares_nameref()` or `_args_json_name_uncertain()`.

  (`[[ x =~ (a|b) ]]` stays uncertain).
- Settling a `=~` or an extended-pattern prefix written across a line
  continuation (A3).
- Narrowing the continuation statement's operator-word reading, which keeps
  scanning the whole statement.

- Editing or removing existing tests, existing case-table entries or their
  labels.
- Any change to the plugin version.
