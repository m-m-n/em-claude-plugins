# Task Plan: task0002 — Share the counted pattern parentheses with item 3 of the shadow scan, and pin the closer that touches a parenthesis

## Goal

The notion call after `[[ x =~ ^(ab)$ ]]` and after
`[[ a == b && true =~ ^(ab)$ ]]` keeps its exclusion through the whole hook:
item 3 of `_args_json_shadow_scan()` stops splitting a statement at the
parentheses the conditional reading counted as a pattern's, under a fail-safe
that keeps every other parenthesis a boundary. The rule that a `]]` touching a
pattern's parenthesis is no closer, already in the conditional reading, gets
its tests and case-table entries.

## Requirements

## Design

### State at the base of this task

- `_args_json_conditional_step()` returns (UNCERTAIN, OPEN, COUNTED) for one
  statement. COUNTED holds the parenthesis tokens of the statement's token
  list that it counted after a pattern start, identified by object identity,
  and is read only when UNCERTAIN is false. `_args_json_nameref_scan()` passes
  COUNTED to `_args_json_simple_commands()`, which keeps those tokens inside
  their simple command.
- Item 3 of `_args_json_shadow_scan()` splits each statement's tokens at every
  boundary of `_args_json_command_boundary()` (fused operators split first,
  the same split as `_args_json_simple_commands()` with no counted tokens) and
  passes each simple command to `_args_json_runs_string_as_code()`. For
  `^(ab)$` the `$` after the `)` begins a simple command whose name cannot be
  restored, so the scan reads true, the notion pair's exclusion is lifted and
  the notion call is inspected and denied (review round 1).
- After a pattern start, a `]]` that touches a `)` before it or a `(` after
  it, with no blank between, is no closer and makes the statement uncertain.
  This rule is in `_args_json_conditional_step()` already; no test and no
  case-table entry pins it.

### Change 1: item 3 of `_args_json_shadow_scan()` (FR7)

Terms:

- **Item 3 tokens**: for one statement, the token list item 3 splits today:
  the statement's tokens as the shadow scan's own lexing of the chunk gives
  them, before the unresolved-mark stripping that items 1 and 4 read.
- **Settled conditional**: a conditional whose closer the reading reaches with
  no statement read uncertain, from the statement that holds its opener
  through the statement that holds its closer.

Rules:

1. The conditional reading runs over the chunk's statements in order, the
   conditional closed before the first statement, the same way
   `_args_json_nameref_scan()` runs it. For each statement,
   `_args_json_conditional_step()` receives the item 3 tokens, the simple
   commands of those tokens split at every boundary, the statement's
   separator, and the open state the previous statement left.
2. A statement read uncertain stops the reading. That statement, every later
   statement of the chunk, and every earlier statement of the conditional
   still open at that point use no counted parentheses.
3. A statement read certain that leaves its conditional open keeps its
   counted parentheses pending. When a later statement read certain closes
   the conditional (OPEN false), the pending counted parentheses and that
   statement's own become usable; a statement that opens and closes its
   conditional itself makes its own usable at once. A conditional still open
   at the end of the chunk never makes its pending counted parentheses
   usable.
4. A statement with usable, non-empty counted parentheses is split by
   `_args_json_simple_commands()` given those counted tokens. Every other
   statement is split at every boundary, as today.
5. Each simple command goes to `_args_json_runs_string_as_code()`, unchanged.

Why this scope: `_args_json_nameref_scan()` answers true at its first
uncertain statement and for a conditional left open at the end of the chunk,
so its counted parentheses change its answer only inside a settled
conditional. Rules 2 and 3 give item 3 the same scope, so a parenthesis is
kept inside its simple command only where the reading has placed the whole
conditional that holds it (TM-3).

Constraints:

- **Same tokens**: the counted tokens are used only with the token objects of
  the same call. Nothing is taken from `_args_json_nameref_scan()`, its result
  or its cache, nor from another lexing of the chunk (FR7).
- **Placement (NFR2)**: the references to `_args_json_conditional_step()` and
  `_args_json_simple_commands()` stand directly in the body of
  `_args_json_shadow_scan()`, not inside a nested function and not inside a
  new module-level function: the call-site tests attribute a reference to the
  innermost enclosing function definition, and NFR2 allows only the two scans.
- **Mechanism**: the reading may run as a pass over the statements before the
  per-statement loop, or item 3's check of a pending statement may wait until
  its conditional settles or is abandoned. Either way the scan returns the
  same boolean, and a statement the lexer could not read still makes the scan
  true (item 5).
- **Unchanged**: items 1, 2, 4 and 5, the judgment of
  `_args_json_runs_string_as_code()`, `_args_json_notion_lifted()` and its
  cache (A8), and the conditional reading itself.

Effect: in `[[ x =~ ^(ab)$ ]]` the `ab` and the `$` stay words of the `[[`
command, so item 3 reads no unrestorable command name. In
`[[ a == @(eval) ]]` the `eval` is pattern text, as in Bash, and is no command
name (A7). Parentheses before a pattern start, before the opener, after the
closer, in a statement without a conditional, and in a conditional that is
not settled stay boundaries.

### Change 3: tests and case table (FR2, FR3, FR6, NFR1, NFR2)

Constraints from the existing tests:

- New tests and forms go into the existing class `TestDbracketRegexSettled`,
  this feature's own class. Its exact-set check compares the case table's
  `dbracket-regex-settled` entries with the forms the class lists, so every
  new entry is also listed in the class.
- Inside that class:
  - The two `$` forms leave the tuple that holds them as still inspected and
    join the allow forms (the opener form with the regex forms, the
    continuation form with the continuation forms), so the
    `[KIND_NOTHING]`, allow and case-table checks cover them. The comment
    stating that their notion call is still inspected is removed.
  - The three touching-closer forms of the case table join the deny forms.
    The existing line-continuation test reads the last two entries of the
    deny tuple; it keeps reading exactly the two line-continuation forms.
  - The call-site check of the functions this feature adds expects
    `_args_json_nameref_scan` and `_args_json_shadow_scan` for
    `_args_json_simple_commands`.
- Outside that class, only `test_the_readings_are_called_only_from_the_scan`
  (in `TestSourceTextReadings`) changes, as NFR1 allows: it expects both
  scans for `_args_json_conditional_step` and only `_args_json_nameref_scan`
  for `_args_json_fd_variable_deferred`. No other test outside the class is
  edited or removed.
- Every new label starts with `dbracket-regex-settled`. None starts with
  `args-json-deferred-eval-bypass` or `dbracket-opener-arith-scan`.
- Every new command is the array assignment
  `A=(json --mcp desktop-commander --tool start_process); `, then the form,
  then `; `, then the canonical notion call with `--session "$SID"` whose
  `--args-json` payload `command` is `git branch -D example`. A deny entry has
  the fourth element with `rule` set to `git-branch-force-delete`; an allow
  entry has three elements. No new command string repeats an existing one or
  another new one.
- Case-table additions:
  - **allow**: `[[ x =~ ^(ab)$ ]]`, `[[ a == b && true =~ ^(ab)$ ]]`;
  - **deny**: `[[ x =~ (x)]] || true -eq 0 ]]`,
    `[[ a == @(x)]] || true -eq 0 ]]`,
    `[[ a == b && true =~ (x)]] || true -eq 0 ]]`.
- The two existing `^(ab)c` entries stay as they are. No existing entry is
  removed or edited.
