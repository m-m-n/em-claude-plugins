# Task Plan: task0002 — TaskStop journal `failed` recorder hook

## Goal

Deliver a new fail-open hook that appends a `failed` journal event when an em-workflow
implementer is stopped through the stop tool, so that a subsequent `/em-workflow:develop`
re-entry treats the task as a retry rather than as in-flight.

## Requirements

FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

- `em-workflow/hooks/queue_taskstop_net.py` — the hook: fires after a stop-tool call,
  resolves the stopped agent to an em-workflow task, appends one `failed` journal event.
- `tests/test_queue_taskstop_net.py` — subprocess-driven unit tests for the hook.

### Files to Modify

- `em-workflow/hooks/hooks.json` — add this hook's registration entry only.

## Design

### Responsibility

One job: make a deliberate stop visible in the journal exactly once. It does not decide
what happens next, does not touch `workflow.yaml`, and never blocks the tool call.

### Trigger

The post-invocation hook event for the stop tool (`TaskStop`), matched by tool name.
The post-invocation event is used deliberately rather than the pre-invocation one — see
IMPLEMENTATION.md D1 for why recording before the stop succeeds would be unsafe.

### Processing flow

1. Parse the hook input. Non-object input, or a tool name other than the stop tool,
   ends the run with no action.
2. Extract the harness agent identifier: prefer the stop tool input's task-identifier
   field; when absent, fall back to the corresponding field of the tool result
   (IMPLEMENTATION.md D3). Finding none ends the run with no action.
3. Locate the search root by walking up from the hook input's working directory to the
   nearest ancestor containing the em-workflow worktrees directory, per the Agent index
   contract's read discipline. No such ancestor ends the run with no action.
4. Scan the agent index of each feature directory one level below that root for entries
   whose agent identifier matches. Use the LAST matching entry. No match ends the run
   with no action.
5. Validate the entry's task identifier and worktree path per the Conventions in
   IMPLEMENTATION.md. Invalid values end the run with no action.
6. Derive the journal path from the worktree path (Shared Components:
   Journal-directory derivation). A missing journal directory ends the run with no
   action — never create it.
7. Replay the journal for that task identifier. If its last event is the merged event
   or the failed event, end the run with no action (IMPLEMENTATION.md D4).
8. Otherwise append exactly one `failed` event per the Journal append discipline
   contract, with a reason string that identifies the stop as stop-tool-initiated and
   is textually distinct from `queue_failure_net.py`'s reason string.

Steps 7 and 8 run inside one exclusive-lock critical section over the journal file, so
that a concurrent writer cannot slip a terminal event in between the replay and the
append.

### Failure policy

Every abnormal condition ends the run with exit status 0 and no output. `main()`
carries a top-level catch-all so that no exception can escape.

### Registration

Add one entry to `em-workflow/hooks/hooks.json` under the post-invocation tool event,
matching the stop tool by name, with the plugin-root-relative `python3` command form
and `timeout: 15`. Do not modify, reorder, or remove the pre-existing registrations
(IMPLEMENTATION.md D5).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Given a stop event for an agent whose index entry maps to a task whose last
      journal event is `launched`, exactly one `failed` line is appended for that task,
      carrying the event name, task identifier, an RFC 3339 timestamp with offset, and
      a reason string. Exit status is 0.
- [ ] AC-2: The appended reason string is not equal to the reason string
      `queue_failure_net.py` writes, so the two stop causes are distinguishable in a
      post-mortem.
- [ ] AC-3: When the task's last journal event is `merged`, nothing is appended and
      exit status is 0. Likewise when it is already `failed` (idempotency, FR4).
- [ ] AC-4: A stop event whose agent identifier appears in no agent index appends
      nothing and exits 0. Likewise when no agent index file exists at all, and when
      no em-workflow worktrees ancestor is found from the working directory.
- [ ] AC-5: An index entry with an invalid task identifier, a relative worktree path,
      or a worktree path containing a `..` segment appends nothing and exits 0.
- [ ] AC-6: When the derived journal directory does not exist, nothing is appended, no
      file and no directory are created, and exit status is 0.
- [ ] AC-7: Malformed JSON on standard input, and a hook input naming a different tool,
      each produce exit status 0, no output, and no journal write.
- [ ] AC-8: With three tasks recorded as `launched` in one feature, a stop event for
      one of them appends `failed` for that task only; the other two tasks' last events
      remain `launched`.
- [ ] AC-9: After this hook appends `failed` for a task, feeding
      `em-workflow/hooks/queue_launch_guard.py` a launch for the same task yields no
      deny decision on standard output and appends a `launched` event — the retry path
      is open (this is the acceptance criterion that closes the originating bug).
- [ ] AC-10: When two index entries exist for the same agent identifier, the LAST one
      determines the task.
- [ ] AC-11: The agent identifier is recovered both from the stop tool input's
      task-identifier field and, when that is absent, from the tool result, verified by
      two separate cases.
- [ ] AC-12: `em-workflow/hooks/hooks.json` remains valid JSON, still contains the
      pre-existing registrations unchanged, and additionally registers this hook with
      `timeout: 15` and the plugin-root-relative command form.

## Test Notes

- Follow `test/README.md`: invoke the hook as a subprocess with JSON on standard input,
  assert on exit status and journal side-effects. Build a throwaway feature directory
  tree per test (`<root>/.claude/worktrees/em-workflow/<feature>/` holding
  `journal.jsonl`, the agent index, and per-task worktree directories) and pass the
  working directory through the hook input.
- AC-9 is an integration test that drives two hooks in sequence: this recorder, then
  `queue_launch_guard.py`. Assert both the absence of a deny decision on the guard's
  standard output and the resulting journal contents. Do not assert on the guard's
  internals — only on its observable output and side-effects.
- AC-3 and AC-10 are the idempotency and last-wins boundary cases; give each its own
  test rather than folding them into AC-1's case.
- The reason string is part of the contract (AC-2). Assert it against the constant
  imported or read from `queue_failure_net.py` rather than against a hardcoded copy, so
  the test cannot silently pass if that constant changes.

## Out of Scope

- Writing the agent index (task0001 owns it). This task only reads it.
- Any change to `queue_launch_guard.py`, `queue_failure_net.py`, or
  `queue_stop_guard.py`. `queue_launch_guard.py` is exercised read-only by AC-9.
- Relaxing the launch guard's in-flight judgment in any way.
- Documentation updates under `em-workflow/references/` (task0003 owns those).
