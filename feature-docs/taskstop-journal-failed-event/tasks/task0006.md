## Findings to resolve (verbatim from round 1)

### F-1 (severity: medium, category: architecture)

**agents.jsonl の join 契約が SSOT のどこにも無く、2 つのフックの docstring にしか
存在しない**

実装が依存している契約は 5 点ある: (1) 1 エントリが識別子候補リストを持つ、(2) 読み手は
候補のいずれかと一致すればマッチ、(3) 候補リストを持たない旧エントリのみ代表キーで
フォールバック、(4) 代表値は候補リストの先頭と一致する（読み手のフォールバックの
正しさがこれに依存）、(5) 同一 (feature, task) により新しいエントリがあればマッチを
stale として no-op。IMPLEMENTATION.md の Agent index contract は今も「a harness agent
identifier」（単数）と「uses the LAST such entry」（無条件 last-wins）のままで、
どれも記述していない。契約から再実装した読み手は、3 ループかけて潰した join 非対称
バグをそのまま再導入する。

### F-2 (severity: medium, category: comprehensive/architecture)

**README の hook 説明が 3 つのままで、新規 2 フックが反映されていない**

`em-workflow/README.md` の hook 列挙は個数・列挙・検知対象のいずれも実体と食い違う。
最初の実装パスで担当ファイル集合に README が入っていなかった計画側の欠落であり、
round 1 では 2 観点が繰り返し指摘している。

### F-3 (severity: medium, category: architecture)

**plugin.json の description のフック構成が実装とドリフト**

description はフックのイベント種別を列挙しているが、PostToolUse 2 本と新しい索引
ファイルが未記載。

### F-4 (severity: medium, category: architecture)

**Task-identity プリミティブの 4 コピー目を追加し、SSOT が要求する identical が実際には
不一致**

タスク割り当てヘッダの正規表現が `queue_launch_guard.py` と
`queue_agent_index.py` / `queue_failure_net.py` で既に乖離している（前者はヘッダ記号の
直後の空白を 1 個に固定、後者 2 つは 0 個以上を許容）。そのため空白 2 個のヘッダは索引側
だけが受理し、launch guard は起動と認識しない。その状態で停止が起きると、`launched`
イベントを持たないタスクに `failed` が権威ログへ追記される。

## Design notes

- 件数を数え上げる表現（「3 つの hook」等）は次の追加で必ず陳腐化する。README と
  plugin.json は個数・イベント列挙を持たない書き方にして、詳細は
  `references/implement-phase.md` へ委譲すること。
- F-4 の恒久策は共有モジュール化だが、このタスクでは**正規表現の一致だけ**を行う。
  共有モジュール化は 5 ファイルの挙動を同時に変えるため、独立したタスクとして起票する
  のが適切（このタスクの Out of Scope）。`queue_launch_guard.py` は round 1 を通じて
  一切変更していないので、他の 2 ファイルをそちらの綴りに揃える方向で統一すること。
- 索引ファイルは診断用プラミングであって権威ある状態ファイルではない、という位置づけを
  どの文書でも崩さないこと。
