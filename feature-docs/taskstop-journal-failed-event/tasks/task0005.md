## Goal

Stop the index writer from promoting untrusted free-text into a join key, widen the
payload shapes it can actually read an identifier out of, and cover both with tests.

## Requirements

FR3, FR5, NFR1, NFR2, NFR3, NFR5

## Scope

### Files to Modify

- `em-workflow/hooks/queue_agent_index.py` — candidate-source policy, text extraction.
- `tests/test_queue_agent_index.py` — the missing coverage.

## Findings to resolve (verbatim from round 1)

### F-1 (severity: medium, category: security)

**サブエージェント自由文由来の識別子が常時 agent_ids に永続化され、照合キーとして
採用される**

round 1 loop 3 以降、構造化フィールドがあってもテキスト由来の候補が候補リストに並記
され、読み手が「いずれか一致」で採用するため、偽装値が常に有効な join key になる。
この結果テキストはサブエージェント自身の最終出力であり、実装者エージェントは未検証の
リポジトリ内容を読んで要約するため、レビュープロトコルの定義どおり
attacker-influenceable なデータ。停止していない健全な in-flight タスクの journal に
`failed` を書かせる誤誘導が成立しうる。

Suggested approach: 自由文由来の候補は「構造化フィールドが 1 つも取れなかったとき」
のみのフォールバックに戻す。綴り揺れの吸収という loop 3 の目的は構造化フィールドの
列挙だけで達成できており、自由文由来値を照合キーに昇格させる必要はない。

### F-2 (severity: medium, category: comprehensive)

**tool_response の content が文字列のとき識別子を回収できず、機能全体が恒久的な
no-op に落ちる**

テキスト抽出は content がリストのときしかテキストを返さない。したがって結果が
オブジェクトで content が素の文字列という、ツール結果として最もありふれた形だけが
穴として残っている。踏むと索引が一切書かれず、recorder は常に no-op になり、この
feature が実装しようとしている記録が丸ごと死ぬ。fail-open のため観測もできない。

Suggested approach: content が文字列の場合もテキストとして扱う。候補が全て 1 エントリ
にまとまる現方式と整合するため、オブジェクトの他の文字列キーも走査対象に加えてよい。
ただし F-1 の結論（テキスト経路はフォールバック限定）を先に適用し、その制約の中で
広げること。

### F-3 (severity: medium, category: comprehensive/spec)

**候補リスト結合そのものにテストが無い**

書き手側は候補リストキーの存在・中身・代表値との不変条件・複数候補ケースを一切
assert しておらず、候補リストの書き出しを落としても全テストが緑のまま通る。

## Design constraints

- **1 launch = 1 エントリを維持すること。** 候補ごとに複数行を書いてはならない。
  recorder の staleness ガードが「同一 (feature index, task) の後続エントリ =
  supersede」と判定するため、1 回の起動で 2 行書くと自分自身を stale にして機能が
  壊れる（round 1 でこの案は明示的に却下されている）。
- 代表値は候補リストの先頭要素と一致し続けること。recorder の後方互換フォールバック
  がこの不変条件に依存している。
- 埋め込みテキストの識別子パターンを task 系の綴りへ広げてはならない。implementer の
  プロンプトには必ずタスク ID 行が含まれるため、テキスト経路で `task0001` を
  エージェント識別子として誤って拾う。

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: When the launch result carries at least one structured identifier field, no
      identifier harvested from free-text is recorded — the candidate list contains only
      structured-field values.
- [ ] AC-2: When the launch result carries no structured identifier field, the
      free-text fallback still recovers an identifier, and the entry is written.
- [ ] AC-3: An identifier is recovered when the result is an object whose content is a
      plain string, and when it is an object whose content is a block list, and when it
      is a plain string result — verified by three separate cases.
- [ ] AC-4: Exactly one index line is appended per launch in every case above.
- [ ] AC-5: The recorded representative identifier always equals the first element of
      the recorded candidate list, asserted in a multi-candidate case.
- [ ] AC-6: A launch result carrying two distinct structured identifier spellings with
      DIFFERENT values records both, in discovery order, with duplicates removed.
- [ ] AC-7: The embedded-text identifier pattern still does not match a task-assignment
      style task id, verified by a negative case whose text contains such a line.
- [ ] AC-8: Symlink coverage: with the index path replaced by a symlink to a file
      outside the feature directory, the hook exits 0 and the link target stays
      unwritten.
- [ ] AC-9: No structured field and no recoverable text — nothing is written, exit 0.
- [ ] AC-10: The full suite (`python3 -m unittest discover -s tests`) passes.

## Test Notes

- Follow `test/README.md`: subprocess + JSON on standard input, throwaway directories.
- AC-1 is the security-relevant assertion: construct a result that carries BOTH a

  free-text value is absent from the entry.
- AC-6 is what makes the loop-3 join fix regression-detectable; without it, removing the
  candidate list leaves the suite green.
