# Task Plan: task0001 — Dev server in the design skill's agreement loop

## Goal

In `/em-workflow:design`, the agreement loop (Step 4) serves the target feature's mocks through a local dev server started in the background and guides the user to its local URL, falls back to the current open-directly procedure when the server cannot be used, and the closing step (Step 6) stops the server with `TaskStop`.

## Design

### Step 4 flow (agreement loop)

1. **When to start**: only when the target feature has at least one mock. In the system-wide scope, which handles no mock, nothing is started. `tokens.html` is never given to the server; the user still opens it directly, as today.
2. **Availability check**: before starting, check that the dev server command exists (example: `command -v bun`) through Bash with the Bash tool's timeout parameter set. A shell timeout command is not used.
3. **Command missing**: go to the fallback (item 6).
4. **Start**: run the dev server with the feature's mocks as arguments (example form: `bun ./<mock>.html`) through Bash with `run_in_background`, and keep the task id it returns for the restart and for Step 6. Several mocks go to one server together; each is then served at `/<file name without extension>`. The command fixes no port and carries no option or address that widens where the server listens.
5. **Guide**: read the started task's output, take the local URL from its `url` / `Routes` lines, and guide the user to it, presenting the server as local development use. When the task has already ended or its output shows no URL, treat this as a start failure and go to the fallback.
6. **Fallback**: guide the mock file path; the user opens it in the browser directly and reloads by hand after each edit. No question is asked, and the loop continues.
7. **State switch**: in both the server case and the fallback, tell the user that appending `?state=<name>` to the mock URL shows one state, and point to designer.md's mock rules as where the rule lives (D1). Step 4 does not restate the rule.
8. **During the loop**: a mock edit reaches the browser through the server's own update feature; the mock file holds no reload code (Mock reload stance).
9. **Mock added during the loop**: when a new mock is not served by the running server, stop the running task with `TaskStop`, then start one server again with all the feature's mocks (back to item 4). When that task has already ended, go straight to the restart.
10. **Replaced text**: the existing instruction that only asks the user to open the mock in a browser (quoted in SPEC.md FR1) is replaced by this flow. The Step 4 mock-discipline summary (self-contained / token CSS variables / every SPEC state) stays.

### Step 6 (closing)

- A server task was started in Step 4: stop it with `TaskStop` on its task id.
- No server was started (no mock, system-wide scope, or fallback): do nothing.
- The task has already ended, or `TaskStop` cannot stop it: continue closing. No other means of stopping is used.
