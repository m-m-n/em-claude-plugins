## Goal

Every per-task TDD evidence record this feature produced conforms to the
implementer record contract and resolves against the code as it now stands: no
`acceptance_tests` entry is missing a mandated key, and no recorded test method
name points at a method that no longer exists.

## Requirements

NFR3

Rationale for the mapping: NFR3 is this change's test-discipline requirement —
the suite stays green with nothing skipped, removed or hollowed out to get
there. The `tests.yaml` records are the evidence trail for exactly that claim.
An entry missing a mandated key cannot be audited, and a reference to a deleted
method makes the trail unfollowable — a later reader cannot tell whether the
recorded red was ever observed. No FR describes the evidence-record format.

## Design

### Defect A — entries missing `red_confirmed` (`task0003.tests.yaml`)

`agents/implementer.md` gives every Acceptance Criterion an entry carrying all
three of `tests`, `red_confirmed` and `red_reason`, and states explicitly that a
criterion whose verifiable outcome is an inspection rather than a test is
included too, as `tests: []` with the outcome named in `red_reason`.
`task0003.tests.yaml`'s `AC-7` and `AC-8` carry `tests: []` and `red_reason` but
no `red_confirmed`.

**Fix.** Add `red_confirmed: false` to both entries.

`false` is the truthful value, not a formality: both criteria are process/meta
criteria verified by inspection, so no test was ever watched failing for them.
The contract's rule that a `red_confirmed: false` must be explained is already
satisfied — each entry's existing `red_reason` names the inspection that stood
in for a red. That text is preserved byte-for-byte; this fix adds a key and
changes nothing else. Key order follows the file's existing convention
(`tests`, then `red_confirmed`, then `red_reason`), which is what
`task0002.tests.yaml` and the repaired `task0001.tests.yaml` already use.

This is the identical repair task0004 applied to `task0001.tests.yaml`'s `AC-6`
and `AC-7`; the same reasoning and the same value apply, on a different record.

### Defect B — stale test-method references (`task0001.tests.yaml`)

task0003 renamed methods in `tests/test_implement_routeback_gate.py`. Three
names recorded in `task0001.tests.yaml` did not follow the rename and now
resolve to nothing:

- `AC-3`'s `test_implement_stays_failed`
- `AC-4`'s `test_document_order_gate_before_refresh_tip_writeset_cleanup_commit`
- `AC-4`'s `test_rejected_path_commits_nothing_and_starts_no_cleanup`

`AC-4` is the worse case: after the rename, neither of its two references
survives, so the criterion has no reachable evidence at all.

**Fix.** Replace each stale name with the name of the method that carries that
criterion's assertion in `tests/test_implement_routeback_gate.py` as it stands
on the integration branch. Establish the mapping by reading the current module
and matching on what each method asserts — the criterion text of `AC-3` and
`AC-4` in `tasks/task0001.md` is the reference for "which assertion belongs to
which criterion". Where a renamed method absorbed or split the old one's
assertions, record every current method that carries part of that criterion's
evidence.

**What this fix must NOT do.** The recorded red observations themselves are
historical fact: `red_confirmed` values and `red_reason` texts stay unchanged.
This is a re-pointing of names, not a re-litigation of what was observed. Nor is
a criterion allowed to reach resolvability by having its `tests` list emptied —
an entry that had evidence keeps evidence.

If no current method can be identified as carrying an `AC-3` or `AC-4`
assertion, that is a finding about the merged test module, not something to
paper over in the record: report it as a plan deviation rather than inventing a
plausible name or emptying the list.

### Why this is not a mechanical checker

FR5 and ASM4 forbid this feature from adding a script, validator rule, hook or
test module — including one that would enforce the `tests.yaml` shape. The
checks below are run ad hoc and their observed results recorded; nothing under
`tests/` or `em-workflow/scripts/` is created.
