## Design

### Surface A — the rejected path reaches a persisted terminal (FR2, FR3)

**Defect.** Step I.2.c currently says the rejected path leaves `implement`
`failed` ("stays `failed`"). Nothing in the phase ever writes that status:
Step I.1 sets `implement` to `in_progress` "in all cases", and Step I.2.b's
reconcile writes only `tasks.{T}.status`. On the rejected path `implement` is
therefore still `in_progress` when the phase ends, develop Step B's stop
condition 3 (evaluated against a step's `failed` / `needs_update` status when
Step B selects the step to run) does not fire, and the next Step B iteration
re-enters implement as a resume. SPEC FR2/AC2's terminal state does not hold.

**Fix.** The rejected path performs exactly one workflow.yaml write — set the
`implement` step to `failed` — and commits exactly that write via
`commit-docs.sh` (refresh the integration worktree, capture the tip, write,
commit — the standing discipline that no workflow.yaml write is left
uncommitted across turns), then ends the phase with a report. The next Step B
iteration reads `implement: failed` and stops on stop condition 3.

**Scope statement, mandatory (FR3/AC3).** The sentence that today reads
"nothing is committed and no worktree/branch cleanup is started" must be
replaced by one that states the same guarantee at its true scope: on the
rejected path there is **no route-back write set, no worktree/branch cleanup
and no route-back commit** — the ONLY side effect is the single
`implement: failed` status write and its own commit. The gate decision still
precedes every one of those side effects in document order, which is what
FR3/AC3 constrains. A reader must be able to see, from the sentence alone,
that the terminal write is not part of the route back.

**Ordering (unchanged from task0001's AC-4).** The gate decision still comes
first in document order — before the refresh, the tip capture, the write set,
the cleanup and every `commit-docs.sh` invocation on either branch.

### Surface B — in-flight is decided by the rule I.2.b owns (FR1, NFR2)

**Defect.** The gate reads `in_progress` from workflow.yaml "as an independent
check", but the same document's Step I.2.b declares that for in-flight
determination the journal is authoritative ("a `launched` last event is always
in-flight regardless of workflow.yaml `status`"). The gate exists to catch the
crashed/diverged regime, and in exactly that regime it consults the side the
document says not to trust: a live implementer whose task row still reads
`pending` would be missed, the route back admitted, its task reset to `pending`
and its running worktree deleted with `--force`.

**Fix.** The `in_progress` half of the gate is stated as a **union** of two
sources, either of which blocks:

1. no task has status `in_progress` in workflow.yaml, AND
2. no task is in-flight under Step I.2.b's last-event-per-task rule
   (`launched` last event, with the recycled-task-id carve-out that step
   already defines) — cited to Step I.2.b as the owning rule, never restated.

Both conjuncts of the widened gate survive verbatim as gate conjuncts
(`merged`, `in_progress`), so AC1's admissibility phrasing is unchanged; the
journal check only ever ADDS blocking power and never admits a route back that
the workflow.yaml conjuncts alone would refuse. NFR2 is strengthened, not
weakened: the workflow.yaml statuses remain an independent check that the
drain behaved, and the journal check adds a second independent one.

The same union is what the Surface C proof must reference — the two surfaces
must not describe in-flight-ness differently.

### Surface C — the exit-4 carve-out is stated in every SSOT it binds (FR4)

**Defect.** `commit-docs.sh`'s header declares its exit-4 RECOVERY CONTRACT
"binding on every caller", and `skills/develop/SKILL.md` scopes its exit-4
paragraph to "commit-docs.sh の全呼び出し箇所で共通". This feature removed one
call site from that obligation in `implement-phase.md` alone, leaving three
SSOTs that disagree about the same event. Additionally the unreachability proof
argues only over `merge-task.sh` callers, while exit 4's actual trigger is any
divergence between `expected_base_tip` and the real tip — i.e. any ref advance.

**Fix, in three parts.**

1. **`implement-phase.md`, Branch & Worktree Model.** The bounded-recovery
   enumeration lists Step I.1's baseline commit, Step I.2.b's wake-phase commit
   **and Step I.2.c's rejected-path terminal status commit** (Surface A's new
   call site — reachable precisely when the gate found a `merged` task or an
   in-flight one, so a concurrent ref advance is possible there and the bounded
   recovery genuinely applies). The single carve-out remains Step I.2.c's
   **route-back** commit, and the bullet must say so in those words, so that
   "I.2.c" appearing in the enumeration can never be read as the route-back
   commit returning to it. The proof is restated over the real trigger
   condition: it enumerates the paths that can advance
   `refs/heads/em-workflow/{feature}/integration` during a develop run
   (`merge-task.sh`, run only by this feature's implementers; the
   orchestrator's own `commit-docs.sh`, serialized on the shared lock and
   single-threaded), shows the widened gate's union rule (Surface B) excludes
   the first, and names the residual assumption — no process outside the
   develop run advances this ref — together with the defined terminal that
   covers it if it is ever false (below). The bounded procedure's own
   sentences ("retry `commit-docs.sh` once", the second-exit-4 stop) stay
   byte-stable; other suites pin them.

2. **Destructive-order fix at the route-back call site.** Today the route back
   runs `git worktree remove --force` / `git branch -D` BEFORE committing the
   write set, so an unexpected non-zero exit at that commit stops the phase
   with the deletions already done and the write set uncommitted — a state the
   next `reset --hard` cannot restore. The route back is reordered to write set
   → commit → cleanup, so the "unexpected non-zero exit stops the phase with a
   report" terminal is reached with nothing destroyed and nothing to reconcile
   beyond discarding the uncommitted write set. The prose states that
   consequence explicitly, and states the one residual leftover state the new
   order can produce (commit succeeded, cleanup not yet run → stale worktrees
   for tasks now `pending`, which Step I.2.a's resume guard and its
   recycled-task-id rule already cover).

3. **The two non-owning SSOTs.** `commit-docs.sh`'s RECOVERY CONTRACT header
   and `develop/SKILL.md`'s scoping parenthetical are narrowed to match: the
   contract binds every caller EXCEPT a call site whose owning protocol
   document states both a proof of unreachability and a defined terminal for an
   unexpected non-zero exit, and both name `implement-phase.md` Step I.2.c's
   route-back commit as the only such site today. `commit-docs.sh`'s change is
   confined to comment text — exit codes, checks and behavior are untouched, so
   `tests/test_commit_docs.py` must stay green unmodified. `develop/SKILL.md`'s
   change is confined to the scoping parenthetical: the strings
   `exit-4 リカバリ`, "`commit-docs.sh` を 1 回だけ再試行する。2 回目も" and the
   line-wrapped "無限リトライ\nしない" are pinned by
   `tests/test_develop_skill_rewiring.py` and must survive byte-identical,
   line breaks included.

### Surface D — the document-contract tests (FR5, NFR3)

All test changes land in `tests/test_implement_routeback_gate.py`; no new test

## Test Notes

- Same style as the module already uses: read the target file as text, slice
  the section by a heading or anchor phrase, assert against a
  whitespace-normalized copy except where byte identity is the criterion.
  `commit-docs.sh` and `develop/SKILL.md` are sliced the same way (header
  comment block / the `exit-4 リカバリ` paragraph).
- TDD order: update the assertions first and watch them go red against the
  current prose, then edit the documents. An assertion that was green before
  the edit is evidence the update did not take — record such cases honestly in
  the task's `tests.yaml` with `red_confirmed: false` and a reason.
- Ordering criteria (AC-2, AC-5) are index comparisons inside the sliced
  section, not prose review.
- Byte-stability criteria (AC-4's procedure sentences, AC-6's Japanese
  strings) are asserted against the raw text, not the normalized copy —
  "無限リトライ\nしない" only proves anything with its newline intact.
- AC-6's "comment lines only" half is verified by inspecting `git diff` on
  `commit-docs.sh` before reporting completion, not by a committed checker
  (FR5 forbids adding one).
- Suites outside this task's file set — `tests/test_commit_docs.py`,
  `tests/test_develop_skill_rewiring.py`,
  `tests/test_review_implement_develop_lock_contracts.py`,
  `tests/test_reference_sweep.py`,
  `tests/test_check_plugin_invariants.py` — must pass unmodified. If one goes
  red, the fix belongs in this task's document edit, never in that suite; if a
  document edit genuinely cannot keep such a suite green, that is a reportable
  plan deviation.
