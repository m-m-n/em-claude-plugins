# Task Plan: task0001 — Widen the I.2.c route-back gate and correct the exit-4 enumeration

## Goal

`em-workflow/references/implement-phase.md` admits route back to planning only
from a state that `replace_all` accepts, gives the rejected path a single
defined terminal that commits and mutates nothing, and stops listing the I.2.c
route-back commit among the exit-4 recovery cases — with the document-contract
tests that pin this prose updated in the same change.

## Requirements

## Design

### Surface A — Step I.2.c route-back admissibility (FR1, NFR2)

The gate is decided from `workflow.yaml` task statuses alone. Its admissibility
condition is the conjunction of two blockers:

1. no task has status `merged`, AND
2. no task has status `in_progress`.

The literal phrase `no task has status \`merged\`` already exists and stays; the
second conjunct is stated in the same shape (`no task has status
\`in_progress\``) and joined to the first conjunctively, in one sentence, so the
condition reads as a single admissibility test rather than two separate rules.

The preceding drain of in-flight siblings is a fact about the normal case, not
the basis of admissibility. Any wording that lets the drain stand in for
checking `in_progress` ("the drain above has already retired every
`in_progress` sibling by this point", or equivalent) must stop functioning as
the justification — the gate is an independent check that also catches a stale
or unretired `in_progress` entry left by a crashed implementer (NFR2). The
drain's operational instruction itself (stop launching, let in-flight tasks
drain) is unchanged.

**The write set is unchanged.** The one ordered write set still contains, in
this order and still positioned before the worktree/branch cleanup:

- `create-plan` set to `needs_update`,
- the `implement` step set back to `pending`,
- each failed task's failure reason recorded in `tasks.{T}.notes`,
- every failed task's `tasks.{T}.status` set back to `pending`.

Postcondition of the admitted path: no task is left `merged`, `in_progress` or
`failed`, i.e. every existing task is `pending`. The document continues to name
`references/workflow-patch.md`'s `replace_all` permission conditions as the
owner of the admissibility rule and must not restate that rule's condition set
(IMPLEMENTATION.md, Conventions).

### Surface B — the rejected path's single terminal (FR2, FR3)

When the condition is not met — for either blocker — the section states exactly
one outcome: `create-plan` is NOT set to `needs_update`, `implement` is/stays
`failed`, and the phase reports and returns control to the user via develop
Step B's stop condition 3 (the same terminal as the sibling "abort phase"
option). No retry loop, no alternative recovery route, no degraded/partial
route back is offered for this path.

Today this branch is written for the `merged` case only, opening with a literal
phrase about a task having already merged. It must be generalized to the gate's
condition so that a blocking `in_progress` task reaches the same terminal.

Ordering requirement (FR3): the gate decision is stated strictly before the
integration-worktree refresh, before the tip capture, before the write set,
before the cleanup and before the `commit-docs.sh` invocation — in document
order, so a reader executing the section top-down cannot reach a side effect
before deciding. An explicit sentence states that on the rejected path nothing
is committed and no worktree/branch cleanup is started.

**Not in scope of this surface**: the sibling **retry** option, the **abort
phase** option, the "There is NO skip option" paragraph and the batch-mode
paragraph that closes the section. The "no alternative offered" property is
scoped to the rejected route-back path, not to the failure-handling menu as a
whole. The batch-mode paragraph and the `### I.2.c: Failed handling` heading
stay byte-identical.

### Surface C — exit-4 recovery enumeration (FR4)

The Branch & Worktree Model section's exit-4 recovery bullet currently
enumerates three `commit-docs.sh` call sites in this phase. The I.2.c
route-back commit is removed from that enumeration, leaving Step I.1's baseline
commit and Step I.2.b's wake-phase commit. In its place the bullet states why
that call site is unreachable, as a chain: the widened I.2.c gate lets route
back proceed only when no task is `in_progress` → no implementer of this
feature can be running → implementers are the only callers of `merge-task.sh`
against this integration branch → no concurrent ref advance can occur between
that call site's refresh and its commit attempt. The justification is tied to
the widened gate, not to the drain step alone, so the two surfaces of this
document agree on which condition guarantees the exclusion.

The recovery procedure itself is untouched: the refresh / re-capture the tip /
re-derive from source / retry once discipline and the second-exit-4 stop stay
as written. Other suites assert those sentences and must stay green without
being modified.

### Surface D — reconciling the I.2.c call-site pointer

The route-back `commit-docs.sh` invocation in I.2.c currently carries an inline
pointer to the bounded exit-4 recovery procedure. Once Surface C declares that
call site unreachable, a pointer to a recovery that no longer lists it is
self-contradictory. Replace it with a note that exit 4 cannot occur at this
call site (justification owned by the Branch & Worktree Model) and that an
unexpected non-zero exit here stops the phase with a report — a defined
terminal, not a bounded retry loop. The existing test assertion pinning the old
pointer is updated to the new wording in the same change.

### Surface E — the document-contract tests (FR5, NFR3)

All test changes land in the existing module; no new test module, script,
validator rule or hook is created (FR5). Concretely:

- The class that asserts the exit-4 enumeration names the I.2.c route-back
  commit is rewritten to assert its **absence** plus the presence of the
  unreachability justification. Renaming it to match its new meaning is
  expected; deleting or skipping it is not (IMPLEMENTATION.md D4).
- The class asserting the gate is extended to assert both conjuncts and their
  conjunctive joining, and to assert the absence of drain-as-justification
  wording.
- New absence assertions get a matching entry in the module's
  regression-proof class, demonstrating that the matcher flags the pre-change
  wording — the module's existing discipline.
- Assertions that slice the section or a branch by a literal anchor phrase
  must be re-anchored when this task changes that phrase; a stale anchor makes
  the test error out rather than fail meaningfully.
- Module and class docstrings are updated to describe this feature's contract
  and to cite this feature's task plan
  (`feature-docs/routeback-gate-postcondition/tasks/task0001.md`) instead of
  the earlier feature's.

## Test Notes

- All criteria are unit-level document-contract assertions: read the target
  document as text, slice the relevant section by its heading, assert on a
  whitespace-normalized copy (line-wrap independence) except where byte
  identity is the criterion. This is exactly what the existing module does —
  reuse its helpers rather than inventing a second style.
- TDD order: update the assertions in the test module first (they go red
  against the current prose), then edit the document until green. The
  documentary nature of the change does not exempt it from red-first — a
  pre-existing assertion that stays green after being "updated" is evidence
  the update did not take.
- Ordering criteria (AC-2, AC-4) are expressed as index comparisons within the
  sliced section, not as prose review.
- Absence criteria (AC-1's drain wording, AC-5's removed enumeration entry) are
  brittle in the wrong direction: an absence assertion passes trivially if the
  phrase was never spelled the way the matcher expects. Pair each with a proof
  against a sample of the pre-change wording, as the module already does.
- Slice anchors are a known trap: AC-3 changes the phrase that the current
  merged-branch test slices on, which would make that slice raise instead of
  fail. Re-anchor deliberately.
- AC-7's diff-scope half is not automatable without adding a checker, which
  FR5 forbids: verify it by inspecting the task branch's changed-file list
  before reporting completion.
- Suites outside this task's file set (the lock-contract suite, the phase-state
  suite, the reference sweep) must pass unmodified; if one goes red, the fix
  belongs in this task's document edit, never in that suite.
