## Design

**Defect.** The implementer contract (`agents/implementer.md`) gives every
Acceptance Criterion an entry carrying `tests`, `red_confirmed` and
`red_reason`, and states explicitly that criteria whose verifiable outcome is
a build or an inspection rather than a test are included, as `tests: []` with
the outcome named in `red_reason`. In `task0001.tests.yaml` the `AC-6` and
`AC-7` entries carry `tests: []` and `red_reason` but no `red_confirmed`,
while `task0002.tests.yaml` — same feature, same change — writes
`red_confirmed: false` on all four of its `tests: []` entries. One feature,
two schemas.

**Fix.** Add `red_confirmed: false` to `AC-6` and to `AC-7`.

`false` is the truthful value, not a formality: both criteria are process/meta
criteria verified by inspection (`git diff --stat`, a full-suite run), so no
test was ever watched failing for them. The contract's rule that
`red_confirmed: false` must be explained is already satisfied — each entry's
existing `red_reason` states the inspection that stood in for a red. That text
is therefore preserved byte-for-byte; this task adds a key and changes nothing
else.

Placement follows the file's existing convention (`tests`, then
`red_confirmed`, then `red_reason`), matching `task0002.tests.yaml`, so the two
records read identically.
