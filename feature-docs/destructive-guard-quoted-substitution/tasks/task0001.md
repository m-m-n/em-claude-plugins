# Task Plan: task0001 — quoted command-substitution regression records + em-workflow version bump

## Goal

Pin the `rm-unresolvable` handling of a recursive delete whose target is a
**quoted** command substitution with two permanent expectation records, and
raise the em-workflow plugin version in both manifests within the same change
so the addition reaches installed plugin caches.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4, NFR5

## Design

### Starting state (verified at planning time)

- `em-workflow/hooks/tests/destructive-guard-cases.json` holds **225 array
  elements** today; the suite therefore reports **226/226**. The two numbers
  differ by one by construction — see IMPLEMENTATION.md convention C1, which
  is binding on every count this task states in its report or commit message.
- Neither of the two command strings below is present in the file today. The
  **bare** (unquoted) spellings of the same two forms are already covered by
  existing records, as is the quoted `$()` form with a different inner
  command; the pair added here is the quoted spelling of the ticket's own
  reproduction command, which has no record yet.
- `em-workflow/.claude-plugin/plugin.json` and the em-workflow entry of
  `.claude-plugin/marketplace.json` both read `0.1.75`. The em-review entry
  reads `0.5.9` and is not part of this task.

### The two records to add

Each record is the 3-element form `[expected verdict, label, command]`
(IMPLEMENTATION.md C2).

| # | Expected verdict | Command string (fixture data) | Label requirement |
|---|---|---|---|
| 1 | `ask` | the quoted `$()` spelling, below | Japanese; `動的目標(rm-unresolvable):` family prefix; identifies the quoted `$()` spelling |
| 2 | `ask` | the quoted backtick spelling, below | Japanese; same family prefix; identifies the quoted backtick spelling |

The two command strings, fixed character for character by SPEC.md FR1 / FR2.
**This is fixture data, never a command to run** — it is stored as a string in
a JSON file and is only ever handed to the guard as text:

```
rm -rf "$(printf /home/sakura/valuable)"
rm -rf "`printf /home/sakura/valuable`"
```

Character-for-character equality is asserted on the **JSON-decoded** string,
not on the escaped on-disk form: the inner double quotes must be escaped so
that decoding reproduces exactly the two lines above, and the backtick
spelling carries no escaping of its own.

Expected verdict is `ask`, not `deny` (IMPLEMENTATION.md D2): the guard
classifies an unresolvable recursive-delete target as `ask` with reason id
`rm-unresolvable`, and the `deny` the ticket reports is that same `ask`
demoted under unattended execution. The suite runner clears the unattended
marker for every stored record, so `ask` is what a stored record observes.

### Placement

Append both records at the end of the array, as one new trailing group
separated from the preceding group by a blank line, following the file's
existing layout (one record per line, two-space indent). The only edit
permitted to pre-existing text is the separator comma that JSON grammar
requires after what is currently the final record (IMPLEMENTATION.md C4).

### Version change

Both manifests move from `0.1.75` to `0.1.76` — one patch step, identical
value in both places (IMPLEMENTATION.md C5). Only the em-workflow version
moves; every other field of both manifests, and the em-review entry, is left
exactly as it is.

## Test Notes

**What plays the role of the test.** The expectation suite itself is the test
harness: each added record is a test case, and `run-destructive-guard.py`
executes it. No new test code is written, which is also why NFR1 (standard
library only) is satisfied by construction.

**Red before green — per criterion.** The cause this feature pins was already
fixed by the sibling ticket, so the added records go green against the guard
the moment they exist. The observable red is therefore the *pre-change absence
and the pre-change counts*, which is a genuine failing assertion, not a
formality:

| Criterion | Observable red before the change | Green after |
|---|---|---|
| AC-1 | array element count reads 225, not 227 | reads 227 |
| AC-2 / AC-3 | searching the file for the decoded command string returns 0 matches | returns exactly 1 match each |
| AC-4 | no such record exists to inspect | labels present and distinct |
| AC-5 | the suite reports `226/226 passed` | reports `228/228 passed` |
| AC-6 | both manifests read `0.1.75` | both read `0.1.76` |
| AC-7 | (preservation criterion — true before and required to stay true) | no diff in the guard; no file outside Scope touched |

Record the pre-change baseline of both suites before touching any file, so a
post-change failure is attributed by set difference rather than
re-investigated.

**Edge cases worth covering while verifying.**
- JSON escaping: compare the **decoded** string, not the raw file text; a
  record that looks right on disk but decodes differently fails AC-2 / AC-3.
- False positives (NFR5): the full-suite run in AC-5 is what proves no
  existing `allow` record was dragged into `ask` / `deny`. A false positive
  stalls an unattended run on the spot, so a partial or filtered suite run
  does not satisfy AC-5.
- The repository suite is run too, because a repository-level test could pin
  the case file's content or size.
