# Task Plan: task0005 — Record-writing rules in implementer.md and test/README.md

## Goal

Step 4c of `em-workflow/agents/implementer.md` carries language-independent rules for writing `tests` IDs, for checking after writing the record, and for other records broken by a test rename or deletion; `test/README.md` states this repository's ID format and the notation the record check reads; a document-contract test pins both documents.

## Design

### implementer.md, Step 4c

Added in English, in the document's existing style. The added text names no programming language, no test framework, no module of this repository and not this repository's `tests.` prefix (FR10), because the agent serves every project.

1. Writing rule (FR10): each `tests` element is an ID that the project's test command can select directly. Free text, abbreviations, wildcards and runner script paths are never written there; explanations go in `red_reason`.
2. After-write check (FR11): after writing the record in Step 4c, run `project_commands.test` and confirm that no failure absent from the Step 4b baseline appeared. A failure caused by the record is fixed in the record.
3. Other records (FR12): when renaming or deleting a test makes another feature's or another task's record fail the project's record check, fix that record's IDs as well. File changes outside the planned files are reported in `deviations`. A request to extend the planned files names the existing AC, the path needed, and the check that fails without the change.

### test/README.md

4. ID format (FR13): IDs start with `tests.` and are dot-separated; module, class and method level are all accepted. The acceptance criterion is summarised from IMPLEMENTATION.md SC-1, judged as under `python3 -m unittest discover -s tests` run from the repository root.
5. Notation (FR7): the record check's notation from IMPLEMENTATION.md SC-2 (supported forms, the opaque-value rule and every error condition), stated consistently with SC-2 and naming the record check module from SC-6.

### Document-contract test

6. Reads both documents as text, never importing or executing them, and imports the standard library only.
7. One test per rule (items 1 to 5 above), each asserting phrases this task chooses and keeps in the documents, so a missing rule surfaces under its own test name. The implementer.md assertions are limited to the Step 4c section, from its heading to the next step heading.
