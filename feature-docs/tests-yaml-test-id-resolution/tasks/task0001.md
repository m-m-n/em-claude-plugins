# Task Plan: task0001 — Record check test module

## Goal

A standard-library-only unittest module that enumerates every `test-docs/**/*.tests.yaml`, extracts `acceptance_tests.*.tests` per IMPLEMENTATION.md SC-2, judges every ID per SC-1, and fails once per record file with every extraction and resolution error listed.

## Requirements

FR4, FR5, FR6, FR7, FR8, FR9, NFR1, NFR2, NFR3

## Scope

### Files to Create

- `tests/test_tests_yaml_id_resolution.py` — the record check (enumeration, extraction, resolution, per-record tests, zero-record guard) and its own fixture-based tests

### Files to Modify

None.

## Design

Everything lives in the one module named in SC-6: NFR1 forbids importing other test modules or repository helpers, so the fixture-based tests sit beside the check itself.

### Components

| Component | Input | Output / postcondition |
|---|---|---|
| Record enumeration | a root directory | sorted repository-relative paths of every file under the root's `test-docs/` whose name ends in `.tests.yaml`, at any depth; the real-repository root is the parent of the directory holding this module, never the working directory |
| Extractor | one record file | either an ordered AC key to ID list mapping, or extraction errors (file, AC or record-level marker, reason); implements SC-2 exactly; reads text only and never imports anything |
| Resolver | a root and one ID | success, or a failure reason; implements the SC-1 steps in order, with the root at the front of the module search path only for the duration of the call and the path restored afterwards in every case |
| Record check | a root and one record path | the full list of error lines for that record: every extraction error, plus a resolution error for every invalid ID of every AC that was extracted without error; nothing stops at the first error (FR5) |
| Per-record tests (FR9) | the record list of a root | one test per record whose name is deterministic, unique, a valid identifier and recognisably derived from the record path (names that collide after sanitising are told apart deterministically); each test runs the record check and fails with one message that lists every error line; the generator accepts any root so fixture tests can build per-record tests for a fixture root |
| Zero-record guard (FR8) | the real-repository record list | a separate test that fails when enumeration finds no record |

Module import performs record enumeration only, never extraction or resolution: records may name this module itself, which is then imported a second time under its `tests.` name.

### Failure message

The first line names the record path and the number of errors. Each further line carries file, AC (or the record-level marker), ID when one applies, and a short English reason. Reasons cover at least: unsupported notation (with the line number), duplicate AC key, duplicate tests key, missing tests key, missing acceptance_tests, unreadable record, not a canonical ID, module import failed, attribute not found, not a test case class, not a test method, loader raised, loader error recorded, loader returned a failed test.

### Fixture strategy

- Each fixture test builds a temporary root holding `test-docs/{feature}/{task}.tests.yaml` files and, where resolution is exercised, a fixture `tests` package with modules written by the test.
- The real `tests` package and any fixture `tests` package never see each other. Around every fixture-root resolution, the module-cache entries for `tests` and everything under it are set aside and restored afterwards, with fixture entries discarded, so outcomes do not depend on test order.
- Marker fixtures: a fixture test module whose test method body creates a marker file; a module-level callable that creates a marker when called; a class attribute that is not a test case class; a module outside the `tests` package that creates a marker when imported (TM-1). After resolution, no marker exists.
- Nested runs (TS-8): the per-record tests generated for a fixture root are run by an inner runner whose result yields the failed test names. These are the check's own tests, never the resolved targets.

### Real repository in this worktree (IMPLEMENTATION.md D2)

The records are cleaned by sibling tasks in parallel. In this worktree, the per-record tests for records not yet cleaned fail. This is expected: list them in `final_failures`, edit no record, and do not relax SC-1 or SC-2 to make them pass. When a real record fails only because a line outside its `tests` values falls outside SC-2, report the record and the notation as a deviation instead of widening SC-2.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR7, FR4, TS-6): Fixture records covering every SC-2 form yield exactly the expected IDs per AC and nothing from opaque values. The forms covered: block `tests` lists in both the deeper and the same-indentation style, one-line flow lists including `[]`, single- and double-quoted items, trailing comments on key and item lines, AC keys other than `AC-n`, multi-line `|` and `>` `red_reason` bodies containing `tests:` and dash lines, and `baseline_failures` / `final_failures` lists.
- [ ] AC-2 (FR7, TS-6): Fixture records with, respectively, an unsupported notation on a structural line, a duplicate AC key, a duplicate `tests` key, a missing `tests` key and a missing `acceptance_tests` each fail with a message naming the record file, the AC (or the record-level marker for the missing `acceptance_tests`) and the matching reason.
- [ ] AC-3 (FR8, TS-7): A record whose every AC is `tests: []` passes. A record that cannot be decoded as UTF-8 and a record whose `tests` key has neither a value nor items each fail instead of being read as an empty list. A root without any record makes the zero-record guard fail.
- [ ] AC-4 (FR5, FR6, TS-4, TM-1): A fixture record holding IDs for a nonexistent module, a nonexistent class and a nonexistent method, an ID without the `tests.` prefix, a `path::Class::method` ID and a free-text element fails in one test, and that test's single failure message lists the file, the AC, every one of those IDs and a reason for each. An ID naming a module outside the `tests` package whose import would create a marker file leaves no marker, because the syntax gate rejects it before any import (TM-1).
- [ ] AC-5 (FR6, TS-5, TM-2): An ID naming a nonexistent method on an existing test case class is judged a failure through the loader's error path, not through an exception. Resolving the module, class and method IDs of a fixture test module whose test body creates a marker file creates no marker, and those IDs pass. IDs naming a module-level callable that creates a marker when called, and a class attribute that is not a test case class, are rejected and create no marker. A method available only through the unittest base class is rejected; a test method inherited from a non-base mixin is accepted (TM-2).
- [ ] AC-6 (FR6, TM-3): The module search path is identical before and after every resolution, including when resolution fails or raises. Fixture-root resolutions leave no fixture `tests` module in the module cache, and their outcomes are the same whether or not the real-repository tests ran before them (TM-3).
- [ ] AC-7 (FR9, TS-8): Every record under a root yields its own deterministic, unique test name. With two fixture records where the first already fails, adding an invalid ID to the second grows the set of failed test names by exactly the second record's test name.
- [ ] AC-8 (NFR1, NFR2, NFR3, TS-10): The module's own source, parsed as a syntax tree, imports only top-level modules contained in the interpreter's list of standard-library module names, and no repository or test module. `python3 -m unittest discover -s tests` run from the repository root collects and runs the module's real-repository per-record tests and the zero-record guard without any registration. `tests/test_exit4_ac2_test_id_drift.py` is unchanged and passes.

## Test Notes

- AC-1 to AC-7 are unit tests over temporary-directory fixtures; AC-8 combines a self-inspection test with a full-suite run.
- TS-1 (every real record passes) cannot hold in this worktree (IMPLEMENTATION.md D2); it is confirmed on the integrated branch.
- Edge cases worth covering: a `#` inside a quoted item is not a comment; a comment line inside an opaque body is body text; an opaque body line less indented than its key ends the body; a module that exists but raises while importing is reported with the import error as its reason.
- This task's own record cites only statically defined fixture-test methods of this module, never the generated per-record tests.
