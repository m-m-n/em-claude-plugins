# Task Plan: task0005 — Own-operator check that can return undetermined

## Goal

The FR2 own-operator check reports that a host statement holds a heredoc's
operator only when it really does. Today the check is always true, so FR2
has no effect. When the guard's two quoting readers disagree, a heredoc whose
destination is a shell is judged data and its body is not scanned. After this
task, such a heredoc is undetermined and goes to the existing fallback. This
closes review finding bc9a99dd0d07ffa5 (round 1).

## Design

### Defect being fixed

- The own-operator check (named `_statement_holds_operator()` in the
  finding) has two conditions:
  - the statement index comes from a bisect over the same statement starts
    that selected the statement, so the "operator lies inside the statement"
    condition always holds;
  - the operator position is where the heredoc operator pattern matched, so
    the "text at that position starts with `<<`" condition always holds.
- Because of this, the check never reports a missing operator.
- The harm appears when two readers disagree. The operator-context reader
  interprets `$'...'` quoting. The tokenizer that lex_segments() is built on
  does not. When they disagree, the selected statement can lack the
  heredoc's own operator, and the heredoc is still classified through that
  statement.

### Operator-start record (per statement)

- The lexing pass that lex_segments() is built on (the tracked layout pass
  named `_lex_layout(track=True)` in the finding) records operator starts
  for each statement it yields.
- A recorded start is the position of `<<` inside an unquoted, bare
  operator token that contains `<<`. This covers `<<` and `<<-`, with any
  delimiter quoting.
- Positions use the same coordinate system as the operator position in the
  heredoc recognition result (IMPLEMENTATION.md C3). The finding calls this
  the marked coordinate system.
- A token can be fused with neighbouring text, for example `cat<<EOF` or
  `>out<<EOF`. Its start is the token's own start plus the offset of `<<`
  inside it. That offset comes from the piece/offset mapping the pass
  already keeps. The finding names `_operator_token_start()` as the helper
  that finds the start.
- The record is built inside the existing pass. No additional pass over the
  input, and no additional pass per heredoc (NFR3).

### Own-operator check (FR2)

- Input: a recognized heredoc's operator position, and the statement
  selected as its host.
- The check returns "holds" only when the operator position equals a start
  recorded for that statement.
- In every other case it returns undetermined:
  - no recorded start matches;
  - the statement has no record;
  - the position cannot be mapped to the record's coordinates.
- Undetermined sends the heredoc to the existing fallback (C1).
  It is never data.
- The check is the single place where this decision is made. Its result is
  either "holds" or undetermined. The test procedures in AC-3 and AC-4 rely
  on this: they temporarily replace this one decision on a copy of the
  guard.
- Cost: one lookup per heredoc against the record of a single statement
  (NFR3).

### Unchanged

- The host statement boundaries (FR1). Heredoc recognition, including which
  operators are fake (FR5). The skipped-word and override rules (FR6, FR7).
  The existing fallback, and SHELL_SINK.
- The direction of every change follows IMPLEMENTATION.md Conventions,
  Fail-safe direction. A heredoc that is shell-sink today stays shell-sink.
