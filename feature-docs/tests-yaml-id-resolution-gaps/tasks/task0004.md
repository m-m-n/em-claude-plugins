# Task Plan: task0004 — Report test-docs scan errors as a test failure

## Goal

Directories under `test-docs/` that cannot be listed during the record scan
are reported as the failure of a test collected by the normal discovery run,
naming each directory's repository-relative path and the reason, without
stopping the module import or the checks of the records that were readable.

## Requirements

FR3, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_tests_yaml_id_resolution.py` — the record scan (collection of traversal errors), generation of the scan-error test case class, and their fixture tests

## Design

Collection:

- The traversal of `test-docs/` gets an error callback. Each directory
  listing failure is recorded as a pair: the directory's repository-relative
  path and the reason.
- A failure for the `test-docs/` root itself because it does not exist is not
  recorded; that case stays with the existing zero-record guard (SPEC FR3 and
  its edge case). Every other listing failure is recorded, including a
  subdirectory that disappears during the scan.
- enumerate_records keeps its return shape (SPEC A3, IMPLEMENTATION.md
  Shared Components). Errors are collected through a separate path — for
  example an optional error sink or a sibling entry point — that the
  module-level generation uses.

Generation and reporting:

- The single scan that generates the per-record test classes also yields the
  scan errors; they are handed to one generated scan-error test case class.
  Generation never raises because of scan errors, so the module import
  continues and the readable records keep their per-record classes.
- The scan-error test has one test method: with zero errors it passes; with
  one or more it fails with a message listing every error's
  repository-relative path and reason.
- A factory builds the class from an error list, so fixture tests can
  exercise both outcomes without touching the real tree.
- The class is a module-level TestCase subclass, so the discovery run collects
  it without registration (NFR2).
- The per-record tests and the zero-record guard are otherwise unchanged.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: For a temporary root whose `test-docs/` holds a readable record and a subdirectory whose listing raises a permission error (simulated, as SPEC TS-3 describes), the scan returns the readable record and records exactly one scan error carrying that subdirectory's repository-relative path and a reason that names the permission error (FR3).
- [ ] AC-2: The scan-error test built from a non-empty error list fails, and its failure message contains every error's repository-relative path and reason; built from an empty list, it passes (FR3, SPEC AC-3).
- [ ] AC-3: A scan error does not stop module-level generation: the readable records still get their per-record test classes and the scan-error class is generated (FR3).
- [ ] AC-4: For a root without `test-docs/`, no scan error is recorded and the record list is empty, so only the zero-record guard fails, as at base (FR3).
- [ ] AC-5: enumerate_records returns the same shape as at base for the same tree, and the existing tests that use it pass unchanged (SPEC A3, NFR3).
- [ ] AC-6: In the real repository, `python3 -m unittest discover -s tests` collects the scan-error test without registration and it passes, together with every per-record test and the zero-record guard; the checker module imports only standard-library modules (NFR1, NFR2, NFR3).

## Test Notes

- AC-1, AC-4: unit tests on a temporary root (SPEC TS-3); simulate the
  permission failure by substituting the directory-listing primitive for one
  subdirectory only.
- AC-2: build the scan-error class through the factory with a fabricated
  error list and run its test programmatically, asserting on the outcome and
  the failure message.
- AC-3: drive the module-level generation step with the simulated failure
  and assert both the per-record classes and the scan-error class exist.
- Placement: next to the existing enumeration/record tests
  (IMPLEMENTATION.md Conventions).
