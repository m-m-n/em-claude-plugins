# Task Plan: task0002 — Reject dunder method IDs and confirm the loader returns a suite

## Goal

Structural resolution rejects method IDs whose last segment is a dunder name
before Loader confirmation, and Loader confirmation turns a non-suite result
and any exception raised while walking the returned suite into that ID's
resolution error, so judging continues for later IDs. The module docstring
and the resolver-section comment state the realigned non-execution guarantee.

## Requirements

FR4, FR5, FR6, FR7, NFR1, NFR2, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_tests_yaml_id_resolution.py` — Structural resolution (dunder rejection), Loader confirmation (_loader_failure and its suite walk), module docstring, resolver-section comment, and their fixture tests

## Design

Structural resolution, FR5:

- When an ID resolves to the method form (module, class, method) and its last
  segment is a dunder name (starts with two underscores and ends with two
  underscores), resolution fails with the reason `not a test method`.
- This holds even when the TestCase subclass itself defines that name (for
  example its own `__init__`).
- The check runs before Loader confirmation, so the class is never
  instantiated for such an ID.
- Only the last segment of a method ID is subject to it; the handling of
  module and class segments is unchanged.

Loader confirmation, FR4 (flow):

1. Ask the standard loader for the ID, as at base.
2. If the result is not an instance of the standard test-suite type (SPEC
   A1), the ID fails with a reason stating that the loader returned a
   non-suite, naming the returned type.
3. Walk the suite recursively, as at base, inside the same failure-capturing
   region; an exception raised during the walk becomes the ID's reason,
   carrying the exception type and message.
4. The base restoration of the module search path and the module cache holds
   on every exit path, including the two new failure paths.

Net effect: resolve_id never raises for an ID (IMPLEMENTATION.md Shared
Components and D2). check_record is not edited by this task; its existing
loop continues with the next ID.

Documentation, FR6 (this task is the module docstring's single owner,
IMPLEMENTATION.md D3):

- Module docstring: describes the stages as SPEC FR1-FR5 specify them — two
  or more dot-separated segments; dunder method IDs rejected; Loader
  confirmation fails on a non-suite result and on an exception while walking
  it; readable IDs in an AC with extraction errors are still resolved;
  `test-docs/` scan errors are reported as a test failure — and states the
  IMPLEMENTATION.md D1 guarantee range.
- Resolver-section comment: states the D1 range. Any statement that resolved
  objects are never called or instantiated is removed.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With a fixture TestCase subclass whose own `__init__` creates a marker, resolve_id on the method ID ending in `__init__` returns `not a test method` and the marker is not created (FR5, SPEC AC-5).
- [ ] AC-2: A method ID whose last segment is another dunder name is also rejected with `not a test method`, while module IDs, class IDs and non-dunder test method IDs that resolved at base still resolve (FR5).
- [ ] AC-3: A module ID whose `load_tests` hook returns None, and one whose hook returns a plain list of test cases, each produce a resolution error for that ID, both from resolve_id and in check_record's result (FR4).
- [ ] AC-4: An ID whose loader result raises an exception during the recursive walk produces a resolution error for that ID that names the exception type, and no exception propagates out of resolve_id or check_record (FR4).
- [ ] AC-5: For one record listing an AC-3 or AC-4 failing ID followed by another ID, check_record's result contains both the failing ID's error and the later ID's judgment, and the module search path and the module cache are identical before and after the call (FR4, SPEC AC-4).
- [ ] AC-6: The module docstring and the resolver-section comment state the IMPLEMENTATION.md D1 range and the FR1-FR5 behaviors listed in Design, and neither claims that resolved objects are never called or instantiated (FR6).
- [ ] AC-7: `python3 -m unittest discover -s tests` passes and the checker module imports only standard-library modules (NFR1, NFR2).
