## Design

### Background: why the third argument matters

`commit-docs.sh` takes an optional third argument, `expected_base_tip`. When
it is supplied, the script compares it against the branch tip observed AFTER
it acquires the shared lock, and exits 4 on any divergence. That is the
authoritative staleness check: it covers the window between the caller's own
refresh+edit and the script's internal pre-lock tip read. When the argument
is omitted, only the script's weaker start-vs-under-lock comparison runs,
which cannot see that window — so a write built on a tip a concurrent
`merge-task.sh` has already moved past can still be committed. This task
removes that degraded path from the two sites that still take it.

The commit-docs helper script itself is NOT modified by this task: its third
argument, its exit codes and its RECOVERY CONTRACT already support this
change as-is.

### The uniform four-part mechanism

Both new sequences state the same four steps, in this normative order — the
refresh precedes the capture, the capture precedes the write, and the write
precedes the commit. The wording mirrors the pattern Step I.2.b steps 2-3
already use (NFR1), so all six sites read as one mechanism rather than as
per-step variants:

1. **refresh** the integration worktree —
   `git -C {integration_worktree} reset --hard em-workflow/{feature}/integration`
2. **capture** the tip —
   `{NAME}_TIP=$(git -C {integration_worktree} rev-parse HEAD)`
3. **write** the step's own workflow.yaml edit, on the worktree just
   refreshed
4. **commit** that write with the captured tip as the third argument —
   `commit-docs.sh {integration_worktree} "docs({feature}): {summary}" "${NAME}_TIP"`,
   cross-referencing the Branch & Worktree Model's exit-4 recovery for the
   exit 4 case

The variable names `LAUNCH_TIP` (Step I.2.a) and `COMPLETION_TIP` (Step I.3)
match the existing `BASE_COMMIT` / `RECONCILE_TIP` / `ROUTEBACK_TIP` /
`TERMINAL_TIP` series. The names are not load-bearing — any name consistent
with that series is acceptable — but the test module must assert whatever
names the prose actually uses. The `{summary}` text is likewise
unconstrained beyond following the document's existing
`docs({feature}): {summary}` convention.

### Site A — Step I.2.a (Launch phase)

Anchor: the existing instruction that today reads, in one sentence after the
`git worktree add -b` block —

```
Branch point = integration branch AT THIS MOMENT (includes every task merged
so far). Set `tasks.{T}.status = in_progress`, `tasks.{T}.branch` in
workflow.yaml.
```

That bare write instruction is what expands into the ordered four-part
sequence: refresh, capture `LAUNCH_TIP`, write
`tasks.{T}.status = in_progress` and `tasks.{T}.branch` into workflow.yaml on
the worktree just refreshed, then commit with `"$LAUNCH_TIP"` as the third
argument. The "Branch point = integration branch AT THIS MOMENT" statement
stays — it describes where the task branch forks from, which is independent
of the integration worktree's checkout state.

The sequence must be placed AFTER the launch-selection paragraph that opens
Step I.2.a (see the retention inventory below — a pinned ordering depends on
it) and must not disturb the resume-guard, command-approval, prompt-payload
or end-the-turn material that follows.

**Refill statement (FR5)**: the sequence states that it is entered on EVERY
entry into Step I.2.a — including the refill re-entry from Step I.2.b step 5
within the same turn — and that a fresh tip is captured each time. It states
explicitly that `$RECONCILE_TIP` is never reused as the third argument, and
why: `RECONCILE_TIP` is captured at Step I.2.b step 2, BEFORE Step I.2.b step
3's own commit advances the branch tip, so it is already stale by the time the
refill path re-enters. `$RECONCILE_TIP` may appear in Step I.2.a's text ONLY
inside that not-reused statement, never as a value passed to
`commit-docs.sh`. Whether the same point is additionally restated at Step
I.2.b step 5 is the implementer's judgment; stating it once in Step I.2.a
satisfies the requirement, and any restatement must not contradict it.

Reproduced here exactly, including the line break that falls immediately

```
When every task is `merged`: set `implement` step `status = completed`,
`completed_at_commit = $(git rev-parse "em-workflow/{feature}/integration")`.
```

Every character of that span — both lines and the newline between them —
survives untouched: not re-wrapped, not re-indented, not re-worded. All new
material goes strictly BEFORE or strictly AFTER that span. Placing the
ordered sequence immediately after it (and before the existing "There is no
other way to complete this phase" sentence) is the recommended placement.

The sequence states: refresh, capture `COMPLETION_TIP`, the workflow.yaml
write of the `implement` step's `status = completed` and
`completed_at_commit`, then the commit with `"$COMPLETION_TIP"` as the third
argument, cross-referencing the exit-4 recovery.

The sequence must not contradict the pinned sentence. Because step 1's
refresh makes the worktree's HEAD equal the integration branch ref, the
captured tip and the value the pinned sentence assigns to
`completed_at_commit` denote the SAME commit; the prose may say so, and must
never imply they differ.

## Test Notes

- Everything here is unit-level: assertions over the text of one document
  plus their negative proofs. There is no integration or e2e surface.
- **TDD order matters for the negative proofs**: capture the pre-change
  samples (verbatim excerpts of Step I.2.a and Step I.3 as they read today)
  BEFORE editing the document. After the edit those passages no longer exist
  in that form and the samples cannot be reconstructed honestly.
- Record the suite's pre-existing failures before touching anything, so a
  post-edit failure is attributed by set difference rather than
  re-investigated.
- Edge case — refill re-entry: the assertion is textual (the statement is
  present, and `RECONCILE_TIP` occurs only in the not-reused context), since
  the behavior itself is orchestrator prose with no runtime surface.
- Edge case — pin adjacency: assert the pinned sentence against the RAW
  document text, never against a normalized copy; a normalized assertion
  would pass even if the internal newline were lost, which is exactly the
  regression AC-3 exists to catch.
- Edge case — the bare-git-line invariant: after the edit, re-check every
  inserted line, since a wrap decision (not a wording decision) is what
  breaks it.
