# Task Plan: task0002 — plugin version bump in both registries

## Goal

The em-workflow plugin's version moves to the next patch level in both
registries — the plugin manifest and the marketplace entry — carrying the
identical string, so an installed plugin cache picks up this feature's
corrected protocol document.

## Requirements

FR6, NFR3

## Scope

### Files to Create
- `tests/test_exit4_tip_argument_version_bump.py` — contract-style
  assertions over the two parsed JSON registries: the version is past the
  pre-change baseline, both registries report the identical string, and the
  unrelated marketplace entry is untouched.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — the version field is bumped.
- `.claude-plugin/marketplace.json` — the em-workflow entry's version field
  is bumped to the same value.

## Design

### Why the bump is required

Installed plugins are unpacked into a version-keyed cache directory, and the
cache's freshness is decided by that version. A change under `em-workflow/`
that leaves the version untouched leaves the cache serving the old files —
the repository is correct while the code actually running is not. The rule is
therefore: files under `em-workflow/` change ⇒ the version moves in the same
change, in BOTH locations, to the SAME value.

This feature's other task edits a document under `em-workflow/`, which is
what triggers the bump. This task owns the bump exclusively; the other task
must not touch either registry, and this task must not touch any file under
`em-workflow/references/`.

### The value

Both registries currently report `0.1.44`. This feature is a documentation /
protocol correction, so the bump is patch level: both move to `0.1.45`
(IMPLEMENTATION.md D3). The two files must end up carrying the identical
string — not merely equivalent values.

Structure of each registry, for orientation:

- The plugin manifest is a single JSON object whose `name` is `em-workflow`
  and whose `version` is the value to change. `name`, `description` and
  `author` are untouched.
- The marketplace file is a JSON object with a `plugins` array. Two entries
  exist: `em-review` (no `version` key at all, `source` `./em-review`) and
  `em-workflow` (the entry whose `version` changes). Only the `em-workflow`
  entry's `version` is touched — the `em-review` entry keeps having no
  `version` key.

### Test module design (the new version-bump module)

Reads only the two registry files, parsing them as JSON — never
pattern-matching raw JSON text. Standard library only; imports no other test
module. Follows the assertion conventions in IMPLEMENTATION.md.

Two matchers, each factored out so both its positive test and its negative
proof use the same code path:

- **Baseline matcher**: the version parses as `X.Y.Z`, its major/minor are
  `0.1`, and its patch is strictly greater than 44. Expressed as a durable
  baseline rather than a fixed literal, so it does not go stale on the next
  unrelated bump — but it IS red on the un-bumped `0.1.44` tree, which is
  what makes it a real test of this task.
- **Equality matcher**: the marketplace entry's version string equals the
  plugin manifest's version string.

Each matcher carries a negative proof (a forged pre-bump `0.1.44` value for
the baseline matcher; a forged pair of differing well-formed versions for the
equality matcher) and, alongside it, a non-vacuity guard showing the forged
sample is itself a well-formed `X.Y.Z` value the parser accepts — so the
proof exercises the comparison rather than a parse failure.

The `em-review`-entry assertions (`source` unchanged, no `version` key) are
pure regression guards over retained fields and need no negative proof.

- [ ] AC-2 (FR6): the marketplace file parses as JSON; its `plugins` entry

      rather than a fixed literal.
- [ ] AC-4: each of the two matchers has a negative proof plus a non-vacuity
      guard on its forged sample.
- [ ] AC-5 (NFR3): `python3 -m unittest discover -s tests` exits 0 with no

      task's declared file set is touched.

## Test Notes

- Unit-level only: assertions over two parsed JSON documents plus their
  negative proofs. No integration or e2e surface.
- TDD sequence: write the module first and observe it red on the un-bumped
  `0.1.44` tree (both the baseline matcher and — before the marketplace edit
  — the equality matcher), then apply the bump and observe green. If the
  module is green before the bump, the baseline is wrong.
- Record the suite's pre-existing failures before touching anything, so a
  post-change failure is attributed by set difference.
- Edge case — a partial bump (one registry moved, the other not) is exactly
  what the equality matcher exists to catch; make sure it is exercised by the
  forged-pair negative proof rather than only by the live files.

## Out of Scope

- Every file under `em-workflow/references/` — in particular the
  implement-phase protocol document, owned by another task.
- The commit-docs helper script under `em-workflow/scripts/` — read-only for
  this feature.
- Any pre-existing file under `tests/`.
- The `em-review` plugin entry's own fields, and the `description` /
  `author` / `name` fields of either registry.
- Editing any other plugin's version, or introducing a version-consistency
  check into the plugin's runtime scripts.
