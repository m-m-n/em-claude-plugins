# Task Plan: task0001 — Reject a symbolic-ref integration ref in merge-task.sh and stop update-ref from following one

## Goal

merge-task.sh ends with exit 2, touching no ref and no journal, whenever
`refs/heads/<parent-branch>` is a symbolic ref (or its symbolic-ref status
cannot be determined) once the merge lock is held, and neither of its
update-ref calls follows a symbolic ref placed after that check. The script's
comments, its content pin and the integration tests are updated to match.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/scripts/merge-task.sh` — symbolic-ref rejection of the integration ref (FR1 to FR4), the no-deref option on both update-ref calls (FR7), comment updates (FR5)
- `tests/test_merge_task_journal.py` — new integration tests for TS-1 to TS-5, TS-7, TS-8 and TS-9, plus the test-local helpers they need
- `tests/test_merge_unverified_exit_doc_contract.py` — the merge-task.sh content pin value and its provenance comment (FR6)

## Design

Cross-task conventions (error policy, content pin, test rules, version
handling) are in IMPLEMENTATION.md and are not restated here.

### D1. Placement of the check (FR1, FR2)

Processing order after the merge lock is acquired:

1. Post-lock HEAD re-check — unchanged.
2. Clean-tree precondition — unchanged.
3. Merge source read from the exact task ref, and its commit-type check — unchanged.
4. **New**: symbolic-ref status of `refs/heads/<parent-branch>`, asked with
   the quiet symbolic-ref query FR1 names (its stderr discarded; the target it
   prints is never used as a ref value).
   - status 0 (a symbolic ref, dangling included) → rejection line R-SYM, exit 2.
   - status 1 (not a symbolic ref; an absent ref also answers 1) → step 5.
   - any other status → rejection line R-UNK, exit 2.
5. Parent value read by exact ref name, and its commit-type check — unchanged
   (an absent ref still ends here with its existing message).
6. Already-contained case — unchanged (no update-ref).
7. Fast-forward case → update-ref on `refs/heads/<parent-branch>` with the
   no-deref option; new value = merge source, old value = PARENT (D3).
8. merge-tree / commit-tree — unchanged.
9. Merge-commit case → update-ref with the no-deref option; new value = merge
   commit, old value = PARENT (D3).
10. Journal append — unchanged.

Step 4 sits immediately before step 5, with no other git call between them;
nothing after the lock and before step 4 updates a ref or writes the journal.

Contract of step 4 — **Precondition**: the merge lock is held and
PARENT_BRANCH has passed the pre-lock name binding. **Postcondition**: either
the run has ended with exit 2 having written no ref and no journal line, or
the query reported status 1. The branch is decided on the exit status of the
query itself — never on its output, and never on the status of a wrapper
(assignment, pipeline, condition) that could mask it.

### D2. Rejection lines (FR3)

Both go through the script's existing error helper (one line on stderr
starting with `ERROR:`, exit 2):

- **R-SYM** names PARENT_BRANCH and states that its ref is a symbolic ref
  (the words "symbolic ref" appear in the line). It may also name the target
  the query printed.
- **R-UNK** names PARENT_BRANCH, states that whether its ref is a symbolic
  ref could not be determined, and includes the query's exit status.

Neither line contains "uncommitted", "untracked" or "commit everything".

### D3. update-ref (FR7)

Only the no-deref option is added to each of the two update-ref calls on the
integration ref. The ref name, the new value, the old value (PARENT) and the
two existing failure messages stay as they are. For a direct ref this changes
neither what is updated nor the old-value comparison (NFR1).

### D4. Comments (FR5)

- The header paragraph stating that the parent value is read from the exact
  integration ref: add that a symbolic ref at that name, or an undeterminable
  answer, ends the run with exit 2 after the lock and before any ref update,
  and that both update-ref calls use the no-deref option so a symbolic ref
  placed later is never followed.
- The exit-code list's exit 2 examples: add the case of an integration ref
  that is a symbolic ref.
- The "Merge source and parent" section comment: describe step 4 (statuses
  0 / 1 / other) and the no-deref option on both update-ref calls.

Constraints already pinned by existing tests: exactly one line contains
"Parent already contains us", and the line right after it is the
merge-base ancestor check; no comment contains "manual invocation",
"merge-only" or "exercising only merge".

### D5. Content pin (FR6)

Every commit of this task that changes merge-task.sh also sets
`EXPECTED_MERGE_TASK_SH_SHA256` to the sha256 of that commit's merge-task.sh.
The comment above the constant gains an entry for this feature's task0001 in
its provenance enumeration, in the same form as the existing entries. Nothing
else in that test module changes.

### D6. Test-local helpers (tests/test_merge_task_journal.py)

- `_run_merge` gains an optional environment argument that defaults to the
  current git environment; existing callers are unchanged.
- **Parent symbolic-ref reader**: returns the ref name the integration ref
  points at, or none when it is not a symbolic ref.
- **Symref-case rejection assertion**: exit 2; one `ERROR` line naming
  PARENT_BRANCH (and, when requested, the words "symbolic ref"); no
  dirty-worktree wording; no `journal.jsonl` anywhere under the test's
  temporary directory.
- Helpers that resolve the integration branch by name (`_parent_sha`,
  `_assert_rejected_without_side_effects`, a log of the integration branch)
  follow a symbolic ref, so they are not used to judge the symref cases. Ref
  values in those cases are checked through exact lookups of the referent ref
  and the task ref, and the symbolic ref itself through the reader above.
- **Git shim builder**: writes an executable named `git` into a fresh
  directory under the test's temporary directory and returns an environment
  whose PATH starts with that directory. The shim hands every invocation to
  the real git (its absolute path resolved by the test before the shim is
  written), keeping arguments, working directory, output and exit status,
  except for one targeted pattern per mode:
  - **re-point mode (TS-8)**: the first invocation whose subcommand is
    update-ref and whose arguments include `refs/heads/<parent-branch>` — at
    any argument position, so the unmodified script is intercepted too —
    first makes `refs/heads/<parent-branch>` a symbolic ref targeting
    `refs/heads/main` through the real git, records the interception, then
    hands the original invocation to the real git.
  - **status mode (TS-9)**: every invocation whose subcommand is symbolic-ref
    and whose arguments include `refs/heads/<parent-branch>` records the
    interception and exits with a status other than 0 and 1 (e.g. 128)
    without calling git. Queries on HEAD pass through unchanged.

  Interceptions are recorded as files under the test's temporary directory so
  the test can count them. The shim environment is passed only to the
  merge-task.sh subprocess; the test's own git calls never see it.

## Test Notes

- All new tests are integration tests in the existing `TestMergeTaskJournal`
  class: subprocess runs against throwaway repositories, standard library
  only.
- Mapping: AC-1 → TS-1, TS-2, TS-3 (lock-wait helper; the mutation re-points
  the integration ref with the test's own git). AC-2 → TS-4, TS-5 (planted
  before `_run_merge`). AC-3 → TS-9 (shim status mode). AC-4 → TS-8 (shim
  re-point mode; one test per path). AC-5 → TS-7. AC-6 → TS-6 (the existing
  suites) plus review of the comments and the commit history. AC-7 → review
  of the diff.
- Setups:
  - TS-2 / TS-4: main stays at the initial commit, an ancestor of the task tip
    (fast-forward position).
  - TS-3: a side branch with one commit on top of the integration tip, on a
    file the task commit does not touch, created without changing the main
    working tree's checkout; the task commit touches a different file, so the
    unmodified script would take the merge-commit path.
  - TS-5: the target is a `refs/heads/` name that does not exist; the test
    confirms it is still absent after the run.
  - TS-8 fast-forward: confirm main's tip equals the integration tip before
    the run (already true in the base fixture). TS-8 merge-commit: advance the
    integration branch with an unrelated commit (the existing pattern), then
    move main to the integration tip and confirm the equality. With the
    no-deref option, git may either reject the update or replace the symbolic
    ref by a direct ref (SPEC.md Assumptions), so only main's value and the
    interception count are asserted.
  - TS-7: the mutation re-points the task ref, which is checked out in the
    task worktree, to a symbolic ref targeting another existing branch; the
    post-lock HEAD re-check resolves it recursively and rejects the run.
- Red phase: TS-1 to TS-4 and TS-9 fail on the unmodified script (exit 0, a
  moved referent, or no rejection). TS-5 fails only on the "symbolic ref"
  wording, because the unmodified script already rejects a dangling ref at
  the parent lookup with a different message. TS-8 fails on the unmodified
  script and still fails with step 4 alone (the re-point happens after the
  check); it passes only with the no-deref option. TS-7 pins existing
  behaviour and passes before the change — record that in the task's
  tests.yaml instead of forcing a red phase. The content-pin test fails
  between a script edit and the pin update; keep both in the same commit.
- NFR4: the shim tests do not wait on the lock and need no process control;
  nothing in the new tests sends a signal.
- Targeted run: `python3 -m unittest tests.test_merge_task_journal tests.test_merge_unverified_exit_doc_contract`;
  full suite: `python3 -m unittest discover -s tests`.

## Out of Scope

- Task-ref side code (the post-lock HEAD re-check); TS-7 only pins it.
- A pre-lock symbolic-ref check of the integration ref (detection happens
  once, after the lock).
- The already-contained path's window between step 4 and its ancestor check
  (REQUIREMENTS.md 14.1).
- Restoring or rewriting a symbolic ref found at the integration ref: on
  rejection the script leaves it as it is.
- Any file outside the Scope list, including the plugin version fields
  (NFR3).
