# Task Plan: task0002 — Preflight approval comparison trims leading and trailing blanks

## Goal

`merge-preflight.py` approves a verification command exactly when bash_guard would: the trimmed command is in the approved set. Line-break / CR rejection and the exact inner-whitespace match stay as they are, and the original command string is still emitted (FR4).

## Design

**Approval rule** (per collected entry `(component, field, command, approvable)`):
1. `approvable` is computed exactly as today in `collect_commands`, from the raw value:
   - false for a non-string value, an invalid component name, or a raw value containing a line break or CR
   - an entry whose trimmed value is empty is still skipped before this point
2. An entry is approved when it is approvable and its trimmed value is a member of the set read through `bash_guard.py --list`. The trim is the one FR4 names, identical to the trim bash_guard's `approved_for()` and its hook apply to stored and incoming commands.
3. Inner whitespace is not normalized: the trimmed value must equal a stored entry character for character.
4. The `commands[].command` of the proceed output is the original, untrimmed string, so step 10 of the skill runs, and the hook judges, the exact string that was declared.

Unchanged:
- the approval list is read once, only when there is at least one entry
- an unreadable list or malformed components stop `commands_unapproved`
- the `detail` names `component.field` only
- the script writes nothing

**Why the raw line-break check stays**: the trim also removes a trailing line break, but a command carrying a line break is never approvable (FR4, THREAT-MODEL TM-1). This keeps preflight at least as strict as the hook for multi-line values.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR4, TM-1, TS4): The workflow's `test_command` is `make test ` (trailing blank) and the approval store holds `make test`. Preflight then proceeds, and its `commands` entry for that field carries `make test ` byte for byte. The same holds for a leading blank and for a leading or trailing tab.
- [ ] AC-2 (FR4, TM-1, TS4): The store holds `make a`. A `test_command` of `make a` followed by a line break, or one containing a CR, still stops `commands_unapproved`. With the store holding `make test`, a `test_command` of `make  test` (two inner blanks) also still stops `commands_unapproved`. The stop names `main.test_command`.
- [ ] AC-3 (FR4, TM-1, TS5): Take a set of commands with leading and/or trailing blanks, some trimmed-approved and some not, and one approval store. For each command, preflight's verdict (proceed vs `commands_unapproved`) matches bash_guard.py's own approval decision for that command. The decision is made by running the plugin's `em-workflow/hooks/bash_guard.py`, not by re-implementing its rule in the test.
- [ ] AC-4 (FR6, NFR2): The existing test asserting that leading or trailing blanks are not approved by a stripped entry is replaced by AC-1's expectation. AC-1 and AC-3 fail against the pre-change script. The other approval tests still pass: exact inner match, multi-line, non-string, invalid component, approval checked last, store not written, list-call failures. The whole `tests/test_merge_preflight.py` passes.
