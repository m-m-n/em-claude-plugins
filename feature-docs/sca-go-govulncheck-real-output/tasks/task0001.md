# Task Plan: task0001 — Go SCA normalization against real govulncheck output

## Goal

Running the SCA axis on a Go project with real vulnerabilities never returns a
silent "no vulnerabilities" result: Go stream validity, severity, directness,
per-unit collapsing and fixed-version lookup follow real govulncheck JSON
output, and a real capture replaces the synthetic Go fixture in the tests.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR9, FR10, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create
- `tests/sca_govulncheck_capture.txt` — the real govulncheck JSON stdout capture, verbatim except for path placeholders
- `tests/sca_govulncheck_capture_provenance.md` — provenance note for the capture
- `tests/test_sca_go_govulncheck_real_output.py` — tests for this task's Acceptance Criteria

### Files to Modify

- `tests/test_sca_scan_normalization.py` — the synthetic GO_FIXTURE object is removed; the Go normalization tests replay the capture; the stub writer gains a raw-text mode
- `tests/test_sca_per_project_scan_binding.py` — GO_PAYLOAD becomes the capture's config-object text; the recording stub gains a raw-text mode

## Design

Shared contracts (Go normalizer, Go stream validity rule, capture fixture,
raw-text stub mode, Go token vocabulary) and conventions are pinned in
IMPLEMENTATION.md and are not restated here. This section adds the behavior
inside them.

### 1. Go stream intake (Go branch of `judge_scan_outcome`)

1. Stdout empty after stripping whitespace: not completed, `go_empty_output` (unchanged, checked first).
2. Decode stdout as a sequence of JSON values; a stdout holding one JSON document is a sequence of one. Decoding fails, the sequence is empty, or any top-level value is not an object: not completed, `go_unparseable_output`.
3. Exit status outside `{0, 3}`: not completed, `go_undocumented_exit_status` (unchanged).
4. No top-level object has a `config` key whose value is an object: not completed, `go_unparseable_output`. This replaces the Go success-structure check, so the synthetic single-object `{"vulns": [...]}` payload no longer completes (FR7).
5. Otherwise completed. The payload handed on carries the decoded objects; its internal shape is this task's choice.

The npm, cargo and pip branches keep their exact order and results (NFR5).

### 2. Stream reduction (`_merge_govulncheck_stream`)

- `osv` objects are indexed by their `id`.
- Each `finding` object yields an OSV id (its `osv` value) and a module (the `module` of its first trace frame). A finding object without a string OSV id or without a string module contributes nothing.
- Finding objects are collapsed by (OSV id, module): any number of objects, at module, package or symbol level, with any number of traces, become one advisory record holding the OSV id, the module and the OSV object for that id (an id-only record when the stream holds no `osv` object for it) (FR5).
- Reduction computes neither severity nor directness and never reads `database_specific`.
- The docstring describes the real stream shape and no longer promises single-object compatibility (FR7).

One stdout is one scan unit, so collapsing is per unit by construction.

### 3. go.mod resolution and require parsing (FR3, FR8)

Resolution:

- The go.mod to read is the unit target itself when its basename is go.mod, and the go.mod in the same directory when the target is go.sum.
- It is resolved and read only through the existing project-relative confinement and the existing confined UTF-8 read: inside the real project root, a regular file, valid UTF-8.
- Any failure (cannot resolve, outside the root, not a regular file, cannot open or read, not UTF-8) makes the unit not completed with `go_direct_manifest_unreadable`: no findings, no undetermined count, no fallback to an empty direct set.
- The file is only read; nothing is written (NFR4).

Parsing, producing the direct module set:

- `//` starts a comment that runs to the end of the line. A full-line comment contributes nothing.
- Single-line form: the `require` keyword, a module path, a version, optionally a trailing comment.
- Block form: the `require` keyword followed by an opening parenthesis opens the block; each following line up to the line holding only the closing parenthesis (a trailing comment allowed) is one entry of a module path, a version and an optional trailing comment. A line inside the block that does not have this shape contributes nothing.
- A double-quoted or back-quoted module path is unquoted before use.
- An entry is indirect when its trailing comment, with the leading `//` removed and split into whitespace-separated words, is the single word `indirect`, or has `indirect;` as its first word followed by more words. Any other trailing comment, including one that merely contains the word, leaves the entry direct.
- The direct set is the module paths of every require entry that is not indirect.
- Every other directive, in single-line or block form (`module`, `go`, `toolchain`, `godebug`, `replace`, `exclude`, `retract`, `tool`, or any unknown keyword), contributes nothing, even when it names the finding's module.
- Malformed content is not an unreadable go.mod: it only contributes no entries.

### 4. Directness, severity and undetermined counting (per collapsed advisory)

1. Direct when the module equals a path in the direct set exactly, or the module is `stdlib` or `toolchain` (FR4). Trace length plays no part.
2. Not direct: neither a finding nor counted, whatever its severity.
3. Band: every entry of the OSV object's top-level `severity` list whose `type` is exactly `CVSS_V3`, whose `score` is a string starting with `CVSS:3.0/` or `CVSS:3.1/`, and for which `_cvss_severity_band` yields a band, is considered; the highest band wins (critical, high, medium, low, none in that order). Other types (for example `CVSS_V4`), non-string scores and unparseable vectors are ignored. `database_specific` is never read (FR1).
4. No band: undetermined. A direct undetermined advisory adds one to the unit's undetermined count; it never becomes a finding and never adds a skip reason (FR2).
5. A band is mapped through the registry `severity_map`, then the existing threshold rule applies; passing yields one finding, failing drops the advisory without counting it.

### 5. Finding content

- Built through the existing finding builder: package is the module, advisory id is the OSV id, title is the OSV `summary` (else the id), summary text is the OSV `details`, affected range none, severity the mapped value, file label the unit target (all as today apart from the source fields).
- Fixed version (FR10): only `osv.affected` entries whose `package.name` equals the finding's module are considered; the choice among their fixed events follows the existing rule. With no matching entry the finding carries no fixed version.

### 6. Unit and run aggregation

- The Go unit passes the project root to the Go normalizer, as the cargo unit does.
- A returned reason becomes the unit audit's only reason, with no findings, and the unit is not completed (FR8).
- The unit audit carries the unit's undetermined count. `run_scan` sums it over every Go unit; when the sum N is non-zero it appends the note ` N go advisory with undetermined severity (go_severity_undetermined).` for N = 1 and ` N go advisories with undetermined severity (go_severity_undetermined).` for N > 1, after the existing pip notes, in both the skipped and the non-skipped summary (FR2).
- Units from different project directories keep all their findings (FR5).

### 7. Capture production (FR6)

1. In a scratch location outside the repository, create a minimal Go module whose go.mod requires a known-vulnerable dependency version directly (no `// indirect`). Importing and calling an affected symbol is recommended, so the capture holds module-, package- and symbol-level finding objects for one OSV id.
2. Run `go run golang.org/x/vuln/cmd/govulncheck@<pinned version> -json ./...` in that module and save its stdout verbatim as the capture file.
3. Replace every machine-local absolute path in the capture with a placeholder token and change nothing else. Record the placeholder tokens in the provenance note.
4. Write the provenance note with five labelled items: govulncheck version, go version, the exact command, the minimal module's go.mod (verbatim) and the capture date.
5. If no real capture can be produced (no go toolchain, no network, a failing run), stop and report blocked. Never hand-craft a stream.

The scratch module is not committed.

### 8. Test fixtures and stubs

- Both existing stub writers gain the raw-text mode (IMPLEMENTATION.md). Every Go stub prints text; npm, cargo and pip stubs keep passing values.
- Capture replays (TS1, TS2 and the rewritten Go tests of the normalization module) print the capture file's text verbatim.
- The clean stream is the verbatim text of the capture's config object, cut from the capture text. GO_PAYLOAD in the binding test module becomes this text.
- Scenario streams (TS3-TS8 and the no-config case) are built from the capture's own objects with the smallest edit the scenario needs (a replaced `severity` list, an added `affected` entry, a removed config object, a substituted module, a second module-, package- or symbol-level finding object), serialized as a multi-object stream, and printed verbatim by the stub.
- go.mod variants written into the bound unit: the provenance go.mod (direct), the same with the vulnerable requirement marked `// indirect`, the same without that requirement, one with no require at all, one holding invalid UTF-8 bytes.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR6, NFR1, NFR2; TM-6; TS9): `tests/sca_govulncheck_capture.txt` is a real capture produced by the pinned govulncheck command, and `tests/sca_govulncheck_capture_provenance.md` sits beside it. A test asserts: the capture decodes as a stream of JSON objects with at least one top-level object whose `config` value is an object and at least one `finding` object; no string value anywhere in the decoded capture begins with `/`; neither file contains `/home/` or `/tmp/`; the provenance note carries the five labelled items and its go.mod text equals the go.mod the tests use for the direct case. When no real capture can be produced, the task reports blocked and commits no hand-crafted stream.
- [ ] AC-2 (FR7, FR9; TM-1; TS6): Through `run_scan` with the Go stub printing raw text: the single-object `{"vulns": [...]}` payload, the capture with its config object removed, and a stream holding a non-object top-level value each give `skipped: true` with `go_unparseable_output` in skip_reason and no Go findings; the config-object text alone completes with findings `[]`, `skipped: false`, `skip_reason: null`; empty stdout gives `go_empty_output`; the capture with exit status 3 completes, and with an exit status outside `{0, 3}` gives `go_undocumented_exit_status`. The binding test module prints the config-object text for every Go stub and all its tests pass.
- [ ] AC-3 (FR1, FR2, FR3, FR6; TM-2; TS1, TS2): With the Go stub printing the capture verbatim and the provenance go.mod in the bound unit, the result has `skipped: false`, `skip_reason: null`, and for the capture's advisory on the directly required module either a high or critical finding (when it has a valid CVSS v3 vector) or the `go_severity_undetermined` note with the exact expected count; it is never findings 0 without that note. With the requirement marked `// indirect`, and again with it removed, the result has no finding and no undetermined count for that advisory. The Go tests of `tests/test_sca_scan_normalization.py` replay the same capture and pass.
- [ ] AC-4 (FR1, FR2; TM-2; TS3): With streams derived from the capture for a directly required module: CVSS:3.1 high plus critical vectors give one critical finding; a CVSS:3.0 high vector gives a high finding; a valid high vector plus a malformed one gives high; only `CVSS_V4`, only a malformed `CVSS_V3` vector, a `CVSS_V3` score without the 3.0/3.1 prefix, and a `database_specific.severity` with no `severity` list each give undetermined; a determinable medium band gives no finding and no count; an undetermined advisory on a module that is not direct gives no finding and no count. The note reads exactly ` 1 go advisory with undetermined severity (go_severity_undetermined).` for one and uses `advisories` for two or more; undetermined severity never adds a skip reason.
- [ ] AC-5 (FR3, FR4; TM-4; TS4): Directness: single-line and block require entries count; double-quoted and back-quoted paths match after unquoting; `// indirect` and `// indirect; <words>` mark an entry indirect, while a trailing comment that merely contains the word (for example `// not indirect`) does not; full-line comments and `module`, `go`, `toolchain`, `replace`, `exclude`, `retract`, `tool` directives (single-line and block) naming the module do not make it direct; a go.sum target resolves directness from the sibling go.mod; a single-frame trace on a module not required directly is not direct; `stdlib` and `toolchain` findings are direct with a go.mod that holds no require.
- [ ] AC-6 (FR5; TS5): Module-, package- and symbol-level finding objects, with several traces, for one OSV id and module in one unit give exactly one finding (or a count of one); the same OSV id on two different modules gives two results; two bound project units each holding the advisory give one finding per unit, each labelled with its own unit's file.
- [ ] AC-7 (FR8, NFR4; TM-5; TS7): A bound Go unit whose go.mod holds invalid UTF-8 bytes, scanned beside a completing npm unit, gives `skipped: true`, a skip_reason holding `go_direct_manifest_unreadable` combined with any other reasons sorted, de-duplicated and `+`-joined, the npm findings kept, and no Go findings or Go undetermined note. Called directly, the Go normalizer returns the same reason when the go.mod to read resolves outside the project root or is not a regular file. The project tree is unchanged after the scan.
- [ ] AC-8 (FR10; TS8): For an OSV object with two `affected` entries for different modules, each with a different fixed event, the finding's description and suggestion name the fixed version of the entry whose `package.name` equals the finding's module; with no matching entry the finding names no fixed version.
- [ ] AC-9 (NFR1, NFR3, NFR5; TM-3; TS10): With advisory summary, details and id text carrying instruction-like and absolute-path-like content, the summary and skip_reason contain none of it, only counts and fixed tokens; an advisory details text longer than the untrusted-text byte bound appears in the finding capped with the truncation marker. The new test module imports only the standard library and launches no real go, govulncheck or network access. The existing npm, cargo and pip tests pass with unchanged expectations, and `python3 -m unittest discover -s tests` and `python3 em-workflow/scripts/check-plugin-invariants.py .` both pass.

## Test Notes

- All scenario tests run `run_scan` end to end with stubs on a PATH restricted to the stub directory, except the direct normalizer call in AC-7 and any pure unit checks of the go.mod parser.
- The expected OSV id, module and undetermined count for TS1 are constants of the test module, read off the committed capture; TS9 asserts that the capture really holds that finding, so the constants cannot drift from the fixture.
- The direct-case go.mod is a constant of the test module; AC-1's test asserts the provenance note contains it verbatim.
- The two existing Go tests in the normalization module (schema conformance; transitive and below-threshold advisories dropped) keep their intent but replay the capture with the go.mod variants above. Their assertions follow AC-3, since the capture's real severity data decides between finding and note.
- Edge cases from SPEC: go.sum target (AC-5), quoted paths (AC-5), determinable below-high band (AC-4), undetermined and not direct (AC-4).
- Write TS-tagged test names or docstrings (TS1-TS10) so verification can trace each scenario.
