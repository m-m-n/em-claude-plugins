# Task Plan: task0001 — cd prefix: refuse `..` after a non-directory on the physical side

## Goal

`is_below()` in the Bash guard treats the physical path as an existing
directory only when the operating system can resolve the path exactly as
written to a directory, so a path where a regular file or a missing component
is followed by `..` is never allowed as a cd prefix. The two new forms are
pinned as silent cases in the cd-prefix test module.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

No new files.

- `tests/test_bash_guard_cd_prefix.py` — new silent path cases, the

## Design

### Contract of `is_below(path, area)` (name and parameters unchanged, SPEC A3)

- Precondition: `path` is the text written between the double quotes of the
  cd prefix (an absolute path that may still contain NUL or `..`); `area` is
  the resolved worktree area.
- Postcondition: returns a boolean and never raises.
  - True only when every condition below holds; False otherwise.
  - Any OSError or ValueError raised while resolving either path yields False
    (NFR3).
- Side effects: none. The path is resolved inside the hook process only. It
  is never used as the working directory or an argument of a child process
  (NFR4), and the hook process's own working directory is never changed to
  it.

### Terms

- **Logical path**: unchanged from today. It is the realpath of `path` after
  each `..` has been collapsed lexically against the component written before
  it (SPEC A2: this side is not touched).
- **Physical path is an existing directory**: NEW meaning (FR1). It is true
  only when the operating system's own resolution of `path` exactly as written
  ends at a directory. The kernel applies each `..` to the directory already
  reached, so a regular file, a missing component, or a link to a file or to
  a missing target placed before a `..` makes the resolution fail (not a
  directory / no such file). Then the physical path is not an existing
  directory.
- **Physical location**: the realpath of `path` as written, the same value
  as today. It is compared against `area` only after the as-written
  resolution above has ended at a directory (FR1, last sentence).

### Decision flow (branch structure unchanged)

1. Compute the logical path and the physical location as today.
2. Decide "physical path is an existing directory" by the as-written
   resolution (Terms above). Do not decide it from the realpath result alone.
3. If the logical path is an existing directory, return True only when the
   physical path is an existing directory (step 2) and the logical path and
   the physical location are both strictly below `area` (FR2).
4. Otherwise (physical-path fallback branch), return True only when the
   physical path is an existing directory (step 2) and the physical location
   is strictly below `area` (FR3).
5. Any resolution error in steps 1–4 returns False.

The caller (`is_cd_prefixed_approved`) is unchanged. A False from
`is_below()` already makes the command be judged as if it had no cd prefix,
so the excluded forms produce no new deny (FR4).

### Constraints carried from the existing tests

- Python version independence (NFR1): step 2 must not rely on whether the
  realpath function, asked for strict resolution, rejects a regular file
  followed by `..`. That behavior differs between Python versions. The kernel's
  resolution of the path as written does not.
- `TestNulInPath.test_ac5_a_resolution_error_makes_the_path_check_false`
  replaces, in turn, the realpath function and the directory-existence check
  with ones that raise. It expects False for the plain inside directory. It
  also expects True for that directory without the replacement. `is_below()`
  must keep consulting both on its normal path for an ordinary existing
  directory, so that test passes without modification.
- Standard library only, and no `status` substring in the hook's executable
  text (NFR2; `TestAc7StandardLibraryOnly`).

### Wording

No wording change is required (SPEC A4): the hook docstring and the
protocol's "Verbatim execution rule" already define the physical path as the
path resolved exactly as written, each `..` applying to the directory already
resolved, and the fixed code matches that text. If either text is touched
anyway, it keeps every term `TestPathConditionWording` checks (logical path /
physical path / strictly below / existing directory / otherwise / both, the
parenthesized `logical path (... .. ...)` and `physical path (... as written
...)` forms) and never uses the phrase "realpath of <path> is an existing
directory".

### Test additions

- `PATH_CASES` (silent, run from the main worktree by the existing AC-3
  test) gains two forms:
  - file then `..`: the file fixture followed by `/../task0001`, i.e.
    `<area>/afile/../task0001`. The logical path is the existing
    `<area>/task0001`.
  - missing component then `..`: the inside directory followed by
    `/does-not-exist/..`, i.e. `<area>/task0001/does-not-exist/..`. The
    logical path is `<area>/task0001`.
- A test that puts `/proc/self/root/..` in front of the absolute path
  `<area>/afile/../task0001` expects silent from the main worktree and from
  the git worktree. It is skipped when `/proc/self/root` is not a directory,
  the same skip condition as the existing physical-fallback AC-1 test.
- A fixture-layout guard for the added forms, in the style of the existing
  `..._fixture_layout_matches_...` tests.
- Direct `is_below()` tests use the module loaded the way `TestNulInPath`
  loads it.
- Existing cases and tests are not removed or edited. Adding a paragraph for
  this feature to the module docstring is allowed.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Calling `is_below()` directly with the area returns False for
  `<area>/afile/../task0001` and for `<area>/task0001/does-not-exist/..`. It
  returns False for both shapes again when `/proc/self/root/..` is put in
  front (when `/proc/self/root` is a directory). It still returns True for
  `<area>/task0001` and for the link-then-`..` form `<root>/hop/../sub`.
  (FR1, FR2, FR3)
- [ ] AC-2: `PATH_CASES` contains the two forms `<area>/afile/../task0001` and
  `<area>/task0001/does-not-exist/..` followed by `&& make test`, with
  expected decision silent. Through the hook they produce no output, exit
  code 0 and empty standard error. (FR2, FR4, FR5; TS-1, TS-2)
- [ ] AC-3: A test runs `cd "/proc/self/root/..<area>/afile/../task0001" &&
  make test` through the hook from the main worktree and from the git
  worktree. It expects silent each time and is skipped when `/proc/self/root`
  is not a directory. (FR3, FR4, FR6; TS-3)
- [ ] AC-4: For each form added in AC-2 and AC-3, a fixture-layout test
  asserts two facts. The operating system's resolution of the path as written
  is not an existing directory (the resolution raises not-a-directory or
  no-such-file, or the directory check is False). The lenient (non-strict)
  realpath of the same path is an existing directory strictly below the area.
  Together these show the form was allowed before this change. A second test
  replaces the realpath function with one that ignores any request for strict
  resolution and always resolves leniently. Under that replacement `is_below()`
  still returns False for the added forms and True for `<area>/task0001`, so
  the decision does not depend on strict-mode realpath. (FR5, NFR1; TS-4)
- [ ] AC-5 (TM-1): The change does not widen the allowance and adds no
  deny. Every existing case in `tests/test_bash_guard_cd_prefix.py` passes
  without modification:
  - still allow: `ALLOW_CASES`, `FALLBACK_ALLOW_CASES`, and the
    `/proc/self/root/..` + worktree-path AC-1 test;
  - still silent: `SYNTAX_CASES` and the pre-existing `PATH_CASES` entries,
    including the TM1 / TM2 cases;
  - still deny: the refusal-pattern and declared-but-unapproved tests;
  - still pass: the wording tests and the standard-library-only tests.

  `python3 -m unittest discover -s tests` passes. (FR1, FR4, NFR2; TS-5,
  TS-6)
- [ ] AC-6 (TM-2): `is_below()` starts no child process. A test calls it
  directly for the two added forms and for `<area>/task0001` while the
  standard library's child-process entry points are replaced with ones that
  fail the test. It observes no call. The existing
  `test_ac1_no_child_process_uses_the_prefixed_path` still passes. (NFR4)
- [ ] AC-7 (TM-3): `is_below()` returns False and never raises when the
  as-written resolution added in this task raises OSError or ValueError. A
  direct test replaces that resolution step with one raising each error. It
  also returns False for a NUL inserted into an added form, for example
  `<area>/afile\0/../task0001`. The existing `TestNulInPath` tests pass
  without modification. (NFR3)

## Test Notes

- AC-2, AC-3 and AC-5 are hook-level subprocess tests through the existing
  `check_cases` / `decide` helpers; `decide` already fails on a non-zero exit
  or any standard-error output.
- AC-1, AC-4, AC-6 and AC-7 are direct unit tests on the module loaded the
  way `TestNulInPath` loads it.
- TDD order: add the AC-2 / AC-3 cases and the AC-1 direct calls first. They
  fail (allow / True) against the current code. Then change `is_below()`.
- The AC-4 fixture guard compares against the lenient realpath, whose
  treatment of a regular file before `..` is the same in every supported
  Python version. Never make a test rely on what the strict mode does with
  that shape.
- `PATH_CASES` runs only from the main worktree. The `/proc/self/root` test
  in AC-3 iterates both working directories itself.
- Optional extra forms (a link to a file, or a dangling link, followed by
  `..`) may be added as silent cases. They are not required by any criterion
  (SPEC A5).

## Out of Scope

- The logical-path side of `is_below()` and its normalization (SPEC A2). No
  allowance is widened for forms whose physical path lands below the area
  while the logical `..` follows a non-directory.
- Process-dependent paths such as `/proc/self/cwd` (SPEC A6).
- Syntax conditions of the cd prefix, the approval store, refusal patterns,
  and the deny guidance text.
- Any plugin version field (`plugin.json` / marketplace entry).
