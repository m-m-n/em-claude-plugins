# Task Plan: task0003 — Plugin version bump in both registries

## Goal

The em-workflow plugin version moves from `0.1.40` to `0.1.41` in both
registries — the plugin manifest and the em-workflow entry of the root
marketplace file — with the em-review entry and every other field
untouched, and a new module pins the invariant that the two registries
agree and that the version has advanced.

## Requirements

FR8, FR9, NFR1, NFR4, NFR5

## Scope

### Files to Create
- `tests/test_spec_file_set_completeness_version_bump.py` — registry
  assertions for TS-10, with a negative proof per matcher.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — the version value advances to
  the target patch; no other field changes.
- `.claude-plugin/marketplace.json` — the em-workflow entry's version
  advances to the same value; the em-review entry and every other field are
  untouched.

## Design

Both files are JSON. The edit is a value replacement in each; formatting,
key order and every other key stay as they are, so the change reads as a
one-line diff per file. The target value is `0.1.41` (FR9), a patch bump
from `0.1.40`.

The pinning module's responsibilities:

| Responsibility | Behaviour |
|---|---|
| Both files parse | Each registry is parsed as JSON, and a parse failure is reported as a named assertion failure rather than an exception trace |
| Version advanced | The version string has the shape `X.Y.Z`; its major and minor equal the pre-change major and minor; its patch is strictly greater than the pre-change baseline patch `40` |
| Registries agree | The em-workflow marketplace entry's version equals the plugin manifest's version |
| em-review untouched | The em-review marketplace entry is located by name and its pre-change fields are asserted unchanged |
| Negative proofs | Each matcher above is run against a forged sample — a version string at the baseline patch, a mismatched pair of versions, and an altered em-review entry — and reports the violation |

IMPLEMENTATION.md **D4** governs the version assertion form: the module
asserts the durable invariant (advanced patch plus agreement between the two
registries) rather than the literal `0.1.41`, following the precedent in
`tests/test_recycled_task_id_version_bump.py` where a pinned literal was
rejected because the next unrelated bump makes it stale. The literal itself
is checked at verify time by reading both files (VERIFICATION.md, AC-9).

Registry lookup is by the entry's name field, never by array index — the
marketplace plugin list's order is not a contract.

## Test Notes

- Unit level only; the assertions parse two JSON files.
- Write the module first (tdd-testing): before the bump, the advanced-patch
  assertion FAILS (the patch equals the baseline) while the agreement
  assertion passes; after the bump both pass. Record that transition.
- Edge case: the em-review marketplace entry carries no version key at the
  base revision — the "unchanged" assertion must compare what is actually
  there rather than assume a version field exists.
- Edge case: never address the marketplace plugin list by index; look the
  entry up by name, and fail with a clear message when no such entry exists.
- The repository already contains other version-bump modules asserting the
  same manifest; run the whole suite so a stale baseline in any of them is
  caught here rather than at verify time.

## Out of Scope

- Both template documents and their contract tests — sibling tasks own them.
- Any change to the plugin description, name, source or any other registry
  field (FR9 restricts the change to the version value).
- Editing any pre-existing module under `tests/` (NFR4), including the other
  version-bump modules.
- Bumping any version other than the em-workflow plugin's.
