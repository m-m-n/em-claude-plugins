# Task Plan: task0001 — Declared Change Set section in the SPEC template

## Goal

`em-workflow/references/templates/spec-document.md` carries a
`## Declared Change Set` section inside its template body whose fixed
default membership is `feature-docs/{feature}/**` and
`test-docs/{feature}/**`, so that every SPEC rendered from this template
declares the workflow's own generated artifacts from the moment it is
written, and a new document-contract module pins that section.

## Requirements

### Files to Modify

## Design

### The inserted section

Position is fixed by IMPLEMENTATION.md's **Contract AN**: the heading
`## Declared Change Set`, placed after the `### File Structure` subsection
of `## Implementation Approach` and before `## Test Scenarios`, inside the
template's outer fenced body. Content is fixed by **Contract DM**
(rows DM-1 .. DM-9). This task realises the English half:

1. The section states the feature-specific paths the SPEC author enumerates,
   using the template's existing `{placeholder}` convention (DM-8), so a
   rendered SPEC lists its own files there.
2. It states the fixed default membership: both root literals verbatim
   (DM-1), the feature-docs members and the test-docs member enumerated
   verbatim (DM-2, DM-3), each attributed to the document that owns its
   generation by citation only (DM-4).
3. It states the two semantics: default-unless-explicitly-removed (DM-5)
   and superset/containment with the zero-implement-task instance
   (DM-6, DM-7).
4. It carries no rationale beyond what the requirements state, and
   introduces no rule that subtracts anything from the observed change set
   at verification time (DM-9).

Style (NFR3): English, `{placeholder}` form, and the same `## ` / `### `
heading structure as the surrounding template. The whole addition sits
INSIDE the outer fenced template body — the body opened by the file's first
fenced-markdown line and closed by the file's final fence line. Per
IMPLEMENTATION.md **D5**, that outer boundary is determined from the first
opening fence and the last closing fence, because the body already contains
nested fenced blocks (the architecture diagram, the API examples, the
file-structure tree).

### The document-contract module

Responsibilities, in the repository pattern named by IMPLEMENTATION.md's
Conventions:

| Responsibility | Behaviour |
|---|---|
| Position (TS-1) | The section anchor exists, and its offset in the whitespace-normalized text lies after the `### File Structure` anchor and before the `## Test Scenarios` anchor |
| Containment in the template body (TS-2) | The section anchor's offset in the raw text lies strictly between the outer opening fence and the outer closing fence, both located per D5 |
| Root literals (TS-5, spec half) | The sliced section contains both root literals of Contract MK |
| Enumeration and citation (TS-6, spec half) | The sliced section names every DM-2 member and the DM-3 member, and cites `implement-phase.md` and the phase-state / phase documents |
| Semantics (TS-7, spec half) | The sliced section states DM-5, DM-6 and DM-7, including the zero-implement-task instance |
| Negative proofs (TS-13) | Each matcher above is exercised against a verbatim captured pre-change sample of the corresponding template text and reports absence; each sample carries a retained anchor asserted positively so it cannot be silently emptied |

Section slicing runs from the section anchor to the following anchor
(Contract AN), so an assertion can never be satisfied by text belonging to
a neighbouring section. Prose assertions read the whitespace-normalized
slice; the fence-boundary and position assertions read raw offsets.

The pre-change samples are captured verbatim from the template at this
task's base revision — the surrounding `### File Structure` block and the
`## Test Scenarios` opening are the natural retained anchors, since both
survive the edit unchanged.

## Test Notes

- All assertions are unit-level document-contract checks over one file; no
  integration or E2E level applies (the project defines no E2E harness).
- Write the module first (tdd-testing): with the template unedited, the five
  positive matchers must FAIL and the negative proofs must PASS. After the
  insertion, all pass. That transition is the task's own proof that the
  matchers are meaningful — record it rather than assuming it.
- Edge case: the position assertion must not be satisfiable by a heading of
  the same text appearing in the file's leading prose (outside the fenced
  body). Locating the anchor by its offset relative to the outer fences
  (AC-1) closes that hole.
- Edge case: the `### File Structure` anchor appears once; if a future edit
  made it ambiguous, the slice would silently move. Assert the anchor's
  uniqueness where the slice depends on it.
- The whole suite (not only the new module) must be run before reporting
  done, because the repository-wide sweeps in
  `tests/test_reference_sweep.py` and `tests/test_check_plugin_invariants.py`
  read this template.
