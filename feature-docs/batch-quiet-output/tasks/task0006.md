## Design

### 1. Container name in the consumer table (SC-6)

`references/phase-state.md` is the schema owner and is correct as it
stands: `records` is a list, each element carrying the answer record's
per-field shape including a required `resolution_note`. The consumer —
`references/batch-mode.md`'s audit-item source map — is what must move to
it. Both rows that name `feature-docs/{feature}/phase-state/batch-audit.yaml`
name `records[]` (and `records[].resolution_note`) instead of `answers` /
`resolution_note`.

Three things in that table are load-bearing and stay exactly as they are:

- the auto-approved-command row keeps naming the
  `create-spec.command-approval` gate and its Step A.5 writer;
- the assumption row (`feature-docs/{feature}/phase-state/*.yaml` `answers`
  / resolution notes) is about the PER-PHASE files, whose `answers` mapping
  does exist — it is not part of this correction and must not be touched;
- both changed cells keep the `feature-docs/{feature}/phase-state/batch-audit.yaml`
  path literal and the `references/phase-state.md` citation, because
  pre-existing assertions match on them.

The two Non-packet gates rows (batch-mode.md lines for the diff-size gate
and the per-command approval fallback) already name the file without a key
and are already correct — they are out of scope and stay byte-identical.

### 2. `question_id` for the writers that carry no `gate_id` (SC-6-b, part 1)

`references/question-resolution.md`'s Batch resolution sequence is scoped by
its own step 1 to "A gate identified by a `gate_id`", and its step 7 fixes
`source: batch-decision-table`. It therefore cannot be the cited basis for
the review diff-size gate or the per-command approval fallback, neither of
which carries a `gate_id` and both of which resolve with `batch-safe-default`
/ `batch-codex-consultation`. This section declares those two writers'
`question_id` rule on its own authority, and keeps the step 7 citation for
the one writer it does reach: Step A.5's `create-spec.command-approval`
gate, whose `question_id` is that `gate_id` and whose `source` is
`batch-decision-table`.

Every `question_id` value this section prescribes conforms to the answer
object's pattern, whose owner is `references/question-packet-schema.md`
(cited, not restated):

- the two gate-id-less gates keep an identifying name of the gate itself
  (`review.diff-size-gate` is already pattern-conforming); the per-command
  approval fallback's value is stated in a pattern-conforming form rather
  than as "a per-literal-command identifier", which a raw command string
  would not satisfy — the command string itself is carried by
  `resolution_note`, which is where `## Reporting` already reads it from;
- the implement wake decline record gets a fixed, pattern-conforming
  literal instead of `null`, since the pattern admits no null.

This changes no value any writer produces today for the
`create-spec.command-approval` gate, and no gate's resolution path.

### 3. Commit reach for a writer that belongs to no phase step (SC-6-b, part 2)

The per-command approval fallback is the path
`references/command-execution-protocol.md` takes when the PreToolUse hook
is inactive. It belongs to no phase step, so "committed by the next
`commit-docs.sh` call the same phase step already makes for its own
reasons" does not hold when it fires in Step 0 / Step A / Step A.5 — before
any `commit-docs.sh` call in the run. An uncommitted record there is
destroyed by `references/implement-phase.md` I.2.b step 2's
`git -C {integration_worktree} reset --hard`, which is exactly the loss the
whole file exists to prevent.

The first writer bullet states the reach-point conditionally: inside a
phase step, the step's next existing `commit-docs.sh` call; outside any
phase step, the writer commits the record itself immediately via the same
`commit-docs.sh` path, exactly as Step A.5's batch branch already does and
for the same stated reason. The append-only paragraph's closing sentence
keeps its wording and extends its exception list to name this case
alongside Step A.5's. The writer count stays three — this adds no writer,
it completes one writer's reach-point.

### 4. Version bump (FR13)

Files under `em-workflow/` change, so both registries move to the same next
patch value on the `0.1.x` line (project rule `core-plugin-version-bump`,
IMPLEMENTATION.md D8). Both currently read `0.1.53`.
`tests/test_batch_quiet_output_version_bump.py` pins the relation, not a
literal, so it stays green unmodified.

## Test Notes

`tests/test_batch_quiet_output_audit_record_contract.py` is a unit-level
document-contract module over the raw text of `batch-mode.md` and
`phase-state.md`: standard library only, no import from another test
module, every constant re-declared locally — the same form
`tests/test_batch_quiet_output_audit_persistence.py` uses.

Red first, and this task has a genuine red for every substantive criterion
against the current tree: AC-1's `records[]` assertion, AC-4's "no step 7
citation for the gate-id-less writers" assertion, AC-5's pattern assertion
over the wake decline value, and AC-6's out-of-step reach-point assertion
each fail against the text as committed. Observe all four failing before
editing either document.

Each NEW matcher carries a negative proof over a forged sample plus a
non-vacuity guard that the forged sample is well-formed and actually found:
the container-key matcher (a forged row naming `answers`), the
citation-scope matcher (a forged section citing step 7 for a gate-id-less
writer), the `question_id`-pattern matcher (a forged section carrying
`question_id: null`), and the reach-point matcher (a forged bullet whose
only reach-point is the phase step's own call). Assertions that pin
retained wording — the assumption row, the ten gate rows, the `gate_id`
count, the three-writers sentence — are pure regression guards and are
exempt.

AC-5's pattern check compiles `^[a-z][a-z0-9._-]*$` locally and applies it
to each literal the section prescribes as a `question_id` value, so a
future value that violates the pattern fails here rather than only at
`references/question-packet-schema.md`.

TDD-awkward: there is no runtime behaviour in this task, so "red" means the
assertion fails against the current document text.
