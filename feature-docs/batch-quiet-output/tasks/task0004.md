# Task Plan: task0004 — Plugin version bump in both registries

## Goal

Because files under `em-workflow/` change in this feature, both registries
carry the same raised `version` value, so an installed copy of the plugin
refreshes its cache instead of serving the pre-change files.

## Requirements

FR13

## Scope

### Files to Create
- `tests/test_batch_quiet_output_version_bump.py` — parses both registries
  and asserts the bump and the parity.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — raise the version field.
- `.claude-plugin/marketplace.json` — raise the em-workflow entry's version
  field to the identical value.

## Design

Both registries currently read `0.1.51`. This change is a behavioural fix, so
it is a patch bump on the `0.1.x` line, applied identically in both places
(IMPLEMENTATION.md D8). Nothing else in either file changes: `name`,
`description` and `author` in the plugin manifest stay as they are, and in the
marketplace file the `em-review` entry keeps its `source` and its absence of a
`version` key.

The test module pins a BASELINE rather than a fixed literal — `(major, minor)`
is `(0, 1)` and `patch` is strictly greater than `51` — so a later unrelated
bump does not turn the module red, while the un-bumped tree does. This follows
`tests/test_batch_stop_contract_version_bump.py`, which pins its own baseline
the same way.

Both JSON files are parsed as JSON, never pattern-matched, so a malformed edit
surfaces as a parse failure with the offending path named.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR13): `em-workflow/.claude-plugin/plugin.json` parses as JSON,
      its `version` is of the form `X.Y.Z` with `(major, minor) == (0, 1)` and
      `patch` strictly greater than `51`, and its `name` still reads
      `em-workflow`.
- [ ] AC-2 (FR13): `.claude-plugin/marketplace.json` parses as JSON; its
      `plugins[]` entry named `em-workflow` carries a `version` equal, as a
      string, to the plugin manifest's, and the entry named `em-review` still
      has `source` `./em-review` and still carries no `version` key.
- [ ] AC-3: each matcher this module introduces (the baseline matcher and the
      equality matcher) has a negative proof — a forged pre-bump version and a
      forged pair of differing versions are each rejected — plus a non-vacuity
      guard showing the forged sample is itself a well-formed `X.Y.Z` value,
      so the proof exercises the comparison rather than a parse failure.
- [ ] AC-4: the module is discovered by `python3 -m unittest discover -s
      tests` from the repository root, imports the Python standard library
      only, and the whole suite passes with no pre-existing module modified.

## Test Notes

Unit-level assertions over parsed JSON; there is no runtime behaviour to
integration-test. Write the module first: against the current tree it goes red
on the baseline assertion (both registries still read `0.1.51`), which is the
observed red for AC-1 and AC-2.

`tests/test_plugin_version_parity.py` already exists and guards parity
independently; this module adds the feature-specific baseline. Do not modify
that pre-existing module.

## Out of Scope

- Any edit to a protocol document (task0001 / task0002 / task0003 own those).
- Any change to `description`, `author`, `category` or `source` in either
  registry.
- Any change to the `em-review` plugin's entry.
