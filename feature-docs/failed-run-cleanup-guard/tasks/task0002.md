# Task Plan: task0002 — plugin documentation and version bump

## Goal

Make the new guard discoverable to a plugin user by documenting it alongside
the existing guard chain, and raise the plugin version in both registries so
installed caches actually pick the change up.

## Requirements

FR1, FR11, NFR3

## Scope

### Files to Modify
- `em-workflow/README.md` — document the new guard in the bundled-hooks table
  and update the sentence describing the Bash guard chain order
- `em-workflow/.claude-plugin/plugin.json` — raise the plugin version
- `.claude-plugin/marketplace.json` — raise the em-workflow entry's version to
  the identical value

## Design

Read IMPLEMENTATION.md first: the guard chain order, the new guard's identity
and registration form, and the version value are pinned there (Shared
Components, D1, D5) and are not restated here.

### Documentation

The plugin README already carries a table of bundled hooks — one row per
script, giving the hook event it is registered for and one sentence of
behaviour — followed by a sentence naming the Bash guard chain's execution
order and explaining why the blanket-allow guard must stay last. Two edits:

1. Add one row for the new guard, in the same column shape as the existing
   rows, describing it as: denies worktree removal, integration branch
   deletion and pull-request creation for an em-workflow run whose workflow
   document contains a failed step, returning the reason so an unattended run
   can report and stop; unresolvable targets become a confirmation, demoted
   to a denial in an unattended run.
2. Update the order sentence so it names five guards in the pinned order and
   keeps its existing explanation of why the blanket-allow guard is last.

The description is written from the feature's requirements, never by reading
the guard source — this task's worktree does not contain that script, and
does not need it.

### Version bump

Both registries move to the pinned value. The marketplace entry is located by
its plugin name, never by array position: the sibling entry in that file
carries no version key at all, and position is not a contract. The repository
already owns a version-parity test that asserts the two registries agree and
that the value compares strictly greater than a recorded baseline under
component-wise numeric comparison; no new test is needed, and that existing
test is what verifies this half of the task.

### Independence note

Nothing in this task references the new guard script as a file, so this task
is complete and green in its own worktree even though the script itself is
delivered by another task.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The plugin README's bundled-hooks table gains exactly one row for
      the new guard, in the same column shape as the existing rows, naming
      its hook event and stating both the denial condition and the
      unattended-run demotion.
- [ ] AC-2: The README sentence describing the Bash guard chain names all
      five guards in the order IMPLEMENTATION.md pins and keeps its
      explanation that the blanket-allow guard runs last.
- [ ] AC-3: The plugin manifest and the marketplace entry for this plugin
      both carry the pinned version value, and no other plugin's entry is
      touched.
- [ ] AC-4: The repository's version-parity test passes: the two registries
      agree, and the value compares strictly greater than the baseline the
      test records.
- [ ] AC-5: The repository's README-content assertions still pass — every
      previously documented guard script remains named in the README, and the
      classifier side-effect section is unchanged.

## Test Notes

- No new test module is added. The version half is already covered by the
  repository's existing version-parity test, and the README half by the
  existing assertions that every bundled guard is named there.
- Run the repository-root unit test command after the edits; it is the
  verification for all five criteria in this task.
- Edge case worth a manual check while editing: the marketplace file contains
  a second plugin entry with no version key, so a positional or uniform edit
  would corrupt it — the edit must target the entry by name.
