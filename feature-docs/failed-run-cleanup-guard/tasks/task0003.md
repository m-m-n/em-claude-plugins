# Task Plan: task0003 — withhold destructive-guard's blanket allow for the new guard's targets

## Goal

Stop destructive-guard's trailing blanket allow from cancelling the new
guard's denial, by deferring on the same three command shapes, and prove it
with expectation rows that also prove nothing else lost its allow.

## Requirements

FR8, NFR1

## Scope

### Files to Modify
- `em-workflow/hooks/destructive-guard.py` — withhold the trailing blanket
  allow for the target invocation shapes
- `em-workflow/hooks/tests/destructive-guard-cases.json` — add expectation
  rows covering the new deferral and its boundaries

## Design

Read IMPLEMENTATION.md first: the target invocation shapes S1/S2/S3, the
superset invariant, and decision D2 (deferral fires on real invocations,
judged quote-aware, never on a raw substring scan) are pinned there and are
not restated here.

### Behaviour change

The hook already has exactly this mechanism for process-termination
commands: the destructive checks all still run, and only the final blanket
allow is withheld, so the other hook's verdict survives. The change extends
that withholding to S1/S2/S3, leaving every other behaviour of the hook
untouched:

- Every existing deny and ask keeps firing, unchanged, including the hook's
  own denials for a forced worktree removal and for a forced branch deletion
  — those are decided before the end of the run and are unaffected by
  whether the blanket allow would have been reached.
- A command that matches no destructive rule and none of S1/S2/S3 still gets
  the blanket allow.
- A command that matches no destructive rule but does invoke one of
  S1/S2/S3 now ends with no output and exit 0, which is what lets the new
  guard's own decision stand.

### Cost boundary

Withholding the allow does not deny anything; it hands the command back to
the auto mode classifier, whose false-positive rate is the cost NFR1 weighs
as heavily as a miss. The deferral is therefore evaluated over real
invocations only: a mention of one of the shapes inside quotes, inside a
here-document body, or inside a commit message keeps its blanket allow. This
also matches how the new guard itself treats those mentions.

### Expectation rows

The expectation suite is a data file of triples — expected verdict, label,
command — driven by a runner that reports a run producing no output as its
own distinct verdict, so "the blanket allow was withheld" is directly
expressible as an expected value. Rows to add:

- One per shape, for a command that matches no destructive rule: expected
  verdict is the no-output one.
- One per shape, for a mention inside quotes: expected verdict is allow,
  pinning the narrowness half of decision D2.
- At least one near-miss per shape that must keep its allow — for example
  listing worktrees rather than removing one, and a pull-request command
  that is not creation.
- One row proving an existing denial that overlaps a shape still denies:
  the forced worktree removal.

No existing row is edited or deleted; the file only grows.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: For a real invocation of each of the three target shapes that
      matches no destructive rule, the hook produces no output and exits 0
      instead of emitting the blanket allow.
- [ ] AC-2: A command that merely mentions one of the three shapes inside
      quotes or a here-document body still receives the blanket allow.
- [ ] AC-3: Near-miss invocations of the same command families that are not
      one of the three shapes still receive the blanket allow.
- [ ] AC-4: Every verdict the hook produced before this change is unchanged
      for every pre-existing expectation row, and no pre-existing row is
      removed or edited.
- [ ] AC-5: The expectation suite passes in full, including its unattended
      demotion check, and the added rows cover all four categories described
      in the Design section.
- [ ] AC-6: The repository-root unit test suite still passes, so the change
      breaks none of the hook's other consumers.

## Test Notes

- The verification command for this task is the hook's own expectation suite
  runner, plus the repository-root unit test command.
- New test code is not added under the plugin directory: only case data rows
  are, which keeps the distributed-content rule satisfied while reusing the
  suite that already exists for this hook.
- Edge case worth an explicit row: a compound command whose first statement
  is a target shape and whose second statement is genuinely destructive must
  still produce the destructive denial, proving the deferral suppresses only
  the trailing allow and not the checks themselves.
- The rows added here must not depend on the new guard existing: this
  suite runs one hook in isolation, and the task's own worktree contains
  no other guard.
