# Task Plan: task0001 — failed-run cleanup guard hook and its registration

## Goal

Deliver the new PreToolUse(Bash) guard that denies cleanup commands aimed at
an em-workflow run containing a failed step, together with its registration
in the plugin's Bash guard chain and its unit tests.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR9, FR10, NFR1, NFR2, NFR3, NFR4, NFR5,
NFR6

## Scope

### Files to Create
- `em-workflow/hooks/failed-run-cleanup-guard.py` — the guard script: command
  classification, target resolution, failure determination, decision output
- `tests/test_failed_run_cleanup_guard.py` — unit tests driving the script as
  a subprocess with a JSON payload on stdin

### Files to Modify
- `em-workflow/hooks/hooks.json` — add the guard to the PreToolUse Bash
  matcher group, in the position IMPLEMENTATION.md pins
- `tests/test_guardrail_hooks_migration.py` — extend the expected Bash guard
  order list so it matches the new five-entry chain

## Design

Read IMPLEMENTATION.md first: the guard chain order, the script identity and
registration form, the target invocation shapes S1/S2/S3, the decision output
contract, and decisions D1, D3, D4, D6 are all pinned there and are not
restated here.

### Processing flow

1. Read the PreToolUse payload from stdin. Anything that cannot be
   interpreted as a Bash tool call carrying a command string ends the run
   with no output and exit 0.
2. Decompose the command string into statements in a quote-aware way, so
   that a target command appearing inside quotes, inside a here-document
   body, or as an argument to another command is data and not an invocation.
3. Classify each real invocation against S1/S2/S3. Zero matches ends the run
   with no output and exit 0, before any file access.
4. Resolve the target feature and the worktree that holds its documents:
   - S1: the operand of the remove operation is the worktree path. Join it
     with the payload's working directory when it is relative, normalize it
     lexically, and accept it only when its trailing segments spell the
     em-workflow integration worktree layout — a `.claude/worktrees` segment
     pair, an `em-workflow` segment, the feature segment, and a final
     `integration` segment. Anything else yields no decision.
   - S2: the operand is a branch name. Accept only the integration branch
     spelling, taking the feature from its middle segment. The branch name
     carries no path, so the worktree is located by walking upward from the
     payload's working directory through a bounded number of ancestors and
     taking the first one that actually contains the integration worktree
     directory for that feature. Failing to locate one yields no decision.
   - S3: the feature comes from the payload's working directory ALONE. Only a
     working directory that is the integration worktree, or a descendant of
     it, resolves a feature; command arguments are never consulted, so a head
     reference or any other argument can never select a feature.
5. Detect a target that cannot be resolved statically — a variable
   expansion, a command substitution, or a glob metacharacter in the operand
   that decides the feature. This case skips the file read entirely and
   emits an ask, demoted to deny in an unattended run per the decision output
   contract.
6. Read the resolved worktree's own workflow document for that feature — at
   most one file — and determine failure exactly as decision D3 states.
7. Emit the decision: deny with a Japanese reason naming the feature and the
   failed step and instructing the caller to report and stop rather than
   clean up; or, in every other case, no output and exit 0.

### Registration

The manifest edit adds one entry in the position IMPLEMENTATION.md pins, in
the same shape as the neighbouring Python hook entries, with the standard
15 second timeout so no exception row is needed in the repository's
per-script timeout table. The existing order assertion lists the group's
script filenames verbatim, so its expected list gains the new filename in the
same position; this is what proves the new guard runs before the blanket
allow.

### Non-negotiable behaviours

- The guard never emits an allow decision.
- Every failure path is silent: broken payload, unresolved worktree, missing
  or unparsable document, unavailable parser, unexpected internal error.
- No external process is started and nothing is written.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The guard script exists at the pinned path and is registered in
      the PreToolUse Bash matcher group immediately before destructive-guard,
      in the pinned command form with the pinned timeout; the repository's
      order assertion and its manifest-shape assertions both pass against the
      edited manifest with no new exception entry.
- [ ] AC-2: Only S1/S2/S3 invocations are evaluated. Any other command, and
      any command that merely mentions one of the three shapes inside quotes
      or a here-document body, produces no stdout and exit 0.
- [ ] AC-3: Target resolution behaves as specified per shape: an integration
      worktree path resolves its feature; a non-em-workflow worktree path
      yields no decision; an integration branch name resolves its feature; a
      working directory inside the integration worktree resolves the feature
      for the pull-request creation shape, while a working directory outside
      it yields no decision even when a head argument names a branch.
- [ ] AC-4: For a feature whose workflow document has at least one top-level
      step with a failed status, each of the three shapes yields a deny whose
      reason is Japanese, names that feature and that step, and tells the
      caller to report and stop instead of cleaning up; the output shape and
      exit code match the existing hooks.
- [ ] AC-5: No decision is emitted, with exit 0 and empty stdout, for each
      of: all steps completed with the design step skipped; only
      needs_update / pending / in_progress steps present; a healthy feature
      whose free-text goal block contains the failure phrase verbatim; the
      workflow document missing; the workflow document unparsable; the
      payload itself malformed.
- [ ] AC-6: A target that cannot be resolved statically (variable expansion,
      command substitution, or a glob) yields an ask when the unattended-run
      variable is unset and a deny when it is set, and the reason tells the
      caller to rewrite the command into a statically determinable form.
- [ ] AC-7: The guard never emits an allow decision on any input exercised by
      the tests, starts no external process, and leaves the fixture tree
      byte-identical after every run.

## Test Notes

- All new test code lives in the repository-root test directory, uses the
  standard library only, and drives the script as a subprocess with a JSON
  payload on stdin, asserting exit code and parsed stdout — the contract
  Claude Code itself uses.
- Fixtures are built per test in a temporary directory reproducing the
  integration worktree layout down to the feature's own workflow document,
  so the working-directory-based resolution can be exercised without touching
  any real worktree.
- The unattended demotion is exercised by running the subprocess twice with
  the environment variable respectively unset and set, mirroring how the
  existing expectation suite covers the same demotion.
- Deliberate edge cases, each its own test: relative and absolute spellings
  of the worktree path; a trailing separator on the path; a worktree path
  that is not an em-workflow integration worktree; the force spelling of the
  branch delete flag (already owned by destructive-guard, so this guard must
  not double-decide unless the non-force flag is what was used); a healthy
  feature whose goal text quotes the failure phrase; a workflow document
  containing instruction-shaped natural language that must not influence the
  decision.
- The unmodified-tree assertion for AC-7 compares the fixture tree's file
  contents before and after the run, which is how the static-evaluation
  requirement becomes objectively verifiable rather than a source review.
- TDD-awkward area: the absent-parser path (decision D4) cannot be triggered
  by a fixture without manipulating the interpreter's module search path for
  the child process. Handle it by running the subprocess with a search path
  that shadows the parser module, asserting silence and exit 0.
