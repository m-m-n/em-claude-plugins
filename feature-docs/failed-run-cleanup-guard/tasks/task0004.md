All five findings share one root cause: the previous round narrowed the
blanket-allow deferral in `destructive-guard.py` to the integration-worktree
shapes, but neither the expectation rows that pinned the old behaviour nor
the statement decomposition the deferral judges on were carried along. The
result is a red expectation suite AND a deferral that no longer covers every
command the new guard can decide on.

## Goal

Make the blanket-allow deferral cover every command shape the new guard can
decide on again, pin that superset property with an executable check instead
of a comment-level promise, and leave both test commands green with the
recorded test results matching what actually reproduces.

## Design

Read IMPLEMENTATION.md first: the target invocation shapes S1/S2/S3, decision
D2 (the deferral fires on real invocations, judged quote-aware, and the
deferred set is a SUPERSET of the decidable set) and decision D7 (the
compound-form vocabulary and the unresolvable-marker set are a two-way parity
contract between the two guards) are pinned there and are not restated here.

### Which side moves

The two guards disagree in both directions, and only one direction breaks the
invariant. The direction that breaks it is: the new guard reaches an
invocation nested in a grouping construct and decides on it, while
destructive-guard sees the grouping token as the statement's head, matches
nothing, and emits its blanket allow — which ends the permission decision and
cancels the deny. Every such command is protection that is shipped but inert.

This task moves destructive-guard's side up to the new guard's, and does NOT
move the new guard's side down. Removing the new guard's recursion would also
restore the invariant, but only by withdrawing protection that already
shipped with task0001 and is pinned by that task's tests; the superset
property is meant to be satisfied by deferring more, never by deciding less.
No shared module is extracted: the layer structure pinned in
IMPLEMENTATION.md keeps hook scripts free of cross-imports, and this
repository's established substitute for a shared module is a duplicated
primitive pinned by a test that compares the copies. This task supplies
exactly that test.

### What must agree

1. **Grouping constructs.** Before a statement's head is matched against
   S1/S2/S3, leading grouping tokens are consumed so that the enclosed
   invocation is what gets matched. The vocabulary is D7's: subshell, brace
   group, a function body defined and invoked within the same command,
   command substitution, and an inline interpreter string. A statement whose
   head is a grouping token is not a statement that matches nothing — it is a
   statement whose real head is one level in.
2. **Unresolvable markers.** The character set that makes an operand "not
   statically resolvable" is the same set in both guards. Today one guard
   treats the bracket form as a glob and the other does not, so an operand
   using it produces an ask on one side and a blanket allow on the other, and
   the ask loses.

Nothing else about destructive-guard changes: every existing rule, every
existing deny and ask, and the blanket allow itself all stay as they are. The
deferral still only withholds the trailing allow; it never denies.

### The parity check

The invariant is currently a sentence in IMPLEMENTATION.md, which is what let
it drift. It becomes an executable check: one corpus of command strings, each
fed to both guards with a payload whose working directory is a fixture
integration worktree carrying a failed step, asserting for every member that
if the new guard emits any decision then destructive-guard emits no allow.
The corpus is data, so a later shape is added as a row rather than as new
assertion code. It carries, at minimum, one member per target shape in each
of: the plain form, each grouping construct of D7, and the unresolvable-
operand form; plus narrowness members (quoted mention, here-document body,
near miss of the same command family, unrelated command) for which the
assertion is the opposite one — the new guard stays silent and the blanket
allow survives.

### The expectation rows

Two rows added by the previous round now assert the pre-narrowing behaviour
and fail. They are corrected rather than deleted: the commands they name are
kept as explicit allow rows, so the narrowing itself stays pinned as
intentional, and a companion row per shape using an integration-shaped
operand takes over the "deferral fired" assertion. Rows for the compound and
unresolvable forms are added before the script change, so the suite first
reproduces the defect and then goes green.

Rows predating this feature are neither deleted nor re-verdicted.

### The recorded result

The previous task's test record claims a fully green suite; the tree it
describes produces two failures. The correction is not to restate a future
number: the suite is run once on the unchanged tree, and that observed result
— counts plus the identity of each failing row — is what the record carries.
This task's own record then carries the green result after the change.

## Test Notes

- Both verification commands for this task are the ones `workflow.yaml`
  already declares for the two components; no new command is introduced.
- Order matters for the expectation file: the rows for the compound and
  unresolvable forms are added first and observed failing, then the script
  change turns them green. That ordering is also what produces the
  measurement AC-1 records.
- The parity module drives both scripts as subprocesses with a JSON payload
  on stdin — the same contract Claude Code uses and the same one the existing
  guard tests use — so neither guard is imported and neither is refactored to
  be importable.
- The fixture the parity module builds is a temporary integration worktree
  layout whose feature workflow document carries a failed step, because only
  then does the new guard emit a decision at all; a corpus row would silently
  become vacuous against a healthy fixture, so the module asserts up front
  that the plain form of each shape does produce a decision.
- The unattended-run environment variable is left unset for the parity
  corpus: an ask and a deny are both "a decision" for the invariant, and
  pinning the demotion is TS-4's job, not this one's.
- Edge case worth its own corpus row: a compound command whose first
  statement is a target shape and whose second is genuinely destructive must
  still produce the destructive denial — the deferral suppresses only the
  trailing allow, never the checks.

## Out of Scope

- Extracting the shape classification into a module shared by the two hooks.
  The layer structure pinned in IMPLEMENTATION.md keeps hook scripts free of
  cross-imports; the parity check is what replaces the module.
- The opposite direction of the divergence, where destructive-guard withholds
  its allow for a form the new guard stays silent on — interpreter wrappers,
  environment-variable prefixes, here-document bodies. The invariant is a
  superset, not an equality; those cost one classifier round trip and are
  deliberately left standing.
- Removing the new guard's own recursion into grouping constructs, and any
  other change to `em-workflow/hooks/failed-run-cleanup-guard.py`.
- Any new destructive rule, and any change to an existing verdict of
  `destructive-guard.py`.
- The plugin version bump and the README (task0002's files; the version value
  pinned in IMPLEMENTATION.md is unchanged by this task).
