# Task Plan: task0001 — Refuse /proc and /dev/fd paths in the cd prefix path check

## Goal

`is_below(path, area)` returns False whenever the written path, a stage of either stage-by-stage resolution, or a followed link target lies under /proc or /dev/fd, so the attack form `cd "/proc/self/cwd/../tests" && <approved>` is never allowed, and regression tests pin this, including a hook run whose own working directory differs from the input cwd.

## Requirements

FR1, FR2, FR3, FR4, FR6, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6, NFR7

## Scope

- `tests/test_bash_guard_cd_prefix.py` — the optional process working directory parameter of the hook runner, the new test classes, the two existing tests whose expectation changes, and module docstring lines 39-40

## Design

The contracts of `is_below` and of the "under /proc or /dev/fd" predicate are pinned in IMPLEMENTATION.md Shared Components; the prose of the rule is IMPLEMENTATION.md D1, and the /proc/self/root decision is D2. This section adds only what is specific to this task.

### The exclusion runs in front of the existing rule and never replaces it

The FR1 exclusion is an additional precondition evaluated before the existing logical/physical rule. The existing rule, including its realpath and is-directory queries and the call to `resolves_to_directory`, stays on the decision path for every path the exclusion does not refuse. Existing tests replace those queries with failing or lenient stand-ins and replace `resolves_to_directory` with a stub (lines 787-795, 905-915, and the AC-7 tests of `TestNonDirectoryBeforeDotDot`); they keep their meaning only because the queries are still made (FR4, NFR4).

### Lexical predicate

A private helper of the module implementing the predicate exactly as pinned. It takes one path text and touches no file.

### Stage-by-stage resolution walk

One private helper serves both resolutions. Input: an absolute path text. Output: "clear" or "refused". It reproduces how the kernel resolves a path, stopping as soon as a stage is refused, so it never resolves anything inside /proc.

1. Start at the root directory with every component of the input still to process and a followed-link count of zero.
2. Take the next component. Skip empty and `.` components. For `..`, move to the parent of the location reached so far (the root stays the root); that location is always free of links, so its parent is its lexical parent.
3. Any other name forms the next stage: the location reached so far joined with the name. When the predicate holds for the stage, the walk is refused.
4. When the stage is a symbolic link, increase the count; beyond the bound the walk is refused. Read the link's target; when the predicate holds for the target text, the walk is refused. Place the target's components in front of the remaining ones; an absolute target restarts at the root, a relative one continues from the link's directory. Continue at step 2.
5. When the stage does not exist, the walk ends as clear. When it exists, is not a directory, and components remain, the walk ends as clear. In both cases the operating system cannot resolve any further stage of this path, so there is nothing left to check; the existing rule then decides the path exactly as it does today. Otherwise the stage becomes the location reached so far; continue at step 2.
6. When no component remains, the walk is clear.

Every location reached, including one reached through `..`, is a stage. Only the two endings of step 5 are non-failures; any other OSError or ValueError raised while probing a stage or reading a link refuses the walk.

The bound on followed links is a module-level constant equal to the Linux kernel's own limit for one resolution (40). A loop always exceeds it, so the bound is also the loop detection (NFR5).

### `is_below` flow

1. The predicate holds for the path as written: False.
2. Logical walk: the walk applied to the path with each `..` first collapsed against the component written before it (the same collapse the existing logical-path computation uses). Refused: False.
3. Physical walk: the walk applied to the path as written. Refused: False.
4. Otherwise: the existing decision, unchanged (logical/physical comparison, `resolves_to_directory`, `strictly_below`).

The existing handler that turns OSError and ValueError into False covers the whole body. The function docstring of `is_below` gains the rule in the wording of IMPLEMENTATION.md D1.

Why the lexical variants are covered: `//proc/...`, `/./proc/...` and a trailing slash are refused at step 1; `/<existing directory>/../proc/...` is refused by the logical walk (the collapsed path starts with `proc`) and by the physical walk (the `..` returns to the root before `proc`).

Why an early clear ending cannot let a refused form through: the existing rule returns True only when the physical path is an existing directory as written, and, when the logical path is an existing directory, that one too. Each such path resolves completely, so its walk visited every stage the operating system visits.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TM-1): with the hook subprocess's own working directory set so that `/proc/self/cwd/../<name>` and `/proc/self/cwd/<name>` resolve, inside the hook process, to existing directories strictly below the area, and the input cwd set to the main tree and then to the git worktree, both `cd "/proc/self/cwd/../<name>" && <approved>` and `cd "/proc/self/cwd/<name>" && <approved>` produce no output. Existing calls to `Fixture.run_hook` that omit the new parameter behave as before.
- [ ] AC-2 (TM-1): `is_below` is False for `/proc/self/cwd/<name>`, `/proc/self/cwd/../<name>`, `/proc/thread-self/cwd/<name>`, `/proc/self/fd/<N>` and `/dev/fd/<N>` for a file descriptor opened on a directory inside the area, `/proc/<own pid>/cwd/<name>`, `/proc/self/root<inside>`, `/proc/self/root/..<inside>`, and the lexical variants `//proc/self/cwd/<name>`, `/./proc/self/cwd/<name>`, `/<existing directory>/../proc/self/cwd/<name>` and a trailing slash, including forms whose final resolution is an existing directory strictly below the area.
- [ ] AC-3 (TM-2): `is_below` is False for a link inside the area whose target is `/proc/self/cwd`, a link inside the area whose target is `/dev/fd/<N>`, and a link inside the area whose target is `/proc/self` followed by `/cwd/<name>`.
- [ ] AC-4: `is_below` is True for directories inside the area named `proc`, `procfoo`, and `dev/fd`, and for the existing in-area form and the `@HOP@/../sub` form. The lexical predicate is true for `/proc`, `/dev/fd`, `//proc/x`, `/./proc/x` and `/proc/x/`, and false for `/procfoo`, `/dev`, and `<area>/proc`.
- [ ] AC-5 (TM-1): `cd "/proc/self/root/..<worktree path>" && <approved>` produces no output from the main tree and from the git worktree (the changed existing test), and the final assertion of `test_ac1_proc_self_root_dotdot_in_front_changes_nothing` expects False. - [ ] AC-6 (TM-3, TM-4): `is_below` is False for a link loop inside the area and for a chain that exceeds the followed-link bound, and False when an OSError or ValueError is raised while a stage is probed or a link target is read. Through the hook, a cd prefix form using the loop or the over-bound chain exits with code 0, writes nothing to stderr, and is not allowed.
- [ ] AC-7: `python3 -m unittest discover -s tests` passes; every existing expectation other than the two above is unchanged, including lines 870-915 and the NUL, resolution-error and lenient-realpath cases; `bash_guard.py` imports only standard-library modules and its executable text contains no `status` substring; the path check starts no child process for the added forms either; `is_below` keeps the parameters `(path, area)` and `is_cd_prefixed_approved` calls it unchanged; the /proc-dependent tests skip when `/proc/self` is not a directory.
