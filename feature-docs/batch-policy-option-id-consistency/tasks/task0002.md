# Task Plan: task0002 — Document the correspondence rule and the uncheckable-gate exemption registry

## Goal

The rule that a select gate's policy option_id must be offered by its issuing
site, the canonical declaration format that rule is expressed in, and the
registry recording any gate that cannot be checked mechanically, all exist as
plugin documentation instead of being implicit in test code.

## Requirements

FR6, NFR3, NFR4

## Scope

### Files to Create
- `em-workflow/references/gate-option-vocabulary.md` — the correspondence rule, the canonical declaration format, and the exemption registry
- `tests/test_gate_option_vocabulary_doc.py` — asserts the documentation states the rule and the format, and that every exemption row carries a reason and a compensating guarantee

### Files to Modify
- `em-workflow/references/batch-policies.yaml` — its header comment gains a pointer to the correspondence rule document, with no change to any gate entry
- `em-workflow/references/question-resolution.md` — the protocol-error step gains a pointer to the same document

## Design

### The rule document

Contains, and nothing beyond:

1. **The correspondence rule.** For every gate whose policy entry is
   `action: select` with an `option_id`, that option_id must be among the
   option_ids the gate's issuing site declares. The policy file is the
   authoritative side: reconciliation always moves the issuing site toward the
   policy, never the reverse.
2. **Why it matters.** Applying a policy whose option_id the gate does not
   offer reaches the batch resolution sequence's protocol-error abort, which
   stops a run at a non-blocking preference gate. The rule exists to make that
   abort unreachable at every listed select gate.
3. **The canonical declaration format**, exactly as pinned in
   IMPLEMENTATION.md's Shared Components: the dedicated level-2 heading, the
   three-column table, one row per offered option, backtick-quoted gate_id and
   option_id, prose meaning.
4. **Why the format uses its own heading** rather than the contract heading
   the output validator already parses: that heading is a machine-read surface
   of a frozen script, and reusing it would begin enforcing policy option_ids
   against the existing fixture corpus. This is stated as the reason the
   format is what it is, so a future editor does not "simplify" it back.
5. **Where the issuing-site map is pinned**: the correspondence-check module
   under `tests/`. The document cites it and does not restate its rows
   (IMPLEMENTATION.md D2) — one map, one place.
6. **The exemption registry**, per IMPLEMENTATION.md's Shared Components:
   a table of gate_id, the reason mechanical checking is not possible, and the
   compensating guarantee that stands in its place. The document states that
   this registry is the only source of exemptions, that the checker holds no
   exemption list of its own, and that an absent registry means zero
   exemptions. At the end of this feature it holds zero rows, and the document
   says so in words as well as by the empty table.

The document introduces no policy decision and no gate's option vocabulary of
its own, so `batch-policies.yaml` remains the single policy table (NFR4). It
states this about itself explicitly.

### The two pointers

The policy file's header comment and the resolution protocol's
protocol-error step each gain a short pointer to the rule document. Neither
gains a restatement of the rule, and no gate entry, option_id or resolution
step changes.

### Wording constraints

An existing suite check forbids the phrase "decision table" (and its Japanese
equivalent) in the policy file and the resolution protocol; the new document
follows the same discipline. Both pointers are additions placed so that no
existing section-scoped assertion over those two files is disturbed.

## Test Notes

- Unit: presence and content assertions over the new document (rule statement,
  format specification, registry columns, the only-source and absent-means-
  empty statements), each scoped to the section that must carry it rather than
  to the file as a whole.
- Unit (hermetic): the registry parser against synthetic documents — a row
  missing its reason, a row missing its guarantee, a row naming a
  non-select gate, and a well-formed row — proving each verdict.
- Unit: the two pointer additions, asserted at the file that must carry them,
  plus the absence of the forbidden phrase in both.
- Non-vacuity: the empty-registry case must not make the registry assertions
  trivially true; the synthetic cases are what keep them meaningful.
- The correspondence check itself belongs to a sibling task; this task asserts
  nothing about the vocabulary blocks in the issuing documents, which do not
  exist in this worktree.
