# Task Plan: task0001 — Declare every select gate's option vocabulary and pin the correspondence mechanically

## Goal

Every `action: select` entry in `em-workflow/references/batch-policies.yaml`
has an issuing document that declares and offers the option_id the policy
names, and the repository-root unittest suite fails whenever that
correspondence breaks.

## Design

### What each issuing document gains

One `## Gate option vocabulary` section per document, in the canonical block
form pinned in IMPLEMENTATION.md's Shared Components. Every row states one
offered option of one gate, with its meaning in one sentence. The rows to
produce, per gate:

| gate_id | the option_id the policy names | the rest of that gate's vocabulary, taken from the prose already present at the site |
|---|---|---|
| `create-spec.feature-identity` | `derive_from_task_description` | the freeform feature-name entry the interactive path already describes (describe it in prose beneath the table if it is not an option_id) |
| `create-spec.design-step` | `decide_autonomously` | the ask-the-user counterpart already present in the design-step question the analyst raises |
| `create-spec.design-system` | `top_candidate_or_none` | the three `kind` values step 11a already documents |
| `design-system.reclassify` | `em_workflow` | the other `kind` values the reclassification gate can resolve to |
| `create-spec.artifact-overwrite` | `preserve_and_reuse` | the overwrite and abort branches the digest-mismatch paragraph already describes |
| `design.artifact-overwrite` | `preserve_and_reuse` | same three, identical semantics across the family |
| `create-plan.artifact-overwrite` | `preserve_and_reuse` | same three, identical semantics across the family |
| `create-spec.stalled` | `record_tbd` | the other two branches of the three-way stalled gate |
| `create-plan.tbd-resolution` | `assume` | the other two branches of the TBD decision point |
| `create-plan.license-conflict` | `compatible_alternative` | the other branches of the license decision point |
| `create-plan.existing-files` | `merge` | the other branches of the existing-files decision point |

Rules that hold for every row:

1. The policy-named option_id is written exactly as `batch-policies.yaml`
   writes it. No policy value is renamed, and `batch-policies.yaml` is not
   modified by this task at all.
2. The non-policy option_ids are new identifiers minted for choices the site's
   prose already offers — the prose is the source of the meaning, the
   identifier is what was missing.
3. Semantics are stated for every option, including the ones that only the
   batch path uses.
4. The two documents that declare the same gate (a contract and its agent
   prompt) offer the same option_id set for that gate.

### The frozen machine-read surface

IMPLEMENTATION.md's "Frozen machine-read surface" contract governs this task
in full. Restated only as it applies here: the new sections use the dedicated
vocabulary heading; no contract gains a gate-identifiers heading it does not
already have; the analyst contract's existing gate-identifiers section is left
as it is, with the new vocabulary section placed outside it.

### The check module

Structured in two independent halves:

1. **Hermetic half** — the parser and the correspondence decision are
   exercised against synthetic document trees built in temporary directories,
   so every negative case (a mutated policy option_id, a vocabulary block that
   omits the option, an option_id that appears only in an unrelated field, a
   malformed row) is proven to fail rather than assumed to.
2. **Repository half** — the same decision applied once to the real
   repository: for each entry of the pinned issuing-site map, the policy's
   option_id must be among the option_ids that gate's declaring documents
   offer.

The issuing-site map is this module's own pinned data (IMPLEMENTATION.md D2).
Exemptions come only from the documented exemption registry, and an absent
registry file means zero exemptions (IMPLEMENTATION.md D3) — this task must
stay green in its own worktree, where that registry does not yet exist.

Frozen-file assertions in this module compare the recorded content of the two
frozen files and of the design-step fixture against digests captured from the
current tree, and compare the pinned line of the existing validator test
module against its recorded text.

### The policy-structure half in the existing module

The module that already pins the policy file's structure gains: the explicit
expected set of select gates (so a newly added select gate fails until it is
deliberately registered), the assertion that the two non-select gates carry no
option_id, and the assertion that the intentionally unlisted gate is neither
in that set nor reported as missing.

## Test Notes

- Unit (hermetic, synthetic trees): the block parser (well-formed, malformed
  row, absent section, section present but empty), the correspondence decision
  (member, non-member, mutated policy value), the on_unanswered
  disambiguation, and the absent-exemption-registry degrade.
- Integration (real repository): the full correspondence sweep over the pinned
  map, the two regression pins, and the frozen-file digest pins.
- Non-vacuity: every real-repository assertion needs a companion synthetic
  case proving the same matcher reports failure when the fact is untrue —
  otherwise a parser that silently returns nothing would pass everything.
- TDD-awkward: the frozen-file digest pins can only be written after their
  digests are read from the current tree; write them as failing placeholders
  first, then fill in the recorded values, so the assertion is exercised in
  both directions.
- Watch for section-scoped assertions in other existing modules when choosing
  where to place each new section; the whole suite, not just the two modules
  this task owns, must be green.
