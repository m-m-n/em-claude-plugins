# Task Plan: task0001 — Post-lock identity re-check and merge source from the verified task ref

## Goal

merge-task.sh merges only the task branch it verified before waiting for the
merge lock: right after the lock it re-checks HEAD's symbolic ref, and it reads
the merge source from the verified task ref instead of HEAD. A regression test
pins the rejection of a branch switch made during the lock wait, and the
content pin follows the new script.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/scripts/merge-task.sh` — post-lock symbolic-ref re-check, merge source read from the verified task ref, comment updates
- `tests/test_merge_task_journal.py` — post-lock regression tests and their shared lock-wait harness
- `tests/test_merge_unverified_exit_doc_contract.py` — content pin set to the new script's sha256

## Design

### Terms

- **Verified task ref**: the ref the pre-lock identity binding compares HEAD's
  symbolic ref against (`IB_EXPECTED_REF`). In the test fixture it has the
  shape `refs/heads/em-workflow/feat/<task>`.
- **Side-effect-free rejection**: exit 2, the integration branch ref is
  unchanged, no `merge: <task_id>` commit exists, and no `journal.jsonl` is
  written. The test module already has a helper asserting exactly this
  (`_assert_rejected_without_side_effects`); the new tests reuse it.

### merge-task.sh processing order after the change

1. **Pre-lock identity binding — unchanged (FR1).** Layout, TASK_ID match,
   parent-branch match and the HEAD-symbolic-ref check keep their order,
   their exit 2 and their placement before the lock.
2. **Merge lock acquisition — unchanged.**
3. **Post-lock re-check — new (FR2, FR3, NFR1, TM-1).** Immediately after the
   lock is acquired, read HEAD's symbolic ref again with the same quiet query
   the pre-lock binding uses, and compare it with the verified task ref.
   - Equal: continue.
   - A different ref: emit one `ERROR:` line on stderr naming both the
     expected ref and the ref found, then exit 2.
   - Detached HEAD, or the query fails: emit one `ERROR:` line on stderr
     naming the expected ref and stating that HEAD is detached or cannot be
     resolved, then exit 2.
   - Placement: before the worktree-clean check, and before the merge-tree,
     commit-tree and update-ref steps and every journal append. Only the
     symbolic ref is re-checked; layout, TASK_ID and parent-branch checks are
     not repeated (A2).
4. **Worktree-clean check — unchanged.** It still inspects the current
   checkout (A3).
5. **Merge source — changed (FR4, NFR1, TM-2).** HEAD_SHA is resolved from the
   verified task ref, not from HEAD. When the ref does not resolve to a
   commit: one `ERROR:` line, exit 2, before any merge-tree, commit-tree,
   update-ref or journal append. The already-contained, fast-forward and
   merge-commit paths all use this one value. A new commit made on the same
   task branch during the wait is therefore merged (A1).
6. **Everything after — unchanged** (merge, `merged` journal append, output).

### Error-line contract

- Existing channel only: stderr, the existing `ERROR:` prefix, exit 2. No new
  exit code, environment variable, argument or test hook (NFR2).
- Wording is the implementer's choice, with two constraints: it contains the
  expected ref and either the ref found or a statement that HEAD is detached
  or unresolvable; and it shares no wording with the existing worktree-dirty
  error, so a test can tell the two apart (FR3).

### Comment updates (FR5)

Three sites in merge-task.sh:

| Site | New content |
|---|---|
| Header paragraph stating that rejections finish before the merge lock | Pre-lock rejections still finish before the lock; one identity re-check runs right after the lock; the merge source comes from the verified task ref |
| Identity-binding block comment | The binding has a pre-lock part and a post-lock symbolic-ref re-check |
| Concurrency note | The lock-wait window, and how the re-check plus the ref-sourced HEAD_SHA close it |

Fixed properties that must hold afterwards (A5): exactly one line contains
'Parent already contains us', and the line right after it holds the
`merge-base --is-ancestor` check; no comment contains 'manual invocation',
'merge-only' or 'exercising only merge'.

### Content pin (FR6)

`EXPECTED_MERGE_TASK_SH_SHA256` in the doc-contract test equals the sha256 of
the final merge-task.sh bytes. Every commit that changes merge-task.sh updates
the pin in that same commit, so the doc-contract test passes at each commit.
The test's other fixed properties stay as they are.

### Regression test harness (FR7, NFR3)

One shared harness in `tests/test_merge_task_journal.py` runs every new
post-lock test. It takes a mutation step from the caller and runs:

1. Build the throwaway repository, integration branch and task worktree with
   a commit to merge on the task branch, using the module's existing fixture
   helpers.
2. The test process acquires the merge lock, the same way the existing
   locked-run rejection test holds it.
3. Launch merge-task.sh from the task worktree as the test's own child
   process, capturing stdout and stderr.
4. Poll the process table until a process whose parent is the launched child
   and whose command name is `flock` appears. The deadline is about 10
   seconds on a monotonic clock; no appearance by then fails the test. No
   fixed sleep is used as synchronization.
5. Run the caller's mutation in the task worktree.
6. Release the lock.
7. Wait for the child to exit with an upper bound; exceeding it fails the
   test.

On every exit path (assertion failure, timeout, exception) the harness
releases the lock if it still holds it, then terminates and reaps the launched
child through its own handle if the child is still running. It never signals
any other process and never kills by pattern. The flock grandchild finishes on
its own once the lock is released.

New tests on top of the harness:

| Mutation during the wait | Expected outcome | VERIFICATION.md |
|---|---|---|
| Switch to a newly created branch at the current commit | Side-effect-free rejection; ERROR names both refs | TS-1 |
| Same switch, then create an untracked file before release | Side-effect-free rejection with the identity ERROR; no worktree-dirty wording | TS-2 |
| Detach HEAD | Side-effect-free rejection; ERROR states detached or unresolvable | TS-5 |
| Delete the verified task ref | Side-effect-free rejection with an ERROR line | TS-6 |
| Add a new commit on the same task branch | Exit 0; the integration branch contains that commit; a `merged` event for the task | TS-7 |

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TM-1; FR2, FR7, NFR1): With the test holding the merge lock and merge-task.sh waiting on it from a task worktree whose task branch has a commit to merge, switching the worktree to a newly created branch and then releasing the lock makes the run exit 2 with a stderr ERROR line that contains both the verified task ref (`refs/heads/em-workflow/feat/<task>` in the fixture) and `refs/heads/<other>`; the rejection is side-effect-free (integration branch ref unchanged, no 'merge: <task_id>' commit, no journal.jsonl). The test fails against the pre-change script.
- [ ] AC-2 (TM-1; FR3): Same procedure, with an untracked file created in the worktree after the switch and before the lock is released: exit 2, the ERROR line is the identity mismatch naming both refs, stderr contains none of the worktree-dirty error's wording, and the rejection is side-effect-free.
- [ ] AC-3 (TM-1; FR2, NFR1): Same procedure, detaching HEAD instead of switching branches: exit 2, an ERROR line naming the expected ref and stating that HEAD is detached or unresolvable, and the rejection is side-effect-free.
- [ ] AC-4 (TM-2; FR4, NFR1): HEAD_SHA is resolved from the verified task ref, never from HEAD, and that single value feeds the already-contained, fast-forward and merge-commit paths (checked on the diff). Same procedure, deleting the verified task ref during the wait: exit 2 with an ERROR line and a side-effect-free rejection. Same procedure, adding a new commit on the same task branch during the wait: exit 0, the integration branch contains that commit, and journal.jsonl holds a `merged` event for the task.
- [ ] AC-5 (FR1, NFR2): Every test that existed in `tests/test_merge_task_journal.py` before this task (fast-forward, merge commit, already contained, conflict, concurrent merges, and the pre-lock rejections including the locked-run test bounded by LOCKED_RUN_BOUND_SECONDS) passes with its body unchanged. merge-task.sh gains no environment variable, test hook or argument, and its usage, exit-code meanings (0/1/2), MERGED: / CONFLICT: / ERROR: formats and journal line format are unchanged.
- [ ] AC-6 (FR5, FR6): The header paragraph, the identity-binding block comment and the concurrency note describe the post-lock re-check and the HEAD_SHA source; exactly one line contains 'Parent already contains us' and the next line holds the `merge-base --is-ancestor` check; no comment contains 'manual invocation', 'merge-only' or 'exercising only merge'; EXPECTED_MERGE_TASK_SH_SHA256 equals the sha256 of merge-task.sh in every commit that changes the script; `python3 -m unittest tests.test_merge_unverified_exit_doc_contract` passes.
- [ ] AC-7 (NFR3, NFR4): The new tests use only stdlib unittest and throwaway git repositories under temporary directories, synchronize through the flock-child poll (about 10 seconds on a monotonic clock, failing when the child never appears) rather than short sleeps, bound the wait for exit, and on every failure path release the lock and terminate and reap only the test's own child through its handle, with no pattern-based kill. `python3 -m unittest discover -s tests` passes from the repository root. The task modifies no file outside its file set; `em-workflow/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` stay untouched.

## Test Notes

- Write AC-1, AC-2 and AC-3 first: against the pre-change script AC-1 and
  AC-3 exit 0 with a `merged` event, and AC-2 reports the worktree-dirty
  error, so all three fail before the fix.
- AC-4's ref-deletion and same-branch-commit tests guard fail-closed handling
  and A1; they may already pass before the change. The ref-deletion run may be
  rejected by the worktree-clean check rather than by the merge-source
  resolution; AC-4 requires only exit 2, an ERROR line and no side effects.
- The HEAD-versus-ref distinction itself (a switch after the post-lock
  re-check, A3) cannot be produced deterministically without a test hook,
  which NFR2 forbids. It is checked on the diff (VERIFICATION.md TS-9), not by
  a timing-dependent test.
- The flock process must be a direct child of the launched merge-task.sh
  (FR7). If it turns out not to be, report that as a plan deviation instead of
  widening the search to grandchildren.
- The suite runs on Linux with /proc (A4); add no skip for hosts without it.
- Compute the pin only after the last edit to merge-task.sh in that commit.
- Targeted run while iterating:
  `python3 -m unittest tests.test_merge_task_journal tests.test_merge_unverified_exit_doc_contract`.

## Out of Scope

- Repeating the layout, TASK_ID or parent-branch checks after the lock (A2).
- Guarding against a switch after the post-lock re-check beyond reading
  HEAD_SHA from the verified task ref (A3).
- Changing any other script, skill or reference that calls or describes
  merge-task.sh. If another document states that every merge-task.sh
  rejection finishes before the merge lock, report it as a plan deviation
  rather than editing it.
- Plugin version fields (NFR4).
- A skip path for hosts without /proc (A4).
