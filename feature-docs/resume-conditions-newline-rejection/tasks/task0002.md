# Task Plan: task0002 — Bump the em-workflow plugin version in both registries

## Goal

Both distribution manifests carry the same new em-workflow patch version,
strictly greater than the pre-change value, and a regression module pins
that pairing so a forgotten bump turns the suite red.

## Requirements

FR10, NFR1, NFR3, NFR4

## Scope

### Files to Create

- `tests/test_resume_conditions_newline_rejection_version_bump.py` — the
  per-feature regression module: the two manifests agree on the version and
  the version is past this feature's baseline, each assertion paired with a
  negative proof and a non-vacuity guard.

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — the version field.
- `.claude-plugin/marketplace.json` — the version field of the plugins[]
  entry whose name is em-workflow.

## Design

### The bump

`.claude/rules/core-plugin-version-bump.md` requires a version bump in the
same change whenever a file under `em-workflow/` changes; this feature
changes `em-workflow/references/batch-terminal-line.md`, so the bump is
required. The increment is a patch increment (assumption A3): the change
is a correction to documented behaviour, not a feature addition and not a
compatibility break.

Both manifests currently read `0.1.84`. The new value stays on the `0.1.x`
line, has a patch component strictly greater than `84`, and is written
identically as a string into both places. The em-review entry in the
marketplace manifest is not touched.

### The regression module

The module follows the pattern already established by this repository's
other per-feature version-bump modules:

- Both manifests are parsed as JSON; a parse failure is reported as an
  assertion failure naming the file, never as an uncaught decode error.
- The marketplace entry is located by its `name` field, never by array
  position — the plugin list's order is not a contract.
- Version comparison is per-component and numeric, over a tuple of integers
  parsed from the dot-separated string — never a whole-string comparison,
  which sorts a two-digit component backwards.
- The baseline pinned by this module is this feature's pre-change value
  (`0.1.84`), so an un-bumped tree goes red. No existing module pins a
  baseline that high — the highest is `0.1.82` — which is why a new module
  is added rather than an existing one edited (IMPLEMENTATION.md D4).
- The em-workflow version is asserted past baseline in both manifests and
  asserted equal between them. The em-review entry's identity fields are
  asserted unchanged and its version is asserted by shape only (a dotted
  numeric string), never against a literal value, since that plugin's
  version changes independently.

### Matcher inventory and proofs (NFR3)

| Matcher | Negative proof | Non-vacuity guard |
|---|---|---|
| version-past-baseline | a forged pre-bump version string equal to the baseline, and one below it, are rejected | the forged strings parse cleanly, so the proof exercises the comparison rather than a parse failure |
| versions-agree | a forged pair of differing well-formed version strings is rejected | both forged strings parse cleanly |
| entry-lookup-by-name | a forged manifest holding no em-workflow entry raises rather than returning a default | the lookup against the real manifest returns a mapping that has a version key |

A comparison-trap case is included: a version pair where whole-string
comparison and per-component numeric comparison disagree because of a
two-digit patch component, proving the helper uses the numeric form.

### Dependency discipline (NFR1)

The new module imports only the Python standard library, and asserts that
fact about its own source.

## Test Notes

- All criteria are unit-level assertions over parsed JSON, except AC-5's
  full-suite outcome and AC-6's exit code, which are command-level: a suite
  cannot assert its own full-suite result without recursion, so both are
  verified by running the commands and recording the result in the
  implementer report.
- TDD order: write the regression module first with the baseline pinned at
  the pre-change value. It goes red against the un-bumped manifests; edit
  both manifests until it goes green.
- Edge case worth covering: the marketplace manifest holds more than one
  plugin entry and the em-review entry has a different version line, so a
  lookup by array position or a version assertion against a literal would
  pass or fail for the wrong reason.
- Before touching any file, record which tests are already failing on the
  base revision.

## Out of Scope

- Any change to `em-workflow/references/batch-terminal-line.md` or

  (IMPLEMENTATION.md D2 and the declared file-set disjointness).
- Any change to the em-review plugin's version or to any other marketplace
  entry.
- Raising the baseline of any pre-existing version-bump module: each one
  records its own feature's bump and editing it would falsify that record
  (IMPLEMENTATION.md D4).
- Any change to the plugin description fields in either manifest.
