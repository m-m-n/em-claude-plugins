# Task Plan: task0001 — Keep the wrapper-args harness out of the caller's cache

## Goal

`_run_wrapper_pid()` in `tests/test_codex_hook_wrapper_args.py` stops handing
the caller's `XDG_CACHE_HOME` to the wrapper, so a run of the module creates
nothing in the caller's cache directory, and a recurrence test with its
negative proof pins that behavior.

## Requirements

FR1, FR2, FR3, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_codex_hook_wrapper_args.py` — the harness's environment construction drops XDG_CACHE_HOME; a shared cache-leak checker, the recurrence test and its negative proof are added; the module and harness docstrings mention the new isolation.

## Design

### Harness change (FR1)

- `_run_wrapper_pid()` builds the wrapper's environment from a copy of the
  caller's environment. Today it overrides `PATH`, `HOME` and
  `CODEX_STUB_LOG` and removes `CODEX_OTLP_ENDPOINT` and `CODEX_HOME`. It
  additionally removes `XDG_CACHE_HOME`, at the same point and in the same
  way as those two removals.
- Order contract (unchanged): every removal happens first, then `extra_env`
  is applied. A caller that names `XDG_CACHE_HOME` in `extra_env` still gets
  that value into the wrapper's environment. The negative proof below relies
  on this order.
- Postcondition: when no `extra_env` entry names it, the wrapper sees no
  `XDG_CACHE_HOME`. The `--litellm` path then places its launch-home parent
  under the harness's isolated `HOME`, which lies inside the harness's own
  temporary directory and is removed when the run ends.
- The harness docstring states the new removal next to its existing
  isolated-HOME statement.
- `_run_wrapper`, `_launch_record` and `_launch_argv` all go through
  `_run_wrapper_pid()` and need no change (SPEC A-2).
  `_run_command_through_shell` does not launch the wrapper and is left as it
  is.

### Cache-leak checker (shared by FR2 and FR3)

- A snapshot of a directory is the set of relative paths of every entry
  beneath it, recursively. The directories this task inspects start empty,
  and the wrapper only creates directories there, so names are enough.
- One module-level checker takes a directory and the snapshot taken before a
  launch. When the directory's current snapshot differs, it raises an
  assertion failure whose message names the entries that appeared or
  disappeared, and says explicitly when an `em-workflow` entry is present.
  When the snapshots match, it returns without effect. This follows the
  module's existing checker style: raise with a descriptive message rather
  than return a bool.
- The recurrence test and the negative proof use the same snapshot helper
  and the same checker, so the negative proof exercises exactly the check
  the recurrence test relies on.

### Recurrence test (FR2)

1. Create a test-owned, empty directory with an absolute path. The harness
   creates a fresh working directory of its own on every run, so a directory
   the test creates itself lies outside the run's working directory.
2. For the duration of this test only, point the test process's own
   environment `XDG_CACHE_HOME` at that directory. The previous value, or
   its absence, is restored when the test ends, whether it passes or fails.
3. For each mode (`readonly`, `readwrite`), as a subtest: take the snapshot,
   launch `LITELLM_PATH` through `_run_wrapper_pid()` with no `extra_env`,
   then assert exit status 0, exactly one recorded stub invocation, and that
   the checker passes against that snapshot.

### Negative proof (FR3)

- The setup is the same: a test-owned empty directory and a snapshot taken
  before each launch. This time the directory is handed to the wrapper as
  `XDG_CACHE_HOME` through `extra_env`, which reproduces what the harness
  passed before FR1.
- For each mode: assert the launch itself succeeded (exit status 0, exactly
  one stub invocation), so the failure below can only come from the cache
  write. Assert that an `em-workflow` directory now exists in the
  directory, and that the checker raises an assertion failure against the
  pre-launch snapshot.
- It is documented as a non-vacuity proof, like
  `TestCheckerDetectsRegressions` and `TestStopCheckerDetectsRegressions`.

### Docstring

- The module docstring gains a short paragraph after the existing Stop-hook
  paragraph. Following the style of the existing paragraphs, it names this
  task plan (`feature-docs/wrapper-args-test-xdg-cache-isolation/tasks/task0001.md`)
  and maps the new tests to FR1–FR3.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1): `_run_wrapper_pid()` removes `XDG_CACHE_HOME` from the
  environment it hands to the wrapper. The removal sits at the same point as
  the `CODEX_HOME` and `CODEX_OTLP_ENDPOINT` removals, before `extra_env` is
  applied. An `XDG_CACHE_HOME` given through `extra_env` still reaches the
  wrapper, as the AC-4 test observes.
- [ ] AC-2 (FR2): A test sets the test process's `XDG_CACHE_HOME` to a
  test-owned, initially empty, absolute-path directory for the duration of
  the test only. It launches `LITELLM_PATH` through `_run_wrapper_pid()` in
  `readonly` and in `readwrite`, and asserts for each launch: exit status 0,
  exactly one stub invocation, and directory contents equal to the snapshot
  taken immediately before that launch (no `em-workflow` entry).
- [ ] AC-3 (FR2, FR3): One checker helper performs the comparison in AC-2.
  It raises an assertion failure whose message names the unexpected entries,
  and names the `em-workflow` entry when present. It passes silently when the
  contents match. AC-2 and AC-4 call this same helper on the same kind of
  snapshot.
- [ ] AC-4 (FR3): A negative-proof test hands a test-owned empty directory to
  the wrapper as `XDG_CACHE_HOME` through `extra_env`. It launches
  `LITELLM_PATH` through `_run_wrapper_pid()` in `readonly` and in
  `readwrite`, and asserts for each launch: exit status 0, exactly one stub
  invocation, an `em-workflow` directory present in that directory, and the
  AC-3 checker raising an assertion failure against the pre-launch snapshot.
- [ ] AC-5 (FR1, FR2): Run against the harness before the AC-1 change, the
  AC-2 test fails on the `em-workflow` entry, not on a launch error. This is
  the TDD red step. The test passes after the change.
- [ ] AC-6 (FR1, NFR2, NFR3):
  `python3 -m unittest tests.test_codex_hook_wrapper_args tests.test_codex_litellm_launch_home_location`
  passes in full, `test_module_imports_are_all_stdlib` included. It passes
  both with `XDG_CACHE_HOME` absent from the shell and with it set to a
  fresh, empty, absolute-path directory. After the second run, that
  directory holds no `em-workflow` entry.
- [ ] AC-7 (NFR1, NFR3, NFR4): The task's change set modifies only
  `tests/test_codex_hook_wrapper_args.py`. Nothing else changes: neither
  `run_codex_exec.sh`, not `tests/test_codex_litellm_launch_home_location.py`,
  and no file under `em-workflow/`, `em-review/`, `plugin-dev/` or
  `.claude-plugin/`.

## Test Notes

- AC-1 to AC-4 and AC-6 are covered by the module's own tests plus the two
  module runs of AC-6. AC-1 is observed through its effects: AC-2 shows the
  removal and AC-4 shows the override order. The stub's record shape is not
  extended for it.
- AC-5 is the TDD order: write the AC-2 test first and run it against the
  unchanged harness. It must fail on the `em-workflow` entry. The red step
  is safe: the test points `XDG_CACHE_HOME` at its own directory, so the
  `em-workflow` directory lands there, never in the real cache.
- AC-6's second run reproduces the goal's reproduction steps. Use a
  directory created under the system temporary directory for it.
- AC-7 is a change-set check against the implement base commit.
- Edge case: the test process may already carry an `XDG_CACHE_HOME` that
  points at the real cache. The scoped override replaces it for the test and
  restores it afterwards, so neither the new tests nor the rest of the
  module write to it.
- Each test-owned directory is removed when its test ends. The `em-workflow`
  directory the negative proof creates goes with it.
- NFR2: the scoped environment override comes from the standard library's
  unittest support. The module's import checker counts it under `unittest`.
