# Threat Model: wrapper-args-test-xdg-cache-isolation

## Verdict
no-trust-boundary

## Rationale
Inspected at the reduced tier:

- SPEC.md: FR1–FR3, NFR1–NFR4 and assumptions A-1 to A-3.
- The single planned change, in `tests/test_codex_hook_wrapper_args.py`
  (task0001, domains `config-infra` and `external-io`).
- The `--litellm` launch-home code of `em-workflow/scripts/run_codex_exec.sh`.
  The tests run it unchanged.

What moves:

- The test harness copies the developer's own process environment into a
  child `bash` process.
- That process runs the repository's own wrapper, which calls a stub `codex`
  generated by the harness.
- Every file-system write lands in a directory the same user owns: the
  harness's temporary directory, a test-owned temporary directory, and,
  before this change, the user's own cache directory.

Every hand-off has the same user and the same privilege level on both
sides. Nothing crosses from a party of different trust:

- no external or user-supplied input
- no network call or external service
- no file read from outside the project
- no text placed into an LLM prompt
- no privilege change

The `em-workflow` directory left behind is a test-isolation defect (SPEC.md
Objectives), not a security threat. The change only narrows where a test run
writes.

The `external-io` domain of task0001 deepened the review of those
file-system side effects. Every write stays inside the same user's own
directories, so it adds no trust boundary. That is why task0001's file
appears in no Boundary files line.
