# Task Plan: task0001 — loop-command-guard hook, registration, docs and version

## Goal

Every Bash command with a while / until loop at a command position is
denied by a new PreToolUse(Bash) guard, including loops inside nested shell
texts. Every other command passes through with no output. The guard is
registered directly before destructive-guard.py, and the registration tests,
README, test-procedure rule and em-workflow version all match the change.

## Design

IMPLEMENTATION.md pins the guard's I/O contract, its registration position,
the version-bump convention and decisions D1–D3. This section covers only
how this task meets them.

### Components inside loop-command-guard.py

| Component | Responsibility | Contract |
|-----------|----------------|----------|
| Input gate | Accept only a well-formed Bash payload | Pre: raw standard input. Post: the command string when standard input is one JSON object, `tool_name` is exactly Bash, `tool_input` is an object, and `command` is a non-empty string. Otherwise the run ends silently (FR8) |
| Shell-text reader | Decide one shell text | Pre: a text and its nesting depth. Post: exactly one of three results (loop found / no loop / undecidable). The reader is deterministic and has no side effects |
| Nested-text finder | List the shell texts that one shell text hands to another shell | Post: the nested texts that the rules below name. Each is decided by the shell-text reader at depth + 1 |
| Output | Turn the top-level result into the hook's output | Loop found: the deny object. No loop or undecidable: nothing. Never allow or ask |

### Processing flow
1. The input gate reads standard input. If the gate rejects it, the run ends silently.
2. The command is read as a shell text at depth 0.
3. If the depth-0 text is undecidable, the run ends silently, even when a loop
   was seen in it (FR8).
4. Otherwise, a loop found in the text itself or in any nested text leads to
   deny. No loop leads to silence.
5. Any unexpected failure at any step ends silently. This includes
   recursion exhaustion. The exit status is 0 and standard error is empty.

### Reading one shell text
The reader tracks these lexical contexts:
- **Single quotes**: data, ending at the next single quote.
- **Double quotes**: data, except for command substitutions and backticks.
  Their contents are nested texts. A backslash escapes the next character.
- **Backslash outside quotes**: makes the next character literal. A
  backslash followed by a newline continues the line; it is not a separator.
- **Comments**: a `#` that begins a word in unquoted context starts a
  comment, which runs to the end of the line. A `#` inside a word, as in
  `a#b`, is not a comment.
- **Heredocs**: the `<<` or `<<-` operator takes a quoted or unquoted
  delimiter. The body runs from the line after the operator's line up to the
  delimiter line. `<<-` ignores leading tabs when it matches the delimiter.
  When several heredocs start on one line, their bodies follow in order.
- **Herestrings**: `<<<` followed by one word.
- **Command substitutions**: a `$(` up to its matching `)`, with nested
  quotes and parentheses tracked. Backtick substitutions work the same way.
  Arithmetic expansion `$((` … `))` is data, not a command substitution.

**Command position (FR2).** A word is at a command position when it is the
first word of the text, or when it follows any of these:
- a separator: newline, `;`, `&`, `&&`, `||`, `|` or `|&`
- an opening `(`, or the reserved word `{`
- `!`
- one of the reserved words if, then, elif, else or do

A reserved word counts only when it stands at a command position itself.
So in `echo do while`, `while` is an argument. Redirection operators that
contain `&` or `|`, such as `2>&1`, `&>` and `>|`, are not separators. A loop
is found when the word at a command position is exactly the unquoted,
unescaped literal while or until (A7). The loop's condition and whether it
runs in the background do not matter (FR2).

**Nested texts (FR3, FR5, A6).** Each of these is read with the same rules
at depth + 1:
- **Command substitutions**: the content of every command substitution and
  backtick in unquoted or double-quoted context, whatever the command word
  is.
- **Shell commands**: this covers a simple command at a command position
  whose command word is bash, sh or zsh, compared by last path segment. The
  command word is found by first skipping:
  - leading NAME=value assignments
  - any chain of the A6 prefix commands (timeout, nohup, env, nice, setsid,
    stdbuf, command, exec, time), together with their options, option
    values, timeout's duration operand and env's NAME=value operands

  For such a command, the reader re-reads:
  - **The `-c` string**, when a c option is present. The c option can stand
    alone, combine with other single-letter options in one word (`-lc`), or
    follow other options (`-euo pipefail -c`). An option that takes a value,
    such as `-o` / `-O` and their `+` forms (including when combined, as in
    `-euo`), consumes that value. The nested text is the first operand after
    the options, unquoted to the literal text the shell would receive, with
    parameter expansions left as written.
  - **Heredoc bodies**: the body of each heredoc attached to that simple
    command.
  - **Herestrings**: the unquoted word of each herestring attached to that
    simple command.
- **eval**: for a simple command at a command position whose command word is
  eval, including behind the same prefixes, the nested text is its operands,
  each unquoted, joined by single spaces.

**Not read (FR4, A3, A6).**
- single-quoted content
- double-quoted content outside substitutions
- comments
- argument words, and every operand of a shell other than its `-c` string
- heredoc bodies and herestrings attached to any command other than bash,
  sh or zsh
- script-file operands
- shells reached as another command's argument (`find -exec`, `xargs`),
  over ssh, or through a pipe

**Undecidability and depth.**
- At depth 0, any of these makes the text undecidable: an unterminated
  single or double quote, heredoc, command substitution or backtick, or a
  heredoc operator with no delimiter.
- Nesting is read only to a maximum depth. This is a named constant of no
  less than 8.
- A nested text that is undecidable, or that lies beyond the maximum depth,
  yields no finding for itself. Findings elsewhere in the enclosing text
  still stand.
- Rationale: FR8 governs the command as submitted. If a broken nested
  string could cancel a loop that is already visible in the enclosing text,
  any command could get past the guard easily (THREAT-MODEL.md TM-1).

### Output (FR6, FR7, NFR3)
- **Deny**: exactly one JSON object on standard output, whose
  `hookSpecificOutput` carries:
  - `hookEventName` PreToolUse
  - `permissionDecision` deny
  - a `permissionDecisionReason` that begins with `[loop-command-guard]` and
    states that while / until loops are prohibited
- **Otherwise**: nothing on standard output.
- Every run exits with status 0 and writes nothing to standard error.
- The hook never reads CLAUDE_BATCH.

### Side-effect freedom (NFR1, NFR2)
- The hook imports only standard-library modules and no other hook
  (IMPLEMENTATION.md D3).
- It creates no process, evaluates no part of the command text, and opens no
  file and no network connection.
- It reads nothing from environment variables, the clock or the filesystem.
  So the same input always gives the same output.
- Its work grows with command length and nesting depth.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR2, FR6; SPEC AC1, AC2, AC7): each of these commands
      produces a deny result:
      - `while true; do sleep 1; done`
      - `until false; do :; done`
      - a while loop followed by `&`
      - a loop after `&&`, `||`, `;`, `|`, a newline, `(`, `{`, `!`, then,
        elif, else, and do inside a for loop
      - a pipe into a while-read loop

      A deny result is one JSON object on standard output. Its
      hookSpecificOutput holds hookEventName PreToolUse, permissionDecision
      deny, and a permissionDecisionReason that begins with
      `[loop-command-guard]` and states that while / until loops are
      prohibited. The exit status is 0. The result is identical whether
      CLAUDE_BATCH is set or unset.
- [ ] AC-2 (FR3, FR5, A6; SPEC AC3, AC4; TM-1): each of these is denied:
      - a loop inside the `-c` string of bash, sh and zsh, including `-lc`

## Test Notes

- **AC-1 to AC-4**: one CASES table in tests/test_loop_command_guard.py. Each
  row is (expected verdict, label, command) with the verdict deny or silent,
  in the same shape as tests/test_interpreter_mismatch_guard.py. Every row
  runs the guard as a subprocess of the running Python interpreter, with a
  Bash payload on standard input. Each row asserts:
  - exit status 0
  - empty standard error
  - an exact standard-output expectation: empty for silent; a parsed deny
    object with the three fields and the reason prefix for deny
- **AC-1 CLAUDE_BATCH variation**: rerun every deny row with the variable
  set and with it removed from the child environment.
- **AC-4**: the malformed payloads (non-JSON, non-object, wrong tool, missing
  or bad command) go in their own test, as in the interpreter-mismatch-guard
  module. Undecidable commands can be ordinary silent rows.
- **AC-5**:
  - Walk the guard's syntax tree for imports and call names.
  - Bounded-time checks use a generous named bound so they are not flaky:
    - a heredoc of about one megabyte fed to a non-shell command: silent
    - the same heredoc fed to bash with a loop: deny
    - a several-hundred-level nesting: silent
  - Determinism: run a representative deny row and a representative silent
    row twice each and compare the outputs.
- **AC-6**: lives in the two registration modules. Keep the existing
  non-vacuity style, where a forged reordering must not equal the pinned
  expectation.
- **AC-7**: documentation checks are structural: presence of the row, the
  relative order of names in the sentence, and presence of the command and
  the case format. They do not pin exact wording.
- **AC-8**:
  - tests/test_plugin_version_parity.py already covers the equality of the
    two manifests.
  - plugin-version-guard enforces the "raised from HEAD" part at commit
    time. The verify phase rechecks it against the merge base.
  - Record the full-suite run in the implementer report.
- **Edge cases worth a row**:
  - a pipe into a while-read loop: deny, because FR2 ignores the loop's
    condition
  - `echo then until`: silent
  - `a#b while`: the `#` is not a comment, and `while` is an argument
  - `2>&1` directly before a word: not a separator
  - backslash-newline continuation before while: silent
  - `<<-` with a tab-indented delimiter
  - two heredocs on one line
  - a quoted heredoc delimiter
  - `$((1+2))`
  - a loop in a command substitution inside a double-quoted echo argument:
    deny
  - `bash -c "echo 'while true'"`: silent
  - a second operand after the `-c` string that mentions while: silent

## Out of Scope

- Command positions that FR2 does not list: after the time reserved word at
  top level, inside process substitution, in case arms, and after coproc. No
  test pins their outcome.
- Command substitutions inside a heredoc body fed to a non-shell command.
  FR4 excludes the whole body.
- Shells other than bash, sh and zsh, and the A3 / A6 exclusions (script
  files, shells as another command's argument, ssh, piped shells).
- Any change to an existing hook script, to em-review, or to
  em-workflow/references/implement-phase.md (FR1, A9, A13).
- README content beyond the new row and the execution-order sentence. That
  includes the opening guard count and rows for other guards.
- A per-feature version-bump test module. Existing tests already check the
  manifests' parity.
