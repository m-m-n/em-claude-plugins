# Task Plan: task0001 — State that format non-execution never overrides another rule's fail, and pin it with a document test

## Goal

Both procedure documents (implementer.md Step 3 and the worktree-task-workflow
skill's Command execution gate section) state, in one sentence each, that not
running the format command does not override a `tests: "fail"` that another
rule decides, citing the case where the build command also falls outside the
cd prefix form. A new standard-library document test pins that sentence.

## Requirements

FR1, FR2, FR3, NFR1, NFR2, NFR3, NFR4, NFR5

### Files to Modify

## Design

### The FR1 sentence (both documents)

One sentence, added once to each of the two sections, carrying three
elements together:

1. the format command not being run (the subject of the sentence);
2. that this does not override a `tests: "fail"` decided by another rule;
3. as the cited example of "another rule", the case where the build command
   is also an approved string that the cd prefix form does not cover.

Placement:

- implementer.md Step 3: after the existing paragraph that holds the build
  sentence and the format sentence — appended to that paragraph on a new line,
  or as a new paragraph directly after it.
- SKILL.md gate section: after the existing format bullet and before the
  existing deny bullet — as a new bullet, or as a second sentence on new
  lines inside the format bullet.

Either placement must leave every existing line byte-unchanged (additions
only), so the existing format, build and test-command sentences, the deny
bullet and the Step 7 JSON block are untouched (FR2).

Use the documents' established term "cd prefix form" and refer to the two
commands as "the format command" / "the build command". Further examples of
"another rule" (such as a hook deny) are optional (SPEC A3) and must obey the
same constraints.

Illustrative wording that satisfies every constraint below (the implementer
may rephrase, provided each constraint still holds):

> Not running the format command does not override a `tests: "fail"` that
> another rule decides, for example when the build command is also an
> approved string that the cd prefix form does not cover.

Wording constraints on the new sentence (and on any other text this task adds
to either section):

- Must not contain `project_commands.format`, `project_commands.build`,
  `project_commands.test` or `notes`, and must not contain the phrase
  "the report sets `tests: "fail"`". This keeps it out of the existing
  format, build and test-command matchers and out of the "no sentence sets
  fail for the format case" check (NFR2 a–d).
- Must not contain an internal full stop followed by whitespace (no "e.g.",
  "i.e." and the like), so sentence splitting keeps it whole.
- Must not contain the word "separate" (it shares a sentence with the word
  "cd"), the substring "chain", the token `&&`, "may reset" or
  "may have reset" (NFR3).
- Must not contain `#`, `$'`, `$"`, `${`, nor — compared in lowercase —
  "unclosed", "trailing backslash", "parenthes", "command substitution" or
  "backtick" (NFR2 f, g).
- implementer.md Step 3: must not contain "Step 4" (NFR3).
- SKILL.md gate section: must not contain "Run nothing, set",
  "Untrusted input", "byte", "identical to" or "equal to the line" (NFR2 e,
  NFR3).

### The document test module

Self-contained and standard-library-only, following the convention of the
existing document tests (repository root computed from the module's own
path; no import of sibling test modules; no edit to any existing module).

Components and contracts:

| Component | Responsibility | Contract |
|---|---|---|
| Section extraction | Return the text of the section whose heading is the given name | Pre: document text and heading name. Post: the text from the line after the heading up to the next heading of the same or a higher level (or end of file); headings inside fenced code blocks are ignored. A heading that is absent raises an assertion failure — it never yields an empty string. |
| Sentence splitting | Split a section into whitespace-normalized sentences | Paragraphs and list items are separate blocks; wrapped lines join their block; a sentence ends at a full stop followed by whitespace. |
| FR1 matcher | Return the sentences that carry all three FR1 elements | A sentence is returned only when it holds, within itself, a literal phrase for each element of the chosen wording: the format command not being run; not overriding a `tests: "fail"` decided by another rule (the negated override, the `tests: "fail"` value and "another rule" all present); the build command also falling outside the cd prefix form. Each element is keyed on a literal phrase, never on a loose bag of words. |

Real-document flow: for each of the two sections, extract by heading →
split into sentences → apply the FR1 matcher → assert exactly one hit.

Fixtures for the paired accept / reject assertions (literal strings inside
the module):

- the intended sentence (accepted);
- false sentence 1: even when the build command and the format command both
  fall outside the cd prefix form, the report's `tests` follows the result of
  the test command (rejected);
- false sentence 2: the not-override statement without the build case
  (rejected);
- false sentence 3: the existing format sentence, verbatim as it stands in
  the documents (rejected).
