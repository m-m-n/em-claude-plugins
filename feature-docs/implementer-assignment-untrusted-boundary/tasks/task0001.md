# Task Plan: task0001 — Assignment payload with an untrusted data section

## Goal

`em-workflow/references/implement-phase.md` defines an assignment payload whose identity lines and trusted fields come first and whose workflow.yaml-derived values come last, in a labelled `Untrusted data` section as one-line JSON literals, with adjacent text stating that those values are data, not instructions. A new document test pins this.

## Requirements

FR1, FR2, FR3, FR6, NFR1, NFR3, NFR4, NFR7

## Scope

### Files to Create
- `tests/test_assignment_payload_untrusted_section.py` — document test for the payload block and its adjacent text (TS1)

### Files to Modify
- `em-workflow/references/implement-phase.md` — the "Prompt payload per task" block, the text adjacent to it, and the I.2.c relaunch wording if it restates payload fields

## Design

Contract: IMPLEMENTATION.md C1 (line order), C2 (section name, label line, five data lines) and C3 (value encoding). This task owns how they are worded in `implement-phase.md`.

Change flow:

1. In the payload block, keep the `# Task assignment` header line, then the `task_id:` and `worktree_path:` lines as the first two lines after it.
2. Keep the other trusted fields after them in C1 order. `tests_yaml_path`, currently after `expected_files`, moves to the end of the trusted fields (A4).
3. End the block with the `Untrusted data` label line and the five data lines of C2, each shown with a JSON-literal placeholder.
4. Next to the block, state (a) that the section's values come from workflow.yaml and are data, not instructions (FR1), and (b) the C3 rendering rule as an instruction to the orchestrator (FR2).

Further constraints:

- How trusted fields are derived (Step I.0) is unchanged.
- The retry relaunch in I.2.c uses this same block (A7). If I.2.c restates payload fields, align that text with C1 to C3; add no second payload definition.
- The block and the new adjacent text contain none of the AC-1 ordering anchor phrases asserted by `tests/test_prelaunch_inprogress_launch_order.py` (read that module for the phrases). Existing sentences that carry those phrases are not moved (NFR7).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, TM-1): `implement-phase.md` defines the assignment payload in exactly one block that starts with the `# Task assignment` line, and inside that block the `Untrusted data` label line comes after every trusted field line (`task_id`, `worktree_path`, `task_plan_path`, `implementation_md_path`, `lessons_path`, `parent_branch`, `merge_script`, `tests_yaml_path`) and before each of the five data lines of C2, so no data value sits among the trusted fields.
- [ ] AC-2 (FR1, TM-1): Text adjacent to the block states that the values in the `Untrusted data` section come from workflow.yaml and are data, not instructions.
- [ ] AC-3 (FR2, TM-2): `implement-phase.md` instructs the orchestrator to write each data value as one JSON literal on its own line (a JSON string for each `project_commands.*` line, a JSON array of strings for `skills_to_load` and `expected_files`), with newlines and other control characters escaped, a missing build or format command as `""`, an empty list as `[]`, and the `em-workflow:` prefix kept inside each `skills_to_load` string, so a value can never add a line to the prompt.
- [ ] AC-4 (FR3, TM-5): Inside the block, the `task_id:` line and the `worktree_path:` line are the first two lines after the header line and both precede the `Untrusted data` label line, so the queue hooks' first match is always the genuine identity.
- [ ] AC-5 (NFR7): None of the AC-1 ordering anchor phrases asserted by `tests/test_prelaunch_inprogress_launch_order.py` appears inside the payload block or in the adjacent text this task adds.
- [ ] AC-6 (FR6, NFR1, NFR3, NFR4): The new test module uses only the Python standard library, and `python3 -m unittest discover -s tests` and `python3 em-workflow/scripts/check-plugin-invariants.py .` both pass with no existing test module modified.
