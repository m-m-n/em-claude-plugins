# Task Plan: task0001 — Stop the implement phase when a canonical worktree_path carries a control character

## Goal

Step I.2.a of the implement phase checks the canonical `worktree_path` of
every selected task for control and line-separator characters before the
launch loop, and stops the phase without building any implementer launch
prompt when one is found. The document tests pin that procedure and its
placement, and the existing document tests keep passing.

This feature has no IMPLEMENTATION.md (a single task); this plan is
self-contained.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/references/implement-phase.md` — add the control-character check paragraph to Step I.2.a
- `tests/test_canonical_worktree_path_docs.py` — add the checks and forged-copy tests for the new paragraph

## Design

### The new paragraph in Step I.2.a

One new paragraph in Step I.2.a ("I.2.a: Launch phase") states the following.

1. **Scope**: once every task selected in this entry into Step I.2.a has its
   canonical `worktree_path` (the value the Canonical worktree path paragraph
   yields, for a worktree just created and for one reused under the Resume
   guard alike), the orchestrator checks each of those values. The check
   covers all selected tasks, not only the first or the current one.
2. **Rejected set**: any character of Unicode general category Cc
   (U+0000–U+001F, U+007F, U+0080–U+009F), plus U+2028 and U+2029. Name the
   set by these code-point ranges in the document; the tests key on them.
3. **Stop**: when the value of one or more selected tasks contains a
   character of the set, the orchestrator ABORTs the implement phase, reports
   the IDs of the offending tasks, builds no implementer launch prompt for any
   selected task (clean ones included) and launches no implementer. It never
   strips, escapes or replaces the characters and continues, and it never
   falls back to the unresolved path string.
4. **Checking the value itself**: phrase the check as a test over the
   characters of the resolved value, not over how the value looks when
   printed — most members of the set are invisible or render as a line break.
5. **Discipline**: the stop follows the same fail-closed discipline as
   Step I.0's identifier validation gate (never sanitize, never proceed); the
   paragraph may cite that gate rather than restate it.

Placement: after the Canonical worktree path paragraph and before the
launch-loop paragraph (the one opening "Launch each selected task as a
BACKGROUND"). Put it directly after the Canonical worktree path paragraph,
ahead of the approval-gate paragraph, so that a stop happens before the
approval gate asks about any command.

### Constraints from the existing document tests (NFR1)

The existing tests in `tests/test_canonical_worktree_path_docs.py` slice
Step I.2.a into sentences, blocks and blank-line paragraphs and require
several of them to be unique. The new paragraph must keep all of these true:

- No sentence and no block other than the existing canonicalization
  sentence contains all three of "`$WT_ROOT/{T}`", "strict realpath" and
  "worktree exists", and no other blank-line paragraph contains both
  "strict realpath" and "worktree exists".
- No other sentence contains all of "unresolved", "`$WT_ROOT/{T}`" and
  "never passed". State the no-fallback point without that combination, for
  example by citing the Canonical worktree path paragraph's own statement.
- No other sentence contains all of "`worktree_path`", "canonical absolute
  path" and "passed to the implementer".
- No block begins with any of the openings the existing tests anchor on:
  "- Clean re-attempt (fresh implementer", "Before launching, verify every
  `project_commands`", "Launch each selected task as a BACKGROUND", or
  "`tests_yaml_path` points INSIDE the task's own worktree".
- No sentence carries three or more of the path-condition markers listed in
  the module's CONDITION_MARKERS. The paragraph cites the path conditions; it
  does not restate them.
- The assignment payload block is not touched.

### Document tests

Add checks in the module's existing style: each is a function from the
Step I.2.a section text to a list of problems, locates text by the heading
slice and stable phrases, and never uses a line number. The checks cover the
four points FR4 names:

- **Every selected task**: the check paragraph applies to every selected
  task.
- **Rejected set**: the paragraph names Cc and each of U+0000–U+001F, U+007F,
  U+0080–U+009F, U+2028 and U+2029. Each range is required on its own, so a
  copy that names only the line feed fails.
- **Stop before any launch prompt**: the paragraph states the ABORT of the
  implement phase, the report of the offending task IDs, and that no launch
  prompt is built for any selected task.
- **Placement**: the paragraph's block comes after the canonicalization
  block (the one block holding "strict realpath", "`$WT_ROOT/{T}`" and
  "worktree exists") and before the block opening with "Launch each selected
  task as a BACKGROUND".

Forged copies, each built from the live section and each required to yield
at least one problem:

- (a) the check paragraph removed;
- (b) the rejected set reduced to the line feed only;
- (c) the ABORT statement replaced by a statement that escapes the characters
  and continues;
- (d) the check paragraph moved after the launch-loop paragraph;
- (e) the scope narrowed from every selected task to a single task;
- (f) the report of the offending task IDs removed.

New constants, helpers and test classes are added alongside the existing
ones. Existing tests, the check functions they call and the constants they use
are not modified or removed; reusing the module's existing helpers (section
slicing, block and sentence splitting, paragraph removal and moving) is
expected.

## Test Notes

- Write the new checks and the forged-copy tests first. Against the current
  document, which lacks the paragraph, the live-document tests of AC-3 fail
  (red); adding the paragraph turns them green.
- Give each forgery of AC-4 its own test method. Build forgeries from the live
  section (removal, replacement, moving) so they follow the final wording, and
  assert that the forgery differs from the live text, as the module's existing
  forged-copy tests do, so that a replacement matching nothing cannot pass
  vacuously.
- The placement check compares block indices, like the module's existing
  placement check. Forgery (d) can use the module's existing paragraph-moving
  helper with the launch-loop opening as its anchor.
- AC-5 is covered by running the module unchanged plus a review of the diff of
  the test module (only additions).
