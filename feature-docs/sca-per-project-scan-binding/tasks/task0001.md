# Task Plan: task0001 — Per-group scan job construction and workspace-escape pins

## Goal

build_scan_jobs returns exactly one pure scan job per (ecosystem, lexically
normalized project directory) group, and the scanner registry and the go child
environment keep npm and go from escaping to an ancestor workspace or rewriting
go module files.

## Requirements

FR2, FR3, FR11, FR12, FR14, NFR1, NFR2, NFR4

## Scope

### Files to Create
- `tests/test_sca_scan_job_grouping.py` — this task's job-construction tests (TS-7 and the build_scan_jobs grouping cases)

### Files to Modify
- `em-workflow/scripts/scan-dependencies.py` — build_scan_jobs grouping and filtering, a new private lexical-grouping helper, the go entry of the child-environment pin table and its comment block
- `em-workflow/references/vuln-scanners.yaml` — the npm args gain the workspace flag as their third element

- `tests/test_sca_scan_normalization.py` — the npm command-assembly expectation gains the workspace flag

## Design

Cross-task contracts used here are pinned in IMPLEMENTATION.md: Shared
Components (build_scan_job, Target convention, manifest_file_for, Group order,
Registry npm args and go child-environment pins, Skip-reason vocabulary),
Conventions (region ownership — inside scan-dependencies.py this task edits only
build_scan_jobs, its own lexical helper and the child-environment pin table),
and decisions D1–D3.

### Registry and child environment (FR11)

- npm registry args become audit, --json, --workspaces=false — the two existing
  elements followed by the new flag (A-8). The flag already satisfies
  validate_ecosystem_entry's argument rules (no path-separator prefix, no shell
  metacharacter), so that function is not touched.
- go child-environment pins: GOENV off (kept), GOWORK off (new), GOFLAGS
  -mod=readonly (replaces the empty GOFLAGS pin), GOPROXY (kept). npm, cargo and
  pip pins stay as they are; nothing is added for cargo.
- Pins are layered over the caller's environment, so a caller-supplied GOWORK or
  GOFLAGS never reaches the child.
- The comment block above the pin table states, for go, what each pin prevents
  (workspace discovery above the project directory; module-file rewrites).

### Lexical project directory (pure helper)

For one changed path: normalize it textually (collapse repeated separators, drop
`.` segments, cancel each `name/..` pair), then take its directory part, `""`
for the root, `/`-separated. No filesystem access; never raises for any string,
including one containing NUL.

An npm / cargo / go path is **lexically unbindable** when it is absolute, still
starts with a `..` segment after normalization, or contains NUL. pip paths are
never classified this way (D3).

### build_scan_jobs flow

1. select_ecosystems (unchanged).
2. For each selected ecosystem in registry order:
   - validation failure → its existing reason once, no job; executable not on
     PATH → `<ecosystem>_tool_not_found` once, no job. Steps 3–6 do not run for
     that ecosystem.
3. Collect this ecosystem's changed files (basename in its manifests or its
   lockfiles), keeping input order.
4. npm / cargo / go: drop every lexically unbindable path; when at least one was
   dropped, add `<ecosystem>_project_unbindable` once. pip: drop nothing.
5. Group the remaining paths by lexical directory; order the groups per Group
   order.
6. Per group: manifest_file_for over the group's files in input order. npm /
   cargo / go target = Target convention with the lexical directory; pip target
   = the raw selected file. One build_scan_job call per group.
7. Return (jobs, reasons): reasons in ecosystem registry order, each at most
   once per ecosystem.

A pip lockfile target stays outside this function's contract, as before
(build_scan_job rejects it without a prepared file).

**Postcondition**: no file is opened, read or written and no process is
launched; the only environment interaction is the existing PATH lookup for the
executable.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TM-3): With the real registry, the npm job's argument vector is exactly [absolute executable path, audit, --json, --workspaces=false]; the cargo and go vectors are the absolute executable path followed by their unchanged registry args; the pip vectors for requirements.txt, pyproject.toml, and a lockfile with a prepared file are unchanged.
- [ ] AC-2 (TM-3, TM-4): The go job's environment holds GOWORK=off, GOFLAGS=-mod=readonly, GOENV=off and GOPROXY at its existing value, also when the supplied environment carries other GOWORK / GOFLAGS values; the npm, cargo and pip pins equal their previous values.
- [ ] AC-3: For changed files services/web/package.json then services/api/package.json with npm resolvable, build_scan_jobs returns two npm jobs whose manifests are services/api/package.json then services/web/package.json; with npm and cargo both changed, every npm job precedes every cargo job (registry order).
- [ ] AC-4: a/package.json, a/./package-lock.json and a repeated a/package.json yield one npm job with manifest a/package.json; a change holding only a/./go.sum yields one go job with manifest a/go.sum; a root-level change keeps the bare basename (package.json) as the manifest.
- [ ] AC-5: For npm / cargo / go, an absolute changed path, a path escaping through `..`, and a NUL-containing path join no group and add `<ecosystem>_project_unbindable` exactly once per ecosystem, while a valid group of the same ecosystem still yields its job; pip paths of the same three kinds are not filtered and add no such reason.
- [ ] AC-6: An ecosystem whose entry fails validation, or whose executable is absent, contributes its existing reason exactly once and no job even with several groups (two npm directories with npm absent → reasons are exactly npm_tool_not_found), and no `<ecosystem>_project_unbindable` is added for it.
- [ ] AC-7: With file opening (built-in and low-level) and process launching patched to fail, build_scan_job completes for root and nested targets and build_scan_jobs completes for nested, alias, absolute, escaping and NUL-containing inputs, without calling any patched entry point.
- [ ] AC-8: The existing npm argument-vector and command-assembly expectations are updated for --workspaces=false (FR14) and no other existing assertion is weakened; the new test module imports only standard-library modules (asserted inside the module); `python3 -m unittest discover -s tests` and `python3 em-workflow/scripts/check-plugin-invariants.py .` both exit 0.
