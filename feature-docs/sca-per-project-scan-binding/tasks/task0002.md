# Task Plan: task0002 — run_scan per-project grouping, binding and aggregation

## Goal

run_scan audits every changed npm / cargo / go project inside its own directory —
or reports it as `<ecosystem>_project_unbindable` without launching anything —
groups pip changes per project while keeping pip's existing behavior, and
aggregates the per-project outcomes into one deterministic, path-free result.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR9, FR10, FR12, FR14, NFR1, NFR2, NFR3, NFR4, NFR5

## Design

Cross-task contracts are pinned in IMPLEMENTATION.md: Shared Components
(build_scan_job — this task owns its cwd rule and its target precondition;
Target convention; manifest_file_for; Group order; Skip-reason vocabulary),
Conventions (region ownership — do not edit build_scan_jobs, the
child-environment pin table or vuln-scanners.yaml) and decisions D1–D3.

### build_scan_job changes

- Working directory per the contract: npm / cargo / go → the project root joined
  lexically with the target's directory part, exactly the project root's string
  form for a root target; pip → the project root's string form for every form.
- Precondition check (pure): an npm / cargo / go target that is absolute,
  contains a `..` segment or contains NUL raises JobConstructionError.
- Still pure: no file access, no path resolution on disk, no process launch.

### run_scan flow

1. Registry load, ecosystem selection and the no-manifest / unsupported-manifest
   results: unchanged.
2. For each selected ecosystem, in registry order:
   1. **Ecosystem gate (FR9)**: validation failure → its existing reason once;
      executable absent → `<ecosystem>_tool_not_found` once. On either, nothing
      below runs for this ecosystem (no path verification, no binding check, no
      launch).
   2. Collect this ecosystem's changed files (basename in its manifests or its
      lockfiles), keeping input order.
   3. **Grouping (FR1, FR10)**:
      - npm / cargo / go: verify every changed file (below). A failing file
        joins no group and adds `<ecosystem>_project_unbindable` (A-10). A
        passing file's group key D is its containing directory's real path
        relative to the real project root, `/`-separated, `""` for the root —
        duplicate and alias spellings of one directory therefore share a group.
      - pip: key = that same verified D when the containing directory resolves
        inside the real project root without error; otherwise the raw directory
        part of the path as given. No pip path is rejected (D3).
   4. Process the groups in Group order.
   5. Per group:
      - pip: target = manifest_file_for over the group's raw files. A lockfile
        target goes through the existing lockfile audit for that group; any
        other target goes through the existing job (cwd = project root) and
        normalizer. The undetermined-severity and excluded-entry counts
        accumulate over groups.
      - npm / cargo / go: target = Target convention with D. Binding check
        (below) fails → `<ecosystem>_project_unbindable`, nothing launched.
        Passes → build_scan_job → execution → outcome judgment → normalizer, with
        the target as the findings' label (cargo's normalizer also receives the
        project root, as today). A completed group marks the ecosystem as
        scanned; a not-completed outcome adds its existing reason.
3. **Aggregation (FR7, FR8)**: reasons de-duplicated, sorted and joined with
   "+"; skipped is true exactly when at least one reason exists; the findings of
   every completed group are kept in processing order; the summary's scanned
   list holds each ecosystem name once (sorted), and its not-completed /
   skipped list uses the same de-duplicated sorted reasons; the existing pip
   count notes are unchanged.

### Changed-file verification (npm / cargo / go, FR5)

A changed file passes only when all hold: it is a non-empty string; it is not
absolute; it contains no NUL; resolving the file and its containing directory
raises nothing; both real paths equal the real project root or lie under it.

### Binding check (npm / cargo / go, FR4, FR5), for group directory D

Bindable only when all hold:

- The real project directory exists, is a directory, and equals or lies under
  the real project root.
- Anchor — npm: npm-shrinkwrap.json when an entry of that name exists in the
  directory, otherwise package-lock.json (an invalid shrinkwrap never falls back
  to package-lock.json); cargo: Cargo.lock; go: go.mod.
- Required manifest — npm: package.json; cargo: Cargo.toml; go: go.mod.
- The anchor and the manifest each resolve to a regular file whose real
  containing directory is the real project directory (a symlink to another file
  in the same directory is allowed; one resolving into another directory is
  not).
- The selected target exists and resolves to a regular file inside the real
  project directory (a deleted target is unbindable).
- Any exception during the check → unbindable.

yarn.lock and pnpm-lock.yaml still select npm but never serve as an anchor
(A-9). There is no fallback to the root or an ancestor directory in any case.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TM-1): build_scan_job's npm / cargo / go working directory is the project root joined with the target's directory (services/api/package.json under /proj → /proj/services/api) and exactly the project root's string form for a root target (/proj stays /proj); every pip form keeps the project root; an absolute, `..`-containing or NUL-containing npm / cargo / go target raises JobConstructionError; with file opening and process launching patched to fail, it completes for nested targets without calling them.
- [ ] AC-2 (TM-2): (TS-1) with services/api holding package.json and package-lock.json and the change [services/api/package.json], the npm stub runs once, its recorded cwd is the real path of project_root/services/api, the finding's file is services/api/package.json and skipped is false; (TS-2) with services/api and services/web both bindable and both package.json files changed, npm runs twice — services/api first — each in its own directory, and each finding carries its own project's package.json path; (TS-6) a/package.json, a/./package-lock.json and a repeated a/package.json produce one launch labelled a/package.json.
- [ ] AC-3 (TM-4): Nothing is launched and skip_reason is exactly `<ecosystem>_project_unbindable` for: npm package.json without package-lock.json and npm-shrinkwrap.json (root and nested, and a yarn.lock-only project); cargo Cargo.toml without Cargo.lock (root and nested); a go.sum-only change without go.mod. A go.sum-only change whose directory holds go.mod launches the go stub with cwd at that directory. In a git repository holding a cargo project without Cargo.lock, with a cargo-audit stub that would write Cargo.lock if launched, git status --porcelain is identical before and after the scan and no Cargo.lock exists (TS-10).
- [ ] AC-4 (TM-1): Nothing is launched for the project, `<ecosystem>_project_unbindable` is reported, and no launch happens at the root or an ancestor directory, for each of: anchor symlinked into another directory (inside and outside the project root); manifest symlinked into another directory; npm-shrinkwrap.json symlinked elsewhere while package-lock.json is valid; an absolute changed path; a changed path escaping through `..`; a NUL-containing changed path; a deleted selected target; an absent project directory. In each case a separate valid npm project changed in the same run is still launched in its own directory and keeps its findings.
- [ ] AC-5 (TM-2, TM-5): Bindable and unbindable npm projects mixed → skipped is true, skip_reason is exactly npm_project_unbindable, the bindable project's findings are kept and the summary's scanned list names npm once; two unbindable npm projects → skip_reason is npm_project_unbindable (once); npm absent with two groups, one of them anchorless → skip_reason is exactly npm_tool_not_found and nothing is launched; neither skip_reason nor summary contains any fixture directory name; every result conforms to review-output-schema.json.
- [ ] AC-6: pip changes in two directories (one requirements.txt project, one poetry.lock + pyproject.toml project) → pip is audited once per group with lockfile-first selection, every pip launch's cwd is the project root, and each group's findings carry that group's raw target; every pre-existing pip lockfile test still passes.
- [ ] AC-7 (NFR2): Scanning the same inputs twice yields byte-identical result JSON; reversing changed_files leaves skip_reason identical and the launch order still follows ascending project path.
- [ ] AC-8 (FR14): Every pre-existing run_scan fixture that launched npm / cargo / go without an anchor now creates the manifest and the anchor and keeps asserting what it asserted before (fixtures listed in Test Notes); the new test module imports only standard-library modules (asserted inside the module); `python3 -m unittest discover -s tests` and `python3 em-workflow/scripts/check-plugin-invariants.py .` both exit 0.

## Test Notes

- Stubs: one executable per tool on a temporary PATH that appends its working
  directory and argument vector to a record file outside the project root and
  prints a fixture payload. No real scanner runs (NFR4).
- Compare recorded working directories against the project directory's real
  path — temporary directories can sit behind a symlinked temp root.
- AC-1 is unit-level on build_scan_job; AC-2 to AC-7 are end-to-end through
  run_scan with real temporary trees and symlinks.
- TS-9's "no binding check" is observable: skip_reason is exactly the tool
  reason even though one project lacks its anchor.
- NUL-containing and very long paths follow the existing pip tests' pattern:
  run_scan returns a result and never raises.
- Schema conformance: a structural assertion against review-output-schema.json,
  written locally in the new module like the existing modules' helper (no
  import from another test module).
- FR14 fixtures to update (each must still reach its stub; the substring "npm"

    TestErrorEnvelopeAndUndocumentedExitAreDistinctReasons (end-to-end cases),
    TestDocumentedAdvisoryFoundExitIsCompleted, TestPartialCoverageAcrossTwoEcosystems,
