### 1. `## Field values`: the `step` bullet

**Unchanged, byte for byte**:

- the domain declaration sentence ("a closed value domain: one of the seven
  `workflow.yaml` step ids (...), or the single sentinel `no-step`.");
- the general-rule sentence;
- the "Two rules take precedence over the general rule" sentence;
- everything from the sentence that starts "When `state` is `completed`" to
  the end of the bullet, which includes the Step C asymmetry.

**Rewritten**: the sentence or sentences that begin "`no-step` applies
whenever".

- **Condition**: `no-step` applies whenever no `workflow.yaml` step was
  executed in that turn, or the stop occurs outside Step B. This condition
  governs, and the stop points named after it are examples, not an exhaustive
  list.
- **Examples**, as backticked keys:
  - `stop-condition-6` (Step 0's git-setup abort);
  - `step-a-abort` (Step A's feature-resolution failure);
  - `step-c-abort` (Step C's abort; every workflow step has already
    completed).
- **stop-condition-4 case**: a `stop-condition-4` stop takes `no-step` when no
  step was executed in that turn. Otherwise the general executed-step rule
  applies.
- **Step A.5 case**: a stop raised in Step A.5, including the command-approval
  refusal-pattern hard fail, takes `no-step`. The refusal stop is named in
  prose only, never by a backticked coverage key (SC1, D4).

**Constraints on the rewritten span**:

- The anchor phrase "`no-step` applies whenever" stays on one physical line.
- The only backticked hyphenated tokens in the span are `stop-condition-6`,
  `step-a-abort`, `step-c-abort` and `stop-condition-4`, besides the sentinel
  `no-step` itself.
- The old condition phrase "no `workflow.yaml` step is in effect at the stop
  point" is replaced by the condition above. The sentinel-condition assertion
  in `test_batch_stop_contract.py` moves to the new condition phrase.

### 2. `## Stop point coverage`: the Precedence rule paragraph

**Keep**:

- the label "Precedence rule:";
- the principle that a phase-specific stop point takes precedence over the
  generic `stop-condition-N` rows, so exactly one code applies;
- the names `implement-second-failure`, `verify-rework-cap` and
  `docs-commit-conflict`;
- the implement `failed_kind` restriction. It applies when `failed_kind` reads
  `decision` (including the missing-value case), or when the automatic-resume
  attempt count has reached its cap per `skills/develop/SKILL.md`, with the
  pointer to the `step_needs_intervention` row.

**Replace**:

- **Status claim**: `implement-second-failure` and `verify-rework-cap` write
  `failed`, which is `stop-condition-3`'s own trigger. `docs-commit-conflict`
  aborts without writing any status, because the failed status write is
  itself its stop cause.
- **Route-based restriction**:
  - A phase-specific row wins when the current run reaches the stop through
    that phase's own abort route. This includes `implement-second-failure`,
    which the same run realizes through its next Step B evaluation when that
    evaluation reads the `failed` the run wrote.
  - `stop-condition-3` binds a stop at Step B's entry evaluation that reads a
    `failed` / `needs_update` status no route of the current run produced.
    For example, a `failed` left by an earlier run's
    `implement-second-failure`.

**Must not**:

- name `no-work-required`, `unmapped_stop`, `unmapped-terminating-stop` or
  `command-refusal`;
- contain "no phase-specific row covers" or "all three leave".

**Postcondition**: implement-phase.md's pinned sentence ("since
`references/batch-terminal-line.md` already gives `implement-second-failure`
precedence over `stop-condition-3`") stays true. `references/implement-phase.md`
is not edited.
