# Task Plan: task0005 — Read a lone dash in flag position as a positional word that ends the mcp-bridge run flag sequence

## Provenance

- source: review
- source_ids: ca547a9f716957df
- review_round: 2

## Goal

In the flag reading of `_mcp_bridge_args_json_chunks()`, a flag-position word
whose restored text is shorter than two characters (a lone `-`, as well as the
empty text) is a positional word that ends the flag sequence, as
IMPLEMENTATION.md D2 step 2 now states. The `--args-json` values read before it
are inspected, so `mcp-bridge run ... --args-json '{"command":"git branch -D example"}' -`
becomes deny. A new case (TS-30) and revised unit tests pin it.

## Design

The flag reading and its stops are pinned in IMPLEMENTATION.md D2 (revised in
this round: step 2) and D5. This section gives the task-level detail.

### Starting point

The merged code (task0003) ends the flag sequence on the restored text `--`
and on a restored text that does not begin with `-`. A lone `-` begins with
`-` and is not `--`, so one dash is removed, the remaining name is empty, the
empty name is not a known name, and the whole statement becomes "nothing to
do": the `--args-json` values already collected are dropped and the raw-string
verdict (allow for a plain `command` value) stands. The empty restored text
already ends the sequence, because it does not begin with `-`.

### The change (FR3 (d), D2 step 2)

- A flag-position word that is static (D5) and whose restored text is shorter
  than two characters ends the flag sequence exactly as a positional word does:
  the reading stops normally, and every `--args-json` value read before it is
  handled as D2 states for values (each on its own, D5 classification, D3
  decode). Words after it are not read as flags.
- The restored text `--` and a restored text that does not begin with `-` keep
  ending the sequence as they do.
- Everything else of the reading is unchanged: the D5 classification of the
  word comes first (a lone `-` that is not static or is unrestorable keeps the
  outcome D2 step 1 gives it), the removal of one or two leading dashes, the
  split at the first `=`, the value-taking and `dry-run` names, an unknown name
  (including a name left empty or starting with `-` or `=` after the dashes
  are removed, such as three dashes or `-=x`) making the statement "nothing to
  do", and the canonical notion-pair reading, which is not widened (a lone
  `-` in flag position makes the pair undeterminable, as any positional word
  does today).
- A lone `-` before any `--args-json` ends the reading with no `--args-json`
  read: the statement stays "nothing to do" (FR6 (5)), now for that reason
  instead of the unknown-name stop.

### Docstring (FR10)

The flag-reading step of the `_mcp_bridge_args_json_chunks()` docstring (its
step 3, which task0003 wrote) states that a restored text shorter than two
characters, as well as `--` and a word that does not begin with `-`, ends the
flag sequence as a positional word. The out-of-scope list O1 / O2 in that
docstring does not change: an unknown flag stays O2 (3), and a lone `-` is not
an unknown flag. No other explanation site changes: the out-of-scope
declaration of `extract_shell_payload_anchored()` and the other sites task0004
owns already state the O1 / O2 scope that stays.

### New case (FR9)

The label is Japanese like the existing labels, begins with
`mcp-bridge-args-json-exec-guard TS-30`, and describes the case. It is a
three-element case (no fourth element). The command is the shell text below.
It is placed after this feature's TS-29 case.

| ID | Expected | Command (shell text) |
|----|----------|----------------------|
| TS-30 | deny | `mcp-bridge run --mcp desktop-commander --tool start_process --args-json '{"command":"git branch -D example"}' -` |

The cases file is JSON, so each `"` of the shell text is written as an escaped
quote. After writing, the command is read back from the file and compared with
the shell text above.

### Unit tests (`tests/test_destructive_guard_args_json.py`, FR13)

TestFlagReading changes as follows; every other test keeps its assertions.

- The entry labelled "a lone dash" (a lone `-` before `--args-json`) leaves the
  group of unknown-flag forms: it stays among the forms that are not inspected,
  placed and labelled with the positional forms (next to "positional before the
  flag"), since the lone `-` ends the reading before any `--args-json`.
- The test of a value before the terminator or a positional word gains these
  inspected forms, each giving exactly one inspected result:
  - a lone `-` after the value;
  - a lone `-` after the value followed by an unknown flag;
  - an empty single-quoted word after the value;
  - a lone `-` written quoted (single-quoted) after the value.
- A test pins that the value before a lone `-` is inspected and a value after
  it is not: for a statement with an `--args-json` value, then a lone `-`,
  then a second `--args-json` value, the result holds exactly the first
  value's `command` strings.
- The forms that stay not inspected keep their entries: an unknown flag,
  an unknown single-dash flag, an unknown flag after the value, three dashes,
  and the other entries of that test.
