# Task Plan: task0001 — Structural tests for the contributor-consent skill

## Goal

The contributor-consent test module checks both skill copies structurally: each
answer of step 5 is bound to the commands the skill itself runs, the text shown
to the user holds no unresolved environment-variable reference, and step 5 says
the skill runs the commands. The wording-locked command checks and the
descriptions of the commands as presented to the user are gone.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_contributor_consent_skill.py` — remove the wording-locked command checks; add the structural checks and their synthetic-input proofs; rewrite the task0009 test names, comments and module docstring
- `em-workflow/skills/contributor-consent/SKILL.md` — conditional: changed only when a new check cannot pass against the current text, and then identically to the em-review copy (expected unchanged)
- `em-review/skills/contributor-consent/SKILL.md` — conditional: the same change as the em-workflow copy, made only when that copy changes (expected unchanged)

## Design

### Terms

- **Skill copy**: one of the two SKILL.md files above. Every check runs on each
  copy as a separate sub-case, as the existing tests of the module do.
- **Step N**: the text from the `### N.` heading up to the next heading of level
  1, 2 or 3. The level-4 subsections of step 3 and step 4 belong to their step.
  The preamble before step 1 and the constraints section after step 6 belong to
  no step.
- **Paragraph**: a run of non-blank lines outside fenced blocks.
- **Guard invocation**: text that contains the path segment `hooks/muse_guard.py`.
- **Skill-executed command**: a fenced block that is a guard invocation and sits
  in step 2 or step 5.
- **User-visible text**: a fenced block in step 1 or step 6 that is not a guard
  invocation; every inline code span in step 4 (the question wordings); every
  option label of step 4 (the text of an option list item before its
  description separator).
- **Element**: every fenced block of the copy, plus the user-facing literals of
  step 4 named above.
- **Unclassified element**: a fenced block that is neither kind. This covers a
  fenced block outside steps 1, 2, 5 and 6, a guard invocation in step 1 or 6,
  and a block in step 2 or 5 that is not a guard invocation.
- **Unresolved environment-variable reference**: `${NAME}` or `$NAME`, where NAME
  is a shell variable name (a letter or underscore, then letters, digits or
  underscores). A command substitution `$(...)` is not a reference.
- **Term matching**: wherever a check looks for a term in prose, it compares the
  text and the term with all whitespace removed. A wrap at any column then
  cannot split a term, including in Japanese text, which has no spaces between
  words.

### Check 1: classification (FR4)

- Precondition: the body of one skill copy.
- Passes only when all of these hold. Every element is exactly one kind. No
  user-visible text holds an unresolved reference. Step 2 holds a skill-executed
  command carrying `--list`. Step 5 holds the skill-executed commands carrying
  `--record` and `--remove`.
- `${CLAUDE_PLUGIN_ROOT}` inside a skill-executed command is never flagged. The
  variable check reads user-visible text only.

### Check 2: branch binding (FR3)

- The option labels come from the two option lists of step 4. Their roles are
  consent and decline for the not-consented state, and keep and revoke for the
  consented state. The roles are taken from the option constants that the
  existing question-round check already pins, so this check adds no new wording.
- A branch of step 5 is a paragraph that begins with one or more option labels.
  One paragraph may name several labels; the current text names decline and keep
  together. The commands bound to a branch are the skill-executed commands
  between that paragraph and the next branch paragraph or the end of step 5.
- Passes only when all of these hold:
  - The consent branch is bound to exactly one command. That command names
    `hooks/muse_guard.py`, `--record` and `--project-dir`.
  - The revoke branch is bound to exactly one command. That command names
    `hooks/muse_guard.py`, `--remove` and `--project-dir`.
  - The decline and keep branches are present and bound to no command.
  - Step 6 holds no guard invocation, and holds exactly one user-visible block,
    equal to the existing no-write line constant.
- Every assertion is in positive form. A missing branch, a missing command or a
  missing step fails the check; it never passes the check.

### Check 3: run statement (FR5)

- Passes only when both of these hold:
  - Every branch bound to a command states that the command is run. This is the
    run verb of the branch instruction, found by term matching.
  - Step 5 contains no term of a closed vocabulary. The vocabulary names the
    user's own terminal and copying or pasting a command, in Japanese and
    English, matched case-insensitively.
- The vocabulary lives in one module-level constant.

### Synthetic inputs (NFR4)

- A synthetic body is made by editing the text of a real copy: removing,
  duplicating, moving or inserting blocks and paragraphs. A synthetic input
  that is not made from a real copy is a short free-standing string.
- Inserted text and free-standing strings never spell out:
  - a full guard command line;
  - the quoted plugin-root form `"${CLAUDE_PLUGIN_ROOT}"`;
  - the project-directory argument form `--project-dir "$(pwd)"`.
- A synthetic case that needs a guard command duplicates or moves a block of the
  real copy. This keeps the text search of AC-1 meaningful.

### Rewrap variants (NFR3)

Two variants are built from each real copy. In both, every prose paragraph is
re-flowed; fenced blocks, headings and list items stay as they are.

- The first variant joins each prose paragraph into one line.
- The second variant splits each prose paragraph at a narrower column. It never
  splits inside an inline code span.

Checks 1 to 3 run on each variant.

### Existing checks and descriptions (NFR2, FR6, FR7)

- These tests keep their substance: task0002 AC-1 to AC-6, and task0009 AC-2,
  AC-3 and AC-5, including the cross-copy equality check.
- The task0009 AC-1 test is removed. Checks 1 to 3 replace it, because its
  assertions encode the presented, never-executed design.
- The module docstring is rewritten to describe the skill-executed design:
  - its task0009 part;
  - the parenthetical under task0002 AC-5;
  - the comments around the removed constants and the context-line constant.
- The docstring gains a part for this feature's checks. That part cites
  `feature-docs/contributor-consent-command-path/SPEC.md` by its
  repository-relative path.

### THREAT-MODEL.md TM-1

Checks 1 and 2 together are mitigation TM-1. With them, a mutating guard command
is reachable only from the explicit consent answer or the explicit revoke
answer. Any other placement fails at least one of the two checks.

## Test Notes

- AC-2 to AC-6 and AC-8 map to unit tests in the module. Write the synthetic
  tests of AC-5 first: they fail until Checks 1 to 3 exist. Then write the
  real-copy tests of AC-2 to AC-4 and the variant tests of AC-6.
- AC-1, AC-7 and AC-9 are text searches over the changed files. SPEC.md allows
  TS-8 to be a static check. A test in the module that searched its own source
  would have to spell out the forbidden strings itself.
- Edge cases:
  - one branch paragraph names two labels (decline and keep);
  - a branch paragraph wraps across lines in the narrower variant;
  - a Japanese term split by a wrap.
- When a check cannot pass against the current text of the copies, record which
  check failed and why before changing the copies, then make the same change in
  both (AC-9).

- The wording of the skill copies, except under the condition of AC-9.
- `tests/test_muse_consent_no_new_questions.py`, and every other test module.
- Running the skill in an interactive session.
