# Task Plan: task0001 — Component-wise safe-delete judgement and case-table realignment

## Goal

The recursive-delete guard stops treating a path that merely prefixes a safe
directory name, or that escapes a safe root through a parent reference, as
safe, and the expectation table states those corrected decisions instead of
pinning them as known holes.

### Decision order inside the recursive-delete check

Per target of a recursive delete, in this order:

1. **Zero targets** — unchanged early return (a command whose only target
   disappeared during lexing stays as it is today).
2. **Root / home target** — unchanged, and judged on the **raw** token, so the
   existing reason id for that case survives. Normalization must not be moved
   ahead of this step.
3. **Unresolved expansion** — a target carrying a variable expansion or a
   command substitution is unresolvable regardless of how it looks; it never
   reaches the safe exception and takes the existing unresolvable branch.
4. **Lexical normalization** — the target is normalized through the shared
   helper (home-form expansion, lexical folding). The filesystem is not
   consulted.
5. **Surviving parent reference** — a relative target still beginning with a
   parent reference after normalization is not safe and falls through to the
   recursive-delete deny.
6. **Component-wise containment** against the safe-root vocabulary (below).
7. **Otherwise** — the existing recursive-delete deny.

A pure glob (no expansion, no substitution) still reaches step 6, except that a
dot-leading glob component is excluded from the safe exception because it can
match a parent reference.

### Containment predicate

A predicate over one normalized target, answering "is this inside a safe root".
Precondition: a normalized target, already known to carry no unresolved
expansion. Postcondition: true only when one of the following holds, and it
never touches the filesystem.

| Class | Members | Safe when | Never safe |
|---|---|---|---|
| Build artifacts (relative targets only) | node_modules, dist, build, target, .next, coverage | the leading path component equals a member exactly, either as the whole target or with further components below it | an absolute path spelled with the same name; a leading component that merely starts with a member's text |
| Scratch roots | /tmp, /var/tmp (absolute); tmp, .cache (relative, leading component) | at least one further component exists below the root | the root itself, in any spelling that normalizes to it |

A match is on whole components only: a member's name followed by more
characters within the same component is not a match. Because normalization
folds a trailing separator away, a spelling that differs only by a trailing
separator reaches the same decision as its counterpart.

### Reason text

The reason id of each branch is unchanged. Whether the emitted message echoes
the raw or the normalized target is free, as long as no case-table expectation
depends on the choice.

### Case-table realignment

- The 14 entries whose label mentions the safe-delete exception flip from
  allow to deny, and their labels are rewritten to state the corrected reason
  without the "known hole" wording.
- One new deny entry covers a recursive delete of a path that reaches outside
  a scratch root through a parent reference.
- Regression entries are added for the behaviours this task's criteria name
  that no entry pins yet.
- No existing deny or ask entry is removed.

## Test Notes

- The case table plus its runner is this component's only test mechanism; every
  criterion above is expressed as case-table entries and verified by one suite
  run. Treat an entry as the unit test it is.
- **TDD order**: flip the 14 expectations and add the new entries first. The
  suite then fails on exactly those entries — that failure set is the red state
  the logic change must turn green. This also matches the project's hook-test
  rule (add the case before the fix).
- Record which cases were already failing before any edit, so a post-change
  failure is attributed by set difference rather than re-investigated.
- Edge cases worth an explicit entry: a home-form target that normalizes below
  a scratch root; a relative target whose leading component matches a build
  artifact but continues within the same component; a nested occurrence of a
  build-artifact name (`foo/build`), which stays outside the exception.
- Re-run the suite twice and compare: identical output on both runs is the
  cheapest evidence for the determinism criterion.

- Any check other than the recursive-delete one; other reason ids and other
  command families keep their current behaviour.
- Refactoring the lexer, the segmentation, or the shared normalization helper's
