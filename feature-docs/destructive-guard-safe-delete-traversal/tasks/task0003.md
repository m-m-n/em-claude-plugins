# Task Plan: task0003 — Unresolvable evidence and decision precedence in the recursive-delete check

## Goal

The recursive-delete guard stops deciding on incomplete evidence: a target
whose text the lexer altered, or whose spelling the guard cannot resolve, never
reaches the safe exception, and a `deny` warranted anywhere in the command is
never hidden by an `ask` raised on an earlier target.

## Design

The cross-task contracts this task implements against — the unresolved-evidence
signal at the lexing boundary, and the decision-precedence rule — are pinned in
IMPLEMENTATION.md ("Shared Components", D6, D7). This section states only what
is specific to this task.

Three reported defects, one root cause: **the decision is emitted from evidence
the guard has already lost, never had, or stopped collecting.**

### 1. Evidence lost at the lexing boundary

When the lexer removes a command substitution from a word, the remainder
reaches the check indistinguishable from literal text. Lexical folding then
cancels a parent reference against that remainder, the residue lands inside a
safe root, and the safe exception allows a delete whose real destination is
outside it.

The distinction the check needs is static and must be preserved across the
boundary:

| Shape of the word | Meaning for the check |
|---|---|
| The removed substitution covered the **whole** word | The word contributes no target — the existing zero-target early return applies and the decision is unchanged |
| The removed substitution was **adjacent to** other text in the same word | The word is a target whose value cannot be resolved |

The first shape is the one the SPEC pins to `allow` (US3's acceptance criterion
for entries whose only targets are command substitutions). Widening the second
shape's treatment to cover the first is a specification violation, not an
expectation-table lag — the table is not to be re-pinned to accommodate it.

The representation that carries this distinction is the implementer's choice;
the criteria below constrain only the decisions it produces.

### 2. Evidence never recognized

The unresolvable-spelling vocabulary covers only the substitution forms and
`${name}` / `$name`. Positional and special parameter forms, and the tilde
forms the normalizer does not expand, are treated as ordinary path components
and are therefore cancelled by a following parent reference, leaving only a
safe-looking trailing component to judge.

- Parameter forms to treat as unresolvable: positional (`$1`…`$9`, `${10}`-style
  spellings) and special (`$@`, `$*`, `$#`, `$?`, `$$`, `$-`, `$!`, `$0`).
- Tilde rule: a leading `~` whose next character is neither a path separator nor
  the end of the token is a form the normalizer does not expand (`~+`, `~-`,
  `~user`), so it is unresolvable. A bare `~` and a leading `~/` are expanded as
  today and keep their current decisions.

Both are judged **before** normalization, so no parent reference is ever folded
against an unresolved component.

### 3. Evidence collection stopped early

The check returns the first decision it reaches and exits, so an `ask` on an
early target ends the scan and the remaining targets — and the remaining
segments of the command — are never examined. A target that would decide `deny`
is silently approved along with the `ask`, and the reason text names only the
target that triggered the `ask`.

The selection rule becomes: evaluate every target of every segment, keep the
strongest decision found (`deny` outranks `ask`, `ask` outranks `allow`), and
emit once at the end. The reason text names every target that contributed to
the emitted decision.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Substitution residue never reaches the safe exception — a recursive
      delete of `$(pwd)/../tmp/scratch`, of a `printf`-substitution spelling
      followed by `/../../tmp/scratch`, and of a backtick spelling with the same
      shape, each decide `ask` or `deny` (never `allow`), with or without the
      batch environment variable set.
- [ ] AC-2: The pinned allow side does not move — a recursive delete whose only
      targets are command substitutions still decides `allow` through the
      zero-target early return, and every allow-side case task0001 pinned
      (`node_modules` with output discarded, `/tmp/x` with and without
      redirection, `dist/*`, `./build`) still decides `allow`. No pre-existing
      `allow` entry in the case table changes its expectation.
- [ ] AC-3: Unresolvable spellings decide `ask` with the unresolvable reason id
      before normalization — `"$@/../build"` preceded by a positional-parameter
      assignment, `$1/../build`, `~+/../build`, `~-/../build` and
      `~someone/../build` each decide `ask` (`deny` under batch demotion), while
      a bare `~` target and a `~/`-leading target keep the decisions they make
      today.
- [ ] AC-4: A deny is never hidden by an earlier ask — a recursive delete of
      `tmp/$X` followed by `/home/sakura/valuable` decides `deny`, the
      target-order-swapped spelling decides `deny`, and a compound command whose
      first segment is the `ask` form and whose later segment is a destructive
      form decides `deny`; the emitted reason text names every contributing
      target. A command whose unresolvable target is its only target still
      decides `ask`.
- [ ] AC-5: The case table pins each command named in AC-1, AC-3 and AC-4 as an
      entry with its expected decision; no pre-existing `deny` or `ask` entry is
      removed and none changes its expectation; and
      `python3 em-workflow/hooks/tests/run-destructive-guard.py` reports every
      case passing, including the trailing batch-demotion assertion.
- [ ] AC-6: The decision stays deterministic and string-only — no real-path
      resolution, file-status inspection or subprocess call is introduced on any
      decision path, two consecutive suite runs produce identical output, and a
      command containing neither a substitution nor an expansion decides exactly
      as it does before this change.

## Test Notes

- The case table plus its runner is this component's only test mechanism. Each
  criterion above is expressed as case-table entries and verified by one suite
  run; treat an entry as the unit test it is.
- **TDD order**: add the new entries for AC-1, AC-3 and AC-4 first, matching the
  project's hook-test rule (add the case before the fix). The suite then fails on
  exactly those entries — that failure set is the red state. Record the failing
  set before any edit so a post-change failure is attributed by set difference.
- AC-2 is the regression half and is what the earlier attempt at this fix broke:
  run the full suite, not only the new entries, and compare the allow-side count
  against the pre-change run.
- AC-1 and AC-3 are asserted in both modes: `ask` is demoted to `deny` under
  batch, so "never allow" is the property to check, and the batch spelling is
  worth its own entry where the existing table has a precedent for one.
- Edge cases worth an explicit entry: a substitution adjacent to text on the
  right instead of the left; `~/`-leading and bare `~` targets (the false
  positive AC-3 must not create); an unresolvable target that is the only target
  (AC-4's negative half).
- Re-run the suite twice and compare output for AC-6's determinism half.
