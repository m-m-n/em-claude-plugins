# Task Plan: task0001 — Close the two remaining quoted-value false-open paths in the multiline value tracker

## Goal

In `em-workflow/hooks/queue_stop_guard.py`, the multiline value tracker no
longer opens a quoted value from a `?` in the middle of a flow-collection
scalar, nor from a line made only of non-ASCII whitespace. A genuine
`routeback_failed_journal_line` record and every later task stay visible,
and the Stop hook exits 2 where it must.

## Requirements

## Scope

- `tests/test_queue_stop_guard_routeback_record.py` — new regression tests for both paths, the block-scalar non-regression, the edge cases and the no-exception property.

## Design

### Context

`_MultilineValueTracker` decides, line by line, which lines of
`workflow.yaml` are body text of a multiline value. `task_ids_from_workflow`,
`iter_task_block_lines` and `task_routeback_records_from_workflow` rely on it.
A false "open" turns every later line into value body, which hides a later
`routeback_failed_journal_line` record and later task blocks. This task
changes only the tracker's line reading; the three readers keep their own
logic.

Cross-task decisions: none. This feature has a single task, and no
IMPLEMENTATION.md is written at the `reduced` tier.

### Rule 1 — `?` as the flow mapping-key indicator (FR1)

In `_scan_flow`, a `?` outside an inner string is the mapping-key indicator
only when both conditions hold:

- (a) `_at_start` is true at that point — the `?` begins a flow entry,
  directly after `[`, `{` or `,`, with or without whitespace in between;
- (b) the next character is a space, a tab, or the end of the line.

Any other `?` is an ordinary plain-scalar character. It sets `_at_start` and
`_after_close` to false, so a quote after it opens no inner string, whether
later on the same line or at the start of a later body line of the same flow
value. The `:` rule is unchanged.

Postconditions:

- `[retry? 'failed]` and `{reason: retry? 'failed}` open no inner string; the
  value closes at its closing bracket.
- `[retry?` followed by the body line `'failed]` (and the `{reason: retry?` /
  `'failed}` pair): the trailing `?` is ordinary because `_at_start` is false;
  scanning carries `_at_start` false into the next body line, `'failed]`
  opens nothing, and `]` closes the value.
- `{? 'tried }` and `[a, ? 'x]`: the `?` is at an entry start and followed by
  a space, so it stays an indicator and the quote after it still opens, as at
  base (FR3).
- `[retry?'failed]` (no space) keeps its current non-opening behavior.

### Rule 2 — the tracker's blank-line rule (FR2)

Within `_MultilineValueTracker` only, a line is blank exactly when, after
its trailing line terminator is removed, it consists only of U+0020 spaces
and U+0009 tabs (the empty line included). This one rule replaces both
current whole-whitespace checks: the one in `_read_line` (near line 240 at
base) and the one in `feed`'s block-scalar branch (near line 230 at base).
Both sites apply the identical rule.

A line made only of other whitespace characters (U+3000, U+00A0, U+000B,
U+000C and the like) is not blank and is read by the normal rules:

- At a value-start position it is a plain scalar, and deeper subsequent
  lines are its plain-scalar continuation lines. A following `- '…`, `"…`
  or `[…` line indented deeper than the key therefore opens nothing.
- In block-scalar state, its indentation decides whether it is a body line
  or ends the block scalar.

The blank-line checks of the readers outside the tracker —
`task_ids_from_workflow` (near line 420), `iter_task_block_lines` (near line
463) and `task_routeback_records_from_workflow` — are not changed (FR3).

### Rule 3 — wording (FR4)

- The `_MultilineValueTracker` class docstring's sentence about `?` (near
  lines 208–210) states Rule 1's condition: indicator only at a flow-entry
  start and only when followed by a space, a tab or the end of the line;
  otherwise an ordinary character.
- The comment on `_scan_flow`'s `:` / `?` branch (near lines 375–379) states
  the same condition.
- The class docstring also states Rule 2: a blank line is a line made only
  of spaces and tabs.

- Standard library only (NFR1): no import outside it is added.
- Fail-open (NFR2): the tracker and every reader return normally for any

- Change scope (NFR3): only the two files in Scope change.
  `em-workflow/.claude-plugin/plugin.json` and
  `.claude-plugin/marketplace.json` are not touched.
- Regression (NFR4): no existing test assertion is changed or deleted.

### Fixture shape (used by AC-1 through AC-6)

- Journal: line 1 is a `failed` event for task0001.
- `workflow.yaml`: task0001 is `pending`; its `notes` key (4-space indent)
  holds the form under test; after the notes value, task0001 has the direct
  child key `routeback_failed_journal_line: 1`; after that comes a `pending`
  task0002 block with no journal event.
- "Launch list" means the task IDs named for launch in the hook's BLOCK
  output.
- "Opens" means the tracker reads the following lines as value body, so the
  later record key and task0002 are not read; "opens nothing" means they are
  read.
