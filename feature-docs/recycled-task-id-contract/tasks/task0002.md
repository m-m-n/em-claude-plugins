# Task Plan: task0002 — plugin version bump in both registries

## Goal

Raise the em-workflow plugin version by one patch increment in both places
that carry it, and pin the two values' agreement with a test module of this
feature's own.

## Requirements

FR6, NFR1, NFR2, NFR3

## Scope

### Files to Create
- `tests/test_recycled_task_id_contract_version_bump.py` — asserts the bumped
  version in both registries, by parsing them as JSON.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — the version field only; no other
  field of the plugin manifest changes.
- `.claude-plugin/marketplace.json` — the version field of the em-workflow
  entry in the plugins array only; no other entry and no other field changes.

## Design

Files under `em-workflow/` change in this feature (task0001 edits the phase
document), so the plugin version must rise in the same change — otherwise an
installed copy keeps serving the cached older files.

Contract for the two registries (IMPLEMENTATION.md Shared Components):

- Both carry the identical version string after the change.
- The new value is exactly one patch increment above the pre-change value;
  the major/minor family does not move.
- Nothing else in either file changes: the plugin's other fields, the sibling
  marketplace entries, and the marketplace entry's source reference are
  untouched.

Test module contract:

- Both files are PARSED as JSON, never pattern-matched, so a structural
  breakage in either file is reported as such.
- The version assertion is durable, not a fixed literal: it states the
  major/minor family and that the patch number is strictly above the
  baseline recorded at this task's start. A hard-coded exact version is
  guaranteed to go stale on the next unrelated bump — the established pattern
  in this suite records a baseline instead.
- A separate assertion states the two files' versions are equal to each
  other, so a one-sided future edit is caught independently of the baseline
  check.
- Each matcher gets a negative proof: a forged pre-bump version value must
  make the durable assertion fail.
- This module must NOT assert on wording in
  `em-workflow/references/implement-phase.md`. task0001 rewrites parts of
  that document and the two tasks merge in an unspecified order; an assertion
  on wording that only holds on one side of that edit would be green in this
  worktree and red after the merge (IMPLEMENTATION.md D5).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR6): the plugin manifest parses as JSON and its version is one
      patch increment above the pre-change value, with the major/minor family
      unchanged.
- [ ] AC-2 (FR6): the em-workflow entry of the marketplace registry parses as
      JSON and its version is byte-identical to the plugin manifest's version.
- [ ] AC-3 (FR6): no field other than the two version values changes in
      either file — the plugin manifest's name, and the marketplace entries'
      name and source values, are unchanged.
- [ ] AC-4 (NFR1, NFR2): the new module lives under the repository-root tests
      directory as a `test_*.py` module, is discovered by
      `python3 -m unittest discover -s tests` from the repository root,
      imports only the standard library, and asserts AC-1 to AC-3 by parsing
      both files as JSON.
- [ ] AC-5 (NFR2, NFR3): the version assertion is a durable invariant
      (family plus a recorded baseline floor), each matcher has a negative
      proof that a pre-bump value fails it, no hook source file is modified,
      and the full suite passes.

## Test Notes

- Unit level throughout: two JSON reads and value assertions; no fixture, no
  temporary directory.
- TDD order: write the module first — it is red against the pre-change
  version — then edit the two registry files until it is green.
- Edge cases worth covering: a version string that is not of the
  three-part dotted shape must fail the assertion rather than pass by
  accident; the equality assertion must fail if only one file is bumped.
- The negative proofs run against forged values inside the test, never
  against a mutated repository file.

## Out of Scope

- The phase reference document and the two test modules task0001 owns.
- Any other plugin's version, and any other field of either registry file.
- Any change under the plugin's hooks directory (NFR3).
- Generating or changing a LICENSE file (the project records no license).
