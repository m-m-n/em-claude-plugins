# Task Plan: task0003 — remove the restated hook classification literals from the pin module

## Goal

Make the documentation-side classification table the only place a hook's
classification is written down, by deleting the four methods in
`tests/test_hook_classification_pin.py` that restate a hook-to-classification
mapping as a test literal, so NFR4 holds and FR5's single-pin rule is not
undercut by four parallel per-hook classification checks.

## Provenance

Verify-sourced rework. Failed item: TS13 (verify round of the `verify` phase).
No review round applies.

## Requirements

FR5, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_hook_classification_pin.py` — delete the four per-hook
  classification methods from the observation test class, replace the
  docstring-stripping rationale they claimed to carry with a synthetic-source
  proof, and update the module docstring and comments that refer to them.

## Design

### The second source of truth to remove (NFR4, FR5)

The observation test class currently holds four methods that each pair a hook
path taken from the classification table with the classification expected of
it:

- `test_queue_stop_guard_reads_status`
- `test_queue_launch_guard_does_not_read_status`
- `test_queue_failure_net_does_not_read_status`
- `test_queue_taskstop_net_does_not_read_status`

Each names one table hook and asserts its classification directly (True /
False out of the observation step). Together they are a complete, independent
copy of the documentation table's contents living inside test code — exactly
the duplicated classification NFR4 forbids, and a set of four extra
per-hook classification checks alongside the one pin FR5 permits. They are
deleted, not rewritten: any rewrite that still names a table hook next to its
expected classification recreates the same duplication.

### What the deletion must not cost

The two facts these methods appeared to protect are already carried, and must
remain carried, by tests that name no table hook's classification:

1. **The table-to-source agreement** — owned by the single pin test
   (`test_documented_classification_matches_observed_classification_for_every_row`),
   which covers every row, and by the two group assertions in
   `TestRecycledTaskIdRuleScopedToOrchestrator`, which derive their groups
   from the parsed table.
2. **The observation rule's non-triviality** — owned by the `bash_guard.py`
   counter-example (a module that reads the workflow state file for an
   unrelated purpose and must observe as not reading per-task status) and by
   the two synthetic-source tests (a bare workflow-state mention without a
   per-task-status accessor; a synthetic source losing only its status
   carve-out).

`bash_guard.py` is NOT a row of the classification table, so its
counter-example asserts a property of the observation rule rather than a
documented classification — it stays.

### The docstring-stripping proof (replacement, not an addition)

The deleted `queue_taskstop_net` method carried, in its comment, the claim
that stripping docstrings before the search is load-bearing. That claim must
survive its carrier in a form that names no hook: a synthetic source whose
ONLY mention of the workflow state file sits in a module docstring, together
with a defined-and-called per-task-status accessor, must be observed as NOT
reading per-task status — while the same source with that mention moved into
executable code is observed as reading it. The pair proves the stripping step
changes the outcome, using the existing temp-file helper and no hook path.

### The module's import surface is a contract

`tests/test_recycled_task_id_consistency.py` loads this module by absolute
path through `importlib.util.spec_from_file_location` and consumes
`parse_classification_table`, `READS_STATUS` and `DOES_NOT_READ_STATUS` from
it. The deletion touches test methods only; every module-level public name
stays exactly as it is, or the sibling module breaks at import time.

## Test Notes

- The change is a test-code deletion, so the acceptance surface is the suite
  itself: AC-1 through AC-7 are properties of the resulting module, and AC-8
  is the whole-suite run that proves nothing else depended on the removed
  methods.
- AC-1 is checkable by inspection of the module plus a search of the test
  directory for any remaining pairing of a table hook path with a
  classification value; the four method names are the concrete starting point,
  but the criterion is the property, not the four names.
- AC-3 is the riskiest part of the deletion: run
  `python3 -m unittest discover -s tests` (not just this module) after the
  edit, because the sibling module's failure mode is an import-time error that
  a single-module run will not reveal.
- AC-5's synthetic pair is the only new test code. Build it with the existing
  temp-file helper in the class, so no new import is introduced (NFR1).
- Edge case worth a moment: the observation step returns False for a source
  with no per-task-status accessor regardless of stripping, so AC-5's
  synthetic source must include such an accessor — otherwise the pair passes
  vacuously and proves nothing about the stripping step.
- TDD order: this task removes tests rather than adding behaviour, so the
  order is (1) add AC-5's synthetic pair and watch it pass against the current
  observation rule, (2) delete the four methods, (3) run the full suite.
