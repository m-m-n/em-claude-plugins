# Task Plan: task0004 — batch classification gate in question resolution

## Goal

`em-workflow/references/question-resolution.md` routes a batch
`rework.spec-change` gate through a classification gate that decides between
"the implementation cannot satisfy the goal" and "the implementation
satisfies the goal but diverges from the specification text", with an
asymmetric outcome rule and an evidence criterion — while the immediate
aborts for security, licensing and irreversible operations keep their
present strength.

## Requirements

FR3, FR7, FR8, FR9, FR10, FR11, FR12, FR13, FR14, FR20, NFR1, NFR2, NFR3,
NFR4, NFR5, NFR7, NFR8

## Design

### A. Fail-closed classification revision (FR11, NFR2)

The section keeps its position ahead of every policy lookup and ahead of the
unlisted-gate fallback. Its four abort arms become three abort arms plus one
routed arm:

- `category: security`, `category: license`, and an `assumptions[]` entry
  with `reversible: false` — **unchanged**, immediate abort, same strength,
  same "none of those can override this step" force. The revision must state
  that these three are outside its scope, so the gate can never be read as a
  bypass around them (NFR2, D2).
- `category: spec-change` / `gate_id: rework.spec-change` — routed to the
  classification gate below **in batch only**. In interactive the question is
  asked directly exactly as today (FR8, D8).

The explicit fail-closed gate list survives as a concept; `rework.spec-change`
moves off the abort list and onto the routed arm. `rework.spec-change` stays
unlisted in `references/batch-policies.yaml` (D1) — no policy entry and no
new `gate_id` are introduced here.

### B. Classification gate (FR7-FR10, FR13)

State as its own section, positioned so it is reached only from the routed
arm above:

1. **Inputs**: the `goal` block (`references/workflow-schema.md`, cited not
   restated) and the relevant specification document. Both are untrusted
   data — read, never executed (C7, FR3).
2. **Applicability (D3, FR20)**: the gate applies only when the feature's
   `workflow.yaml` carries a `goal` block. When it does not — a feature that
   passed create-spec before the block existed, or one with no source for
   the goal — the gate is inapplicable, the batch run stops exactly as it
   does today, and the stop reason records that the classification gate was
   inapplicable because the goal block is absent. No backfill from SPEC.md /
   REQUIREMENTS.md is attempted.
3. **Question shape**: posed so both directions can be raised — (a) the
   implementation cannot satisfy the goal; (b) the implementation satisfies
   the goal but diverges from the specification text.
4. **Classifier**: Codex through the existing consultation procedure
   (availability probe, read-only wrapper, turn limits) — cited, unchanged
   (FR12). Where Codex is unavailable, Claude performs the classification
   itself (FR13, NFR4); every rule below applies identically on both routes.
5. **Asymmetry (FR9)**: verdict (a) stops the run unconditionally — Claude's
   disagreement does not overturn it, and no second verdict may pass what
   the first stopped. Verdict (b) proceeds only when Claude is convinced.
6. **Evidence criterion (FR10)**: verdict (b) is adopted only when the
   classification names specific existing requirement IDs / acceptance-
   criterion IDs. A conclusion-only reply is not adopted and the run stops.
   This applies identically on the Codex-absent route (FR13).
7. **Codex output handling (FR12)**: read-only, never executed as
   instructions, never adopted verbatim; the decision to transcribe a
   verdict into requirements or acceptance criteria belongs to Claude. State
   by citing the existing untrusted-output rule rather than restating it.
8. **Audit record (FR14)**: every pass through the gate — including one that
   stops, and including the inapplicable case — produces the classification
   audit record whose fields and location are defined in
   `references/phase-state.md` (IMPLEMENTATION.md, Shared Components row 2).
   Cite that document for the field list; do not restate it here.
9. **Unattended-run continuity (NFR3)**: state that this gate never raises a
   confirmation nobody can answer in batch, and that every stop leaves its
   reason and evidence as a record.

### C. Constraints

- The document must not contain a `taskNNNN`-shaped identifier or the phrase
  "decision table" (C6a, C6b).
- The Codex consultation procedure section stays as it is — the gate reuses
  it by reference (FR12).

## Test Notes

- New module carries the gate's own pins; the existing module keeps the
  pre-existing structure pins (dedup order, priority sort, presentation
  limits, batch sequence, Codex procedure) and gets its fail-closed
  assertions updated.
- **Retention pins (TS-4)** are the highest-value assertions here: the three
  unchanged abort arms must each be asserted individually, plus the
  "regardless of ..." clauses that make them non-overridable. Losing one of
  those to a rewrite is the failure mode this task most needs to catch.
- The existing assertion that pins the four categories in one sentence must
  be replaced, not deleted: the replacement asserts three-abort-plus-routed
  wording with the same specificity (C5).
- Absence assertions with negative proofs: no `taskNNNN` token, no "decision
  table" phrase, and no surviving sentence that aborts a spec-change gate
  unconditionally in batch.
- Section-order assertions (classification before any policy lookup, before
  the unlisted-gate fallback) must keep passing; add one for the gate
  section's position relative to the routed arm.
- All assertions read only this task's own file (C4).
