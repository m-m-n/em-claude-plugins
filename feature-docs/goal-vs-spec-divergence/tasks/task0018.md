# Task Plan: task0018 — create-spec re-entry is a partial update

## Goal

`create-spec-phase.md`'s workflow.yaml construction step states that a
`needs_update` re-entry is a partial update, so the state the re-planning
path depends on — `tasks`, each step's `status`, `implement.base_commit`,
each `completed_at_commit` — survives the re-entry instead of being rebuilt
away.

## Requirements

FR5, FR6, NFR1, NFR5, NFR8

## Scope

### Files to Create

- `tests/test_create_spec_reentry_preservation.py` — pins the preservation
  statement and its enumeration.

### Files to Modify

- `em-workflow/references/phases/create-spec-phase.md` — section 11
  (workflow.yaml construction).

## Design

### What is wrong today

Section 11 opens with "The orchestrator builds `workflow.yaml` directly
here" and then enumerates every field it writes, including `tasks: {}` and
the seven-step `workflow` array with statuses. The only re-entry carve-out
written anywhere in that section is the one for `goal`.

Read as written, a `needs_update` re-entry rebuilds the file: `tasks` returns
to `{}` and `implement.base_commit` disappears with the step array. That
destroys the premise of everything downstream of the SPEC-change transition:

- FR5 requires `workflow.implement.base_commit` to be preserved across
  re-planning, and EC-4 requires already-merged work not to be discarded.
  Both are unreachable if the value is gone before re-planning starts.
- The re-planning path's second case is recognized partly by
  `workflow.implement.base_commit` already being set. If create-spec
  re-entry clears it, that case can never match and the transition is
  rejected again — the exact defect this feature exists to remove.

The carve-out for `goal` shows the section's author had re-entry in mind;
it was simply scoped to one field.

### The repair

Section 11 gains an explicit statement, alongside the existing `goal`
carve-out rather than replacing it, that a `needs_update` re-entry is a
**partial update, not a reconstruction**. It enumerates what survives
untouched:

- `tasks` in full — every entry, with its `status`, `branch` and `files`;
- every `workflow` step's `status` and `completed_at_commit`, except the
  statuses the SPEC-change transition itself sets;
- `workflow.implement.base_commit`;
- `project`, `requirements`, and `goal` (the last already stated).

and what the re-entry does write: the create-spec artifacts and the step
statuses the transition assigns.

The statement cites `references/workflow-patch.md`'s re-planning path as the
consumer of the preserved state, and `references/rework-task-synthesis.md`
Section 10 as the transition that causes the re-entry. Both citations are
one-directional: neither document is edited from this task, and neither needs
a back-reference for the rule to have exactly one home (NFR1). The rule's
home is this section, because this is the only place that describes building
the file.

### Convention notes

- C3: section 11 is extended in place. No numbered section is renumbered and
  no existing sentence of section 11 is reworded — the preservation statement
  is added.
- C2/NFR1: the base-commit rule already lives in `workflow-patch.md` as a
  `preserve` obligation on a patch. What this section states is different and
  not stated anywhere else: that the orchestrator's own direct rebuild does
  not clear it. Phrase it as the re-entry's scope, not as a second copy of
  the patch rule.
