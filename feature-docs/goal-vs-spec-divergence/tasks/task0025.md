# Task Plan: task0025 — the classification gate's outcome closes its question

## Goal

A question routed to the classification gate ends as a resolved question:
its packet and its answer record are written by a rule stated in one place,
and the develop state machine has a named point where the gate is called and
a named branch where its stop verdict halts the run.

## Design

### What is wrong today

The routed arm removes a question from the Batch resolution sequence
entirely and declares that "the gate's own proceed/stop outcome and its
audit record are the resolution for that question". Every other resolution
path in the document ends by writing two things — the packet's status and an
answer record — and the gate writes neither. Its only output is the
classification audit record, which is a sibling of `spec_change` in the
rework phase-state and has nothing to do with the packet lifecycle.

Two consequences follow. First, the packet stays `issued`, so the Resume
decision table re-presents it on every resume — a question nobody can
answer, in a mode where nobody is there to answer it (NFR3). Second, the
transition the gate stands in front of has no caller: `skills/develop/SKILL.md`
Step B, which drives the spec-change transition, contains neither a point at
which the gate runs nor a branch that halts on its stop verdict. Nothing
under `skills/` was changed by this feature at all.

### The contract

One place — the Classification gate section in
`references/question-resolution.md` — states what a gate pass writes, citing
the field shapes from `references/phase-state.md` and
`references/question-packet-schema.md` rather than restating them (NFR1):

- **Proceed.** The question is answered. One answer record is written for
  it, carrying `source: batch-classification-gate` and a `resolution_note`
  naming the verdict and the audit record it belongs to. The packet's
  per-question status becomes answered, and the packet's own status follows
  the same rule any other fully-answered packet follows.
- **Stop.** The question is not answered and never will be by this run. The
  packet does not stay `issued`: the section names the status a
  gate-stopped packet takes, so the Resume decision table has no reason to
  re-present it, and the stop's reason and evidence remain as the record
  NFR3 requires (the audit record already carries them; nothing is
  duplicated).
- **Inapplicable** (no `goal` block, FR20 / D3): the run stops exactly as it
  did before this revision, and the packet is closed by the same stop rule
  above — the audit record already covers this pass.

`batch-classification-gate` is the fixed name for the new `source` value; it
is added to `question-packet-schema.md`, which owns that vocabulary, and
mirrored in the validator's constant in the same change. The name is pinned
in IMPLEMENTATION.md's Shared Components (Gate-resolved answer source) —
implement against that row.

`skills/develop/SKILL.md` Step B's spec-change transition branch names:

- the point at which a batch run calls the gate — after the packet's
  `gate_id` has been identified and the routed arm has sent it there, before
  any of the transition's five steps runs;
- the stop branch — a stop verdict (including the inapplicable case) halts
  the run at that point, with no step of the transition performed and the
  reason recorded;
- that interactive is unchanged: the user is asked directly, and this
  revision introduces no new interactive question (FR8).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR7, NFR1): `references/question-resolution.md` states, in
      exactly one place, what the classification gate's proceed outcome and
      its stop outcome each write to the packet and to the answer model, and
      cites the field shapes from their owning documents rather than
      restating them. The routed arm's exit sentence in the Batch resolution
      sequence points at that place instead of ending the question's story
      there.
- [ ] AC-2 (FR7): a gate-resolved answer carries
      `source: batch-classification-gate`; that value exists in
      `references/question-packet-schema.md`'s `source` vocabulary and in the
      validator's own vocabulary, and an answer object using it validates.
- [ ] AC-3 (NFR3): the document states that no packet resolved by the gate —
      on proceed, on stop, or in the inapplicable case — is left `issued`,
      and names the status each outcome leaves, so the Resume decision table
      never re-presents a question the gate has already settled.
- [ ] AC-4 (FR7, FR8): `skills/develop/SKILL.md` Step B's spec-change
      transition branch names the gate's call point in batch, names the stop
      branch that halts the run before any step of the transition runs, and
      states that interactive is unchanged.
- [ ] AC-5 (NFR3): the stop branch records its reason and the evidence
      considered, and raises no confirmation in batch that nobody can
      answer; the statement cites the existing classification audit record
      rather than defining a second record (NFR1).
- [ ] AC-6: negative proofs exist for each new matcher — a gate outcome with
      no answer record, one with a packet still `issued`, and a Step B
      variant with no stop branch are each detected against a synthetic
      violating sample.
- [ ] AC-7 (NFR5, NFR8): `python3 -m unittest discover -s tests` passes in
      full, no pre-existing pin over `question-resolution.md`,
      `question-packet-schema.md` or the validator is deleted or relaxed, and
      the byte-identity pins in `tests/test_gate_option_vocabulary.py`
      covering a file this task changed are refreshed with the reason
      recorded in the comment above them (C10).
