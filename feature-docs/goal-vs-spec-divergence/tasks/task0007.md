# Task Plan: task0007 — create-spec writes the goal and resolves reference-scan targets

## Goal

`em-workflow/references/phases/create-spec-phase.md` writes the `goal` block
verbatim during workflow.yaml construction, never rewrites it on re-entry,
and resolves the reference-impact scan targets before dispatching the
analyst.

## Requirements

FR1, FR2, FR17, NFR1, NFR5, NFR7, NFR8

## Scope

### Files to Create
- `tests/test_create_spec_goal_persistence.py` — document pins for the goal
  write procedure, the re-entry rule, the no-source case and the scan-target
  resolution step.

### Files to Modify
- `em-workflow/references/phases/create-spec-phase.md` — the workflow.yaml
  construction section (goal write), the re-entry / reconcile behaviour, and
  the analyst dispatch loop's resolution step.

## Design

### A. Goal write (FR1, FR2)

In the workflow.yaml construction section, add the `goal` block to the list
of fields the orchestrator builds. State:

1. The value is the `/em-workflow:develop` launch-time task description,
   stored verbatim — no summarizing, normalizing or truncating, and no size
   limit. The block's schema and semantics live in
   `references/workflow-schema.md` and are cited, never restated (C2).
2. The orchestrator is the sole writer; the analyst and spec-writer never
   produce it, and it is not derived from REQUIREMENTS.md or SPEC.md.
3. **Re-entry**: when create-spec is re-entered with `status: needs_update`
   (the SPEC-change transition), an existing `goal` block is left exactly as
   it is. Only a first construction writes it.
4. **No source (EC-7)**: when there is no launch-time task description — an
   empty description, or a resumed feature reached without one — no `goal`
   block is written. State that this is a valid outcome, that no goal is
   synthesized from other documents, and that the consequence at the batch
   classification gate is defined in `references/question-resolution.md`
   (cited by path, not restated).
5. The content is untrusted data (C7); cite the envelope's Untrusted-Input
   Handling rather than re-deriving the rule.

### B. Reference-scan target resolution (FR17)

In the analyst dispatch loop, the step that resolves glob-derived categories
before dispatch currently names two categories. Extend it so the
reference-impact scan's targets are resolved there too, under the category
name fixed in IMPLEMENTATION.md's Shared Components row 3
(`resolved_input_paths.reference_scan_targets`). State:

1. The orchestrator resolves the scan targets before dispatch and passes
   them in the envelope, preserving the discipline that the analyst performs
   no filesystem discovery of its own (assumption A-4).
2. The resolution participates in the same caching and re-resolution-trigger
   rules the step already states for the other categories — cited, not
   restated.
3. The request-side flag the analyst reads
   (`analysis_scope.inspect_reference_impact`) and the result field it
   returns are owned by `references/contracts/analyst-contract.md`; this
   document names them only where it must and cites that contract.

### C. Structural constraints

The document's numbered section list and its order are pinned against a
document outside this feature's change set: extend existing sections, never
renumber and never insert a new numbered section (C3, C8).
