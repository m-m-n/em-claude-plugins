# Task Plan: task0016 — validator agreement with the two replace_all permission paths

## Goal

`em-workflow/scripts/validate-worker-output.py`'s `replace_all` permission
check accepts a re-planning patch that carries `merged` tasks and rejects an
initial-planning patch that does so, matching the two paths
`em-workflow/references/workflow-patch.md` states, so FR4's relaxation and
FR6's SPEC-change transition survive layer-3 validation instead of being
rejected there.

## Design

### The contract this task implements

`workflow-patch.md` is the definition site and task0013 owns the wording
there. Restated here so this task is implementable without reading a sibling
plan; where the two disagree, `workflow-patch.md` as task0013 writes it wins,
and the disagreement is a reportable deviation rather than a local
correction.

Two permitted paths, and one rule common to both:

1. **Initial-planning path** — the first planning pass. Permitted only when
   `tasks` is empty or every existing task's `status` is `pending`.
   Unchanged from today.
2. **Re-planning path** — an explicit re-plan, the SPEC-change transition
   being its live case. Permitted regardless of task status, `merged`
   included. It is entered when `create-plan` is `needs_update`, OR when
   `create-plan` is `pending` on a re-entry that came through
   `create-spec: needs_update` — the second form being what the transition
   actually produces, recognizable from the SPEC-change record the
   transition's own step 4 writes into the `rework.yaml` phase-state
   together with `workflow.implement.base_commit` already being set.
3. **Common to both** — a `replace_all` received while any task is
   `in_progress` or `failed` is a protocol error on BOTH paths.

### What is wrong today

The check runs its task-status test (line 1171) independently of the
`create-plan` status, so ANY non-pending task rejects the patch before the
path is even determined. A re-planning patch over merged tasks — precisely
what FR4 permits and FR6 requires — is rejected with
`replace-all-not-permitted`. The document and the validator have disagreed
since FR4 landed; only the document half was corrected.

### The repair

- Determine the path first, then apply that path's task-status rule: the
  initial-planning path keeps the empty-or-all-pending test; the re-planning
  path drops it for `merged` while keeping rule 3.
- Keep rule 3 as a single test applied on both paths, so `in_progress` /
  `failed` cannot slip through the re-planning branch.
- Keep the existing rejection when `create-plan` is neither `pending` nor
  `needs_update` (e.g. `in_progress`) exactly as it is.
- **Fail closed on a missing signal**: when the inputs needed to recognize
  the second form of the re-planning path are not supplied to the validator
  (no `--phase-state`, or no SPEC-change record in it), the run is treated as
  initial planning, not as re-planning. A narrower invocation must never
  widen what is permitted — the same discipline `create-plan-phase.md`
  states about omitted validator flags.
- Error identifiers stay as they are: a rejection still reports
  `replace-all-not-permitted`, and each rejection carries exactly one
  identifier so a regression cannot pass for the wrong reason.

### Fixture placement

New cases go in the existing `workflow-patch/replace_planning` group with the
established `valid-` / `invalid-` naming, so the fixture-coverage sweep keeps
finding a valid and an invalid case per group. Each case carries its own
synthetic `workflow.json` rather than depending on this feature's real
`workflow.yaml`, matching the group's existing convention.

### `check-plugin-invariants.py`

Only the rationale comment above `INTENTIONALLY_UNLISTED_GATE_IDS` changes:
it still says `rework.spec-change` is unlisted "so the unlisted-gate fallback
aborts it", which the classification-gate routing superseded. The exclusion
BEHAVIOUR stays — the gate id remains intentionally unlisted under decision
D1 — so this is a comment correction with no behavioural change, and the
existing both-directions exclusion test must keep passing untouched.

## Test Notes

- Every criterion is fixture-driven through the CLI, matching how the
  existing `TestDryRunApplyRejections` and `TestReplaceAllCreatePlanEntryStatus`
  classes exercise this check — extend that module rather than starting a new
  one, so the branch table for this check stays in one place.
- Both directions per branch: for each new permitted case, a mirror case that
  must still be rejected. AC-2 and AC-6 are the negative proofs for AC-1.
- AC-3's "exactly one error identifier" assertion is the retention half:
  keep it, so a change that accidentally suppresses the whole check cannot
  pass by producing no errors at all.
- The existing four cases are asserted by name, not only through the
  aggregate sweep, so a regression names the case that broke.
- Do not assert over `em-workflow/references/workflow-patch.md` from this
  module: that document belongs to task0013 in this round, and its text does
  not exist in this task's worktree. Document/validator agreement is a
  verify-phase item.
