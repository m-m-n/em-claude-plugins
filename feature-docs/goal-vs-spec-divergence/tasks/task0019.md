# Task Plan: task0019 — the classification gate's trust boundary

## Goal

Reaching the classification gate, and being aborted before it, both depend
only on values the orchestrator owns: the route is chosen from `gate_id`,
the originating findings are read from a record the orchestrator locates
itself, and irreversibility is decided from orchestrator-held metadata — so
no field a worker writes can move a question out of an abort arm.

## Design

### What is wrong today

Two independent bypasses, and one gap that makes the second harder to close.

1. **The route is chosen from a worker-set field.** The routed arm is
   entered on `category: spec-change`. A packet carrying
   `gate_id: rework.spec-change` with any other `category` enters neither
   the immediate-abort arms nor the routed arm, and falls through to the
   unlisted-gate fallback. Irreversibility has the same shape: the abort
   fires on an `assumptions[]` entry the worker itself supplies, so omitting
   `reversible: false` removes the abort. NFR2 says the three fail-closed
   arms keep their strength; today their strength is conditional on the
   worker's own honesty.
2. **Origin verification reads a path the worker chose.** Step 3 requires
   the question to name its findings' `stable_id`s "together with the review
   round record that carries them", and the orchestrator then reads the
   named finding's `category` from THAT record. Which file that is comes
   from `evidence[].path`. There is no containment, no symlink rule, no
   filename requirement and no orchestrator-side confirmation — and this
   worker writes files under `tasks/` in the same worktree. A record-shaped
   file naming its own findings `comprehensive` satisfies the check. The
   step's fail-closed clause and the precedence reservation both sit
   downstream of the read and cannot help.
3. **`stable_id` has no structured home.** `evidence[]` carries `path`,
   `line` and `detail` only, so step 3's requirement is met by prose in
   `detail`, which nothing can check.

### The repair

**Route on `gate_id`, never on `category`.** The routed arm's condition
becomes `gate_id: rework.spec-change`. `category` stops being a routing
input entirely; it is kept only as a value the packet must agree with, and
disagreement is itself fatal: a packet whose `gate_id` is
`rework.spec-change` and whose `category` is anything other than
`spec-change` is malformed and aborts. That single pairing is the whole
mapping — decision D1 keeps this feature to exactly one routed gate — so it
is stated as the arm's own condition and needs no new registry file or
vocabulary entry (NFR1).

**Make the three abort arms independent of the packet.** The immediate-abort
conditions are re-stated as a floor, not a filter:

- `category: security` / `category: license` still abort, exactly as today —
  a worker can only *add* an abort by declaring one, never remove one;
- irreversibility no longer depends on the packet alone. The orchestrator
  aborts when the operation the gate stands in front of is on its own
  irreversible list, whatever the packet's `assumptions[]` says; a packet's
  `reversible: false` still aborts on top of that.

Both are strengthenings. The section says so explicitly, so the revision can
be read as monotone against NFR2 rather than as a rebalancing.

**The orchestrator locates the round record; the packet only names ids.**
Step 3 is rewritten so the read target is derived, not supplied:

- the record is the review round record for this feature at the position
  `references/review-phase.md` "Phase R5: Persist the round record" defines
  — cited, never restated, and never taken from the packet;
- the orchestrator resolves that position itself and searches only there for
  each named `stable_id`;
- `evidence[].path` is demoted in writing to a human-readable hint: it is
  presented to a reader and never opened as part of this check;
- the existing fail-closed outcomes are unchanged in strength — an origin
  that is absent, unresolvable, or not found in the located record aborts,
  and each abort records its reason and the evidence considered (NFR3).

**Give `stable_id` a structured place.** `questions[].evidence[]` gains one
field, `finding_stable_id`, in the schema's field table. Step 3 requires at
least one `evidence[]` entry carrying it for a `rework.spec-change`
question, and aborts when none does — enforced at the gate, where the trust
decision already lives, rather than in a worker-output shape check. No
`record_path` field is added: under this repair the packet never names the
record, so a field for it would re-open the channel just closed.

`rework-planner-contract.md`'s paragraph is updated to match: the packet
names each originating finding's `stable_id` in `evidence[].finding_stable_id`
and does **not** name the round record; the orchestrator locates that itself.

### Why the enforcement sits at the gate

`scripts/validate-worker-output.py` would be a natural second place to check
the packet's shape, and the finding suggests it. It is not done here for two
reasons: task0017 owns that file this round, and — more durably — a check
there would validate the same worker-written values the repair is
deliberately removing from the trust path. The gate's abort does not depend
on the validator running, and must not. A shape check in the validator
remains a reasonable later addition; it is not what closes this finding.
