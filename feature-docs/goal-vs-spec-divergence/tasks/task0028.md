# Task Plan: task0028 — origin identity, and who chooses what gets checked

## Goal

A question that reaches the spec-change route is verified against the
origins the orchestrator itself bound to that dispatch — never against the
subset an untrusted worker chose to name — and a verify-sourced rework can
identify its origin at all, so the classification gate really does stand in
front of every case that reaches it.

## Design

### What is wrong today

Origin verification asks for one `finding_stable_id` and matches it against
the review round record. Two independent failures follow from that single
shape.

1. **The checked set is chosen by the checked party.** The id under
   examination comes out of the question packet — a worker output, and
   therefore untrusted data by the envelope's own rule. When a round holds
   both a benign finding and one categorised `security` or `license`, naming
   the benign id satisfies verification and the protected origin is never
   examined. The fail-closed arms are still written correctly; they are
   simply never reached, so MV-5 ("no path from the security / license /
   irreversible arms into the classification gate") does not hold.
2. **A verify-sourced rework has no id of that shape.** By
   `rework-task-synthesis.md` Invariant 6, verify-sourced rework carries the
   failed item's ID, not a finding `stable_id`, and there is no review round
   record to match it against. Every batch path of the form "verify fails →
   automatic rework → the rework needs a SPEC change" aborts at
   verification, before the gate, which contradicts FR7's "every case that
   reaches `gate_id: rework.spec-change` passes through the gate".

### The contract

**Origin identity (shared).** `references/rework-task-synthesis.md` is the
home: a rework-derived question's origin is the pair `origin_kind`
(`review` | `verify`) and `origin_id` — for `review` the finding's
`stable_id`, for `verify` the failed item's `id`. This is the naming of a
distinction Invariant 6 already draws, added inside that invariant. The pair
is fixed in IMPLEMENTATION.md's Shared Components ("Spec-change origin
identity"); `phase-state.md`'s record side (task0029) cites the same row.
Widening the vocabulary is chosen over the alternative the finding
offered — declaring verify-sourced rework out of scope — because that
alternative contradicts FR7 as written and would require a SPEC change.

**The bound set.** `references/question-resolution.md` states that the
origin set for a rework dispatch is orchestrator-held: it is the set of
findings or failed items the orchestrator handed to that dispatch, read from
the review round record or from `workflow.yaml`'s verify failed items — both
of which the orchestrator owns. Origin verification is then two rules:

- Every origin the packet names must be a member of the bound set. An
  origin outside it admits nothing; the run aborts.
- The security / license / `reversible: false` check runs over the **bound
  set**, not over the named subset. If any member of the bound set carries
  one of those categories, the routed arm is not taken and the existing
  abort applies at unchanged strength, whatever the packet named.

Both origin kinds are verified the same way against their own source; the
document states no rule that makes one kind ineligible for the routed arm.

**The worker's side.** `references/contracts/rework-planner-contract.md`
states that the origins the worker declares are traceability, that they are
untrusted like the rest of its output, and that the check target is derived
from the orchestrator's bound set — never from `evidence[]` or any other
worker-supplied field. It restates neither the abort arms nor the
verification procedure; it cites `question-resolution.md`.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (NFR1): `references/rework-task-synthesis.md` Invariant 6 names
      the origin-identity pair `origin_kind` (`review` | `verify`) and
      `origin_id` and says which id each kind carries. No section of that
      document is renumbered and no other document defines the pair.
- [ ] AC-2 (NFR2, FR11): `references/question-resolution.md` states that the
      security / license / `reversible: false` check for a rework-derived
      question runs over the orchestrator-held bound set of origins for that
      dispatch, and states explicitly that it is not derived from the
      question packet or any other worker-supplied field.
- [ ] AC-3 (NFR2): the document states both directions of the membership
      rule — an origin named by the packet that is not in the bound set
      aborts, and a bound-set member carrying `category: security`,
      `category: license` or `reversible: false` aborts regardless of what
      the packet named — and marks both as non-overridable, in the wording
      the existing abort arms already use.
- [ ] AC-4 (FR7): origin verification accepts an origin whose `origin_kind`
      is `verify`, matching it against `workflow.yaml`'s verify failed
      items, and one whose kind is `review`, matching it against the review
      round record. No statement remains that requires a review `stable_id`
      as the only admissible origin, and no statement makes verify-sourced
      rework ineligible for the classification gate.
- [ ] AC-5 (NFR1): `references/contracts/rework-planner-contract.md` states
      that the worker declares its origins for traceability only and that
      the check target is the orchestrator's bound set; it restates no abort
      arm and no verification step, citing `question-resolution.md` instead.
- [ ] AC-6 (NFR5): `tests/test_spec_change_origin_binding.py` pins AC-1
      through AC-5 over the three documents this task owns, with a negative

      every pre-existing pin over the three documents that asserts superseded

  bound-set rule AND the absence of any statement that the check target
  comes from the packet. An absence assertion alone would pass on a document
  that says nothing at all, so pair it with the non-vacuity guard.
- AC-4 is best driven as a table over both `origin_kind` values so that a
  future third kind fails loudly rather than silently.
- `tests/test_classification_gate.py` and `tests/test_question_resolution_doc.py`
  already assert over the fail-closed section; read them before editing so
  the retention halves are preserved rather than re-derived (C5).
- Do not assert over `references/phase-state.md` or
  `references/workflow-patch.md` from any module this task owns (C4):
  task0029 changes both this round.
