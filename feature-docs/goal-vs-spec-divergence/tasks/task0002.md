# Task Plan: task0002 — `replace_all` permission relaxation for re-planning

## Goal

`em-workflow/references/workflow-patch.md` permits `replace_planning` when
the `create-plan` step is `needs_update` even though merged tasks exist, and
states that `workflow[implement].base_commit` survives that re-planning —
without weakening any other arm of the condition.

## Requirements

FR4, FR5, NFR1, NFR5, NFR7, NFR8

## Scope

### Files to Create
_None._

### Files to Modify
- `em-workflow/references/workflow-patch.md` — rewrite the replace_all
  permission conditions and state base_commit preservation on the
  needs_update path.
- `tests/test_workflow_patch_doc.py` — update the pinned permission-condition
  assertions to the revised rule and keep every unrelated guard.

## Design

Today the permission conditions are a conjunction: (tasks empty **or** every
task `pending`) **and** (create-plan is `pending` **or** `needs_update`).
That conjunction is what rejects a post-implementation SPEC change, because
after implementation the tasks are `merged`.

Target rule, stated as two explicit paths so neither can be widened by
accident:

1. **Initial-planning path** — `create-plan` is `pending`: unchanged. The
   task-state floor (tasks empty, or every existing task `pending`) still
   applies in full.
2. **Re-planning path** — `create-plan` is `needs_update`: `merged` tasks no
   longer block the patch. State the reason in one line: the SPEC-change
   transition sets that status deliberately, so re-planning after
   implementation is the intended flow rather than an accident.
3. **Unchanged rejection** — any `in_progress` or `failed` task is still a
   protocol error on both paths. Say this explicitly and separately from
   (2), so the relaxation reads as narrow rather than as "merged tasks are
   fine now".
4. **`base_commit` preservation** — on the re-planning path,
   `workflow.implement.base_commit` appears in the patch's `preserve` list.
   State that this does not contradict the existing rework invariant that a
   rework patch never changes `base_commit`; the two say the same thing from
   different sides. The mandatory-preserve table's `replace_planning` row
   stays as it is (mandatory sets are a separate concept from what a given
   patch lists) unless the task concludes otherwise, in which case the
   change is stated in one place only.
5. **Application rule 5** keeps pointing at the permission-conditions
   section by name; the numbered rule list keeps exactly sixteen entries in
   order (an existing pin derives the count from a document outside this
   feature's change set — C3/C8).

Old wording must not survive anywhere in the document: TS-2 requires the
superseded condition to be gone, not merely supplemented.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR4): the permission-conditions section states the initial-
      planning path (`create-plan` is `pending`) with the task-state floor
      unchanged.
- [ ] AC-2 (FR4): the same section states that when `create-plan` is
      `needs_update`, existing `merged` tasks do not reject the patch.
- [ ] AC-3 (FR4): the same section still states that an `in_progress` or
      `failed` task is a protocol error, and no third `create-plan` entry
      status is listed as permitted.
- [ ] AC-4 (FR4): no sentence stating the superseded blanket condition
      ("every existing task must be `pending`" as an unconditional
      requirement of both paths) remains anywhere in the document.
- [ ] AC-5 (FR5): the document states that `workflow.implement.base_commit`
      is preserved on the re-planning path and that this is consistent with
      the rework invariant that never changes it.
- [ ] AC-6 (NFR8): the numbered application-rule list still has sixteen
      ordered entries and rule 5 still refers to the permission-conditions
      section; the `preserve` vocabulary is unchanged.
- [ ] AC-7 (NFR8): `tests/test_workflow_patch_doc.py` pins the revised rule
      — including the absence of the old wording — with every guard it held
      before either retained or replaced by an equivalent-strength assertion,
      and the full suite passes.

## Test Notes

- Assertions stay scoped to the permission-conditions section and to the
  application-rule list, never to "somewhere in the document" — the existing
  module already establishes that scoping helper; reuse it.
- The existing class that pins the permission conditions is the one to
  update. Its two current guarantees split into: the pending-path floor
  (retained verbatim in spirit) and the needs_update-path relaxation (new).
  Deleting the class outright would violate C5.
- Add an explicit absence assertion for the superseded wording (AC-4) with a
  negative proof: a synthetic sample containing the old sentence must trip
  the matcher.
- Do not weaken the fixture-derived checks (rule count, preserve
  vocabulary): they read a document outside this feature's change set and
  must keep passing untouched.
