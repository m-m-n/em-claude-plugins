## Design

### What is wrong today

The Re-planning path's second case is entered only on an **unconsumed**
`spec_change` record. `consumed` is set the moment that record grounds one
`create-spec` dispatch — that is `skills/develop/SKILL.md` Step B's rule, and
it exists for a different purpose: to stop the develop state machine's
stop-condition 3 from firing on the `needs_update` the SPEC-change transition
itself set.

The transition's actual order is:

1. the SPEC-change transition writes the record and sets `create-spec` to
   `needs_update`, `create-plan` / `implement` / `review` to `pending`;
2. the state machine re-enters `create-spec`; the record is marked consumed
   at that dispatch;
3. `create-spec` finishes; the state machine reaches `create-plan`, still
   `pending`;
4. `create-plan` produces a `replace_all` patch — with `merged` tasks
   present.

At step 4 the record is always consumed, so the re-entry signal is always
absent, so the patch always falls back to the Initial-planning rule and is
always rejected. FR6 therefore does not hold in the flow it was written for.
No fixture catches this because every fixture supplies the record directly
with the flag already set the way the case wants it, never reproducing steps
2 and 3.

### The decision (settled by the user; do not re-open)

Split the flags. `consumed` keeps its current meaning and its current
consumption point. A second, independent flag carries the re-planning
authorization: the SPEC-change transition sets it when it writes the record,
and it is spent when a re-planning `replace_all` has been applied — not
before, and never by a `create-spec` dispatch.

Two alternatives were considered and rejected by the user:

- moving `consumed`'s consumption point later — keeps one flag doing two
  jobs and lengthens the window in which stop-condition 3 is suppressed;
- having the transition set `create-plan` to `needs_update` — that is what
  SPEC.md FR6 states as `pending`, so it is a specification change and out of
  reach here.

### The contract

`phase-state.md` owns the record's schema and is the only place the two
flags are defined. The fixed names and semantics are pinned in
IMPLEMENTATION.md's Shared Components (`spec_change` flag pair) — implement
against that row, do not rename locally:

- `consumed` — stop-condition-3 suppression. Written by the orchestrator,
  `true` once the record has grounded one `create-spec` dispatch, whatever
  that dispatch's outcome. Never read as a re-planning permission.
- `replan_authorized` — re-planning `replace_all` authorization. Written
  `true` by the SPEC-change transition at record time. Set `false` once a
  re-planning `replace_all` has been applied. Never read as a stop-condition
  suppressor.

Every occurrence of the transition replaces the record wholesale, so a newly
written record is both unconsumed and authorized — that existing sentence in
`phase-state.md` must cover the second flag too.

`workflow-patch.md`'s second case changes from "an **unconsumed**
`spec_change` record" to a record carrying an **unspent re-planning
authorization**; `consumed`'s value stops participating in the decision.
Every other condition of that case (rework-phase mapping available, `feature`
match, mandatory fields non-empty, `workflow.implement.base_commit` set,
fail-closed fallback to the Initial-planning rule) is unchanged and is not
restated anywhere else (NFR1).

The validator's helper follows the document: the mandatory-shape check gains
the new flag (present and boolean), the acceptance condition becomes "the
re-planning authorization is unspent", and `consumed` is no longer consulted.
Absent, non-boolean or spent → not this form → Initial-planning rule
(fail-closed).

`skills/develop/SKILL.md` Step B states the two consumption points
separately, so the reader cannot conclude that dispatching `create-spec`
also spends the re-planning permission.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (NFR1): `references/phase-state.md` defines both flags in one
      place — name, writer, the judgement each grounds, and the point at
      which each is spent — and states explicitly that neither flag is read
      for the other's judgement. The wholesale-replacement sentence covers
      both flags. No other document restates the schema.
- [ ] AC-2 (FR6): `references/workflow-patch.md`'s Re-planning path second
      case reads the re-planning authorization flag and no longer makes
      `consumed`'s value part of the condition; its mandatory-field list and
      its fail-closed fallback sentence are updated in the same edit.
- [ ] AC-3 (FR4, FR6): the validator's re-entry helper returns true for a
      record with `consumed: true` and an unspent re-planning authorization,
      and false when that authorization is spent, absent, or not a boolean.
      Each direction has a test case.
- [ ] AC-4 (FR6): an ordering test reproduces the transition's real sequence
      — record written (authorized, unconsumed) → `create-spec` dispatched
      (`consumed` becomes true) → `create-spec` completes → `create-plan`
      read as `pending` with `merged` tasks present — and asserts that a
      re-planning `replace_all` validated at that point produces no
      `replace-all-not-permitted` error. The test drives
      `create-plan-phase.md`'s canonical validator invocation form, adding no
      flag to it.
- [ ] AC-5 (NFR1): `skills/develop/SKILL.md` Step B states the two
      consumption points separately — stop-condition 3's exclusion keyed on
      `consumed`, the re-planning authorization spent at re-planning patch
      application — and no sentence there implies one flag grounds both.
- [ ] AC-6 (FR5, NFR8): the `replace_planning` fixture group is consistent
      with the new rule: the pre-existing positive replanning case carries
      the second flag, the canonical-ordering case is accepted, the
      spent-authorization case is rejected with exactly one error identifier,
      and the case that today rejects purely on `consumed: true` no longer

      its current outcome; no guard is deleted.
- [ ] AC-7 (NFR5, NFR8): `python3 -m unittest discover -s tests` passes in
      full, and the byte-identity pins in `tests/test_gate_option_vocabulary.py`
      are refreshed to the post-change digests with the reason recorded in the
      comment above them.

## Test Notes

- AC-4 is the point of the task. A test that hands the validator a record
  with `consumed: false` proves nothing here — that is the state the current
  fixtures already assert. The case must set `consumed: true` and still
  expect acceptance.
- Build the ordering case as a sequence over one temporary feature
  directory: write the record, mark `consumed`, then validate. Asserting the
  final state alone is acceptable only if the intermediate mark is performed
  by the test rather than baked into the fixture.

  and malformed cases are the negative proofs for AC-4.

  regression names the case that broke.

  task0023 and task0024/task0025 own those documents this round and their
  text does not exist in this worktree. Cross-document agreement is a
