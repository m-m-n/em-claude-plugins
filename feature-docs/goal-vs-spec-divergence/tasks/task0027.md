# Task Plan: task0027 — the carry-over rule reaches its producer and its consumers

## Goal

The re-planning carry-over rule that `references/workflow-patch.md` owns is
actually usable end to end: the only worker that produces a re-planning
`replace_all` is told how to number ids and how to declare
`carried_task_ids`, and no consumer document restates the rule set's size in
a form that can drift away from it again.

## Requirements

FR4, FR5, FR6, NFR1, NFR5, NFR8

## Scope

### Files to Create

- `tests/test_replanning_producer_alignment.py` — pins the producer-side
  instructions and the absence of a restated rule count in the three
  documents this task owns.

### Files to Modify

- `em-workflow/agents/implementation-planner.md` — the task-id allocation
  instruction and the `workflow_patch` output description: a re-planning
  pass declares registered ids and supplies bodies only for new ones.
- `em-workflow/references/contracts/planner-contract.md` — the tasks_patch
  description gains the carry-over field by citation, and its hard-coded
  count of `workflow-patch.md`'s application rules goes away.
- `em-workflow/references/phases/create-plan-phase.md` — the same hard-coded
  count in the reading list at the top of the document.

## Design

### What is wrong today

Two symptoms, one root cause: the carry-over rule was added to
`references/workflow-patch.md` (application rule 17 and the Re-planning
task-id allocation section) and never reached anything downstream of it.

1. Two consumers state how many application rules exist — the reading list
   at the top of `references/phases/create-plan-phase.md` and the
   `tasks_patch` paragraph of `references/contracts/planner-contract.md`
   both say "sixteen". The SSOT has seventeen. The rule the count drops is
   exactly the carry-over obligation, and the count is what a reader uses as
   the measure of what create-plan must satisfy. A restated count is a
   restated rule (NFR1 / SC-7): it has no way to stay true.
2. `agents/implementation-planner.md` — the sole producer of a
   `replace_planning` patch — still numbers tasks from `task0001` and still
   puts every task into `entries`. `carried_task_ids` appears neither in the
   prompt nor in `planner-contract.md`. A re-planning patch produced by
   following the current instructions is rejected by the validator every
   time, so the feature's central path (re-plan while merged tasks stay
   registered) has never been able to run.

### The contract

The rule set stays in exactly one home. Consumers cite
`references/workflow-patch.md` by path and say what a reader must do there;
they never state how many rules it contains, and they never restate a rule's
content. Removing the count is not a renumbering of anything the consumers
own — the citation sentence replaces the count sentence in place (C3).

The producer side gains a two-branch allocation instruction, expressed in
terms of the patch fields whose meaning `workflow-patch.md` owns:

- **Initial planning** (`create-plan` is `pending`): unchanged. Ids run from
  `task0001`, every task appears in `entries`, and `carried_task_ids` is
  absent or empty.
- **Re-planning** (`create-plan` is `needs_update`): every id already
  registered in the target `workflow.yaml` is listed in
  `tasks_patch.carried_task_ids`, and no body is supplied for any of them —
  their records are copied verbatim by the application. `entries` carries
  only ids that are not yet registered, allocated above the high-water mark,
  and the two sets are disjoint.

The IMPLEMENTATION.md Shared Components row "Re-planning carry-over
declaration" fixes the field names; implement against that row rather than
inventing a name here.

The planner's own output description follows the same split: on a
re-planning pass its `workflow_patch` must carry `carried_task_ids`, and the
instruction that used to say "every task goes in `entries`" must be gone,
not merely qualified — a producer that reads both statements still produces
the rejected shape.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (NFR1): neither `references/phases/create-plan-phase.md` nor
      `references/contracts/planner-contract.md` states a count of
      `workflow-patch.md`'s application rules — no number word, no numeral —
      and each of the two sites that carried the count now cites
      `references/workflow-patch.md` by path instead.
- [ ] AC-2 (FR4, NFR1): `references/contracts/planner-contract.md` states
      that a re-planning `replace_all`'s `tasks_patch` carries
      `carried_task_ids` alongside `entries`, and defers to
      `references/workflow-patch.md` for what the two fields mean — it
      states no eligibility, disjointness or copying rule of its own.
- [ ] AC-3 (FR4, FR5, FR6): `agents/implementation-planner.md`'s task-id
      allocation instruction has two branches keyed on the `create-plan`
      step's status. The initial-planning branch numbers from `task0001`;
      the re-planning branch requires every id already registered in the
      target `workflow.yaml` to appear in `carried_task_ids`, requires
      `entries` to contain only unregistered ids allocated above the
      high-water mark, and states that no body is supplied for a carried id.
- [ ] AC-4 (FR4): `agents/implementation-planner.md`'s description of the
      `workflow_patch` it returns names `carried_task_ids` as a field it
      emits on a re-planning pass, and the document contains no surviving
      instruction to place every task in `entries`.
- [ ] AC-5 (NFR5): `tests/test_replanning_producer_alignment.py` pins AC-1
      through AC-4 by scanning only the three documents this task owns. Each
      matcher carries a negative proof against a synthetic violating sample
      (a document that states a count; one that omits `carried_task_ids`;
      one whose allocation instruction has a single branch), and AC-1's
      absence assertion carries a non-vacuity guard proving the scanned
      sections were found and non-empty.
- [ ] AC-6 (NFR8): `python3 -m unittest discover -s tests` passes in full,
      and no pre-existing pin over the three documents is deleted or
      relaxed — a pin asserting a superseded count is rewritten to assert
      the citation, in this same change.

## Test Notes

- AC-1 is an absence assertion over prose, so state the matcher as a single
  regular expression covering both number words and numerals followed by the
  rule-set's name, and prove it fires on a synthetic sample. Without the
  non-vacuity guard the assertion passes on an empty read.
- AC-3 and AC-4 are structural: match on the branch headings / list items
  and on the field name, not on a full sentence, so ordinary rewording of
  the prompt does not break the pin.
- `agents/implementation-planner.md` is a worker prompt: check that the two
  branches are stated in the imperative form the rest of that prompt uses,
  and that the re-planning branch is reachable from the prompt's own
  description of when it is dispatched.
- Do not assert anything over `references/workflow-patch.md` from this
  task's module (C4): task0029 changes that file this round, and this task's
  worktree does not contain its edit.

## Out of Scope

  refreshed by this task.
- The validator (`scripts/validate-worker-output.py`) and the
  `replace_planning` fixtures — they already enforce the carry-over rule;

  consumption — task0029 owns that this round.
- Any change to how a carried record is copied, or to the high-water mark's
  definition. Both are `workflow-patch.md`'s to state.
- A second plugin version bump.
