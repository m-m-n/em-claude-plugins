# Task Plan: task0011 — plugin version bump

## Goal

The em-workflow plugin's version is raised in both manifests to the same
value, so an installed cache picks up this feature's changed files.

## Requirements

NFR6, NFR5, NFR7, NFR8

## Scope

### Files to Create
- `tests/test_goal_vs_spec_divergence_version_bump.py` — pins that both
  manifests parse, carry the same em-workflow version, and that the version
  is strictly greater than the pre-change baseline.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — raise the version field.
- `.claude-plugin/marketplace.json` — raise the em-workflow entry's version
  field to the same value.

## Design

1. Read the current version from both manifests and confirm they match
   before changing anything; a pre-existing mismatch is a finding to report,
   not something to silently normalize.
2. Raise by one patch step (semantic versioning; this feature changes
   protocol documents and prompts, i.e. behaviour of the workflow, and the
   repository's convention is that most changes are patch-level). Choose a
   minor step only if the version's own history in this repository shows that
   convention for comparable feature-sized changes; state the choice in the
   completion report either way.
3. Write the identical value to both files. No other field of either manifest
   changes — in particular the plugin description stays as it is, since other
   modules assert its content.
4. Report, in the completion report, that applying the new version requires
   restarting Claude Code (repository rule).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (NFR6): `em-workflow/.claude-plugin/plugin.json` parses as JSON
      and its `version` is strictly greater than the value recorded as this
      feature's baseline.
- [ ] AC-2 (NFR6): `.claude-plugin/marketplace.json` parses as JSON and its
      em-workflow entry's `version` equals plugin.json's `version` exactly.
- [ ] AC-3 (NFR6): no field other than `version` changed in either manifest.
- [ ] AC-4 (NFR5): the new test module is discovered by
      `python3 -m unittest discover -s tests` and imports only the standard
      library.
- [ ] AC-5 (NFR6): the version comparison in the test is a component-wise
      semantic-version comparison, not a string comparison.
- [ ] AC-6 (NFR8): every pre-existing module that reads either manifest still
      passes, including the ones asserting the plugin description and an
      earlier baseline comparison.
- [ ] AC-7 (NFR8): the full suite passes.

## Test Notes

- The baseline the module compares against is a literal recorded in the
  module itself (the version as it stood before this feature), matching how
  the repository's existing version-bump modules are written.
- Assert equality between the two manifests by parsing both, never by
  substring search.
- Edge case: a version with more or fewer than three components must not
  crash the comparison — normalize before comparing.
- Negative proof: a synthetic pair of manifests with mismatched versions must
  fail the equality matcher, and a synthetic non-increasing version must fail
  the ordering matcher.

## Out of Scope

- Any content change to either manifest beyond `version`.
- Regenerating or editing the LICENSE file (`project.license` is `none`; no
  license change is part of this feature).
