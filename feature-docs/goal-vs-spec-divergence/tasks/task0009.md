a create-plan derivation from the tasks' `files` plus the default entries,
stated as a guard rather than as a statement of the goal.

## Design

### A. Derivation (create-plan protocol)

Define, in the create-plan phase document, that a feature's declared change
set is derived — not authored:

1. **Inputs**: the union of every `tasks.*.files` entry the planner
   registered in `workflow.yaml`, plus the default entries. The default
   entries' enumeration and their membership semantics stay in the document
   templates and are cited by path — this document must not enumerate the
   two workflow-artifact root globs together (C6c; a repository-wide guard
   fails if a third file carries both).
2. **Status**: it is a **guard**, not a statement of the goal. Say this
   explicitly — it is the distinction the whole feature turns on.
3. **Superset semantics**: the observed change set must be contained in the
   derived set; equality is not required, and a declared path that never
   materializes is not a violation. Cite the template for the semantics
   rather than restating them.
4. **Timing**: the derivation is available once planning has registered the
   task set, and it is re-derived whenever the task set changes (re-planning,
   rework append) rather than being frozen at first planning.
5. No verify-side exclusion rule may be introduced: nothing in this
   document may say that workflow-generated artefacts are excluded, ignored
   or subtracted from the observed change set at verification time (C6d).

### B. SPEC template

Replace the instruction that asks the author to enumerate every file and
directory the feature creates or modifies with a statement that the
feature-specific paths are derived at create-plan from the tasks' `files`,
and that this section states the derivation and the default entries rather
than a hand-authored list. Keep, unchanged: the two default entries, what
each covers, the "part of the declaration unless explicitly removed"
semantics, the superset/containment paragraph, and the zero-implement-task
case.

### C. Requirements template

Decide within this task whether its declared-change-set subsection must
follow. If the SPEC template no longer asks for a hand-authored list while
the requirements template still does, the two contradict each other; align
it in that case. If alignment is unnecessary, leave the file untouched and
record the conclusion in the completion report.

## Test Notes

- New module: pins scoped to the create-plan phase document's derivation
  section only (C4).
- Existing template module: the placeholder pin is replaced, not deleted;
  its replacement asserts the derivation statement with equal specificity
  (C5). Every other assertion in that module must keep passing.
- The repository-wide invariant module is a guard this task can break by
  moving where the enumeration lives. Run it early; if it fails, the correct
  fix is to keep the enumeration in the templates (C6c), not to widen the
  guard. Editing that module is a last resort, allowed only when this task
  deliberately moved a carrier.
- Negative proof per new matcher; non-vacuity guard on every absence
  assertion.
- The new module must not combine a wildcard scan of SPEC paths under
  `feature-docs/` with a requirement that a section be present (C9) — read
  fixtures by literal path only.
