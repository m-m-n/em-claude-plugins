# Task Plan: task0029 — the phase-state records' writer, origin and lifetime

## Goal

The two records the rework phase-state carries stop being write-only
artefacts: the re-planning authorization has a named actor and a named
moment at which it is spent, the classification audit accumulates instead of
overwriting itself, and a `spec_change` record can name a verify-sourced
origin as well as a review-sourced one.

## Design

### What is wrong today

Three defects in the same two records, all of the same kind: a rule is
stated about a record's content while nothing states who maintains it.

1. **`replan_authorized` is never spent.** `skills/develop/SKILL.md` points
   at `workflow-patch.md`'s re-planning path as the consumption site, and
   that path only reads the flag. `phase-state.md` lists the SPEC-change
   transition — the writer that sets it `true` — as its only writer. The
   authorization therefore stays `true` forever, which is a standing
   permission to re-plan; FR4's premise that the `create-plan` `pending`
   path is unchanged does not survive it. The fixture
   `invalid-replace-all-replan-authorization-spent` verifies a state no
   producer ever reaches.
2. **The classification audit erases itself.** `phase-state.md` says one
   record per gate pass and, in the next breath, that each pass replaces the
   record wholesale. A run that passes the gate twice keeps only the second
   `classifier` / `verdict` / `evidence_ids` / `decision` / `reason`. FR14
   asks for a record for every case, and NFR3 asks that a stop's reason and
   evidence remain — neither holds once a second pass happens.
3. **A verify-sourced origin cannot be recorded.** The `spec_change`
   record's origin field is a review finding's `stable_id`, and it is
   mandatory. A rework that came from a verify failed item has no value of
   that kind, so it cannot write a valid record, and therefore cannot use
   the re-entry route FR4 / FR6 opened.

### The contract

**One consumption procedure.** `references/workflow-patch.md`'s re-planning
path states it once: after a re-planning `replace_all` has been applied, the
orchestrator sets that record's `replan_authorized` to `false`, in the same
state write that records the application — so an authorization grounds
exactly one re-planning pass. `phase-state.md`'s writer list for
`spec_change` names both writers (the SPEC-change transition, which sets the
record with the flag `true`; the orchestrator's re-planning application,
which spends it) and points at the procedure rather than repeating it.
`skills/develop/SKILL.md` cites the same place. If stating the procedure
requires a new application rule in `workflow-patch.md`, that document's own
count statement is updated in the same edit — it is the only document
allowed to state one (task0027 removes the restatements elsewhere).

**An append-type audit list.** `classification` becomes a list: a gate pass
appends one entry and never rewrites or removes an earlier one, so a run
that passes the gate n times holds n entries in order. Entry fields are
unchanged. The record leaves the id-uniqueness exemption it currently sits
in and follows the same entry-id rule as the other lists in the document.

**The origin pair.** The `spec_change` record identifies its origin with
`origin_kind` (`review` | `verify`) and `origin_id`, replacing
`finding_stable_id`. The pair is defined in
`references/rework-task-synthesis.md` (task0028, IMPLEMENTATION.md Shared
Components "Spec-change origin identity"); `phase-state.md` cites that
definition and states only what the record stores. The validator's
mandatory-field set for `spec_change` follows, and every `replace_planning`
fixture moves to the pair in the same change. A record with
`origin_kind: verify` is a re-entry signal on exactly the same terms as a
review-sourced one — the kind never changes what the flags mean.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR4, NFR1): exactly one document — `references/workflow-patch.md` —
      states the procedure that sets `spec_change.replan_authorized` to
      `false`, naming the actor (the orchestrator) and the moment (once the
      re-planning `replace_all` has been applied, in the same state write).
      `references/phase-state.md` and `skills/develop/SKILL.md` cite that
      place and state no procedure of their own.
- [ ] AC-2 (FR4): `references/phase-state.md`'s writer list for the
      `spec_change` record names both writers — the SPEC-change transition
      that sets the record, and the re-planning application that spends the
      authorization — so no reader can conclude the flag has a single
      writer.
- [ ] AC-3 (FR14, NFR3): `references/phase-state.md` defines
      `classification` as an append-type list — one appended entry per gate
      pass, earlier entries never rewritten or removed — the
      wholesale-replacement statement is gone, and the record no longer
      appears in the id-uniqueness exemption.
- [ ] AC-4 (FR14, NFR3): a phase-state document carrying two classification
      entries validates, and both entries' `classifier`, `verdict`,
      `evidence_ids`, `decision` and `reason` are readable afterwards; a
      document in which a second pass replaced the first is detected as a
      violation.
- [ ] AC-5 (FR6): the `spec_change` record carries `origin_kind`
      (`review` | `verify`) and `origin_id` in place of
      `finding_stable_id`, citing `references/rework-task-synthesis.md` for
      the pair's meaning; a record whose `origin_kind` is `verify` is
      accepted as a re-entry signal on the same terms as `review`.
- [ ] AC-6 (FR4, FR6): the validator's `spec_change` mandatory-field set is
      the new pair plus the fields it already required, every
      `replace_planning` fixture's `phase-state.json` uses the pair, and the
      suite still shows a spent authorization rejected, an absent
      authorization rejected, and a fresh authorization accepted.
- [ ] AC-7 (NFR5): `tests/test_classification_audit_retention.py` pins AC-3
      and AC-4 with a negative proof per matcher — a document that replaces
      the record, one that drops an earlier entry's `reason` — and a
      non-vacuity guard on every absence assertion.
- [ ] AC-8 (NFR8): `python3 -m unittest discover -s tests` passes in full;
      the byte-identity SHA256 pins in `tests/test_gate_option_vocabulary.py`
      covering each file this task changed are refreshed in the same change
      with a comment naming task0029 and the reason, and no pin is deleted
      or relaxed.
