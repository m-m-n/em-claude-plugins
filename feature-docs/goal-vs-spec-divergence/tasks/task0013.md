# Task Plan: task0013 — re-planning permission premise, task-id allocation, and the mandatory preserve set

## Goal

`em-workflow/references/workflow-patch.md` states a `replace_all`
re-planning permission condition that actually holds in the state the
SPEC-change transition produces, forbids a re-planning pass from re-issuing
a retired task id, and lists `workflow.implement.base_commit` in the
mandatory `preserve` set for that path.
`em-workflow/references/implement-phase.md`'s recycled-task-id reasoning
rests on that id-allocation rule instead of on renumbering from `task0001`,
so no re-planned task can inherit a retired id's `merged` journal event.

## Design

Three findings share one root cause: the re-planning path was specified
against a transition state that no document actually produces, and against
an id-allocation habit that makes journal events outlive the task ids that
wrote them.

1. **Permission key that matches the transition.** The SPEC-change
   transition — identically in `rework-task-synthesis.md` Section 10,
   `contracts/rework-planner-contract.md` and `agents/rework-planner.md` —
   sets `create-spec` to `needs_update` and `create-plan` / `implement` /
   `review` to `pending`. The Re-planning path's current key
   (`create-plan` is `needs_update`) is therefore never satisfied by the
   transition, and the pass falls into the Initial-planning path where merged
   tasks make it a protocol error — the exact rejection FR6 says must not
   happen. Widen the Re-planning path ADDITIVELY so it admits both the
   `create-plan: needs_update` case (unchanged, FR4's literal condition) and
   the case the transition produces: `create-plan` is `pending` on a
   re-entry that came through `create-spec: needs_update`. Name the signal
   that makes the second case recognizable from state the transition itself
   writes, rather than from intent — the SPEC-change record the transition's
   own step 4 puts in the `rework.yaml` phase-state, together with
   `workflow.implement.base_commit` already being set. The transition
   documents are authoritative and are NOT edited by this task (FR6, NFR1).

2. **Unchanged halves.** The Initial-planning path's condition for a genuine
   first pass, and the rule that a `replace_all` received while any task is
   `in_progress` or `failed` is a protocol error on both paths, stay exactly
   as they are (FR4). Say so explicitly, because item 1 is otherwise
   readable as a general relaxation.

3. **Task ids are never re-issued.** State in the `replace_all` section that
   a re-planning pass allocates task ids continuing ABOVE the highest id the
   feature has ever registered — a retired id is never issued a second time.
   This is the only one of the three repair directions the finding lists that
   stays inside SPEC.md's Declared Change Set: widening the recycled-task-id
   carve-out to `merged` would need `em-workflow/hooks/queue_launch_guard.py`
   to agree, and switching journal generations would need the journal writers
   — both outside the declared set (C8).

4. **I.2.a reasoning rebuilt on item 3.** Step I.2.a currently argues that
   `pending` + a stale journal event can only arise because "the planner's
   `replace_all` re-numbers tasks from `task0001`", and that no `merged` last
   event can be inherited because I.2.c's route-back gate admits no merged
   task. The SPEC-change transition reaches re-planning by a different door,
   with merged tasks present, so that second half is false today. Replace the
   renumbering premise with a citation of item 3's allocation rule (stated in
   `workflow-patch.md`, cited here and never restated) and derive the same
   conclusion from it: because no retired id is ever re-issued, no journal
   event can be inherited by a later task at all, so the carve-out stays
   correctly scoped to `failed` and a `pending` task can never carry an
   inherited `merged` last event. The hook classification table, the
   `failed`-only carve-out itself, and every statement about which hook reads
   what are unchanged — no file under `em-workflow/hooks/**` is touched.

5. **Mandatory preserve row.** Application rules 13 and 14 check only paths
   the patch actually lists, so FR5's prose about carrying
   `workflow.implement.base_commit` on a re-planning patch is unenforced
   while the Mandatory `preserve` table's `replace_planning` row reads
   `(none)`. Put `workflow.implement.base_commit` in that row for the
   re-planning path, and state the initial-planning case explicitly (no
   `implement` base commit exists yet on a first planning pass), so the
   requirement is well defined when the key is absent.
