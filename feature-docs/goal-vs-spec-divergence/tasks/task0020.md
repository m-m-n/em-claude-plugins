# Task Plan: task0020 — a writer, an operation and an evidence form for deviation auto-addition

## Goal

An admitted implement deviation is written to a named location by a named
actor through a named operation, on evidence with a defined form, and it
survives re-planning — so FR19's auto-addition is an executable rule rather
than a described outcome.

## Requirements

FR18, FR19, NFR1, NFR3, NFR5, NFR8

## Scope

### Files to Modify

- `em-workflow/references/implement-phase.md` — the wake phase's step 3 and
  the Deviation auto-addition rule that follows it.
- `em-workflow/references/phases/create-plan-phase.md` — section 12's
  **Retention** bullet.
- `tests/test_deviation_auto_addition.py` — the evidence-form and
  write-procedure pins.
- `tests/test_change_set_derivation.py` — the retention pins.

## Design

### What is wrong today

The rule names a destination and stops there.

1. **Nobody writes it.** Section 12 says an admitted addition is retained in
   "the `files` list of the task whose deviation was admitted, in
   `workflow.yaml`". `implement-phase.md`'s wake step 3 — the only place an
   implement wake writes `workflow.yaml` — sets `tasks.{T}.status` and
   nothing else. `workflow.yaml`'s write ownership is the orchestrator plus
   the two patch operations, and neither patch operation appends to an
   existing task's `files`. So the retention location is named by one
   document and written by none.
2. **The evidence has no form.** "a named, checkable condition, not a
   judgement call" says what the evidence is not. It does not say what a
   valid one looks like or how the orchestrator checks it, so the admission
   decision is unfalsifiable and EC-5 (implementer convenience is not
   evidence) cannot be applied mechanically.
3. **The audit trail points at an input field.** The rule routes its record
   through the completion report's `deviations` entries. That is the
   implementer's own input to step 3, consumed and discarded — not a place
   an audit record persists.

`tasks.{T}.files` is not a passive note: it is the implementer's
`expected_files` and an input to the planner's task-independence judgement,
so leaving its writer undefined leaves both consumers reading a value nobody
maintains.

### The repair

**Name the writer and the operation.** Wake step 3's enumeration of what it
sets grows from `tasks.{T}.status` to `tasks.{T}.status` and, for each
admitted deviation, an append to that same task's `files`. The actor is the
same orchestrator, in the same already-refreshed worktree, inside the same
single commit step 3 already performs — no new write path, no new patch
operation, no new phase. The append is stated as an append: an existing entry
is never removed or rewritten by this rule, and re-admitting an already
listed path is a no-op.

**Define the evidence form.** An admitted deviation carries, in its
completion-report entry:

- the path being added;
- the identifier of the acceptance criterion that would otherwise be
  dropped — an `AC-n` of this task's own plan, or a requirement id
  registered in `workflow.yaml`; and
- how the criterion fails without the path, stated as an observable outcome
  (a named test that cannot be written or cannot pass), not as a preference.

The orchestrator admits the deviation only when all three are present and
the named identifier actually exists. Anything else — a missing identifier,
an identifier that resolves to nothing, a rationale of convenience or
tidiness — is not admitted (EC-5), surfaces as an ordinary deviation, and
the containment check handles it exactly as before. The containment check
itself is unchanged, and no exclusion rule is introduced anywhere (C6d).

**Name where the audit record persists.** The decision — admitted or
declined, the evidence considered, and for a decline the reason — is
recorded in the same commit step 3 writes, alongside the `files` append it
justifies: an admission is legible from the `files` entry plus the wake
commit that added it, and a decline is recorded in the wake phase's report
for that task. The completion report stays the *channel* the evidence
arrives on, which is what decision D7 fixed; this task names what outlives
it, without adding a phase-state field (D7 unchanged).

**State why retention survives re-planning.** Section 12's Retention bullet
gains one clause: the location survives re-derivation because a re-planning
`replace_all` may not drop an already-registered task entry, so the task
carrying the admitted path is still there to be read. That rule's home is
`references/workflow-patch.md`, which task0017 writes this round; it is cited
by path here and never restated (NFR1, C2). If at integration that document
does not carry the rule, this is a reportable deviation, not a licence to
restate the rule locally or to invent a second retention location.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR19): `implement-phase.md`'s wake step 3 names
      `tasks.{T}.files` among what it updates, states that the update is an
      append performed by the orchestrator in the same commit as the status
      update, and states that an existing entry is never removed or
      rewritten by this rule.
- [ ] AC-2 (FR19): the auto-addition rule defines the evidence form as three
      named parts — the path, the identifier of the acceptance criterion or
      requirement that would otherwise be dropped, and the observable way it
      fails without the path — and states that the identifier must resolve
      to something that exists.
- [ ] AC-3 (FR19, EC-5): the rule states that a deviation failing any part
      of AC-2 is not auto-added, surfaces as an ordinary deviation, and is
      handled by the unchanged containment check; implementer convenience is
      named as a non-qualifying rationale.
- [ ] AC-4 (NFR3): the rule states where the admission decision persists —
      for an admission, the `files` entry and the wake commit that added it;
      for a decline, the wake report's record of the reason — and does not
      point at the completion report as the record's resting place.
- [ ] AC-5 (FR18): section 12's Retention bullet states that the location
      survives re-derivation because a re-planning `replace_all` may not drop
      a registered task entry, citing `references/workflow-patch.md` by path
      without restating the rule.
- [ ] AC-6 (FR19, retention): the containment check is still stated as
      unchanged, unjustified scope expansion is still stated as stopped, and
      no statement is added anywhere that workflow-generated artifacts are
      excluded, ignored or subtracted from the observed change set (C6d).
- [ ] AC-7 (NFR1): the evidence form and the write procedure are each stated
      in exactly one document — the rule's own home in `implement-phase.md` —
      and section 12 cites rather than repeats them.
- [ ] AC-8 (NFR5, NFR8): both pin modules keep their existing assertions
      passing, every new matcher carries a negative proof against a synthetic
      violating sample, and `python3 -m unittest discover -s tests` passes
      for the modules this task owns.

## Test Notes

- AC-2's matcher must fail on the current text. Write the negative proof
  first against a sample that says only "a named, checkable condition" — if
  that sample passes, the matcher is testing for the wrong thing.
- AC-6 is the retention half (C5). The C6d scan already exists in
  `tests/test_declared_change_set_invariants.py`; do not edit that module —
  re-run it and treat a failure as a signal that the new wording strayed into
  exclusion language.
- Keep the two modules' ownership split along document lines:
  `test_deviation_auto_addition.py` asserts over `implement-phase.md`,
  `test_change_set_derivation.py` over `create-plan-phase.md` (C4). Neither
  asserts over `workflow-patch.md` — task0017 owns it this round and its
  text does not exist in this worktree.
- The `files`-append assertion should pin the enumeration inside step 3, not
  a free-floating sentence, so a statement that landed in the wrong step
  fails.
