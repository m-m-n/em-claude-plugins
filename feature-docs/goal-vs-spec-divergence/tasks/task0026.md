# Task Plan: task0026 — create-spec re-entry upserts the requirement map instead of freezing it

## Goal

A SPEC change that adds or alters a requirement produces a `workflow.yaml`
requirement map that contains it, so the re-planning pass that follows can
register tasks against it — while every requirement's already-earned `tasks`
and `tests` history survives the re-entry.

## Requirements

FR5, FR6, NFR1, NFR5, NFR8

## Scope

### Files to Modify

- `em-workflow/references/phases/create-spec-phase.md` — section 11's
  "Partial update on re-entry" list and the upsert rule that replaces its
  `requirements` member.
- `tests/test_create_spec_reentry_preservation.py` — the pins for the
  partial-update list, extended with the upsert rule's matchers.

## Design

### What is wrong today

`create-spec-phase.md`'s re-entry rule lists `project` and `requirements`
among the things a `needs_update` re-entry leaves untouched. But the only
reason create-spec is ever re-entered is the SPEC-change transition, and the
only reason that transition fires is that the specification has to change —
very often by adding or restating a requirement.

Freezing the map produces a state the rest of the protocol rejects: the new
FR exists in `SPEC.md` and in spec-writer's `spec_index`, but not in
`workflow.yaml`, and the very next thing that happens is a re-planning pass
whose task entries name their requirements. The task-entry check requires
every listed requirement id to already exist in `workflow.yaml`, so the
patch is rejected and the transition dead-ends. `requirements_patch` is not
a way out: its `set` admits only the `_append` forms of `tasks` and `tests`
plus three status fields, so it can update an entry but can never create
one — an entry with no `title` is not a valid entry.

### The contract

`requirements` leaves the untouched list and gains an upsert rule of its
own. The re-entry rebuilds the map from spec-writer's `spec_index` — the
same source the first construction uses, so there is one derivation, not two
(NFR1) — under three constraints:

1. **New id** — an id present in the new `spec_index` and absent from
   `workflow.yaml` is created, with its `title` / `status` / `tbd_reason` /
   `excluded_reason` from the index and empty `tasks` / `tests`.
2. **Surviving id** — an id present in both keeps its `tasks` and `tests`
   arrays exactly as they are; the fields the index owns (`title`, `status`,
   `tbd_reason`, `excluded_reason`) are refreshed from it. Nothing that
   records what has already been implemented or verified is rewritten from
   the specification.
3. **Disappearing id** — an id present in `workflow.yaml` and absent from
   the new `spec_index` gets exactly one documented outcome, and that
   outcome preserves the traceability of any task already merged against it.
   The document states that outcome explicitly; silent deletion is not
   available, because a merged task's `requirements` list would then name an
   id `workflow.yaml` no longer has.

The rest of the partial-update list is unchanged and must stay verbatim in
force: `tasks` in full with each entry's `status` / `branch` / `files`, each
step's `status` and `completed_at_commit` except those the transition
assigns, `workflow.implement.base_commit`, `project`, and `goal` (whose own
re-entry carve-out further down the section is untouched).

The write is the create-spec orchestrator's own — this phase builds
`workflow.yaml` directly and uses no worker patch; that sentence already
exists at the top of section 11 and is cited, not restated. The document
also states the ordering the downstream pass depends on: the requirement
upsert happens during create-spec, therefore before the re-planning patch is
validated, which is what makes a task entry naming a new FR acceptable.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR6): `requirements` is no longer listed among the things a
      `needs_update` re-entry leaves untouched, and the section states an
      upsert rule in its place, sourced from spec-writer's `spec_index`.
- [ ] AC-2 (FR5): the upsert rule states that a surviving requirement's
      `tasks` and `tests` arrays are preserved and that only the fields the
      `spec_index` owns are refreshed — a requirement that merged tasks
      already reference does not lose that reference.
- [ ] AC-3 (FR6): the rule states exactly one outcome for a requirement that
      disappears from the new `spec_index`, and that outcome keeps the id
      resolvable for any merged task whose `requirements` names it. No
      wording permits dropping such an entry.
- [ ] AC-4 (FR6): the section states that the upsert happens during
      create-spec and therefore precedes the re-planning patch's validation,
      so a task entry naming a newly added requirement id is acceptable when
      that patch is applied.
- [ ] AC-5 (NFR8): every other member of the partial-update list is still
      present with the same force — `tasks` in full including `status`,
      `branch` and `files`; step `status` and `completed_at_commit` except
      those the transition assigns; `workflow.implement.base_commit`;
      `project`; and the `goal` carve-out. The existing pin module keeps its
      assertions for each; none is deleted to make an AC above pass.
- [ ] AC-6 (NFR1, NFR5): the rule is stated once, in
      `create-spec-phase.md`, and cites `references/workflow-schema.md` for
      the requirement entry's shape rather than restating it; and
      `python3 -m unittest discover -s tests` passes in full.

## Test Notes

- The existing module asserts an "untouched" list by membership. Removing a
  member must not weaken that assertion into a vacuous one — keep the list
  matcher and add a positive matcher for the upsert rule, plus a negative
  proof that a document still listing `requirements` as untouched fails.
- AC-3's matcher should assert the presence of a named outcome, not merely
  the absence of the word "delete"; an absence-only assertion passes against
  a document that says nothing at all.
- This task changes one protocol document and one pin module. It has no
  fixture and no validator work: the check it unblocks
  (`requirements` ids must exist in `workflow.yaml`) is already implemented
  and is intentionally left alone.
- Do not assert over `references/workflow-patch.md`,
  `references/phase-state.md` or `skills/develop/SKILL.md` from this module —
  task0022 and task0023 own those this round (C4).

## Out of Scope

- `references/workflow-patch.md`'s `requirements_patch`: widening its `set`
  vocabulary so a worker could create a requirement entry is explicitly not
  the fix — the create-spec orchestrator is the writer here, and workers
  never write `workflow.yaml`.
- The `goal` block's re-entry rule (task0018 settled it; untouched).
- The re-planning patch's own permission and content rules (task0022,
  task0023).
- `SPEC.md` / `REQUIREMENTS.md`: this task states how the workflow map
  follows a specification change, and makes no specification change itself.
- A second plugin version bump.
