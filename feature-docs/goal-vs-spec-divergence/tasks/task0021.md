# Task Plan: task0021 — realign the guardrail migration pins with the current repository

## Goal

`tests/test_guardrail_hooks_migration.py` asserts the repository as it is
today — rule files under their current names, and rule discoverability
located where the current policy puts it — so the full suite passes without
any guard being removed.

## Requirements

NFR5, NFR8

## Scope

### Files to Modify

- `tests/test_guardrail_hooks_migration.py` — `REPO_RULE_FILES` and the
  `TestRepositoryRulesAreInPlace` class.

## Design

### What is wrong today

Three assertions in this module fail, and all three are stale pins rather
than real regressions. The user reviewed them and decided the test side is
what is out of date (`phase-state/rework.yaml`, `pending_decisions[0]`,
id `ac11-stale-guard`).

1. `REPO_RULE_FILES` names `plugin-version-bump.md`. The file was renamed to
   `core-plugin-version-bump.md` when the `core-` prefix convention was
   adopted for rules the project cannot lose. `slash-commands-as-skills.md`
   is still correct. So `test_every_repository_rule_exists` fails on the
   first name.
2. `test_root_claude_md_points_at_the_rules_directory` asserts the root
   `CLAUDE.md` contains the string `.claude/rules/`. It does not: the
   current policy is that `CLAUDE.md` carries the product's value and its
   users only, with every rule living under `.claude/rules/`.
3. `test_root_claude_md_names_every_repository_rule` asserts `CLAUDE.md`
   names each rule file. Same cause — under the current policy `CLAUDE.md`
   enumerates nothing.

Cases 2 and 3 pin a superseded convention: that `CLAUDE.md` acts as an index
of the rules directory.

### The repair

**Names.** `REPO_RULE_FILES` is updated to the rule files actually present
under `.claude/rules/`, using their current names. The tuple is derived from
the directory rather than being re-typed by hand where that keeps the
assertion meaningful — but the existence check must not become vacuous:
whatever form it takes, it fails when the directory is empty or a named rule
disappears.

**Discoverability.** The property cases 2 and 3 were protecting — that a
repository rule is findable and not orphaned — is kept, and re-pointed at
where it now lives. The two `CLAUDE.md` assertions are replaced by
assertions of equal strength against `.claude/rules/`: every rule file
listed exists there, is non-empty, and carries a level-1 heading naming what
it governs. The `core-` prefixed rules are asserted to be present as a named
subset, so losing one of the rules the project depends on fails loudly.

This is a rewrite of two expectations, not a deletion of two guards: the
module keeps the same number of assertions about repository rules, and each
replacement states an outcome that can fail. The reason for the change is
recorded in a comment above the changed class, naming the current policy and
the decision that authorized the rewrite (`ac11-stale-guard`), so a later
reader does not restore the `CLAUDE.md` index expectation by mistake.

**Nothing else moves.** `CLAUDE.md` is not edited — it is outside this
feature's declared change set, and the user's decision is that the test side
is what is stale. The hook guards, the gitleaks cases, the
`MIGRATED_RULE_FILES` citation sweep and the README cases are untouched.

## Test Notes

  re-expressed against `.claude/rules/` at equal strength, report that as a
