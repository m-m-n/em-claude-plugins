# Task Plan: task0003 — SPEC-change transition consistency and the wording-correction route

## Goal

`em-workflow/references/rework-task-synthesis.md` states a SPEC-change
transition that survives create-plan re-entry with merged tasks present, and
defines an independent route for wording-only corrections to create-plan-owned
documents that never re-enters the planner.

## Requirements

FR6, FR15, FR16, NFR1, NFR5, NFR7, NFR8

## Design

### A. SPEC-change transition (FR6)

Section 10's transition list (create-spec → `needs_update`; create-plan /
implement / review → `pending`; `base_commit` preserved; phase-state records
the reason; re-entry at create-spec) stays as the five-step sequence it is.
Two statements change around it:

1. State that create-plan re-entry under this transition is **not** rejected
   when merged tasks exist, referring to the permission conditions in
   `references/workflow-patch.md` by path for the rule itself (C2 — that
   document owns it; this one must not restate the conjunction).
2. Replace the sentence claiming that batch mode falls through to the
   unlisted-gate fallback and aborts. The replacement states that in batch
   the gate goes through the classification gate defined in
   `references/question-resolution.md`, citing it by path without restating
   the verdicts, the asymmetry or the evidence criterion. Interactive is
   unchanged: the user is asked directly (D8).

### B. Wording-correction route (FR15, FR16)

A third branch of route selection, beside "synthesize a rework task" and
"take the SPEC-change transition" (IMPLEMENTATION.md, Shared Components row
5). Define it as:

- **Applies to**: a change confined to the wording of create-plan-owned
  documents — `IMPLEMENTATION.md` and `VERIFICATION.md`.
- **Eligibility (all three, conjunctive)**: (i) no planner re-entry is
  needed; (ii) no plan or task metadata changes — task set, `files`,
  `skills`, `domains`, `complexity`, plan paths; (iii) no requirement
  metadata changes — requirement statements, IDs, `status`, and the
  task/test mapping.
- **Outcome when eligible**: the correction is applied through the existing
  Section 9 document-update channel with no task synthesized, `create-plan`
  is NOT set to `needs_update`, and no workflow patch touching planning is
  produced.
- **Guard (FR16)**: failing any condition makes the route inapplicable, and
  the change goes through the normal rework / SPEC-change route instead.
  State the conditions so that a deviation is detectable — each condition
  names the concrete artefact whose change disqualifies the route, so an
  edit that turned out to touch requirement metadata (EC-8) is recognizable
  after the fact rather than only by intent.
- **Ordering**: route selection checks the wording-correction route first;
  only a change that fails it can reach the SPEC-change transition and thus
  the classification gate.

### C. Structural constraints

- Section numbering and the thirteen-section order are pinned; add content
  inside Sections 9 / 10 (and Section 11's invariant list if the route needs
  one) rather than inserting a new numbered section (C3).
- If an invariant is added, the invariant list's count changes — update the
  pin in the same edit (C5).
- Decide inside this task whether the route needs a field in the
  rework-planner's result shape. If it does, state it in the contract
  document and the worker prompt; if it does not, leave both files untouched
  and record the conclusion in the task's completion report.
