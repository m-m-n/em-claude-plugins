# Task Plan: task0014 — structure-preserving write of the goal block

## Goal

`em-workflow/references/workflow-schema.md` requires the verbatim `goal`
value to be written so that it cannot alter `workflow.yaml`'s structure, and
requires the written file to be re-parsed and checked before the write is
accepted; `em-workflow/references/phases/create-spec-phase.md` carries the
matching write-time procedure by citation, including what happens when the
check fails.

## Design

`workflow.yaml` is a hand-written file produced with the Write tool, and the
`goal` value is attacker-influenceable text carried in verbatim with
normalization explicitly forbidden. Today the only stated constraints are on
the VALUE (no summarizing, normalizing, truncating); nothing constrains the
SERIALIZATION, so a multi-line description whose second line starts at column
0 can close the scalar and introduce sibling keys — reaching, among others,
the repository-controlled `*_command` strings and the review summary block.

1. **Verbatimness constrains the value, not the serialization.** State this
   distinction explicitly, then require the value to be written as an
   indented block scalar in which EVERY line sits inside the block's
   indentation — including blank lines and lines that themselves look like a
   YAML key, a list item, or a document marker. Indentation added by the
   block scalar is not normalization of the value: the parsed-back value is
   still the original text, which is what "verbatim" fixes.

2. **Post-write verification.** After writing `workflow.yaml`, re-parse the
   written file and confirm three things: it parses; `goal` reads back as a
   single scalar equal to the launch-time description; and every other
   top-level key and value matches the content that was intended to be
   written. State the check as a required step of the write, not as advice.

3. **Failure outcome.** A failed verification means the `goal` block is NOT
   written: `workflow.yaml` is constructed without it — the optional-absence
   state the schema already defines and whose gate consequence
   `question-resolution.md` already states — and the failure is reported. A
   partially written or unverified `goal` block is never left behind. This
   keeps the failure inside an already-defined state instead of inventing a
   new one.

4. **Phase-side procedure.** `create-spec-phase.md`'s `goal` bullets state
   that the orchestrator performs the indentation and the re-parse check as
   part of constructing `workflow.yaml`, and what it does on failure, citing
   `workflow-schema.md` for the rule itself. The verbatim, single-writer,
   immutability, optionality and untrusted-read statements keep exactly one
   home each (NFR1, C2) — this task adds no second statement of them, and the
   untrusted framing continues to reach the envelope's Untrusted-Input
   Handling by citation (C7).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1): `workflow-schema.md` distinguishes the value from its
      serialization and requires every line of the goal — blank lines and
      lines shaped like YAML keys, list items or document markers included —
      to be written inside the block scalar's indentation.
- [ ] AC-2 (FR1, FR3): it requires a post-write re-parse confirming that the
      file parses, that `goal` reads back as one scalar equal to the
      launch-time description, and that every other key and value is
      unchanged from the intended content.

      block.

      the failure outcome while citing `workflow-schema.md` for the rule, and
      adds no second statement of the verbatim / immutability / untrusted
      rules.
