## Goal

canonical validator invocation already supplies, its mandatory `preserve` set
is actually enforced, and its task-id allocation rule is mechanically
guaranteed — with the document, the validator and the fixtures changed
together so no half of the contract can disagree with the other.

## Design

### What is wrong today

Three defects share one root cause: the re-planning permission contract was
written as a document rule and enforced (or not) somewhere else.

1. **The re-entry signal never arrives.**
   `workflow_replace_all_spec_change_reentry()` reads the single mapping
   passed as `--phase-state`, but `create-plan-phase.md`'s canonical
   invocation passes `phase-state/create-plan.yaml`. Phase-state is one file
   per phase and `spec_change` is written only into the rework phase's file,
   so under the canonical invocation the helper returns `False`
   structurally, never contingently. The existing fixture passes only
   because the test harness hands it a rework-shaped mapping directly, and
   that mapping carries no `phase` key at all, so nothing in the suite
   notices the mismatch.
2. **The mandatory `preserve` set is documentation only.**
   `REQUIRED_PRESERVE_BY_OPERATION["replace_planning"]` is `set()`, so
   application rule 13 asks for nothing on this operation, and rule 14 only
   checks paths the patch itself volunteered. A re-planning patch that omits
   `workflow.implement.base_commit` passes. The `valid-` fixture added last
   round carries `preserve: []`, so the suite currently pins the
   counter-example of what the document declares mandatory.
3. **The task-id allocation rule has no anchor.** The document requires new
   ids to continue above the highest id the feature ever registered, but
   `replace_all` replaces `tasks` wholesale, so a retired id leaves no trace
   to compare against. Rule 4's check is `append`-only. The `valid-` fixture
   re-issues `task0001` over a workflow that already registered `task0009`.

Also folded in here, because it is the same signal: the re-entry record's
freshness and shape are unchecked. Any non-empty mapping under `spec_change`
grants the permission, the record is never removed (only marked
`consumed: true`), and nothing ties it to this feature or this phase — so one
SPEC change opens the permission permanently.

### The decision: repair the wiring, do not move the transition

Three approaches were available. This task takes the third.

- **Rejected — add a dedicated validator flag** (e.g.
  `--rework-phase-state`) and put it in the canonical invocation. This
  re-creates the exact failure mode the finding describes: a permission that
  holds only when a caller remembers to pass one more flag, with the
  narrowing invisible at the call site. It also requires editing
  `create-plan-phase.md`, which task0020 owns this round.
- **Rejected — set `create-plan` to `needs_update` in the SPEC-change
  transition**, which would delete the second case outright. This is the
  cleanest shape, but SPEC.md's FR6 states the transition as "create-spec →
  `needs_update`; create-plan / implement / review → `pending`". Changing it
  is a specification change, and rework may not make one.
- **Chosen — read the signal from a path the canonical invocation already
  supplies.** `--feature-dir` is already mandatory-in-practice in the
  canonical invocation, and the validator already reads task plans and
  IMPLEMENTATION.md from underneath it. The re-entry signal is read from
  `{feature-dir}/phase-state/rework.yaml`, so the canonical invocation needs
  no change at all and a test can drive that exact documented form. A
  `--phase-state` mapping that identifies itself as the rework phase is
  accepted as an equivalent source, so a caller that already has the file
  open is not forced to re-supply it.

The signal's location and its fail-closed direction are stated once, in
`workflow-patch.md`, beside the permission rule they belong to (NFR1). They
are not restated in `create-plan-phase.md`; that document's existing
statement — that omitting a flag narrows validation and that anything less
than the canonical invocation is a coverage regression — already covers the
consequence, and the file belongs to task0020 this round.

### The re-entry signal, made verifiable

The second case of the Re-planning path is entered only when ALL of the
following hold. Any one of them missing means this is not the second case,
and the initial-planning rule applies (fail-closed: a narrower invocation
never widens what is permitted).

1. A rework-phase state mapping is available — from
   `{feature-dir}/phase-state/rework.yaml`, or from a `--phase-state`
   mapping whose `phase` is `rework`.
2. That mapping's `feature` matches the workflow's `feature`.
3. It carries a `spec_change` record shaped as
   `references/phase-state.md` defines it: `reason`, `finding_stable_id`,
   `recorded_at_commit` present and non-empty, and `consumed` present.
4. `consumed` is `false` — the record has not already grounded a
   create-spec dispatch. A consumed record is spent, not a standing
   permission.
5. `workflow.implement.base_commit` is already set.

`workflow-patch.md`'s wording changes from "a `spec_change` record present
in `phase-state/rework.yaml`" to an **unconsumed** `spec_change` record, and
names the reading position. `references/phase-state.md` already defines every
field used above, so this task adds no field and restates no schema — it
cites (NFR1).

### The mandatory `preserve` set, made path-dependent

`REQUIRED_PRESERVE_BY_OPERATION` becomes a function of the path, not of the
operation alone: on the re-planning path `workflow.implement.base_commit` is
required; on the initial-planning path there is no `implement` base commit
yet and nothing is required. That is exactly what the document's table row
already says; only the enforcement side is missing. The `valid-` fixture
gains the path in its `preserve`, and the missing-path case becomes a new
`invalid-` fixture so the requirement is pinned from both directions.

### Task-id allocation, made mechanical: ids are not retired

The high-water mark has no storage because `replace_all` deletes the
evidence. Rather than inventing a place to keep a number, this task removes
the need for one: **a re-planning `replace_all` may not drop an existing task
entry.** Its `entries` must re-declare every task id already registered in
`workflow.yaml` — a `merged` task keeps its `status`, its `branch` and its
`files` — and any genuinely new task is numbered above the highest id
present. The high-water mark is then always `max(registered ids)`, readable
from the workflow the patch is being applied to, and no id can be re-issued
because none is ever released.

This also matches EC-4 (work already merged into the integration branch is
not discarded) and it is what `preserve`'s recommended
`tasks.<task_id>.status` listing was gesturing at. The initial-planning path
is unaffected: its `tasks` is empty or all-`pending` by its own condition.

The application-rule list gains one rule for this, appended after the
existing sixteen; rules 1-16 keep their numbers and their text (convention
C3 forbids renumbering, not appending). The list's own "All sixteen rules"
sentence is updated in the same edit, and its pin is updated with it.

### Consequences the implementer should expect

- The `valid-replace-all-replanning-merged-tasks` case needs three
  corrections at once: `preserve` gains `workflow.implement.base_commit`,
  `phase-state.json` gains `phase: rework` / `feature` / a complete
  unconsumed `spec_change` record, and its `entries` stop re-issuing ids
  that the accompanying `workflow.json` already registers.
- `em-workflow/references/implement-phase.md` argues about task-id reuse and
  relies on this rule. The rule gets stronger here, not weaker, so that
  argument stays valid. The file belongs to task0020 this round and is not
  edited here.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR6): a `replace_all` re-planning patch is accepted when the
      validator is invoked in exactly the form `create-plan-phase.md`'s
      canonical invocation documents — no flag added to that form — with the
      re-entry signal present only in the feature directory's
      `phase-state/rework.yaml`. A test drives that invocation form

      canonical form does not carry.

      `replace-all-not-permitted` when the rework phase-state is absent,
      when its `phase` is not `rework`, when its `feature` does not match
      the workflow's, when the `spec_change` record is missing a mandatory
      field, or when `consumed` is `true`. Each direction has a case.
- [ ] AC-3 (FR5): a `replace_all` patch on the re-planning path that omits
      `workflow.implement.base_commit` from `preserve` is rejected, driven
      by the new `invalid-…-missing-base-commit-preserve` fixture; the same
      omission on the initial-planning path is still accepted.
- [ ] AC-4 (FR4): the existing `valid-replace-all-replanning-merged-tasks`
      case passes with `workflow.implement.base_commit` in its `preserve`,
      with a rework-shaped `phase-state.json`, and with task ids that do not
      re-issue any id its `workflow.json` already registers.

## Test Notes

- AC-1 is the whole point of the task and needs a test that reproduces the
  documented invocation rather than the harness's convenient shortcut: build
  a temporary feature directory containing `phase-state/rework.yaml`, pass
  `--feature-dir` and `--phase-state {create-plan.yaml}` exactly as the
  canonical form does, and assert acceptance. A test that passes the rework
  file as `--phase-state` proves the old wiring, not the new one — keep such
  a case, but as an additional equivalence case, never as the AC-1 case.
- Every new permitted direction gets a mirrored rejection case; AC-2 and
  AC-5 are the negative proofs for AC-1.
- Assert the pre-existing fixture outcomes by name, not only through the
  aggregate sweep, so a regression names the case that broke.
- Do not assert over `create-plan-phase.md` or `implement-phase.md` from any
  module this task owns: both belong to task0020 this round and their text
  does not exist in this worktree. Document agreement across the two tasks is
  a verify-phase item.
