# Task Plan: task0023 — carried task ids, so a re-planning pass cannot rewrite what is already merged

## Goal

A re-planning `replace_all` keeps every already-registered task entry
byte-for-byte — `status`, `branch`, `files` and the rest — because those
entries are carried over by id rather than re-supplied by the worker, and
the validator, the in-memory apply and the fixtures all enforce that one
form.

## Design

### What is wrong today

`workflow-patch.md` says a re-planning `replace_all` must re-declare every
registered id and that "a `merged` task keeps its `status`, its `branch` and
its `files`". No patch can actually do that:

- application rule 12 forces `initial_status: pending` on every entry, so a
  re-declared `merged` task is declared `pending`;
- a task entry has no place to carry `branch` at all;
- the in-memory apply sets `status` from `initial_status` and defaults
  `branch` to null;
- listing `tasks.<id>.status` in `preserve` does not rescue it — the
  invariance check then compares `merged` before against `pending` after and
  rejects the patch.

So the document's requirement has no satisfying patch, and the fixture that
is supposed to demonstrate it demonstrates the opposite: it re-declares
merged tasks as pending and is pinned as valid.

The enforcement side is equally thin. Rule 17 is implemented as "no
registered id is missing from `entries`" plus a high-water check. Everything
inside a re-declared entry is whatever the worker wrote: `files` can shrink
(dropping a path an implement wake admitted, which is exactly what
`create-plan-phase.md` §12 promises will survive), `domains` and
`complexity` can be rewritten (which selects the review perspectives),
`title` and `plan` can be replaced, and a merged id can be handed a fresh
body and re-dispatched.

### The decision: carry ids over, never re-supply their bodies

Rather than growing the `preserve` vocabulary until every field of a merged
entry is individually protected, remove the worker's ability to state those
fields at all. A re-planning `replace_all` declares two disjoint sets:

- `tasks_patch.carried_task_ids` — every task id already registered in the
  `workflow.yaml` the patch is applied to. Each carried id's record is
  copied from that file **verbatim** (`title`, `plan`, `files`, `skills`,
  `domains`, `complexity`, `requirements`, `status`, `branch`, `notes`). The
  patch supplies no body for a carried id, so there is nothing to disagree
  with.
- `tasks_patch.entries` — only ids not yet registered. Application rule 12
  (`initial_status: pending`) and every per-entry rule apply here, and only
  here.

Consequences that fall out for free:

- a `merged` task is still `merged` after the patch, so `preserve` of
  `tasks.<id>.status` and `tasks.<id>.branch` holds instead of failing;
- `files` survives without entering the `preserve` vocabulary, which is what
  `create-plan-phase.md` §12's Retention bullet needs — its citation is
  re-pointed at this rule;
- the high-water mark is `max(carried_task_ids ∪ entries)`, still readable
  from the workflow the patch is applied to;
- dropping a registered id and re-dispatching a merged id both become
  structurally impossible rather than separately policed.

The names and the split above are fixed in IMPLEMENTATION.md's Shared
Components (Re-planning carry-over declaration). Implement against that row.

### Enforcement

The validator rejects, each with its own error identifier:

- an `entries` key naming an id already registered in `workflow.yaml`;
- a `carried_task_ids` list that omits any registered id, or names an id
  that is not registered;
- a new id in `entries` at or below the high-water mark over
  `carried_task_ids ∪ entries`.

`apply_patch` simulates the same shape — carried records copied from the
current workflow, entries upserted — so the post-application `preserve`
invariance check and the post-application mandatory-field check both operate
on the record the orchestrator will really write.

The Initial-planning path is unaffected: its `tasks` is empty or all
`pending` by its own condition, so `carried_task_ids` is empty there and the
patch is exactly what it is today.

### Consequences the implementer should expect

- `valid-replace-all-replanning-merged-tasks` needs both halves changed at
  once: its `workflow.json`'s merged tasks move into `carried_task_ids` and
  disappear from `entries`, and its `preserve` entries for those ids now
  actually hold.
- Application rule 12's text narrows to `entries`; rule 17's text is restated
  in terms of `carried_task_ids`. Rules keep their numbers — convention C3
  forbids renumbering, not rewording a rule in place.
- `create-plan-phase.md` §12 cites this rule; it must not restate it (NFR1).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR4): `references/workflow-patch.md` defines
      `tasks_patch.carried_task_ids` for a re-planning `replace_all`: it
      lists every id already registered, `entries` may name only ids not yet
      registered, and the two sets are disjoint. Omitting a registered id
      from `carried_task_ids` is stated as rejected.
- [ ] AC-2 (FR5): the same document states that a carried id's record is
      copied from the current `workflow.yaml` verbatim — naming the fields —
      and that the patch supplies no body for a carried id, so a `merged`
      task is still `merged`, on the same `branch`, with the same `files`,
      after the patch. Application rule 12 is stated to apply to `entries`
      only.
- [ ] AC-3 (FR4): the validator rejects, with distinct error identifiers, an
      `entries` key naming a registered id; a `carried_task_ids` list missing
      a registered id or naming an unregistered one; and a new id at or below
      the high-water mark over `carried_task_ids ∪ entries`.
- [ ] AC-4 (FR5): the in-memory apply copies carried records verbatim, so a
      patch that lists `tasks.<id>.status` and `tasks.<id>.branch` in
      `preserve` for a `merged` carried task passes the invariance check, and
      the applied workflow still carries every mandatory task field. A test
      asserts field-by-field equality between the pre- and post-apply record
      of a carried task, including `files`.
- [ ] AC-5 (FR18, FR19): `references/phases/create-plan-phase.md` §12's
      Retention bullet cites the carry-over rule as the mechanism by which a
      path admitted by an implement deviation survives a re-planning pass,
      and states no rule of its own (NFR1).
- [ ] AC-6 (FR4, NFR8): the `replace_planning` fixture group demonstrates the
      rule rather than contradicting it — the positive replanning case
      carries its merged tasks and re-declares none of them, the drop case is
      re-grounded on `carried_task_ids`, and the new
      entry-for-a-registered-id case is rejected. Every other case in the
      group keeps its current outcome; no guard is deleted.
- [ ] AC-7 (NFR5, NFR8): `python3 -m unittest discover -s tests` passes in
      full, and the byte-identity pins in `tests/test_gate_option_vocabulary.py`
      are refreshed to the post-change digests with the reason recorded in
      the comment above them.

## Out of Scope

- What makes a re-planning `replace_all` *permitted* — the re-entry signal
  and its flags are task0022's contract. This task assumes the patch has
  already been recognised as a re-planning one and governs only its content.
- Adding `files` (or any other field) to the `preserve` vocabulary: the
  carry-over form makes that unnecessary, and a second protection mechanism
  for the same fact would violate NFR1.
- `references/implement-phase.md`'s deviation auto-addition rule and its
  audit trail (task0010 / task0020 own it; §12 keeps citing it unchanged).
- `append_rework`'s task entries: `append` already forbids overwriting a
  registered id and is untouched here.
