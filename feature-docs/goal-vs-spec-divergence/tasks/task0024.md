## Design

### Defect 1: the category left the abort list, and nothing else caught it

Before this feature, `category: spec-change` aborted the phase immediately
on the category alone. The revision replaced that with a `gate_id`-keyed
routed arm, and removed the category from the abort list. A question whose
`category` is `spec-change` but whose `gate_id` is anything else now
satisfies none of the guards:

- not an immediate-abort condition (the category is no longer listed);
- not the routed arm (its entry condition is the `gate_id`);
- not the malformed-pairing rule (that too keys on the `gate_id`).

It therefore reaches the policy lookup, finds no entry, falls to the
Unlisted-gate fallback, and — `category: spec-change` requires
`on_unanswered: block` — is auto-answered under the "smallest side effect"
branch. A specification change gets decided by the fallback in an unattended
run. The validator does not intercept it either: its gate registry is built
from `batch-policies.yaml`'s gate ids and from the gate ids contracts
attribute to a worker, and `rework.spec-change` appears in neither, so the
gate_id → category binding never fires for it, and no rule constrains the
opposite direction at all.

The fix keeps the routed arm but restores the category as a guard:

- `category: spec-change` returns to the immediate-abort list;
- the routed arm is written as the single exception to that abort, admitted
  only when the `gate_id` is exactly `rework.spec-change` (the routed arm's
  entry condition is still the gate id, never the worker-set category — a
  worker-set category still selects no route on its own; it now only
  *fails* closed);
- the malformed-pairing rule becomes bidirectional, so each of the two
  mismatched pairings aborts and records its reason;
- `rework.spec-change` is registered in the gate registry via the
  rework-planner contract's own "## Gate identifiers" section, and the
  validator gains the missing direction: a question declaring
  `category: spec-change` with any other `gate_id` is rejected.

The precedence reservation (security / license / `reversible: false` are
evaluated first and their abort is final) is unchanged and must survive the
edit verbatim in force.

### Defect 2: a declared defence with no definition

The same section asserts that irreversibility "is decided from
orchestrator-held metadata, never from the packet alone", and that the
orchestrator aborts whenever the operation a gate stands in front of is on
"its own irreversible-operations list". No such list, and no such metadata,
is defined anywhere in this repository; the only thing that matches the
string is that sentence and a test asserting the sentence exists. The single
trigger that can actually fire is the packet's own
`assumptions[].reversible: false` — a predicate the worker writes. A reader
of the current text concludes a second, worker-independent defence is
already in place.

Two repairs were available: build the registry, or withdraw the claim. This
task withdraws it, and the choice is settled by the requirements rather than
by preference: SPEC.md FR11 places the `reversible: false` abort **outside
this revision's scope** and requires only that it not be weakened. Adding a
new orchestrator-side irreversible-operations registry would be a new
mechanism no requirement asks for, spanning every gate in the plugin;
withdrawing the claim restores the documented state to exactly the
unchanged, not-weakened strength FR11 requires. NFR2 is satisfied either
way, because the abort that actually fires is untouched.

So the paragraph is replaced by an accurate one: the irreversibility abort
fires on an `assumptions[]` entry naming the question with
`reversible: false`; that basis is worker-declared, which is a stated
limitation of the current design, not a second defence; and the abort
records its reason exactly as every abort in the section does. Nothing in
the replacement may read as though a non-packet source exists today.
