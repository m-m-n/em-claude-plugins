# Task Plan: task0001 — Define the `assumptions[].reversible` criterion at its SSOT and bind it in the six packet-capable worker documents

## Goal

The judgement criterion for `assumptions[].reversible` exists once in the
schema document that owns the field, is carried as a binding rule by the three
packet-capable agent prompts and their three worker contracts, and is pinned per
file by a new recurrence-detecting test module — while the fail-closed
classification stays byte-for-byte unchanged.

## Design

### Definition site

The `assumptions[].reversible` row of the question-packet schema is today a bare
type word. It becomes the type statement followed by the criterion's two halves:
`false` is attached only to an assumption about an operation that cannot be
undone once applied; a preserved constraint, an invariant, or a fact pinned by
an existing test is `true`. This is the only place the criterion's full wording
exists — see IMPLEMENTATION.md C1 (token set) and C2 (site role split).

### Citing sites

Each of the six worker-facing documents gains one binding sentence, placed where
that document already speaks about the question packet / assumptions it emits,
so the rule is reachable by a worker reading only that document. The sentence
carries both halves in condensed form and names
`references/question-packet-schema.md` as the owner. It restates none of the
schema row's surrounding text, adds no rationale, and cites no originating
incident.

The three prompts are `requirements-analyst`, `implementation-planner` and
`rework-planner`; the three contracts are their counterparts. These are exactly
the workers whose capability entry permits `status: needs_user_input` — no other
worker document is touched.

### Consumption site

`em-workflow/references/question-resolution.md` is NOT edited (IMPLEMENTATION.md
D1). The task's obligation toward it is to pin its current wording so a later
change is caught.

### Test module responsibilities

1. Per-file criterion assertions — one assertion per document, seven in total,
   so a single omission fails alone and names the file that lost the criterion.
   The matcher is C1's token set; the six citing sites additionally require the
   pointer token.
2. Fail-closed retention assertions — the four abort arms (security, license,
   spec-change with its single routed exception, irreversibility), the
   Precedence reservation, the surviving-abort enumeration, the batch
   relaxation, the Classification gate's direction-2 irreversibility check, and
   the worker-declared-basis paragraph are all still present in the consumption
   document.
3. Non-vacuity proofs — each matcher is applied to forged in-memory text with
   the criterion removed (must reject) and to forged text containing it (must
   accept). Forged text is constructed inside the test; no file is written.
4. Absence assertions for NFR2/NFR3 — no `gate_id` identifier that is new to
   this feature appears in any of the seven documents, and no `task00NN`
   identifier or `feature-docs/` path appears in them as attribution. These are
   absence assertions, so they also hold in a worktree where a sibling task's
   edits are not present (IMPLEMENTATION.md C4).
5. Standard-library-only assertion — every module present under `tests/` imports
   only standard-library names. If a pre-existing module is found to import a
   non-standard-library name, narrow the assertion to the modules this feature
   introduces rather than weakening or deleting the pre-existing module, and
   report the narrowing as a finding.

All assertions read files relative to the repository root and depend on no file
that another task creates or edits.

## Test Notes

- All seven per-file criterion checks and the fail-closed retention checks are
  unit tests over document text; no subprocess is needed.
- The non-vacuity proofs are the TDD entry point: write the matcher and its
  forged-text pair first, watch the real-tree assertions fail, then edit the
  seven documents until they pass.
- Edge case worth covering: a document that contains the pointer but has lost
  one half of the criterion must fail — a pointer alone is not "carrying the
  criterion".
- Edge case worth covering: the definition site must not be accepted merely
  because it contains the field name; both halves are required on the row.
- TDD-awkward: "no new `gate_id`" is an absence property. Handle it by
  enumerating the gate identifiers currently present in the seven documents and
  asserting the set does not grow, rather than by pattern-matching prose.
- Run the whole suite (`python3 -m unittest discover -s tests`) from the
  repository root before declaring done; the pre-existing arm tests must pass
  unmodified.
