# Task Plan: task0002 — Add the `reversible: true` counter-example question-packet fixture

## Goal

A question-packet fixture carries an assumption of the reported shape — a
constraint that survives because an existing test pins it — declared
`reversible: true`, and is accepted by the worker-output validator both directly
and under the full fixture sweep, standing as the positive companion to the
existing irreversible fixture.

## Requirements

FR6, NFR3, NFR4, NFR5

## Scope

### Files to Create
- `em-workflow/references/fixtures/question-packet/category-fail-closed/valid-test-pinned-constraint-assumption/input.json`
  — the new fixture case's single member file, matching the one-member layout
  every existing sibling case under the question-packet fixture tree uses.
- `tests/test_question_packet_reversible_fixture.py` — validates the new fixture
  directly and under the sweep, and pins the existing irreversible fixture's
  declaration.

### Files to Modify

None.

The existing valid-irreversible-assumption-blocking fixture is read as the shape
reference and must stay byte-for-byte unchanged.

## Design

### Fixture case

The new case sits under the same category directory as the existing
irreversible case, so the two read as a matched pair: one assumption that
legitimately declares an irreversible operation, one that legitimately declares
a preserved constraint. The case is a single input document, following the
layout the existing sibling cases already establish; its internal shape — the
envelope fields, the packet fields and their ordering conventions — is taken
from the existing sibling rather than invented here.

The packet's assumption carries:

- a `statement` of the reported shape — a constraint that survives whichever
  option is chosen, because an existing test pins it;
- `reversible` set to `true`, which is what the criterion
  (IMPLEMENTATION.md C1) yields for a test-pinned preserved constraint;
- `related_question_ids` naming a blocking question in the same packet, so the
  case exercises exactly the input shape that previously reached the
  irreversibility arm and shows it no longer names a question into that arm;
- everything else the envelope and packet schema require of a valid instance of
  the worker that owns the fixture's category.

The fixture's data contains no `task00NN` identifier and no `feature-docs/`
path introduced as attribution (IMPLEMENTATION.md conventions, NFR3); any path
values it needs follow the sibling case's own usage.

### Test module responsibilities

1. The new fixture parses, and its assumption declares `reversible` true on a
   statement describing a test-pinned preserved constraint whose
   `related_question_ids` names a question present in the same packet.
2. The worker-output validator accepts the new fixture when pointed at it
   directly, and the full fixture sweep still exits successfully with the new
   case present. The validator is invoked as an external process using standard
   library facilities only.
3. The pre-existing `valid-irreversible-assumption-blocking` fixture still
   declares `reversible` false and is still accepted — the feature removes no
   ability to declare a genuinely irreversible operation (NFR5).

Every assertion here reads only files this task creates plus files that already
exist on the base branch, so the module is green in a worktree holding only this
task's change (IMPLEMENTATION.md C4).

## Test Notes

- AC-3 / AC-4 are integration checks: they run the validator as a subprocess and
  assert on its exit status, surfacing its output on failure so a rejection is
  diagnosable.
- AC-2 is a unit check over the parsed fixture data.
- Edge case worth covering: the assertion must fail if `reversible` were flipped
  to `false` on this fixture — verify by mutating the parsed structure in memory
  and checking the assertion helper rejects it, not by editing the file.
- TDD order: read the sibling case's input document first to fix the envelope and
  packet shape, write the tests against the new path, watch them fail, then
  create the fixture. Needing any file outside this plan's two declared paths is
  a reportable plan deviation, not a licence to expand.
- Run `python3 -m unittest discover -s tests` from the repository root before
  declaring done.
