# Task Plan: task0001 — Skip quoted-scalar and flow-collection bodies in the Stop hook's task-block scan

## Goal

The line-based reading of workflow.yaml in the Stop hook ignores every body
line of a multi-line double-quoted scalar, single-quoted scalar, flow
sequence or flow mapping, so text inside such values (notably
`tasks.{T}.notes`) can neither forge nor hide a task boundary, task id,
status or route-back record. Regression tests pin the behavior.

## Requirements

- `tests/test_queue_stop_guard_routeback_record.py` — add fixture builders for single-quoted and flow-form multi-line notes, and the regression tests of FR7

## Design

### Multi-line value body tracking (new, module-private, in the hook module)

Responsibility: given the physical lines of workflow.yaml in file order,
decide for each line whether it is a **body line** — a line after the
opening line of a multi-line quoted scalar or flow collection, up to and
including the line on which that value closes.

Contract:
- Precondition: the lines exactly as the existing readers already obtain
  them (text decoded with replacement of undecodable bytes). Any content is
  admissible.
- Postcondition: one body / non-body decision per line. The opening line
  itself is non-body and keeps today's handling. A value that has not closed
  by end of file makes every remaining line a body line (NFR2). It never
  raises.
- State is carried from the first line of the file, not from the `tasks:`
  line (FR1), so a value opened anywhere earlier is honoured.

Opening (FR4). A double quote, single quote, `[` or `{` opens only when it is
the first character of a value at a value-start position:
1. the value of a mapping key on the same line (a task's direct key, a
   nested key or a top-level key);
2. the value of a key whose own line carries nothing after the colon but
   whitespace or a comment — the value then starts on the next non-blank,
   non-comment line;
3. the content of a sequence item after its item indicator, including the
   value of a key that follows the item indicator.

Never an opening:
- any line of a block scalar body (`|` / `>` with any chomping or
  indentation indicator; the body is the blank lines and the lines indented
  deeper than the header line that follow it);
- a comment line;
- a quote or bracket in the middle of a plain scalar or on a plain-scalar
  continuation line (for example an apostrophe inside a word);
- a value prefixed by an anchor or a tag, or a value after a quoted key
  (SPEC A6).

Closing (FR3):
- Double-quoted: an unescaped double quote closes. A backslash-escaped
  double quote does not. A double quote after an escaped backslash (two
  backslashes) closes. A line ending in a backslash continues the body.
- Single-quoted: a single quote closes unless doubled (two single quotes).
- Flow: count the nesting depth of `[` / `{` against `]` / `}`; the value
  closes when the depth returns to zero. Brackets inside inner quoted
  strings and inside comments are not counted. Inside a flow collection a
  quote opens an inner quoted string only at the start of a flow entry or a
  flow mapping value; a quote inside a plain flow scalar does not.
- After a close on the same line, trailing whitespace and a comment are
  allowed; any quote or bracket in them never opens (for example a comment
  holding a lone double quote after a closed title value).
- A value that closes on its opening line produces no body line (FR5).

### Consumers

| Reader | Behavior after this task |
|--------|--------------------------|
| task_ids_from_workflow | Consults the tracking before any existing check. A body line is treated as if it did not exist: it never starts the `tasks:` section, never ends it (even at column 0), never matches a task key (FR1). |
| iter_task_block_lines | Same as above, and additionally a body line never ends the current task block (even when indented at or above the task key) and is never yielded (FR1). |
| task_statuses_from_workflow | Unchanged logic; reads only the task-block scan's output (FR2). |
| task_routeback_records_from_workflow | Unchanged logic (direct-key indentation, first occurrence wins, canonical value); reads only the task-block scan's output (FR2, FR5). |
| implement_in_progress | Unchanged (SPEC A5). |

Constraints:
- The tracking lives only in the hook module itself; no new import beyond
  the standard library, no YAML library (NFR1). No identifier is shared with
  or moved into queue_launch_guard.py, queue_failure_net.py or
  queue_taskstop_net.py (NFR4).
- Hook exit codes, stderr formats, the direct-key indentation rule, the
  first-occurrence rule, the canonical-value rule and the block-range rule
  stay as they are (FR5).
- When closure cannot be determined, later lines are treated as body (not
  read), which falls to "no record, no block" (NFR2).

### Docstrings and comments (FR6)

The module docstring, the docstrings of iter_task_block_lines,
task_ids_from_workflow and task_routeback_records_from_workflow, and the
comment block directly above the ROUTEBACK_RECORD_KEY assignment each state
that body lines of quoted-scalar and flow-collection values are not read as
a task boundary, task id, status or record.

- Keep every wording pinned by TestModuleDocstring ('only when all three
  hold', '`routeback_failed_journal_line` record', 'Any other task whose
  last event is `failed` is failed', "the task's own id, returned from
  `failed` to `pending` by route-back") and by TestDirectKeyWording ('direct
  keys', 'block scalar bodies', 'nested').
- Do not introduce 'a recycled task id left behind by a route-back
  re-plan'.
- The ROUTEBACK_RECORD_KEY comment stays a contiguous block of comment
  lines immediately above the assignment (the existing test reads it that
  way).

### Test fixture builders (FR7)

- Add a builder for multi-line single-quoted notes and builders for
  multi-line flow-sequence and flow-mapping notes, each with a
  continuation-indent parameter like that of notes_double_quoted.
- notes_double_quoted keeps its signature and default; existing calls stay
  unchanged. New tests pass a continuation indent of 4, 2 or 0.
- Fixtures whose forged lines need different indents per line (for example
  a 2-space task key followed by a 4-space record) may use continuation
  indent 0 with explicit leading spaces in each part, or literal line lists.
