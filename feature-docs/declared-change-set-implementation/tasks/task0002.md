# Task Plan: task0002 — Bump the plugin version in both manifests

## Goal

The plugin's version declaration reflects that plugin-owned content changed in
this feature, with both manifests carrying one identical new value so an
installed copy of the plugin refreshes its cache.

## Requirements

FR4, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — the plugin's own version
  declaration.
- `.claude-plugin/marketplace.json` — the version declared on the marketplace
  entry whose source points at this plugin.

## Design

### What changes

Exactly one value in each of the two manifests: the version each declares. Both
end up with the same string, one patch increment above the value they currently
share (IMPLEMENTATION.md Shared Components, "Plugin version value"; decision
D4).

### Reading the current value

The current value is read from the manifests at implementation time; it is
deliberately not restated in the planning documents, so those documents cannot
go stale against the manifests. Read both, confirm they agree, and increment
from that shared value. If they do **not** currently agree, that is a
pre-existing defect outside this feature's scope: report it as a plan deviation
rather than silently reconciling it.

### Which marketplace entry

The marketplace manifest lists several plugins. The entry to touch is the one
whose source points at this plugin's directory — identified by that source, not
by list position.

### What must not change

Every other field of both manifests: names, descriptions, author blocks,
category, source, schema reference, and the relative order of all keys.
Indentation and the trailing-newline convention of each file are preserved, so
the diff is one changed line per file.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR4): the plugin manifest declares a version one patch increment
      above the value it declared before this task, with the major and minor
      components unchanged.
- [ ] AC-2 (FR4): the marketplace entry for this plugin declares a version
      string byte-identical to the one the plugin manifest now declares.
- [ ] AC-3 (NFR4): both files still parse as valid JSON, and the only difference
      from their previous content is the version value — every other key, value,
      key order, and indentation is unchanged, so each file's diff is a single
      changed line.
- [ ] AC-4 (NFR4): exactly the two files listed under Scope are modified; no
      file is created, renamed or deleted.
- [ ] AC-5: `python3 -m unittest discover -s tests` run from the repository root
      reports no failures and no errors, confirming the manifest edit causes no
      regression.

## Test Notes

- **No automated assertion exists for AC-1 through AC-4.** The project has no
  test that reads either manifest, and adding one would require a new test
  module, which NFR4 places outside this feature's change scope. These criteria
  are verified by inspection of the diff, which is the form VERIFICATION.md
  records for them.
- **AC-5** is the regression guard only: the suite does not read the manifests,
  so a green run proves the edit broke nothing, not that the edit is correct.
- **Edge case — the two manifests already disagree**: do not reconcile them as
  part of this task; report the disagreement as a plan deviation. Reconciling
  would change a value this feature did not intend to change.
- **Edge case — a JSON formatter reflowing the whole file**: an editor or tool
  that rewrites the entire manifest violates AC-3 even if the resulting JSON is
  semantically identical. Edit the value in place.

## Out of Scope

- The two document templates and the two test modules (task0001 owns them).
- Generating or updating any `LICENSE` file; the project declares no license and
  license generation is a separate command's job.
- Updating either manifest's description text to mention this change.
- Bumping any other plugin's version in the marketplace manifest.
