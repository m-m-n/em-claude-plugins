## Design

### What is being added

One member name, in one spelling, in four places. The spelling, the position and
the per-destination notation are pinned by IMPLEMENTATION.md's Shared Components
entry "Feature-docs member literal" and by decisions D2 (position) and the
"Notation follows the destination" convention. Do not re-derive them here.

### The four destinations and their existing shape

| Destination | Where in the file | Existing notation of its members |
|---|---|---|
| SPEC template | the paragraph inside `## Declared Change Set` that states what the `feature-docs` root entry covers | English prose sentence; each member is inline-code and the members are comma-separated, the last one joined by "and" before a trailing prose phrase naming the design artifacts |
| REQUIREMENTS template | the sentence inside `### 9.4 宣言された変更集合` that states what the `feature-docs` root entry contains | Japanese prose sentence; each member is inline-code, separated by the ideographic comma, ending with a prose phrase naming the design artifacts |
| SPEC test module | the module-level literal set named `FEATURE_DOCS_MEMBERS` | one entry per member, plain string, one per line, in the same order as the template sentence |
| REQUIREMENTS test module | the module-level literal set named `FEATURE_DOCS_MEMBERS` | same shape as above |

### How the two test modules consume the literal set

Both modules use their `FEATURE_DOCS_MEMBERS` set twice, and both uses are
affected by adding an entry:

1. A **positive** test iterates the set and asserts each entry appears in the
   whitespace-normalized slice of its template's section. The SPEC module
   asserts the entry wrapped in inline-code delimiters; the REQUIREMENTS module
   asserts the bare entry. This is the assertion that turns red until the
   corresponding template is edited.
2. A **negative-proof** test iterates the same set and asserts each entry is
   absent from that module's captured pre-change sample. The pre-change samples
   contain no occurrence of the member being added, so this assertion continues
   to hold with no edit to the sample — and it must be confirmed, not assumed.

Because the SPEC module's positive assertion wraps each entry in inline-code
delimiters, the SPEC template's added member must carry those delimiters like
its neighbours do; a bare occurrence would fail.

### Section slicing constraints the edit must not break

Both modules locate their section by slicing between two heading anchors and
then normalizing whitespace. Two consequences:

- The added member must land **inside** the sliced section — in the same
  paragraph as the other members, not in a neighbouring section.
- Re-wrapping the surrounding English paragraph to accommodate the longer
  sentence is safe, because the content assertions read a whitespace-normalized
  copy. Both templates' heading anchors, their uniqueness, their relative order,
  and the outer fenced body that encloses them must remain exactly as they are —
  position, uniqueness and fence-boundary assertions read raw, un-normalized
  offsets.

### Ordering of the edits

Follow IMPLEMENTATION.md D3: the two test literal sets change first and the
suite is observed failing on the two positive assertions, then the two templates
change and the suite is observed passing. A run that was never red proves
nothing here, because the tests being changed are the tests that verify the
change.

## Test Notes

- **Test-first cycle**: add the entry to the two literal sets, run the suite,
  and record the observed failures (one positive assertion per module) as the
  red state for AC-1 and AC-2. Then edit the two templates and re-run to green.
  The red observation is the evidence that the template edits were necessary.
- **AC-3 / AC-6 mapping**: these are structural properties of the test modules
  themselves and are verified by inspection of the diff, not by a new test.
  Adding a test that asserts them would require a new test module, which NFR4
  places outside this feature's change scope.
- **AC-4 mapping**: half of it is covered by the existing negative-proof tests
  (they iterate the enlarged literal set, so the new member is automatically
  proven absent from the samples); the other half — the samples themselves being
  untouched — is verified by inspection of the diff.
- **AC-7 mapping**: verified by inspection of the diff against the Scope list.
- **Edge case — heading uniqueness**: both modules assert that their anchor
  headings occur exactly once. Adding a member never introduces a heading, but
  if the edit is applied to the wrong paragraph the slice moves and unrelated
  assertions fail; a failure in a position or fence-boundary test means the edit
  landed outside the intended section.
- **Edge case — the ideographic comma**: the Japanese sentence separates members
  with the ideographic comma, not the ASCII comma. Using the wrong separator
  still passes the substring assertion but violates NFR1; this is an inspection
  item.
- **No coverage tooling** exists in this project; coverage is not measured.
