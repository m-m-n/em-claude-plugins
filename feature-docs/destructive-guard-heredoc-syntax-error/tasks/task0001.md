# Task Plan: task0001 — Do not register heredoc operators written directly in array compound assignments

## Goal

destructive-guard classifies the lines bash executes after discarding a
line that holds a `<<` written directly inside an array compound assignment
as ordinary commands, so destructive commands on those lines get deny.
Real heredocs inside substitutions, after closed arrays, and on lines after
the discarded line keep their current allow.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/hooks/destructive-guard.py` — lex_shell() and _lex_pass(): array compound-assignment context, non-registration of heredoc operators written directly in it, the discarded-line rule, and the line-end reset
- `em-workflow/hooks/tests/destructive-guard-cases.json` — append the deny and allow cases listed in the Acceptance Criteria; pre-existing entries stay untouched

## Design

The conventions in IMPLEMENTATION.md (case-table format, verdict
direction, test commands) apply to this task. In the command examples
below, `\n` stands for a newline.

### Terms

- **Array context**: the lexer state that starts at the opening
  parenthesis of an array compound assignment and ends at its matching
  closing parenthesis, or at the reset described below. The opening
  parenthesis is one of:
  - `NAME=(` or `NAME+=(` read as an assignment word (command position, or
    after other assignment words);
  - the same shape read as an argument word of a declaration builtin.
    SPEC.md names `declare -a x=(`; the other declaration builtins bash
    parses the same way (typeset, local, export, readonly) follow the same
    rule — Bash 5.3.9 discards the line and runs the next one for each of
    them. Only a `NAME=(` / `NAME+=(` read as an argument of one of these
    builtins qualifies; the same text as an argument of any other command,
    or inside quotes, does not.

  A parenthesis that is none of these (subshell, command or process
  substitution, arithmetic, function definition, case pattern) never
  starts an array context.
- **Direct position**: a `<<` or `<<-` is at direct position when the
  innermost open lexical context at that point is an array context — no
  command substitution (`$(` or backquote), process substitution, quoting,
  or other nested context the lexer already tracks (such as arithmetic
  expansion) lies between the operator and the array. An array among the
  ancestors alone is not enough (FR4).
- **Discarded line**: the line on which a direct-position `<<` / `<<-` is
  read. It ends at the first physical newline after that operator. A quote,
  command or process substitution, comment, or backslash-newline
  continuation that appears after the operator on that line does not extend
  it: bash's error recovery drops the rest of the physical line and reads
  the next line as a fresh command line (Bash 5.3.9, measured with
  `bash -c`, a script on stdin and an interactive-less shell on stdin:
  `x=( <<A "` + newline + `echo RAN2` + newline + `"` runs `echo RAN2`;
  the same holds for `$(` and for `\` at the end of the discarded line).

### Behavior

1. **Non-registration (FR1)**: a direct-position `<<` / `<<-` is not
   registered as a heredoc operator, and the word after it is not a
   delimiter. Here-strings and other redirections keep their existing
   treatment.
2. **The discarded line takes no bodies (FR2, SPEC A3)**: no heredoc
   operator registered on the discarded line takes a body — neither one
   registered before the direct-position operator (e.g.
   `cat <<'A'; x=( <<B`) nor one registered after it on the same line,
   including after the array has been closed on that line. FR4's "closed
   array" means an array closed on a line that is not a discarded line.
3. **Reset (FR3)**: at the physical newline that ends the discarded line,
   every open lexical context — the array context, any context enclosing
   it, and any quote, substitution or continuation opened after the
   operator on that line — is cleared, and the next line is read at
   top-level command position.
   Heredoc operators on later lines are registered and take bodies as
   before.
4. **Unchanged elsewhere (FR4)**: a `<<` / `<<-` not at direct position —
   inside a substitution or a quote within an array, or after an array
   closed on a line that is not discarded — keeps its existing treatment
   (registered when it is an unquoted operator outside the array context,
   never an operator inside quotes).
5. **Map and consumers (NFR1)**: the outcome of 1–3 is expressed only in the
   map lex_shell() produces — no operator or body entries for the
   discarded line, so the lines after it are ordinary command lines.
   strip_heredocs(), scan_structure(), _TrackingLexer and tokens() keep
   reading that map and gain no array-context logic of their own. The map
   must also keep the consumers from re-reading a quote, substitution or
   continuation left open on the discarded line (for example, a `"` that
   `_MarkedText` leaves in place and `_TrackingLexer` would otherwise
   re-lex as an opening quote) — the lines after it are read as commands
   by every consumer, not only by lex_shell().
6. **Work bound (NFR2)**: array-context tracking and the discarded-line rule
   stay inside the existing single left-to-right pass. Cancelling pending
   operators removes them from the lexer's existing pending-operator record
   without re-reading earlier input, so each operator is handled a bounded
   number of times. The work bound (LEX_WORK_FACTOR × length + floor) and
   the scan-budget ask on overrun are kept.
7. **Ambiguous forms**: when a form not covered above admits two readings,
   take the one that classifies more lines as commands (NFR3 direction),
   provided no allow case in the Acceptance Criteria or in the pre-existing
   table changes its verdict.

## Acceptance Criteria (MANDATORY)

Each criterion is met when the listed entries exist in the case table with
the stated expected verdict and the runner passes them. `\n` stands for a
newline.

- [ ] AC-1 (FR1, FR5, TM-1): the deny cases `x=( <<EOF\ngit reset --hard HEAD\nEOF` and `x=( <<EOF\nrm -rf /home/sakura/valuable\nEOF` exist, and the hook returns deny for both.
- [ ] AC-2 (FR1, FR5, TM-1): deny cases for `x+=( <<EOF`, `x=(a b <<EOF`, `declare -a x=( <<EOF`, `typeset -a x=( <<EOF`, `export x=( <<EOF`, `readonly x=( <<EOF`, `f() {\nlocal x=( <<EOF` and the two-line `x=(\na <<EOF`, each followed by a `git reset --hard HEAD` line and an `EOF` line, exist, and the hook returns deny for all eight.
- [ ] AC-2b (FR1, FR3, FR5, TM-1): deny cases where something opened after the direct-position operator would span the line end — `x=( <<A "\ngit reset --hard HEAD\n"`, `x=( <<A $(\ngit reset --hard HEAD\n)`, `x=( <<A # "\ngit reset --hard HEAD` and `x=( <<A \\\ngit reset --hard HEAD` — exist, and the hook returns deny for all four.
- [ ] AC-3 (FR2, FR5, TM-2): the deny case `cat <<'A'; x=( <<B\ngit reset --hard HEAD\nA\nB` exists, and the hook returns deny.
- [ ] AC-4 (FR3, FR5, TM-4): the allow case `x=( <<A\ncat <<'EOF'\ngit reset --hard HEAD\nEOF` exists, and the hook returns allow.
- [ ] AC-5 (FR4, FR5, TM-4): the allow cases `x=( $(cat <<'EOF'\ngit reset --hard HEAD\nEOF\n) )`, `x=( "$(cat <<'EOF'\ngit reset --hard HEAD\nEOF\n)" )`, `x=( <(cat <<'EOF'\ngit reset --hard HEAD\nEOF\n) )` and `x=(a b); cat <<'EOF'\ngit reset --hard HEAD\nEOF`, and the deny case `x=( '<<EOF' )\nrm -rf /home/sakura/valuable\nEOF`, exist, and the hook returns the stated verdict for each.
- [ ] AC-6 (FR6, NFR3, NFR4, TM-3): compared with the integration base, the case table only gains entries — no pre-existing entry is removed or rewritten and the number of deny plus ask entries does not decrease — and, in the same change, `python3 em-workflow/hooks/tests/run-destructive-guard.py` and `python3 -m unittest discover -s tests` both pass every case and test.
- [ ] AC-7 (NFR1, NFR2, TM-5): the heredoc-operator decision for every form above is made only in lex_shell() / _lex_pass() (strip_heredocs(), scan_structure(), _TrackingLexer and tokens() gain no array-context classification); the unittest suite's lexer consistency check passes; every case finishes within the runner's 10-second per-case limit; and an input exceeding the work bound still returns the scan-budget ask.

## Test Notes

- The case table is the TDD vehicle for this hook. Add the AC-1 to AC-5
  entries first and confirm the deny entries of AC-1, AC-2 and AC-3 fail
  (allow) before the change; then implement until the whole table passes.
  The allow entries of AC-4 and AC-5 may already pass; they pin FR4 and FR3
  against over-suppression.
- Deny-side follow-up lines use only commands that are deny on their own
  (`git reset --hard HEAD`, `rm -rf /home/sakura/valuable`; SPEC.md A6), so
  a deny shows the line was read as a command.
- Edge cases worth adding to the same table (beyond the AC set):
  - an array closed on the discarded line followed by a later heredoc on
    the same line, e.g. `x=( <<A ); cat <<'B'\ngit reset --hard HEAD\nB` →
    deny (Behavior 2);
  - a `declare` word that is not a declaration builtin, e.g.
    `echo declare x=( <<EOF` — out of scope here; record whatever verdict
    the hook yields and do not tune for it.
- NFR2: a stress entry with many pending heredoc operators on a line
  followed by a direct-position operator, repeated over many lines, shows
  the cancellation does not re-scan. It must finish within the per-case
  limit; record whichever verdict the bounded lexer yields (deny, or the
  scan-budget ask if the bound is reached). If no pre-existing case already
  exercises the scan-budget ask, add one.
- AC-6's count check compares the deny plus ask entries against the
  integration base's table; it is a count and diff check, not a new test
  file.
- AC-7's "no array-context classification in consumers" is checked on the
  diff: only lex_shell() / _lex_pass() and helpers they own change.

## Out of Scope

- Syntax-error lines other than array compound assignments — an unmatched
  closing parenthesis, misplaced reserved words (SPEC.md A2). Their
  verdicts stay as they are.
- A `NAME=(` word appearing as an ordinary argument of a command that is
  not a declaration builtin, and here-strings inside arrays.
- Changes to the verdict logic, to the map consumers, to other hooks, or to
  documentation.
- Editing or removing any pre-existing case.
