# Task Plan: task0002 — Complete array-context recognition and keep valid array contents from discarding the line

## Goal

destructive-guard recognizes every compound array assignment bash parses —
including those after `eval` / `let` / `alias` and those whose name carries a
subscript — so the lines bash runs after discarding such a line are judged as
commands. A `<<` inside an array subscript and an extended-glob parenthesis
inside an array no longer make the hook discard a line bash keeps, so the
destructive commands bash runs on later lines are deny again. The forms the
round-1 auto-fix loop changed are pinned in the case table.

## Design

The conventions in IMPLEMENTATION.md (case-table format, verdict direction,
test commands) and the terms of the feature's first task — array context,
direct position, discarded line, reset — apply unchanged. In the command
examples below, `\n` stands for a newline.

### Terms

- **Assignment position**: a word position where bash reads `NAME=` /
  `NAME[...]=` as an assignment word: command position, after other
  assignment words or redirections, and an argument of a builtin bash parses
  assignment arguments for. That builtin set is the existing declaration
  builtins (declare, typeset, local, export, readonly) plus `eval`, `let` and
  `alias`. A word in any other argument position, or inside quotes, is not at
  assignment position.
- **Subscript**: the bracketed part of a word bash reads with its matched-pair
  rule for `[` … `]`, in two places:
  - a word at assignment position that starts with `NAME[`;
  - a word inside an array context that starts with `[` (an element
    subscript such as `[1<<2]=foo`).

  Inside a subscript, quotes, `$(` / `${` / `$((`, backquotes and nested
  brackets are matched the way bash matches them, and blanks, `<<` and other
  operator characters are part of the subscript. A `<<` inside a subscript is
  never a heredoc operator and never makes the line a discarded line.
- **Extended-glob parenthesis**: a `(` directly preceded, inside the same
  word, by one of `?`, `*`, `+`, `@`, `!`, at direct position in an array
  context.

### Behavior

1. **Array context after eval / let / alias (fd4b0e41e037d221)**: a
   `NAME=(` / `NAME+=(` word that is an argument of `eval`, `let` or `alias`
   opens an array context exactly as one after a declaration builtin does.
   An argument that is quoted, or that is not shaped `NAME=(` / `NAME+=(` /
   `NAME[...]=(` / `NAME[...]+=(`, opens none.
2. **Subscripted array names (c630bfb6a19f88a2)**: at assignment position, a
   word `NAME[` has its subscript read to the matching `]`; when that `]` is
   immediately followed by `=(` or `+=(`, the `(` opens an array context.
   The subscript's content (quoted, expanded, or containing blanks) does not
   change this.
3. **Unmatched subscript**: when the matching `]` of a subscript is not found
   before the end of the input, the hook returns ask. bash keeps reading for
   the `]` and the hook cannot place the line boundaries it would use.
4. **Element subscripts (4b5de463a6e5e162)**: inside an array context, a word
   starting with `[` has its subscript read to the matching `]` (rule above).
   A `<<` inside it is an arithmetic shift, so the line is not discarded and
   heredoc operators registered on that line after the array keep their
   bodies. A direct-position `<<` after the subscript's `]` is still
   non-registered and still makes the line a discarded line.
5. **Extended-glob parentheses (c231452e02deec9b)**: whether bash accepts an
   extended-glob parenthesis depends on the `extglob` option at parse time,
   which the hook cannot know. With it on, the line is valid; with it off,
   the `(` is a syntax error and the line is discarded. The verdict for such
   a command must be at least as strict as the verdict under each of the two
   readings: every line bash would run as a command under either reading is
   judged as a command. A bare `(` (no extended-glob prefix) directly inside
   an array keeps discarding the line, as now. This applies the first
   task's rule for ambiguous forms (take the stricter reading) and NFR3; it
   still distinguishes extended-glob parentheses from syntax-error
   parentheses as the finding suggests, so the benign case
   `x=( @(foo|bar) ); cat <<"EOF"\nhello\nEOF` is allow under both readings.
6. **Unchanged elsewhere**: everything the first task established — the
   direct-position rule, the discarded-line rule, the reset, and the
   treatment of substitutions, quotes and closed arrays — keeps its current
   behavior, including every fix the round-1 auto-fix loop applied (leading
   `<` redirect before an array assignment, fd-number and `{fd}` redirects
   before it, a bare `(` directly inside an array discarding the line, an
   unclosed `${` on a discarded line not suppressing later lines' array
   checks, and the redirect flag reset on a `(` / `((` push).
7. **Map and consumers (NFR1)**: heredoc-operator and body decisions stay in
   lex_shell() / _lex_pass() and helpers they own. If the two readings of
   rule 5 are evaluated by lexing under each reading, the reading is an
   input to lex_shell(), and whatever combines the two results only compares
   verdicts — it never classifies heredoc operators itself.
   strip_heredocs(), scan_structure(), _TrackingLexer and tokens() gain no
   array, subscript or extended-glob logic of their own.
8. **Work bound (NFR2)**: subscript matching and extended-glob handling stay
   inside the left-to-right pass. Each lexing pass keeps the work bound
   (LEX_WORK_FACTOR × length + floor) and the scan-budget ask on overrun; a
   second reading, if used, is lexed only when an extended-glob parenthesis
   appeared at direct position in an array context.

## Test Notes

- The case table is the TDD vehicle. Add the AC-1 to AC-5 entries first and
  record which ones fail before the change: the AC-1 and AC-2 deny entries,
  the AC-3 and AC-4 regression deny entries, and the AC-4 allow entry are
  expected to fail; the AC-5 entries are expected to pass already and pin
  the loop fixes against this task's changes.
- For each AC-5 entry, confirm it fails when its loop fix is reverted
  locally; an entry that passes with the fix reverted does not pin that fix
  and needs a different form. Do not commit the reverted state.
- Deny-side follow-up lines use only commands that are deny on their own
  (`git reset --hard HEAD`; SPEC.md A6), so a deny shows the line was read
  as a command. The AC-2 ask case uses a benign follow-up (`echo hi`) so the
  ask comes from the unmatched subscript alone.
- Edge cases worth adding to the same table (beyond the AC set):
  - `eval x[a b]=( <<EOF` followed by the git lines → deny (rules 1 and 2
    combined);
  - `x=( [a b]=c <<EOF` followed by the git lines → deny (a blank inside an
    element subscript does not end the word);
  - `builtin declare x=( <<EOF` / `command declare x=( <<EOF` — out of
    scope; record whatever verdict the hook yields and do not tune for it.
- When a form is uncertain, measure it with Bash 5.3.9 (`bash -c`, with
  `extglob` off and on where relevant) before choosing the expected verdict,
  and keep the stricter verdict per Behavior 5.
