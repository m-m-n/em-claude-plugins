# Task Plan: task0001 — Tokenize requirements option lines and follow includes at any position

## Goal

The pip directness resolver reads every option on a requirements option line, so an include (`-r` / `--requirement`) or editable (`-e` / `--editable`) placed anywhere on the line contributes direct-dependency names, and any option line it cannot interpret marks the name set incomplete instead of silently leaving it complete.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/scripts/scan-dependencies.py` — option-line handling of the pip requirements directness resolver (the leading-option classification and its caller that collects direct names)
- `tests/test_scan_dependencies_pip_directness.py` — new test cases for this task, appended; existing tests stay untouched

## Design

### Where the change lives

The change is confined to the pip requirements directness resolver in `em-workflow/scripts/scan-dependencies.py`: the option-line classification that today examines only the leading option (`_requirements_option`) and the direct-name collector that calls it (`_pip_requirements_direct_names`). Either may be reshaped or replaced, under these constraints:

- The resolver's external contract is unchanged: same inputs, same result (the set of direct-dependency names plus the completeness flag), same callers.
- Lines that do not start with `-` keep their current handling (SPEC A5).
- The existing include rules are reused, not reimplemented: resolve a target relative to the including file, keep it within the project root, never fetch a URL, open each file at most once. Every include found by the new flow goes through them, whatever its position on the line.
- The existing requirement-name extraction (`_requirement_name`) is reused for editable values.
- The existing summary note `pip_directness_undetermined` remains the only channel for reporting an incomplete set.
- Standard library only (NFR1).

### Option-line processing flow

For each logical line whose first character is `-`:

1. Split the line into tokens with the standard library's POSIX-mode shell-style splitting (shlex, as SPEC FR1 / A2 fix).
2. If splitting fails (unclosed quote, trailing escape, or any other splitting error), take nothing from that line, mark the set incomplete, and continue with the next line and the remaining files. No exception leaves the resolver (NFR2).
3. Walk the tokens from left to right and classify each one with the table below. When a form takes its value from the next token, that token is consumed and is not classified on its own.
4. Hand each include value to the existing include rules (see above). Every outcome those rules already define — including marking the set incomplete for an outside-root target or a URL — is kept.
5. Once the set is marked incomplete it stays incomplete; reading continues so that names declared elsewhere are still collected.

Token classification (the first matching row applies; long names are compared on the part before `=` where a row says so):

| Token shape | Kind | Value | Behaviour |
|---|---|---|---|
| exactly `-r` | include | next token, verbatim | follow; no next token → incomplete |
| `-r` followed by more text | include | the text after `-r` | follow |
| exactly `--requirement` | include | next token, verbatim | follow; no next token → incomplete |
| `--requirement=` followed by text | include | the text after `=` | follow; empty text → incomplete |
| exactly `-c` or `--constraint` | constraint | next token (consumed if present) | never opened; completeness unchanged, also when the value is missing |
| `-c` followed by more text, or `--constraint=` followed by text | constraint | attached text | never opened; completeness unchanged |
| exactly `-e` or `--editable` | editable | next token, verbatim | a name from the name extraction becomes a direct name; no name, or no next token → incomplete |
| `-e` followed by more text, or `--editable=` followed by text | editable | attached text | same as the row above; empty text → incomplete |
| a token starting with `--` whose part before `=` is longer than `--` and a proper prefix of `--requirement` or `--editable` (for example `--requirem`, `--re`, `--e`, `--editab`) | abbreviation | not interpreted | incomplete; nothing is opened; the following token is not consumed |
| exactly `--` | none | none | ignored |
| anything else (`--index-url` and its URL, `--hash=…`, unknown options, stray words) | other | none | ignored; completeness unchanged |

Consequences the implementer must preserve:

- Several includes on one line are all followed (SPEC A1); a constraint on the same line never prevents an include from being followed.
- A leading `-e` now takes only the next token as its value, not the rest of the line (FR5).
- An abbreviated option is never resolved to the option it abbreviates and its value is never read (FR6).

### Reporting

The reporting mechanism does not change: an incomplete set is reported through the existing `pip_directness_undetermined` note as the count of advisories that matched no declared name and are at or above the threshold or of unknown severity (FR8). No new note token is introduced. The splitter's error text, line content and path names never reach the summary (NFR4).

### Plugin version

Per SPEC NFR6, this task leaves the version fields of `em-workflow/.claude-plugin/plugin.json` and the root `.claude-plugin/marketplace.json` as they are.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR2, FR7, FR8; TM-5): with a requirements.txt consisting only of `-c constraints.txt -r deps.txt` and a deps.txt declaring vuln-pkg, the resolver returns the name set {vuln-pkg} with complete=True and never opens constraints.txt; a full scan through the pip-audit substitute reporting one high advisory for vuln-pkg yields exactly one finding and no `pip_directness_undetermined` note. The same holds for `--index-url https://x/simple -r deps.txt`, and no network connection is attempted.
- [ ] AC-2 (FR1, FR2; TM-4, TM-5): on a single line, `-r a.txt -r b.txt` contributes the names of both files; `-c c.txt --requirement=b.txt`, `-c c.txt -rb.txt` and `--index-url URL --requirement b.txt` each follow b.txt and never open c.txt. When the same include target is named more than once — repeated on one line, or a cycle between two files formed by mid-line includes — each file is opened at most once and resolution terminates.
- [ ] AC-3 (FR3, FR4, NFR2; TM-3, TM-4): an option line that cannot be split (an unclosed quote such as `-c a -r "deps.txt`, a trailing escape) contributes no names, sets complete=False, raises no exception, and does not stop other lines and files from being read; an undeclared high advisory is then counted exactly once as pip undetermined. `--index-url URL -r` with no value, a trailing `--requirement` with no value, and an empty `--requirement=` each set complete=False.
- [ ] AC-4 (NFR3, FR1; TM-1, TM-2): a mid-line include pointing outside the project root (`-c a -r ../outside/x.txt`, an absolute path) is not opened and sets complete=False; `--index-url URL -r https://...` attempts no network connection and sets complete=False.
- [ ] AC-5 (FR5; TM-2, TM-3, TM-5): `-e X`, `-eX`, `--editable X` and `--editable=X` are read at any position on an option line. A value from which the existing name extraction yields a name (for example `--index-url URL --editable=<value with a name>`) adds that name to the direct set; a value yielding no name (`-c a -e ./pkg`, `--index-url URL -e git+https://...` without a name) or a missing value sets complete=False, with no network connection attempted. A leading `-e` takes only the next token as its value.
- [ ] AC-6 (FR6, FR7; TM-1, TM-3): abbreviated long options (`--requirem deps.txt`, `--requirem=deps.txt`, `-c a --editab ./pkg`, and ambiguous prefixes such as `--re` and `--e`) set complete=False and no referenced file is opened. A lone `--`, `--index-url`, `--hash=` and unknown option tokens are ignored and leave completeness unchanged.
- [ ] AC-7 (FR8, NFR4; TM-6): in every incomplete case above, the scan summary reports the set only through the existing `pip_directness_undetermined` note (its fixed token and a count); the summary contains no splitter error text, no requirements line content and no path name, and no new note token exists.
- [ ] AC-8 (NFR1, NFR5, NFR6): `python3 -m unittest discover -s tests` (including the standard-library-only test) and `python3 em-workflow/scripts/check-plugin-invariants.py .` both pass; this task's diff of `tests/test_scan_dependencies_pip_directness.py` consists of additions only, so no existing test is modified or removed; this task's diff does not touch the version fields of em-workflow's `plugin.json` or of `.claude-plugin/marketplace.json`.
