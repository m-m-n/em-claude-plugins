# Task Plan: task0001 — Exact-ref resolution of the merge source and the parent in merge-task.sh

## Goal

After the post-lock identity re-check, `merge-task.sh` takes the merge source
only from the exact task ref and the parent value only from the exact
integration-branch ref, and confirms that both are commits. If either check
fails, the run exits 2 with no ref change, no merge commit and no journal
line. Regression tests and the script's content pin are updated with the
change.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/scripts/merge-task.sh` — post-lock resolution of the merge source and the parent value; the comments that describe both resolutions
- `tests/test_merge_task_journal.py` — extend the existing clean-worktree task-ref deletion test; add the parent-side test and the two non-commit tests
- `tests/test_merge_unverified_exit_doc_contract.py` — content pin of the changed script and the history comment above it

## Design

### Post-lock resolution flow (merge-task.sh)

The pre-lock identity binding, the lock acquisition, the post-lock
symbolic-ref re-check and the clean-tree precondition stay as they are.
Between the clean-tree check and the first of the three merge paths, the
flow is as follows. It follows SPEC.md's Resolution Flow order: task ref
first, then parent.

1. **Task ref lookup (FR1, FR2).** Look up the expected task ref
   (`refs/heads/em-workflow/{feature}/{taskNNNN}`, already held by the
   identity binding) by its exact full name. Ambiguous-name resolution
   (gitrevisions trying the name under `refs/`, `refs/tags/`,
   `refs/heads/`, `refs/remotes/`, ...) plays no part. SPEC.md FR1 requires
   git's exact ref verification lookup with only the object ID printed
   (`show-ref` in verify mode). If the lookup fails (the ref is absent or
   git fails), the script prints an ERROR line naming the full task ref and
   exits 2.
2. **Task commit-type check (FR3).** The object ID from step 1 must name a
   commit object. If it does not, the script prints an ERROR line and exits
   2.
3. **Parent ref lookup (FR7).** The same exact lookup runs for
   `refs/heads/{parent-branch}`. If that ref is absent, the script prints an
   ERROR line naming the parent branch and exits 2. The existing "parent
   branch not found" wording satisfies this.
4. **Parent commit-type check (SPEC.md A3).** Same as step 2, for the parent
   value.
5. **Three paths.** The already-contained, fast-forward and merge-commit
   paths keep their logic. They use the single merge-source value from
   steps 1-2 and the parent value from steps 3-4.

Every exit in steps 1-4 happens before any update-ref, merge-tree,
commit-tree or journal append.

### Single merge-source value contract (FR4)

- Precondition: steps 1-2 succeeded.
- Postcondition: one value is used by all of the following:
  - the already-contained ancestry check
  - the fast-forward ancestry check, its update-ref, its journal event and
    its message
  - the merge-commit path's merge-tree input, its commit-tree second parent,
    its journal event and its message
- After step 2, nothing reads the task ref, HEAD, or any other name for the
  merge source again.
- The parent value from steps 3-4 stays the compare-and-swap old value of
  both update-ref calls, as it is today.

### Exit and side-effect contract

- Exit-code meanings are unchanged. Every new rejection uses exit 2.
- The step 1 ERROR line names the full task ref. This keeps the module's
  existing ERROR-line assertion for the task ref valid (SPEC.md A1). The
  step 3 ERROR line names the parent branch. Steps 2 and 4 may use any
  wording, as long as the line is an ERROR line.
- "No side effects" means that no ref is changed, no `merge: {TASK_ID}`
  commit is created and no journal line is appended.

### Comment and text constraints (NFR2, SPEC.md A2)

- Some comments describe how the merge source and the parent are resolved:
  the header paragraph on the identity binding and the merged commit, the
  Concurrency paragraph, and the comment block directly above the
  merge-source resolution. These comments state that both values are
  resolved by exact ref-name match.
- Exactly one line of the script carries the text "Parent already contains
  us". The line directly after it carries the `merge-base --is-ancestor`
  check.
- No comment contains "manual invocation", "merge-only" or "exercising only
  merge". The contract test matches these phrases case-insensitively and
  also across wrapped comment lines.

### Content pin (FR5, SPEC.md A5)

- `EXPECTED_MERGE_TASK_SH_SHA256` holds the sha256 of the script's bytes.
  Every commit of this task that changes `merge-task.sh` sets the pin to the
  new content's sha256 in that same commit. The contract test then passes at
  every commit of the task branch.
- The history comment above the pin may add this feature's task0001 to its
  list of changes that set the pin.

### Tests (tests/test_merge_task_journal.py)

The new and extended tests reuse the module's existing fixtures:

- the task worktree with a commit to merge
- the lock-wait mutation runner `_run_merge_with_mutation_during_lock_wait`.
  It holds the shared merge lock, starts the run, applies a mutation while
  the run waits, then releases the lock.
- the ERROR-line and dirty-worktree-wording assertions

Tests:

- **Extended task-side test (FR6, TS-1).**
  `test_task_ref_deleted_in_a_clean_worktree_is_rejected_at_the_merge_source`
  keeps its current mutation (delete the task ref, empty the worktree) and
  its current assertions. Before the run, it also creates the tag
  `refs/tags/refs/heads/em-workflow/feat/task0001` at a new commit whose
  parent is the integration tip and which is on no branch. Against the
  pre-change script, this tag makes the run fast-forward the integration
  branch to that commit with exit 0, so the test fails there.
- **Parent-side test (FR8, TS-3).** During the lock wait, delete
  `refs/heads/em-workflow/feat/integration` and create the tag
  `refs/tags/refs/heads/em-workflow/feat/integration` at the task tip. The
  side-effect checks must not depend on the integration ref existing. The
  module's existing side-effect helper reads the integration branch through
  a name lookup that would itself resolve to the planted tag. So this test
  checks the following instead:
  - the exact ref `refs/heads/em-workflow/feat/integration` is still absent
  - the tag and the task ref still hold their pre-run values
  - no `journal.jsonl` exists under the test's temporary directory
- **Non-commit task ref test (FR3, TS-4).** During the lock wait, write the
  task ref's loose ref file directly in the shared git directory, pointing
  it at a non-commit object of the repository (a tree or a blob). git's
  ref-update command refuses a non-commit object under `refs/heads/`
  (SPEC.md A4). The run may stop at the clean-tree check or at the
  commit-type check. Only exit 2 and no side effects are required.
- **Non-commit parent ref test (SPEC.md A3).** Write the integration ref's
  loose ref file directly, pointing it at a non-commit object. This can
  happen before the run, because the pre-lock binding compares only the
  parent branch name. The existing side-effect helper cannot be used here
  either, because it reads the integration branch's history. Check instead
  that the integration ref still holds the same object ID, that the task
  ref is unchanged and that no `journal.jsonl` exists.

## Test Notes

- AC-1 to AC-4 are integration tests in `tests/test_merge_task_journal.py`
  against a disposable repository, using the module's existing fixtures.
  Write AC-1's extension and AC-2's test first and confirm that both fail
  against the unchanged script (SPEC.md AC-4) before changing the script.
- AC-1's tagged commit must be a child of the integration tip. A commit
  already contained in the integration branch would let the pre-change
  script exit 0 through the already-contained path without advancing the
  branch, which weakens the red check.
- AC-3 may also pass against the pre-change script. Only exit 2 and no side
  effects are required, so a red phase is not mandatory for it. The same
  applies to AC-4.
- AC-5 is covered behaviourally by the existing tests it lists. The rest of
  AC-5 (no ambiguous-name lookup remains, one value feeds all paths) is
  confirmed by reading the changed post-lock section. No new text-scanning
  test is required for it.
- AC-6 is covered by the existing contract module. Recompute the pin after
  the final edit of each commit that touches the script.
