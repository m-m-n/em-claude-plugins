### Content added to Step 4c (the tests.yaml contract)

Write the rules in the language, style and terminology already used in Step 4c. Field
names are written exactly as the tests.yaml schema and the Step 7 report spell them.

**R1 — criterion with no executable red (FR1)**

- Trigger: an Acceptance Criterion for which no executable check that can be made to
  fail (test, build, lint, or similar) exists.
- Recording form for such a criterion: `tests: []`, `red_confirmed: false`, and a
  `red_reason` stating why no executable red exists; the criterion is also listed in the
  Step 7 report field `unconfirmed_reds`.
- Tasks whose only deliverable is documentation are named explicitly as covered by this
  rule.
- The rule is applied per criterion: in a task that mixes criteria with and without an
  executable check, only the criteria lacking one use this form.
- Consistency requirement: naming documentation-only tasks must not read as a blanket
  exemption. When a document-contract test that reads the document can be written, the
  criterion has an executable red and the normal rule applies.

**R2 — meaning of `red_confirmed: true` and no local redefinition (FR2)**

- `red_confirmed: true` means only: with no implementation present, the executed check
  was actually observed to fail.
- A criterion verified by a build or lint result gets `red_confirmed: true` only if the
  failure of that check was actually observed before implementation.
- Reading, searching for, or locating a document or an anchor is not observing a red.
- The meaning of `tests`, `red_confirmed` and `red_reason` must not be locally redefined
  in `notes` or in any other text of the tests.yaml or the report.

**R3 — report destination of `red_confirmed: false` (FR3)**

- The existing Step 4c wording that sends `red_confirmed: false` criteria to "the
  report's notes" is replaced by wording that sends them to the Step 7 report field
  `unconfirmed_reds`.
- After the change, no wording in Step 4c routes `red_confirmed: false` criteria to
  `notes`. Other, new mentions of `notes` (the R2 prohibition, the R4 skipped re-run
  statement) are legitimate and stay.

**R4 — `final_failures` recording discipline (FR4, NFR1)**

The record lives in the comment attached to `final_failures`; no key is added to or
removed from tests.yaml. If Step 4c shows a tests.yaml example or schema block, only the
comment text for `final_failures` may change there; its keys stay as they are.

1. (a) The `final_failures` comment records the output of the run actually re-executed
   after implementation.
2. (b) The re-run may be skipped only when no file the suite reads — source, tests, and
   documents the tests read — was changed at all. When skipped, the comment says
   "not re-run; baseline inherited" together with the reason, and the report's `notes`
   also states that no re-run was performed (ASM-2: existing Step 7 field, no new report
   field).
3. (c) If it cannot be confirmed that the skip condition holds, re-run. A task that
   changed a document the tests read cannot skip.
4. (d) The same run result is never written into both `baseline_failures` and
   `final_failures` as if they were two independent observations.

### Content added to Step 6 (parent-side adoption)

**R5 — mandatory re-run after parent-side adoption (FR5)**

- After parent-side adoption, the R4 (b) skip condition does not apply: the suite is
  always re-run, and `baseline_failures` and `final_failures` are updated.
- This holds on every adoption within the Step 6 conflict loop, not only the first.

### Document-contract test (new module)

Responsibility: fail when any of R1 to R5 is missing from implementer.md; pass when all
are present. Read-only; Python standard library `unittest` only.

Processing flow:

1. Resolve the repository root from the test module's own location (independent of the
   current working directory) and read `em-workflow/agents/implementer.md`.
2. Extract the Step 4c section and the Step 6 section, each from its own heading up to
   the next heading of the same or a higher level.
3. Before any rule check, assert that each section was found and is non-empty (a missing
   heading must fail loudly, never make a negative check pass vacuously).
4. One test method per rule R1 to R5, so a failure names the missing rule. R1 to R4 check
   the Step 4c section; R5 checks the Step 6 section.
5. Positive checks look for short, distinctive phrases the new wording introduces —
   including the field names and values listed in R1 to R4 (`tests: []`,
   `red_confirmed: false`, `red_reason`, `unconfirmed_reds`, `red_confirmed: true`,
   `baseline_failures`, `final_failures`), the "not re-run; baseline inherited" wording,
   and the mention of documentation-only tasks. Each rule's check includes at least one
   phrase that is absent from the pre-change section; a phrase that already exists before
   the edit does not count as a red for its rule.
6. The R3 negative check asserts that the specific pre-change phrase routing
   `red_confirmed: false` criteria to the report's notes is absent from Step 4c. Identify
   that exact phrase in the pre-change file before editing; do not use the bare word
   `notes` as the negative pattern.

### Version bump

- The em-workflow version in plugin.json and in the em-workflow entry of marketplace.json
  hold the same value at the task base. Raise the patch component of that value by one in
  both files (ASM-6: 0.2.8 to 0.2.9 at the SPEC's base revision; if the base already
  holds a later value, bump from that value).
- No other field changes; other plugins' entries in marketplace.json are untouched.
- The version bump is committed together with the implementer.md change (the repository's
  commit guard rejects a plugin-file commit without it).

## Acceptance Criteria (MANDATORY)

- [ ] AC-2 (FR2): Step 4c states that `red_confirmed: true` means only that the failure of an executed check was observed with no implementation present, that reading or searching for a document or anchor is not observing a red, and that the meaning of `tests` / `red_confirmed` / `red_reason` must not be locally redefined in `notes` or any other text.
- [ ] AC-3 (FR3): Step 4c names `unconfirmed_reds` as the report destination for `red_confirmed: false` criteria, and the pre-change phrase routing them to the report's notes no longer appears in Step 4c.

- [ ] AC-5 (FR5): Step 6 states that after parent-side adoption the skip condition does not apply, and the suite is always re-run with `baseline_failures` and `final_failures` updated.
- [ ] AC-6 (FR6, NFR4): `tests/test_implementer_tests_yaml_record_contract.py` uses only the standard library `unittest`, is collected by `python3 -m unittest discover -s tests`, checks the rules of AC-1 to AC-5, was observed failing against the pre-change implementer.md, and passes after the change.
- [ ] AC-7 (FR7): the em-workflow version in `em-workflow/.claude-plugin/plugin.json` and in the em-workflow entry of `.claude-plugin/marketplace.json` is the same value and is exactly one patch increment above the value at the task base; no other plugin's version changes.

## Test Notes

- AC-1 to AC-5 map to one method each in the new test module. Write the module first, run
  it alone against the pre-change implementer.md, and observe each method fail before
  editing the document. This is the SPEC edge case "a documentation-only change for which
  a document-contract test can be written has an executable red", so these criteria are
  recorded under the normal rule.
- AC-6 is satisfied by the observed red-to-green of AC-1 to AC-5 plus the discover run.
- AC-7 is checked by comparing both manifest values with the values at the task base; the
  check fails before the bump (values equal the base). It is not made a permanent unit
  test, because a pinned version number would break on every future bump.
- AC-8's first two items already hold before any change, so no failing check can be
  observed for them; record them in tests.yaml with the R1 form this task introduces
  (`tests: []`, `red_confirmed: false`, a `red_reason`, listed in `unconfirmed_reds`).
  Its third item is checked by the full-suite run.
- This task changes a document the suite reads, so the `final_failures` re-run cannot be
  skipped (R4 (c)).
- Edge cases the new wording must resolve (confirm by reading the result against SPEC
  Edge Cases): mixed criteria in one task; a build or lint criterion; a documentation-only
  task with a writable document-contract test; a task that changed a document the tests
  read; an unconfirmable skip condition; repeated adoptions in the Step 6 conflict loop.
