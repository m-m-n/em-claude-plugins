## Design

### What the document says (fixed input, not changed by this task)

Step 4's fenced block holds exactly one line,
`python3 {cleanup_script} --integration-worktree {integration_worktree} --feature {feature} --task {T}`.
The prose after it states that the script is resolved per Step I.0 step 4,
that the line runs with the resolved absolute path of `cleanup-task.py` in
place of `{cleanup_script}` and with the validated literal values in place of
the other three placeholders, that each substituted value is first escaped
for the shell as one whole argument (single-quoted, an embedded single quote
written as close-quote, escaped quote, open-quote), that no placeholder,
unescaped `$` or brace is left on the line that runs, and that when the script
cannot be resolved nothing is invoked and no other location, a path relative
to the current directory included, is tried. IMPLEMENTATION.md C1 is the
contract for this shape.

### Changes to the module

1. **Expected call line**: the module's expected call line becomes the C1
   line above, compared byte for byte. The extraction of the call line picks
   the fenced-block line whose first word is `python3` and which holds
   `{cleanup_script}`; it still fails, naming the reason, when the region has
   no such line or more than one.
2. **Resolution statements**: the matcher for the resolution statements
   covers, besides the three phrases it checks today, the statement that the
   resolved absolute path replaces `{cleanup_script}`, the statement that each
   substituted value is escaped for the shell as one whole argument, and the
   statement that no placeholder, unescaped `$` or brace is left on the line
   that runs. Each phrase is taken verbatim, whitespace-normalized, from the
   current step 4.
3. **Relative-path detection**: the check over the whole of
   `implement-phase.md` accepts an occurrence of `cleanup-task.py` when it is
   written as `${CLAUDE_PLUGIN_ROOT}/scripts/cleanup-task.py` or as the bare
   file name (nothing path-like directly before it: no `/`, no `\`, no
   `./`). Any other occurrence is a naming by a relative path and is
   reported. The call line itself must name the script only through
   `{cleanup_script}` and hold no `cleanup-task.py`.
4. **Expansion**: one expansion helper replaces `{cleanup_script}`,
   `{integration_worktree}`, `{feature}` and `{T}` with values, each escaped
   for the shell in the form step 4 states. It runs over these value sets:
   - the sample set: the script under the module's sample plugin root, and
     the sample feature, task and integration worktree of
     `tests/test_protocol_git_ops_pass_destructive_guard.py`;
   - the repository copy: the absolute path of
     `em-workflow/scripts/cleanup-task.py` in this repository, with the sample
     feature, task and integration worktree;
   - shell-special paths: for the script path and for the integration
     worktree, values holding a space, a single quote, a double quote, a
     backtick, `$` (a variable form, a brace form and a command-substitution
     form) and a newline. The feature and task values stay the sample ones,
     since Step I.0 step 2 admits nothing else for them.
5. **Argument check**: an expanded line is correct when no placeholder is
   left and splitting it by POSIX shell word rules (standard library) yields
   exactly eight words: `python3`, the script path, `--integration-worktree`,
   the integration worktree, `--feature`, the feature, `--task`, the task,
   each value recovered exactly as given.
6. **Guard check**: every expanded line of step 4 goes through the
   repository copies of `destructive-guard.py` and
   `interpreter-mismatch-guard.py`, with `CLAUDE_BATCH` removed and set, in
   the invocation form the module uses today.

### Test names that stay

Every test class and test method that
`test-docs/wake-task-cleanup-script/task0002.tests.yaml` and

now proves that no placeholder and no `CLAUDE_PLUGIN_ROOT` text survives the
expansion). New methods may be added.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR4, TM-3, TS-8): The module asserts that the step 4 region holds
      exactly one fenced block whose only non-blank line is, byte for byte,
      the C1 call line, and that extracting the call line returns that line.
      Negative proofs: the pre-change step 4 copy yields "no call line"; a
      region with a second fenced call line yields "more than one call line";
      a second fenced block and an extra token after the call line are each
      detected. These pass against the current `implement-phase.md`.
- [ ] AC-2 (FR4, TM-3, TS-8): The module asserts that the region states, as
      whitespace-normalized phrases taken from the current step 4: the
      resolution per Step I.0 step 4; the resolved absolute path in place of
      `{cleanup_script}`; the escaping of each substituted value for the shell
      as one whole argument; no placeholder, unescaped `$` or brace left on
      the line that runs; and that when the script cannot be resolved nothing
      is invoked and no other location, a path relative to the current
      directory included, is tried. The pre-change step 4 copy fails every
      one of these phrases, and removing any single phrase from the region is
      detected.
- [ ] AC-3 (FR4, TM-3, TS-8): The module asserts that no occurrence of
      `cleanup-task.py` in `implement-phase.md` is named by a path relative to
      the current directory (Design, item 3), and that the call line holds no
      `cleanup-task.py`. It passes against the current document. Negative
      proofs: replacing `{cleanup_script}` in the call line with
      `em-workflow/scripts/cleanup-task.py`, with `scripts/cleanup-task.py`
      and with `./cleanup-task.py` is each detected, and adding a prose
      mention of `em-workflow/scripts/cleanup-task.py` to the region is
      detected.
- [ ] AC-4 (NFR2, TM-4, TS-9): For each value set of Design item 4, the call
      line extracted from the region and expanded with escaped values leaves
      no placeholder and splits into exactly the eight intended words, each
      value recovered exactly (Design item 5). The shell-special set covers a
      space, a single quote, a double quote, a backtick, `$` in a variable,
      brace and command-substitution form, and a newline, in both the script
      path and the integration worktree. Negative proof: expanding a value
      that holds a space, and one that holds `$` and a newline, without
      escaping fails the word check.
- [ ] AC-5 (NFR2, TM-4, TS-9): Every expanded line of AC-4 passes both
      `destructive-guard.py` and `interpreter-mismatch-guard.py` (exit status
      0 and a verdict that is neither `ask` nor `deny`), with `CLAUDE_BATCH`
      removed from the guard's environment and with it set. The existing
      negative proofs stay: a forced branch deletion does not pass the
      destructive guard, a Python script run by `bash` does not pass the
      interpreter guard, and a guard that exits non-zero is not a pass.
- [ ] AC-6 (FR3, FR8, FR4, TM-5, TS-8, NFR3): The checks of
      `TestAC2NoGitCommandInTheRegion`, `TestAC3ReadsTheJsonAndReports` and
      `TestAC4PinnedWordingStays` keep their assertions; every class and
      method named in `test-docs/wake-task-cleanup-script/task0002.tests.yaml`
      and `task0003.tests.yaml` still exists under the same name;
      `TestModuleHygiene` passes (the module writes no files and needs no
      temporary directory). Afterwards
      `python3 -m unittest tests.test_implement_phase_step4_cleanup_script tests.test_tests_yaml_id_resolution`
      and `python3 -m unittest discover -s tests` report no failure and no
      error.

## Test Notes

- AC-1 to AC-3 are static tests over `implement-phase.md`; AC-4 is a pure
  string check; AC-5 runs the two hooks as child processes; AC-6 is the
  existing suite.
- The module docstring is updated to describe the C1 call-line shape and the
  value sets; its statement that the module writes no files stays true.
- Values with a newline are passed to the guards inside the JSON on standard
  input, never through a command line or a file.
- If a guard returns `ask` or `deny` for a correctly escaped line, that is
  reported as a plan deviation with the value and the verdict; the guard and
  the document are not edited by this task.
