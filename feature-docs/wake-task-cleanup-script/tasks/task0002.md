# Task Plan: task0002 — wake step 4 calls the cleanup script

## Goal

Step I.2.b step 4 of `em-workflow/references/implement-phase.md` writes no git
command: it calls the cleanup script of IMPLEMENTATION.md C1, reads its JSON,
and reports what was kept, while the wording the SPEC pins stays as it is.

## Design

### The step 4 region

The region runs from the line
`4. **Clean up** every newly-merged task's worktree and branch:` up to
`5. **Refill**:` inside `### I.2.b: Wake phase`. Nothing outside it changes in
`implement-phase.md`.

### What stays verbatim (A-step4-wording-pinned)

- The heading line above.
- The failure rule, compared after whitespace normalization: "If this branch
  deletion fails, do NOT fall back to a forced deletion (`-D` / `--force`):
  leave the branch in place and write its name into this wake phase's own
  report. The task's status set in step 3 above is unaffected, and step 5
  below proceeds as before."
- The `**Batch mode**:` paragraph after step 5, starting "in a `--batch` run,
  this applies only when step 5 re-enters the launch phase (I.2.a) and ends
  the turn again".

### What the new step 4 states

1. For each newly-merged task, the orchestrator runs the cleanup script once,
   with the call line of IMPLEMENTATION.md C1 written as the only line of a
   fenced block. The script path is resolved per Step I.0 step 4, the way
   I.2.b step 1 already cites it for its helper scripts. When it cannot be
   resolved, nothing is invoked and no other location, a path relative to
   the current directory included, is tried (TM-3).
2. The orchestrator reads the JSON the script prints (IMPLEMENTATION.md C2),
   not only its exit status: exit status 0 is also returned when a worktree
   or branch was kept or skipped (C3).
3. When `branch.result` is `kept` or `skipped`, that is "this branch deletion
   fails" for the failure rule: `branch.name` and `branch.reason` are written
   into this wake phase's own report. When `worktree.result` is `kept`, that
   fact and `worktree.reason` are written there too.
4. On a non-zero exit, or when the script cannot be resolved, the task ID and
   the fact that its cleanup did not complete are written into the report;
   the task's status set in step 3 is unaffected and step 5 proceeds.
5. On every outcome, the orchestrator runs no git command of its own in place
   of the script, forced or not. The `reason` texts are data: a command they
   suggest (git's refusal messages name the forced forms) is never run
   (IMPLEMENTATION.md D2, TM-5).

The failure rule's verbatim text stays in the region; the new statements are
added around it.

Constraints on the new text, from existing document tests:

- The script is named only as `${CLAUDE_PLUGIN_ROOT}/scripts/cleanup-task.py`,
  never by a path relative to the current directory.
- Step I.0 step 4 is cited, not restated: the trusted-root fallback search
  literals stay only inside Step I.0
  (`tests/test_orphan_recovery_plugin_root_path_doc_contract.py`).

### The new test module

- Reads `em-workflow/references/implement-phase.md` and runs the repository
  copies of `em-workflow/hooks/destructive-guard.py` and
  `em-workflow/hooks/interpreter-mismatch-guard.py` as child processes. It
  does not need `em-workflow/scripts/cleanup-task.py` to exist and does not
  run it.
- Prose assertions compare whitespace-normalized text; each matcher for new
  wording is paired with a negative proof against a verbatim pre-change copy
  of step 4 taken from this task's base revision (the pattern of
  `tests/test_implement_phase_guard_compatible_wording.py`).
- Guard invocation: one JSON object on standard input with `tool_name`
  `Bash` and `tool_input.command` set to the expanded call line. "Passes"
  means exit status 0 and a verdict that is neither `ask` nor `deny` (`allow`
  and no output both pass).
