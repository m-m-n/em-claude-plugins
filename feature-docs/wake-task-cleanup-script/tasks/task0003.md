# Task Plan: task0003 — cleanup script deletes only this repository's merged task branch

## Goal

`em-workflow/scripts/cleanup-task.py` deletes a task branch only when the
deletion itself is judged against the integration branch, and touches no
worktree or branch of a repository other than the one the integration
worktree path names.

## Design

The CLI, the result JSON and the exit status are IMPLEMENTATION.md C1, C2 and
C3 (C1's `--integration-worktree` rule, C2's `kept` meaning and C3's exit 1
row were extended for this task). They are not restated here.

### Repository identity (findings ae2ab614431664d3, 6ca3af1949db66a6)

The project root is the part of the `--integration-worktree` value before its
five fixed segments (`.claude`, `worktrees`, `em-workflow`, the feature,
`integration`). It is fixed from the input value before anything is read
through the feature directory.

1. Without running git, as part of input validation (exit 2, no git run):
   - The real path of the `--integration-worktree` value equals the project
     root's real path joined with the five fixed segments. A symbolic link at
     `.claude`, `.claude/worktrees` or any deeper segment that leads elsewhere
     fails this.
   - The expected task worktree path is the project root's real path joined
     with `.claude`, `worktrees`, `em-workflow`, the feature and the task ID.
     When something exists at the lexical task worktree path (the integration
     worktree's sibling named by the task ID), its real path must equal that
     expected path; a symbolic link there fails this.
2. With read-only git queries only, before the worktree registration list is
   used for any decision: the git common directory of the project root and
   the git common directory of the integration worktree, both compared by
   real path, are the same directory. When they differ, or either query
   fails, the script exits 1 with empty standard output and runs no worktree
   removal and no branch deletion.
3. The existing checks of the integration worktree's registration and branch
   stay. Registration matching for the task worktree compares registered
   paths against the expected task worktree path of step 1, not against a
   path obtained by resolving the lexical task directory.

### Branch deletion (findings ed06793e93ac3c27, c092d863994f0170)

After the exact ref of the task branch resolves, and after the script's
existing check that the branch tip is contained in the integration branch:

1. Read the task branch's upstream configuration (its remote and merge
   settings) with a read-only query, immediately before the deletion. When
   either setting is present, the branch is `kept` with fixed text saying the
   deletion was not run because the branch has an upstream configured, and no
   branch deletion runs.
2. Otherwise run the non-forced branch deletion with the integration worktree
   as the repository location, as before. With no upstream, git judges the
   deletion against the integration worktree's checked-out branch at the
   moment of deletion, so a tip that moved off the integration branch after
   the script's own check is refused by git and reported as `kept` with git's
   message.

The set of git operations stays closed: the worktree registration list, the
common-directory queries, exact ref resolution, the containment check, the
upstream configuration read, a non-forced worktree removal and a non-forced
`branch -d`. No forcing flag, no worktree prune, no other write.

### Existing tests

- The unmerged-branch test (TS-2) asserts the C2 contract — `branch.result`
  `kept`, `branch.name`, a non-empty `branch.reason`, and the ref unchanged —
  and no longer requires git's own refusal text, since the script reports its
  own fixed reason when the tip is not contained in the integration branch.
- Any existing test that pins the closed set of git operations is extended
  to the operations listed above.

## Test Notes

- AC-1 to AC-5 are integration tests on disposable git repositories built in
  a temporary directory whose real path is resolved first (NFR3), with the
  existing fixture and `PATH` shim of `tests/test_cleanup_task.py`.
- AC-2's timing is made deterministic by the shim itself: it recognizes the
  branch-deletion invocation, moves the task ref with the real git (outside
  the script), then runs the real git with the original arguments. The
  commit it moves to is prepared by the fixture beforehand. No load or
  repetition is used to provoke the race.
- AC-3 to AC-5 need two repositories in one temporary directory. The
  fixture's own git commands, the symbolic links and the second repository
  are made with an environment that does not put the shim on `PATH`.
- AC-5's integration directory is added as a worktree of the second
  repository at the project repository's expected path; the project
  repository is itself a git repository.
- Run the script with the current interpreter and bytecode writing off;
  never import it into the test process (IMPLEMENTATION.md Conventions).
