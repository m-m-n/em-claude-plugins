# Task Plan: task0002 — Scenario test: legacy verify re-run to merge-preflight proceed

## Goal

A scenario test pins that, on a fixture whose verify step lacks round / passed_ids and whose latest review round holds a deferred high finding with category spec, merge-preflight.py returns unresolved_findings before the verify re-run, and after the re-run is recorded, resolve-verified-findings.py is run and the result is committed, the finding is fixed and merge-preflight.py returns proceed.

## Requirements

FR2, FR5, FR6, NFR1, NFR4

## Scope

### Files to Create
- `tests/test_verify_rerun_legacy_resolution.py` — the scenario test (fixture construction, the state before the re-run, the re-run record, the script run, the commit and the final checks)

### Files to Modify

None.

## Design

### Fixture (before the re-run)

A git repository in a temporary directory, with an integration branch for one feature, holding in a committed state:

- A workflow.yaml in the legacy form: every step completed or skipped, and a completed verify step that has neither round nor passed_ids.
- The latest review round record (round 2) holding exactly one finding: severity high, category spec, resolution deferred, whose claim is the miss of one acceptance criterion ID, written together with a cause-analysis add-on (the shape IMPLEMENTATION.md D3 maps).
- Whatever else merge-preflight.py's other checks need to pass, built as the script defines them, so that the review-findings check is the only reason the state before the re-run does not proceed.

### Scenario flow

Follows IMPLEMENTATION.md Shared Components "Legacy re-run procedure", simulating the orchestrator's side of it:

1. Run merge-preflight.py on the fixture: it returns unresolved_findings.
2. Record the re-run in one workflow.yaml write: round 1, passed_ids containing the criterion ID the finding claims, and result pass.
3. Write a mapping file associating the finding's stable_id with that criterion ID, in the format resolve-verified-findings.py reads.
4. Run resolve-verified-findings.py on it: it reports success.
5. Commit the changed files to the integration branch.
6. Read the review round record: the finding has resolution fixed and a verify_resolution field.
7. Run merge-preflight.py again: it returns proceed.

The script's command-line shape, its mapping-file format and the way the existing test builds its fixture are taken from resolve-verified-findings.py and tests/test_resolve_verified_findings.py; this test follows them and changes neither (IMPLEMENTATION.md D1).

### Isolation

Every git command and every script run uses the temporary repository as its working tree. The commit identity is set inside the temporary repository only. Nothing is written to the real repository or to user-level git configuration, and the temporary directory is removed when the test ends.

## Test Notes

- AC-1 to AC-3 are one integration scenario; split them into separate test methods sharing one fixture builder so that a failure names the step that broke.
- If merge-preflight.py does not reach proceed with the fixture after the resolution, first check that the fixture satisfies the script's other checks. If proceed is unreachable without a script change, stop and report a plan deviation; do not change the script (FR6).
- Read the YAML files the way tests/test_resolve_verified_findings.py does; no third-party parser is imported.
- Use neutral identifiers for the feature, the finding's stable_id and the criterion ID.
