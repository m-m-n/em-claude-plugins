# Task Plan: task0007 — fallback reachability so no perspective ends a round unreviewed

## Provenance

- `source`: review
- `source_ids`: `0113d89b57312c50`
- `review_round`: 1

## Goal

Close the fail-open path in which a perspective whose whole primary chain
returns retryable skips (or a malformed result) ends the round with zero
completed reviewer runs and the review step still completes — by making the
Claude fallback reachable at chain exhaustion, sequentially, without ever
running it alongside a harness reviewer.

## Design

### D-H: availability is evaluated at the moment of decision, not only at Phase R2

SPEC FR3 licenses the Claude reviewer when a perspective's chain has no
available entry. Today that condition is read once, at Phase R2, from the
Phase R0 availability probes, and Phase R2b then forbids a Claude re-run at
chain exhaustion. The probe answers a different question from the one that
matters: `codex_available` is true whenever the CLI is installed, so a codex
that answers `rate_limited` at run time — with the `vertex-review` plugin
not installed, which the README presents as the standard configuration —
leaves the perspective with no reviewer at all and no path back.

Read the condition as effective availability, evaluated whenever the
orchestrator must decide who reviews this perspective: at Phase R2 from the
probes, and again at Phase R2b when the walk ends with every eligible entry
having proven unavailable (each returned a retryable skip, or was excluded
as unavailable). In that state the perspective genuinely has zero available
chain entries, so the Claude fallback is dispatched for it — after the walk,
never concurrently with a harness reviewer, and never as a second opinion
alongside one that completed. FR3's other clause ("no parallel simultaneous
dispatch with another LLM reviewer") is therefore preserved exactly, and no
SPEC.md change is proposed: what changes is the moment the existing
condition is evaluated, not the condition.

The malformed-non-retryable case (Phase R2b) reaches the same state by a
different route — a perspective with no completed run and no further chain
entry — and takes the same one fallback dispatch. The existing prohibition
on dispatching an ADDITIONAL harness reviewer from R2b is unchanged; only
the Claude fallback becomes reachable.

### D-I: the fallback is bounded and the round still degrades rather than aborts

At most ONE fallback dispatch per perspective per round is added by this
task. It does not consume the per-perspective 2-hop chain-walk budget (that
budget counts harness dispatches), and it is issued in one message together
with any other perspective reaching the same state, preserving FR9's fan-out
shape. A perspective whose fallback dispatch itself fails or skips ends the
round unreviewed; there is no further reviewer to try, so the round
continues and degrades rather than aborting (IMPLEMENTATION.md
Error-handling policy). What must not survive is the silence.

### D-J: the disclosure stays a disclosure, and becomes visible in batch

`unreviewed_perspectives` keeps its name, its position at the round-record
root, and its record-keeping status — making it a completion blocker would
require a new user gate, which NFR3 forbids. Two things change: a
perspective may only appear there after its fallback has been dispatched and
failed to produce a completed run (so the common case of the finding is
structurally gone rather than merely disclosed), and the round record — a
committed artifact that batch mode's output suppression explicitly does not
touch (Phase R5) — is stated as the batch-visible channel for it, alongside
the Phase R6 report in interactive mode. No new `gate_id` is introduced and
`references/batch-policies.yaml` is not touched (NFR3, FR15).

The evaluator is also told: Phase R3a's input block carries
`unreviewed_perspectives` so the round's evaluation is made with knowledge
of which perspectives produced no reviewer output. The field name and
meaning are pinned in IMPLEMENTATION.md Shared Components; this task
produces the value, task0006 owns what the evaluation contract says the
evaluator does with it.

### D-K: role vocabulary stays as it is

`perspective_runs`' `role` vocabulary (`primary` / `fallback` /
`evaluator`) is unchanged: a fallback dispatched at chain exhaustion is
still `role: fallback` with `source: claude`. Phase R5's note explaining
`role: fallback` is widened to cover both the R2-time and the
exhaustion-time route, keeping FR12's round-record compatibility intact —
this is a prose change only, no new field and no changed field meaning.
