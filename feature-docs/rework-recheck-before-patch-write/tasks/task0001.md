# Task Plan: task0001 — Rework section 10: return-time recheck before the patch write, with an order probe

## Goal

In the "Return-time digest" paragraph of rework section 10, the return-time
recheck sits after step 3's validation and before step 3's application of the
rework patch. The paragraph states that the patch is applied only after a
passing recheck, so a stale result leaves no workflow.yaml write and no commit
from the patch. A regression probe in the existing dispatch-site test file pins
this order.

## Design

### Document change (FR1, FR2, FR3)

The paragraph stays one blank-line-delimited block in section 10, under the
same bold label. Its statements come in this order:

1. Unchanged opening: the `dispatch_digest_inputs` sentence, then the sentence
   in which the orchestrator, after the scope verification (layer 4) passes,
   recomputes the current digest_source and runs `scripts/self-write-digest.py`
   (operation `identify_and_substitute`), citing Rule R1.
2. Step 3's validation. The sentence still begins with "Step 3 validates" and
   validates the patch against the digest_source the script returned. It names
   the validation as application rules 1-14 of `references/workflow-patch.md`.
   It keeps rule 1's comparison of the substituted digest_source with the
   dispatch-time `input_digest`, and keeps "a mismatch, or a script exit other
   than `0`, makes the result stale". It no longer says that step 3 applies
   the patch.
3. The return-time recheck sentence, in its current form. The orchestrator is
   the actor. The sentence cites `references/contracts/worker-envelope.md`,
   Rule R1, "Recomputation and comparison timing", and states that a recheck
   mismatch, or a recheck that cannot run, makes the result stale. It still
   runs before the recording phase-state write. It may also say that it runs
   before step 3's application. It stays one sentence (the existing probe
   reads the first sentence that names the recheck). It states nothing about
   what the recheck compares, the membership matrix or the substitution.
4. Step 3's application, stated after the recheck sentence. The patch is
   applied only after a passing recheck. The application is the rule 15 single
   Write to workflow.yaml and the rule 16 R2 commit sequence. A stale result
   (from the rule 1 comparison, the script exit or the recheck) reaches no
   workflow.yaml write and no commit made by the patch.
5. The unchanged recording sentence: the orchestrator records `self_write_set`
   in the same phase-state write as the `Layer 5 recording` of
   `written_artifacts` into `phase-state/rework.yaml`.

The paragraph does not set an order between statement 4 and statement 5 beyond
"both follow a passing recheck" (SPEC.md, Unchanged Documents).

Existing suites that must keep passing unchanged (NFR3) read this paragraph.
The wording must therefore keep these facts:
- The paragraph contains `dispatch_digest_inputs`, `phase-state/rework.yaml`,
  `identify_and_substitute` and "orchestrator". The order "scope verification"
  -> `scripts/self-write-digest.py` -> "Step 3 validates" -> the recheck holds.
- After the script token, one sentence names both "rule 1" and "substituted
  digest_source", and one sentence names both "stale" and "exit".
- The first mention of `self_write_set` and of `Layer 5 recording` comes after
  the recheck. Their sentence keeps "same phase-state write" and
  `phase-state/rework.yaml`.
- No wording that the existing no-restatement probes catch is added. No
  sentence says that Layer 5 `Calculation` runs after the recheck.

Outside the paragraph, section 10 does not change:
- the numbered steps 1-4 of review-sourced rework, including step 3's "The
  orchestrator validates and applies rework-planner's patch", which an existing
  test pins;
- the "Verify-sourced rework" sentence;
- the "Dispatch input (step 2, all four routes)" paragraph;
- the SPEC-change list.
The recheck is stated inside the paragraph, not as a new numbered step (FR3).

### Order probe (FR4, NFR2)

The probe is a new check in the existing test file. It has the same shape as
the existing recheck probe: it takes paragraph text and returns a list of
defect strings with a leading code, and an empty list means the order is right.
It works on whitespace-removed, lowercased text and compares first positions
of tokens, like the file's existing helpers. It reports a defect when:
- the "return-time recheck" token is missing;
- the recheck does not come after the step 3 validation token ("step 3
  validates");
- the recheck does not come after the end of the rule-1 compare/stale sentence
  (the rework site's existing stale tokens);
- no application token is present;
- any application token comes before the recheck.

The application tokens are one named set. It covers:
- the verb wording with which the base-revision paragraph says step 3 applies
  the patch ("validates and applies");
- the rule 15 write to workflow.yaml;
- the rule 16 commits.
No application token may match the validation wording ("application rule 1",
"application rules 1-14"). Otherwise the real paragraph would fire.

A second check covers the statement-4 content (AC-2). After the recheck
sentence, one sentence states that the patch is applied only after a passing
recheck, and names the workflow.yaml write and the commit.

Forged controls, each held as module-level text or derived from the real
paragraph:
- The base-revision paragraph: the "Return-time digest" paragraph exactly as it
  stands in the integration worktree before this task's edit, which is this
  feature's base. Its recheck follows "Step 3 validates and applies". It is
  copied verbatim into the test file before the document is edited.
- The real paragraph with the statement-4 sentence moved before the recheck
  sentence.
- The real paragraph with the statement-4 sentence removed.

do not change.
