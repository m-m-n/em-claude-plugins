# Task Plan: task0003 — Negative proofs for the eight unproven matchers in the recycled-task-id document-contract module

## Provenance

- **source**: verify
- **source_ids**: TS-14, SC-6
- **review_round**: not applicable (verify-sourced rework)

Verify found that `tests/test_recycled_task_id_consistency.py` carries
negative proofs for only four of its matchers (the journal-only phrasing, the
"never read workflow.yaml" claim, the missing precondition, and the
`rework`/`append` tokens). Eight matchers that assert NEW post-change wording

asserts NEW post-change wording a negative-proof test showing it does not
match the corresponding captured pre-change wording, so TS-14's inventory is
complete and SC-6 holds.

## Design

### The gap, stated exactly

A matcher that asserts text the change ADDED needs a proof that the same
matcher does NOT match the document as it read before the change — otherwise
the assertion could be satisfied by wording that never changed, and it would
still pass on a document where the requirement was never implemented. Eight
such matchers currently have no proof:

| Group | Test | Matcher asserts |
|---|---|---|
| AC-1 (FR1) | `test_reconciled_state_phrasing_present` | the step-1 reconciled-state write-back phrasing |
| AC-4 (FR4) | `test_inapplicable_branch_states_implement_stays_failed` | the INAPPLICABLE marker and "`implement` stays `failed`" |
| AC-4 (FR4) | `test_inapplicable_branch_cites_stop_condition_3_and_abort_phase` | the INAPPLICABLE-anchored slice cites stop condition 3 and the "abort phase" terminal |
| AC-4 (FR4) | `test_inapplicable_branch_names_no_partial_write` | the two no-partial-write phrases |
| AC-5 (FR5) | `test_unreachability_sentence_present` | the unreachability sentence anchor and its three tokens |
| AC-6 (FR6) | `test_scope_sentence_names_all_four_hooks` | all four hook filenames together |
| AC-6 (FR6) | `test_scope_sentence_states_status_never_consulted` | the "never consult `tasks.{T}.status`" claim |
| AC-6 (FR6) | `test_scope_sentence_governs_only_orchestrator_interpretation` | the orchestrator-only scope claim |

The four matchers that already have proofs
(`TestValidationDetectsRegressions`) are unaffected and stay as they are.

### Contract 1 — one literal, two users

Each of the eight matchers' literals becomes a module-level constant. Both
the existing positive test and its new negative-proof test reference that same
constant. Duplicating the literal in the negative proof is what would let the
two drift apart, at which point the proof stops proving anything about the
matcher that actually runs. Rewriting the positive tests to read the constants
is a mechanical substitution: their assertion behaviour is unchanged.

### Contract 2 — pre-change samples are captured, not invented

Each of the four groups gets one module-level pre-change sample constant, a
verbatim excerpt of the corresponding section of
`em-workflow/references/implement-phase.md` as it read at the implement
phase's base commit `b73c6e69e4ee81519d0e6f7f8f6a03ec06b5db24`. The samples
are read from that revision as reference material; they are not paraphrased
and not reconstructed from the requirements. Each sample is long enough to
contain the sentence(s) the matcher targets in their pre-change form:

| Sample | Covers | Excerpt scope |
|---|---|---|
| pre-change I.2.b step 3 | AC-1 group | the write-back sentence including its `merged` half and its report clause |
| pre-change I.2.c route-back bullet | AC-4 group | the bullet from its opening gate sentence through the ordered write set |
| pre-change I.2.a recycled-task-id paragraph | AC-5 group | the paragraph from the normative statement through the retained in-flight sentence |
| pre-change I.2.a hook parenthetical | AC-6 group | the same paragraph, which already named `queue_launch_guard.py` before the change |

### Contract 3 — samples are normalized the same way the matcher runs

Every positive matcher in this module runs against a whitespace-normalized
section. Each negative proof therefore applies the module's own
whitespace-normalizing helper to its sample before asserting, so the proof
exercises the same comparison the positive test does. A proof that compares
against raw text while the matcher compares against normalized text does not
constrain the matcher.

### Contract 4 — a sample must not be vacuously non-matching

`assertNotIn(X, "")` passes for every X. Each sample therefore also carries a
RETAINED anchor: a phrase that is present both in the sample and in the
post-change document, asserted positively in a guard test. A sample that was
emptied, truncated past the relevant sentence, or replaced with unrelated text
fails its guard, so a negative proof cannot silently degrade into a tautology.

Retained anchors available per group: the `merged` half of the write-back
sentence (AC-1), "no task has status `merged`" (AC-4), "A task whose journal
last event is `launched` is always in-flight" (AC-5), and
`` `queue_launch_guard.py` `` (AC-6).

### Group-specific proof shapes

Three of the eight matchers are not plain substring checks, so their proofs
take the shape the matcher itself has:

- `test_inapplicable_branch_cites_stop_condition_3_and_abort_phase` slices the
  section from the INAPPLICABLE marker. Its proof shows the marker is absent
  from the pre-change I.2.c sample, so the slice cannot be taken at all — and
  therefore that the surviving mention of "abort phase" in the pre-change text
  could not satisfy the matcher.
- `test_unreachability_sentence_present` slices from an opening anchor to a
  closing anchor and then checks three tokens that also occur elsewhere in the
  pre-change paragraph. Its proof shows the opening anchor is absent from the
  pre-change I.2.a sample, so the presence of `launched` / `pending` /
  `replace_all` elsewhere in that paragraph cannot satisfy it.
- `test_scope_sentence_names_all_four_hooks` is a conjunction over four names,
  one of which (`queue_launch_guard.py`) the pre-change paragraph ALREADY
  contained. Its proof shows the conjunction fails on the pre-change sample by
  naming the hooks that are absent from it, rather than asserting that all
  four are absent.

### What this task deliberately does not change

The four matchers that assert RETAINED pre-change wording
(`test_merged_half_unchanged`, `test_report_failed_or_malformed_clause_survives`,
`test_retained_in_flight_sentence_survives`, `test_existing_merged_gate_survives`)
and the regression guards (TS-7 .. TS-10) are not new-wording matchers: the
pre-change document satisfies them by construction, and TS-14's finding does
not name them. Their assertions stay exactly as they are.

## Test Notes

- Every criterion is verified by the same single project command,
  `python3 -m unittest discover -s tests`, run from the repository root. There
  is no build, format or E2E command.
- TDD order that produces a real red: add each negative-proof test BEFORE
  extracting the constant it uses, writing it against the pre-change sample
  first; it fails at import/name resolution until the constant exists, then
  passes once the constant is the one the positive matcher also uses. Wiring
  the positive test to the constant last is what proves the two share it.
- The guard tests of AC-2 are the ones that would catch the classic failure of
  this task: a sample trimmed until it no longer contains the pre-change
  sentence, which makes every `assertNotIn` against it pass for the wrong
  reason.
- The pre-change I.2.c sample necessarily contains no `rework` / `append`
  tokens beyond what the existing negative proof already embeds; embedding
  sample text in this module never affects the assertions that run over
  `implement-phase.md`, which read that file rather than this one.
- Do not import from any pre-existing module to obtain a sample. Copy the
  excerpt into this module as its own constant, the same way TS-9's
  byte-identity literal was copied.
