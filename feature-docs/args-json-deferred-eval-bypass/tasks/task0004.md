# Task Plan: task0004 — One classification for compound-assignment element subscripts

## Goal

A compound-assignment element `[subscript]=value` keeps the notion-pair
exclusion only when its subscript is digits only, in both the expansion-level
reading and the command-level reading of the per-chunk scan. An `@` or `*`
element subscript reads as uncertain in both, and the unit tests pin that
classification instead of the opposite one.

## Design

### The classification

The verify round found the two readings disagreeing on an element subscript of
`@` or `*`:

- The expansion-level reading (the array-subscript region of a compound
  assignment's element, read by the region reading of
  `_args_json_regions_defer_evaluation()`) keeps the exclusion only for a
  subscript of digits only. This matches IMPLEMENTATION.md D3 and SPEC.md A4:
  only digit-only array subscripts, and compound assignments without
  subscripts, keep the exclusion; the `@` / `*` exemption of D3 is that of a
  parameter expansion's subscript.
- The command-level reading of an element (the leading-subscript case of
  `_args_json_variable_subscript()`, called for the words of an array
  literal) and the unit test `test_the_words_of_a_compound_assignment_are_no_command`
  treat `@` and `*` as harmless, so the subtest `A=([@]=1 [12]=2)` expects
  KIND_NOTHING while the chunk reads as uncertain.

The classification this task settles: an element subscript keeps the exclusion
only when it is digits only. An element subscript of `@` or `*` is uncertain
(the fail-safe side; Bash rejects it as an indexed-array element subscript, so
it is not a form a legitimate command needs).

- The expansion-level reading is unchanged.
- The leading-subscript case of `_args_json_variable_subscript()` (an element
  `[sub]=value` of a compound assignment) reports a subscript as variable
  unless it is digits only. Its non-leading case (any subscript in the
  restored text of a declaration-builtin argument) is unchanged: digits only,
  `@` and `*` stay harmless there.
- The helper's docstring states the two cases separately.
- No other function changes. The fd-variable redirection reading
  (`{name[subscript]}`) keeps its own `@` / `*` treatment.

### Unit tests

- In `test_the_words_of_a_compound_assignment_are_no_command`, the subtest
  `A=([@]=1 [12]=2)` is replaced by `A=([0]=1 [12]=2)` (every element
  subscript digits only), still expected not uncertain.
- In `test_a_subscript_element_of_a_compound_assignment_is_uncertain`, the
  forms `A=([@]=1)`, `A=([*]=1)` and `A=(x [@]=1)` are added, expected
  uncertain. The docstring's "not digits only, `@` or `*`" wording becomes
  "not digits only".
- A new test pins the command-level helper directly: its leading case reports
  `[@]=1` and `[*]=1` as variable and `[12]=2` as not; its non-leading case
  reports `a[@]`, `a[*]` and `a[3]` as not variable and `a[i]` as variable.
- A new test pins the notion-call kind: after `A=([@]=1)` the call with
  `--format "$r"` is inspected; after `A=([0]=1 [12]=2)` the call with
  `--session "$SID"` keeps KIND_NOTHING.

### Case table entries (appended at the end of the array)

Every entry follows IMPLEMENTATION.md Conventions (label prefix
`args-json-deferred-eval-bypass` followed by `TS-18`, the notion call, `rule`
`git-branch-force-delete` on deny, `--session "$SID"` on allow).

- TS-18 deny: `A=([@]=1)`, `A=([*]=1)` and `A=(x [@]=1)`, each before the
  notion call with `--format "$r"`.
- TS-18 allow: `A=([0]=1 [12]=2)` before the notion call with
  `--session "$SID"`.
