# Task Plan: task0001 — Expansion-level deferred-evaluation detection

## Goal

A chunk holding an expansion that re-evaluates a value as code in the current
shell reads as shell-state-uncertain, wherever the lexer reads it as syntax
and also in the body of an unquoted-delimiter heredoc, so the notion-pair
exclusion is dropped and `--args-json` is inspected. A construct that only
stands in a data position or inside a subshell body leaves the exclusion as it
is.

## Requirements

## Design

### Constructs the expansion level counts

The predicate reads the lexer's map of the chunk text. A region is counted
when it is one of the following:

| Construct | Lexer reading | Counted when |
|---|---|---|
| Arithmetic expansion `$((...))` | an `arithmetic-expansion` region | always |
| Bracket arithmetic `$[...]` | a `bracket-arithmetic` region | always |
| Subscript of an assignment word (`a[...]=`) or of a compound-assignment element (`([...]=v)`) | an `array-subscript` region | its content is not made of digits only (it uses a `$` expansion, a name or any other expression) |
| Subscript inside a parameter expansion (`${a[...]}`, `${#a[...]}`, `${a[...]:-x}`, ...) | the text of a `parameter-expansion` region | the subscript that follows the parameter name is not digits only, `@` or `*` |
| `@P` transformation (`${x@P}`, `${a[0]@P}`) | the text of a `parameter-expansion` region | the transformation operator is `@P` |
| Indirect expansion `${!x}` (key and prefix lists included) | the text of a `parameter-expansion` region | the text starts with the `!` form |
| Assigning expansion `${x=...}`, `${x:=...}` | the text of a `parameter-expansion` region | always, whatever the name (it may name an integer-attribute variable or `PS4`) |
| Substring expansion `${x:offset}`, `${x:offset:length}` | the text of a `parameter-expansion` region | the offset or the length is not a plain digit string (an optional sign and blanks allowed); the `:-`, `:=`, `:?` and `:+` operators are not substrings |

The last two rows are counted for the same reason as the enumerated FR1
constructs: Bash re-evaluates the value as arithmetic, or assigns it
(IMPLEMENTATION.md, Open Questions).

Nested regions are read as well: a parameter expansion inside another, an
arithmetic expansion inside a parameter expansion's operand, any of them
inside double quotes, inside a here-string word, inside a function body, a
`{ }` group, a conditional or a loop of the chunk.

### Positions that are not read

- A region that has a `command-substitution`, `backtick-substitution` or
  `process-substitution` region around it (IMPLEMENTATION.md D2). A region
  under a `brace-command-substitution` region is read.
- Single quotes, ANSI-C quotes and comments: the lexer gives no region inside
  them, so nothing there is counted (IMPLEMENTATION.md D3).
- A digit-only subscript, an `@` / `*` subscript and a compound assignment
  without subscripts are not counted (D3, A4).

### Heredoc bodies

The chunk text the per-chunk scan reads has its heredoc bodies removed. The
removal step already marks the stripped text (the stripped-text marker type
`_ChunkLinks.register()` reads) when an unquoted-delimiter body holds a
current-shell substitution opener. The mark is widened: an unquoted-delimiter
body that holds a counted construct is marked too.

- The body is read as the shell expands it: the lexer's `heredoc-body` mode,
  in which quote characters and a bare `((` are literal and the `$` expansions
  are recognized. The same counting rules apply to its regions, subshell
  bodies left out.
- A quoted-delimiter body is not read (A3).
- A body the lexer cannot settle (its work bound exceeded, or any other lexing
  failure) reads as marked. No exception leaves the removal step: it serves
  every command the hook judges, not only the `--args-json` step.
- The existing opener check stays, line continuations removed as today.
- The marker type, the predicate and `_ChunkLinks.register()` may keep their
  names; their docstrings state the widened meaning. A rename updates every
  reference.

### Contract of the expansion-level predicate

- Pre: the marked text of one chunk (its source, the text the lexer reads).
- Post: true when a counted construct stands at a read position, and true when
  the lexer cannot settle the text; false otherwise. It reads nothing but the
  text, executes and evaluates nothing (NFR1) and raises nothing.
- Called only from `_args_json_nameref_scan()`, so its result is cached with
  the per-chunk answer (NFR2). It reuses the lexer's map of the same text that
  the literal check already asks for, rather than adding a separate reading
  with a different mode or body flag.

### Per-chunk scan flow (`_args_json_nameref_scan()`)

1. No chunk, or no top regions: uncertain (unchanged).
2. The round-3 literal / brace substitution check (`_args_json_has_brace_substitution()`, FR4): uncertain when it holds. Its body is not changed.
3. The expansion-level predicate: uncertain when it holds.
4. The lexed statements: a statement the lexer could not read is uncertain (unchanged); every simple command goes through `_args_json_declares_nameref()` (IMPLEMENTATION.md Shared Components).
5. Otherwise certain.

The docstring of `_args_json_nameref_scan()` is rewritten to state these
sources, referring to `_args_json_declares_nameref()` for the command-name
rules (IMPLEMENTATION.md Conventions).

### Case table entries (appended at the end of the array)

Every entry follows IMPLEMENTATION.md Conventions (label prefix, the notion
call, `rule` on deny). Preceding forms use `echo` (or `:`) as the command
that carries the construct, so that each entry would keep the exclusion
without its construct.

- TS-1: `p=$'$\x7b declare -gn r=A[@]; }'` then `: "${p@P}"` before the call: deny.
- TS-4 (expansion level): one deny entry per row of the table above, the
  enumerated FR1 rows first (arithmetic expansion, bracket arithmetic,
  assignment-word subscript, compound-element subscript, parameter-expansion
  subscript with a `$` expansion and with a name, `@P`, indirect expansion);
  plus one deny entry per position for at least the arithmetic expansion and
  `@P`: inside a function body, a `{ }` group, an `if` body, a `while` body,
  double quotes, the body of an unquoted-delimiter heredoc, a here-string.
- TS-9: `echo $( ... )` whose body holds an arithmetic command, an arithmetic
  expansion and `${p@P}`, then the call with `--session "$SID"`: allow. The
  same with a backtick substitution and a process substitution: allow.
- TS-11: allow entries with `--session "$SID"` after
  `echo '(( a )) $((a)) ${p@P} ${!x}'`, after an `echo` with a
  quoted-delimiter heredoc whose body holds `$(( a ))` and `${p@P}`, after
  `echo "${A[0]}" "${A[@]}" "${A[*]}"`, and after a compound assignment
  without subscripts.
- TS-12: `echo "${s:p}"` and `echo "${s:0:n}"` before the call: deny;
  `echo "${s:1:2}"` before the call with `--session "$SID"`: allow.

### Unit tests (new class directly before the module's main guard)

- For each counted construct and each position above: the per-chunk scan of
  the chunk reads true, and the notion call's kind is inspected.
- For each control form of TS-9 and TS-11, and the digit-offset form of
  TS-12: the per-chunk scan reads false (its other sources quiet) and the
  notion call keeps KIND_NOTHING.
- Heredoc bodies: an unquoted-delimiter body with a counted construct marks
  the chunk; the same body under a quoted delimiter does not.
- NFR1: with the lexer made to fail for the chunk text, the predicate reads
  true; with it made to fail for an unquoted body, the removal step returns a
  marked text and raises nothing.
- NFR2: asking the per-chunk answer of the same chunk twice runs the
  expansion-level reading once.
