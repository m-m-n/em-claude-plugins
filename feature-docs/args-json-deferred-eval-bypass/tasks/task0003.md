# Task Plan: task0003 — Syntax read from source text: subscripted fd-variable redirections and escaped conditional brackets

## Goal

The per-chunk scan reads two pieces of shell syntax from the token's source
text instead of its quote-removed text: a `{name[subscript]}` word that Bash
takes as the variable of a redirection (and whose subscript it evaluates as
arithmetic in the current shell), and the `[[` opener and `]]` closer of a
conditional (which a backslash-escaped or quoted bracket never forms). Each
makes the chunk shell-state-uncertain where Bash may evaluate a value, so the
notion-pair exclusion is dropped and `--args-json` is inspected.

### Reading 1: subscripted fd-variable redirection (finding `9a42fe083737c591`)

Bash takes a word as the variable of a redirection when the word starts with
`{`, ends with `}` and is directly followed, with no blank between, by a
redirection operator that starts with `<` or `>` (`>`, `>>`, `<`, `<>`, `>&`,
`<&`, `>|`, a heredoc operator, `<<<`). When the text between the braces is
`name[subscript]`, Bash assigns the file-descriptor number to that array
element and evaluates the subscript as arithmetic in the current shell.

- The chunk is uncertain when such a word stands at a read position of the
  chunk and its subscript, read from the word's source text, is anything other
  than digits only, `@` or `*`: a name, a `$` expansion, an expression, a
  quoted subscript, or a subscript that cannot be read.
- This holds whatever command carries the redirection: an allowlisted name
  (`:`, `echo`, `mcp-bridge`), a closing reserved word of a compound command
  (`done`, `fi`, `}`), or a command with no command name.
- Not counted: `{name}` without a subscript (handled as today), a digit-only,
  `@` or `*` subscript (IMPLEMENTATION.md D3), a `{...}` word separated from
  the operator by a blank (it is an argument word), and the same text inside
  single quotes, ANSI-C quotes, a comment or a quoted-delimiter heredoc body.
- A word inside a command substitution, backtick substitution or process
  substitution body belongs to that inner chunk (IMPLEMENTATION.md D2).

### Reading 2: the conditional's brackets (finding `8016dc2435c250f7`)

The per-chunk scan reads a `[[ ]]` conditional across the fragments its `&&`,
`||` and parentheses produce. The opener and the closer are judged from each
token's source text:

- An opener is a command-position word whose source text is exactly `[[`. A
  command word whose quote-removed text is `[[` but whose source holds a
  backslash or a quote (`\[\[`, `\[[`, `"[["`, `'[['`) opens no conditional:
  Bash runs it as an ordinary command name, which is not on the allowlist, so
  that command is uncertain.
- A closer is a word whose source text is exactly `]]`. A word whose
  quote-removed text is `]]` but whose source holds a backslash or a quote
  (`\]\]`, `\]]`, `]\]`, `"]]"`, `"]"]`, `']]'`, `$']]'`) is an operand: the
  conditional stays open and its later fragments are read as the conditional's
  words.
- A conditional that reaches the end of the chunk without a closer leaves the
  chunk uncertain. A `;` or a lone `&` reached while the conditional is open
  (Bash accepts neither inside `[[ ]]`) leaves the chunk uncertain as well, so
  a misread closer never lets the conditional reading swallow the statements
  after it.
- A closer written with a line continuation between its brackets (`]`,
  backslash, newline, `]`) is a closer to Bash. The implementation reads it as
  a closer, or reads the chunk as uncertain; it never reads the statements
  after it as words of the conditional.

### Case table entries (appended at the end of the array)

Every entry follows IMPLEMENTATION.md Conventions (label prefix

- TS-16 deny: the finding's form, an `x` assigned an ANSI-C value that hides
  the opening brace of a current-shell substitution in a subscript, then
  `: {a[x]}>/dev/null`; `: {a[x]}` directly followed by each of `>`, `>>`,
  `<` and `<>` with the target `/dev/null`, by `>&-`, and by `<<<` with a
  plain word; `echo {a[$i]}>/dev/null`; `: {a[i+1]}>/dev/null`;
  `: {a["x"]}>/dev/null`; `while false; do :; done {a[x]}>/dev/null`; a
  command with no command name, `{a[x]}>/dev/null`.
- TS-16 allow: `: {fd}>/dev/null`, `: {a[12]}>/dev/null`, `: {a[@]}>/dev/null`,
  `echo {a[x]} >/dev/null` (blank before the operator), `echo '{a[x]}>/dev/null'`.
- TS-17 deny: `[[ \]\] == x && true -eq 0 ]]`; `[[ a == \]\] || true -eq 0 ]]`;
  the same with `\]]`, `]\]`, `"]"]` and `$']]'` in place of `\]\]`;
  `\[\[ a == b ]]`; `"[[" a == b ]]`; an unclosed conditional
  `[[ a == \]\]; echo ok`; a closer split by a line continuation,
  `[[ a == b ]`, backslash, newline, `]; read x; [[ c == d ]]`.
- TS-17 allow: `[[ \]\] == x ]]`; `[[ a == "]]" ]]`; `[[ a == b ]] && echo ok`.

## Test Notes

- AC-1 to AC-6 are case-table entries with unit counterparts; AC-7 runs both
  suites.
- Write each command as JSON text: escape backslashes, the ANSI-C value, the
  newline of the line-continuation form and the quotes as the existing
  round-3 entries do. Check that the JSON-decoded command holds the intended
  backslashes (`\]\]` is two backslashes in the decoded text, one before each
  bracket).
- A preceding form must not also contain a current-shell substitution opener
  (`${` followed by whitespace or `|`) in its literal text, or the literal
  check, not this task's reading, decides the entry.
- When an entry's decision comes from a rule other than
  `git-branch-force-delete`, the preceding form is changed, not the expected
  rule.
- The implementer may confirm once, with Bash and a harmless value, that a
  `{a[expr]}>/dev/null` redirection on `:` evaluates `expr` in the current
  shell (for example, an expression that assigns a scratch variable). The
  observation goes into the completion report; the acceptance criteria do not
  depend on it, and the tests never run Bash.
