# Task Plan: task0002 — Canonicalize worktree_path at the producer and state the assumption in the implementer procedures

## Goal

implement-phase.md hands each implementer a worktree_path that is the strict
realpath of `$WT_ROOT/{T}`, and derives tests_yaml_path from that value. The
implementer's procedures state that the cd target is that worktree_path,
used as supplied, and that it is assumed to be a canonical absolute path.

## Requirements

FR7, FR8, NFR1

## Scope

### Files to Create
- `tests/test_canonical_worktree_path_docs.py` — document tests for the producer statement (TS10) and the implementer procedure statement (TS12)

### Files to Modify
- `em-workflow/references/implement-phase.md` — Step I.2.a: the canonicalization step and the worktree_path and tests_yaml_path placeholders of the assignment payload
- `em-workflow/agents/implementer.md` — Inputs and Step 3: the cd target is worktree_path as supplied, assumed canonical
- `em-workflow/skills/worktree-task-workflow/SKILL.md` — the cd prefix statement in the command execution gate: the same assumption

## Design

This task owns the producer and consumer-procedure side of the Canonical
worktree path contract (IMPLEMENTATION.md Shared Components, D2). It cites
the Path-condition statement and does not restate it (D1).

### Producer: implement-phase.md, Step I.2.a

- Applies once task T's worktree exists, whether `git worktree add` just
  created it or the Resume guard reused it. The orchestrator then resolves
  `$WT_ROOT/{T}` with a strict realpath (every component must exist, links
  resolved).
- The resolved value is the task's worktree_path. This is the canonical
  absolute path in the IMPLEMENTATION.md sense.
- The text gives no fallback to the unresolved string.
- Assignment payload:
  - the `worktree_path:` placeholder names the canonical value;
  - the `tests_yaml_path:` placeholder is built from the canonical
    worktree_path followed by `test-docs/{feature}/{T}.tests.yaml`, so it
    stays below worktree_path;
  - the paragraph on `tests_yaml_path` states that derivation.
- Kept as they are:
  - the payload's line order, its header line, `task_id` and
    `worktree_path` as the first two lines, and the `Untrusted data` section
    with its five data lines;
  - the order of the existing Step I.2.a anchors. Place the new step with
    the worktree creation and the Resume guard, before the approval-gate
    paragraph;
  - every other use of `$WT_ROOT/{T}`: worktree add and remove, the Resume
    guard's existence check, and the stale-launched `--task-worktree`
    evidence input.
- The step refers to the Verbatim execution rule of
  `references/command-execution-protocol.md` as the reason for the canonical
  form. It does not restate the path conditions.

### Consumer procedures

- `agents/implementer.md`:
  - the `worktree_path` entry of the Inputs list says it is a canonical
    absolute path;
  - Step 3, where the single-call `cd "{worktree_path}" && <command>` form is
    described, says that the cd target is worktree_path exactly as supplied:
    not rewritten, normalized or resolved.
- `skills/worktree-task-workflow/SKILL.md`: the command execution gate
  bullet that names `cd "{worktree_path}" &&` as the only prefix states the
  same two points.
- Neither document gains a runtime check of worktree_path (REQUIREMENTS.md
  as-2), and neither restates the hook's path conditions. They cite the
  Verbatim execution rule.

## Test Notes

- Everything here is a document test, following the document-test
  convention of IMPLEMENTATION.md: slice by heading (Step I.2.a, Inputs,
  Step 3, the command execution gate), normalize whitespace, match stable
  phrases, and pair each absence check with a forged-text case.
- For AC-2, the pre-change placeholders serve as the negative sample. They
  are `{absolute path to $WT_ROOT/{T}}` and
  `{absolute path to $WT_ROOT/{T}/test-docs/{feature}/{T}.tests.yaml}`.
- For AC-4, the "no restatement" check looks for the path-condition wording
  (for example "strictly below" together with "realpath" and "existing
  directory" in one sentence) in the changed paragraphs. Use a forged-text
  case.
- Existing modules that constrain the wording and must keep passing:
  - `tests/test_assignment_payload_untrusted_section.py`: payload structure,
    field order, `worktree_path` as the second line, and no ordering anchor
    in the text adjacent to the block;
  - `tests/test_prelaunch_inprogress_launch_order.py` and
    `tests/test_prelaunch_failed_launch_state.py`: the order of the Step
    I.2.a anchors;
  - `tests/test_exit4_tip_argument_consistency.py`;
  - `tests/test_stale_launched_missing_artifacts_doc_contract.py`: the
    `--task-worktree` statement with `$WT_ROOT/{T}` stays as it is;
  - `tests/test_implementer_cd_chain_docs.py`, which rules out these
    patterns in Step 3 and in the gate and contract sections: a sentence
    with both "separate" and "cd"; a sentence with "chain", "&&" and a
    prohibition word; "may reset"; and, in the gate section, "byte" outside
    "(byte-for-byte)", "identical to" and "equal to the line".
- Red phase: AC-1 to AC-3 are red against the current documents, which
  carry none of these statements.
