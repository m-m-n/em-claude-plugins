# Task Plan: task0001 — Stop-hook recycled-task-id carve-out

## Goal

The implement-phase Stop hook classifies a task whose journal last event is
`failed` but whose workflow status reads `pending` as unlaunched, so the
refill net fires again on features that went through a route-back re-plan,
while every genuine failure keeps suppressing the block exactly as today.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR7, FR8, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None. Both files below already exist.

### Files to Modify

- `em-workflow/hooks/queue_stop_guard.py` — add the per-task status read and the classification branch it discriminates; everything upstream and downstream of the classification stays as it is
- `tests/test_queue_stop_guard.py` — give the fixture builder a per-task status option that leaves existing call sites working, and add the scenarios below

## Design

### Where the change lands

The feature evaluator already gates on the `implement` step being in
progress, collects the task ids declared under the `tasks:` mapping, and
reduces the journal to one last event per task. The only behavioural change
is in the branch that handles a `failed` last event; free-slot arithmetic,
the ascending bounded launch list, the stderr messages, the fingerprint and
the sidecar cap are downstream of it and are untouched.

### Per-task status read (contract)

- **Input**: the path of a feature's workflow.yaml.
- **Output**: for each task id declared under the `tasks:` mapping, either a
  determined status string or the explicit absence of one.
- **Precondition**: none — an unreadable or malformed file yields "no status
  determined" for every task rather than an error.
- **Postcondition**: a value is attributed to a task id only when it comes
  from a status key inside that id's own block. A status line belonging to a
  workflow step, or to any other mapping, is never attributed to a task, and
  a task's status is never mistaken for a step's.
- **Technique constraint**: one line-based pass, standard library only, in
  the same family as the existing step-status and task-id readers. No YAML
  library, no extra subprocess, no extra filesystem scan.

### Classification

| Journal last event | Per-task workflow status | Classification |
|---|---|---|
| none recorded | any | unlaunched |
| `launched` | any | in-flight |
| `merged` | any | terminal, not tracked |
| `failed` | exactly `pending` | unlaunched |
| `failed` | `failed` / `in_progress` / `merged` / any unrecognized value | failed → whole-feature suppression |
| `failed` | status key absent, or block status undeterminable | failed → whole-feature suppression |
| any | task id not declared under `tasks:` | not evaluated at all |

Whole-feature suppression keeps its current meaning: the evaluator reports
nothing actionable for that feature and the hook exits 0. See
IMPLEMENTATION.md D1 and D2 for the rationale and the shared contract.

### Test-side change

The fixture builder currently writes a fixed `pending` status for every
task. It gains a way to specify a status per task id; call sites that do not
specify one keep producing exactly the workflow.yaml text they produce today,
so no existing test changes behaviour. Fixtures must keep containing both
workflow-step status lines and per-task status lines, since that co-existence
is what the scoping postcondition above is asserted against.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR4): with the implement step in progress, three declared
      tasks all at status `pending`, and a journal whose only record is a
      `failed` event for the first task, the hook exits 2 and its stderr
      names all three task ids, in ascending order, in the existing BLOCK
      message format.
- [ ] AC-2 (FR2): with the same shape, the hook exits 0 whenever the task
      carrying the `failed` last event has a workflow status of `failed`, of
      `in_progress`, of `merged`, an unrecognized value, no status key at
      all, or an undeterminable task block — and also when a retired-id task
      and a genuinely failed task are both present.
- [ ] AC-3 (FR3): a status value is attributed to a task only from that
      task's own block. A fixture whose workflow steps and whose tasks both
      carry status lines classifies exactly as the table above predicts, and
      the read introduces no YAML-library import, no additional subprocess
      and no additional filesystem scan.
- [ ] AC-4 (FR4, FR5): a reclassified task participates normally in
      free-slot arithmetic against the parallel-implementer limit, in the
      ascending bounded launch list, and in the fingerprint that drives the
      consecutive-block cap and its sidecar; a `failed`-then-`launched`
      journal history still counts as in-flight; a task id absent from the
      `tasks:` mapping is still ignored entirely; the sidecar's field set,
      the BLOCK and WARNING strings and the cap semantics are unchanged.
- [ ] AC-5 (NFR1, NFR2, NFR3, NFR4): the fail-open sweep still passes — a
      missing journal directory, a malformed journal line, malformed stdin, a
      missing feature-docs directory and an undeterminable per-task status
      each exit 0 with no traceback; the hook still imports only standard
      library modules; it still writes nothing but its existing sidecar; and
      it still performs one line-based pass per file.
- [ ] AC-6 (FR8): the test module covers the retired-id case, the genuine
      failure cases, the mixed case, the free-slot/bounded-list case, the
      relaunched case, the undeterminable-status case, the absent-id case and
      the cap case, and its fixture builder accepts a per-task status without
      any existing call site changing the workflow.yaml text it produces.
- [ ] AC-7 (FR7): the other three queue hooks and every test module outside
      this task's two files are byte-unchanged, and
      `python3 -m unittest discover -s tests` passes from the repository root.
