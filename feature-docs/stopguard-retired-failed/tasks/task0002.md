## Goal

consults a task's workflow status, and both plugin registries carry the
bumped patch version, so the shipped documentation and plugin metadata match
the hook this feature changes.

## Design

### The hook-scope sentence (section I.2.a)

Today the sentence names all four queue hooks together and states that they
derive a task's state from the journal's last event alone and never consult
the per-task workflow status. After the amendment it must convey three
things at once:

1. the Stop hook is an explicit exception that applies the same
   recycled-task-id carve-out the surrounding section defines for the
   orchestrator;
2. the remaining three hooks are still journal-last-event-only and still
   never consult the per-task status;
3. the recycled-task-id rule itself is otherwise unchanged in meaning — this
   is a scope correction, not a new rule.

### Retention constraints (IMPLEMENTATION.md D3)

Test modules outside this feature's declared change set assert literal
phrases in this document and use one of its headings as a section boundary.
Those modules must not be edited, so the amendment is additive with respect
to the literals listed in IMPLEMENTATION.md D3: the four hook filenames, the
never-consult phrase (now predicated of the other three hooks), the
orchestrator-scope phrase, the sentence scoping the carve-out to `failed`
only, the retained in-flight sentence, the supporting-cast heading text, and
the absence anywhere in the document of a claim that a hook never reads
workflow.yaml.

### The supporting-cast Stop-hook bullet

That bullet currently describes the hook as blocking when refillable slots
and unlaunched tasks exist and no task has failed. It must be reworded so
"failed" there means the reconciled classification — a residual `failed`
event on a task the current plan still lists as pending no longer counts —
consistent with the amended sentence and with the shared classification
contract in IMPLEMENTATION.md.

### The two registries

Both files carry the version as a plain value; the edit changes only those
values, to the same string in both places. The key set of each file, the
identity fields of the em-workflow entries, and the whole em-review entry
stay exactly as they are — an existing test module pins them
(IMPLEMENTATION.md D4).
