# Task Plan: task0002 — Select mixed-rm-precedence cases by label and check their contiguity

## Goal

`tests/test_destructive_guard_mixed_rm_precedence.py` selects the cases of its own
feature (destructive-guard-mixed-rm-precedence) from the case table by label instead
of by a fixed open-ended position, and checks that those cases form one contiguous run
that starts right after the pre-existing cases. The module, and with it the full test
suite, passes again with later features' cases in the table.

## Requirements

FR4, FR12

## Scope

### Files to Create

None.

### Files to Modify
- `tests/test_destructive_guard_mixed_rm_precedence.py` — the case selection in the two setUpClass methods, and one added check in TestCaseTable

## Design

### Background (SPEC.md FR12, A7, A8)

- The case table is `em-workflow/hooks/tests/destructive-guard-cases.json`. Each case is
  a list whose second element is its label; a label starts with the name of the
  feature that added the case, followed by one space.
- The table holds, in order: the pre-existing cases (PRE_EXISTING_CASE_COUNT of them),
  then the 33 cases of destructive-guard-mixed-rm-precedence, then 96 cases a later
  feature (destructive-guard-heredoc-literal) appended, some of which have only three
  elements.
- TestCaseTable.setUpClass and TestScenarioCasesPassAgainstTheHook.setUpClass take every
  case from position PRE_EXISTING_CASE_COUNT to the end of the table (SPEC.md writes this
  `[PRE_EXISTING_CASE_COUNT:]`). They therefore also take the later feature's 96 cases,
  which is the cause of every failure and error that verify round 1 recorded in this
  module.
- The check of the head of the table (its first PRE_EXISTING_CASE_COUNT cases against
  PRE_EXISTING_CASE_COUNT and PRE_EXISTING_CASES_DIGEST) passes today and is not changed.

### Selection rule

| Item | Rule |
|------|------|
| Selected cases | Every case whose label begins with the feature name destructive-guard-mixed-rm-precedence followed by exactly one space |
| Order | The order of the case table |
| Where it applies | TestCaseTable.setUpClass and TestScenarioCasesPassAgainstTheHook.setUpClass, both with the same rule |
| What it replaces | Only the open-ended position selection in those two methods; everything else those methods prepare stays as it is |

The trailing space is part of the prefix, so a label of another feature whose name
merely begins with the same text is not selected. One rule shared by both methods, or
the same rule written in each, is the implementer's choice; a shared helper counts as
part of the selection change.

On the current case table the rule selects 33 cases, the number the scenarios' existing
expected counts already account for.

### Contiguity check (one new check in TestCaseTable)

- Input: the 0-based positions, in the whole case table, of the cases the selection rule
  selects.
- Passes exactly when all three hold:
  1. at least one case is selected;
  2. the first position equals PRE_EXISTING_CASE_COUNT;
  3. each following position is exactly one greater than the one before it.
- A failure message names which condition failed and, for conditions 2 and 3, the
  offending position.

### What stays unchanged

- PRE_EXISTING_CASE_COUNT, PRE_EXISTING_CASES_DIGEST and the head-of-table check.
- Every scenario's expected count, and every other check and expectation of the module.
- The case table file, every other pre-existing test file, and the hook.
