# Task Plan: task0001 — I.2.c reconciliation verification record

## Goal

Deliver the feature's single verification record: a markdown document that establishes, with
re-checkable anchors, that the already-merged `### I.2.c: Failed handling` text expresses both source
features' intent without contradiction, names every deliberate departure from a source SPEC together
with its authoritative document, and records PR #5's settled disposition.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

- `feature-docs/i2c-routeback-reconciliation/RECONCILIATION-RECORD.md` — the single verification
  record this feature delivers, structured per the record section contract in IMPLEMENTATION.md.
- `test-docs/i2c-routeback-reconciliation/task0001.tests.yaml` — the per-task test record the

### Files to Modify

None. Every source this task consults is read-only: the merged protocol document, both

a defect, not a permitted extension (see IMPLEMENTATION.md, Layer Structure).

## Design

SPEC.md cites a line range for most of these anchors. Treat each cited range as a starting point to
confirm, not as a fact to copy: locate the quoted phrase first, then record the range observed in
this worktree, noting any difference from the range SPEC.md cites (IMPLEMENTATION.md, D3).

### Record structure

Seven sections in the fixed order of IMPLEMENTATION.md's record section contract, each self-contained
so a reader can re-check one section without reading the others. Each section states its claims, then
its anchors, then — where a source SPEC statement is involved — its classification from the
three-value vocabulary in IMPLEMENTATION.md Conventions.

### Processing flow

1. Re-observe: run the project test command from the repository root and read every anchor listed
   above, recording what was actually seen (exit status, test count, quoted phrases, observed line
   ranges, version strings).
2. Classify: for each source-SPEC statement in scope, assign one of `satisfied-verbatim`,
   `satisfied-under-the-reconciled-reading`, `superseded`, naming the authoritative document for the
   latter two.
3. Write: compose each record section from the observations of step 1 and the classifications of
   step 2. A claim with no observation behind it is not written.
4. Self-check: confirm the change set contains only the two files listed under Scope.

### The documentary form of test-first

This task builds nothing executable, so its "tests" are re-observations, and they run BEFORE the
claim they support is written: the project test command over the unmodified suite, the anchor reads,
and the change-set listing. Writing a claim first and looking for its anchor afterwards inverts the
contract and is what the ordering in step 1-3 above exists to prevent. No new checker, matcher, hook
or script is introduced (NFR4).

## Test Notes

- **Automated evidence**: `python3 -m unittest discover -s tests` from the repository root. Run it
  before writing AC-4's section and record the actual exit status and test count; both source test
  modules must also pass when run as modules in their own right.
- **Command evidence**: `git diff --name-only` against the task branch's base, for AC-8. Record the
  listing itself, not a summary of it.
- **Document evidence**: each anchor read, for AC-1 through AC-3, AC-5 and AC-6. The quoted phrase is
  the primary locator and the line range the secondary one.
- **Edge cases worth covering**: a cited line range that no longer matches (record the observed range
  and note the difference); a quoted phrase that occurs more than once (pair it with its containing
  section); a task with no journal event at all (must be stated as non-blocking for route-back); the
  distinction between the route-back commit and the terminal status commit when stating what the
  rejected path does and does not commit.
- **TDD-awkward part and its handling**: there is no executable unit under test, so criterion
  satisfaction is judged by reading the produced record against the acceptance criteria above. The
  ordering discipline in Design step 1-3 (observe, classify, then write) is what stands in for
  test-first here; the per-task test record under `test-docs/` captures those observations.
