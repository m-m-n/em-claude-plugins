### Root cause (one root cause, one task)

main commit 090a4f06 added a third entry, `plugin-dev`, to
`.claude-plugin/marketplace.json`. The five modules were written when the
marketplace had two entries, and each pins that fact in one of three ways.
None of the failures involves a version value. The same five failures already
occur at the implement base commit 7d296b4d.

### Per-module change

1. **Other-entries baseline (`test_batch_policy_option_id_version_bump.py`)**
   - Add a `plugin-dev` baseline entry to OTHER_PLUGIN_ENTRIES_BASELINE,
     after the em-review entry. The matcher pairs entries in marketplace
     order, and in marketplace.json `plugin-dev` comes after em-review. Pin
     the same identity fields as the em-review entry: `name`, `author`,
     `category` and `source` exactly, plus a stable substring anchor taken
     verbatim from the current `plugin-dev` description. The version keeps
     being checked by shape only, through the existing matcher.
   - Name the em-review baseline entry and the `plugin-dev` baseline entry
     separately, so a hermetic proof can use either one alone.
   - The existing em-review hermetic proofs pass a one-entry forged list:
     `rejects_altered_identity_field`, `rejects_missing_or_malformed_version`,
     `accepts_forged_higher_version` and `rejects_new_unexpected_key`. Each
     one must compare against a one-entry baseline holding the em-review
     entry. Otherwise the length mismatch would make every rejection pass
     for the wrong reason, and the acceptance proof would fail.
   - Add two negative proofs in the module's existing style:
     (a) a forged list of other entries that has only the em-review entry is
     rejected against the full baseline, which detects a removed
     `plugin-dev` entry;
     (b) a forged `plugin-dev` entry with one altered identity field
     (`name`, `author`, `category` or `source`) is rejected against a
     one-entry `plugin-dev` baseline.
   - The matcher function, EXPECTED_OTHER_ENTRY_KEYS and the dotted-numeric
     version check stay unchanged.

2. **Non-version marketplace digest (`test_batch_structured_result_output_version_bump.py`, `test_muse_consent_version_bump.py`)**
   - Replace MARKETPLACE_NONVERSION_SHA256 in both modules with the digest
     of the current `.claude-plugin/marketplace.json`. Compute it with the
     module's own `_canonicalize_marketplace` and `_sha256`, which are the
     same in both modules, so both modules get the same new value.
   - Before replacing the value, confirm that canonicalizing the current
     file with the `plugin-dev` entry removed gives the previous value
     (`91990cec…`). This shows that adding `plugin-dev` is the only
     non-version change the new digest absorbs. Report the result of this
     check.
   - Update the comment above the constant. Following the precedent in
     `test_muse_consent_version_bump.py` for EM_WORKFLOW_MANIFEST_NONVERSION_SHA256
     (repo-suite-pinned-test-drift task0004, FR5), state that the value was
     recomputed from the current tree after the `plugin-dev` entry was
     added, and name this feature's task0002.
   - The plugin-manifest digests stay unchanged:
     PLUGIN_MANIFEST_NONVERSION_SHA256, EM_WORKFLOW_MANIFEST_NONVERSION_SHA256
     and EM_REVIEW_MANIFEST_NONVERSION_SHA256.

3. **Plugin count (`test_goal_vs_spec_divergence_version_bump.py`, `test_rework_contract_drift_version_bump.py`)**
   - Set EXPECTED_PLUGINS_COUNT to 3, with a short comment naming this
     feature's task0002 and the `plugin-dev` addition. It stays an exact
     equality check.

### Strength rules for all five modules

- No test is deleted or skipped. No exact check is turned into a range, a
  minimum or a subset check.
- No version literal or version baseline is added, removed or changed.
- Every existing negative proof and forged-sanity test still runs and still
  fails for its original reason. The only exception is that the em-review
  hermetic proofs in module 1 now compare against a one-entry baseline.
- Each module keeps using only the standard library.
