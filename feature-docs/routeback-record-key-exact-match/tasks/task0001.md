# Task Plan: task0001 — Exact-key match for the route-back record key line, with regression tests

## Goal

The route-back record read in the queue Stop hook treats a direct-child line of
a task block as a `routeback_failed_journal_line` key line only when its key is
exactly that name. A line whose key merely starts with
`routeback_failed_journal_line:` (for example `routeback_failed_journal_line:x: 1`)
no longer hides the genuine record that follows it. Regression tests pin the
corrected behaviour both at the reader-function level and at the
hook-subprocess level.

## Requirements

FR1, FR2, FR3, NFR1, NFR2

## Scope

### Files to Create

(none)

### Files to Modify
- `em-workflow/hooks/queue_stop_guard.py` — the record key-line pattern accepts only an exact-key line; the comment above the record key constant and the record-read function's docstring state the exact-key rule
- `tests/test_queue_stop_guard_routeback_record.py` — a new test section for this feature (direct reader calls and one hook-subprocess scenario), plus an observed-red note for that section in the module docstring

## Design

### Key-line rule (FR1)

A line inside a task block is a record key line exactly when, after its
leading whitespace, it begins with the key name `routeback_failed_journal_line`
immediately followed by a colon, and that colon is followed by an ASCII space,
an ASCII tab, or the end of the line. This is the colon rule that
`_find_key_colon` and `TASK_STATUS_KEY_RE` already apply in the same file;
`ROUTEBACK_RECORD_LINE_RE` adopts it so that all three agree.

- "End of the line" includes the position just before the line's trailing
  line feed. Lines are read in text mode, so a CRLF line arrives ending in LF
  only (SPEC A-4); no CR-specific handling is added.
- Any other character directly after the colon (a letter, a digit, another
  colon, or a non-ASCII whitespace character) means the line's key is not
  `routeback_failed_journal_line`, so the line is not a record key line.
- Matching stays ASCII-only, as it is today.

### Effect on the record read (FR2)

Processing flow of `task_routeback_records_from_workflow`. Only step 4
changes meaning:

1. Lines of a task whose record decision is already made are skipped.
2. The direct-child indentation is fixed from the first line of the block that
   is neither blank nor a comment (unchanged).
3. Lines not at that indentation are skipped (unchanged).
4. A line that is not a record key line under the rule above is skipped, and
   the task stays undecided. A later exact-key line in the same block can
   therefore still be the first occurrence.
5. The first exact-key line decides the task. If the text after its colon is
   the canonical value (the value rule is unchanged), the record is that
   digit string. Otherwise the task has no record. Later lines are not
   consulted (first occurrence wins, unchanged).

Resulting behaviour:

| Direct-child lines of the task0001 block, in order | Record |
|---|---|
| `routeback_failed_journal_line:x: 1`, then `routeback_failed_journal_line: 1` | "1" (was: none) |
| `routeback_failed_journal_line:1`, then `routeback_failed_journal_line: 1` | "1" (was: none) |
| `routeback_failed_journal_line:` with no value, then `routeback_failed_journal_line: 1` | none (unchanged: the empty-value line is an exact-key line and is the first occurrence) |
| `routeback_failed_journal_line:` followed by a tab and `1` | "1" (unchanged) |
| `routeback_failed_journal_line:x: 1` alone | none (unchanged) |
| `routeback_failed_journal_line:1` alone | none (unchanged: before the change the value was non-canonical; after the change the line is not a key line). The existing test `test_value_without_a_space_after_the_colon_is_no_record` keeps passing (SPEC A-2) |

### Unchanged (SPEC A-1)

The value rule (`ROUTEBACK_RECORD_VALUE_RE`), the direct-child indentation
rule, the first-occurrence rule among exact-key lines, the exclusion of body
lines of multi-line quoted-scalar and flow-collection values, the status read,
and every other reader in the file.

### Wording (SPEC A-3)

The comment block directly above `ROUTEBACK_RECORD_KEY` says the regex "only
recognizes the key". It is extended to state the exact-key colon rule, in the
same way the comment above `TASK_STATUS_KEY_RE` states it. The docstring of
`task_routeback_records_from_workflow` states that among the direct keys, only
a line whose key is exactly the record key counts as an occurrence. Every edit
keeps the phrases that the existing wording tests check, in each location
those tests read (the module docstring, this function's docstring and that
comment): "direct keys", "block scalar bodies" and "nested" (checked by
`TestDirectKeyWording`), and the body-line statement (checked by
`TestBodyLineStatements`).

## Acceptance Criteria (MANDATORY)

Fixture shorthand: "the reproduction block" is a task0001 block, with status
`pending`, in which a `routeback_failed_journal_line:x: 1` line comes before a
`routeback_failed_journal_line: 1` line, both at the block's direct-child
indentation.

- [ ] AC-1 (FR1, FR2): Called directly on a workflow.yaml that contains the reproduction block, `task_routeback_records_from_workflow` returns exactly `{"task0001": "1"}`.
- [ ] AC-2 (FR1, FR2): The hook is run as a subprocess with Stop-hook JSON on stdin, against a workflow.yaml that contains the reproduction block (task0001 `pending`) and a journal whose physical line 1 is a `failed` event of task0001. It exits with code 2, and the task list after `launch=` on stderr contains task0001.
- [ ] AC-3 (FR1, FR2): Called directly on a workflow.yaml whose task0001 block has a `routeback_failed_journal_line:1` line before a `routeback_failed_journal_line: 1` line, both at the direct-child indentation, the reader returns exactly `{"task0001": "1"}`.
- [ ] AC-4 (FR1): Called directly, the reader keeps the existing behaviour: (a) a lone line made of the key, the colon, a tab and `1` yields the record "1"; (b) an empty-value `routeback_failed_journal_line:` line before a `routeback_failed_journal_line: 1` line yields no record for task0001; (c) a lone `routeback_failed_journal_line:x: 1` line yields no record for task0001.
- [ ] AC-5 (FR3): The AC-1 to AC-4 tests are added to `tests/test_queue_stop_guard_routeback_record.py`. The tests written for AC-1, AC-2 and AC-3 are observed to fail against the hook as it was before this task's change (red before green). The test module's docstring records that observation for this feature's section, following the module's existing "Observed red" notes.
- [ ] AC-6 (NFR1, NFR2): The hook and the test module import only Python standard-library modules, and `python3 -m unittest discover -s tests` passes in full. That includes the existing wording tests and `test_value_without_a_space_after_the_colon_is_no_record`.

## Test Notes

- Placement: add a new section headed with this feature's name, following the
  module's existing per-feature section convention. The module builds its own
  helpers and imports no other test module. Reuse the module's existing pieces:
  the workflow fixture builder (a task block with extra lines), the
  direct-reader helper that loads the hook from its file path, and the
  hook-subprocess scenario runner together with its exit-code and stderr
  assertions.
- Unit tests (direct reader call): AC-1, AC-3, AC-4 (a) to (c). Integration test
  (subprocess): AC-2.
- Red and green: AC-1, AC-2 and AC-3 fail on the base revision. There, the
  non-key line is taken as the first occurrence, and its non-canonical value
  yields no record. For AC-2 the hook then classifies task0001 as failed and
  exits 0. The AC-4 cases pass both before and after the change: they are
  preservation tests, not red tests.
- Keep the fixture lines at the task block's direct-child indentation (the
  indentation of `title:` and `status:`). A deeper line is excluded by the
  unchanged indentation rule, so it would not exercise this change.
- An edge case worth covering, though not an AC: a non-ASCII whitespace
  character (for example U+3000) directly after the colon makes the line a
  non-key line, so a genuine record after it is read.
