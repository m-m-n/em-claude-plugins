## Goal

`em-workflow/references/batch-terminal-line.md` の中で、`state` の値域だけが
`phase_done` を含み `reason` と `step` の値域記述が旧来の 2 状態前提のまま

## Design

### 発生した矛盾（修正対象の事実）

| 箇所 | 現状の記述 | 矛盾の内容 |
|---|---|---|
| `## Field values` の `reason` | `none` は `state=completed` のときだけ使う値、と限定している | 11 個の停止理由コードは `Applies to state` がすべて `stopped`。この限定に従うと `state=phase_done` の行に入れられる `reason` 値が存在しない |
| `## Stop reason codes` 末尾 | `none` は `state=completed` のための予約値、と再宣言している | 同上。値域記述が 2 箇所に重複しており、どちらも `state` 側の更新から取り残された |
| `## Field values` の `step` | 「そのターンで実行した step を指す」という一般規則と、`no-step` の定義、`state=completed` では常に `retrospect` という規則が、優先関係なしに並んでいる | `--once` は retrospect 完了でターンを終え Step C を次の起動に送るため、「workflow step を 1 つも実行しないターン」が必ず発生する。三者の優先関係が未定義だと相互に矛盾して読める |

根本原因は、`state` の値域を広げた変更が「`state` の値域は 1 箇所」という
前提で行われ、同じ値域に依存する他フィールドの記述が同期対象に入って
いなかったこと。したがって修正は「`state` を増やしたときに真でなくなる
記述をすべて同期する」という単一の作業であり、個別の文言修正の寄せ集めでは
ない。

### R-A: `reason` の予約範囲

`none` は「停止でない終端状態」に予約された値である、という形に統一する。
現時点でその集合は `state=completed` と `state=phase_done` の 2 つであり、
両方を明示する。あわせて次の既存の性質を保つ:

- `none` は停止理由コードの 1 つではない。
- `none` は `state=stopped` とは決して併用されない。
- 停止行は `reason` と並んで `step` を必ず持ち、`detail` も必ず持つ。

同じ規則を述べる箇所は `## Field values` の `reason` 箇条書きと
`## Stop reason codes` 末尾の 2 つで、両方を同時に更新する。片方だけの更新が
今回の欠陥そのものなので、両方が同じ範囲を述べていることを検査で固定する。

### R-B: `step` の規則の優先関係

「そのターンで実行した step を指す」を一般規則とし、それに優先する既存の
2 規則を明示する:

1. `no-step` センチネル — 停止点で `workflow.yaml` の step が 1 つも
   実行中でない場合（`stop-condition-6` / `step-a-abort` / `step-c-abort`）は
   `no-step`。
2. `state=completed` の行は常に `retrospect`。

さらに、Step C は `workflow.yaml` の step ではないため、Step C を実行した
ターンは成否で値が分かれる（正常完了は規則 2 により `retrospect`、中断は
規則 1 により `no-step`）。この非対称は読者が推論するのではなく、文書が
明示する。

verify 失敗からの rework 境界で `verify` になる、という既存の例示は残す。

### 変えてはならないもの（NFR4 / FR11）

- level-2 見出しはちょうど 7 個、順序も現状のまま。
- `## Stop reason codes` の 11 コードと、その `Applies to state` 列が
  すべて `stopped` であること。prose の "eleven" という個数表現。
- `## Stop point coverage` の 11 行と key→code の対応。
- `state=completed` / `state=stopped` の意味。
- `phase_done` について task0003 が加えた記述（`reason=none`、非空の 1 物理行の
  `detail`、prefix と 4 フィールドと順序の同一性、consumer は同じ feature を
  再起動する）。
- 終端状態の個数を述べる表現を新たに導入しないこと（IMPLEMENTATION.md D4）。
- prefix が同文書のフェンス付きブロック内にのみ出現すること。

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `## Field values` の `reason` 箇条書きが、`none` を停止でない
      終端状態の予約値として述べ、`state=completed` と `state=phase_done` の
      両方を名指ししている。`none` の使用を `state=completed` のみに限定する
      表現は同箇条書きに残っていない。
- [ ] AC-2: `## Stop reason codes` 末尾の記述が AC-1 と同じ予約範囲を述べ、
      かつ「`none` は停止理由コードではない」「`state=stopped` とは併用しない」
      「停止行は `step` と `detail` も持つ」という既存の 3 点を保っている。
      予約範囲を `state=completed` だけに限定する表現は残っていない。
- [ ] AC-3: `tests/test_batch_stop_contract.py` が、AC-1 / AC-2 の 2 箇所
      それぞれについて `state=phase_done` の存在と旧限定表現の不在の両方を
      検査する。旧限定表現を含む forged なセクションを与えると落ちる負の証明と、
      その forged テキストが他の点では整形されている（検査が空振りしていない）
      ことを示す非空虚性ガードを伴う。
- [ ] AC-4: `## Field values` の `step` 箇条書きが、実行 step 規則と、それに
      優先する `no-step` 規則および `state=completed` ⇒ `retrospect` 規則を、
      優先関係が読み取れる形で述べている。verify 失敗 rework 境界で `verify` に
      なる既存の例示が残っている。
- [ ] AC-5: 同箇条書きが、Step C を実行したターンの値が成否で分かれること
      （正常完了は `retrospect`、`step-c-abort` は `no-step`）を明示している。
- [ ] AC-6: `tests/test_batch_stop_contract.py` が AC-4 の優先関係の文言と
      AC-5 の非対称の文言をそれぞれ固定し、除外句を削ると落ちる。
- [ ] AC-7: 非退行 — level-2 見出しはちょうど 7 個で順序どおり、理由コード表は
      11 コードに展開されその `Applies to state` 列はすべて `stopped`、
      coverage 表は 11 組の key→code に展開される。task0003 が加えた
      `phase_done` の記述はいずれも不変。リポジトリルートで
      `python3 -m unittest discover -s tests` が exit 0。
