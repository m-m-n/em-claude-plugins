# Task Plan: task0003 — 終端行契約 SSOT に 3 つ目の `state` 値を追加する

## Goal

`em-workflow/references/batch-terminal-line.md` が `--once` のフェーズ境界を
表す 3 つ目の `state` 値を定義し、`step` が「そのターンで実行された step」で
あることを述べ、終端状態の個数を固定した記述が追加後も真である状態にする。
契約テストモジュールがその構造を固定する。

## Requirements

FR7, FR8, FR10, FR11, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Modify
- `em-workflow/references/batch-terminal-line.md` — `## Field values` の
  `state` / `step`、`## Line format`、`## No line on a wait turn` の該当記述
- `tests/test_batch_stop_contract.py` — 上記の構造を固定し、ポインタ文書側の
  literal 不在チェックを `state` 値集合まで拡張する

## Design

### 契約文書に加える内容

| 対象 | 追加・変更する内容 |
|---|---|
| `## Field values` の `state` | 値域に 3 つ目の値（IMPLEMENTATION.md D1 が定める `phase_done`）を加える。意味は「`--once` 指定の起動が 1 フェーズを終えてターンを終えた」。個数を固定した表現（"closed set of two values"）は個数を言わない表現に置き換える |
| `## Field values` の `step` | `step` はそのターンで**実行された** step を指し、次の起動が再開する step ではないこと。verify 失敗からの rework 境界では値が `verify` になること |
| `## Line format` | 3 つ目の状態でも prefix・4 フィールド・その順序が同一であること。既存の 2 状態に関する記述の意味は変えない |
| 新しい state の随伴条件 | `reason` は `none`、`detail` は非空の 1 物理行（既存の正規化規則がそのまま適用される） |
| 外側ドライバの扱い | この state を見たら同じ feature を再起動する、という消費側の期待 |
| `## No line on a wait turn` | 終端状態の個数を固定した表現（"either of the contract's two terminal states"）を、個数を言わない表現に置き換える。停止条件 5 / launch / wake が非終端である既存の規則は不変 |

### 変えてはならないもの（NFR4）

- level-2 見出しはちょうど 7 個、順序も現状のまま。
- `## Stop reason codes` の 11 コードと、prose の "eleven" という個数表現。
- `## Stop point coverage` の 11 行と key→code の対応、precedence 規則、
  Source 列の各パスが実在すること。
- `state=completed` / `state=stopped` の意味、`none` が `state=completed`
  専用の予約値であること。
- prefix が同文書のフェンス付きブロック内にのみ出現すること。

### ポインタ側 literal guard の拡張（FR10）

拡張の規則は IMPLEMENTATION.md D2 が唯一の定義元。このタスクは
`tests/test_batch_stop_contract.py` の `batch-mode.md` 向け不在チェック側の
実装を担う。既存の検査（prefix、11 理由コード、sentinel、`state=` /
`step=` / `reason=` / `detail=` の各形）は残したまま、`state` 値の検査を
D2 の形で足す。`completed` / `stopped` / `skipped` の裸の語は違反にしない。

### 個数表現の同時更新（FR11）

契約文書の文言を変えると、この文書自身を固定している既存アサーション
（「どちらかの終端状態に達していない」という 2 値前提の文言を照合しているもの）が
落ちる。文言とアサーションは同じタスク・同じマージで更新する
（IMPLEMENTATION.md D4）。

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR7): `## Field values` の `state` 値域が 3 つ目の値
      （IMPLEMENTATION.md D1）を含み、その値が `reason=none` と非空 1 行の
      `detail` を伴って出力されること、prefix・4 フィールド・順序が既存と同一で
      あることが文書から読み取れる。
- [ ] AC-2 (FR7): 外側のドライバがこの state を見たら同じ feature を再起動する、
      という消費側の扱いが述べられている。
- [ ] AC-3 (FR8): `step` がそのターンで実行された step を指し、再開位置では
      ないこと、および verify 失敗からの rework 境界では `verify` になることが
      述べられている。
- [ ] AC-4 (FR11): 終端状態の個数を固定した 2 箇所（`state` の箇条書き、
      「No line on a wait turn」 の文）が、追加後も真である表現に更新され、
      それらを照合していた既存アサーションも同じ変更の中で更新されている。
- [ ] AC-5 (NFR4): level-2 見出しがちょうど 7 個で順序不変、理由コードは 11 個で
      prose の個数表現も 11、カバレッジ表は 11 行で key→code 対応が不変、
      `state=completed` / `state=stopped` の意味が不変、prefix は同文書の
      フェンス付きブロック内にのみ出現する。
- [ ] AC-6 (FR10): `batch-mode.md` に対する literal 不在チェックが `state` 値集合
      まで拡張され、実ファイルで違反 0 件、新しい `state` 値を再掲した偽造抜粋を
      拒否し（negative proof）、その偽造抜粋が well-formed であることを示す
      非空虚性ガードを伴い、`completed` / `skipped` / `stopped` の step status
      用法に誤検知しないことが明示的に検証されている。
- [ ] AC-7 (NFR2, NFR3): `python3 -m unittest discover -s tests` が exit 0。
      `tests/test_batch_stop_contract.py` は標準ライブラリのみを import したまま。

## Test Notes

- 変更対象モジュールは `tests/test_batch_stop_contract.py` 1 つだけ
  （IMPLEMENTATION.md D6）。既存のクラス・抽出ヘルパー・negative proof は
  削らず、拡張として足す。
- AC-1 / AC-3 は `## Field values` 節に対する存在アサーションで足りる。新しい
  判定ヘルパー（matcher）を導入する場合のみ negative proof と非空虚性ガードを
  付ける。
- AC-4 の更新は「既存アサーションの文言差し替え」なので、差し替え後も**空でない**
  ことを確かめる: 個数表現を消すだけにして何も検査しなくなる形にしない。
  置き換え後のアサーションが、規則そのもの（終端状態に達していないターンは
  行を出さない）を依然として固定していることを保つ。
- AC-5 の「11 個」系アサーションは既存のものをそのまま維持する。3 つ目の
  `state` 値を足しても理由コード数・カバレッジ行数が動かないことが、この feature
  の非回帰の核心。
- AC-6 の誤検知検証は、実ファイル中に `completed` / `skipped` / `stopped` が
  実際に出現していること（非空虚性）も併せて確認する。
- 端: 3 つ目の値の追加で `## Field values` の `state` 箇条書きの構造が変わるため、
  値を「表ではなく箇条書きの文」から読む既存の流儀を保つ（表を新設すると
  他の表を数えるアサーションに影響しうる）。
- 端: prefix はフェンス付き例の中だけ。新しい state の例を足すなら既存の例と
  同じフェンス内に置く。
