# Task Plan: task0007 — 終端行契約 SSOT に `step` の閉じた値域を復元する

## Goal

`em-workflow/references/batch-terminal-line.md` が冒頭で宣言している
「`state` / `step` / `reason` の値ドメインの唯一の所有者」という性質を、
`step` について実際に成り立たせる。`## Field values` の `step` 箇条書きに
7 個の `workflow.yaml` step id とセンチネル 1 個からなる閉集合の宣言を
復元し、task0005 が加えた一般規則・優先規則・Step C 非対称の記述を
1 文字も失わずに両立させる。`tests/test_batch_stop_contract.py` が、
この値域宣言の消失を再発時に検出できる形で固定する。

## 事実（修正対象）

- `em-workflow/references/batch-terminal-line.md` は冒頭 3-6 行で
  「the `state` / `step` / `reason` value domains」の唯一の所有者を宣言して
  いる。
- task0005 が `## Field values` の `step` 箇条書きを「一般規則 + 優先関係 +
  Step C 非対称」の形に書き換えた際、旧文の値域宣言
  「a `workflow.yaml` step id (`create-spec`, `design`, `create-plan`,
  `implement`, `review`, `verify`, `retrospect`), or the single sentinel
  `no-step`」が丸ごと消え、現行 bullet は「the general rule: …」から始まる。

- `state` 側には値域を固定するテスト
  （`test_field_values_state_domain_includes_phase_done`）があるが、`step`
  側には無い。7 個の step id は現在テストスイート中では
  `FORGED_OLD_STEP_BULLET_WITHOUT_PRECEDENCE`（棄却されるべき偽造サンプル）の
  中にしか存在しない。

## Design

### R-C: `step` 値域宣言の復元位置

値域宣言は `step` 箇条書きの**先頭**に前置する。task0005 が加えた次の 3 つの
記述は削らず、値域宣言のあとに現在の順序のまま残す。

1. 一般規則（そのターンで実行した step を指し、次の起動の再開点ではない。
   verify 失敗 rework 境界では `verify`）
2. 一般規則に優先する 2 規則（センチネル `no-step`、`state=completed` ⇒
   `retrospect`）と、その優先関係の明示
3. Step C 非対称（正常完了は `retrospect`、`step-c-abort` は `no-step`）

「値域は何か」と「その中のどれを載せるか」は別の問いであり、前者を欠いた
文書は後者だけを述べている。前置はこの 2 問を順に並べる形になる。

### 前置でなければならない理由（既存抽出器との関係）

`tests/test_batch_stop_contract.py` の `NO_STEP_BULLET_RE` は
「`` `no-step` applies whenever ``」を開始アンカー、次の箇条書き開始
（`\n- ` + バッククォート）を終了アンカーとする raw テキストの正規表現で、
その範囲内のハイフン付きバッククォートトークン集合を
`_extract_no_step_stop_points` が抽出し、
`{stop-condition-6, step-a-abort, step-c-abort}` との集合一致を検査している。

したがって:

- 値域宣言を開始アンカーより**前**に置けば、`create-spec` /
  `create-plan` はこの捕捉範囲の外になり、集合一致は現状のまま成立する。
  アンカーより後ろに置くと、この 2 トークンが停止点として混入して既存
  テストが落ちる。
- 開始アンカー文字列「`` `no-step` applies whenever ``」は raw テキストで
  1 物理行に収まっていなければならない。ハードラップがこの語句の中に入ると
  正規表現がマッチせず、抽出結果が空集合になって検査が無効化される。

### 値域の内容

`workflow.yaml` の 7 step id（`create-spec`, `design`, `create-plan`,
`implement`, `review`, `verify`, `retrospect`）と、センチネル `no-step` 1 個。
これは閉集合であることが読み取れる形で述べる。テスト側は 7 個の id を
モジュール内のローカル定数として宣言し（IMPLEMENTATION.md の Cross-module
isolation の慣行どおり、他モジュールからの import はしない）、文書からの
構造的抽出と集合一致を見る。

### 変えてはならないもの（NFR4 / FR11）

- level-2 見出しはちょうど 7 個、順序も現状のまま。
- 11 個の停止理由コードと `Applies to state` 列、prose の "eleven"。
- `## Stop point coverage` の 11 行と key→code 対応、precedence rule。
- task0003 / task0005 が加えた `phase_done` と `reason` 予約範囲の記述。
- 終端状態の個数を述べる表現を新たに導入しないこと（IMPLEMENTATION.md D4）。
- prefix が同文書のフェンス付きブロック内にのみ出現すること。
- ポインタ文書（`SKILL.md` / `batch-mode.md`）は一切触らない。

## Test Notes

- 文書テキストに対する unit レベルの構造アサーション（NFR2 により実行時の
  挙動変化は無い）。既存モジュールの `_sections` / `_normalize` /
  `_HYPHENATED_BACKTICK_TOKEN_RE` をそのまま使う。
- NFR3: AC-2 の値域抽出は新規 MATCHER なので負の証明（AC-3）と非空虚性
  ガードが必須。AC-5 は既存文言の保持を見るだけの純粋な回帰ガードで、
  同モジュールの慣行どおり免除。
- AC-4 は「既存の抽出器が新しい文の追加で壊れていないこと」を見るガードで、
  この修正が抱える唯一の機械的な失敗モードを直接固定する。
  `_extract_no_step_stop_points` はマッチ失敗時に空集合を返すため、
  「マッチが成立していること」を別途アサートしないと検査が空振りする。
- 値域の 7 id はモジュール内のローカル定数として宣言する。他テストモジュール
  からの import はしない（IMPLEMENTATION.md Cross-module isolation）。
- モジュール所有権（IMPLEMENTATION.md D6）: このタスクが所有するテスト
  モジュールは `tests/test_batch_stop_contract.py` のみ。
  `tests/test_batch_stop_contract_skill_wiring.py` を編集する必要が生じたら、
  黙って直さず plan deviation として報告する（task0008 の所有物）。
