# Task Plan: task0002 — Derive the repo test's suite-runner timeout from the case count

## Goal

The repo test that runs the destructive-guard expectation suite finishes
without `subprocess.TimeoutExpired` while still detecting a hung runner.
Its bound for the runner invocation grows with the size of the case file
instead of staying at a fixed 120 seconds.

## Provenance

- source: verify
- source_ids: VF-1

## Requirements

FR3

## Scope

### Files to Create

None.

### Files to Modify
- `tests/test_destructive_guard_command_substitution.py` — the timeout given
  to the runner invocation in
  `TestCaseTableDiscipline.test_runner_reports_every_case_passing`, plus one
  test that pins how that timeout is derived.

## Design

### Defect (VF-1)

`TestCaseTableDiscipline.test_runner_reports_every_case_passing` starts
`em-workflow/hooks/tests/run-destructive-guard.py` as a subprocess with a
fixed 120-second timeout. The runner starts one hook subprocess per case,
one after another, so its wall time grows linearly with the number of cases
in `em-workflow/hooks/tests/destructive-guard-cases.json`. With 458 cases,
measurements on the verify host were:

| Hook copy | Wall time |
|---|---|
| fixed hook | 2:02 |
| base revision's hook | 2:44 |

The load average during these runs was 16-33. Both times exceed the bound,
so the repo-tests component command (`python3 -m unittest discover -s tests`)
exits 1. All 458 cases pass. The failure is in the test's time bound, not
in any verdict.

### Change

- The runner invocation's timeout becomes **case count × per-case budget**.
- The case count is the number of cases loaded from
  `em-workflow/hooks/tests/destructive-guard-cases.json` when the test runs.
- The per-case budget is at least 1 second. Observed cost under the load
  above was 0.27-0.36 seconds per case.
- The timeout stays finite, so a hung runner still fails the test instead of
  blocking the suite.
- The derivation is exposed at module level (a helper or a constant plus the
  count) so that a separate test can check it without running the suite.

### Behaviour that stays unchanged

These stay as they are:

- the runner's arguments;
- the exit-status assertion of `test_runner_reports_every_case_passing`;
- its every-case-passing assertion;
- every other test in the file.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: In `TestCaseTableDiscipline.test_runner_reports_every_case_passing`, the runner invocation no longer uses a fixed 120 seconds. It passes a finite timeout equal to the number of cases in `em-workflow/hooks/tests/destructive-guard-cases.json` multiplied by a per-case budget of at least 1 second. (FR3)
- [ ] AC-2: A test in `tests/test_destructive_guard_command_substitution.py` loads the current case file and asserts two things: the derived timeout is finite, and it is at least the case count in seconds. Changing the derivation back to a fixed 120 seconds makes that test fail. (FR3)
- [ ] AC-3: `test_runner_reports_every_case_passing` keeps its assertions on the runner's exit status and on every case passing. Only the timeout value changes. (FR3)
- [ ] AC-4: `python3 -m unittest tests.test_destructive_guard_command_substitution` exits 0. `test_runner_reports_every_case_passing` passes without raising `subprocess.TimeoutExpired`. (FR3)
- [ ] AC-5: `python3 -m unittest discover -s tests` exits 0. (FR3)
- [ ] AC-6: The task's change set modifies only `tests/test_destructive_guard_command_substitution.py`. (FR3)
