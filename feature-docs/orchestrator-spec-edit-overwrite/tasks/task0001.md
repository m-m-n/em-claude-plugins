# Task Plan: task0001 — create-spec action decision counts the orchestrator's create-plan record

## Goal

The create-spec action decision in spec-writer-contract.md gives an existing
target `replace_own` when its current digest equals the last create-spec output
for the path or the last `orchestrator_doc_edits` entry for the path. Every other
existing target still takes the digest-mismatch branch. The action table's
`replace_own` row and create-spec-phase.md section 9 cite that rule without
restating it.

### Owner section: "How the orchestrator chooses each target's action before dispatch"

Structure after the edit, top to bottom:

1. The introductory paragraph and the three bullets (create / match / mismatch).
   Unchanged.
2. The paragraph that starts "For an implementation-planner dispatch of
   create-plan". One sentence changes: the sentence that today says the three
   bullets apply as written to create-spec and the design step. After the edit,
   the design step still applies the three bullets as written to every existing
   target whose action is not fixed individually. For create-spec, the sentence
   points to the create-spec rule below, which says which recorded outputs count
   as the immediately preceding same-phase output. Every other sentence of this
   paragraph (the token-file sentences, the scope list of create-plan dispatches)
   stays verbatim.
3. The paragraph "The rule applies only to ordinary planning artifacts" and the
   four create-plan bullets (Match. / No match. / Reading
   `phase-state/rework.yaml`. / Recorded values.). Unchanged.
4. New: the create-spec block, after the "Recorded values." bullet and before
   the next level-2 heading ("`completed` payload"). It is a lead paragraph
   followed by bullets. It adds no heading. The lead paragraph begins with the
   exact words "For a spec-writer dispatch of create-spec", and these words occur
   once in the section. The block makes these statements:
   - **Match.** The orchestrator gives an existing create-spec target
     `replace_own` when the path's current digest equals either (a) the last
     `artifacts` entry for that path in `phase-state/create-spec.yaml`, or (b)
     the last entry for that path in the `orchestrator_doc_edits` record of
     `phase-state/create-plan.yaml`, the record `references/phase-state.md`
     defines. The last entry for a path is the entry for that path that comes
     last in that list. Only those two and only their last entries count:
     earlier entries for the same path, entries for other paths, and other
     phase-state files do not count.
   - **No match.** An existing create-spec target whose current digest equals
     neither takes the digest-mismatch branch above: the
     `create-spec.artifact-overwrite` gate in interactive mode and the
     `references/batch-policies.yaml` decision in batch mode. No other condition
     gives `replace_own`. A spec-change record or a re-planning authorization
     does not.
   - **Reading the record.** The orchestrator counts (b) only when the file's
     mapping has phase `create-plan` and a feature equal to the workflow's
     feature. Five cases each count as no (b) record: an absent file, an
     unreadable file, a malformed file, a mismatched phase or feature, and no
     `orchestrator_doc_edits` entry for the path. The decision then rests on the
     `phase-state/create-spec.yaml` comparison alone.
   - **Recorded values.** The orchestrator compares a (b) recorded value that
     differs from the current digest as `references/artifact-digest.md`
     "Legacy records" states, the same way as a `phase-state/create-spec.yaml`
     recorded value.
   - **Verification.** A target that gets `replace_own` by either match carries
     `expect_digest`, and the orchestrator verifies it by
     `references/artifact-digest.md` "Pre-dispatch verification" like every
     other such target (SPEC A-11).
   - **Scope.** The (b) record counts only in this create-spec decision. The
     create-plan planning-lineage rule above and the design step do not count
     it (FR5).

Wording rules for the block: every sentence that speaks of a digest names the
orchestrator as its subject (IMPLEMENTATION.md Conventions, worker digest
stance). The block does not name `git hash-object`. For (b) it never writes "last
`artifacts` entry for that path in `phase-state/create-plan.yaml`", because (b)
is the `orchestrator_doc_edits` list and not `artifacts`.
