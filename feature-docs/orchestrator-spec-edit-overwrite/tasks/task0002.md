# Task Plan: task0002 — record the orchestrator's own SPEC / REQUIREMENTS edits during create-plan

## Goal

phase-state.md defines the append-only `orchestrator_doc_edits` record of
`phase-state/create-plan.yaml`, and the develop skill's Step B tells the
orchestrator to append one entry, in the same commit, whenever it changes and
commits the feature's own SPEC.md or REQUIREMENTS.md during create-plan.

## Requirements

FR1, FR2, FR7, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_orchestrator_doc_edits_record_docs.py` — document tests for this task's Acceptance Criteria, with forged-copy cases

### Files to Modify
- `em-workflow/references/phase-state.md` — the orchestrator_doc_edits block of the Schema example and its row in the top-level field table
- `em-workflow/skills/develop/SKILL.md` — a new bold-labelled paragraph in Step B for the recording procedure

## Design

The record's name, entry keys, path form and last-entry meaning are fixed in
IMPLEMENTATION.md (Shared Components, D1 to D4). This task writes the schema
and the writer procedure. The read conditions and the last-entry rule are the
action-decision owner section's (D3) and are not restated here.

### phase-state.md, `## Schema`

- **Example block**: in the `## Schema` yaml example, a top-level
  `orchestrator_doc_edits:` key placed directly after the
  `other_feature_doc_fixes` block and before `patches:`. Its trailing comment
  says it is held only when `phase: create-plan` and is append-only. It holds
  exactly one example entry with `path` (an own-feature path such as
  `feature-docs/example/SPEC.md`), `sha256` and `reason`. The key starts at
  column 0, so the block above it ends where it did before.
- **Field table row**: one row whose first cell is the backticked field name
  `orchestrator_doc_edits`, in the table under "Every top-level field:",
  directly after the `other_feature_doc_fixes` row. Its statements, in English:
  - `phase: create-plan` only.
  - An append-only list of the changes the orchestrator itself made to the
    feature's own SPEC.md or REQUIREMENTS.md during create-plan and committed.
  - Each entry: `path`, `sha256` and `reason`. `sha256` is the digest
    `references/artifact-digest.md` "Digest definition" defines.
  - The writer: `skills/develop/SKILL.md`, Step B. The entry is committed in the
    same commit as the document change.
  - The reader: `references/contracts/spec-writer-contract.md`, "How the
    orchestrator chooses each target's action before dispatch".
  - The list is never rewritten or cleared, a phase restart (`generation`
    increases) included.
  - A file written before the field existed lacks it and stays valid.
- The row does not restate the reader's rule. It names no last-entry wording, no
  read condition (phase / feature match, malformed file), and no `replace_own`
  decision. It names no `git hash-object` and no existing restatement marker.
- Nothing else in phase-state.md changes. That covers the
  `other_feature_doc_fixes` example and row, which existing tests pin, the
  "ID uniqueness and idempotency" section and the file layout.

### skills/develop/SKILL.md, `## Step B: 自走ループ`

- **Placement**: a new paragraph opened by the bold label
  `**create-plan 中の自 feature 文書修正の記録**`. It goes directly after the
  `**exit-4 リカバリ**` paragraph (which ends with "しない）。") and directly
  before `**batch: verify の cap 到達に対する停止条件の例外**`. Other tests slice
  the text between those two labels and run every git command they find there
  through the destructive guard. So the new paragraph writes no git command and
  no script invocation.
- **Statements**, in Japanese like the rest of the skill:
  1. When: during create-plan, when the orchestrator itself changes the
     feature's own SPEC.md or REQUIREMENTS.md and commits the change.
  2. What: the orchestrator appends one entry to `orchestrator_doc_edits` in
     `phase-state/create-plan.yaml`. The entry holds the changed document's
     path, the digest of that document at that moment calculated by
     `references/artifact-digest.md` `Calculation`, and the reason for the
     change. The record's shape is cited from `references/phase-state.md`.
  3. Same commit: the entry is included in the same `commit-docs.sh` commit as
     the document change. The commit form a phase-state write takes is cited
     from `references/phase-state.md` ("Update, commit, and exit-4 recovery"),
     not restated.
  4. Calculation failure: when the digest calculation fails, no entry is
     written.
  5. Exit 4: when that commit returns exit 4, the orchestrator follows the
     `**exit-4 リカバリ**` above. It re-creates the edit on the refreshed tree,
     recalculates the digest from the re-created body, appends the entry to the
     re-read `phase-state/create-plan.yaml`, and retries with the entry in the
     same commit.
  6. Purpose, by citation only: the entry is read by the create-spec action
     decision of `references/contracts/spec-writer-contract.md` ("How the
     orchestrator chooses each target's action before dispatch").
- **Not in the paragraph**: the match rule, the last-entry rule,
  `phase-state/create-spec.yaml`, the read conditions, `git hash-object`, and
  any existing restatement marker (raw bytes, hexadecimal, the script name, its
  error tokens, the quoting rule).
- The paragraphs Step B already has stay byte-identical: the create-plan
  exemption block, the commit-discipline paragraph that begins
  "workflow.yaml か feature-docs/ 配下のドキュメントを Write/Edit するたび", and
  the `**exit-4 リカバリ**` paragraph.
