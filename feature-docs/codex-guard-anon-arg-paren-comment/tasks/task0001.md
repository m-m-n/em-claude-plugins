# Task Plan: task0001 — Rescue unclosed anonymous-function argument groups at `;` / lone `&`

## Goal

In both copies of codex-hook-interactive-guard, an anonymous-function
argument `(` that never closes, and whose first direct separator is `;` or a
lone `&`, no longer makes the command undecidable: the commands after that
separator are judged, so a hidden interactive launch is denied.
Newline-first provisional groups and genuinely unclosed groups stay
undecidable (no output).

## Design

### Terms
- **Provisional group**: a frame opened at an anonymous-function argument `(`
  that `_read_argument_parens` reads — both the word-internal form (`foo(`)
  and the word-initial form (`(`).
- **Genuine group**: every other frame (command-position `(`, `{` groups,
  function-definition bodies, and the rest).
- **First direct separator** of a provisional group: the first separator the
  main reader reads while that provisional group is the innermost open frame.
  A separator read inside a nested frame is not direct.
- **Rescue** and **genuinely unclosed group**: as defined in REQUIREMENTS.md
  section 13.

### What counts as the first direct separator

| Token read directly in a provisional group | Effect |
|---|---|
| the `;` operator | recorded as `;` — rescuable (FR1) |
| a lone `&` (background) | recorded as `&` — rescuable (FR2) |
| a newline | recorded as newline — not rescuable (FR3) |
| any other list or pipeline operator the main reader reads (`&&`, `\|\|`, `\|`, `\|&`, and the rest) | recorded as first — not rescuable (FR4) |
| a redirection containing `&` (`&>`, `>&`, and the like), a quoted `;` / `&`, a backslash-escaped `;` / `&` | not a separator — records nothing (FR4) |

- Only the first such token is recorded; later separators do not change it.
- The kind is taken from the main reader's own tokenization, not from the
  lookahead that decides whether the `(` opens a group. Quoting, escaping and
  comments are therefore interpreted exactly as for every other command.
- Each provisional group also records where its content after the first
  direct separator begins, so the commands read after it can be handled as
  one unit.

### End-of-input rescue (flow)

Runs when input ends, before the existing "group never closed" undecidable
check.

1. Take the innermost open frame.
2. If it is a provisional group whose first direct separator is `;` or a lone
   `&`, rescue it:
   1. The group is treated as ending at that separator. Content before the
      separator keeps the reading it already has (the same reading a closed
      argument group gets) — no command is dropped.
   2. The commands read after the separator stop belonging to the
      provisional group and become commands that follow the
      anonymous-function command in the enclosing frame. The
      anonymous-function head's pipe or input redirection, and any connection
      the provisional group inherits, do not reach them (FR6).
   3. The frame is no longer open.
3. Cascade: if the enclosing frame is a provisional group with no first
   direct separator recorded, the rescued separator now counts as its first
   direct separator (it is now read directly in that frame). Return to step 1.
4. Stop at the first innermost frame that is genuine, or provisional but not
   rescuable (first direct separator is a newline or another operator, or
   there is none).
5. If any frame is still open, the existing "group never closed" check yields
   undecidable (no output), unchanged (FR5). This covers a genuine group left
   open after rescues (TS-10) and an argument `(` with no separator (TS-11).
6. Otherwise, the existing end-of-input confirmation (group connection and
   function-definition skip) runs over every recorded command, rescued
   commands included, unchanged (FR6).

Consequence: a rescue succeeds only when every frame open at end of input is
a rescuable provisional group, and the rescued commands then end at the top
level.

### Complexity contract (NFR1)
- The main reader reads each input character a bounded number of times; the
  rescue does not re-read the remaining input once per rescued frame.
- A rescue moves a frame's post-separator commands to the enclosing frame as
  one unit (for example, by redirecting which frame owns the unit), not one
  command at a time, so a cascade over many nested frames with many trailing
  commands stays linear.
- No recursion (the existing recursion check applies).
- Any realization that meets these points and the Acceptance Criteria is
  acceptable.
