# Task Plan: task0001 — Scan the operator words of a `[[ ]]` conditional in its opening statement

## Goal

`destructive-guard` reads a statement that opens a `[[ ]]` conditional as
uncertain when an arithmetic comparison operator (`-eq` `-ne` `-lt` `-le`
`-gt` `-ge`) or `-v` stands anywhere between the opener and its closer, so the
canonical notion call that follows loses the notion-pair exclusion and its
`--args-json` is decoded and judged. A conditional with no such word keeps the
reading it has today.

## Requirements

FR1, FR2, FR3, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/hooks/destructive-guard.py` — the opener-statement branch of
  the conditional reading also reads the words between the opener and the
  closer for the operator words; that function's docstring states the new
  reading.
- `tests/test_destructive_guard_args_json.py` — one new test class for this
  task's unit, integration and case-table checks.
- `em-workflow/hooks/tests/destructive-guard-cases.json` — the new deny / allow
  cases.

## Design

### Root cause (as read at the base commit)

- `_args_json_nameref_scan()` reads a chunk statement by statement
  (`lex_segments()`). `&&` and `||` split a `[[ ]]` conditional across several
  statements; inside a statement, the `(`, `)`, `{` and `}` boundaries
  (`_args_json_command_boundary()`) split it into simple commands.
- `_args_json_conditional_step()` checks words against
  `_ARGS_JSON_DOUBLE_BRACKET_WORDS` only in its `was_open` branch, that is, in
  the statements after the one holding the opener. In the statement holding
  the opener it only locates the opener and the closer.
- That statement's words are otherwise read per simple command by
  `_args_json_declares_nameref()`. A simple command after a `(` or `)`
  boundary whose name is on the allow-list (`true`, `false`, `echo`, `:`,
  `mcp-bridge`, `fi`, `done`) is certain whatever its words hold, so the `-eq`
  of `[[ ( true -eq 0 ) && true ]]` is never counted, the chunk reads certain,
  and the following notion call with `--session "$SID"` stays `KIND_NOTHING`.

### Change: the opener-statement branch of `_args_json_conditional_step()`

The signature, the (UNCERTAIN, OPEN) return shape and the single call site in
`_args_json_nameref_scan()` stay as they are.

- **Precondition**: `was_open` is false, and the statement holds an opener —
  the command-name word of a simple command written exactly `[[`, found the
  way the function finds it today.
- **Scan range**: the statement's non-operator words strictly after the
  opener, up to but excluding the first later word written exactly `]]` (the
  closer, judged by `_args_json_word_source()` as today). When the statement
  has no closer, the range runs to the end of the statement.
- **Rule**: when any word in the range has a restored text (the text part of
  `_args_json_declaration_word()`'s result — the same test the `was_open`
  branch and the `[[` branch of `_args_json_name_uncertain()` use) that is in
  `_ARGS_JSON_DOUBLE_BRACKET_WORDS`, the statement is uncertain (UNCERTAIN is
  true). Which simple command holds the word, and that command's name, play no
  part.
- **Otherwise unchanged**: OPEN is false when the closer was found and true
  otherwise, and the `;` / lone `&` rule
  (`_args_json_separator_breaks_conditional()`) applies after it as today.
- **Outside the range**: words before the opener and words after the closer
  are not part of this scan (FR3).

Unchanged by this task:

- The `was_open` branch, which scans the whole statement.
- The judgment of opener and closer by their written form, including the
  rule that a quoted or escaped opener makes the statement uncertain at once.
- The command-level reading (`_args_json_declares_nameref()`, the allow-list,
  `_ARGS_JSON_DOUBLE_BRACKET_WORDS` itself) of every simple command,
  including those inside a conditional. This task adds a reading and removes
  none.
- The helper builds no decision, carries no reason ID and executes nothing
  (NFR2, NFR4).

### Docstrings

- `_args_json_conditional_step()`: state that in the statement holding the
  opener, the words from just after the opener up to just before the closer
  (to the end of the statement when it has none) are read for the operator
  words too, whatever simple command they fall in, and that words before the
  opener and after the closer are not. The function's source must not contain
  the strings `destructive-guard/` or `permissionDecision` (an existing test
  reads the whole source, docstring included).
- `_args_json_nameref_scan()`: no change is required. If its item 5 is
  reworded, it must still name `_args_json_fd_variable_deferred()`,
  `_args_json_conditional_step()`, `_args_json_declares_nameref()`,
  `_args_json_has_brace_substitution()`, `_args_json_has_deferred_evaluation()`
  and `lex_segments()`, and none of the command names NFR3 lists (two existing
  tests pin both).

### Test and case-table placement (constraints from existing tests)

- New forms go into a new test class. They are not added to the tuples of
  `TestSourceTextReadings` (`FD_DENY`, `FD_ALLOW`, `CONDITIONAL_DENY`,
  `CONDITIONAL_ALLOW`, `CLOSER_OPERANDS`): its
  `test_every_case_of_this_task_is_in_the_table_with_its_decision` looks each
  of those forms up in the case table and requires the entry it finds to carry
  an `args-json-deferred-eval-bypass` label.
- For the same reason, no new case-table command equals the joined shape that
  test looks up for one of those tuples' forms: the array assignment
  `A=(json --mcp desktop-commander --tool start_process); `, then the form,
  then `; `, then the notion call.
- No new case repeats the command string of an existing case. The existing
  tests key the table by command string, so a duplicate replaces the earlier
  entry and breaks their label and count checks. A form whose command string
  is already in the table is covered by that entry and is not added again.
- Every new label starts with `dbracket-opener-arith-scan`. No new label
  starts with `args-json-deferred-eval-bypass`; the count of labels starting
  with `args-json-deferred-eval-bypass TS-16:` or `TS-17:` stays at exactly 30.
- Every new case's notion call is the canonical call
  `mcp-bridge run --mcp notion --tool notion-create-comment --session "$SID" --args-json`
  with the payload whose `command` is `git branch -D example` (SPEC AC-2).
  Each deny case carries the fourth element with `rule` set to
  `git-branch-force-delete`; an allow case carries no fourth element.
- Command shapes:
  - **New forms** (the forms this task introduces): the array assignment
    above, the form, `; `, the notion call — the shape SPEC AC-2 gives.
  - **Existing forms** (each `CONDITIONAL_ALLOW` form of
    `TestSourceTextReadings` and each `certain_forms()` form of
    `TestCommandNameAllowlist`): the form, `; `, the notion call, without the
    array assignment — the shape `TestCommandNameAllowlist` already uses for
    `certain_forms()` — so no command equals a shape the existing look-up
    reads.

### SPEC discrepancy: `[[ ( a == b ) && true ]]`

SPEC FR3 and AC-5 list `[[ ( a == b ) && true ]]` as read certain "as before",
with the following call staying `KIND_NOTHING`. At the base commit this form
already reads uncertain. The `(` boundary makes `a == b` a simple command
whose name `a` is outside the allow-list, so `_args_json_declares_nameref()`
reads it as uncertain and the following call is `KIND_INSPECTED`. Making it
certain would need a change to the command-level reading. FR3 ("unchanged")
and NFR1 do not ask for that change, and it would weaken the guard.

This plan follows FR3's "as before":

- the conditional reading reports none of the form's statements as
  uncertain (the FR1 scan finds no operator word in it);
- the chunk's overall answer for the form stays what it was at the base
  commit (uncertain, from the command-level reading);
- the form is not added to the case table as an allow case.

The implementer states this in its task result, so the review sees that this
form follows this plan rather than the literal outcome of SPEC AC-5.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, TM-1): `_args_json_nameref_scan()` returns true for the chunk
  `[[ ( true -eq 0 ) && true ]]`. It also returns true for each of these
  variants: `-ne`, `-lt`, `-le`, `-gt` or `-ge` in place of `-eq`; `||` in
  place of `&&`; and `false`, `echo`, `:` or `mcp-bridge` in place of `true`
  inside the parentheses.
- [ ] AC-2 (FR1, FR2, TM-1): the command made of the array assignment,
  `[[ ( true -eq 0 ) && true ]]`, `; ` and the canonical notion call with
  `--session "$SID"` gives `[KIND_INSPECTED]` through `Spy(...).kinds()`. The
  hook's decision on that command is `deny` with the reason ID
  `git-branch-force-delete`.
- [ ] AC-3 (FR1, FR2): `if [[ ( true -eq 0 ) && true ]]; then :; fi` and
  `[[ ( -v x ) && true ]]` each give the AC-1 result (the scan returns true)
  and the AC-2 results (`[KIND_INSPECTED]`; `deny` with
  `git-branch-force-delete`).
- [ ] AC-4 (FR3): `_args_json_nameref_scan()` returns false for
  `[[ ( true == x ) && true ]]`. The following call with `--session "$SID"`
  gives `[KIND_NOTHING]` after that form (with the array assignment), after
  each `CONDITIONAL_ALLOW` form of `TestSourceTextReadings` (with the array
  assignment) and after each `certain_forms()` form of
  `TestCommandNameAllowlist` (without it).
- [ ] AC-5 (FR3): the scan range is bounded. `_args_json_nameref_scan()`
  returns false for a statement whose only operator word stands after the
  closer, for example as the target of a redirection the command-level
  reading takes out (`[[ a == b ]] >-eq`). It also returns false for one whose
  only operator word stands before the opener in the same way
  (`>-eq [[ a == b ]]`). For `[[ ( a == b ) && true ]]`,
  `_args_json_conditional_step()` reports none of its statements as uncertain
  during the scan, and `_args_json_nameref_scan()` still returns true, as at
  the base commit (see "SPEC discrepancy").
- [ ] AC-6 (FR1, FR2, FR3, NFR1): `destructive-guard-cases.json` gains these
  entries, all under labels starting with `dbracket-opener-arith-scan` and
  each in the shape stated under "Test and case-table placement":
  - deny entries carrying `{"rule": "git-branch-force-delete"}` for
    `[[ ( true -eq 0 ) && true ]]`,
    `if [[ ( true -eq 0 ) && true ]]; then :; fi` and
    `[[ ( -v x ) && true ]]`;
  - allow entries for `[[ ( true == x ) && true ]]` and for each AC-4
    existing form whose command string is not yet in the table.

  No new command string repeats an existing one. A test in the new class
  checks each of these entries for its decision, label prefix and `rule`.
  `python3 em-workflow/hooks/tests/run-destructive-guard.py`,
  `python3 -m unittest tests.test_destructive_guard_args_json` and
  `python3 -m unittest discover -s tests` all pass, and no existing case or
  test is removed.
- [ ] AC-7 (NFR2, NFR3, NFR4, NFR5): the existing tests that pin
  `_args_json_conditional_step()`'s single call site, its lack of a decision
  and reason ID, and the docstring of `_args_json_nameref_scan()` pass without
  being edited. The change adds no process launch, no evaluation of a string
  as code, and no file or network access to the hook. Neither
  `em-workflow/.claude-plugin/plugin.json` nor `.claude-plugin/marketplace.json`
  is changed.

## Test Notes

- Write the tests first. The AC-1 forms, and the AC-2 form and the `if` form
  of AC-3, fail at the base commit; they are the regression detectors for the
  reproduction steps.
- The `-v` form of AC-3 already reads uncertain at the base commit (its
  simple command after the `(` boundary is named `-v`, outside the
  allow-list). It is kept because SPEC AC-4 names it, not as a regression
  detector.
- Reuse the module's existing helpers and constants (`GUARD`, `Spy`,
  `KIND_INSPECTED`, `KIND_NOTHING`, the case-table path constant). For the
  per-chunk answer, use the same approach as `TestSourceTextReadings.scan()`.
  To observe the conditional reading for the AC-5 discrepancy form, wrap
  `_args_json_conditional_step()` with a recording spy for the duration of one
  `_args_json_nameref_scan()` call, the way `TestSourceTextReadings.scans()`
  wraps the scan.
- AC-4's existing forms are read from the existing tuples and method
  (`TestSourceTextReadings.CONDITIONAL_ALLOW`,
  `TestCommandNameAllowlist.certain_forms()`), not copied, so the check
  follows them if they grow.
- The AC-5 range forms pin where the scan starts and stops in the static
  reading. They make no claim about how Bash runs those lines.
- The AC-6 table check reads the case table the same way the existing table
  checks do (keyed by the command string) and covers every entry this task
  adds.
- Per `.claude/rules/hook-tests.md`, run
  `python3 em-workflow/hooks/tests/run-destructive-guard.py` after changing
  `destructive-guard.py`.

## Out of Scope

- Any change to the command-level reading (`_args_json_declares_nameref()`,
  `_args_json_name_uncertain()`, the allow-list) or to the `was_open` branch.
- Any change to `_ARGS_JSON_DOUBLE_BRACKET_WORDS`.
- Making `[[ ( a == b ) && true ]]` read certain (see "SPEC discrepancy").
- A statement holding a second opener after its first closer. The range starts
  at the first opener, the same opener the closer search uses today.
- Editing or removing existing tests, existing case-table entries or their
  labels.
- Any change to the plugin version.
