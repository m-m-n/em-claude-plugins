# Task Plan: task0001 — journal helper: in-lock launch-identity check and the widened reason set

## Goal

`em-workflow/scripts/journal-append-failed.py` gains an optional
launch-identity input that is compared inside its existing exclusive lock
before the append, and accepts exactly one additional reason value,
`stale-launched`, so the decision layer can record a watchdog-killed launch
as terminal without ever failing a different launch.

## Requirements

FR3 (step 7 only), FR6, FR7, FR9, FR13, NFR1, NFR2, NFR3, NFR5, NFR6

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/scripts/journal-append-failed.py` — the closed reason set
  gains exactly one member; the CLI gains one optional launch-identity input;
  the in-lock decision compares the launch, not merely the event name; a
  third outcome value is reported for the mismatch. The module docstring is
  updated to describe all three outcomes and the widened set.
- `tests/test_journal_append_failed.py` — extend: the closed-set membership
  assertion is updated to the widened set, and the new in-lock comparison,
  the new outcome, the new reason value and the concurrency property are
  covered.

## Design

### Contract

The helper's full CLI and outcome contract is IMPLEMENTATION.md's Shared
Components SC2′ and SC2′ outcome vocabulary; the appended line shape is SC4
there. Implement against that contract exactly — the decision layer is built
in parallel against the same text and cannot be consulted.

### What changes

1. **Closed reason set.** The set gains exactly one member, `stale-launched`,
   alongside `orphaned`. Validation still happens before the journal is
   opened, and an unknown value still exits non-zero with no write. Neither
   value's meaning nor emission path changes.
2. **Launch-identity input.** One new optional input carries the raw `at`
   value of the `launched` event the caller's decision was made against
   (`--launch-at`). It is never parsed as a timestamp and never normalised —
   it is compared as an exact string.
3. **In-lock comparison.** Inside the SAME existing exclusive advisory lock,
   after the same replay and before the append, the decision becomes:
   - last event for the task is `launched` AND no launch-identity input was
     supplied → append (today's behaviour, unchanged);
   - last event is `launched` AND the input was supplied AND that event's
     `at` equals the supplied value → append;
   - last event is `launched` AND the input was supplied AND that event's
     `at` differs, is absent, or is not a string → no append, outcome
     `launch_changed`;
   - anything else (`merged`, `failed`, no event for the task, any other
     event name) → no append, outcome `noop_terminal` (unchanged).
   The replay must therefore surface the last event's `at` alongside its
   name; the last-event replay stays tolerant of malformed lines exactly as
   today.
4. **Outcome reporting.** The stdout object keeps its three keys and gains
   the third outcome value. Exit code is 0 for all three decided outcomes.

### Invariants this task must not disturb

- One lock, taken once, held across replay and append; no second lock, no
  widening, no lock held across a subprocess call (NFR2).
- The must-already-exist, no-parent-creation and symlink-refusing open
  preconditions are untouched (FR6).
- The appended line's field names and their order are untouched (SC4).
- Every existing invocation form keeps its current outcome (NFR5).
- Standard library only (NFR6).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR7): the closed reason set accepts exactly `orphaned` and
      `stale-launched`; `manual`, the empty string and a missing value are
      each rejected with a non-zero exit, no stdout outcome line, and a
      byte-identical journal.
- [ ] AC-2 (FR7, SC4): invoking with reason `stale-launched` against a
      journal whose last event for the task is `launched` appends exactly one
      line whose fields are `event`, `task`, `at`, `reason` in that order,
      with `event` = `failed` and `reason` = `stale-launched`, and reports
      outcome `appended`.
- [ ] AC-3 (FR6, FR9): with the launch-identity input supplied and matching
      the last `launched` event's `at`, the append happens and outcome is
      `appended`; with it supplied and NOT matching (different value, absent
      `at`, or non-string `at`), nothing is appended, the journal is
      byte-identical to its pre-call content, outcome is `launch_changed`,
      and the exit code is 0.
- [ ] AC-4 (NFR5): with the launch-identity input omitted entirely, every
      pre-existing case keeps its current outcome — `launched` last event
      appends, `merged` / `failed` / no-event are `noop_terminal` — proven by
      the pre-existing tests in this module continuing to pass.
- [ ] AC-5 (FR9): every non-appending outcome (`noop_terminal`,
      `launch_changed`, reason rejection, precondition failure) leaves the
      journal byte-for-byte identical and creates neither the file nor its
      parent directory.
- [ ] AC-6 (NFR2): N concurrent invocations carrying the SAME launch identity
      against the same journal append at most one `failed` line in total.
- [ ] AC-7 (NFR6): the module imports only the standard library, and the test
      module imports no third-party package.

## Test Notes

- TS5 maps to AC-3 and AC-6. Build a journal whose last event for the task is
  `launched` with one `at` value, then rewrite the file so the last event is
  a `launched` with a different `at`, then invoke with the first value:
  assert no append and the mismatch outcome. The concurrency companion
  follows the existing multi-process pattern already in this module.
- TS6 maps to AC-1 and AC-2, updating the existing closed-set membership
  assertion rather than adding a parallel one.
- Byte-identity assertions read the whole file before and after and compare
  the bytes; a line-count comparison does not satisfy AC-5.
- Edge cases worth a case each: a journal whose last `launched` line carries
  no `at` field; one whose `at` is a number rather than a string; a task with
  interleaved events for OTHER task ids around the launch under recovery.
- TDD order: the closed-set assertion and the mismatch case are both
  expressible before any change, and both fail red first.

## Out of Scope

- Any change to the decision layer, to any hook, or to any documentation.
- Any change to the lock structure, the open preconditions, or the line
  shape.
- Inferring a reason value inside the helper, or adding any input beyond the
  single launch-identity one.
