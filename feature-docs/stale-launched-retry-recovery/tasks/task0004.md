# Task Plan: task0004 — retry reachability proof and the plugin version bump

## Goal

Prove that a task whose journal last event is a `failed` carrying the new
reason value is relaunchable — the launch guard allows it and appends exactly
one `launched` line, while still denying a genuinely in-flight or merged task
— and bump both plugin version fields to the same new value, with the guard's
own source untouched.

## Requirements

FR8, FR11, FR13, NFR4, NFR6

## Scope

### Files to Create

- `tests/test_stale_launched_retry_reachability.py` — the launch-guard
  contract test for the recovered-then-relaunched path and the two deny
  paths.
- `tests/test_stale_launched_version_bump.py` — the version-parity and
  bump-over-baseline test for this feature.

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — the version field moves from
  `0.1.77` to `0.1.78`.
- `.claude-plugin/marketplace.json` — the em-workflow entry's version field
  moves from `0.1.77` to `0.1.78`, the same value as the manifest.
- `tests/test_codex_wrapper_fallback_removal_version_bump.py` — re-anchor the
  em-workflow exact-value assertions, and the value table entry they read,
  from `0.1.77` to the new value; the em-review values and every other
  assertion in that module are untouched.

## Design

### Version bump

Both registries move to the same new value, `0.1.78` — a patch increment, per
the project's version-bump rule, because this feature extends the behaviour
of existing scripts. The value and the one module that pins it exactly are
IMPLEMENTATION.md decision D-H; every other version module compares against a
recorded baseline floor and stays green without an edit.

### Retry reachability (FR8, AC2 of the SPEC)

`em-workflow/hooks/queue_launch_guard.py` is NOT modified by this feature —
any change to it is out of scope. It reads only the journal's last event for
the task: `launched` denies as in-flight, `merged` denies as merged, and
anything else, including `failed`, allows and appends one `launched` line.
This task proves that behaviour holds against a journal whose last event is a
`failed` carrying reason `stale-launched`, so recovery genuinely re-opens the
retry path, and that the two deny paths are undiminished.

The guard is driven as a subprocess with JSON on stdin, the same contract the
harness uses (`test/README.md`). Fixtures are journals written into per-test
temporary directories; the launch payload carries a task-assignment block
whose task id and worktree path resolve to that fixture journal, exactly as
the existing launch-guard tests already do.

### Hook classification and status-read pins (NFR4)

No hook file changes, so the classification table and the status-read pins
stay green unchanged. This task asserts nothing new about them; it must not
edit the modules that pin them.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR8): against a journal whose last event for the task is a
      `failed` line with reason `stale-launched`, the guard exits 0, produces
      no deny decision, and the journal gains exactly one `launched` line for
      that task.
- [ ] AC-2 (FR8): against a journal whose last event for the task is
      `launched`, the guard denies the relaunch and appends nothing; against
      one whose last event is `merged`, it denies and appends nothing —
      double-launch prevention undiminished.
- [ ] AC-3 (FR8): the launch guard's source file is not in this feature's
      change set; the test module reads it only as a subprocess target and
      never imports or rewrites it.
- [ ] AC-4 (FR11): the em-workflow plugin manifest and the em-workflow entry
      of the marketplace registry carry the identical version string, and
      that string parses as three numeric components whose major and minor
      equal the baseline `0.1` and whose patch is strictly greater than `77`
      — compared on parsed numeric components, never on the raw string.
- [ ] AC-5 (FR11): the marketplace entry is located by its name field, and
      the lookup fails loudly when no entry of that name exists; each matcher
      has a negative proof against forged data, plus a well-formedness guard
      on the forged sample.
- [ ] AC-6 (FR11, FR13): every pre-existing version-pinning module passes
      after the bump, including the one whose exact-value assertions this task
      re-anchors.
- [ ] AC-7 (NFR4, FR13): `python3 -m unittest discover -s tests` passes from
      the repository root in this worktree, with the hook-classification and
      status-read pin modules unmodified.
- [ ] AC-8 (NFR6): both new test modules import only the standard library.
