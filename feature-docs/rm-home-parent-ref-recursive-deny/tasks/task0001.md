# Task Plan: task0001 — Select the rm ask over the same statement's self-modification ask for a qualifying operand

## Goal

In a statement whose own rm has a qualifying operand (defined below), the
destructive-guard hook gives the rm `ask` with reason ID `rm-unresolvable`
in place of that statement's self-modification `ask`. `$HOME` stays an
unresolved expansion, every existing case keeps its decision and reason ID,
and the change is pinned by new cases, a new unittest module and the updated
comments and rule document.

## Design

### Terms

- **Operand basis** of a statement's rm invocation. On the plain rm path it
  is the rm command word's arguments, which are passed to check_rm() and
  rm_protected_operand_numbers(). On the substitution-headed path it is the
  remainder after the skipped substitution, which is passed to
  route_substitution_headed_statement() and rm_protected_operand_numbers().
- **Deletion target**: a counted operand of the basis that does not start
  with `-`, numbered by the existing operand-numbering helper. This is the
  same set rm_protected_operand_numbers() judges, and the numbers are the ones
  check_rm() puts on its records for that basis.
- **Qualifying operand**: a deletion target that meets all three conditions:
  - (a) its raw form matches the protected self-config pattern (SELF_CONFIG);
  - (b) its number is not in the set rm_protected_operand_numbers() returns
    for the basis;
  - (c) the statement's rm records for that basis include a record with
    reason ID `rm-unresolvable` and that operand number.
- The check is made only when the statement's self-modification `ask` is held
  (the existing `self_modification_asked` flag) and the statement established
  an rm invocation on that path.

### Qualifying-operand check (new, pure)

Add one helper function with this contract:

- **Input**: an operand basis, the statement's rm records for that basis (as
  returned by check_rm() or route_substitution_headed_statement(), before the
  protected-operand filtering), and the protected-operand set for the basis.
- **Output**: whether at least one qualifying operand exists. Returning the
  set of their operand numbers is equally acceptable.
- **Precondition**: the records and the protected set come from the same
  basis.
- **Postcondition**: no side effects and no file-system access. `$HOME` and
  `~` are not expanded with the hook's `HOME`. The same inputs always give the
  same output. The work is linear in the operand count plus the record count.
- It reuses the existing numbering helper and SELF_CONFIG. It adds no pattern
  and changes none of the functions FR3 names.

### Selection change in main()

1. Per statement, check_self_modification() and the `self_modification_asked`
   computation run as today. The substitution-headed path and then the plain
   path compute their records as today.
2. On the path that established the statement's rm invocation, when
   `self_modification_asked` holds, run the qualifying-operand check. It gets
   that path's basis, the records before the protected-operand filtering, and
   the protected set the existing filtering already computes.
3. When a qualifying operand exists, mark every self-modification `ask` that
   this statement added to the held asks as standing for the rm `ask`. Other
   asks held by the same statement, and every ask held by another statement,
   stay unmarked. The existing held-ask entries are not rewritten, so other
   readers of the held asks see what they see today.
4. The protected-operand filtering of the records is unchanged. A qualifying
   operand is never in the protected set, so its `rm-unresolvable` record stays
   in the pool.
5. Resolution step:
   - Step 1 is unchanged: an rm `deny` is chosen first.
   - Step 2: when the first held ask is marked, the verdict is the rm `ask`
     that the strongest-rm-decision selection returns over the whole pool.
     This is the same verdict the step-6 rm `ask` gives: reason ID
     `rm-unresolvable`, with the reason text built the same way. When the
     first held ask is not marked, step 2 picks it as today.
   - Steps 3 to 7 are unchanged.
6. decide() is unchanged. It applies the `CLAUDE_BATCH` demotion after the
   choice.

Invariant: whenever the first held ask is marked, the pooled rm decision
exists and is an `ask`, because the qualifying operand left an
`rm-unresolvable` record in the pool and step 1 did not fire. If an
implementation could still reach step 2 with a marked ask and no rm `ask`,
it picks the held ask as today. It never falls through to `allow`.

run() judges a payload under two lexer readings and keeps the stricter
result. The change lives in main(), so both readings apply it.

## Test Notes

- Write the cases and the unittest module first. Before the change, TS-1 to
  TS-7, TS-9, TS-12 and TS-15 are expected to fail with `self-modification`.
  TS-8, TS-10, TS-11, TS-13 and TS-14 are expected to pass already.
- `python3 em-workflow/hooks/tests/run-destructive-guard.py` must run in the
  same change as the edit to the hook (project rule).
- The new unittest module, standard library only, pins the following:
  - the case-table run, in the style of the earlier per-feature modules. The
    earlier cases are pinned by count and by a digest computed at the task
    base;
  - the exact (decision, command, rule, batch) set of the 16 cases;
  - the two TS-18 forms, run against the hook;
  - TS-1's reason-text equality from AC-1;
  - the two-run determinism of AC-7;
  - the FR4 bullet and comments, checked by key terms rather than exact
    sentences, as tests/test_hook_tests_rule_key_doc.py does.
- The unchanged-function part of AC-7 and the manifest part are checked with
  a diff against the task base, not with a permanent source-digest test. Such
  a test would block later features that legitimately change those
  functions.
- Do not run any load-based or repeated stress checks. Running each command
  twice is enough for determinism.
