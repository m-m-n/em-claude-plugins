# Task Plan: task0001 — End the list continuation after redirect-only commands and at a closing paren

## Goal

The guard's list continuation also ends after a redirect-only simple command
that follows `&&` / `||`, at any separator other than a newline, and at a `)`
that closes a `(` group after a redirect-only simple command. A later
undecidable fragment then no longer hides an explicit `python3 -i` on an
earlier line: both guard copies deny it, and new case-table rows pin the
behaviour.

## Design

### Current behaviour (what the change builds on)

- The list continuation (`list_pending`) is set when `&&` or `||` is read. It
  is cleared only when the end of a simple command (`_flush`) finds words, and
  when a group opens (`_open_group`).
- Ending a simple command (`_flush`) already reports two facts: whether the
  command held words, and whether it held a redirection (`redirected`).
- A newline the reader itself reads at the top level is a checkpoint only when
  no group is open, no pipe is pending and no list continuation is pending.
  When the string later proves undecidable, the commands up to the last
  checkpoint are judged.
- The pending pipe (`pipe_pending`) already follows the rule this task gives
  the list continuation: set at `|` / `|&`; otherwise cleared when the
  separator is not a newline or the ended simple command held a redirection; a
  newline that ends an empty command with no redirection leaves it.
- Closing a group (`_close_group`) clears the pending pipe unconditionally, but
  not the list continuation.

### Change 1: the separator rule (FR1)

Contract of the separator step (`_separator`) for the list continuation. The
precondition is that the simple command in progress has just been ended and has
reported its two facts. The postcondition depends on the separator read:

- `&&` or `||`: the continuation is set.
- Any other separator that is not a newline (`;`, a lone `&`, `|`, `|&`, or a
  `)` read as a separator): the continuation is cleared, whatever the ended
  command held.
- A newline that ends a simple command holding a redirection (for example a
  line of only `< /dev/null`, `> /dev/null` or `<<EOF`): the continuation is
  cleared.
- A newline that ends an empty command with no redirection (a blank line, a
  comment-only line): the continuation is left as it was.

Around that contract:

- The existing clearing when a simple command with words ends, and when a
  group opens, stays as it is.
- A heredoc body is consumed outside the separator step and leaves the
  continuation unchanged.
- A `)` that is read as a separator (no `(` group is the innermost open group)
  follows the same contract; nothing extra is needed for it.
- Accepted consequence (SPEC.md AS1): syntax-error forms (`python3 -i && ;`,
  `python3 -i && &`, a `>` with no target) now clear the continuation and deny
  when an undecidable line follows. No row is required for them.

### Change 2: a `)` that closes a `(` group (FR6)

Both ways an unquoted `)` closes a `(` group gain one rule: when the simple
command that the `)` ends held a redirection, the list continuation is
cleared; otherwise it is left as it was (`(python3 -i &&)` keeps it).

Flow of the `)` reading after the change:

1. Finish the word in progress.
2. If the innermost open group is a provisional group whose chain is rescued
   at a `)` (the existing condition, unchanged): drop the provisional chain
   down to its base `(` group, end the simple command, clear the list
   continuation when the ended command held a redirection, then close the base
   group. (`_close_paren_after_rescue`)
3. Else, if the innermost open group is a `(` group: end the simple command,
   clear the list continuation when the ended command held a redirection, then
   close the group. (the ordinary branch of `_close_paren`)
4. Else: the `)` is a separator and Change 1 applies.

The pending pipe needs nothing new on these paths: closing the group already
clears it. The redirection fact used in steps 2 and 3 is the one reported by
ending the simple command in that same `)` reading; no other state is read.

### Change 3: documentation (FR3, NFR5)

- `_Parser` docstring, the list continuation paragraph: state that the
  continuation is set when `&&` or `||` is read, and is cleared when a simple
  command with words ends, when a group opens, when a separator other than a
  newline is read, when a separator ends a simple command that held a
  redirection (including one with only redirections), and when a `)` that
  closes a `(` group ends a simple command that held a redirection; a newline
  that ends an empty command without a redirection (a blank line, a
  comment-only line) and a heredoc body leave it as it was.
- `__init__`, the comment on the list continuation field: the same conditions,
  in short form.
- `_close_paren` docstring and `_close_paren_after_rescue` docstring: state
  that the list continuation is cleared when the simple command the `)` ends
  held a redirection. The existing case mark and inherited value wording of
  `_close_paren` stays.
- Unchanged: module docstring step 9, and every sentence the documentation
  tests pin for the checkpoint rule (among them "no group is open, no pipe is
  pending, no list continuation is pending").
- No docstring may contain any of the case-mark permanence phrases the
  documentation tests forbid ("The mark is never cleared", "It is never
  cleared", "for the rest of its life").

### Change 4: case-table rows (FR5)

`\n` below stands for a newline. Add these rows to the case table, next to the
existing checkpoint rows (the rows about `&&` / `||` continuation):

Deny (each is silent before the change):

1. `python3 -i &&\n< /dev/null\necho '`
2. `python3 -i && > /dev/null\necho '`
3. `python3 -i || > /dev/null\necho '`
4. `python3 -i && > /dev/null;\necho '`
5. `python3 -i &&\n<<EOF\nx\nEOF\necho '`
6. to 10. Each of rows 1 to 5 as the operand of `bash -c`, quoted for a shell
   the way the existing nested rows are (single quotes with the embedded quote
   escaped, for example through the standard shell-quoting helper the test
   module already imports).
11. `(python3 -i && < /dev/null)\necho '`
12. `(python3 -i || < /dev/null)\necho '`
13. `(function { :; } foo(a; python3 -i && < /dev/null)\necho '` (the rescue path)
14. `(python3 -i && < /dev/null);\necho '`
15. `(python3 -i && < /dev/null) &\necho '`

Silent (each is silent before and after the change):

16. `python3 -i &&\n# c\necho '`
17. `(python3 -i &&)\necho '`
18. `(function { :; } foo(a; python3 -i &&)\necho '`

Labels are Japanese, in the style of the neighbouring rows. No existing row is
removed or changed.
