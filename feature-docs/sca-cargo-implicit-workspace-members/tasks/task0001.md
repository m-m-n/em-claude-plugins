# Task Plan: task0001 — Treat a Cargo workspace with root path dependencies as an incomplete direct set

## Goal

The cargo scan unit marks the root manifest's direct-dependency set incomplete
when the manifest has a `[workspace]` table and a root dependency entry carries
`path` (directly, or inherited through `workspace = true`). Advisories for
crates declared only by implicit workspace members are then counted in the
existing cargo undetermined note instead of being silently dropped as
transitive.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/scripts/scan-dependencies.py` — widen the completeness rule of the cargo direct-dependency set (workspace view and direct-name resolution) and update both functions' docstrings to state the new condition
- `tests/test_scan_dependencies_cargo_directness.py` — append one new test class covering the Acceptance Criteria below; existing classes, test methods, helpers and constants stay unchanged

## Design

### Definitions

- **Root dependency tables**: the `dependencies`, `dev-dependencies` and
  `build-dependencies` tables at the top level of the root Cargo.toml and
  under each `target.<cfg>` table — the same set the direct-name resolution
  already collects. The sub-table form (`[dependencies.<key>]`) is an ordinary
  entry of these tables once parsed, so it needs no separate handling.
- **Path-bearing entry**: an entry of a root dependency table that is
  - (a) a table that has a `path` key, or
  - (b) a table with `workspace = true` whose same-key entry in the same
    manifest's `[workspace.dependencies]` is a table that has a `path` key.

  Only the presence of the `path` key counts. Its value is never interpreted,
  resolved, normalized, opened, or copied anywhere; a non-string value still
  makes the entry path-bearing.

### Completeness rule after this task

The direct-name set of the root manifest is incomplete when any existing
condition holds (manifest unresolvable, unreadable or unparsable; tomllib
unavailable; `[workspace]` listing members; any unexpected shape), or when
this new condition holds:

- the manifest has a `[workspace]` table, AND
- at least one root dependency table holds a path-bearing entry.

The new condition applies both when `members` is absent and when it is an
empty list (a non-empty list is already incomplete today). It does not apply,
and the set stays complete as today, when:

- the manifest has no `[workspace]` table, even with path dependencies (FR3);
- the only path entries are in `[workspace.dependencies]` and no root entry
  references them through `workspace = true` (FR3);
- the only path entries are under `[patch]` / `[replace]` — these are not root
  dependency tables (SPEC A3).

Where the path points — inside or outside the workspace directory, listed in
`[workspace] exclude` or not — does not matter (SPEC A2).

The names in the set do not change: a path-bearing entry still contributes its
name exactly as today (its `package`, also through a renamed `workspace = true`
entry, otherwise its key).

### Contracts

| Component | Responsibility | Contract (pre/postcondition) |
|-----------|----------------|------------------------------|
| Workspace view (the function reading `[workspace]`) | Returns the `[workspace.dependencies]` table and a completeness flag for the parsed root manifest | Pre: parsed manifest mapping. Post: completeness flag is false for every existing condition; the implementer may move the new condition here (its signature may change — its only caller is the direct-name resolution in the same file) or leave it to the caller |
| Direct-name resolution (the function returning the direct-name set for a manifest path) | Returns the root's direct names with a completeness flag | Pre: a manifest path or nothing. Post: never raises for any manifest content; the set is flagged incomplete whenever the completeness rule above says so; the root Cargo.toml is the only file it reads |

- The new condition is evaluated within the direct-name resolution's existing
  never-raise contract, and only on values already known to be tables; a
  non-table entry is simply not path-bearing (its shape handling stays as
  today).
- No new file is opened (NFR2, SPEC A5).
- The incompleteness reaches the result only through the existing cargo
  undetermined note (fixed token `cargo_directness_undetermined` plus a
  count). No new token, reason text or field is added to summary or
  skip_reason (NFR4). `skipped` and `skip_reason` behave as today (FR4).
- Advisory classification is not modified (FR4): a match against the root's
  resolved names stays a direct finding; an unmatched advisory whose severity
  is determined and below the threshold is dropped uncounted; any other
  unmatched advisory on an incomplete set is counted once in the cargo
  undetermined note.
- pip / npm / go scan units are untouched (NFR5). Standard library only;
  tomllib keeps going through the existing guarded import (NFR1).
- Both changed functions' docstrings state the new incompleteness condition
  (FR1, FR2) and the cases that stay complete (FR3).

### Processing flow (root manifest → classification)

1. Read and parse the root Cargo.toml (existing; any failure → incomplete).
2. Read the `[workspace]` view (existing; non-empty `members` or a bad shape →
   incomplete).
3. Collect the root dependency tables (existing).
4. New: if the manifest has a `[workspace]` table and any collected table
   holds a path-bearing entry → incomplete.
5. Resolve names from the collected tables (existing, unchanged).
6. Classify each advisory against the names and the completeness flag
   (existing, unchanged).

### Constraints

- The plugin version fields (em-workflow's `plugin.json` and the root
  `marketplace.json` entry) are not edited (NFR6).
- Documents of the completed feature `sca-directness-resolution` are not
  edited (SPEC A4).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR4, FR5, TM-1, TM-2): A root Cargo.toml with a `[workspace]` table that has no `members` key and `member = { path = "member" }` in `[dependencies]`; `member/Cargo.toml` declares a crate the root does not declare; the cargo-audit stand-in reports a high-severity advisory for that crate. Result: no finding, `skipped` is false, `skip_reason` is None, and the summary ends with the cargo undetermined note with count 1 — the member manifest's declaration does not turn the advisory into a finding. The same result holds when the `[workspace]` table has `members = []`.
- [ ] AC-2 (FR1, FR5, TM-1): With a `[workspace]` table without `members` and the path entry placed instead in each of `[dev-dependencies]`, `[build-dependencies]`, `[target.'cfg(unix)'.dependencies]`, and the sub-table form `[dependencies.member]` with `path = "member"`, each case yields no finding and the cargo undetermined note with count 1 for an undeclared high-severity advisory.
- [ ] AC-3 (FR2, FR5, TM-1): `[workspace.dependencies]` has `member = { path = "member" }` and the root `[dependencies]` has `member = { workspace = true }` → an undeclared high-severity advisory yields no finding and the note with count 1. When the inherited `[workspace.dependencies]` entry carries both `path` and a `package` rename, the undeclared advisory is still counted once, and an advisory for the renamed package name is a finding.
- [ ] AC-4 (FR4): In a manifest made incomplete by FR1 or FR2, an advisory for a crate declared in the root's own tables (`serde`) is a finding, and when it is the only advisory the summary carries no cargo undetermined note; an undeclared advisory whose severity is determined and below the threshold is neither a finding nor counted (no note when it is the only advisory).
- [ ] AC-5 (FR3, NFR5): An undeclared high-severity advisory stays transitive (no finding, no cargo undetermined note) for each of: a `[workspace]` without `members` and without a path-bearing root entry; the same with `members = []`; a `[workspace]` whose `[workspace.dependencies]` holds a path entry that no root entry references; a `[package]` manifest without `[workspace]` that has a path dependency. The existing tests `test_ac4_a_workspace_without_members_is_complete` and `test_ac4_a_workspace_with_an_empty_members_list_is_complete` pass unchanged.
- [ ] AC-6 (NFR2, NFR3, NFR4, TM-2, TM-3, TM-4): For a `[workspace]` root manifest (no `members`) whose path-bearing entry uses, case by case, (i) a distinctive dependency key with a distinctive path value pointing outside the project root at a directory holding a Cargo.toml that declares the advisory's crate, (ii) a non-string `path` value (an integer; a table) on a root entry, and (iii) a non-string `path` value on a `[workspace.dependencies]` entry inherited through `workspace = true`: the scan returns normally with no exception escaping; the direct-name resolution called directly on that manifest returns without raising and its set is flagged incomplete; the undeclared high-severity advisory is counted once in the cargo undetermined note and is not a finding (the file outside the project has no effect); and neither summary nor skip_reason contains the path value, the dependency key, or the manifest path.
- [ ] AC-7 (NFR1, NFR5, NFR6): `python3 -m unittest discover -s tests` passes with every pre-existing test method in `tests/test_scan_dependencies_cargo_directness.py` unchanged (new tests are additions only), including the existing standard-library-only import test; the change set contains no edit to `em-workflow/.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, or anything under `feature-docs/sca-directness-resolution/`.

## Test Notes

- AC-1 to AC-6 are integration tests through the existing cargo scan harness
  in the test module: a recording cargo-audit stand-in on a PATH restricted to
  its own directory, and fixture projects in a temporary directory. Reuse the
  module's existing base test case, advisory-entry builder and note constants;
  do not modify them.
- "High" severity is at or above the threshold; "low" is a determined severity
  below it — the same values the existing counting tests use.
- AC-1's "member manifest not read" and AC-6 (i)'s "outside file not read" are
  behavioral: the other manifest declares the crate, yet the advisory is
  counted as undetermined rather than becoming a finding — the same approach
  as the existing member-manifest test.
- AC-2 and AC-6 enumerate several placements or shapes; one sub-case per
  placement or shape keeps a failure attributable.
- AC-6's direct check calls the module's direct-name resolution function on a
  written manifest and inspects only its completeness flag.
- Place the new class after the existing classes under a comment header that
  names this feature and maps each test to its AC.
- AC-7: run the full suite and the plugin-invariants check
  (`python3 em-workflow/scripts/check-plugin-invariants.py .`) before
  finishing.
