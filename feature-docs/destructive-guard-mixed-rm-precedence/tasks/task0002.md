### What the destructive-guard part says after this task

1. **The fourth element.** The bullet that describes the fourth element shows all three keys: `cwd`, `batch` and `rule`. It states:
   - Each key is optional.
   - `rule` is a non-empty string: the expected reason id.
   - The reason id is compared with the `<rule>` in the leading `[destructive-guard/<rule>]` of permissionDecisionReason.
   - A case whose decision or reason id differs fails, and its FAIL line shows the obtained reason id.
   - A case without `rule` is judged on the decision only, as before.
2. **Malformed cases.** One sentence states that an unknown key, a `rule` that is not a string, or an empty `rule` stops the run as a malformed case.
3. **Mixed-case guidance.** One new bullet says that a case combining a recursive delete with a check other than rm carries `rule`, so that the reason id is pinned as well as the decision. In a few clauses it summarises the precedence those cases pin:
   - A recursive-delete `deny` wins over an `ask` from another check, in either order.
   - In a statement whose own rm deletion target is a protected self-config path, the self-modification `ask` stands instead.
   - The CLAUDE_BATCH demotion happens after the precedence is decided.
4. **Phrases that stay.** The phrases existing tests require remain in place:
   - `"cwd"`, `"batch"`, `4 要素目`;
   - `{merge_fixture}`, worktree, `em-workflow/demo/integration`, `unregistered`;
   - the two run commands.

The document stays in Japanese and in its current style: short bullets, one fact each. It gives no instruction to change a version.
