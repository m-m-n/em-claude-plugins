# Threat Model: destructive-guard-mixed-rm-precedence

## Verdict
threats-identified

## Rationale
Inspected: REQUIREMENTS.md, SPEC.md (FR1-FR8, NFR1-NFR6, assumptions A1-A8) and the workflow.yaml goal block. Tier is `full`; the design step was skipped (no user interface). task0001 declares `input-handling`, so the one boundary below is analysed at deep depth. task0002 declares `config-infra` only.

The feature's subject is the PreToolUse hook that stands between an agent-authored Bash command and its execution. One trust boundary exists: the command string entering the hook's verdict logic (TB-1). The agent may have assembled that string from attacker-influenced text, such as repository contents or tool output. The feature changes the order in which the hook's verdicts compete, and it lets the scan continue past an `ask`. Every threat below is therefore about a `deny` the hook owes being lost or weakened, or about the cost of the longer scan.

Not modelled as threats, with the reason:
- The reason text returned to the agent. This feature adds no target-derived text to any reason. The rm reasons it now emits for more commands come from the existing rendering, which is left unchanged.
- Under CLAUDE_BATCH the mixed commands already end in `deny`, because the `ask` is demoted. The change there is which reason is shown (FR3, SPEC US2). That reason makes no security decision of its own: a retry meets the same `deny`. It is covered as a functional requirement (task0001 AC-3), not as a threat.
- The case runner, the case table, the new unittest modules and `.claude/rules/hook-tests.md` carry no trust boundary. They are developer-authored test tooling, test data and documentation, never inputs to the hook at run time. This is why task0001's `input-handling` domain is tied to the hook file only: the runner's malformed-case check (FR5) protects test fidelity, not a boundary.
- Spoofing, Repudiation and Information disclosure. At this boundary the hook has no identity to verify, no audit duty and no secret, and SPEC.md records no such requirement.

## Trust Boundaries

### TB-1: Bash command string -> destructive-guard verdict
Crossing: an agent-authored Bash command (possibly built from text the agent read in repository files or tool output) enters the hook's statement scan. The scan decides allow / ask / deny before the command runs, and under CLAUDE_BATCH an `ask` is demoted to `deny`.
Boundary files: em-workflow/hooks/destructive-guard.py
Depth: deep (input-handling)

| STRIDE category | Threat | Mitigation ID | Mitigation | Implemented by | Verified by |
