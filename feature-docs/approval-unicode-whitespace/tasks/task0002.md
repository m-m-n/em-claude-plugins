# Task Plan: task0002 — Space/tab-only trim on the approval store side (approved_for, --list, --record / --remove)

## Goal

bash_guard.py's approved set and its `--record` / `--remove` input follow the
C1 approval trim rule (IMPLEMENTATION.md): a stored entry with any whitespace
other than spaces and tabs at either end is never approved nor listed, and an
input line with such whitespace makes the whole `--record` / `--remove` run
refuse without touching the store.

## Requirements

FR1, FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_bash_guard_store_unicode_whitespace.py` — store-side tests (CLI child processes and hook runs with an isolated store)

### Files to Modify
- `em-workflow/hooks/bash_guard.py` — C2 helpers; approved_for, read_stdin_commands and the --record / --remove path of cli_main

## Design

Cross-task contracts used here: C1 (approval trim rule), C2 (bash_guard.py
trim helpers, with their fixed names and placement), C3 (approved set; this
task is its producer) and decisions D3-D5 in IMPLEMENTATION.md. They are not
restated.

### approved_for and --list

- `approved_for` meets the C3 contract: it trims each stored string entry by
  C1 Trim only and keeps only matchable results. A non-string, empty or
  non-matchable entry is not a member.
- `--list` keeps printing the sorted members of `approved_for`, so a
  non-matchable stored entry is never printed.

### read_stdin_commands and --record / --remove

- Each stdin line has exactly one trailing LF removed (a final line without
  LF has nothing removed), then C1 Trim. CR, U+000B, U+000C, U+00A0 and every
  other non-space/tab character are kept.
- A line that is C1-empty is skipped, as today.
- When at least one line is non-matchable, `--record` and `--remove` both
  refuse the whole input: each such line is reported on stderr in the same
  manner as the refusal-pattern report, the exit code is 1, nothing is printed
  as approved, and the store file is neither written nor replaced.
- Otherwise behaviour is as today: no command left → the existing
  "no commands" message and exit code 1; refusal patterns refuse `--record`;
  the merge base for both modes is `approved_for`, so a non-matchable entry
  already in the store disappears from the stored list on the next successful
  `--record` or `--remove` (SPEC.md Assumption A1).
- The check that refuses the input runs before any store write, so a refused
  run never leaves a partially updated store or a leftover temporary file.

### Not changed here

`hook_main`, `is_cd_prefixed_approved`, `cd_remainder_excluded`,
`declared_commands`, `COMMAND_KEY_RE` and the module docstring belong to
another task (D4). The hook's own refusal of a non-matchable command is not
this task's contract (C3 consumer rule).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR6, TM-7): For a store whose project entry holds an
  approved-looking string with U+00A0, U+000B, U+000C, CR or LF before or
  after it (written directly into the store file): `--list` does not print
  that entry, and the hook does not allow the entry's fully stripped form
  (for example `/usr/bin/true` from a stored U+00A0 + `/usr/bin/true`) unless
  that form is stored as its own entry.
- [ ] AC-2 (FR7, TM-6): `--record` given stdin in which at least one line is
  non-matchable after removing one trailing LF and trimming spaces and tabs —
  U+00A0, U+000B or U+000C before or after the command, or a CRLF-terminated
  line — exits with code 1, reports each such line on stderr, prints no
  "approved:" line, and leaves the store file byte-identical (or still absent
  when it did not exist), even when the other lines of the same input are
  matchable. `--remove` behaves the same way.
- [ ] AC-3 (FR1, FR7): Lines with only spaces and tabs around a command are
  recorded and removed in their trimmed form and approve that trimmed form
  (the existing space/tab behaviour holds); lines empty after the trim are
  skipped; an input with no command left still exits 1 with the existing
  message; a refusal pattern still refuses `--record`.
- [ ] AC-4 (FR6, FR7): A non-matchable entry already in the store is absent
  from the stored list after the next successful `--record`, and after the
  next successful `--remove`.
- [ ] AC-5 (FR1): U+0085, U+2000, U+3000 or U+001F at either end makes a
  stdin line refuse the input and makes a stored entry neither listed nor
  approved. `make<U+00A0>test` is recorded and listed as it is and does not
  approve `make test`.
- [ ] AC-6 (NFR1, NFR2, NFR3): bash_guard.py imports standard-library
  modules only and contains no substring `status`; the C2 helpers have the
  names, contract and placement fixed in IMPLEMENTATION.md. New tests use
  unittest only and isolate the store with `EM_WORKFLOW_APPROVALS`.
  `python3 -m unittest discover -s tests` passes.

## Test Notes

- All criteria run bash_guard.py as a child process: the CLI with
  `--project-dir` pointing at a temporary git repository and stdin given as
  bytes or text, the hook with a PreToolUse JSON payload.
- AC-1 and AC-4 write the store file directly to plant non-matchable entries;
  the test source writes the characters as escapes.
- AC-2 compares the store file's bytes before and after the refused run and
  checks that no temporary file is left beside it; cover both a store that
  exists and one that does not.
- Hook assertions in AC-1 and AC-5 use only matchable commands (for example
  `/usr/bin/true`, `make test`). A command padded with other whitespace is
  judged by the hook entry, which is another task's contract (C3 consumer
  rule); do not assert on it here.
