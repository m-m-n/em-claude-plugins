# Task Plan: task0001 — Treat undecodable task-listing output as a sixth unavailable-listing condition

## Goal

`file-tasks` no longer aborts with a traceback when the `task list` output is
not valid UTF-8. Such output becomes the sixth "listing unavailable"
condition, with the reason token `listing_output_undecodable`, and the run
ends through the existing degraded report branch with one JSON summary on
stdout.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Design

### Listing acquisition contract (`list_security_tasks`)

- Precondition: unchanged (same arguments and entry-point handling as today).
- Postcondition: always returns a `ListingOutcome`; no decoding error ever
  escapes the function (FR3).

Classification flow — evaluated in this order, first match wins (FR2):

1. Entry point invalid → `entry_point_invalid` (unchanged).
2. Launch `task list --type セキュリティ --format json` with stdout and stderr
   captured as raw bytes, not in text mode (FR1). A launch failure of the
   operating-system-error kind → `listing_launch_failed` (unchanged).
3. Non-zero exit → `listing_exit_nonzero`. Neither stdout nor stderr is
   inspected at this step, so garbage output on a failing run still yields
   this token.
4. Decode stdout alone as UTF-8 in strict mode → on failure,
   `listing_output_undecodable` (new). The codec is fixed to UTF-8 and is not
   taken from the locale (FR1). No error handler that replaces, ignores,
   escapes or passes through invalid sequences is used, so a UTF-8-encoded
   surrogate counts as undecodable.
5. Parse the decoded text as JSON → on failure, `listing_output_not_json`
   (unchanged).
6. Parsed value is not an array → `listing_output_not_array` (unchanged).
7. Otherwise the listing is available.

stderr is never decoded at any step (FR4). A stderr full of invalid bytes has
no effect on the outcome when the exit code is 0 and stdout is a valid UTF-8
JSON array.

### Reason vocabulary (six conditions)

| Order | Token | Condition |
|-------|-------|-----------|
| 1 | `entry_point_invalid` | unchanged (NFR2) |
| 2 | `listing_launch_failed` | launch fails with an operating-system error (unchanged) |
| 3 | `listing_exit_nonzero` | non-zero exit; output not inspected (unchanged) |
| 4 | `listing_output_undecodable` | exit 0 and stdout is not strictly decodable as UTF-8 (new) |
| 5 | `listing_output_not_json` | unchanged (NFR2) |
| 6 | `listing_output_not_array` | unchanged (NFR2) |

The new token is a fixed literal. The reason carried out of
`list_security_tasks`, and from there into the summary's `degraded_reason`,
is only the token — never the decode error's message nor any part of the
listing output (NFR3).

### Effect on `file_tasks`

No change to `file_tasks` is expected: an unavailable listing already routes
to the degraded report branch, and the new reason travels that existing path.
The summary keeps its 12 keys; `branch` is `report`, `degraded` is true,
`degraded_reason` is the token, and the CLI ends with `EXIT_OK` (FR5). If
the new token turns out not to reach the summary without a change in
`file_tasks`, that is a plan deviation to report, not a silent widening.

### Docstrings (FR6)

- `ListingOutcome`: the number of unavailable conditions changes from five
  to six, and the list names `listing_output_undecodable` in its position
  from the table above.
- `list_security_tasks`: describes the same six conditions in the same order,
  states that output is received as bytes, and states that stderr is not
  decoded. The two docstrings do not contradict each other.

### Unchanged (NFR1)

- `resolve_main_worktree_root`.
- The process invocation inside `_run_entry_point_with_references` (used for
  `task create` / `task update`) keeps its text-mode capture.

### Test-ID stability (NFR6)

Test IDs recorded in `test-docs/**/*.tests.yaml` must keep resolving. No
existing test class or test method in `tests/test_sca_task_filing.py` is
renamed or removed. The "five" / "other four" wording is updated in
docstrings, comments and assertion messages; if a test method's own name
carries the old count, the name is kept and the sixth condition is added
inside it or in a new method next to it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR3, FR5, FR8, NFR3; TM-1, TM-3): Running the `file-tasks` CLI
  as a subprocess with a stub `--entry-point` whose `task list` exits 0 and
  writes invalid UTF-8 bytes (for example, bytes beginning with 0xFF 0xFE) to
  stdout: the exit code is 0, stderr contains no `Traceback`, and stdout
  parses as exactly one JSON summary with the unchanged 12 keys, `branch`
  equal to `report`, `degraded` true and `degraded_reason` exactly equal to
  `listing_output_undecodable`; the report file is written. With a
  distinctive ASCII marker included in the stub's output, neither the
  summary nor the report file contains that marker or decode-error wording
  (TM-3).
- [ ] AC-2 (FR1, FR3; TM-1): Calling `list_security_tasks` directly with a
  stub whose `task list` exits 0: (a) stdout with invalid UTF-8 bytes
  returns `available=False` and `reason="listing_output_undecodable"`
  without raising; (b) stdout containing a UTF-8-encoded surrogate (bytes
  0xED 0xA0 0x80) returns the same outcome; (c) stdout that is a valid UTF-8
  JSON array containing non-ASCII text returns `available=True` with the
  entries parsed.
- [ ] AC-3 (FR2, NFR2): A `task list` that exits non-zero with invalid UTF-8
  bytes on stdout yields the reason `listing_exit_nonzero`. The existing five
  reason tokens keep their names and the conditions that produce them; their
  existing tests pass without modification of their expectations.
- [ ] AC-4 (FR4; TM-2): A `task list` that exits 0 with stdout `[]` and
  invalid UTF-8 bytes on stderr leaves the listing available: `file_tasks`
  takes the filing branch (`branch` equal to `ntd`) and the target package
  appears in `filed_packages`.
- [ ] AC-5 (FR7): `TestListingUnavailableReasons` in
  `tests/test_sca_task_filing.py` exercises six unavailable conditions (the
  new one: exit 0 with invalid UTF-8 stdout), asserts that each reaches the
  report branch, and asserts that the set of the six reasons has size 6. The
  "five" / "other four" wording in that module reads six; no existing test
  class or method in that module is renamed or removed.
- [ ] AC-6 (FR6): A test asserts that the `ListingOutcome` docstring states
  six unavailable conditions and names all six reason tokens. The
  `list_security_tasks` docstring describes the same six conditions in the
  same order and states that stderr is not decoded.
- [ ] AC-7 (NFR1, NFR4, NFR6): `python3 -m unittest discover -s tests` and
  `python3 em-workflow/scripts/check-plugin-invariants.py .` both pass;
  `resolve_main_worktree_root` and the process invocation inside
  `_run_entry_point_with_references` are unchanged; the added and changed
  tests import only the standard library and contact no external task
  system.
