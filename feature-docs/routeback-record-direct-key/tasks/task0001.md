# Task Plan: task0001 — Restrict the route-back record read to direct keys of tasks.{T}

## Goal

The Stop hook `em-workflow/hooks/queue_stop_guard.py` reads the route-back
record `routeback_failed_journal_line` only from direct keys of the task's own
`taskNNNN:` mapping, so text inside `tasks.{T}.notes` (block scalar bodies,
multi-line quoted scalar continuation lines) or under nested keys no longer
changes the hook's unlaunched / failed classification. Regression tests pin
both directions of the defect (a forged match and a shadowed real record).

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/hooks/queue_stop_guard.py` — record read restricted to direct keys of the task mapping; module docstring item, record-read function docstring and record regex comment updated (FR1, FR2, FR3)
- `tests/test_queue_stop_guard_routeback_record.py` — fixture builder able to emit a non-null multi-line notes value; regression tests for the defect added (FR4)

## Design

No IMPLEMENTATION.md exists for this feature (reduced tier, single task).
This plan is self-contained.

### Direct-key rule (FR1)

Contract of `task_routeback_records_from_workflow` — its input and its
result shape (task id mapped to the record string) stay as they are today;
only which lines count as a record changes.

- Precondition: the existing task-block range logic yields the lines of one
  task's `taskNNNN:` block. That range logic is unchanged.
- Direct-child indentation: the indentation of the first line after the
  `taskNNNN:` key line, within the block, that is neither blank nor a
  comment. It is measured in spaces, the same way the existing block-range
  logic measures indentation (SPEC A1).
- A `routeback_failed_journal_line:` line is a record candidate only when its
  indentation equals the direct-child indentation. A line indented deeper is
  never a candidate, whatever its text. This covers:
  - block scalar bodies of every indicator form: `|`, `|-`, `>`, `>-`, and
    forms carrying an explicit indentation indicator;
  - continuation lines of multi-line quoted or plain scalars;
  - keys of mappings or sequences nested under any direct key.
- The decision uses indentation only; it does not track which key opened a
  block scalar. Consequence (SPEC A1): a line at the direct-child indentation
  that follows an empty `notes: |` is a sibling key of `notes` and is read as
  a record.
- A block with no non-blank, non-comment line yields no record for that
  task.

### Unchanged semantics (FR2)

Among the direct-key candidates of one block, every existing rule holds:

- the first occurrence wins;
- the canonical-value rule: an unquoted ASCII decimal integer whose first
  digit is 1-9, optional trailing whitespace; any other value is no record;
- the block-range rule: step-level lines, top-level lines, sibling-task
  lines, lines after `tasks:` ends, and lines at the task key's own
  indentation are not read;
- the hook's exit codes and stderr format.

The per-task status read (`task_statuses_from_workflow`, `TASK_STATUS_RE`)
behaves exactly as before (SPEC A2). If the direct-key filtering is placed in
a helper the status read also uses, the status read's observable behavior
must not change.

### Constraints (NFR1, NFR2, NFR3)

- The hook keeps importing only the Python standard library and keeps reading
  `workflow.yaml` line by line; no YAML library is introduced.
- Fail-open is preserved: unreadable, broken or malformed `workflow.yaml`
  content never crashes the hook and never causes a block. The indentation
  step adds no new exception path.
- Test code imports only the standard library and imports no other test
  module. Hook behavior is exercised by running the hook as a subprocess with
  the Stop-hook JSON on stdin, per the test README cited by SPEC NFR3.
  Loading the hook module from its file path to call a single function
  directly is allowed only for the function-level criterion (AC-1); the
  precedent is `TestQueueStopGuardOwnershipAmbiguity` in
  `tests/test_queue_stop_guard.py`.

### Docstring and comments (FR3)

Update the module docstring item that reads 'The record is read only from the
task's own `taskNNNN:` block, first occurrence wins', the record-read
function's docstring, and the comment on the record regex. The new text
states that only direct keys of the task's own mapping are read, and that
block scalar bodies and nested lines are not read.

The module docstring keeps containing these phrases, which
`TestModuleDocstring` pins:

- 'only when all three hold'
- '`routeback_failed_journal_line` record'
- 'Any other task whose last event is `failed` is failed'
- "the task's own id, returned from `failed` to `pending` by route-back"

It keeps not containing 'a recycled task id left behind by a route-back
re-plan'.

### Test fixtures (FR4)

- The fixture builder in the test module gains an option to emit a non-null,
  multi-line `notes` value: either a block scalar with a chosen indicator, or
  a multi-line double-quoted scalar. The notes key is placed before the
  record key, following the key order of `workflow-schema.md`.
- When the option is not used, the builder still emits `notes: null`, so the
  fixtures of every existing test are unchanged.
- The nested-mapping case (a record-shaped key one level under another direct
  key) may come from the builder or from fixture text local to that test.
- The journal fixture for the hook-level cases has task0001's `failed` event
  on physical line 1.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1): With the hook module loaded from its file path, `task_routeback_records_from_workflow` returns `{'task0001': '1'}` for (a) task0001 with `status: pending`, a `notes: |` body line `routeback_failed_journal_line: 3` and a direct-key `routeback_failed_journal_line: 1`, and for (b) an empty `notes: |` immediately followed by a `routeback_failed_journal_line: 1` line at the direct-child indentation.
- [ ] AC-2 (FR1, FR4, TM-1): With journal line 1 being task0001's `failed` event, task0001 `pending`, no direct-key record, and a `routeback_failed_journal_line: 1` line placed only in a deeper-indented position, the hook run as a subprocess exits 0 and its stderr contains no BLOCK. The deeper positions checked are: the body of a `notes` block scalar for each of `|`, `|-`, `>`, `>-` and at least one form with an explicit indentation indicator; a key of a mapping nested one level under another direct key; a continuation line of a multi-line double-quoted `notes` value.
- [ ] AC-3 (FR1, FR4, TM-1): With journal line 1 being task0001's `failed` event, task0001 `pending`, and a `notes: |` body placed before the direct-key record: (a) notes body value 3 with direct-key value 1 makes the hook exit 2 with task0001 in stderr's launch list; (b) notes body value 1 with direct-key value 2 makes the hook exit 0.
- [ ] AC-4 (FR2, NFR2, NFR5): Every existing test in `tests/test_queue_stop_guard.py`, `tests/test_queue_stop_guard_routeback_record.py` and `tests/test_queue_hook_status_read_pin.py` passes, and the diff modifies no assertion of an existing test; `python3 -m unittest discover -s tests` passes.
- [ ] AC-5 (FR3): The module docstring, the record-read function docstring and the record regex comment state that only direct keys of the task's own mapping are read and that block scalar bodies and nested lines are not; `TestModuleDocstring` passes, with the four pinned phrases present and the excluded phrase absent.
- [ ] AC-6 (FR4): The fixture builder emits a non-null multi-line `notes` value when asked, and a fixture built without that option still contains `notes: null`.
- [ ] AC-7 (NFR1, NFR3): The hook's import set contains only standard-library modules and no YAML library; the new test code imports only standard-library modules and no other test module; the AC-2 and AC-3 tests run the hook as a subprocess with the Stop-hook JSON on stdin, and only the AC-1 tests load the hook module by file path.

## Test Notes

- AC-1: unit level (module loaded from its file path, one function called).
- AC-2, AC-3: integration level (hook as a subprocess, exit code and stderr
  asserted). Write them first and confirm they fail against the unmodified
  hook: every AC-2 case, AC-3 (a) and AC-3 (b) reproduce the defect today.
  AC-1 (b) already passes before the fix; it pins that the indentation-only
  rule keeps reading a genuine sibling key.
- Per-indicator AC-2 cases are best written as one parameterized test (one
  subtest per indicator) so a failure names the indicator.
- Edge case worth one extra check inside AC-1 or AC-2: blank lines or comment
  lines between the `taskNNNN:` line and its first key do not change the
  derived direct-child indentation.
- AC-4 and AC-5 are covered by the existing suites; AC-6 by a small builder
  test plus the AC-2 / AC-3 fixtures; AC-7 by inspection of the import lines
  and the test structure.
