# Task Plan: task0004 — Validator rejections: feature-docs task files, implement reset on a docs-only round, rename-aware coverage

## Goal

`validate-worker-output.py` mechanically rejects the three rework-planner outputs this feature forbids — a synthesized task whose `files` reach `feature-docs/**`, a docs-only round that returns `implement` to `pending`, and a renamed scenario ID claimed in `covered_by_existing` without a declared rename — with fixtures and unit tests proving each.

## Design

The rules' contracts are IMPLEMENTATION.md Shared Components "Feature-docs files rule", "Docs-only round", "Mixed round", "`payload.doc_corrections`" and "Rename-aware coverage rule". This task changes no prose (Cross-task Design Decision D5); the contract text is owned elsewhere.

### Rule 1 — feature-docs files (FR3, TM-1)

In task-entry validation, for `append` mode (the mode bound to `append_rework`) only: an entry any of whose `files` has `feature-docs` as its first path segment is reported with code `rework-task-feature-docs`, naming the entry and the offending path. Segments are taken with the same normalization the script already applies for allowed-root containment (`\` as a separator, empty and `.` segments dropped), and the comparison is exact segment equality — `feature-docs-archive/x` and `src/feature-docs/x` are not rejected by this rule. `replace_planning` entries are not subject to it.

### Rule 2 — no implement reset on a docs-only round (FR5, TM-2)

In workflow-patch structural validation, for operation `append_rework`: when `tasks_patch.entries` is absent or an empty mapping and any `step_patches` entry has `step_id: implement` with `set.status: pending`, report code `docs-only-implement-reset`. It runs at the structural layer, so it applies with and without `--dry-run-apply` and for both `--kind workflow-patch` and `--kind worker-result`.

### Rule 3 — rename-aware coverage (FR6, FR7, TM-5)

In rework-index validation, build the declared rename relation from `payload.doc_corrections[].scenario_renames` (pairs `from` -> `to`). A `covered_by_existing` ID that is not a key of `verification_index` passes only when a declared pair has it as `to` and that pair's `from` is a key of `verification_index`; otherwise the existing `rework-index` error is reported, its message stating that no declared rename maps the ID to the verification index. The result payload must therefore reach the rework-index check (signature change local to the script). Malformed declarations — `doc_corrections` not a list, an entry not a mapping, `scenario_renames` not a list, a pair not a mapping or missing a non-empty string `from` / `to` — contribute no pair and never raise.

### Fixtures

All six are `worker-result` cases under the `rework-planner` group with `input.json` and `envelope.json` only (no dry run, no feature directory), discovered by the existing runner. None uses `tests_replace` in `requirements_patch` (D4), so each passes in a worktree without the parallel tests-replacement change. The two `valid-` cases are otherwise complete rework-planner results (rework index entry per created task, `shared_contract_rationale`, `implement` step patch for rounds with tasks, base commit preserved). The mixed-round pair differs only in the presence of the `doc_corrections` rename declaration (for example the pre-rename `TS3` in `verification_index`, `TS-3` in `covered_by_existing`).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: TM-1 — for `append_rework`, a task entry whose `files` contain a path whose first normalized segment is exactly `feature-docs` is rejected with code `rework-task-feature-docs`, both when all files are planning documents (TS-2) and when code and planning documents are mixed (TS-3); the leading-`./` and backslash-separator forms are rejected too; `replace_planning` entries are not checked by this rule.
- [ ] AC-2: A code-only `append_rework` task (TS-4) is accepted, and paths `feature-docs-archive/x` and `src/feature-docs/x` do not trigger the rule.
- [ ] AC-3: TM-2 — an `append_rework` patch with absent or empty `tasks_patch.entries` whose `step_patches` set `implement` to `pending` is rejected with code `docs-only-implement-reset` (TS-5), with and without `--dry-run-apply`, through both `--kind workflow-patch` and `--kind worker-result`; a patch with entries that returns `implement`, and an empty-entries patch returning only `verify` or only `review`, are accepted.
- [ ] AC-4: TM-5 — a `covered_by_existing` ID absent from `verification_index` is accepted when `payload.doc_corrections` declares a `scenario_renames` pair with that ID as `to` and a `verification_index` key as `from` (TS-7 valid), and rejected with code `rework-index` without such a declaration or when the declared `from` is not in `verification_index` (TS-7 invalid).
- [ ] AC-5: Malformed `doc_corrections` shapes (non-list value, non-mapping entry, non-list `scenario_renames`, pair missing or blank `from` / `to`) raise no exception and are judged as if no rename were declared.
- [ ] AC-6: The six fixtures listed in Scope exist, their `valid-` / `invalid-` prefixes match their exit codes under the existing data-driven runner, and none contains `tests_replace`.
- [ ] AC-7: `tests/test_rework_docs_only_validator_rules.py` covers AC-1 to AC-5 against the module with asserted error codes, imports only standard-library modules, and every existing fixture and test passes unchanged.

## Test Notes

- Write the invalid fixtures first and confirm they exit 0 before the rules exist (red), then implement.
- AC-3 also exercises the CLI once for `--kind workflow-patch` to prove the rule sits on the structural path.
- Existing valid rework-planner and `append_rework` fixtures all carry task entries and no `feature-docs` files; a failing existing fixture means a rule is too broad.
