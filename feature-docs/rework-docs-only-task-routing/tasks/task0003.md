## Design

The operation's contract is IMPLEMENTATION.md Shared Components "`requirements_patch` tests replacement" and Cross-task Design Decision D3; this task owns both its prose and its validator rendering. The fixture's shape follows Shared Components "Docs-only round" and "`payload.doc_corrections`" (D4).

### `references/workflow-patch.md`

In the `requirements_patch` section: describe the `tests_replace` set key (pairs of `from` / `to`) and the `tests_contains` expected key, the binding of every `from` to `tests_contains`, the dry-run rejection with `expected-mismatch` when an expected ID is absent, and the application order (replacement in place, no duplicate, before `tests_append`). Amend the sentence listing the only operations permitted under `set` so it includes the replacement while keeping the `_append` forms and the direct assignments of `status`, `tbd_reason` and `excluded_reason`. Application rule 3 ("every `expected` value matches") already covers the new expected key; cite it rather than adding a numbered rule (the application rules stay eighteen).

### Validator

1. **Structural layer** (requirements patch handling): add `tests_replace` to the permitted set-key vocabulary (`REQUIREMENTS_PATCH_SET_KEYS`). For each requirement entry carrying it, report a `requirements_patch` error when: the value is not a non-empty list; a pair is not a mapping with non-empty string `from` and `to`; `from` equals `to`; a `from` repeats within the entry; a `from` is not listed in the entry's `expected.tests_contains`; or `expected.tests_contains`, when present, is not a list of strings.
2. **Dry-run layer** (rule 3, beside the existing `tasks_contains` check): when `expected.tests_contains` is present and any of its IDs is absent from the requirement's current `tests` in `workflow.yaml`, report `expected-mismatch`.
3. **In-memory application**: within one requirement entry, apply `tests_replace` before `tests_append`; each `from` is replaced by its `to` at the same position; when `to` is already present, `from` is removed and `to` is not duplicated. Other keys behave as today.

Malformed input never raises (existing convention).

### Fixture `valid-docs-only-round` (TS-1, the reported reproduction)

A verify-sourced docs-only round after a scenario-ID format failure, where three existing tasks are merged and verify failed:

- `workflow.json`: `implement` and `review` completed, `verify` failed with `failed_items` whose `category` is a valid vocabulary value (the validator checks it because the patch targets `verify`); tasks `task0001` to `task0003` present; at least two requirements whose `tests` hold TS-less-hyphen IDs (for example `TS1`, `TS3`).
- `input.json`: `status: completed`, `worker: rework-planner`, `mode_echo: null`; the patch is `append_rework` with `mode: append`, `expected_next_task_id: task0004`, no entries, `requirements_patch` replacing each TS-less-hyphen ID with its hyphenated form under a matching `expected.tests_contains`, a single `step_patches` entry for `verify` (expected `failed`, set `pending`), and `preserve` containing `workflow.implement.base_commit`; payload with `rework_index` as an empty mapping, a `shared_contract_rationale`, and `doc_corrections` with one verify-origin entry listing `VERIFICATION.md`, `tasks/task0001.md`, `tasks/task0003.md` and the renames; `written_artifacts` lists the three corresponding project-relative paths.
- `envelope.json`: echoes the input digest; `verification_index` keyed by the pre-rename IDs; `write_policy.targets` lists the same three project-relative paths, each with `action: replace_own` and an `expect_digest`; `allowed_write_roots` names the feature's `tasks/` directory.
- `digest-source.json` / patch base fields: `base_workflow_blob` equals the digest source's `workflow_blob`, and `base_input_digest` equals the validator's own normalized digest of the digest source (rule R1 normalization).

The fixture uses no task entry, so it is unaffected by the feature-docs files rule, and it returns no `implement` step patch, so it satisfies the empty-entries rule developed in parallel.

### Fixture `invalid-tests-replace-expected-mismatch` (TS-6)

A patch-level dry-run case whose `expected.tests_contains` names an ID the requirement's current `tests` lacks, with base fields consistent with its digest source so that `expected-mismatch` is the only rejection.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `references/workflow-patch.md` documents `tests_replace` (pairs of `from` / `to`) and `expected.tests_contains`, the `from`-to-expected binding, the `expected-mismatch` rejection and the application order, and its list of operations permitted under `set` includes the replacement alongside the unchanged `_append` forms and direct assignments; the numbered application rules stay eighteen.
- [ ] AC-2: TM-3 — the validator accepts `tests_replace` as a requirements-patch set key and reports a `requirements_patch` error for: a non-list or empty value, a pair that is not a mapping with non-empty string `from` and `to`, `from` equal to `to`, a repeated `from` within one entry, and a `from` absent from the entry's `expected.tests_contains`.
- [ ] AC-3: TM-3 — under `--dry-run-apply`, a requirement entry whose `expected.tests_contains` names an ID absent from that requirement's current `tests` is rejected with `expected-mismatch` and no `stale-input-digest` / `stale-workflow-blob` error (TS-6 fixture exits 1).
- [ ] AC-4: In-memory application replaces each `from` with its `to` at the same position, removes `from` without duplicating an already-present `to`, applies `tests_replace` before `tests_append` in the same entry, and leaves `tasks`, `status`, `tbd_reason` and `excluded_reason` handling unchanged.
- [ ] AC-5: The `valid-docs-only-round` fixture exits 0 under the existing data-driven runner with `--dry-run-apply`, with the content described in Design (empty entries, verify-only step patch, tests replacement with expectation, base commit preserved, three written artifacts each covered by a `replace_own` target, payload with empty `rework_index`, `shared_contract_rationale` and a conforming `doc_corrections`).
- [ ] AC-6: Applying the `valid-docs-only-round` patch to its `workflow.json` in memory yields: no task added, `implement` completed, `review` unchanged, `verify` pending, and for each replaced requirement the old ID absent and the new ID present in `tests`.
- [ ] AC-7: `tests/test_requirements_tests_replace.py` covers AC-2 to AC-6 directly against the validator module and imports only standard-library modules; every existing fixture and test passes unchanged.

## Test Notes

- Load the validator module by file path, as `tests/test_validate_worker_output.py` does, and assert error codes, not only exit codes.
- AC-3: assert the returned error codes form exactly the set containing `expected-mismatch`, which proves the fixture's base fields are consistent.
- AC-4 edge cases: replacement where `to` already exists; replacement plus append in one entry; a requirement entry with only `tests_append` behaves as before.
- AC-6 reads the fixture files and calls the module's in-memory application directly; it does not re-implement application logic in the test.
- Write the TS-1 fixture first and watch it fail (unknown set key) before implementing.
