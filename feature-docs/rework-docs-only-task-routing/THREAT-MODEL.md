# Threat Model: rework-docs-only-task-routing

## Verdict
threats-identified

## Rationale
Inspected SPEC.md and REQUIREMENTS.md (FR1-FR9, NFR1-NFR6) at the `full` tier, and the task decomposition in IMPLEMENTATION.md. The feature changes what the rework-planner — an LLM worker whose input includes untrusted review findings and verify failed-item text — may propose and write: it may now rewrite existing planning documents directly, replace requirement test references, and return a patch that leaves `implement` completed. Everything it returns crosses into the orchestrator, which validates it with `validate-worker-output.py` and applies it to `workflow.yaml`. That crossing is the single trust boundary (TB-1). task0003 and task0004 declare `input-handling` (they change the validator), which sets TB-1's depth to deep; no task declares `auth`, `external-io` or `data-persistence`. task0005 changes only the orchestrator's own procedure text (develop SKILL.md, review-phase.md) and adds no crossing. Implementer-side behavior is unchanged (NFR3), so no new boundary exists on the implementer side.

## Trust Boundaries

### TB-1: rework-planner result -> orchestrator validation and workflow.yaml application
Crossing: the rework-planner's result (workflow patch, payload, and the planning documents it writes under `feature-docs/{feature}/`), produced from untrusted findings / failed-item text interpolated into its prompt, crossing into the orchestrator's validator, patch application to `workflow.yaml`, and the next phase's inputs
Boundary files: em-workflow/scripts/validate-worker-output.py, em-workflow/references/workflow-patch.md, em-workflow/references/rework-task-synthesis.md, em-workflow/references/contracts/rework-planner-contract.md, em-workflow/agents/rework-planner.md
Depth: deep (input-handling)

| Denial of service | A synthesized task whose `files` reach `feature-docs/**` is handed to the implementer, which cannot modify those paths, so implement fails with `failed_kind: decision` and the unattended run stops (FR3, NFR3) | TM-1 | The validator rejects any `append_rework` task entry whose `files` contain a path whose first normalized segment is exactly `feature-docs` | task0004 AC-1 | VERIFICATION.md TM-1 (TS-2, TS-3) |

| Tampering | A tests replacement removes or redirects a requirement test reference that the current `workflow.yaml` does not hold, corrupting the requirement-to-scenario trace from a stale or fabricated view (FR4) | TM-3 | Every replaced `from` must be listed in `expected.tests_contains` (structural), and a `tests_contains` ID absent from the current `tests` is rejected with `expected-mismatch` under dry-run | task0003 AC-2, AC-3 | VERIFICATION.md TM-3 (TS-6) |
