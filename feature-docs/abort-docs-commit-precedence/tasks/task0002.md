## Design

### implement-phase.md: the abort terminal-commit exception

**Location.** Inside the Branch & Worktree Model section, at the exit-4 bullet
(the bullet that carries "A second exit 4 stops the phase"). Add it as a
continuation of that bullet or as a sub-bullet immediately after it. Never place
it inside Step I.2.c. The I.2.c batch-mode paragraph and everything after it up
to the end of I.2.c stay byte-identical. The existing bullet phrases stay:

- "A second exit 4 stops the phase"
- "Step I.2.c's abort-phase terminal status commit"
- the carve-out sentence

(NFR2)

**Content.** The exception carries the label "abort terminal-commit exception"
(IMPLEMENTATION.md Shared Components) and states the following:

1. **Definition (FR4).** When the batch second-failure abort's terminal status commit (Step I.2.c abort-phase terminal status commit) hits a second exit 4, the re-applied terminal status write (`implement: failed` / `failed_kind: decision`) stays uncommitted in the integration worktree and is not on the branch.
2. **Named exception (FR4, FR8).** This is the one exception to the claim that the integration worktree never carries uncommitted state across turns. It covers exactly this stop. No other exit-4 call site leaves uncommitted state.
3. **Disposal pointer (FR4).** The leftover is discarded by the resume-entry refresh in develop/SKILL.md Step A. Point to it; do not restate its procedure.
4. **Re-derivation (FR6).** After that discard, the resumed implement phase re-derives the abort only from committed facts:
   - the committed task status;
   - the retry-consumed marker in `tasks.{T}.notes`;
   - the journal (the one implement-phase.md already names).

   It grants no additional automatic retry. It re-applies and commits the terminal status write. When that commit succeeds, the stop follows the existing binding `implement-second-failure` → `implement_task_failed`.
5. **Terminal-line content (FR7).** For this stop:
   - `detail` names the call site (Step I.2.c abort-phase terminal status commit), the failing task(s), and that the terminal status write is uncommitted.
   - `resume_conditions` states that the next run discards the leftover write at develop's resume entry and re-derives the abort from committed facts.

   The binding itself belongs to batch-terminal-line.md's Precedence rule. Cite it; do not restate it.

**Precondition check (a5).** Before writing item 4, confirm from
implement-phase.md's own text that the batch retry-consumed marker is committed
before the second-failure abort runs. If the text shows otherwise, stop and
report a plan deviation. Do not weaken item 4.

### develop/SKILL.md: resume-entry refresh (FR5)

**Location.** Step A's bootstrap check, in the branch for an existing feature
whose integration worktree exists and holds a workflow.yaml ('workflow.yaml
存在する（通常の再開）'). The refresh is placed before the hand-off to Step A.5
in text order.

**Content.**

- Refresh the integration worktree with `git -C {integration worktree} reset --hard em-workflow/{feature}/integration`. The worktree placeholder follows the notation SKILL.md already uses for the integration worktree path.
- State what the refresh is for: it discards any leftover terminal status write left by the abort terminal-commit exception.
- State when it runs:
  - on every resume through this branch, whether the resuming run is batch or interactive;
  - not gated on detecting that stop;
  - before Step A.5 reads or commits anything, and before Step B reads workflow.yaml.
- State that it discards tracked uncommitted changes only; untracked files remain.

**Constraints.**

- The refresh targets the branch name, not a captured commit id, which is the same form the existing refreshes use. Capture no tip here, because no commit follows within this step. Existing refresh-idiom tests (tests/test_tip_capture_idiom_uniformity.py) must stay green.
- The SKILL.md exit-4 リカバリ pins stay untouched (NFR2).
