# Task Plan: task0001 — Planner re-planning branch key and high-water mark cite their owner

## Goal

The implementation-planner prompt and its contract document stop restating the
re-planning decision rule and the high-water-mark definition, and instead cite the
owning document; the test that currently pins the erroneous restatement is updated to
assert both owner-defined paths.

## Requirements

FR1, FR10, NFR2, NFR4, NFR5

## Scope

### Files to Modify
- `em-workflow/agents/implementation-planner.md` — the task-id allocation branches stop naming the erroneous step-status literal and stop restating the high-water-mark formula; both cite the owning document instead
- `em-workflow/references/contracts/planner-contract.md` — the re-planning sentence is aligned to the same citation form
- `tests/test_replanning_producer_alignment.py` — the two-branch test stops pinning the erroneous literal and asserts both owner-defined paths; new coverage is added for the citation form and for an end-to-end acceptance check

## Design

**What is wrong today.** The prompt keys its second task-id allocation branch on a
single step-status literal. The owning document permits that branch through two
distinct states, and the state the specification-change transition actually produces is
the other one. A planner following the prompt therefore takes the initial-planning
branch on a real re-planning pass and emits a patch that is rejected when applied. The
same file also restates the high-water-mark definition in a form that disagrees with
the owning definition, which counts identifiers that have been retired.

**What replaces it.** Both branches are keyed by citing the owning document's
re-planning path by repository-relative path and section name, so that the planner
follows whatever that document defines without the prompt carrying a copy of the
condition. The high-water mark is likewise referred to by citing its owning definition;
no formula, and no characterization of which identifiers it counts, survives in the
prompt. The contract document's corresponding sentence is aligned to the same citation
form. The decision rule's ownership does not move.

**Explicitly not adopted.** Passing the resolved path to the planner as a new dispatch
input field. No new input field is defined, and the prompt's read-restriction is
unchanged.

**Coverage.** The existing two-branch test currently asserts the presence of the
erroneous literal, which freezes the defect in place; it is rewritten to assert that
both owner-defined paths are reachable from the prompt and that no step-status literal
is used as the branch key. A separate assertion covers the absence of the restated
high-water-mark formula from the prompt, paired with a negative proof against a
synthetic sample that still carries it. An acceptance-level check drives the validator
in its dry-run apply mode over a synthetic re-planning patch representing the
specification-change transition — the create-plan step at the status that transition
produces, with at least one already-merged task — and asserts the patch is accepted and
that neither the registered-identifier rejection nor the dropped-task rejection is
raised. Any spec-change record this check builds follows the synthetic-record contract
in IMPLEMENTATION.md Shared Components.

## Test Notes

- AC-1 through AC-4 are structural assertions over Markdown, which is the correct form
  here: the deliverables are a prompt and a contract document, not running code.
- AC-3's pre-change failure is the point of the task. Write the assertion first and
  confirm it fails against the unmodified prompt before changing the prompt.
- AC-5 is an integration-level check: it invokes the validator rather than asserting
  over text. Keep it inside this task's own test module so it does not depend on a
  module another task owns.
- Read every document live from the working tree. An assertion satisfied by a frozen
  revision does not detect drift and does not satisfy this task.
