# Task Plan: task0008 — Patch-apply state checks: evidence-based recovery, scoped category enforcement

## Goal

The two patch-apply-time checks that read state the incoming patch does not
own stop misjudging it: the interrupted-authorization recovery recognizes an
applied patch by the applied-determination its owning document defines instead
of by a blob mismatch, and the verify-category enforcement stops rejecting
patches over pre-existing `failed_items` entries no worker can repair.

## Design

### A. The recovery rule's recognition condition (FR5, FR11, NFR2)

**The defect.** The recovery rule recognizes "this patch has already been
applied" from the conjunction of (i) the base-workflow-blob check failing and
(ii) the authorization still standing. Neither conjunct is evidence that this
patch landed. The blob is a worker-supplied value that the blob check exists to
verify, and the live workflow record's blob changes for many ordinary reasons
between a patch being built and applied — a step status update, an artifact
commit, an unrelated patch. Any of those turns a legitimate rejection into
"already applied, not yet spent": the orchestrator performs only the
authorization-spending write, reports success, and burns the one authorization a
specification change grants without ever re-planning. After that the re-planning
path no longer has a standing authorization and the initial-planning path is
barred by the merged tasks, so the feature cannot be re-planned at all. The
same rule also states that spending an already-spent authorization is a no-op
followed by "under either recognized case", which reads as making a bare blob
mismatch a recognized case once the authorization is spent — i.e. as disabling
the blob check outright. Finally, the rule sits inside a list declared to apply
"in order", yet its whole effect is to overturn an earlier rule in that list,
and it defines an already-applied determination that another document already
owns.

**The fix, three parts.**

1. **Recognition by the owning determination, keyed by patch identity.** The
   recovery is recognized only when the applied-determination owned by
   `references/phase-state.md` — the resume input "whether a patch is already
   applied", backed by the recorded per-patch entry whose status is `applied` —
   returns applied FOR THE PATCH IN HAND, matched on the patch's own identifier,
   AND the authorization record still stands. The condition names that
   determination by repository-relative path and does not restate how it is
   computed. No new field is introduced anywhere: the per-patch record with its
   identifier and status is already defined by that document.
2. **A blob mismatch is not evidence.** The rule states explicitly that a
   base-workflow-blob mismatch which the applied-determination does not confirm
   remains an ordinary rejection under the numbered rule that owns it, and that
   no authorization is ever spent on a rejected patch. The already-spent no-op
   arm is scoped inside the recognized case, so it can never be read as a
   standalone recognized case.
3. **Out of the ordered list.** The recovery procedure is not one of the
   numbered rules. It becomes a section of its own, so nothing inside a list
   that applies "in order" overturns an earlier member of that list, and the
   list's count statement returns to the number of numbered rules it actually
   holds. The idempotency substance the rule already carries — only the
   authorization-spending write is re-run, a repeat is a no-op and not an error,
   and the state after any number of resumptions equals the state after one
   uninterrupted run — is carried over verbatim in meaning.

The ownership-boundary section keeps covering the crossing into the phase-state
document (FR11); where it names the crossing by rule number it follows the
relocation, and it still names the orchestrator as the owning side.

### B. The category check's applicability (FR3, NFR1, NFR2)

**The defect.** The check runs over the live workflow record's verify-step
failing items on every invocation that supplies that record, regardless of what
the patch contains. The required-category field is newer than the records it
judges: a feature whose verify phase recorded failing items before the field
existed carries entries without it. Every patch that feature's workers produce
is then rejected with an error about a field the patch never mentions. A worker
cannot fix it — the workflow record is orchestrator-owned and a step patch may
set only a status — so an unattended run loops on re-dispatch until it gives up.
No fixture in the corpus carries a failing item at all, which is why no test
ever walked this path.

**The fix.** The check's applicability is scoped to what the patch reaches: it
contributes an error for a failing item the patch itself supplies, or for the
entries of a verify step the patch targets. A pre-existing entry that the patch
neither supplies nor targets contributes no error. Fail-closed strength is
unchanged (NFR1): the check keeps rejecting every non-conforming value inside
the patch's reach, the definition of the field and its vocabulary are untouched,
and the classification gate's abort on a missing, unreadable or out-of-vocabulary
category — the arm NFR1 actually rests on — is not on this task's surface at all.

**The owning statement (NFR2).** The scoping rule is not the validator's to
invent. The document that owns the field's meaning and required-ness gains the
pre-change compatibility rule that this scoping implements: an entry recorded
before the field was defined is a pre-change record; it is not made conforming
by being read, and it is not the patch-validation surface's to reject, because
the party receiving the rejection cannot repair it; conformance is restored the
next time the verify phase writes the list, and the fail-closed treatment of a
missing category happens at the point of use. The validator cites that section
rather than restating it — this is the same shape the phase-state document's
format-version compatibility rule already takes for its own destructive shape
change.

  both sides). The existing wiring test asserts the check runs on the
  workflow-reading path rather than only under dry-run apply; keep that intent

  cleanly.

  final; refresh them last, in one pass, and touch no other pinned constant.
