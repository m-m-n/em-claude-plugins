# Task Plan: task0005 — Phase-state: format-version compatibility rule and classification replay rule

## Goal

The phase-state document states explicitly what happens to an on-disk rework record
written before the destructive shape change, so no in-flight feature is left silently
non-re-enterable, and it defines the replay rule for the append-type classification
record that the idempotency section currently omits.

## Design

**The problem.** The spec-change record's shape changed destructively — the origin pair
became mandatory and the classification record became an append-type list — while the
format version stayed at its current value. Nothing in the document says what becomes
of a record already on disk in the pre-change shape, so an in-flight feature's record
silently stops being usable for re-entry.

**The chosen resolution (IMPLEMENTATION.md D5): a stated compatibility rule.** The
format version does not move. The document gains an explicit statement that:

1. a record written before the shape change is still read as the current version — it is
   not treated as an unknown version and does not produce a plugin version mismatch;
2. its pre-change spec-change shape is refused at the point of use by the fail-closed
   conditions that already require the origin pair to be present and non-empty, and that
   refusal carries a named diagnostic identifying the pre-change shape as the cause
   rather than reporting a generic missing field;
3. the remedy is named in the same place: the spec-change transition rewrites the record
   wholesale on its next occurrence, which this document already guarantees, so a
   well-shaped record replaces the pre-change one and re-entry is restored;
4. the outcome is never a silent one — every refusal states its reason and its remedy.

The same statement covers the classification record's shape change: a pre-change record
whose classification is not in the append-type shape is refused on the same terms, with
the same diagnostic and the same remedy.

The resolution is deliberately confined to this document. It requires no change to the
validator, to any fixture, or to the declared format version, because the refusal it
describes is the behavior the existing fail-closed conditions already produce — the
document is stating it, not creating it. Restating any of those conditions here is
forbidden; cite their owners.

**The classification replay rule.** The idempotency section covers every persisted
record except the classification list, which is the only append-type record with no
defined replay rule. Add its rule: state what a repeated write of the same pass must do,
state whether re-appearance of an identical entry is a no-op or a protocol error, and
state that a resumed run produces the same list as an uninterrupted one. Keep it
consistent with how the section treats the other append-type records, and do not
restate the record's field definitions, which the field table already owns.

**Coverage.** A new module pins the compatibility rule's four points, the named
diagnostic, the named remedy, and the classification replay rule's substance, each with
a negative proof against a synthetic document that omits it. This module reads the
document live.
