keyed by citing the owning document's `replace_all` permission conditions, so
the Initial-planning branch no longer matches a state that belongs to the
Re-planning path.

## Design

**The defect.** The owning document permits `replace_all` through two named
paths. Its Initial-planning path is keyed on the `create-plan` step being
`pending` AND a floor condition on task status (no tasks, or every task
`pending`). Its Re-planning path is satisfied by two states, one of which is
also `create-plan` reading `pending`. The prompt copies only the first half of
the Initial-planning key — the step status — and drops the floor condition, so
the two branch conditions as written in the prompt overlap. A planner reading
the prompt literally on a specification-change re-entry matches the
Initial-planning branch, which appears first, numbers from the first task id
and emits no carry-over declaration — reproducing exactly the two apply-time
rejections FR1 exists to prevent. The prompt is additionally self-contradictory:
the Re-planning branch states that the condition is "not restated here as a
single `create-plan` status literal" while the branch directly above restates
one.

**The fix.** Both branches become citations of the same owner, in the same
form. The Initial-planning branch names the owning document by
repository-relative path and identifies its Initial-planning path as the source
of the condition, and states that which states satisfy that path — including
its floor condition on existing task status — is owned there and is not
restated in the prompt. Neither branch carries a bare step-status literal as its
key. Everything else in the branch bodies (numbering from the first task id on
one side; the carry-over declaration, the disjointness of the two id sets and
the cited high-water mark on the other) is unchanged.

**Ownership (IMPLEMENTATION.md D1, NFR2).** The prompt is a citing site, never
an owner. This task writes no condition text of its own into the prompt and does
not touch the owning document.

**Test alignment.** The existing two-branch pin asserts the literal's presence
and therefore freezes the defect. It is replaced — not deleted — by assertions
over the same section: both branch headers still present; each branch cites the
owning document by path and names the path it defers to; neither branch carries
a step-status literal as its key; and a synthetic branch containing the literal
is detected by the same matchers (non-vacuity, per IMPLEMENTATION.md's negative
proof convention). The class's existing Re-planning assertions and the
high-water-mark assertions stay as they are.
