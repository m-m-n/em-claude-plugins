## Design

Contract: IMPLEMENTATION.md C9.

- **Allow rule**: a command segment gets allow only when all of these hold.
  - **Token allow-list**: the segment is exactly the tokens `gh`, `pr`, `merge`, a positive decimal PR number, `--merge`, `--match-head-commit` and a 40-lowercase-hex SHA, in the canonical order. Anything else fails the allow-list:
    - an extra token, including short flags (`-s`, `-r`, `-d`) and `--repo` / `-R`
    - `--admin`, `--auto`, `--squash`, `--rebase` or `--delete-branch` in any spelling
    - a `=`-joined option form
    - an environment-variable assignment prefix
  - **Working directory**: the payload's working directory, after normalizing `.` and `..` segments, has `.claude/worktrees/em-workflow/<feature>/integration` as a path suffix or as a prefix of deeper paths. `<feature>` must match `^[a-z0-9][a-z0-9-]*$` and the segment after it must be exactly `integration`.
- **Fallback**: anything that misses the allow-list or the working-directory condition falls back to the guard's existing judgment for `gh pr merge`: ask, and deny under CLAUDE_BATCH.
- **Segment continuation**: an allowed merge segment does not end evaluation. Every other segment of the same command is still judged, and the command's decision is the most restrictive one across segments.
- **Case format**: existing three-element cases stay valid and unchanged. A case may carry an optional fourth element that sets the working directory and / or CLAUDE_BATCH for that case. The runner applies them when building the hook payload and environment. The path-argument mode for checking another copy of the guard keeps working.
- **Docs**: README's destructive-guard row and hook-tests.md's case-format rule describe the new behavior and format in one or two sentences each.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The canonical form is allowed from an integration worktree, with and without CLAUDE_BATCH (TS9, TM-8):
  - `gh pr merge 42 --merge --match-head-commit <40 hex>` with the working directory at `<root>/.claude/worktrees/em-workflow/demo/integration` → allow
  - the same from a subdirectory of that worktree → allow
- [ ] AC-2: Each of these variants evaluates to ask without CLAUDE_BATCH and deny with it (TS10, TS22, TM-8):
  - the canonical form plus any one of `--admin`, `--auto`, `--squash`, `--rebase`, `--delete-branch`, `-s`, `-r`, `-d`, `--repo x/y`, `-R x/y`, or an unknown extra token
  - an environment assignment prefix such as `GH_REPO=x/y`
  - the SHA missing, 39 or 41 characters long, or non-hex
  - the PR number missing or non-numeric
  - the working directory at the main tree or another path
- [ ] AC-3: The canonical form from an integration worktree followed by a dangerous segment (`&& git push --force ...`, `; rm -rf <path>`) gets that segment's existing deny / ask decision, never allow. (TS10, TM-9)
- [ ] AC-4: Each of these working directories evaluates to ask (deny under CLAUDE_BATCH) for the canonical form (TS22, TM-10):
  - a path that only reaches the integration shape through `..` segments, or that leaves it through `..`
  - a feature segment failing the pattern
  - a path whose segment after the feature is not exactly `integration`
- [ ] AC-5: The runner accepts the optional per-case working directory / CLAUDE_BATCH element. Every pre-existing case passes unchanged, and the path-argument mode still checks a given guard copy. (NFR6)
- [ ] AC-6: Every pre-existing deny / ask case is still present, and `python3 em-workflow/hooks/tests/run-destructive-guard.py` passes. README's destructive-guard row and hook-tests.md's case-format rule describe the change. (NFR6, FR23)
