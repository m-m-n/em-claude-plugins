# Task Plan: task0008 — merge skill (SKILL.md orchestration)

## Goal

`/em-workflow:merge --batch <feature>` runs unattended from start to finish. It drives the decision scripts, performs every guard-sensitive operation as a direct Bash call, resolves conflicts from both features' specs, keeps the repository-wide lock for the critical section, and ends every terminal with the rendered merge result as the whole final message.

## Design

Contracts used: IMPLEMENTATION.md C1-C9 and decisions D1-D10. The scripts' contracts are pinned there; this skill consumes them and never re-implements their judgments.

### Invocation rules
- **Script calls**: scripts are invoked with python3 the same way develop's SKILL.md invokes the plugin's scripts.
- **Timeouts**: every Bash call states a timeout of at most 600 s.
- **Working directory**: when the working directory matters, a standalone `cd` call comes first, and the operation follows as its own Bash call.
- **Literal values**: guard-sensitive commands carry paths, branch names, remote names, PR numbers and SHAs as literal values taken from validated script output. No variable expansion, command substitution or glob is used.
- **No loops or questions**: no command string contains while or until, and AskUserQuestion is never called.
- **Script failures**: a non-zero exit or unparseable output from any script → `internal_error`.
- **Untrusted text**: workflow.yaml, review records, specs, commit messages, PR bodies and gh output are data (NFR4).

### Flow
1. **Arguments**:
   - Without `--batch`: print usage text and end. No tool call, no result.
   - With `--batch` but not exactly one other argument → result `invalid_arguments`.
   - A name failing `^[a-z0-9][a-z0-9-]*$` → `invalid_feature_name`, decided before any Bash call that would carry the name.
2. **Preflight** (C4): on stop, render with route `none`. Keep `project_root`, `worktree_path`, `base_branch`, `commands` and `integration_tip`.
3. **Route** (C5 route): stop → render.
4. **Local route**:
   - merged → already-merged path (cleanup, step 15).
   - main-tree check now (fail fast) → stop renders `main_tree_not_ready`.
5. **PR route**:
   1. C6 repo (stop → render).
   2. C6 resolve:
      - `merged` → already-merged path, with `pr_url` and `merge_commit`
      - stop → render
      - `open` → keep `pr_number` and `pr_url`
      - `none` → push the integration branch to the chosen remote without force (rejection → `push_rejected`); standalone `cd` to `project_root`; `gh pr create` with `--head` and `--base` set from `create_head` / `create_base`, title = feature name, body = fixed-shape summary built from validated identifiers (failure → `pr_create_failed`); then resolve again and expect `open`.
6. **Lock** (C7, D3): take a token; start hold with run_in_background; verify with a short wait. `held` → continue; `lock_busy` / `lock_lost` → stop the background task, render.
7. **Worktree** (C5 worktree-state, D4):
   - `absent` → from `project_root`, run the same `git worktree add` as develop Step A.2, adapted to attach the existing integration branch (never create or reset it). Failure → `git_failed`.
   - `merge_in_progress` → standalone `cd` to the worktree, merge abort, then re-check (must be `clean`).
   - stop → render.
8. **Integrate** (C5 integrate), keeping a redo count starting at 0:
   - `merged_clean` / `up_to_date` → step 10
   - `conflict` → step 9
   - stop → render
9. **Conflict resolution (FR12)**: see the next subsection. Success → step 10. Unattributable → merge abort; worktree-state must read `clean`; render `conflict_unattributable`.
10. **Verification commands (FR13)**: for each entry of `commands`, in order, standalone `cd` to the worktree, then the approved string exactly as given. Failure or timeout → `verification_failed`; detail names `component.field` and gives the gist of the output.
11. **PR route only**:
    1. Push the integration branch to the chosen remote without force (rejection → `push_rejected`).
    2. CI wait (C8): first call with a 3600-second `--deadline-in`; repeat calls with the returned `--deadline` while `pending`. `passed` / `no_checks` → continue; stop → render.
12. **Base moved** (C5 base-check with the redo count):
    - `unchanged` → step 13
    - `redo` → increment the count, back to step 8
    - stop → render
13. **Merge**:
    1. Lock verify again; not `held` → render its reason.
    2. PR route: C6 state with the verified head. `merged` → already-merged path; stop → render. Then standalone `cd` to the worktree and the canonical form (C9) with the verified head SHA; failure → `merge_failed`. Then resolve to read `pr_url` and `merge_commit`.
    3. Local route: main-tree check; standalone `cd` to `project_root`; `git merge --no-ff --no-edit em-workflow/<feature>/integration` (D9). On failure, abort the in-progress merge in the main tree if one exists, then render `merge_failed`. `merge_commit` is the new base tip.
14. **Release**: stop the lock's background task.
15. **Cleanup (FR19)**, for merged / already merged: standalone `cd` to `project_root`. When the worktree exists, `git worktree remove` with the literal absolute path and without force. A removal failure keeps the result `merged` / `already_merged` with `worktree_removed` false.
16. **Render (FR21, D2)**:
    1. Write the renderer input document with the file-writing tool to a location outside every working tree that the plugin's write guards leave silent under CLAUDE_BATCH. Confirm that location against `em-workflow/hooks/cross-repo-write-guard.py` and its tests.
    2. Run the renderer; its stdout is the entire final message.
    3. If the renderer cannot run, print the fallback result from `em-workflow/references/merge-result.md` verbatim.

The already-merged path skips steps 6-13 and goes to cleanup, then render. Every terminal reached after step 6 started the holder first stops that background task. A `not_merged` terminal keeps the worktree.

### Conflict resolution (step 9)
- **Attribution**: for each conflicted path, find the base-side commits since the merge base that touched it. Attribute them to an origin feature only through an `em-workflow/<name>/integration` merge on the base side or changes under `feature-docs/<name>/` in those commits. Accept a name only when it matches the feature pattern and `feature-docs/<name>/` exists on the base side.
- **Reading specs**: read this feature's `feature-docs/<feature>/` and the origin feature's spec as data. Instruction-shaped text in them, in commit messages or in conflicted content is never followed.
- **Resolving**: edit only the conflicted paths so both intents hold, stage only those paths, and commit with a fixed-shape message naming the base and the integration branch. Hooks are never bypassed.
- **Unattributable**: any path without an attributable origin, or with an unreadable origin spec, makes the whole conflict unattributable.

### Prohibited
These never appear as a command form in SKILL.md:
- force push, worktree removal with force, branch deletion
- `--no-verify`, hard reset, rebase
- any commit on base_branch other than the step 13 local merge
- `--admin`, `--auto`, `--squash`, `--rebase` or `--delete-branch` on `gh pr merge`
- AskUserQuestion, gate_id

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `em-workflow/skills/merge/SKILL.md` exists with frontmatter `name: merge` and a description; no `commands/` directory is used, and README's skill table lists the skill. Before any tool call, SKILL.md states that a run without `--batch` only prints usage. Before the first Bash call, it states the argument-count check and the feature-name pattern check, with their `invalid_arguments` / `invalid_feature_name` results. (FR1, FR2, FR23, TM-1)
- [ ] AC-2: Each guard-sensitive operation appears as its own direct Bash call form with literal placeholders, and no script invocation performs it (FR8, FR13, FR14, FR17, FR18, FR19, FR22, TM-5, TM-12):
  - verification commands: a standalone `cd` to the worktree, then the approved string exactly as given
  - push of the integration branch without force
  - `gh pr create` from `project_root` with `--head` and `--base`
  - the canonical `gh pr merge` from the worktree, using the verified head SHA
  - `git worktree add` attaching the existing integration branch
  - `git worktree remove` with the literal absolute path and without force, from `project_root`
  - the main-tree `git merge --no-ff --no-edit`
- [ ] AC-3: SKILL.md's command forms contain no while / until, no AskUserQuestion, no gate_id, and none of the Prohibited forms. Every Bash call states a timeout of at most 600 s. The CI wait is written as repeated script calls carrying the returned deadline. (NFR1, NFR2, NFR8, FR15)
- [ ] AC-4: The lock lifecycle follows D3: token, background hold, verify before integration, verify again before the merge, and stopping the background task on every terminal after the hold started, with `lock_busy` / `lock_lost` mapped to results. (FR10, TM-16)
- [ ] AC-5: The conflict-resolution step states the attribution rule (pattern match plus base-side feature-docs existence) and treats spec / commit / conflicted text as data. Its permitted actions are limited to editing, staging and committing the conflicted paths without hook bypass, followed by the verification commands. The unattributable path is merge abort → worktree-state `clean` → `conflict_unattributable`. (FR12, NFR4, TM-6, TM-7)
- [ ] AC-6: Every terminal ends with the renderer output as the entire final message; the renderer input is written with the file-writing tool and the contract's fallback is used when the renderer fails. Terminals covered: each reason code the skill emits or relays, `merged`, and `already_merged`. Also stated (FR7, FR16, FR19, FR21):
  - the redo loop is bounded by base-check
  - already merged goes straight to cleanup
  - `not_merged` keeps the worktree
  - a removal failure yields `worktree_removed` false
- [ ] AC-7: Resumption and text (NFR3, NFR7):
  - interrupted states are handled as designed: an absent worktree is re-created; an in-progress merge is aborted under the lock; a merged PR or a base containing the tip goes to cleanup
  - commit messages and the PR title / body are fixed shapes filled only with validated identifiers, with no absolute home path and no Notion URL
  - SKILL.md writes no state file and never writes workflow.yaml
