# Task Plan: task0005 — Repository-wide merge lock

## Goal

`merge-lock.py` serializes merge runs per repository with a lock that a background holder process keeps from base integration through the merge. Each run can prove, with its own token, that it is the current holder.

## Requirements

FR10, FR22, NFR5

## Scope

### Files to Create
- `em-workflow/scripts/merge-lock.py` — subcommands token, hold, verify (IMPLEMENTATION.md C7)
- `tests/test_merge_lock.py` — unit tests running holders as child processes of the test

### Files to Modify

## Design

Contract: IMPLEMENTATION.md C1, C2, C7; decision D3.

- **Files**:
  - the lock target is `em-workflow-feature-merge.lock` in the repository's common git directory, so every worktree resolves the same file
  - the holder record is a sibling file
  - `em-workflow-merge.lock` (merge-task.sh) is never opened
- **token**: prints a fresh random 32-hex token.
- **hold**:
  1. Open the lock target without truncating it and try an exclusive, non-blocking lock.
  2. When busy, read the holder record and print stop `lock_busy` with `holder_feature` (empty if unreadable), then exit 0 at once without touching the record.
  3. When acquired, write the holder record by atomic replacement: feature, token, the holder's process id, and the acquisition time with UTC offset. Then print outcome `acquired`.
  4. Wait without consuming CPU until terminated. The operating system releases the lock when the process ends; TaskStop and session end both release it.
- **verify**:
  - Read the holder record and check whether the recorded process is alive, using a signal-free liveness check. Never take the lock.
  - Record carries this token and its process is alive → `held`.
  - A live process with another token → stop `lock_busy` (with `holder_feature`).
  - Otherwise, when no live holder carries this token: keep polling until `--wait` seconds elapse (default 0), then stop `lock_lost`. This covers a missing record, a dead holder, or a holder that has not started yet.
  - A partially written or unreadable record counts as "not yet" while waiting.
- **Operation boundary (FR22)**: no git command other than locating the common git directory; no push, PR or worktree operation.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: token prints a 32-lowercase-hex token, and two calls return different tokens.
- [ ] AC-2: hold, started from a linked worktree of a temporary repository, takes the lock on `em-workflow-feature-merge.lock` in the common git directory and writes a holder record carrying feature, token, process id and an offset-qualified time. It does not create or lock `em-workflow-merge.lock`. (FR10)
- [ ] AC-3: While a holder for feature `a` is alive, hold for feature `b` returns at once with stop `lock_busy` and `holder_feature` `a`, and leaves the record unchanged. verify with `b`'s token returns stop `lock_busy`. (TS8, TM-16)
- [ ] AC-4: Holder liveness is checked against the token (TS23, TM-17):
  - verify with the live holder's token → `held`
  - after the holder process is terminated → `lock_lost`
  - a record left by a dead process makes verify return `lock_lost` for any token, and a new hold then succeeds
- [ ] AC-5: A second run of the same feature, with its own token, gets stop `lock_busy` from hold. verify with the second token returns `lock_busy`, never `held`. (TS23, TM-17)
- [ ] AC-6: verify with `--wait` returns `held` once a holder that starts slightly later carries the token, and returns `lock_lost` within the wait bound when none does. While holding, the holder process stays idle (it does not spin). The script makes no push, PR or worktree operation. (TS20)

## Test Notes

- Holders run as child processes the test starts and terminates through its process API; no shell kill is involved.
- Wrap every wait in a short test timeout so a failing case cannot hang the suite.
- The "slightly later" case in AC-6 starts verify first and the holder after a brief delay inside the test.
- Idleness can be asserted by sampling the holder's CPU time (from the process API or its status) before and after a short sleep.

## Out of Scope

- Where in the merge flow the lock is taken or released (SKILL.md).
- Any lock waiting or queueing beyond `--wait`; retries are the dispatcher's job (A22).
