# Task Plan: task0006 — Bounded CI wait

## Goal

`merge-ci-wait.py` waits for the PR checks of the pushed head, one bounded invocation at a time, against an absolute 60-minute deadline. It reports pass, no checks, still pending, failure, timeout or a moved head.

## Requirements

FR15, FR22, NFR1, NFR5

## Scope

### Files to Create
- `em-workflow/scripts/merge-ci-wait.py` — bounded CI wait (IMPLEMENTATION.md C8)
- `tests/test_merge_ci_wait.py` — unit tests with a PATH-stubbed gh and short timing values

### Files to Modify

## Design

Contract: IMPLEMENTATION.md C1, C2, C8; decision D7.

- **Deadline**: `--deadline-in` (first call) computes now + seconds; `--deadline` (later calls) is used as given. Every outcome echoes `deadline`.
- **Budget**: one invocation returns by min(deadline, start + `--budget`), and the default budget keeps it under the 600 s Bash limit. Every gh call has its own time limit that fits inside the remaining budget.
- **Each poll**:
  1. Read the PR head through gh for `--repo` / `--pr`. When it differs from `--head`, stop `pr_head_moved`.
  2. Read the PR's checks and group them by gh's result category: passing or skipped count as pass; failing or cancelled count as fail; anything else counts as pending.
- **Decision per poll**:
  - any fail → stop `ci_failed`, detail naming the failed checks (names only)
  - all pass, at least one check → `passed`
  - zero checks, while the time since this invocation's first poll is below `--settle` → keep polling
  - zero checks once that time reaches `--settle` → `no_checks`
  - otherwise pending → sleep `--interval`, then poll again
- **End of invocation**:
  - deadline reached with checks still pending → stop `ci_timeout`
  - budget exhausted before the deadline → `pending`
- **No busy loop**: the script sleeps between polls.
- **Operation boundary (FR22)**: only read operations through gh. The skill repeats invocations; no command string loop exists anywhere.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Zero checks before and after the settle window → `no_checks`. Checks that first appear inside the settle window are waited on rather than reported as `no_checks`. (TS6)
- [ ] AC-2: Every check passing or skipped → `passed`. Any check failing or cancelled → stop `ci_failed`, with the failed check names in detail. (TS6)
- [ ] AC-3: The deadline carries across invocations (TS6, TS25, TM-13):
  - checks pending past the per-call budget but before the deadline → `pending`, carrying the same absolute deadline the call computed from `--deadline-in` (or received through `--deadline`)
  - a following call given that deadline continues and can reach `passed`
  - a call whose deadline passes while checks are pending → stop `ci_timeout`
- [ ] AC-4: A gh stub that hangs makes the invocation still return within its budget plus a small margin, as `pending` or `ci_timeout`. With the default budget, an invocation's worst-case duration stays below 600 s. (TS25, TM-13)
- [ ] AC-5: A PR head reported by gh that differs from `--head` stops `pr_head_moved` before checks are evaluated. (TS25, TM-12)
- [ ] AC-6: The gh stub's invocation log contains only read operations on the given repository and PR, and polls are separated by the interval (no busy loop). (TS20)

## Test Notes

- Tests pass small `--budget`, `--interval` and `--settle` values (fractions of a second to a few seconds) so the suite stays fast.
- The gh stub answers from a per-test script of responses (for example "pending, pending, pass") keyed by call count, and logs its arguments.
- AC-4's default-budget bound is checked from the script's documented default value, not by waiting 540 s.

## Out of Scope

- Pushing, merging, and deciding what to do after `passed` / `no_checks`.
- Distinguishing required from optional checks; every reported check counts.
