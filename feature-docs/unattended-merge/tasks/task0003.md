# Task Plan: task0003 — Local git decisions and base integration

## Goal

`merge-git.py` provides the git-side decisions of a merge run:
- which remote to use, or the local route
- whether the local route is already merged
- the integration worktree's state
- integrating the base into the integration branch
- whether the base moved
- whether the main working tree can take the local merge

A local-route integration test (TS1) proves the chain end to end.

## Design

Contract: IMPLEMENTATION.md C1, C2, C5; decisions D4, D7, D9, D11.

- **route (FR6)**:
  - No remote → `local`. For the local route, base_branch must exist locally, else stop `base_branch_invalid`.
  - Otherwise use base_branch's configured upstream remote when it names an existing remote; an upstream of `.` counts as no upstream.
  - Else, when exactly one remote exists, use it.
  - Else stop `remote_unresolved`.
  - A chosen remote name outside C1's conservative set also stops `remote_unresolved`.
- **merged (FR7, local route)**: `merged` when base_branch already contains the integration branch tip, else `not_merged`. Nothing is modified.
- **worktree-state (FR3, D4)**:
  - Expected path: `<project root>/.claude/worktrees/em-workflow/<feature>/integration`.
  - `absent`: no registered worktree and no directory.
  - `clean`: registered, present, on the integration branch, with no tracked modification and no in-progress operation.
  - `merge_in_progress`: same, but a merge is in progress.
  - Anything else stops `worktree_not_clean` with a detail naming the condition: dirty, another branch or detached HEAD, a directory that is not a registered worktree, or a registration whose directory is missing.
- **integrate (FR11)**:
  - Precondition: the state is `clean`.
  - With `--remote`, first fetch base_branch from that remote and use the fetched tip; without it, use the local base_branch tip. The tip used is reported as `integrated_base`.
  - Merge it into the integration branch inside the worktree as a merge commit (`--no-ff --no-edit`). The message is a fixed shape naming the base and the integration branch.
  - Outcome `merged_clean` (new merge commit; `head` = new tip) or `up_to_date` (base already contained; no commit).
  - On conflict: outcome `conflict` with `conflicted_paths`; the merge stays in progress and `head` is the unchanged tip.
  - Any other failure → stop `git_failed`.
  - Never rebases, resets, force-updates or bypasses hooks.
- **base-check (FR16, D7)**:
  - Fetch first when `--remote` is given.
  - Compare the base tip with `--integrated-base`: equal → `unchanged`; moved with `--redo-count` 0, 1 or 2 → `redo`; moved with `--redo-count` 3 → stop `base_moving`.
  - `current_base` reports the tip observed.
- **main-tree (FR18)**: `ready` only when the main working tree has base_branch checked out and is clean by the same definition develop's local-merge completion step uses (see `em-workflow/skills/develop/SKILL.md`), else stop `main_tree_not_ready` with the reason in detail.
- **Operation boundary (FR22, NFR2)**: the script performs none of these:
  - push, PR operations, worktree add / remove
  - any change to the main working tree
  - rebase, reset, force, hook bypass

### TS1 test design (D11)

- **Fixture**:
  - a temporary repository with no remote, and `.claude/worktrees/` git-ignored as em-workflow projects have it
  - base branch `main` advanced by a non-conflicting commit after the integration branch forked
  - the integration branch carries a completed workflow.yaml
  - the integration worktree is at the expected path
- **Core case**: run route → merged → worktree-state → integrate → base-check → main-tree. Then emulate the skill's direct operations: in the main tree, the main-tree merge of D9; from the project root, worktree removal without force.
- **Full-chain case**: the same sequence preceded by `merge-preflight.py` (proceed expected). When that script is absent, the case is skipped with a reason naming it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: route covers every selection rule (TS5):
  - base upstream set to remote `up` among two remotes → `remote` `up`
  - no upstream with exactly one remote → that remote
  - no upstream with two remotes → stop `remote_unresolved`
  - no remote → `local`
  - no remote and base_branch absent locally → stop `base_branch_invalid`
- [ ] AC-2: merged returns `merged` when the base contains the integration tip and `not_merged` otherwise, and no ref or working tree changes in either case. (TS2)
- [ ] AC-3: worktree-state returns (TS19):
  - `absent`, `clean` and `merge_in_progress` for those fixtures
  - stop `worktree_not_clean` for a dirty worktree, another branch, an unregistered directory and a registration whose directory is missing
  - after a merge abort in a `merge_in_progress` fixture, the state reads `clean`
- [ ] AC-4: integrate handles every case (TS18):
  - a clean case creates exactly one merge commit whose first parent is the previous integration tip and whose second parent is `integrated_base`
  - an already-contained base returns `up_to_date` without a commit
  - a conflicting base returns `conflict` listing the conflicted repository-relative paths, with the merge in progress and the branch tip unchanged
  - with a local bare repository as remote, the fetched tip is what gets integrated
  - the previous tip always stays an ancestor of the new tip
- [ ] AC-5: base-check returns `unchanged` when the tip equals `--integrated-base`. With a fixture that advances the base before every check, redo counts 0, 1 and 2 return `redo` and redo count 3 stops `base_moving`. (TS7)
- [ ] AC-6: main-tree returns `ready` when the main tree is on base_branch and clean. It stops `main_tree_not_ready` when the main tree is on another branch, is detached, or has a tracked modification. (TS14)
- [ ] AC-7: TS1's core case and full-chain case (TS1, TS20):
  - the core case leaves on `main` a merge commit whose second parent is the integration tip
  - the integration worktree directory and registration are gone
  - both branches still exist
  - the full-chain case passes whenever `merge-preflight.py` is present
  - across both test modules, the logged git subcommands of the script contain no push, rebase, reset, worktree add / remove or force option

## Test Notes

- Every test uses its own temporary repository; a local bare repository stands in for a remote, so no network is touched.
- The git logging shim (IMPLEMENTATION.md Conventions) records the script's git subcommands for AC-7.
- For AC-5, the fixture's "advance the base" step runs between script invocations inside the test, never inside the script.

## Out of Scope

- GitHub / PR logic, the lock and CI waiting.
- Performing the main-tree merge, worktree add or worktree removal; those are the skill's direct operations, only emulated by the TS1 test.
- Conflict resolution.
