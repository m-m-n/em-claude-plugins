# Task Plan: task0012 — Move the merge allow rule out of destructive-guard's generic body; real worktree fixtures for its cases

## Goal

The unattended-merge-specific parts of destructive-guard's `gh pr merge` exception (canonical form, integration-worktree path shape, registration check, sole-statement policy) live in their own module beside the hook. destructive-guard itself keeps only a generic call into it. The hook cases and unit tests for the exception run against a real registered integration worktree, so every case passes again.

## Design

Contract: IMPLEMENTATION.md C9 (unchanged: the guard allows exactly the canonical form from an integration worktree; every other shape keeps its decision).

- **Module boundary**:
  - `merge_pr_allow.py` owns everything specific to the unattended merge:
    - the seven-token canonical form and its PR-number / SHA patterns
    - the `.claude/worktrees/em-workflow/<feature>/integration` path shape and its normalization
    - the registration check (the worktree's `.git` file points to a direct child of the project's `.git/worktrees/`, whose HEAD is `refs/heads/em-workflow/<feature>/integration`)
    - the policy deciding whether a canonical merge seen in a command keeps its exception, given whether it was the only statement and whether a statement changed directory or environment
  - destructive-guard.py keeps its lexer and generic checks. It passes the module only what it already computes per statement and per command: statement tokens with their lexing flags, the payload's working directory, the statement count and the context-change fact. It holds no merge-specific pattern, path shape or ref name.
  - Behavior is unchanged except for the harmless-trailing-segment case below. Every existing verdict, reason id and message stays the same.
- **Loading**:
  - destructive-guard loads the module from the directory of the destructive-guard.py file actually running, so a copy checked through the runner's path argument uses its own sibling module.
  - Loading writes no bytecode cache.
  - If the module is missing or fails to load, the exception never applies: every `gh pr merge` keeps its `ask` (`deny` under `CLAUDE_BATCH`), and all other verdicts are unchanged. The hook does not crash.
  - The module is not registered in `hooks.json`; it is not a hook of its own.
- **Sole statement**: the canonical merge is allowed only when it is the whole command. Any other statement in the same command, harmless ones included, makes the merge fall back to `ask`, unless another statement earns a `deny`, which still wins. The existing case "gh-pr-merge AC-3 正規形の後ろの無害な区間は allow のまま" changes its expected verdict to `ask`; its label may be reworded to match. No existing deny / ask case is removed.
- **Runner fixture**:
  - Once per run, `run-destructive-guard.py` creates a temporary directory holding a git repository with one commit. It registers a worktree at `.claude/worktrees/em-workflow/demo/integration` on branch `em-workflow/demo/integration` with `git worktree add`.
  - It also creates a plain directory of the same shape for feature `unregistered`, which is not a registered worktree.
  - A case's `cwd` may contain the placeholder `{merge_fixture}`. The runner replaces it with the temporary repository's root before sending the payload. Other `cwd` values are passed unchanged and need not exist.
  - The cases file therefore carries no machine-specific or home-directory path.
- **Unit tests** build an equivalent fixture per test class in a temporary directory, instead of the fixed path `/tmp/merge-guard-fixture`.
