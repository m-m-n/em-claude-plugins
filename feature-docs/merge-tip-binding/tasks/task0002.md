# Task Plan: task0002 — Re-decide after the lock at the current tip (step 6.4)

## Goal

After the merge lock is held, the PR route of step 6.4 reads the integration
branch's current tip, validates it, and re-decides with that value, so a run
whose PR was already merged at a tip advanced by a concurrent run ends
`already_merged` instead of `internal_error`; step 6.4 and 「保持する値」 describe
what each route actually decides on.

## Requirements

FR1, FR5, FR6, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Design

### Step 6 item 4 (re-decision after `held`)
- Opening sentence: replace 「先端は手順 4 / 5.2 と同じ `integration_tip`。」 with
  a statement of what each route decides on: the local route's
  `merge-git.py merged` judges the integration branch tip at the moment it is
  called (its behaviour is unchanged); the PR route judges `locked_tip`.
- Local route: the existing `merge-git.py merged` block, unchanged and still
  before the PR-route blocks.
- PR route, in this order, each its own Bash call with its own
  `Bash 呼び出し（timeout: N）:` line directly before its fence (N ≤ 600000):
  1. `cd "<project_root>"` alone;
  2. `git rev-parse --verify refs/heads/em-workflow/<feature>/integration` alone;
  3. the step 5.2 `merge-pr.py resolve` form with `--integration-tip <locked_tip>`
     instead of `--integration-tip <integration_tip>`, every other token equal.
- Read-value rule, stated in item 4 between the read and `resolve` (contract C3
  in IMPLEMENTATION.md): the output with its trailing newline removed becomes
  `locked_tip` only when it is exactly 40 lowercase hexadecimal characters; when
  git fails or the value is anything else, step 14 stops the hold task and the
  run terminates with `internal_error`. `integration_tip` is not overwritten.
- The outcome bullets (`merged`, `not_merged`, `open`, `stop`, `none`) and the
  single script-failure line keep their content. The read-value rule is prose,
  not a new outcome bullet, and does not reuse the phrase 「スクリプトの失敗」.

### 「保持する値」
- `integration_tip`: preflight's tip; passed to the step 5 `resolve`; also step
  8's expected head on the first integration (contract C2); never overwritten.
- New `locked_tip`: the integration tip read after the lock in the step 6.4 PR
  route; passed only to the step 6.4 `resolve`.

### Composition
When the tip moved during the lock wait and `resolve` answers `open`, the run
continues to step 8, whose expected-head check is bound to `integration_tip`
and stops it (IMPLEMENTATION.md D3). Item 4 needs no extra handling for it.
