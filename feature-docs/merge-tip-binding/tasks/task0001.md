# Task Plan: task0001 — Bind the integration (step 8) to the expected head

## Goal

`merge-git.py integrate` integrates only when the integration worktree HEAD
equals an expected head given on its command line, and the merge skill's step 8
passes that value (the preflight `integration_tip` first, the verified
`head_sha` after a redo) and ends `verification_failed` on a mismatch, so a
commit added after preflight never reaches the base branch.

FR2, FR3, FR4, FR6, NFR1, NFR2, NFR3, NFR4, NFR5, NFR6

## Design

### `integrate` (script)
Contract C1 in IMPLEMENTATION.md. Processing order, as a flow:

1. Argument validation (with the other argument checks): `--expected-head` is
   required for `integrate` only; a value that is not exactly 40 lowercase
   hexadecimal characters is a usage error (exit 2, usage on stderr, nothing on
   stdout). Other subcommands accept no such option.
2. Existing: worktree state must be `clean` (otherwise the existing stops).
3. Existing: worktree HEAD must equal `refs/heads/<integration branch>`
   (otherwise the existing `git_failed`).
4. New: worktree HEAD equals the expected head?
   - No → stop, reason `verification_failed`, detail exactly
     `integration branch moved after preflight`; `head` and `integrated_base`
     stay null, `conflicted_paths` stays empty; no further git invocation
     (no fetch, no merge).
   - Yes → continue exactly as today (record `head`, fetch or resolve base,
     up-to-date check, merge, conflict handling).

The reason is a code the closed 28-code set already contains; nothing is added
to `merge-result.py`.

### Step 8 (skill)
- Two literal integrate forms, each preceded by its own
  `Bash 呼び出し（timeout: 600000）:` line:
  - first integration of the run: the existing form plus
    `--expected-head <integration_tip>`;
  - return from the step 12 redo (also when step 9 resolved a conflict before):
    the existing form plus `--expected-head <head_sha>`, where `head_sha` is the
    value step 10 last verified.
  The existing rule that the PR route appends `--remote <remote>` covers both.
- Outcomes: `merged_clean` / `up_to_date` and `conflict` unchanged. The stop
  bullet lists `git_failed` and `verification_failed` and states that, the lock
  being held, step 14 runs before terminating with that `reason` and `detail`.
- `integration_tip` and `locked_tip` are described in 「保持する値」, which this
  task does not edit (IMPLEMENTATION.md C2, C3, D4). Step 8 never uses
  `locked_tip`.

### Result contract
- SKILL.md 「結果の値」 `verification_failed` row: 出どころ adds
  `merge-git integrate`; 手順 becomes `8, 10, 13`; detail cell adds the step 8
  fixed text `integration branch moved after preflight` and keeps the step 10
  and step 13 texts. The cell separator `|` never appears inside a cell.
- `merge-result.md` `verification_failed` row: Condition adds the case that the
  integration worktree HEAD before integration differs from the expected tip;
  Emitted by adds `merge-git integrate`. The table keeps exactly 28 codes.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR2, NFR1, TM-2): `integrate` without `--expected-head`, or with a value that is uppercase hex, 39 or 41 characters, or contains a non-hex character, exits 2 with `usage:` on stderr and empty stdout. The other subcommands' argument behaviour is unchanged.
- [ ] AC-2 (FR2, NFR1, TM-1): with a clean registered integration worktree whose HEAD (equal to its branch tip) differs from `--expected-head`, `integrate` returns outcome `stop`, reason `verification_failed`, detail exactly `integration branch moved after preflight`, `head` and `integrated_base` null and `conflicted_paths` empty; run with a remote configured, the shim log of that run holds no `fetch` and no `merge`; the integration branch tip, the worktree HEAD and status, and the base branch tip are unchanged.
- [ ] AC-3 (FR2): the comparison comes after the existing checks — with a mismatching expected head, a dirty worktree still stops `worktree_not_clean`, an absent worktree still stops `git_failed` naming `absent`, and a merge in progress still stops `git_failed` naming `merge_in_progress`. With the expected head equal to the worktree HEAD, every existing `integrate` test (merged_clean, up_to_date, conflict, fetch failure, hook failure, remote fetch) and the boundary test pass with unchanged assertions.
- [ ] AC-4 (FR2, FR3, FR6, NFR4): in `tests/test_merge_local_route.py`, after the integration tip is taken (by `merge-preflight.py` in the full-chain class, by the test's own git in the core class), a commit made inside the integration worktree makes `integrate` with that tip stop `verification_failed`; the base branch tip is unchanged and the added commit is not an ancestor of it. Without the added commit, the chain with that tip still lands the merge commit as before.
- [ ] AC-5 (FR3, NFR2, TM-1, TM-4): SKILL.md step 8 holds exactly two `merge-git.py integrate` forms, one with `--expected-head <integration_tip>` (first integration) and one with `--expected-head <head_sha>` (return from the step 12 redo, including after step 9), each with its own timeout line ≤ 600000; neither carries `<locked_tip>`; the stop bullet names `verification_failed` and 手順 14. The existing literal-form, timeout, script-closed-set and script-option-agreement tests pass.
- [ ] AC-6 (FR4): the SKILL.md `verification_failed` row has 手順 exactly {8, 10, 13}, 出どころ containing `merge-git integrate`, and a detail cell containing both `integration branch moved after preflight` and `integration branch moved after verification`; the `merge-result.md` `verification_failed` row's Condition states the pre-integration HEAD mismatch and its Emitted by contains `merge-git integrate`; both tables still hold exactly the 28 codes and `merge-result.py` is not modified.
- [ ] AC-7 (FR6, NFR5): every new doc-test absence or presence matcher is paired with a forged-text case on which it fires; the existing row test is updated to {8, 10, 13} rather than removed; no new detail or document text carries an absolute home path or a Notion URL; `python3 -m unittest discover -s tests` passes.

## Test Notes

- AC-1, AC-2, AC-3 → `tests/test_merge_git.py` (unit, temporary repositories,
  logging shim). The `integrate` helper takes an expected-head argument that
  defaults to the integration branch tip read with the test's own git just
  before the call, so existing tests keep their meaning. The existing
  `integrate` argument cases (`--remote -r`, `--remote a;b`) gain a valid
  expected head so they still fail for the remote value, not for the missing
  option.
- AC-2: create the mismatch by recording the tip, then committing inside the
  integration worktree (keeps the worktree clean and HEAD equal to the branch
  tip, so the comparison is the check that fires). Use the bare-repository
  remote fixture so that a fetch would otherwise have run; assert on the shim
  log of that run only. Also cover a mismatch where the expected value is an
  unrelated valid SHA (for example the base tip).
- AC-4 → `tests/test_merge_local_route.py` (integration). The moved-branch case
  needs no concurrency: one commit at a fixed point between taking the tip and
  calling `integrate` (NFR4). The full-chain variant keeps the existing
  skip-when-preflight-absent rule.
- AC-5, AC-6 → new class in `tests/test_merge_skill_doc.py` (static text).
  Forged controls: a step 8 with a single integrate form without the option;
  a form carrying `<locked_tip>`; a stop bullet without `verification_failed`;
  a table row whose 手順 is {10, 13}; a merge-result.md row without
  `merge-git integrate`.
- The test record lists the new and updated test IDs per AC in the
  `tests.<module>.<Class>.<method>` form described in `test/README.md`.
