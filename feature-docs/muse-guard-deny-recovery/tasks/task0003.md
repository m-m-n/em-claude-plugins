## Design

### Routing table (FR3)

The table under the R2b `skip_reason` header gains one last row, exactly the
row IMPLEMENTATION.md Shared Components "R2b routing row" pins. The four
existing rows keep their bytes. The table then has exactly five data rows.

### Note on the new row (FR3)

Inside the Phase R2b section, after the routing table, prose states the
three points and the budget rule IMPLEMENTATION.md Shared Components "R2b
note on the new row" pins, plus: an exhausted chain takes the existing
Claude fallback. The prose sits outside the table and contains no pipe
character followed by `the next entry`, so the next-entry count of the
section stays equal to the row count.

### Precedence over the harness-level path (FR4)

A statement placed immediately after the paragraph that begins
`A reviewer that fails at the **harness** level never reaches this table`
says:

- A reviewer result that is a valid skip object with `contributor_consent_missing`
  is routed by the R2b table even when the cause was a hook deny.
- When no valid skip object comes back (the Task call is `is_error`, a
  permission denial lands without a skip object, or the wrapper never ran),
  the harness-level path still applies: the one Claude fallback and the
  `workflow-doctor` diagnosis.

The harness-level paragraph itself keeps its bytes.

### README hop paragraph (FR8)

The paragraph starting `R2b はスキップ理由が retryable なときだけチェーンを進める`
lists the retryable values; `contributor_consent_missing` joins the group that
advances to the next entry (the `rate_limited` group). The two phrases SPEC.md
FR8 pins stay verbatim. The README gains no earlier occurrence of the
slash-separated listing that ends with `review_data_too_large`, because an

hop paragraph to lose it.
