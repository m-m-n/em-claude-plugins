# Task Plan: task0001 — 既存テスト検索の規律追加・再発検出テスト・version bump

## Goal

implementer が `*.tests.yaml` に既存テストが無いと記録する前に、変更対象ファイルを参照する既存テストをリポジトリ相対パスとファイル名で検索する規律を tdd-testing/SKILL.md に追加し、implementer.md の Step 4c から参照させる。規律の記述を検査する再発検出テストを追加し、em-workflow の version を 0.2.9 に上げる。

## Design

IMPLEMENTATION.md の D1（1 タスク構成）と D2（規律の置き場所）に従う。

### 1. tdd-testing/SKILL.md の新設セクション（FR1 / FR2）

レベル 2 の見出しでセクションを 1 つ新設し、次の要素をすべて書く。文言は既存本文と同じ英語で、このタスクで決める。

| 要素 | 書く内容 |
|------|---------|
| E1 発動条件 | `*.tests.yaml` のエントリで既存テストが無いと述べる前。具体的には `tests: []` と書く場合と、`red_confirmed: false` の理由に既存テストの不在を挙げる場合 |
| E2 検索の必須化 | 変更対象ファイルを参照する既存テストを、プロジェクトのテストディレクトリから検索することが必須である |
| E3 検索キー | リポジトリ相対パスとファイル名（basename）の両方で検索する。テストがパスを分割して組み立てている場合、相対パスの完全一致では見つからない |
| E4 見つかった場合の tests | 変更対象ファイルを実際に読む既存テストが見つかったら、そのモジュール／クラスを `tests:` に列挙する |
| E5 見つかった場合の red_reason | 「専用の新規モジュール追加はスコープ外だが、既存の X が Y を検出する。今回の変更では red 状態は発生しなかった」という趣旨にする |
| E6 red_confirmed | 観測した事実のまま記録する。red を見ていなければ false |
| E7 合成フィクスチャ | ヒットしたテストが実ファイルではなく、一時ディレクトリなどに合成したフィクスチャを読んでいる場合、そのヒットは変更対象ファイルのカバレッジとして扱わない |
| E8 見つからない場合 | 従来どおり `tests: []` と、既存テストが無い旨の red_reason を書く |
| E9 ビルド／lint の AC | AC の検証結果がビルドや lint の結果である場合も `tests: []` は引き続き許される。ただし既存テストが無いと述べるなら、その前に検索する |

- 既存セクション（Test-first procedure など）の内容は変更しない。
- frontmatter の `name` と `user-invocable` は変更しない。

### 2. implementer.md の Step 4c（FR3 / NFR4）

- Step 4c（4c の見出しから Step 5 の見出しの手前まで）に、tdd-testing スキルの新設セクションを参照する記述を加える。参照にはスキル名 tdd-testing と、新設セクションの見出しの文字列の両方を含める。
- 参照は、`tests: []` に触れる段落と `red_confirmed: false` の段落のどちらから読んでも辿れる位置に置く。
- 参照ではなく同じ規律を書く場合も、SKILL.md の新設セクションと矛盾させない。
- Step 4c 以外の Step、frontmatter、Hard constraints は変更しない。`# Task assignment` 見出しを追加しない。

### 3. version bump（FR5 / NFR3）

- plugin.json の version と、marketplace.json の em-workflow エントリの version を 0.2.9 にする。他のフィールド、em-review エントリ、両ファイルの整形は変えない。description は変更しない（plugin.json description の `/em-workflow:develop drives` はそのまま残る）。
- version 専用の新規テストモジュールは作らない。

### 4. 再発検出テストモジュール（FR4 / NFR1）

| 構成要素 | 責務 | 事前条件 / 事後条件 |
|---------|------|-------------------|
| セクション切り出し | SKILL.md から新設セクションを、implementer.md から Step 4c の範囲（4c の見出しから Step 5 の見出しの手前まで）を取り出す | 見出しが見つからなければ失敗として報告する。空のテキストで黙って通さない |
| マッチャー群 | 切り出したテキストを受け取り、規律の要素がそろっているかを判定する。欠けていれば失敗させる | 入力はテキストのみで、ファイルを読まない |
| 実文書テスト | 実際の SKILL.md と implementer.md にマッチャーを適用する | — |
| 否定テスト | 規律の要素を欠いた偽サンプルにマッチャーを適用し、失敗することを確かめる | 偽サンプルはモジュール内に持つ |

マッチャーの最小セット（1 つのマッチャーが複数の要素を見てもよい）:

- M1: E1 と E2 — 発動条件の 2 つの形と、検索が必須であること
- M2: E3 — リポジトリ相対パスとファイル名の両方
- M3: E4、E5、E6 — 見つかった場合の tests 列挙、red_reason の趣旨の 3 点（専用モジュールはスコープ外／既存テストが検出する／今回 red は発生しなかった）、red_confirmed は観測した事実のまま
- M4: E7 — 合成フィクスチャを読むテストのヒットを除外すること
- M5: implementer.md の Step 4c 範囲が、スキル名 tdd-testing と新設セクションの見出しの文字列を含む（または M1〜M3 を満たす同等の記述を持つ）。参照する見出しが SKILL.md に見出し行として実在する

判定方法:

- 判定は切り出した範囲の中だけで行う。文書の他の箇所の偶然の一致で通らないようにする。
- 文の完全一致ではなく、要素ごとの識別語で判定する。大文字小文字と改行位置の違いは吸収する。
- 新設セクションの見出しの文字列は、モジュール内の定数として 1 か所で持つ。
