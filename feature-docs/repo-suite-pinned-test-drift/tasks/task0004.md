# Task Plan: task0004 — マニフェストのピン留め追随（codex-wrapper / batch-structured-result / muse-consent）

## Goal

Replace the per-plugin specific-version pins (FR8) and the em-review version pin (FR9) with form, floor and agreement checks, and update the stale em-workflow non-version manifest digest (FR5). Every changed check gets a negative proof.

## Requirements

FR5, FR8, FR9, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_codex_wrapper_fallback_removal_version_bump.py` — TestSpecificVersionValues checks form, per-plugin floor and agreement; the expected key and the literal-update comments are removed; negative proofs
- `tests/test_batch_structured_result_output_version_bump.py` — the em-review entry matcher checks identity fields exactly and version form only; EM_REVIEW_VERSION re-purposed; the 99.0.0 rejection case becomes a malformed-version case
- `tests/test_muse_consent_version_bump.py` — EM_WORKFLOW_MANIFEST_NONVERSION_SHA256 and its reference-point comment updated; negative proof for the digest check

## Design

This task implements the Version form rule, Lower-bound comparison and Registry agreement contracts from IMPLEMENTATION.md Shared Components, locally in each module (D2). task0001 bumps em-workflow to 0.2.4 in parallel. Under the manifest artifact contract only the version value changes, so every live check here must pass at 0.2.3 (this worktree) and at 0.2.4, and the non-version digest is the same before and after. Test method names stay as they are (IMPLEMENTATION.md Conventions).

**FR8 (`tests/test_codex_wrapper_fallback_removal_version_bump.py`)**

- The two TestSpecificVersionValues tests currently compare against PLUGIN_SPECS entries' expected values. The em-workflow one is test_em_workflow_manifest_and_entry_agree_on_the_current_version, and there is an em-review counterpart. For each plugin they now verify:
  - the manifest version and the marketplace entry version both pass the form rule
  - the two versions agree
  - the manifest version is at or above that plugin's floor by the lower-bound comparison
- Each plugin's floor is the lower bound already recorded for it in the module. If the module records none, the value that the removed expected key held becomes the floor, under a key whose name says it is a floor. That value is historical and is used only through the lower-bound comparison (NFR2).
- The expected key is removed from every PLUGIN_SPECS entry. Every comment of the "later features update this literal" kind is removed. Docstrings describe the floor and agreement semantics.

**FR9 (`tests/test_batch_structured_result_output_version_bump.py`)**

- `_assert_em_review_entry_unchanged` checks two things:
  - name, author, category and source match their recorded values exactly
  - version passes the form rule
  - It no longer requires any particular version value.
- EM_REVIEW_VERSION is never compared with the live marketplace entry again. It is either removed, or kept only as the well-formed sample version for building forged entries in negative proofs, renamed to say so.
- In test_em_review_matcher_rejects_altered_identity_field, the ("version", "99.0.0") case is replaced by a malformed-version case, such as "0.5", "v0.5.13" or "0.5.x", and that case expects rejection. The identity-field alteration cases stay. A new case shows that a forged entry with the well-formed version 99.0.0 and unchanged identity fields is accepted.
- PLUGIN_MANIFEST_NONVERSION_SHA256 in this module is unchanged.

**FR5 (`tests/test_muse_consent_version_bump.py`)**

- EM_WORKFLOW_MANIFEST_NONVERSION_SHA256 becomes bf70d7104511c338b6f076c3d9ab08b6a19b757b59d45397324242f11008ebf0. That is the digest of the current non-version content of `em-workflow/.claude-plugin/plugin.json`, the same value as PLUGIN_MANIFEST_NONVERSION_SHA256 in the FR9 module.
- The comment that explains the digest's reference point is rewritten to describe the current non-version content as the reference.
- The digest check has a hermetic negative proof, either existing or added. Forged manifest content where one non-version field differs, such as description, is rejected. Forged content that differs only in version is accepted.

**Negative proofs for FR8 (NFR3, D2 applicable columns)**

The FR8 matcher takes a manifest version, an entry version and a floor. It is called with forged values:

- 99.0.0 in both is accepted
- a value below the floor in both is rejected
- a malformed value in either one is rejected
- disagreeing values are rejected
- a version numerically above the floor but lexicographically below it (for example 0.10.0 against a floor of 0.9.0) is accepted
