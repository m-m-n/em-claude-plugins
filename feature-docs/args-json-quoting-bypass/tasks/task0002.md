# Task Plan: task0002 — Unquoted backslash-escaped `=` as the `=`-form separator

## Goal

In the `=`-form name reading of the `mcp-bridge run --args-json` step, an
unquoted backslash-escaped `=` ends the name part the way Bash's quote removal
makes it, so `--mcp\="$S"` reads like `--mcp="$S"` and a later static
`--args-json` value is inspected (finding f16e5bb8d5da2621). The subtest named
by finding 3340375b4b50c4b0 is confirmed.

## Design

### Name-part reading (FR2)

Current behaviour: outside quotes, a backslash keeps the next character as part
of the name, so `\=` adds a literal `=` to the name and the reading goes on into
the value part, where the non-static element makes it give no name.

New behaviour, outside quotes only:

1. A backslash followed by `=` ends the name part, exactly as an unquoted `=`
   does today; the value part starts after the escaped `=`.
2. The name collected so far is checked as today (one or two leading dashes,
   then name characters). A known value-taking name lets the flag reading in
   the decision skip that one word (the non-static value) and read on; an
   unknown or malformed name gives no name, as today.
3. Every other unquoted backslash keeps its current meaning (it keeps the next
   character; with a newline after it, both vanish). An escaped backslash
   followed by `=` is a literal backslash and then an unquoted `=`, as today.

Inside double quotes nothing changes: `\=` keeps its backslash, so
`"--mcp\=$S"` has the name `mcp\`, which is not a known name; the reading
gives no name and the statement stays nothing to do. Single-quote and ANSI-C
handling do not change.

### Docstring (FR10)

The `_flag_equals_prefix_name()` docstring's "followed directly by an unquoted
`=`" now reads: an unquoted `=` or an unquoted backslash-escaped `=`; it also
says a `\=` inside double quotes keeps its backslash.
