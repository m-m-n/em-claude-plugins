# Task Plan: task0004 — run_scan consumes the plans build_scan_jobs returns (plan-units)

## Goal

`build_scan_jobs` becomes the only planning stage of the scan subcommand and returns per-group plans that have not been launched; `run_scan` executes exactly those plans, so the code path the tests exercise is the code path production runs, with no change to what `run_scan` shows from outside.

## Requirements

FR6, NFR1, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_sca_run_scan_plan_units.py` — run_scan-through-build_scan_jobs tests, the binding-check ordering tests, and the argv/env/cwd assertions moved out of build_scan_jobs tests.

### Files to Modify
- `em-workflow/scripts/scan-dependencies.py` — build_scan_jobs returns plans; run_scan and its two group helpers consume them; the lexical grouping helper is removed; affected docstrings and section comments are updated.
- `tests/test_sca_scan_job_grouping.py` — grouping, order, reason and purity tests rewritten as plan checks; argument-vector checks made through build_scan_jobs move to build_scan_job or run_scan.
- `tests/test_sca_scan_invocation.py` — the unresolvable-binary tests check plans instead of built jobs.
- `tests/test_sca_scanner_project_config_isolation.py` — the build_scan_jobs prepared-inputs tests are replaced by plan checks plus working-directory checks on build_scan_job or run_scan.

## Design

Region owned in the script: `manifest_file_for`'s docstring, the scan-job-construction section comment, `build_scan_jobs`, `_lexical_project_directory`, `_scan_bound_group`, `_scan_pip_group` and `run_scan` (IMPLEMENTATION.md D1). Nothing in this task changes normalizers, `build_scan_job`, the binding-check functions, isolation, the pip lockfile stage or file-tasks.

### Plan (one per group, not launched)

A read-only record with exactly six named fields:

| Field | Content |
|-------|---------|
| `ecosystem` | the validated registry entry (its name is read from it) |
| `directory` | the group key D: the real directory relative to the real project root, `/`-separated, empty for the root; for an unverifiable pip path, its raw directory part |
| `real_root` | the real path of the project root |
| `files` | the group's changed files, in input order |
| `target` | the selected target: npm / cargo / go use D, a `/`, and the basename of the file selected by `manifest_file_for` over the group's files (the bare basename at the root); pip uses the raw selected file |
| `executable` | the absolute executable path resolved once for the ecosystem |

### `build_scan_jobs(registry, changed_files, project_root)` → `(plans, skip_reasons)`

- The environment and prepared-inputs parameters are dropped: a plan needs neither.
- Flow per ecosystem, in `select_ecosystems` order:
  1. Validate the entry; on failure append its existing reason and continue (no path work).
  2. Resolve the executable; on failure append `<ecosystem>_tool_not_found` and continue (no path work).
  3. Resolve the real project root and group the ecosystem's changed files with `_verified_groups`; when it rejects a file, append `<ecosystem>_project_unbindable` once.
  4. For each group in group order (ascending directory, root first), select the target and emit one plan.
- `skip_reasons` is a list, each reason at most once per ecosystem, in registry order.
- Postcondition: launches no process, builds no job, opens no file and creates no directory; it only resolves paths and looks up the executable.

### `run_scan`

1. Keep the no-selected-ecosystem early return exactly as it is (unsupported-manifest skip or the empty result).
2. Call `build_scan_jobs` once; add its reasons to the reason set.
3. For each plan in order: a pip plan goes to the pip group audit, any other plan to the bound group audit; both take the plan's `target` and never select a target again.
4. Bound group audit keeps its current order: binding check against the plan's directory and the basename of the plan's target → for npm / cargo, the per-group isolation directory, prepared only after the check passed → `build_scan_job` → launch → judge → normalize. Same fixed tokens (`<ecosystem>_project_unbindable`, `npm_isolation_failed`, `cargo_isolation_failed`), same isolation-directory removal on every path.
5. Findings accumulation, undetermined / unpinnable counts, summary notes, skip-reason joining and the output object stay unchanged.

Planning every ecosystem before the first launch widens the time between grouping and launch; the run-side binding check is what guards that window (TM-5), so the plan never substitutes for it.

### Docstrings, comments and removal

- `build_scan_jobs`' docstring describes plan-units and real-path grouping; the sentence "run_scan does not use this function" is removed, together with the descriptions of lexical grouping and of prepared inputs.
- `_scan_bound_group` and `run_scan` docstrings keep the phrases `tests/test_sca_scanner_project_config_isolation.py` pins ("isolation directory", the removal wording, both `_isolation_failed` tokens) and still never describe npm or cargo as running in the project root or directory.
- `manifest_file_for`'s docstring and the scan-job-construction section comment name `build_scan_jobs` as the caller and say "no plan" where they said "no job".
- `_lexical_project_directory` has no remaining caller and is removed.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR6): `build_scan_jobs` returns `(plans, skip_reasons)`; each plan carries exactly the six fields above; plans follow registry order and, inside an ecosystem, ascending group order with the root first; the rewritten tests in the three existing modules check plans and pass.
- [ ] AC-2 (FR6): Grouping is by real path — a symlinked alias of a directory and a `..` spelling that stays inside the root fall into the same plan as the plain spelling; an npm / cargo / go path that is absolute, escapes the root (lexically or through a symlink) or contains NUL yields no plan and adds `<ecosystem>_project_unbindable` exactly once; pip paths are never rejected, and an unverifiable pip path keeps its raw directory key apart from verified keys.
- [ ] AC-3 (FR6, TM-5): An ecosystem whose entry fails validation or whose executable does not resolve contributes its reason once and no plan, and the path-verification step is never called for it (shown with a recording test double); `build_scan_jobs` launches no process, opens no file and leaves a nonexistent project root nonexistent.
- [ ] AC-4 (FR6, TM-5): With `build_scan_jobs` replaced by a recording test double that returns a plan whose `target` differs from what `manifest_file_for` would pick from the plan's `files`, `run_scan` calls it exactly once and launches the scanner for the plan's `target` (no re-selection).
- [ ] AC-5 (TM-5, NFR1): With a test double that calls the real `build_scan_jobs` and then swaps an npm or cargo plan's project directory for a symlink escaping the root, `run_scan` launches nothing for that plan, creates no isolation directory for it and reports `<ecosystem>_project_unbindable`; a plan that fails the binding check never gets an isolation directory.
- [ ] AC-6 (NFR1): The existing run_scan suites (test_sca_scan_execution, test_sca_scan_normalization, test_sca_per_project_scan_binding, test_sca_pip_lockfile_audit, test_sca_go_govulncheck_real_output, test_sca_scan_unchanged_surfaces, and the run_scan parts of test_sca_scanner_project_config_isolation) pass with their behaviour assertions unchanged, and every argv / env / cwd assertion removed from a build_scan_jobs test has a counterpart in a build_scan_job or run_scan test.
- [ ] AC-7: The `build_scan_jobs` docstring no longer contains "run_scan does not use this function"; the docstring pins of test_sca_scanner_project_config_isolation pass; no reference to `_lexical_project_directory` remains in the script.
- [ ] AC-8 (NFR3): The new and the modified test modules import only the standard library.

## Test Notes

- AC-1 to AC-3 are plan-level unit tests: stub executables on a temporary PATH, a temporary project root; real-path cases (AC-2) need real directories and a symlinked alias created under it, while lexical-only cases can keep a nonexistent root.
- AC-4 and AC-5 are run_scan-level tests with stub scanners that record their working directory and argv; replacing `build_scan_jobs` with a test double on the loaded module is the intended technique (SPEC TS9).
- When moving assertions (AC-6), keep each moved check's meaning: npm argv with the workspace flag, cargo argv with the target flag and the copied lockfile, go argv, absolute argv[0], npm / cargo cwd in the isolation directory, go cwd in the group directory, and the npm job without prepared inputs being rejected by `build_scan_job`.
- Run the whole `tests/` suite before finishing: the binding, isolation and pip lockfile suites are the regression net for NFR1.

- Per-project job construction beyond what exists today (a separate SCA-axis item).
- Title construction (task0001) and file-tasks (task0002).
- Plugin manifests (`plugin.json`, `.claude-plugin/marketplace.json`) are not edited (NFR4).
