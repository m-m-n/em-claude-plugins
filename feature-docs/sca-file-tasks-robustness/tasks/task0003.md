## Design

The receipt's source is the file-tasks summary; its fields and their mapping are pinned in IMPLEMENTATION.md Shared Components ("file-tasks summary", "failure_reason vocabulary", "triage_filing receipt ← summary mapping"). This task writes that mapping into the protocol text; it never redefines the summary. review-phase.md stays the only definition owner of the receipt; batch-mode.md only points at it (IMPLEMENTATION.md Layer Structure).

### The three receipt places

1. **Phase R4, "Triage filing" subsection, item 4 "The receipt"**: besides what it records today, the receipt records `failed_package`, `failure_reason`, `malformed_findings`, `listing_dropped_count` and `unattempted_packages`, each taken from the file-tasks summary key of the same name.
2. **Phase R5, the round-record YAML example, `triage_filing` block**: five new keys inside the block, with the `another-round` values null, null, [], 0, [] and a short inline comment each (for `failure_reason`: `task_create_failed` / `task_update_failed`, null when no failure). The block stays after `rework_required`.
3. **Phase R5, the prose paragraph on the triage-filing receipt**: lists the five fields with their meaning; states that `executed` is false and every other value is empty / null / 0 when the disposition was `another-round`; defines `unattempted_packages` as the failed package plus every later package never attempted, in processing order, malformed findings excluded, and empty when filing completed or the report branch ran.

### Untrusted-text statement (NFR2)

The R5 prose states that every receipt value is copied from the file-tasks summary and nothing else enters the receipt; `failure_reason` is one of the two fixed tokens or null; no advisory-sourced text and no OS-error message text is ever recorded in the receipt (such text goes to the script's stderr only).

### Unattempted-package policy (FR5)

Stated once, in the Phase R4 "Triage filing" subsection (or R5's receipt prose — one place, cited from the other if needed):

- There is no automatic retry.
- When `unattempted_packages` is non-empty, the run reports "triage filing incomplete" together with those packages, in the Phase R6 report and in the batch final result (in batch mode the R6 body is withheld, so the batch final result is where it appears; batch-mode.md's Reporting item below is the route).
- The review completion condition does not change.
- Running file-tasks again files only the remainder through its duplicate detection; this holds only when the latest listing already shows the packages filed earlier.

### Phase R6

R6's rendering rules gain one item: when the round record's `triage_filing.unattempted_packages` is non-empty, the report shows "triage filing incomplete" with the package list. R6's batch paragraph states that the same line is carried into the batch final result. This is disclosure only: no new gate identifier, no completion-gate effect (NFR6).

### Batch final report (batch-mode.md)

The batch final report is assembled from batch-mode.md's Reporting item list, each item resolved through the audit-item source map inside the Batch quiet output section. The addition is deliberately narrow:

1. **Reporting item list**: exactly one new item — every review round whose triage filing was incomplete, reported as "triage filing incomplete" with that round's unattempted packages. It is placed immediately before the kept integration branch name, which stays the last item. Every other item and the rest of the section (the pointer sentence, the in-full value-assignment paragraph) are unchanged, so the new item is covered by "every item above".
2. **Audit-item source map**: exactly one new row for that item, placed immediately before the kept-integration-branch row. Its first cell names the item with the same phrase the Reporting list uses. Its persisted-source cell names the committed round record `feature-docs/{feature}/reviews/roundN.yaml` with the receipt fields `triage_filing.unattempted_packages` and `triage_filing.failed_package` as the only source, and cites review-phase.md as the receipt's owner — the same citation style the batch-audit rows use for phase-state.md.
3. **No restatement**: batch-mode.md does not describe what those fields contain, the processing order, the malformed-finding exclusion, the no-automatic-retry rule, the remainder-only re-run, or the completion condition; review-phase.md owns all of them.
4. **No new structure**: no new section, no gate identifier (batch-mode.md's number of `gate_id` occurrences is unchanged), no change to batch-terminal-line.md or to the develop skill — the skill's completion step already assembles the batch audit items from the source map.
