# Task Plan: task0002 — file-tasks: OS errors become entry-point failures and unattempted packages are recorded

## Goal

An OS error raised while filing (launching the entry point or writing its temporary references file) no longer kills `file-tasks`: the run ends through the existing break-and-return path, prints one JSON summary and exits 0, and the summary names the failed package and every package never attempted.

## Requirements

FR3, FR5, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create
- `tests/test_sca_file_tasks_oserror.py` — CLI-level and in-process tests for OS-error conversion, the new summary key and the untrusted-text policy.

### Files to Modify
- `em-workflow/scripts/scan-dependencies.py` — the two filing helpers convert OS errors; file-tasks adds the unattempted-packages key on every branch and its docstring names five added keys.

## Design

Region owned in the script: the external task-system section and the file-tasks subcommand section (IMPLEMENTATION.md D1). The summary shape and the `failure_reason` vocabulary are pinned in IMPLEMENTATION.md Shared Components; this task produces them.

### Filing helpers (`create_security_task`, `append_security_task_references`)

- Precondition: unchanged (an entry point that fails the existing executable-file check already raises the entry-point failure).
- Postcondition: every OS error raised inside the helper — while creating or writing the temporary references file, while launching the subprocess, or while removing the temporary file afterwards — leaves the helper as the entry-point failure (`EntryPointError`), never as a raw OS error. The original OS error is kept as the cause and its text may appear in the entry-point failure's message; that message only ever reaches stderr.
- The temporary references file is still removed after a launch attempt, as today.
- A non-zero exit of the launched process keeps its existing handling.

### Filing loop and summary (`file_tasks`)

Processing flow on the ntd branch (unchanged except steps 4 and 5):

1. Group findings (recovery, de-duplication, truncation); malformed findings are recorded and excluded from the groups.
2. Walk the groups in their order; for each package either append to the first incomplete task or create a new task.
3. A caught entry-point failure records `failed_package` and the fixed `failure_reason` token for the helper that failed, prints the diagnostic to stderr, and stops the walk (existing break-and-return; still the only early exit).
4. `unattempted_packages` is the failed package followed by every package after it in the group order; empty when the walk completed.
5. Return the summary with all twelve keys.

The report branch (no entry point) and the degraded report branch (listing unavailable) return `unattempted_packages` as an empty list. No other key is added and no existing key changes name or meaning (NFR5). The docstring's list of added keys goes from four to five and describes `unattempted_packages`.

`main` needs no change: once no OS error escapes `file_tasks`, the existing path prints exactly one JSON object and exits 0.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TM-2): Through the real CLI, a 3-package batch with a stand-in entry point whose file stops being executable as a program (a bad interpreter line, swapped in after the listing and after the 1st create) exits 0; stdout is exactly one JSON object; stderr contains no traceback; `filed_packages` is [1st]; `failed_package` is the 2nd; `failure_reason` is `task_create_failed`; `unattempted_packages` is [2nd, 3rd]; and the stand-in recorded no call for the 3rd.
- [ ] AC-2 (TM-2): The same on the append path (each package already has an incomplete task and brings a new advisory): `appended_packages` is [1st], `failed_package` is the 2nd, `failure_reason` is `task_update_failed`, `unattempted_packages` is [2nd, 3rd], exit 0 and one JSON object.
- [ ] AC-3 (TM-2): When writing the temporary references file raises an OS error for the 2nd package, on the create path and on the append path, the result equals AC-1 / AC-2 respectively (same `failure_reason` token per helper) and no exception escapes `file_tasks`.
- [ ] AC-4 (TM-3): When the 1st package fails, `filed_packages` and `appended_packages` are empty and `unattempted_packages` lists every non-malformed package in group order — a second finding for an already-seen package adds no second entry, and an over-long package name appears in its truncated form — while malformed findings never appear in it.
- [ ] AC-5 (TM-3, NFR5): `unattempted_packages` is [] on full success, on the report branch and on the degraded report branch; on every branch the summary's key set is exactly the twelve keys of IMPLEMENTATION.md Shared Components; the existing listing-launch-failure degraded case (bad interpreter from the start) still returns branch `report`, degraded true and reason `listing_launch_failed`.
- [ ] AC-6 (TM-4, NFR2): With an OS error whose message carries a unique marker and an advisory short title carrying another unique marker, neither marker appears in `failure_reason`, in any malformed reason, in `unattempted_packages` or anywhere in the printed JSON summary, and the OS-error marker does appear on stderr.
- [ ] AC-7 (NFR3, NFR5): The `file_tasks` docstring names five added keys including `unattempted_packages`; the new test module imports only the standard library; `tests/test_sca_task_filing.py` passes unchanged.

## Test Notes

- AC-1 and AC-2 are subprocess tests of the real CLI (`file-tasks` with `--entry-point`), parsing the whole of stdout as one JSON document. The stand-in executable records each call and replies from a control file, like the stand-in in the existing file-tasks tests; to fail the 2nd launch, the stand-in rewrites its own first line to a nonexistent interpreter while serving the 1st create / update call, keeping its executable mode so the entry-point validity check still passes. Define the stand-in in the new module rather than importing a sibling test module.
- AC-3 is in-process: replace the temporary-references-file writer with a test double that raises an OS error on its 2nd call.
- AC-4 / AC-5 / AC-6 can be in-process calls to `file_tasks`; the report branches need a temporary git repository as project root.
- Findings are built directly in the Finding text-encoding contract shape (IMPLEMENTATION.md Shared Components).
