# Task Plan: task0001 — Terminal state for the control-character stop, with regression tests

## Goal

When Step I.2.a's Control-character check rejects a canonical
`worktree_path`, the implement phase ends in a committed terminal
workflow.yaml state taken from Step I.2.c's abort phase, so develop stops at
stop condition 3 and the queue Stop hook neither blocks the turn end nor asks
for a launch of a rejected task. Document tests pin the new statement, and
the `failed_kind` write-path count in the schema document stays accurate.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/references/implement-phase.md` — append the terminal-handling statement inside the Step I.2.a Control-character check paragraph
- `em-workflow/references/workflow-schema.md` — failed_kind section, Required-ness paragraph: the write-path count goes from three to four
- `tests/test_canonical_worktree_path_docs.py` — new terminal-handling check function, live-document test and forged-copy tests
- `tests/test_workflow_schema_journal_readers_doc_contract.py` — update the byte-identical pinned capture of the failed_kind section in place to the post-edit text

## Design

This is a single-task feature at the `reduced` tier; there is no
IMPLEMENTATION.md. Everything this task needs is stated here.

### 1. The terminal-handling statement (implement-phase.md, Step I.2.a)

**Location.** Inside the existing Control-character check paragraph — the
single paragraph block that contains "Unicode general category Cc" —
appended at its end, after the sentence comparing the stop with Step I.0's
identifier validation gate. No blank line is introduced and no wrapped line
of the added text starts with a list marker, so the paragraph stays one
block and keeps its position: after the canonicalization paragraph, before
the approval-gate paragraph and the launch-loop paragraph (FR3).

**Content (FR1, FR2).** The added text names Step I.2.c's abort phase as the
source of the handling and states its outcome without restating the abort
phase's command lines:

1. After the rejection, the phase takes the abort phase's terminal handling:
   capture the integration branch tip, refresh the integration worktree,
   make one write that sets the `implement` step's `status` to `failed`
   together with `failed_kind` valued `decision`, and commit exactly that
   write with `commit-docs.sh` (commit subject as the abort phase's, SPEC A5).
2. `failed_kind` is `decision` unconditionally on this path: there is no
   journal `failed` event here, so the abort phase's external-cause rule
   does not apply (SPEC A2).
3. No `create-plan` `needs_update`, no task status or notes write, no
   worktree or branch cleanup. Worktrees and branches created before the
   check stay, and a later re-entry reuses them under the Resume guard
   (SPEC A4).
4. The terminal write happens at the check, without waiting for tasks
   launched by an earlier refill; those tasks are neither cancelled nor
   rolled back (SPEC A1).
5. Control returns to the user through develop's stop condition 3.

**Wording constraints.** Each constraint keeps an existing document test
valid:

- The added text does not contain the phrase 'ABORT the implement phase'
  (FR3). The existing stop check requires exactly one sentence with it, and
  that sentence keeps the offending-ID report and the no-launch-prompt
  phrase unchanged.
- The added text repeats none of the paragraph's stable phrases that the
  test module pins: the locator 'Unicode general category Cc', the scope
  phrases, the rejected ranges, the offending-ID report phrase, the
  no-launch-prompt phrase, the no-sanitize phrase and the no-fallback
  phrase. Several forged-copy tests replace one of these and then assert it
  is absent; a second occurrence would break them.
- The added text contains no literal `reset --hard`. The tip-capture idiom
  test takes the first `reset --hard` in the I.2.a section as the
  launch-time refresh, which must come after the launch-time tip capture
  further down the section.
- The added text contains no tip-capture assignment and no `commit-docs.sh`
  invocation with arguments. It names `commit-docs.sh` and cites the abort
  phase for the invocation (FR2: cite, do not restate).
- The added text does not reuse the marker strings that other document
  tests use to find Step I.2.c's sites by their first occurrence in the
  whole document: the abort-phase bullet opening ('- **abort phase**'),
  'When the gate does not hold', and the batch paragraph opening
  'Batch mode (`references/batch-mode.md`'. Prose such as "Step I.2.c's
  abort phase" is fine.
- Only the `decision` value is named. The `failed_kind` vocabulary is not
  presented as a set and the values' meanings are not glossed. The field is
  owned by the `failed_kind` section of `references/workflow-schema.md`;
  cite that section, do not restate it.
- The existing sentences of the paragraph are not reworded (NFR4).

### 2. failed_kind write-path count (workflow-schema.md)

In the Required-ness paragraph of the `failed_kind` section, the count word
changes from three to four ("Four write paths make such a write"). The
control-character stop is the fourth path that sets the `implement` step to
`failed`. The citation of `references/implement-phase.md` stays. The
paragraph still names no path and states no per-path value. An existing
schema test forbids the words 'second failure' and 'route-back' anywhere in
the section. Nothing else in the section changes, and the line wrap is kept
as far as possible.

### 3. Pinned capture update (test_workflow_schema_journal_readers_doc_contract.py)

That module's byte-identical test compares the live `failed_kind` section
with a verbatim capture that still contains the old count. This task changes
that section on purpose (FR4), so the capture is updated in place to the
post-edit section text. This plan explicitly authorizes the update. The
comparison stays byte-identical, the companion negative-proof test stays,
and no assertion is loosened or removed. A comment next to the capture
records that this feature changed the count.

### 4. New check and tests (test_canonical_worktree_path_docs.py)

- **Constants**: module-level constants hold the stable phrases of the
  added text. One names Step I.2.c's abort phase as the source, one gives
  the `implement` status `failed`, one pairs `failed_kind` with the
  `decision` value, and one is the `commit-docs.sh` name. Each is chosen so
  that it is absent from the paragraph's pre-change text, so a passing
  check is never vacuous.
- **Check function**: same shape as the existing `check_control_char_*`
  functions. Input: the I.2.a section text. Output: a list of problems.
  It locates the control-character paragraph through the existing
  paragraph locator, returns a problem when it does not find exactly one,
  and returns one problem for each of the four elements missing from that
  paragraph (FR5).
- **Aggregate**: the new check joins the existing aggregate helper of
  control-character problems, so the existing aggregate live test covers it
  too.
- **Tests**, following the module's naming and docstring convention (cite
  this feature's task0001 AC labels):
  - Live: the new check returns no problem on the live section. Phrase
    presence on the live paragraph is asserted for the Design 1 items
    3 to 5 (no needs_update / no cleanup, no wait for earlier refills,
    stop condition 3).
  - Forged (a): from the live section, `_replace_phrase` removes the
    terminal-handling text. The copy differs from the live section, and the
    new check returns at least one problem.
  - Forged (b): from the live section, `_replace_phrase` replaces the
    `decision` value of the pairing phrase with another value (for example
    `infra`). The copy differs, and the new check returns at least one
    problem.
  - Existing check retained: `check_control_char_stop` still returns no
    problem on the live section.
- The module keeps importing only the standard library and keeps locating
  text by headings and stable phrases, never by line number (NFR1).

## Test Notes

  Forged copy (a) only exists after the edit, because it removes the added
  text. `_replace_phrase` already fails loudly when the phrase to replace is
  absent, so neither forged test can pass vacuously.
- Map to the feature's VERIFICATION.md scenarios: AC-1 to TS-1 / TS-2,
  AC-3 to TS-3, AC-4 to TS-4, AC-5 / AC-6 / AC-7 to TS-5, AC-7 (diff scope)
  to TS-6.

  `tests/test_exit4_tip_argument_consistency.py`,

  that a feature whose `implement` step is not `in_progress` passes the hook.
