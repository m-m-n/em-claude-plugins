# Task Plan: task0002 — Array subscript of an assignment word

## Goal

At positions where bash accepts an assignment, the lexer reads `name[`
through its matching `]` as an array subscript, so a `<<` inside it is
never registered as a here-document operator and the lines after it stay
inspected; argument-position words keep today's reading (finding
9381769d7116fab2, first half).

### Where a subscript is recognized

- Assignment-acceptable positions, per bash 5.3: a command position (the
  first word of a simple command may start there) and the position directly
  after a leading assignment word of the same simple command (e.g.
  `x=1 a[1<<2]=y`).
- Shape: a word whose text so far is an identifier immediately followed by
  `[`.
- Everywhere else — in particular argument positions such as
  `echo a[1<<2]` and `cat a[1] <<EOF` — the reading is unchanged. Reading
  subscripts more widely than bash is not fail-safe: if bash does register
  the `<<`, its body lines would be read as commands, and a quote in that
  body could open a region that swallows real later lines.
- Tracking the assignment-acceptable position is this task's own state; it
  must not change where reserved words or a bare `((` are recognized for
  any input.
- Declaration builtins (`declare`, `local`, `export`, `readonly`,
  `typeset`): their arguments are treated as subscript positions only if
  bash 5.3 confirms that a `<<` inside `name[...]` there is not an
  operator; otherwise the reading is unchanged.

### How a subscript is read

- From the `[` to the matching `]`, counting nested `[` / `]`. Quotes,
  `$` expansions, command substitutions, backticks and backslash escapes
  inside are read by the same rules as elsewhere, so a `]` inside a quote or
  a substitution does not close the subscript.
- Nothing inside the subscript opens a here-document operator, a comment or
  a command position.
- After the `]` the word continues (`=x`, `+=x`, or whatever bash 5.3 shows
  for a word with no `=` after the subscript).
- A subscript whose matching `]` lies on a later line is relied on only in
  the shapes bash 5.3 is confirmed to read the same way; when the extent
  cannot be matched with confidence, a subscript not closed on its own line
  is handled as unclosed (below), which keeps the following lines inspected.
- The subscript is reported in the lexical map as a region so that the
  masked view hides its content from the word splitter (the `<<` inside
  must not reach downstream tokenization as an operator). If a new region
  kind is introduced, it joins the opaque / masked kind sets as its
  semantics require. Existing fixed expectations in the agreement test may
  gain that region only where a subscript legitimately appears; no
  expected verdict changes.

### Unclosed subscript

- A `name[` with no matching `]` is not a subscript region. Its opener is
  reported through the settle channel (IMPLEMENTATION.md Shared
  Components), so it is literal text and, from the earliest settled opener
  on, no `<<` operator and no comment are read: the following lines stay
  inspected (NFR6, SPEC A3).
- From the tail start on, subscript recognition has nothing left to
  protect (no `<<` operator is read there), so settling one unclosed
  subscript never requires a further re-read for later `name[` openers;
  many unclosed subscripts settle within a bounded number of readings
  (AC-6).

### Edge forms to confirm on bash 5.3 (rm replaced by echo in the probe)

`x=1 a[1<<2]=y`, `a[1<<2]+=x`, `a[b[1]<<2]=x`, a subscript holding a
quote or a `$( )`, the subscript form at a command position inside `$( )`,
and the declaration-builtin argument forms, each followed by the
destructive tail.
