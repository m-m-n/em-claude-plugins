# Task Plan: task0003 — Here-document delimiter read from the whole word

## Goal

The delimiter of a `<<` / `<<-` operator is the whole following word with
quote removal applied, and the close-line lookup accepts such delimiters,
so a delimiter like `END-X`, `E.X` or `E\X` no longer closes the body at
the wrong line; a delimiter word that cannot be read takes no body
(finding 9381769d7116fab2, second half).

## Requirements

FR4, FR6, FR8, NFR1, NFR5, NFR6

## Design

Cross-task rules that apply here (IMPLEMENTATION.md): this task owns the
here-document operator reading row of Shared Components; the case table
append protocol, the test layout row, the fail-safe direction and the bash
confirmation convention also apply.

### Delimiter word

- Extent: after the `<<` / `<<-` and any blanks, the word runs to the next
  unquoted metacharacter (blank, newline, `;`, `|`, `&`, `(`, `)`, `<`,
  `>`). Single-quoted and double-quoted segments and backslash escapes are
  part of the word.
- Value: the word after quote removal. `END-X` → `END-X`, `E.X` → `E.X`,
  `E\X` → `EX`, `E"X"` → `EX`, `'E-X'` → `E-X`, `\EOF` → `EOF`, `E$X` →
  `E$X` (no expansion; the characters are the delimiter).
- Quoted flag: true exactly when the word contains a `'`, `"` or `\`; its
  meaning on the here-document record is unchanged (a quoted delimiter
  makes the body literal).
- `<<<` stays a here-string and is never an operator.
- The single-pattern operator constant (destructive-guard.py:147-154) is
  replaced or removed as the new reading requires; nothing outside the hook
  references it. Its comment is updated to describe the new reading.

### Unreadable delimiter word (NFR6, SPEC A3)

- Unreadable: no word follows before a metacharacter or the end of the
  text; a quoted segment does not close on the operator's line; the word
  holds a command substitution, a backtick or a `${` / `$((` / `$[`
  construct.
- An unreadable delimiter takes no body: the text after the `<<` is lexed
  exactly as it is today for a `<<` that registers no operator, so no line
  after it is skipped as body.

### Close-line matching

- A line closes the body when, after removing its line end and the
  surrounding spaces / tabs (today's allowance, wider than bash, kept
  because it only ends a body earlier), the remainder equals the delimiter
  value. The remainder may contain any non-blank characters, not only word
  characters.
- This applies to both the close-line word function (destructive-guard.py
  :2234, may be renamed) and the per-text line index built from it
  (`_LexLines.word_to_lines()`), which stays one pass over the lines.
- A delimiter value the index cannot represent (e.g. one holding a blank)
  never finds a close line, so it takes no body.

### Not touched

Where a `<<` is reached (command position, subscripts, the settle channel's
tail rule) and the pending-body / line-start trigger belong to the base or
other tasks (IMPLEMENTATION.md D2).

## Acceptance Criteria (MANDATORY)

Commands below use the case table's JSON string notation (`\n` is a
newline, `\\` a single backslash).

- [ ] AC-1 (FR6): Before any commit that changes `em-workflow/hooks/destructive-guard.py`, a commit appends to the case table, after its last pre-existing entry, three deny cases with labels beginning with 9381769d7116fab2: `cat <<END-X\nbody\nEND-X\nrm -rf /home/sakura/valuable\nEND`, `cat <<E.X\nbody\nE.X\nrm -rf /home/sakura/valuable\nE` and `cat <<E\\X\nbody\nEX\nrm -rf /home/sakura/valuable\nE`; the task branch history shows that order.
- [ ] AC-2 (FR4, TM-3): For each of those three commands, `lex_shell()` reports exactly one here-document operator whose delimiter is `END-X`, `E.X` and `EX` respectively, quoted false, false and true, with body `body\n` ending before the delimiter line, and the hook decision is deny both without `CLAUDE_BATCH` and with `CLAUDE_BATCH=1`.
- [ ] AC-3 (FR4): Fixed expectations hold for the delimiter variants `<<E"X"` (`EX`, quoted), `<<'E-X'` (`E-X`, quoted), `<<\\EOF` (`EOF`, quoted — now registered as an operator), `<<E$X` (`E$X`, unquoted) and a `<<-` operator whose close line is tab-indented (the body closes there), each checked for delimiter, quoted flag and body.
- [ ] AC-4 (FR4, NFR6, TM-3): For an unreadable delimiter word with no word before the newline (`cat <<\nrm -rf /home/sakura/valuable\n2`) and with a word holding `$(` or a backtick followed on the next line by `rm -rf /home/sakura/valuable`, no body is taken and the hook decision is not allow; for a quote not closed on the operator's line, no body is taken and the text after the `<<` is lexed as it is today for a `<<` that registers no operator.
- [ ] AC-5 (FR4): A line holding only the delimiter value with optional surrounding blanks closes the body for non-word delimiters (`END-X`, `E.X`); a line where the value is only a prefix or a suffix (`END-XY`, `XEND-X`) does not; all existing word-only delimiter expectations are unchanged.
- [ ] AC-6 (NFR1): For the unit `cat <<END-X\nbody\nEND-X\n` repeated 200 and 400 times, the lexing work of the 400-unit text is at most 2.5 × the 200-unit work + 100 and at most `LEX_WORK_FACTOR` × its length + 1024.
- [ ] AC-7 (FR8, NFR5): No pre-existing case-table entry is removed, edited or reordered (if a new reading, such as registering `<<\EOF`, would flip an existing case's verdict, the case is left as is and the conflict is reported as a deviation), this task's cases sit at index 627 or later (located by label and command text), and `python3 em-workflow/hooks/tests/run-destructive-guard.py` and `python3 -m unittest tests.test_destructive_guard_lexer_agreement` both pass, including `TestStageAgreement` and `TestModuleContract`.

  change the hook.
