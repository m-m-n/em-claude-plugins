# Task Plan: task0002 — develop-skill wiring for the terminal line

## Goal

Make the terminal-line contract reachable from the develop orchestrator's own
stop and completion sites, so that a batch run actually emits the line, while
leaving the existing Step C completion report format untouched.

## Requirements

FR1, FR4, FR5, FR6, FR8, NFR1, NFR2, NFR4

## Scope

### Files to Create
- `tests/test_batch_stop_contract_skill_wiring.py` — documentation contract
  test for the develop-skill wiring and the Step C non-regression guard
  (TS5, and the wiring half of TS1/TS8).

### Files to Modify
- `em-workflow/skills/develop/SKILL.md` — add a batch terminal-line
  subsection near the existing stop-report section, plus a one-line pointer in
  the Step C completion report item. Additive only.

## Design

### What the SKILL.md edit must establish

1. A new subsection, placed immediately after the existing stop-report
   section, stating that in a `--batch` run every turn that ENDS the run
   emits the terminal line as the last line of the final assistant message,
   per `references/batch-terminal-line.md`.
2. That this applies both to normal completion (Step C's completion
   processing) and to every terminating stop — the develop stop conditions for
   a stuck step, a `failed` / `needs_update` step, a `workflow.yaml` parse
   error and a git-setup abort, together with a phase abort, a Step C abort,
   and the implement/verify terminating stops enumerated by the contract
   document.
3. That the turn which ends waiting for an implementer completion
   notification emits no terminal line.
4. A one-line addition to the Step C completion report item stating that the
   batch branch appends the terminal line after the existing report lines.

### Pointer discipline (IMPLEMENTATION.md Conventions)

The subsection names `references/batch-terminal-line.md` and states WHEN
emission happens. It must NOT restate the prefix literal, the field names,
any reason code or the sentinel value — those belong to the contract document
alone. This also keeps the prefix's single-file property (IMPLEMENTATION.md
D6) intact.

### Non-regression surface (FR4)

The following elements of the Step C completion report keep their current
wording and structure, and the edit must not reorder or reword them:

| Element | Kept as |
|---|---|
| Completion headline | The `em-workflow 完了: {feature}` line with its task-count / review-round / residual-findings annotation |
| Retained-branch guidance | The kept integration branch name plus the switch-and-merge-in guidance for the main working tree |
| PR branch | The PR URL line |
| License notice | The single line recommending license generation when `project.license` is `none` |
| Batch audit items | The batch reporting items (auto-approved commands, recorded assumptions, rework rounds consumed, deferred findings) |

### Constraints from IMPLEMENTATION.md D7

- Edits are additive; existing headings and anchor sentences are not reworded
  (several are pinned byte-for-byte by pre-existing test modules).
- No `decision table` / `決定表` string, no `requirements-spec-creator`, no
  `Read してインラインで従う` phrase.
- No new backticked `namespace.name`-shaped token near a `gate_id` / `gate ID`
  mention unless it is a `references/batch-policies.yaml` key.

## Test Notes

- Unit-level document-contract assertions over raw file text; no runtime
  behaviour to integration-test.
- Locate the new subsection by its own heading, then assert within that
  slice — asserting "somewhere in SKILL.md" would let an unrelated mention
  satisfy the check, the scoping mistake recorded in
  `tests/test_batch_policies.py`'s diff-size gate row test.
- Matcher needing a negative proof and a non-vacuity guard: the
  contract-literal absence matcher (forge a sample subsection that does
  restate a field name and confirm the matcher rejects it; the guard shows
  the forged sample is otherwise a well-formed subsection the slicer finds).
  AC-4's five Step C assertions are pure regression guards over retained
  pre-change wording and are exempt.
- Edge case: the Step C guard must survive whitespace/line-wrap differences in
  the surrounding paragraph, so assert on the distinctive substrings rather
  than on a whole reflowed paragraph.
- Run the whole suite, not just the new module: the wiring edit touches a file
  several pre-existing modules assert against.
