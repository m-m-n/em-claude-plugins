# Task Plan: task0003 — Plugin version bump

## Goal

Patch-bump the em-workflow plugin version in both registries to the same
value, and pin that invariant with a documentation contract test that goes red
on the un-bumped tree.

## Requirements

FR9, FR8, NFR1, NFR2, NFR4

## Scope

### Files to Create
- `tests/test_batch_stop_contract_version_bump.py` — documentation contract
  test for the two manifests (TS-7).

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — bump the plugin version string.
- `.claude-plugin/marketplace.json` — bump the em-workflow entry's version
  string to the same value.

## Design

### Responsibilities

| Element | Contract |
|---|---|
| Plugin manifest version | The value fixed in IMPLEMENTATION.md Shared Components (a patch bump from the current 0.1.39), written as a string |
| Marketplace entry version | The em-workflow entry carries a version string identical to the plugin manifest's |
| Every other manifest field | Unchanged — in particular the plugin manifest's name field, and the em-review marketplace entry's source field and its absence of a version key |

Both files are JSON and are parsed, never pattern-matched, by the test.

### Test responsibilities

Two matchers, following the convention of the existing version-bump module
named in IMPLEMENTATION.md Conventions:

1. A baseline matcher asserting the version is on the 0.1 line with a patch
   number strictly greater than the pre-bump baseline fixed in
   IMPLEMENTATION.md D8. A durable inequality is used rather than equality
   with a literal, so the module stays green across later unrelated bumps
   while still failing on the un-bumped tree.
2. An equality matcher asserting the two registries report the identical
   version string.

Each matcher gets a negative proof plus a non-vacuity guard, per
IMPLEMENTATION.md Conventions.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR9): the plugin manifest parses as JSON, its version is on the
      0.1 line with a patch number strictly greater than the IMPLEMENTATION.md
      D8 baseline, and its name field still reads em-workflow.
- [ ] AC-2 (FR9): the marketplace manifest parses as JSON; its em-workflow
      entry's version equals the plugin manifest's as a string; its em-review
      entry still has source ./em-review and still carries no version key.
- [ ] AC-3 (FR8, NFR1): the new test module is discovered by
      `python3 -m unittest discover -s tests` from the repository root and
      imports the Python standard library only.
- [ ] AC-4 (NFR4): the baseline matcher has a negative proof rejecting a
      forged pre-bump version, the equality matcher has a negative proof
      rejecting a forged pair of differing versions, and each has a
      non-vacuity guard showing the forged sample is itself a well-formed
      three-part version the parser accepts — so each proof exercises the
      comparison rather than a parse failure.
- [ ] AC-5 (NFR2): the whole suite passes with every pre-existing test module
      unmodified.

## Test Notes

- Unit-level assertions over parsed JSON. The version is compared as a
  numeric tuple for the baseline check and as a raw string for the equality
  check — the two are different properties, and a string comparison would
  silently accept a smaller patch number that sorts later lexically.
- Edge case: a version value that is not a three-part numeric string must fail
  as a parse failure distinguishable from a comparison failure; the
  non-vacuity guards depend on that distinction.
- Do not raise the baseline used by any pre-existing version-bump module —
  that would modify an existing test module and violate NFR2. This module
  carries its own baseline.

## Out of Scope

- Any change under the plugin's references or develop-skill directories
  (task0001 and task0002 own those).
- Updating the plugin description field.
- Generating or editing a LICENSE file.
