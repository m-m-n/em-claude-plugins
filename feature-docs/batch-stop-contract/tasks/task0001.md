# Task Plan: task0001 — Terminal-line contract SSOT document

## Goal

Create the SSOT document that defines em-workflow's batch terminal line — its
prefix, field grammar, terminal states, closed stop-reason-code set,
stop-point coverage mapping, wait-turn exclusion and responsibility boundary —
and point `references/batch-mode.md` at it without restating any of its
content.

## Design

### Contract document responsibilities

The document is the ONLY place in the plugin that defines what the terminal
line looks like. Its structure is fixed by IMPLEMENTATION.md Shared
Components (heading set, reason-code table shape, coverage table shape); this
task writes the content within that structure.

| Section | Content responsibility |
|---|---|
| `## Purpose` | Why the line exists: a batch run's terminal state must be readable from the output without relying on the caller process's exit code; the line's absence is itself the abnormal-outcome signal |
| `## Line format` | The prefix literal, the fixed four-field order, the separator and end-of-line rules, and the emission site (last line of the final assistant message of a batch turn). At least one fully-formed example line inside a fenced block |
| `## Field values` | The `state` domain, the `step` domain including the `no-step` sentinel and its "no step in effect" definition, the `reason` field's relation to the code set, and `detail`'s constraints (single line, human-facing, non-empty, no confidential information beyond paths) |
| `## Stop reason codes` | The closed set as a table, one backticked code per first column, with the meaning and the `state` each applies to. `none` is documented as reserved for `state=completed` |
| `## Stop point coverage` | The nine stop-point keys, each bound to exactly one reason code, each row naming the source document that owns the stop point |
| `## No line on a wait turn` | A turn ending at develop's stop condition 5 (waiting for implementer notification) emits no line, and why: an in-flight wait must not be readable as a stop |
| `## Responsibility boundary` | em-workflow declares the stop in its own output and performs no status operation against the external task-management service; the relay direction is outbound only, which is also why `detail` carries no confidential information |

### Behavioural conditions the document states

1. If the batch run reaches Step C's completion processing, the line is
   emitted with terminal state `completed`, the final workflow step as the
   step value and the reserved `none` reason.
2. If the batch run reaches any of the nine enumerated stop points, the line
   is emitted with terminal state `stopped`, the step in effect (or the
   sentinel when none is), the bound reason code, and a human-facing detail.
3. If the turn ends while waiting for an implementer notification, no line is
   emitted.
4. In every other case — a crash or a truncated turn — no line is emitted,
   and a consumer reads that absence as an abnormal outcome.
5. Emission happens only in a batch-mode run.

### Pointer in `batch-mode.md`

A short addition that names `references/batch-terminal-line.md` as the owner
of the terminal-line output contract and states that a batch run's final
message carries that line. It must not name the prefix, the fields, the
sentinel or any reason code. It must not add or remove a row of the
Non-packet gates table, and must not alter the catch-all paragraph, the
diff-size gate row or the per-command approval row (IMPLEMENTATION.md D7).

### Contract test responsibilities

The test module reads the two documents as text/data and asserts the
invariants below. Section location is by heading string; table extraction is
by first-column backticked token. Assertions favour durable invariants
(set membership, bidirectional coverage, structural shape) over long prose
literals, so ordinary rewording of the document does not break them.

## Test Notes

- All assertions are unit-level document-contract checks over raw file text —
  there is no runtime behaviour to integration-test.
- Read raw text (not parsed Markdown structure) so a literal hidden inside a
  code fence or an HTML comment is still seen; this matches the existing
  convention in `tests/test_reference_sweep.py`.
- Matchers needing a negative proof and a non-vacuity guard: the reason-code
  set extractor (forge a table with a duplicated code and one with an empty
  first cell — the guard shows the forged table is otherwise well-formed and
  parses), and the bidirectional coverage matcher (forge a mapping missing one
  stop-point key and one with a code outside the set — the guard shows the
  forged mapping parses into a non-empty pair of sets). Pure regression guards
  over retained `batch-mode.md` wording need no negative proof.
- Edge cases worth covering: a reason code appearing in prose but not in the
  table must not be picked up by the extractor; a stop-point key listed twice
  must fail; the prefix sweep must walk every file under `em-workflow/`, not
  a hand-maintained allowlist (the allowlist mistake recorded in
  `tests/test_reference_sweep.py`'s scoping note).
- TDD-awkward: AC-7's sweep is only meaningful once the document exists.
  Write it first against an empty expectation (prefix absent from the whole
  plugin directory), watch it pass, then invert it to the
  exactly-one-file expectation, which goes red until the document is written.
