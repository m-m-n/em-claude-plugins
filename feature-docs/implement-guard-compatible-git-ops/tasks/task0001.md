**Extraction rules**:

1. Candidates are inline code spans and non-comment lines of fenced blocks within the site's boundary. An inline code span that wraps across lines is joined with a single space; a fenced-block line ending in a line-continuation backslash is joined with the next line.
2. A candidate is a command when, after trimming, it begins with `git`. Its kind is its git subcommand, found after skipping git's global options and their values. `reset` kind = subcommand `reset`; worktree removal kind = subcommand `worktree` followed by `remove`; branch kind = subcommand `branch`.
3. Selection is by boundary and kind only — never by verdict, never by flag or target spelling. (A refresh rewritten to another target, or a step-4 deletion reverted to a forced flag, must still be extracted and then fail.)
4. Candidates inside an exclusion-list region are never selected.
5. Placeholder expansion covers every integration-worktree spelling present at in-scope sites — `{integration_worktree}`, `{integration worktree}`, `{integration worktree の絶対パス}`, `$WT_ROOT` (quoted or not) — plus `{feature}` and `{T}`, using the concrete sample values. After expansion, a command still containing a brace placeholder or `$WT_ROOT` fails, naming its site.
6. The command is passed to the guard as the orchestrator would type it (a trailing shell comment on the same line is kept).

**Assertions**:

- Every site document and every boundary anchor resolves; a missing one fails, naming the site.
- Every in-scope site yields at least one command of its kind; zero fails, naming the site.
- Every expanded command passes the guard (IMPLEMENTATION.md guard invocation contract); a failure names the site, the expanded command and the observed verdict.
- Every exclusion-list entry resolves to a region that still contains at least one git command (so the list cannot silently go stale), and no selected command originates inside an excluded region.
