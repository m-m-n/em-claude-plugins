Conventions used here: commit discipline, hook logic is read-only, case table discipline, test modules.

### Case table additions (FR5)

New entries are appended after the existing ones, in the existing three-element format, with Japanese labels in the style of the surrounding entries. Each label names which protocol site the case stands for.

**Allow cases** — exactly the three commands SPEC FR5 lists, verbatim:

| Stands for | Command | Expected |
|------------|---------|----------|
| Refresh (every refresh site) | `git -C /home/sakura/.claude/worktrees/em-workflow/some-feature/integration reset --hard em-workflow/some-feature/integration` | allow |
| Step I.2.b step 4 branch deletion | `git -C /home/sakura/.claude/worktrees/em-workflow/some-feature/integration branch -d em-workflow/some-feature/task0001` | allow |
| Step I.2.b step 4 worktree removal | `git worktree remove /home/sakura/.claude/worktrees/em-workflow/some-feature/task0001` | allow |

**Deny contrast cases** — the refresh shape above with the same `-C` path, differing only in the reset target; one case per excluded target form of the FR3 literal-target rule:

| Target form | Expected |
|-------------|----------|
| the integration branch name with a `refs/heads/` prefix | deny |
| a double-quoted shell variable (`"$BRANCH"`) | deny |
| `HEAD` | deny |
| a literal 40-hex-digit commit SHA | deny |
| no target at all | deny |

The first two are the ones SPEC FR5 / TS-2 names; the other three complete the FR3 excluded-form list.

Constraints: every new command string is unique across the whole table (the existing discipline test rejects duplicates); no existing entry is removed, reordered, or has its expectation or label changed (NFR2) — including the existing `git reset --hard HEAD~1` deny entry (TS-5). No allow case is added for a forced worktree removal or a forced branch deletion (IMPLEMENTATION.md D3).

### Version bump (FR8)

Both manifests carry the IMPLEMENTATION.md plugin version value; the `em-review` entry and every other field of both files are unchanged. The manifest edits and the case-table edit go into one commit (IMPLEMENTATION.md commit discipline).

### Version-bump test module

Follows the shape of the repository's existing per-feature version-bump modules: parse both files as JSON (never pattern-match text); look the marketplace entry up by its `name`; assert the version is strictly greater than `0.2.8` under per-component numeric comparison; assert the plugin manifest and the em-workflow marketplace entry report the identical string; assert the `em-review` entry is not dragged along. Each matcher carries a negative proof and a non-vacuity guard.
