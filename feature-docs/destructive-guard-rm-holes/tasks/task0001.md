# Task Plan: task0001 — rm reasons without raw targets, rm-hole regression tests, version bump

## Goal

The destructive-guard hook's rm reasons designate targets only by position and
templated alternatives, so planted text in a file name can no longer reach the
agent as hook guidance; the four rm holes (SAFE_DELETE prefix match,
substitution-only target, trash-directory creation guidance, raw target in the
reason) are pinned by tests that detect their return; em-workflow's version is
raised at the patch position.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create
- `tests/test_destructive_guard_rm_reason.py` — new unittest module: reason-text regression tests for FR3 and FR4, plus the CLAUDE_BATCH verdict checks for substitution-only targets (FR2, NFR4)

### Files to Modify
- `em-workflow/hooks/destructive-guard.py` — rm reason rendering (rm-unresolvable, rm-recursive, joined multi-target reason, deletion alternative) switches from raw target text to position designations and templated alternatives
- `tests/test_destructive_guard_command_substitution.py` — reason-text tests rewritten to the new notation (FR7)
- `em-workflow/hooks/tests/destructive-guard-cases.json` — additions only, if a form listed in AC-1 is missing from the table; no existing case is edited or removed
- `em-workflow/.claude-plugin/plugin.json` — em-workflow version raised at the patch position
- `.claude-plugin/marketplace.json` — em-workflow entry version set to the same value as plugin.json

## Design

This feature has a single task, so no IMPLEMENTATION.md exists (reduced tier:
it is written only when two tasks declare the same file). This plan is
self-contained; SPEC.md is the requirement reference.

### Why one task

- Any change under `em-workflow/` must carry the version bump in the same
  commit (the plugin-version-guard hook rejects the commit otherwise), so the
  hook change and FR8 cannot live in separate tasks.
- The FR6 / FR7 tests assert the new reason notation; in a separate parallel
  worktree they could never pass against the unchanged hook.

### What stays unchanged (SPEC.md a1-a4)

- SAFE_DELETE matching (FR1) and the substitution-only verdict (FR2) are
  already correct in the current hook. Their logic is not touched; this task
  only pins them with tests.
- The gio-versus-mv branch selection of the deletion alternative (gio on
  PATH, target under HOME, control characters in the target) keeps its
  current decisions. Only the rendering of the chosen alternative changes.
- The rm-root reason (fixed RM_ROOT_SHAPE forms, SPEC.md a2) and the
  safety-bypass reason (fixed BYPASS_FLAGS tokens, SPEC.md a4).
- Every verdict (allow / ask / deny) and every rule id, for every command
  (FR5): the change is confined to reason text.
- The CLAUDE_BATCH ask-to-deny downgrade and its wording (NFR4).
- No new standard-library module that touches the filesystem or spawns a
  process, and no new filesystem or subprocess call (NFR1).

### Target designation (contract)

- Input: an rm target that one of the in-scope reasons must mention.
- Output: a hook-authored designation that identifies (a) which rm invocation
  within the analysed command it belongs to, by ordinal, and (b) which target
  of that invocation it is, by ordinal among the operands (options are not
  counted). SPEC.md FR4 gives the example wording shape; the exact wording is
  the implementer's choice.
- Postconditions:
  - Within one reason, two different targets never get the same designation,
    including across several rm invocations joined in one compound command
    and rm invocations found inside substitution bodies.
  - The designation is a pure function of the command text: the same command
    always yields byte-identical designations (NFR2).
  - The designation contains no character taken from the target. The single
    exception: a target made only of command substitution may be shown with
    the fixed stand-in the hook already writes for substitutions (SPEC.md a3),
    next to its position.

### Deletion alternative (contract)

- Input: the branch facts the hook already evaluates (unchanged).
- Output: the alternative shown as a template with a fixed placeholder in
  place of the target: the gio trash shape or the mv-to-/tmp shape given in
  SPEC.md FR4.
- Postcondition: the template never contains the target string, and never
  contains a command that creates or modifies the trash directory (FR3).

### Joined multi-target reason

When several targets produce reasons of the same strength and the hook joins
them, every joined part uses the designation above; the joined reason as a
whole contains no target-derived text.

### Constraints on how the work proceeds

- The deny cases that catch the known regression of a previous fix attempt
  (bare `tmp`, `.cache`, `/var/tmp` and their trailing-slash forms) must be in
  the case table before any change to the hook (SPEC.md cites them as already
  present; confirm, and add any that are missing).
- After changing the hook, run the case suite (project rule for
  destructive-guard changes) and the repository unittest suite.
- The version values are taken from HEAD at commit time; only the patch
  position is raised, and em-review's version is not touched.

## Test Notes

- Mapping: AC-1 is covered by the case suite (the run-destructive-guard
  command). AC-2 to AC-8 are covered by unittest modules under tests/. AC-9
  is covered by the plugin-invariants command and the existing repository
  version checks run by unittest discovery.
- Test-first: write the AC-3 to AC-7 tests before editing the hook. The AC-3,
  AC-4, AC-5 and AC-6 tests are expected to fail against the current reason
  text; the AC-2 and AC-7 tests, and the verdict / rule-id half of AC-3, are
  expected to pass already (they pin existing behaviour). The control-
  character branch of AC-5 must be pinned against the current hook before
  editing.
- Planted strings: use distinctive text, e.g. Japanese instruction text and a
  bracketed prefix imitating the hook's own prefix but naming a rule the hook
  does not have, so the absence assertion cannot be confused with the hook's
  real prefix. Asserting the absence of a distinctive fragment as well as the
  whole string also catches partial echoes.
- Verdict / rule-id parity: compare each planted target against the same
  shape with neutral text, using the verdict and rule id as the hook reports
  them.
- Environment (NFR5): build the subprocess environment explicitly instead of
  inheriting it. HOME is a fixed test-controlled path; PATH is test-
  controlled. For the gio-on-PATH variants either place a stub executable
  named gio in a test-controlled directory on PATH, or rely on the real gio
  and skip that variant where gio is unavailable (SPEC.md TS8); the gio-absent
  variants must remove every directory containing gio from PATH.
- CLAUDE_BATCH variants: run the same inputs with CLAUDE_BATCH set and unset;
  make sure an inherited CLAUDE_BATCH from the runner cannot leak into the
  unset variant.
- Determinism (NFR2): run the hook twice on a multi-target compound command
  and compare stdout bytes.

## Out of Scope

- Any change to SAFE_DELETE matching, to the substitution-only verdict, or to
  any verdict or rule id.
- The rm-root reason and the safety-bypass reason.
- Checking the trash directory's owner or permissions (the hook does not touch
  the filesystem; SPEC.md FR3, a5).
- New filesystem or subprocess calls in the hook; any non-standard-library
  dependency.
- em-review's version; any other plugin file.
