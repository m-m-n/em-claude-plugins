# Task Plan: task0001 — Skip only the continuation lines of a leading tab line in parse_tests

## Goal

In the record check `tests/test_tests_yaml_id_resolution.py`, a `tests` block
whose first element is a tab line followed by a deeper line without a tab
keeps the readable IDs written after that continuation, so the extraction
errors and the resolution errors appear together in one failure message.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_tests_yaml_id_resolution.py` — the pre-item scan of
  `_RecordParser.parse_tests` (behavior, its docstring and its comments),
  and new test methods in `TestTabLinesInTestsBlock`.

No other file changes. No file under a plugin directory and no
`test/README.md` is touched.

## Design

This feature has no IMPLEMENTATION.md (reduced tier, single task); this
plan is self-contained.

### Terms

- **Tab line**: a line whose first character after its leading spaces is a
  tab (the definition the parser already uses).
- **Depth** of a line: the number of its leading spaces — for a tab line,
  the spaces before the tab. This is the same measure the item loop uses
  when it compares a tab line with the item indentation.
- **Pre-item scan**: the part of `parse_tests` that runs before the item
  indentation is fixed; it passes blank lines and comment lines and reports
  each tab line once as `tab in indentation`.
- **Most recent tab line**: the last tab line the pre-item scan reported.

### Current behavior (the defect)

When the pre-item scan stops at a line without a tab that does not start
with a dash and is deeper than the `tests` key, the parser reports `tests
value is not a block sequence of scalars` and passes over every following
line deeper than the `tests` key. With a leading tab line followed by its
continuation line, this also passes over the readable items after the
continuation, so their IDs never reach resolution.

### New behavior of the pre-item scan

The first line the pre-item scan reaches that is neither ignorable (blank
or comment) nor a tab line is classified as follows:

| # | Condition on that line | Behavior |
|---|------------------------|----------|
| 1 | Starts with a dash | Unchanged: it fixes the item indentation (or takes the existing no-items path when it is shallower than the `tests` key). |
| 2 | Does not start with a dash, is deeper than the `tests` key, a tab line directly precedes it (only blank and comment lines in between), and it is deeper than that most recent tab line | New: report `tests item continues or nests on a deeper line (multi-line or nested value)` once, at this line. Pass over every following line that is ignorable or deeper than the most recent tab line. Resume the pre-item scan at the first line that is not passed over. |
| 3 | Does not start with a dash, is deeper than the `tests` key, and row 2 does not hold (no tab line directly precedes it, or it is not deeper than the most recent tab line) | Unchanged: report `tests value is not a block sequence of scalars`, pass over every following line deeper than the `tests` key, and return no IDs. |
| 4 | Does not start with a dash and is not deeper than the `tests` key | Unchanged: the existing no-items path. Because a tab line was seen, `tests key has neither a value nor items` is not reported. |

The resumed pre-item scan follows exactly the same rules as the first pass:
each tab line it reaches is reported once and becomes the most recent tab
line, rows 1 to 4 apply to the next line that is neither ignorable nor a tab
line, and the record of having seen a tab line is kept, so row 4 still
suppresses the `neither` error.

### Postconditions and invariants

- No element written on a tab line or on a line passed over by row 2
  becomes an ID.
- A tab line inside a range passed over by row 2 (deeper than the most
  recent tab line) is passed over silently, not reported — the same
  treatment the item loop gives a tab line inside a deeper range after an
  item.
- Every row-2 pass consumes at least the reported line, so the pre-item
  scan always advances and terminates at the block end.
- For every record that never reaches row 2, the returned IDs, the next
  index and the reported errors are identical to the behavior before this
  change.
- The error texts are the existing ones; no new error text is introduced.

### Docstring and comments (FR3)

The `parse_tests` docstring and the comments of the pre-item scan
(including the comment that explains where the field loop resumes after the
no-items path) are updated so that they describe rows 2 and 3 above. Text
about the item loop that is unrelated to leading tab lines is left as is.

## Test Notes

- AC-1 to AC-5 are unit tests on the extraction function; AC-2 uses the
  record check the same way the existing tests of `TestTabLinesInTestsBlock`
  do (a temporary root holding one record). Write them first and confirm
  AC-1, AC-2 and AC-5 fail against the unchanged parser (AC-3 and AC-4 pin
  unchanged behavior and pass before and after).
- Add every new test as a new method of `TestTabLinesInTestsBlock`; the
  existing head and tab-line class attributes may be reused, but the new
  records must not be added to the existing `RECORDS` or `TAB_ONLY` tables:
  those tables feed existing tests whose expected error counts assume tab
  errors only, and changing their inputs would change existing tests
  (NFR1).
- Compare errors as complete sorted lists (the style of the existing
  `assert_extraction` helper), so an extra or missing error fails the test.
- AC-6 is verified by reading the docstring and comments; it has no
  automated test.
- A further case worth covering if cheap: after a passed-over range, a line
  without a tab and without a dash that is not deeper than the most recent
  tab line but deeper than the `tests` key takes row 3 (not-a-sequence).
