# Task Plan: task0001 — Exact status key match in the direct-child status read

## Goal

The Stop hook's per-task status read treats a direct-child line of a task
block as the deciding status line only when its key is exactly `status`, so a
differently named key that merely starts with `status:` (for example
`status:detail: ignored`) no longer hides the real direct `status: pending`
that follows it. New tests pin this so the regression introduced by feature
task-status-direct-key cannot return unnoticed.

## Requirements

FR1, FR2, FR3, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_queue_stop_guard_task_status_key_exact_match.py` — regression tests for the exact status key match (reader called directly, plus hook subprocess cases)

### Files to Modify
- `em-workflow/hooks/queue_stop_guard.py` — narrow the status-key recognition used by the direct-child status read, and update the adjacent comment and the reader docstring so they state the key-name rule

## Design

### Contract (unchanged)

`task_statuses_from_workflow(workflow_yaml_path) -> mapping of task id to
status string` keeps its name, signature and return shape (NFR3). It never
raises for any input, and the hook keeps exiting 0 on any internal failure
(fail-open, NFR2). `TASK_STATUS_RE` and `TASKS_SECTION_RE` keep their names
and their matching rules.

### The one rule that changes (FR1)

A line at the task block's direct-child indentation is a *status key line*
exactly when, after its leading whitespace, it begins with the text `status:`
and that colon is immediately followed by a space, a tab, or the end of the
line. This is the same colon rule the hook's existing key-colon finder
(`_find_key_colon`) applies. SPEC.md FR1 and A-1 state the exact pattern for
`TASK_STATUS_KEY_RE`; only that identifier's matching rule changes.

Effect on direct-child lines (the "Before" column is what the base-revision
hook does, which tells which new tests are expected to be red on base):

| Direct-child line | Before (base revision) | After |
|---|---|---|
| `status: pending` | key line, value `pending` | unchanged |
| `status:` + tab + `pending` | key line, value `pending` | unchanged (tab after the colon qualifies) |
| `status:` with no value (with a trailing newline, or as the last line of a file without one) | key line, value not extractable: task left out, later lines not read | unchanged (FR2) |
| `status:detail: ignored` | key line, value not extractable: task left out | not a key line: skipped, reading continues |
| `status:detail:` | key line, value `detail:` recorded | not a key line: skipped, reading continues |
| `status:pending` / `status:failed` | key line, value `pending` / `failed` | not a key line: skipped, reading continues |

### Processing flow of the reader (only step 4 changes)

1. Take each (task id, line) pair from the existing block scan; bodies of
   multi-line quoted scalars and flow collections are already dropped there.
2. Skip the line when the task is already decided.
3. Skip blank and comment lines; the first remaining line of the block sets
   the direct-child indentation; skip any line at a different indentation.
4. Skip the line when it is not a status key line under the rule above; the
   scan continues with the next line of the same block.
5. Mark the task decided; record the value when the existing value rule
   (`TASK_STATUS_RE`) can extract one, otherwise leave the task out.

Everything FR2 lists stays exactly as it is: the first direct status key line
decides, value extraction, how the direct-child indentation is determined
(a skipped non-key line that is the block's first line still sets it, as
today), and block-scalar bodies, nested mappings and comment lines are never
read. Skipping a non-key line leaves the direct-indent state and the
multi-line value tracking untouched (THREAT-MODEL.md TM-1).

### Test module

- Self-contained, following the sibling direct-key test module's convention:
  it imports no other test module and rebuilds its fixture helpers locally (a
  workflow text builder whose `implement` step is in progress and whose
  `tasks:` mapping holds task0001 with caller-supplied block lines, with an
  option to omit the final newline; a temporary integration-worktree layout
  holding workflow.yaml and the queue journal).
- The reader is called directly by loading the hook source into a private
  namespace, as the sibling module does, so no bytecode is written next to the
  hook. Hook cases run the hook as a subprocess with Stop-hook JSON on stdin.
- The module docstring records the red observed against the base-revision
  hook for the FR3 cases.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR3; TS-1, TS-3): Called directly on a task0001 block whose direct-child lines are a title line, `status:detail: ignored`, `status: pending`, the reader returns exactly `{'task0001': 'pending'}`; with a value-less, colon-ending other key `status:detail:` followed by `status: failed`, it returns exactly `{'task0001': 'failed'}`.
- [ ] AC-2 (FR1, FR3; TS-4, TS-7): When the only status-like direct-child line is `status:pending` (no space), the reader returns an empty mapping; when the direct-child lines are `status:failed` then `status: pending`, it returns exactly `{'task0001': 'pending'}`.
- [ ] AC-3 (FR1; TS-5): A direct-child `status:` followed by a tab and then `pending` is a deciding line, and the reader returns exactly `{'task0001': 'pending'}`.
- [ ] AC-4 (FR2; TS-6): A value-less direct-child `status:` that is the first status key line, followed by `status: pending`, leaves task0001 out of the result, both when the bare line ends with a newline and when it is the last line of a file with no trailing newline; the bare-colon subtest of `test_unextractable_first_direct_value_omits_the_task` in `tests/test_queue_stop_guard_task_status_direct_key.py` and `test_failed_task_with_undeterminable_status_still_suppresses` in `tests/test_queue_stop_guard.py` pass unchanged.
- [ ] AC-5 (FR1; TS-2): Running the hook as a subprocess on the AC-1 block plus a direct `routeback_failed_journal_line: 1`, with a journal whose line 1 is a failed event for task0001, ends with exit code 2 and stderr containing `launch=task0001`.
- [ ] AC-6 (TM-1, FR2; TS-8): After a skipped non-key direct-child line `status:detail: ignored`, a `status: pending` that appears only inside a deeper-indented notes block-scalar body, or only inside a nested mapping, is never read: with no direct status key line in the block the reader returns an empty mapping, and the hook run with the AC-5 record and journal exits 0 with no `BLOCK` in stderr. Every existing test in `tests/test_queue_stop_guard_task_status_direct_key.py` passes, with no test in that module modified or removed.
- [ ] AC-7 (FR3, NFR1, NFR2, NFR3, NFR4; TS-9, TS-10, TS-11): The AC-1 first case and both AC-2 cases were observed failing against the base-revision hook and pass after the fix, and the module docstring records that observation; the new module lives under `tests/` as a `test_*.py` file, uses only the standard library's unittest, builds fixtures in temporary directories and runs the hook as a subprocess with Stop-hook JSON on stdin; the hook still imports standard-library modules only; `task_statuses_from_workflow`, `TASK_STATUS_RE` and `TASKS_SECTION_RE` keep their names; and `python3 -m unittest discover -s tests` passes in full.

## Test Notes

- Unit (reader called directly): AC-1, AC-2, AC-3, AC-4 and the reader half
  of AC-6. Integration (hook subprocess): AC-5 and the hook half of AC-6.
- Red phase: write the FR3 tests first and run them against the unmodified
  hook; that run is the base-revision red AC-7 asks for. Expected base
  results per the Design table: TS-1 returns an empty mapping, TS-4 returns
  `pending`, TS-7 returns `failed` (TS-3 also fails, returning `detail:`).
  TS-5, TS-6 and TS-8 pass on base by design; they are regression guards,
  not red tests.
- AC-4 needs the fixture builder's no-final-newline option.
- CRLF needs no case: workflow.yaml is read in text mode, which turns CRLF
  into LF before any line is classified (SPEC.md FR2).

## Out of Scope

- `STEP_STATUS_RE`, `ROUTEBACK_RECORD_LINE_RE`, the value rule of
  `TASK_STATUS_RE`, direct-child indentation determination and multi-line
  value tracking (SPEC.md A-2, FR2).
- Treating `status :` (whitespace before the colon) or a quoted `"status":`
  key as a status key line (SPEC.md A-2).
- Restructuring the reader or the other workflow.yaml readers beyond the
  status-key recognition.
- Modifying or removing any existing test.
