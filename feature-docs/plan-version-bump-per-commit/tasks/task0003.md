# Task Plan: task0003 — plugin_versioning input for implementation-planner and the create-plan dispatch

## Goal

implementation-planner's input contract defines the orchestrator-resolved
`plugin_versioning` value and counts it in the planner's `input_digest`
`value_inputs`; the create-plan dispatch procedure resolves and passes it;
the planner's agent prompt names it and points at the plan-writing rules.

## Requirements

FR5, FR7, NFR1, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_plan_version_planner_dispatch.py` — regression tests for this task's documents (planner half of TS-5)

### Files to Modify
- `em-workflow/references/contracts/planner-contract.md` — owner definition of the dispatch value, its value_inputs membership, mandatory and untrusted status
- `em-workflow/references/phases/create-plan-phase.md` — Planner dispatch resolves and passes the value and includes it in the digest
- `em-workflow/agents/implementation-planner.md` — Inputs enumeration names the value and points at the plan-writing section

## Design

This task owns the definition pinned in IMPLEMENTATION.md ("plugin_versioning
contract"): the field table, resolution rules and behavioral contract items
1-6 there become the content of planner-contract.md's new subsection. The
heading text is a cross-task contract and must match exactly.

planner-contract.md:

1. "Additional input: planning_inputs" lists `plugin_versioning` alongside
   the existing path entries, marked as a value rather than a path.
2. A new subsection with the exact heading
   `### plugin_versioning (dispatch-resolved value)` carries the field
   table, the resolution rules (including the `dir`-ascending order), the
   per-dispatch and return-time re-resolution, the mandatory status with
   `invalid_input` on absence, and the untrusted classification citing
   worker-envelope.md's Untrusted-Input Handling (TM-1).
3. The digest_inputs section no longer says the planner has no
   `value_inputs`; it declares `plugin_versioning` as the planner's
   `value_inputs` member, digested per worker-envelope.md rule R1's
   normalization of the value.

create-plan-phase.md, Planner dispatch: the orchestrator resolves the value
per planner-contract.md on every implementation-planner dispatch (first
dispatch and re-dispatches carrying answers), places it in
`planning_inputs`, adds it to the digest's `value_inputs`, and re-resolves it
from the worktree's current state when recomputing the digest on return.
The procedure cites planner-contract.md for the shape instead of restating
the table.

implementation-planner.md: the Inputs paragraph that enumerates
`planning_inputs` includes `plugin_versioning`, and one pointer states that
plan-writing SKILL.md's "Plugin Version Handling" section governs how it is
applied (including the `files` rule). No version rule text is added.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR5): planner-contract.md lists `plugin_versioning` among `planning_inputs` as a value, and has a subsection headed exactly `### plugin_versioning (dispatch-resolved value)` that defines `exempt`, `plugins`, `plugins[].dir`, `plugins[].name` and `plugins[].marketplace_versioned` with the resolution rules of IMPLEMENTATION.md's plugin_versioning contract (workflow-file presence at the worktree root; git-tracked directories containing `.claude-plugin/plugin.json`; same-named root marketplace entry carrying a version; ordering by `dir`).
- [ ] AC-2 (FR5): planner-contract.md's digest_inputs section declares `plugin_versioning` as a `value_inputs` member and no longer states that the planner has no `value_inputs`.
- [ ] AC-3 (FR5): planner-contract.md states that the value is mandatory on every create-plan dispatch and that a dispatch without it is answered with `invalid_input`.
- [ ] AC-4 (TM-1): planner-contract.md classifies `plugin_versioning` as untrusted input under worker-envelope.md's Untrusted-Input Handling (cited, not restated) and states that the value carries only the exemption boolean, project-relative plugin directory paths, plugin names and the per-plugin marketplace flag — no other text copied from repository files.
- [ ] AC-5 (FR5): create-plan-phase.md's Planner dispatch states that the orchestrator resolves `plugin_versioning` per planner-contract.md at every implementation-planner dispatch including re-dispatches carrying answers, passes it in `planning_inputs`, includes it in the `input_digest` `value_inputs`, and re-resolves it for the return-time digest recomputation.
- [ ] AC-6 (FR5, NFR1): implementation-planner.md names `plugin_versioning` among its `planning_inputs` and points to plan-writing SKILL.md's "Plugin Version Handling" section for how it is applied, without containing version rule statements (no per-commit bump wording, no comparison rule wording).
- [ ] AC-7 (FR7, NFR3): `tests/test_plan_version_planner_dispatch.py` asserts AC-1 to AC-6 against the three documents, using only the standard library and repository files; `python3 -m unittest discover -s tests` passes.

## Test Notes

- All criteria are unit tests over document text. Anchor on the pinned
  subsection heading, the field names, the literals `value_inputs`,
  `invalid_input` and `Untrusted-Input Handling`, and the section names of
  create-plan-phase.md and implementation-planner.md.
- AC-2's negative half: assert the old "no value_inputs" statement is gone.
- AC-6's negative half doubles as this task's FR7 negative check: the agent
  prompt must not restate (or contradict) the version rules; exercise the
  check against an in-test permissive sample such as a sentence allowing
  later tasks to keep the version, per IMPLEMENTATION.md Conventions.
- Assert only on this task's own documents (IMPLEMENTATION.md Test scope);
  the plan-writing heading is checked by name inside implementation-planner.md.
