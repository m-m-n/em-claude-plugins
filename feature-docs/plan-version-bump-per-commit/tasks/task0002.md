# Task Plan: task0002 — conflict-protocol version exception in worktree-task-workflow

## Goal

worktree-task-workflow's parent-side adoption protocol gains a
non-exempt-repository exception that sets the plugin version on adoption
commits and re-implementation commits so that plugin-version-guard accepts
them. Regression tests detect removal of the exception or a permissive
restatement.

## Requirements

FR6, FR7, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create
- `tests/test_plan_version_worktree_conflict.py` — regression tests for the exception (TS-6 and this task's half of the FR7 negative check)

### Files to Modify
- `em-workflow/skills/worktree-task-workflow/SKILL.md` — version exception inside the existing parent-side adoption protocol

## Design

This task owns the conflict-time rule pinned in IMPLEMENTATION.md Shared
Components ("worktree-task-workflow parent-side adoption protocol, version
exception").

Placement: inside the existing parent-side adoption protocol, next to the
steps that produce the adoption commit (`{task_id}: resolve via parent-side
adoption`) and the re-implementation commit (`{task_id}: re-implement on
updated parent`). No new top-level section.

Behavior to describe:

1. **Applicability**: the exception applies only in a non-exempt repository.
   The definition of exempt / non-exempt and the meaning of "greater" are
   cited from plan-writing SKILL.md's "Plugin Version Handling" section (path
   plus heading), not restated.
2. **Adoption commit**: when the adoption commit changes files under a
   plugin, that plugin's `plugin.json` version in the commit is greater than
   both the parent-side value and the task-side HEAD value from before the
   adoption.
3. **Re-implementation commit**: the version in the re-implementation commit
   is greater than the HEAD value after the adoption.
4. **Marketplace alignment**: in each of these commits, the same-named
   `.claude-plugin/marketplace.json` entry, when it carries a version, is set
   to the same value.
5. **Exempt repository**: no additional step is performed.

Decision flow for the implementer at the adoption step: non-exempt? → does
the adoption commit change files under a plugin? → set the version above both
sides (and align marketplace) before committing. Then at the
re-implementation step: set the version above the post-adoption HEAD value.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR6): the parent-side adoption protocol in `em-workflow/skills/worktree-task-workflow/SKILL.md` states that, in a non-exempt repository, an adoption commit (`{task_id}: resolve via parent-side adoption`) that changes files under a plugin sets that plugin's version greater than both the parent-side value and the task-side HEAD value.
- [ ] AC-2 (FR6): the protocol states that a re-implementation commit (`{task_id}: re-implement on updated parent`) sets the version greater than the HEAD value after adoption.
- [ ] AC-3 (FR6): the protocol states that the same-named `.claude-plugin/marketplace.json` entry, when it carries a version, is set to the same value in those commits.
- [ ] AC-4 (FR6): the protocol states that an exempt repository performs no additional version step.
- [ ] AC-5 (NFR1): the exception cites plan-writing SKILL.md's "Plugin Version Handling" section (repository-relative path and heading text) as the owner of the exempt / non-exempt definition and of the comparison rule.
- [ ] AC-6 (FR7): `tests/test_plan_version_worktree_conflict.py` contains a negative check that fails when the protocol permits keeping the version unchanged (or taking the parent-side version as-is) on an adoption or re-implementation commit in a non-exempt repository; the check rejects an in-test permissive sample sentence and accepts the real protocol text.
- [ ] AC-7 (NFR2, NFR3, NFR4): the added text contains no concrete version value and no fenced code block for the rule; the tests use only the standard library and repository files; `python3 -m unittest discover -s tests` passes.

## Test Notes

- AC-1 to AC-5 are unit tests over SKILL.md: locate the parent-side adoption
  protocol (anchor on the two commit-message templates) and assert the key
  terms of each criterion near them.
- AC-6 needs the same two-direction proof as every FR7 negative check (see
  IMPLEMENTATION.md Conventions): the existing protocol's general "adopt the
  parent side" wording is not itself a version statement, so the check must
  target version-specific permissive statements only.
- Assertions touch only this task's own document (IMPLEMENTATION.md Test
  scope); the cited plan-writing heading is checked by name in this
  document, not by opening plan-writing SKILL.md.
