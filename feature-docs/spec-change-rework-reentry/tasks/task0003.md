# Task Plan: task0003 — Step I.0 admits the SPEC-change re-entry

## Goal

Implement Step I.0 recognises the SPEC-change re-entry as an entry route:
identified from committed facts only, it does not ABORT when no task is
pending or failed, and with no pending task it completes the phase through
Step I.3 without launching an implementer. Every other non-fresh entry with
nothing to do still ABORTs immediately.

## Design

Cross-task anchors and conventions: IMPLEMENTATION.md (Shared Components
"Step I.0 re-entry precondition", "SPEC-change transition block",
"`spec_change` record"; Conventions; D3). Items 1 to 4 of Step I.0 and Steps
I.1, I.2 and I.3 are not edited.

**Step I.3 stays as it is.** On the zero-task route every task is `merged`,
which Step I.3's opening condition already covers, and Step I.3's
`completed_at_commit` write is what keeps the same `spec_change` record from
grounding a later re-entry (SPEC A3). Step I.0 routes to it; several existing
tests pin Step I.3 verbatim.

Layout of item 5 after the edit, in order:

1. **Opening sentence**: names four entry routes into `implement: pending` —
   a fresh first pass, a rework re-entry, the SPEC-change re-entry and the
   develop skill's batch infra auto-resume. The auto-resume's parenthetical
   citation of `skills/develop/SKILL.md` is kept word for word.
2. **Fresh first pass** sentence: unchanged.
3. **Rework re-entry** paragraph: unchanged, byte for byte (its condition
   sentence is pinned as raw text with its line break).
4. **Batch infra auto-resume** paragraph: unchanged.
5. **SPEC-change re-entry** paragraph(s), new:
   - Definition: the entry into `implement` after the SPEC-change transition
     (`references/rework-task-synthesis.md` Section 10, the
     `**When rework needs a SPEC.md change**` block, cited and not restated)
     and the create-spec → create-plan re-run that follows it.
   - Identification — all of the following, read from committed facts only
     (SPEC.md Data Flow 1–5, A2): `create-spec` and `create-plan` are
     `completed` and `implement` holds `base_commit` and a prior
     `completed_at_commit`; `phase-state/rework.yaml` holds a `spec_change`
     record with `consumed: true` and `replan_authorized: false` (field
     meanings cited to `references/phase-state.md`, not restated); the prior
     `completed_at_commit` is a proper ancestor of the record's
     `recorded_at_commit`, and `recorded_at_commit` is an ancestor of the
     current integration tip, with no timestamp compared; the commit history
     shows that the SPEC-change transition that wrote this record returned
     `implement` to `pending` (the tier-upgrade procedure writes the same
     record without doing so, so the flags alone do not suffice); the task
     set is non-empty and every task is `merged`.
   - Inputs (TM-3): the identification uses no session memory and no
     worker natural-language output.
   - Commit values (TM-1): before a commit value read from `workflow.yaml` or
     from the `spec_change` record appears in any git command, it is checked
     against the shape of a full hexadecimal commit object id; a value that
     does not match means the entry is not a SPEC-change re-entry, and the
     value is never sanitised (same fail-closed discipline as item 2's
     identifier gate). Ancestry checks are described in prose; no new fenced
     command block is added to Step I.0.
   - Resume: a resume of the same re-entry, where `implement` reads
     `in_progress` written by that re-entry's own Step I.1, is admitted on the
     same facts.
   - Outcome: on this route, an entry with no `pending` task and no task whose
     reconciled state is `failed` is not a protocol error and does not ABORT.
     With no `pending` task, Step I.1 runs as usual (gitignore guard,
     `base_commit` preserved, `implement` → `in_progress` commit), Step I.2 is
     skipped — no implementer is launched and the turn is not ended waiting on
     an empty queue — and the phase proceeds in the same turn to Step I.3,
     whose capture → refresh → write → commit sets `completed_at_commit` even
     though no task ran; that update keeps the same record from grounding a
     later re-entry. When the re-plan registered one or more new `pending`
     tasks, the entry meets the rework re-entry's condition and proceeds
     through Step I.2 as usual.
6. **ABORT** paragraph: amended so that the immediate ABORT applies to a
   non-fresh entry that is not a SPEC-change re-entry and satisfies neither
   the rework nor the auto-resume condition; an entry for which any
   identification condition does not hold falls here (TM-2). The phrase "with
   nothing to launch" is kept.
7. **Step A.6 restoration** paragraph: unchanged, still after the ABORT text.

Pins to keep in other modules: the raw rework-route condition and the
"stated before the launch selection" ordering in
`tests/test_rework_synthesis_contract.py`, the Step I.3 opening sentence
pinned there, the Step A.6 restart checks and their ordering after
"with nothing to launch" in `tests/test_write_rejection_parent_docs.py`, and
the auto-resume pins in `tests/test_failed_kind_resume_reentry.py`.
