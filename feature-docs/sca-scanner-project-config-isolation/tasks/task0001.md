# Task Plan: task0001 — Run npm / cargo scans from a per-group isolation directory

## Goal

npm and cargo scan groups that passed the binding check run from a newly created, owner-only isolation directory outside the reviewed tree. The directory holds only copies of the validated inputs. As a result, the reviewed project's `.npmrc` / `.cargo/audit.toml` are no longer on the scanners' discovery path. An isolation failure makes that unit `not_completed` and never falls back to running inside the tree.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, FR9, FR10, FR11, FR12, FR13, NFR1, NFR2, NFR3, NFR4

## Design

Cross-task contracts are pinned in IMPLEMENTATION.md Shared Components: the isolation failure reason tokens, the npm / cargo execution-location contract, the unchanged scan surfaces and the trusted configuration scope. This task produces or preserves each of them. They are not restated here.

### Isolation workspace (new, internal to scan-dependencies.py)

Responsibility: for one scan group, produce a directory outside the reviewed tree that contains exactly the copied scan inputs, and guarantee that the directory is removed.

Inputs: the ecosystem, the real (fully resolved) project root, and the group's validated inputs. For npm these are `package.json` and the selected anchor. For cargo it is `Cargo.lock`.

Flow:

1. Determine the temp parent that the standard temp-directory selection would use in this process. That selection honors the sources SPEC AC6 lists: `TMPDIR` / `TEMP` / `TMP` / `tempfile.tempdir`. Resolve the parent's real path. If it equals the real project root or lies under it, the isolation fails.
2. Create one new, uniquely named directory under that same checked parent. Access is owner-only from the moment of creation, with no window in which group or other users can access it.
3. Resolve the created directory's real path. If it equals the real project root or lies under it, the isolation fails.
4. For each input, re-validate the source with the same rule the binding check applies. Reuse that rule rather than writing a second, looser one. Read the content: an allowed same-directory symlink is followed to its target. Write the content as a new regular file in the isolation directory under the input's own file name. The content is byte-identical, and nothing else is copied.
5. If any of steps 1–4 fails, remove everything created so far and report an isolation failure for the ecosystem. The failure signal carries no path.

Postcondition on success: the directory exists, its real path is outside the real project root, it is owner-only, and it contains exactly the copied inputs.

Removal: recursive, including files the scanner itself created there. It is structured as a scoped acquisition, so no exit path skips it: success, tool failure, timeout, and an error during copying all lead to removal.

Containment rule: "under the root" is decided on real paths by path components. A sibling whose name merely starts with the root's name is not under the root.

Removal failure: SPEC defines no behavior for it. The unit's recorded outcome stays as the scan determined it, and no path is emitted (IMPLEMENTATION.md Open Questions).

### build_scan_job (stays pure)

- New input: a prepared-input value for npm / cargo, holding the isolation directory path and the path of each copy keyed by input role. pip and go do not use it, and their output for the same inputs is unchanged.
- npm: cwd is the isolation directory. argv is unchanged.
- cargo: cwd is the isolation directory. argv is the scanner, then `audit`, then the registry-declared target flag followed by the copied lockfile path immediately after `audit`, then `--json`. There is no `--url` and no `--db`.
- The job's manifest / label stays the original project-relative path (FR9).
- Precondition: npm / cargo jobs require the prepared-input value. Without it, the function never produces a job whose cwd is the project root.
- Purity: it only composes values. It opens no file and starts no process (NFR1).

### Registry cargo entry (vuln-scanners.yaml)

The cargo entry declares the lockfile target flag (`--file`) explicitly, and build_scan_job reads that declaration to position the flag. Both halves are required (FR3):

- A declaration that build_scan_job ignores does not satisfy FR3.
- A flag hard-coded in build_scan_job without the declaration does not satisfy FR3 either.

### Run side (_scan_bound_group, run_ecosystem_command)

1. The binding check runs unchanged. A group that fails it keeps its existing outcome, and no isolation directory is created for it.
2. npm / cargo: acquire the isolation workspace for the group's validated inputs.
3. On isolation failure: the unit becomes `not_completed` with `<ecosystem>_isolation_failed`. The scanner is not launched and nothing is retried inside the tree. Control returns so that the remaining groups are scanned.
4. On success: build the job with the prepared-input value and run it through run_ecosystem_command with the job's cwd. The environment composition is unchanged: the runner's environment with the existing ECOSYSTEM_ENV_PINS applied and no new variable. The outcome is judged exactly as today. For cargo, the direct-dependency judgment still reads the original Cargo.toml in the reviewed tree.
5. Release the workspace on every path.

pip / go take the existing path unchanged.

### Aggregation (run_scan)

Iteration, processing order and `skip_reason` assembly are unchanged. An isolation failure reason enters like any other unit reason, and completed groups' findings are retained.

### Documentation (FR13, FR11)

- ECOSYSTEM_ENV_PINS comment: the npm pins and the intentionally empty cargo pins are kept as they are, and project-level configuration is excluded by running from the isolation directory. It also states the trusted configuration scope (IMPLEMENTATION.md Shared Components).
- The docstrings of build_scan_job, run_ecosystem_command, _scan_bound_group and run_scan describe, respectively, the prepared-path input and purity, the isolation-directory cwd, ownership of preparation / removal / failure mapping, and the new reason tokens.
- vuln-scanners.yaml cargo comment: cargo-audit runs from the isolation directory with the target flag pointing at the copied lockfile.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR5, FR9, FR12; TM-1): The project root holds an adversarial `.npmrc` (`https-proxy`, `strict-ssl=false`, `registry`, `cafile`). The npm invocation recorded by the stub during run_scan has all of the following:
    - a cwd whose real path is outside the real project root;
    - no `.npmrc` in that cwd or in any of its ancestors;
    - argv exactly `[<npm>, audit, --json, --workspaces=false]`;
    - copies of `package.json` and the anchor that are byte-identical to the originals. When both `npm-shrinkwrap.json` and `package-lock.json` exist, only `npm-shrinkwrap.json` is copied as the anchor.

  The unit completes, and its label is the original project-relative `package.json` path.
- [ ] AC-2 (FR2, FR3, FR5, FR9, FR12; TM-2): The project holds an adversarial `.cargo/audit.toml` (`[advisories] ignore`, `[database] url/path`). The recorded cargo-audit invocation has all of the following:
    - a cwd outside the real project root;
    - no `.cargo/audit.toml` in that cwd or in any of its ancestors;
    - argv exactly `[<cargo-audit>, audit, --file, <copy>, --json]`, where the copy lies inside the recorded cwd and is byte-identical to the original `Cargo.lock`;
    - no `--url` and no `--db`.

  The registry cargo entry declares the target flag, and job assembly uses that declaration. A vulnerability reported for a crate that is direct in the original Cargo.toml is judged direct.
- [ ] AC-3 (FR5, FR8, FR9; TM-3, TM-7): Several npm and cargo groups have mutually different input contents. Each recorded invocation's copied inputs equal its own group's originals, and each group gets a distinct isolation directory. The invocation order and the findings' file labels equal the pre-change behavior. An allowed same-directory symlink source is copied as a regular file whose content equals the link target.
- [ ] AC-4 (FR6, FR7, NFR2; TM-4): Each of the following redirects the temp parent into the reviewed tree:
    - `TMPDIR`;
    - `TEMP`;
    - `TMP`;
    - the process-wide override named in SPEC AC6;
    - a temp parent whose path resolves through a symlink into the tree.

  In every case, the unit is `not_completed` with `<ecosystem>_isolation_failed`, the stub is never invoked, and the reviewed tree's paths and contents are unchanged.
- [ ] AC-5 (FR7, NFR3; TM-5, TM-6, TM-9): A copy fails for one group. That group's scanner is never invoked, inside or outside the tree, and the group gets `<ecosystem>_isolation_failed`. The other groups in the same run are scanned, and their findings remain in the result. `skip_reason` and the summary contain none of these path strings: the project root, the temp parent, or any isolation directory.
- [ ] AC-6 (FR8; TM-7, TM-8): No isolation directory created by the run remains after any of these outcomes:
    - success;
    - tool failure (non-zero exit, malformed output);
    - timeout;
    - failure in the middle of copying.

  The permission bits of its cwd, as recorded by the stub, grant nothing to group or other.
- [ ] AC-7 (FR4, NFR1): With file opening and process creation forbidden by mocks, build_scan_job called with a prepared-input value succeeds for npm and for cargo.
- [ ] AC-8 (FR10, FR11, FR13, NFR4): All of the following hold:
    - The npm / cargo child environments recorded by the stub contain no variable added or overridden relative to the pre-change composition, and HOME is unchanged.
    - ECOSYSTEM_ENV_PINS values are unchanged.
    - The docstrings / comments listed in Design describe the isolation directory as the npm / cargo execution location, and none of them still describes the reviewed project root as that cwd.
    - `python3 -m unittest discover -s tests` passes.

## Test Notes

- Recording stubs: test-owned executables named as the scanner resolves npm and cargo-audit, placed first on PATH.
    - On each invocation, a stub appends a record to a file named by a test-set environment variable. The record holds the cwd real path, argv, HOME and the environment, the cwd permission bits, the cwd listing, the contents of the copied inputs, and whether `.npmrc` / `.cargo/audit.toml` exists in the cwd and in each ancestor up to the filesystem root.
    - Records are written during the invocation, before removal.
    - By default the stub prints a well-formed clean result for its ecosystem. Test-set variables switch it to returning a vulnerability, failing, or sleeping past the timeout.
- Temp parent: success-path tests point the temp parent at a dedicated, empty, test-owned directory that is a sibling of the project tree, never nested inside it. "No isolation directory remains" is asserted as that directory being empty after the run.
- Redirection cases (AC-4): the standard temp-directory selection caches its result process-wide. Each case resets that cache before running and restores it and the environment afterwards.
- "Tree unchanged" is a before/after snapshot of the project tree: paths plus contents.
- Timeout (AC-6): shorten the scan timeout through the existing injection point, or by patching the module's timeout setting for the test only. Use a stub that sleeps beyond it.
- Copy failure in the middle (AC-5, AC-6): inject a failure into the copy of the second npm input. Assert that the stub was not invoked and that no isolation directory remains.
- Purity (AC-7): SPEC TS8 names the entry points to forbid. The test asserts success, not merely the absence of an exception elsewhere.
- Existing tests: update them to the new contract without deleting the coverage they provide. They must not depend on a real npm or cargo-audit.
- Every test here is offline and deterministic (NFR4).

## Out of Scope

- Any change to pip / go jobs or to ECOSYSTEM_ENV_PINS values.
- Adding `--url` / `--db`, or any pin that disables or overrides reviewer-managed configuration.
- `em-workflow/references/review-phase.md`. It is owned by another task and must not be edited here.
- Changes to grouping, the binding check, processing order or `skip_reason` assembly.
- Run-time scanning of ancestor directories for configuration files.
