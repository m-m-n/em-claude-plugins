# Task Plan: task0001 — journal helper accepts `merge-unverified` over a locked `merged` event

## Goal

`em-workflow/scripts/journal-append-failed.py` accepts a third reason,
`merge-unverified`, and appends a terminal `failed` event for it only when the task's
own final journal event is `merged` inside the helper's existing exclusive lock; every
other state is a byte-identical no-op reported with the existing `noop_terminal`
outcome.

## Requirements

FR5, FR10, NFR1, NFR5, NFR6, NFR7, NFR8

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/scripts/journal-append-failed.py` — widen the closed reason set to three values, add the merged-only decision for the new reason inside the existing lock, reject a launch identity supplied with the new reason, and update the module docstring, decision docstrings, argparse description and argparse help
- `tests/test_journal_append_failed.py` — add subprocess-level and function-level tests for the new reason, update the closed-set assertion, keep every existing test

## Design

Normative contract: IMPLEMENTATION.md SC-1 and D3 / D4. This task is the only builder
of SC-1; other tasks describe it in prose.

### Decision table (made inside the same exclusive lock as the replay)

| reason | launch identity supplied | task's own final event | result |
|--------|--------------------------|------------------------|--------|
| `merge-unverified` | no | `merged` | one `failed` line appended (fields in the order event, task, at, reason; reason `merge-unverified`); outcome `appended` |
| `merge-unverified` | no | `launched`, `failed`, none, or any other name | no write; outcome `noop_terminal`; journal byte-identical |
| `merge-unverified` | yes | not read | usage error before the journal is opened: non-zero exit, empty stdout, diagnostic on stderr |
| `orphaned` / `stale-launched` | as today | as today | unchanged: append only over `launched` (with the existing launch-identity comparison when supplied); `merged` / `failed` / none → `noop_terminal`; identity mismatch → `launch_changed` |

### Processing flow for `merge-unverified`

1. Validate the reason against the closed set (now three values) before the journal
   is opened — same position as today.
2. If a launch identity was supplied with `merge-unverified`, stop with a usage error
   (D4) — still before the journal is opened.
3. Open the journal with the existing preconditions (must exist, must not be a
   symbolic link, never created).
4. Take the exclusive lock; replay the task's own final event under it.
5. Final event `merged` → append the `failed` line through the same line builder the
   other reasons use (identical field names, order and timestamp format; only the
   reason value differs) and report `appended`; anything else → report
   `noop_terminal` without writing.
6. Release the lock; print one JSON line (`outcome`, `task`, `reason`) on stdout;
   exit 0.

### Unchanged contracts

- Outcome vocabulary (`appended` | `noop_terminal` | `launch_changed`) and the
  exit-code contract (0 for every decided outcome; non-zero, with no write, for usage
  or internal errors; diagnostics on stderr only).
- The `orphaned` and `stale-launched` decisions, including no-op over `merged`.
- The journal is append-only; replay and append share one exclusive lock (NFR6).

### Documentation inside the script

- The closed-set constant's comment states that adding `merge-unverified` is the
  intended, deliberate widening of that constant.
- The module docstring names all three reasons and states `merge-unverified`'s
  distinct precondition (final event `merged`; never over `launched`; no launch
  identity) and its sole caller: the orchestrator's I.2.b step 1 ancestor-check
  branch in `em-workflow/references/implement-phase.md` (IMPLEMENTATION.md SC-4
  label), cited, not restated.
- The argparse description and the reason help name all three values; the
  launch-identity help states it is not accepted with `merge-unverified`.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR5): With a journal whose final event for the task is `merged` (preceded
  by other tasks' lines), `--reason merge-unverified` exits 0 and prints exactly one
  JSON line with outcome `appended`, the task id and reason `merge-unverified`; the
  journal equals its prior bytes followed by exactly one new line whose keys are, in
  order, event, task, at, reason — event `failed`, reason `merge-unverified`, and an
  RFC 3339 `at` with an explicit offset.
- [ ] AC-2 (FR5, NFR5): For each of the final-event states `launched`, `failed`, no
  event for the task, and an unrecognized event name, `--reason merge-unverified`
  exits 0 with outcome `noop_terminal` and the journal is byte-identical to its prior
  content.
- [ ] AC-3 (FR5): `orphaned` and `stale-launched` over a final `merged` event each
  report `noop_terminal` with a byte-identical journal; `test_final_event_merged_is_noop`
  is kept unmodified and every pre-existing test in the module still passes.
- [ ] AC-4 (FR5): The function-level reason check accepts exactly `orphaned`,
  `stale-launched` and `merge-unverified` and rejects `manual`, the empty string and a
  non-string; the command-line help output names all three values; the module
  docstring names `merge-unverified` together with its merged-only precondition.
- [ ] AC-5 (FR5, NFR5): `--reason merge-unverified` supplied together with
  `--launch-at` exits non-zero, prints nothing on stdout, writes a diagnostic to
  stderr, and leaves the journal byte-identical — including when the final event is
  `merged`.
- [ ] AC-6 (FR5, NFR6): Several concurrent `--reason merge-unverified` invocations for
  one task whose final event is `merged` add exactly one `failed` line in total;
  exactly one invocation reports `appended` and every other reports `noop_terminal`.
- [ ] AC-7 (FR5, NFR7): After a `merge-unverified` `failed` line has been written for
  a task, invoking the unmodified `em-workflow/hooks/queue_launch_guard.py` through its
  hook interface for that task exits 0 with no deny decision, and the task's journal
  last event becomes `launched`.

## Test Notes

- All subprocess tests reuse the module's existing temp-directory journal layout;
  byte identity is asserted with raw byte reads, not line comparisons.
- AC-6 reuses the module's existing threaded concurrent-invocation pattern with a
  `merged` final event.
- AC-7 mirrors the existing launch-guard convergence test (hook driven only as a
  subprocess over stdin; never imported, never modified).
- The existing closed-set function-level test is extended to accept
  `merge-unverified`; no test method is removed or skipped (IMPLEMENTATION.md
  Convention 7). The existing stdlib-only import checks for the helper and this module
  keep passing (NFR8).
- Red first: each new case that depends on `merge-unverified` being accepted must be
  observed failing against the unmodified helper before the helper is changed. The
  AC-5 rejection case (`merge-unverified` with `--launch-at`) already exits non-zero
  with empty stdout and no write today, because the unmodified helper rejects the
  unknown reason; that case is exempt from the red-first requirement, and its test
  additionally asserts the diagnostic that identifies the combination (not the
  unknown-reason diagnostic) so it distinguishes the new rejection from today's.
