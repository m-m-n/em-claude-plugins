# Task Plan: task0004 — automated exit for a journal-`merged` task failing the ancestor check; no status-semantics exception

## Goal

`em-workflow/references/implement-phase.md` gives a task whose journal last event is
`merged` but whose merge fails `git merge-base --is-ancestor` an automated exit: I.2.b
step 1 invokes the journal helper with `--reason merge-unverified`, so the task
reaches the ordinary retry / route back to planning / abort menu in I.2.c. The I.2.c
dead-end prose, the I.2.a launch-guard-denial sentence, and every sentence claiming
the orphan-recovery attempt is the only orchestrator-caused journal write are
replaced (findings `2da3c75adac32650`, `59e58726b1b22211`, `9cc0ce6b64087d2f`).

### R2 — I.2.b step 1 ancestor-check bullet (the new exit; SC-4 site)

The bullet that runs `git merge-base --is-ancestor <task branch>
em-workflow/{feature}/integration` gains the exit. It states, in prose:

1. Preconditions, all required: the ancestor check fails; the task's journal last
   event is `merged`; the task's `Task()` call is not among this reconcile step's own
   currently-outstanding calls.
2. A `merged` event is not proof that the agent terminated; the original run's
   termination is confirmed first under the existing drain and outstanding-call rules
   (cited, not restated).
3. The orchestrator then invokes `em-workflow/scripts/journal-append-failed.py`
   exactly once with the task id and `--reason merge-unverified`, without a launch
   identity (SC-1, D4).
4. Step 1 re-replays the journal within this same reconcile step, so the task's
   journal last event, not only its reconciled state, reads `failed`; the third
   route-back conjunct no longer applies to it; retry (the launch guard admits a
   launch after `failed`) and route back to planning (subject to I.2.c's gate) are
   both reachable.
5. Helper-failure residue: when the helper exits non-zero or reports any outcome other
   than `appended`, the journal is unchanged and the existing text for a task that is
   journal `merged` with reconciled state `failed` governs it — the third conjunct
   blocks route-back, the gate-rejected cause enumeration names the task, and the
   report names the task.
6. Retry follows the existing I.2.c drain and the I.2.a resume guard (kept worktree);
   when the integration branch already contains the task branch, `merge-task.sh`
   records `merged` again (its lines 116-118), so a later reconcile verifies the merge.
7. The bullet's closing sentence that currently says I.2.c narrows this case "because
   the task's raw journal last event is still `merged` here even though the reconciled
   state is `failed`" is kept only as the helper-failure case; it no longer reads as
   the unconditional outcome.
8. No SC6 reason code is named in R2.

### R1 — I.2.a

The sentences from "This holds only when the task's journal last event is actually
`failed`" through "I.2.c owns that narrower outcome, not restated here." are replaced
by: for the ancestor-check-failed case, I.2.b step 1's ancestor-check branch (cited)
records a journal `failed` event, so the launch guard admits the retry; only when that
invocation records nothing does the journal last event stay `merged`, and in that
remaining case the launch guard denies the retry.

### R3 — Orphan recovery paragraph, the "only case" sentence

"This is the ONLY case in which the orchestrator's own action results in an append to
`journal.jsonl` — ..." is replaced by a sentence stating that this invocation is one
of the invocation sites of the single helper exception (SC-3) that the Supporting cast
Journal bullet states, the other orchestrator-caused site being step 1's
ancestor-check branch — cited, not restated.

### R4 — I.2.c ancestor-failure paragraph

The paragraph starting "The state it protects still has a way out" up to, but not
including, "A task the journal reports in-flight whose worktree and branch are both
gone is decided elsewhere" is replaced. The new text states that when the ancestor
verification fails for a task the journal claims `merged`, the task reaches the
ordinary retry / route back to planning / abort menu like any other failure, carrying
the journal `failed` event that Step I.2.b step 1 records for it (cited, not
restated). Constraints: no substring `append` or `rework` (NFR2); no out-of-protocol
or human-only way out; no claim that workflow-schema.md's status semantics are unmet
anywhere; the helper-failure residue is not restated here (the existing third-conjunct
text and gate-rejected enumeration already cover a journal last event still reading
`merged`). The sentence "A task the journal reports in-flight whose worktree and
branch are both gone is decided elsewhere — Step I.2.b step 1's recovery, cited
there, not here." and everything after it stay byte-identical.

### R5 — Supporting cast Journal bullet

The exception clause ("with one narrowly-scoped exception: I.2.b step 1's
orphan-recovery attempt, ...") is extended so the one exception is the
`journal-append-failed.py` helper, invoked by the orphan-recovery attempt and by I.2.b
step 1's ancestor-check branch with `merge-unverified` (SC-3). The phrases "with one
narrowly-scoped exception" and "`em-workflow/references/implement-phase.md`'s own
I.2.b Recovery / Residual block" stay.

### R6 — Stale-`launched` caveat's exception sentence

The "A fourth mechanism ..." sentence no longer makes the orphan-recovery attempt the
sole exception by itself: the attempt falls within the single helper exception, which
also covers the ancestor-check branch's `merge-unverified` invocation (SC-3). If the
literal "the sole exception to the Journal bullet's rule that the orchestrator never
writes the journal directly" is kept, its subject must be the helper exception, not
the orphan-recovery attempt alone.

### README

`em-workflow/README.md`'s journal description (line 104) states that only the
orphaned `launched` residue is an exception where the orchestrator appends `failed`
via the helper. Align it with SC-3 so it also covers the `merge-unverified` exit, by
citing `references/implement-phase.md`, restating no SC6 code.
