# Task Plan: task0002 — Two-layer pin joining the hook classification to the hooks

## Goal

A new test module proves, without reading any prose, that the documented hook classification holds of the implementations: three named hooks perform no per-task workflow.yaml status read (static source scan), and `queue_stop_guard.py` really does apply the recycled-task-id carve-out (behavioral subprocess observation).

## Requirements

FR4, FR5, FR8, NFR1, NFR2, NFR4, NFR5

## Scope

### Files to Create

- `tests/test_queue_hook_status_read_pin.py` — the two-layer pin: Layer 1 static source scan over the three journal-only hooks, Layer 2 behavioral observation of the Stop hook's carve-out, plus the non-vacuity classes for both layers (see Design).

### Files to Modify

None.

## Design

This module renders the Hook classification contract of IMPLEMENTATION.md Shared Components against the implementations. It reads nothing from `implement-phase.md`, so it is green in this worktree both before and after the prose rewrite that another task owns.

### Layer 1 — static source scan (negative claim)

| Aspect | Contract |
|---|---|
| Inputs | the source text of `em-workflow/hooks/queue_launch_guard.py`, `queue_failure_net.py`, `queue_taskstop_net.py`, read by repository-relative path |
| Matcher key | the identifiers that CONSTITUTE a per-task status read in this codebase: the `task_statuses_from_workflow` helper name, and the `TASK_STATUS_RE` / `TASKS_SECTION_RE` line-scan regex names that `queue_stop_guard.py` uses |
| Forbidden key | the bare substring `workflow.yaml` — it must never, on its own, produce a violation (`queue_taskstop_net.py`'s module docstring contains it while reading nothing) |
| Postcondition | the violation list over the three sources is empty; the reported failure message names the offending file and identifier when it is not |
| Shape | one reusable scan function taking source text and returning the violations found, so the same function is applied to the real sources and to both proof samples |

Two paired proofs, both required (IMPLEMENTATION.md Conventions, contract 4 included):
- a sample containing a per-task status read IS reported as a violation (the scan cannot pass over any input);
- a sample containing only the bare substring `workflow.yaml`, in a docstring position, is NOT reported, and that sample carries a positively-asserted retained anchor so it cannot be emptied into a tautology.

The accepted boundary is recorded in IMPLEMENTATION.md D6: a status read via an entirely novel mechanism is not caught by a source-text pin. State that boundary in the module docstring rather than trying to close it.

### Layer 2 — behavioral observation of the carve-out

Invoke `queue_stop_guard.py` as a subprocess with Stop-hook JSON on standard input and assert on exit code and standard error, per `test/README.md`'s hook-contract pattern. Both cases share ONE fixture builder and differ only in the task's own workflow.yaml status value, so a mis-shaped fixture makes the blocking case fail loudly instead of letting the non-blocking case pass vacuously.

Fixture contract (built entirely under a temporary directory, per invocation):

| Element | Requirement |
|---|---|
| enumeration root | a `.claude/worktrees/em-workflow` directory inside the temporary directory, since the hook walks up from its working directory to find one; the subprocess runs with that temporary directory as its working directory |
| feature layout | `<worktrees root>/<feature>/integration/feature-docs/<feature>/workflow.yaml`, with the SAME feature name in both wildcard positions (the hook drops a candidate whose two segments disagree) |
| workflow.yaml content | the `implement` step's own status reads `in_progress`; one declared task under the top-level `tasks:` mapping, carrying its own indented `status:` line |
| journal | `journal.jsonl` at `<worktrees root>/<feature>/` (sibling of `integration`), whose last event for that task is `failed` |
| sidecar | the stop-guard state file lives in that same directory; a fresh fixture per case means the consecutive-block counter starts clean |
| isolation | nothing outside the temporary directory is read or written — never real `~/.claude` state, never the repository's own `.claude/worktrees` tree |

| Case | Task's workflow.yaml status | Expected observation |
|---|---|---|
| carve-out applies | exactly `pending` | exit code 2, and the BLOCK line on standard error names that task id |
| carve-out does not apply | any non-`pending` value | exit code 0, and no BLOCK line |

The hook is observed, never modified: its fail-open convention, lazy status read, consecutive-block cap and sidecar handling all stay as they are.

### Module discipline

Standard library only. No import of any other test module — the fixture shape and any literal borrowed from `tests/test_queue_stop_guard.py` is reproduced locally with a provenance comment (IMPLEMENTATION.md Conventions). The module carries its own class named `TestPreChangeSampleGuards` holding the retained-anchor guards for its samples. The module docstring states why Layer 2 exists alongside the pre-existing stop-guard contract tests (IMPLEMENTATION.md D3): it is the pin joining the DOCUMENTED classification to observable behavior.

## Test Notes

- Layer 1 is unit-level (pure text in, violations out); Layer 2 is integration-level (subprocess + filesystem fixture).
- TDD order: write the scan function's two proof cases first (violating sample flagged, bare-substring sample clean), then apply it to the real sources. For Layer 2, build the blocking case first — it is the one that fails loudly when the fixture is mis-shaped — then derive the non-blocking case by changing only the status value.
- Give the subprocess invocation an explicit timeout so a hang surfaces as a failure rather than a stalled run.
- Vacuity trap to avoid: an exit-0 assertion passes for many wrong reasons (no enumeration root found, `implement` not `in_progress`, no tasks declared, unreadable journal). Deriving the exit-0 case from the SAME fixture as the exit-2 case is what makes it a genuine statement about the carve-out.
- Freshness: the hook ignores candidates whose journal (or, failing that, workflow.yaml) modification time is more than a day old. Files created during the test are fresh, so no explicit timestamp handling is needed — but do not reuse a fixture across cases in a way that could make that assumption interesting.
