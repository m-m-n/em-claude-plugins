# Task Plan: task0003 — Plugin version bump to 0.1.45 in lockstep

## Goal

Both version-carrying files read the same bumped em-workflow version (`0.1.45`), with a durable automated pin that keeps them from ever diverging.

## Requirements

FR7, FR8, NFR1, NFR2

## Scope

### Files to Create

- `tests/test_recycled_task_id_carveout_version_bump.py` — durable lockstep pin over the two version-carrying files, with its negative proofs.

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — bump the plugin manifest's version field from 0.1.44 to 0.1.45; no other field changes.
- `.claude-plugin/marketplace.json` — bump the em-workflow entry's version field from 0.1.44 to 0.1.45; no other entry and no other field changes.

## Design

The bump is required because this feature changes files under `em-workflow/`; a patch-level step matches the repository's stated versioning rule. Exactly one task owns both files (IMPLEMENTATION.md D5), so the two values cannot diverge through a partial merge.

The automated assertion is DURABLE rather than literal, following the repository's established precedent for version-bump modules:

| Assertion | Contract |
|---|---|
| both files parse as JSON | a syntax error is reported as an assertion failure naming the file, not as an uncaught parse error |
| the two versions are equal | the plugin manifest's `version` equals the `version` of the marketplace entry whose name is `em-workflow` |
| the version is past the baseline | of the form `X.Y.Z` with `(X, Y)` equal to `(0, 1)` and `Z` strictly greater than the pre-change baseline `44` |
| neighbours unchanged | the plugin manifest's `name` still reads `em-workflow`, and the `em-review` marketplace entry still points at its own source and carries no version key |

The literal `0.1.45` is deliberately NOT pinned by a test: a fixed literal goes red on the next unrelated bump. The literal is confirmed at verify time by direct file read (VERIFICATION.md).

Two negative proofs, each exercising the same matcher used by the positive tests: a forged pair at the pre-change baseline value fails the past-baseline check, and a forged pair whose two values disagree fails the equality check.

Every pre-existing version-bump module in `tests/` already asserts `patch > <its own older baseline>`, so raising the value keeps them green; no pre-existing module pins the literal `0.1.44`.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR7): `em-workflow/.claude-plugin/plugin.json` parses as JSON and its `version` reads `0.1.45`; its `name` still reads `em-workflow` and no other field changes.
- [ ] AC-2 (FR7): `.claude-plugin/marketplace.json` parses as JSON, the entry named `em-workflow` reads version `0.1.45`, and the `em-review` entry is unchanged (same source, still no version key).
- [ ] AC-3 (FR7, NFR2): The new module is discovered by `python3 -m unittest discover -s tests` with no registration step and asserts, over both parsed files, that the two versions are equal, of the form `0.1.Z`, and that `Z` is strictly greater than `44` — without pinning the literal `0.1.45`.
- [ ] AC-4 (FR7): The module carries a negative proof for each of its two matchers: a forged pair at the baseline value is rejected by the past-baseline check, and a forged disagreeing pair is rejected by the equality check.
- [ ] AC-5 (FR8, NFR1): `python3 -m unittest discover -s tests` exits 0 from the repository root in this task's worktree, only standard-library modules are imported, and no file outside this task's three-file scope is modified.

## Test Notes

- Unit-level only: parse two JSON files and compare. No fixture, no subprocess.
- TDD order: write the module first and observe the past-baseline assertion fail against the un-bumped `0.1.44` pair, then apply the bump.
- Vacuity trap: an equality-only assertion passes when BOTH files are still at the old value. The past-baseline check is what makes the pair's equality meaningful — keep both.
- Numeric comparison, not string comparison, for the patch component, so a two-digit patch is ordered correctly.

## Out of Scope

- Any change to `em-workflow/references/implement-phase.md`, any hook, or any pre-existing test module.
- Adding or changing marketplace entries other than the `em-workflow` version value.
- Regenerating or editing any LICENSE file (the project declares no license).
- Pinning the literal `0.1.45` in a test.
