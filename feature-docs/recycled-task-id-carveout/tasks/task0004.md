## Design

### What is missing today

`TestRecycledTaskIdRuleScopedToOrchestrator` already contains the POSITIVE half of the three-hook claim: an anchored-slice matcher asserting that the three journal-only hook filenames are named inside one slice that also states they never consult `tasks.{T}.status` (the test named `test_three_journal_only_hooks_named_in_anchored_never_consult_slice`). Two things are absent:

1. Its paired NEGATIVE proof. `TestValidationDetectsRegressions` contains no test showing that the same matcher fails on wording in which `queue_stop_guard.py` is folded into that same three-hook "never consult `tasks.{T}.status`" claim. Without it, nothing prevents the matcher from being weakened back into the filename-presence check this feature exists to retire.
2. A correct classification of that matcher in the module docstring. It is currently declared a "RETENTION matcher over unchanged wording (no negative proof needed, Contract 3)". That classification is wrong: the whole point of the claim is that the three journal-only hooks and the carve-out hook form two SEPARATE groups, so it is a new-wording matcher governed by Contracts 1, 2 and 4, and SPEC AC-9 (FR5) requires every new matcher to carry a paired negative proof.

### The violating sample (Contract 2)

The sample the negative proof runs against must be a captured verbatim excerpt, never a paraphrase. Prefer reuse: the module already carries the pre-stopguard-retired-failed wording sample in which `queue_stop_guard.py` appears inside the four-hook "never consults" list — that wording IS a sample folding `queue_stop_guard.py` into the same claim, which is exactly what VERIFICATION.md TS-2's negative half requires. Reuse it if the anchored-slice matcher can be formed against it.

If that sample does not carry enough of the slice context for the matcher to be applied to it, capture a new verbatim excerpt of `em-workflow/references/implement-phase.md` at this feature's base commit, with a provenance comment naming the source file and that commit, and guard it under Contract 4. Which of the two branches applies is determined by reading the module — it is a mechanical determination, not a design choice.

Either way the proof must apply the SAME matcher literal the positive test uses, read from ONE module-level constant (Contract 1). A negative proof that re-states the literal inline is not acceptable.

### Resolving the single-reader constants

Measured state after this feature retired `test_scope_sentence_names_all_four_hooks` and its siblings:

| Constant | Readers today |
|---|---|
| `HOOK_FILENAMES` | 1 — only the `JOURNAL_ONLY_HOOK_FILENAMES` derivation |
| `JOURNAL_ONLY_HOOK_FILENAMES` | 1 — only the anchored-slice positive test |

SPEC AC-6 (FR3) forbids exactly this state. The outcome contract: after the change, every module-level constant in this module has at least two reader sites, or is retired together with ALL of its readers. A reader counts only if it is an assertion or a derivation whose behavior changes when the constant's value changes — a reference added solely to raise the count does not satisfy this.

The natural resolution follows from the negative proof itself: the new negative-proof test is a genuine second reader of the journal-only filename constant and of the matcher-literal constant, and a constant whose only remaining reader is a derivation feeding one other constant is retired together with that derivation. The implementer chooses per constant; the contract above is what must hold.

### Ownership of task0001's test record (deliberate decision)

`test-docs/recycled-task-id-carveout/task0001.tests.yaml` records, against AC-6, a `red_reason` claiming "every module-level constant this task added or revised has >=2 readers, or was fully retired together with all of its readers". That does not match the measured state and is the record half of the same failed item.

A task's own `{T}.tests.yaml` is normally written by that task's implementer inside its own worktree, so a rework task cannot correct another task's record without declaring the path. This task DECLARES `test-docs/recycled-task-id-carveout/task0001.tests.yaml` in `files` and takes ownership of that one correction. This is safe here because task0001 is `merged` and no other task is writing that file; the alternative — leaving a merged record asserting something untrue about the module this task is fixing — would leave the feature's own evidence trail contradicting its code. The correction is confined to the AC-6 entry; every other entry stays byte-unchanged. See IMPLEMENTATION.md D7.

### What must NOT move

The prose of `em-workflow/references/implement-phase.md` passed verification (TS-1, TS-3, TS-4, TS-8 are green against it) and is not touched. IMPLEMENTATION.md D4's protected-literal inventory therefore still applies as a floor for this module's untouched assertions: the raw-literal guards, the byte-identity guard and the ordering guards keep comparing raw text and keep passing unchanged. The authority is the whole suite.

## Test Notes

- Unit-level only. No subprocess, no filesystem fixture, no new module — every assertion lands in the existing module beside the assertions it pairs with.
- TDD order: write the negative-proof test first and run it. If it passes immediately, that is expected — the positive matcher is already anchored — and the non-vacuity is carried by AC-3's retained-anchor guard, which is what Contract 4 exists for. Do NOT manufacture a red step by weakening the matcher.
- Constant resolution is the step most likely to break something quietly. After retiring or re-shaping a constant, run the whole suite, not just this module: the raw-literal, byte-identity and ordering guards inside this module and `test_routeback_reset_scope_consistency.py` / `test_implement_routeback_gate.py` read the same document and are the likeliest to trip.
- AC-4 and AC-5 are inspection-verified rather than test-asserted (a module asserting over its own docstring or counting its own constants' readers would be self-referential). State them plainly enough in the docstring and the constant layout that a reader can check them by reading the file top to bottom.
- The tests.yaml correction is a text edit to one entry. Re-read the file after editing to confirm no neighbouring entry's indentation or quoting changed.
