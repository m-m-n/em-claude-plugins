# Implementation Plan: destructive-guard-quoted-substitution-fail-open

## Overview

destructive-guard の「引用符付きコマンド置換 + 親参照 + safe ルート着地」形が
fail-closed であることを期待値スイートに固定する。判定ロジックは変更せず、期待値表
への追加と、それに伴うプラグイン version の patch 更新だけで閉じる。

## Technology Stack

- **Language**: Python 3 — 判定フックとスイートランナーの実行環境（いずれも本変更では
  変更しない）
- **Data format**: JSON — 期待値表（`[期待する判定, ラベル, コマンド]` の 3 要素配列の
  配列）とプラグインマニフェスト 2 種
- **New dependencies**: なし（NFR4: 標準ライブラリのみ）。新規依存を導入しないため、
  ライセンス照合の対象となる依存は 0 件。`workflow.yaml` の `project.license` は
  `none` であり、ライセンス制約は発生しない。

## Layer Structure

| 層 | 実体 | 本変更での扱い |
|----|------|----------------|
| 判定層 | `em-workflow/hooks/destructive-guard.py` | **凍結**（FR4）。どのタスクも変更しない |
| 実行層 | `em-workflow/hooks/tests/run-destructive-guard.py` | **凍結**（NFR2）。構造を変えない |
| 期待値層 | `em-workflow/hooks/tests/destructive-guard-cases.json` | task0001 が**追加のみ**行う |
| 配布メタ層 | `em-workflow/.claude-plugin/plugin.json` / `.claude-plugin/marketplace.json` | task0002 のみが触る |

依存方向は 期待値層 → 実行層 → 判定層 の一方向（読み取りのみ）。期待値層の変更が
下位 2 層に影響しないことが、本変更が「挙動を変えない」ことの構造的根拠になる。逆方向
の変更（判定層・実行層の修正）は本フィーチャーのスコープ外。

## Shared Components

| Component | Responsibility | Contract (pre/postcondition) | Used by tasks |
|-----------|----------------|------------------------------|---------------|
| 期待値表エントリ | 1 ケース = 期待する判定 / ラベル / コマンド文字列の 3 要素配列 | pre: 判定値はランナーが返しうる語彙（`allow` / `deny` / `ask` / `(silent)`）のいずれかであり、同じコマンド文字列を現行フックへ通した実測値と一致する。post: ファイル全体が JSON としてパースでき、ランナーの 3 要素アンパックが全エントリで成功する | task0001 |

## Conventions

- **エントリ様式**: 既存と同じ 3 要素配列。ラベルは「カテゴリ(判定カテゴリ): 説明」の
  日本語 1 行で、既存の「評価境界(rm-recursive): …」「スクラッチ外(rm-recursive): …」に
  揃える（FR5）。
- **ラベルの内容要件**: 「引用符で囲んでも裸形と同じ判定になること」を検証している旨が
  ラベルだけで読み取れること。対照となる裸形の性質（親参照付きパスが置換の直後に続く／
  置換が対象の末尾に隣接する 等）に触れる。
- **追加位置**: 対照関係が読んで分かるよう、既存の裸形の双子エントリ群の直後に隣接して
  まとめて置く。既存行の並べ替えは行わない。
- **期待値の決め方**: 推測で書かない。コマンド文字列を現行フックへ通して観測した判定を
  そのまま書く（FR2）。
- **エラー時の扱い**: 追加したケースがスイートで FAIL になった場合、期待値をスイートに
  合わせて書き換えるのではなく、実測の再取得からやり直す（期待値 = 実測 の不変条件を
  壊さないため）。

## Cross-task Design Decisions

### D1: 判定ロジックは変更しない

報告された fail-open は現行実装では再現しない（9 形すべて deny の実測が確定事実として
与えられている）。したがって本フィーチャーは挙動修正ではなく回帰テスト整備であり、
判定層・実行層は凍結する。影響タスク: task0001, task0002。

### D2: version bump の所有権を task0002 に一本化する

version は 2 ファイルで同一値でなければ意味を持たない（片方だけ上がるとキャッシュ判定
が壊れる）。タスクは並列実行され順序を持たないため、「同一性」は 1 タスクの内側に閉じ
たときだけ構造的に保証される。よって 2 ファイルの更新をまとめて task0002 が所有し、
task0001 は version ファイルに一切触れない。task0001 の変更が bump の必要性を生むが、
両者の間に実行順序の依存は無く、共有するのは「新しい version 値は 0.1.79 の patch 後継
である」という契約のみ。影響タスク: task0001, task0002。

### D3: 実測が `allow` になった形はエスカレーションする

いずれかの形で実測が `allow` になった場合、それは報告された fail-open が現行実装でも
再現したことを意味する。その値を期待値として記録してはならない（fail-open を正常と
して固定することになる）。該当タスクは記録を行わず、観測した形と実測値を計画逸脱と
して報告し、判定層の修正が要るかどうかの判断を上位に返す。`deny` 以外でも `ask` は
fail-closed 側（無人実行では deny に降格される）なので、そのまま理由付きで記録してよい。
影響タスク: task0001（判定が変わればスコープが task0002 にも波及するため横断決定として
置く）。

### D4: 追加ケースは外部状態に依存しない

フックは静的解析でありコマンドを実行しないが、ケースのコマンド文字列は実在パス・
カレントディレクトリ・ネットワークのいずれにも判定が依存しない形に限る（NFR1）。
着地先として使うルート名は、既存ケースが用いている語彙（scratch / dist /
node_modules / .cache 等の safe ルート名）から選ぶ。影響タスク: task0001。

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| 実測せず推測で期待値を書く | 中 | 高（fail-open を deny と誤記録、または逆） | FR2 をタスクの受け入れ条件に落とし込み、「観測 → 記録 → スイート実行」の順序を Test Notes で固定する |
| 既存エントリの誤改変・並べ替え | 低 | 高（スイートの検知力低下） | 追加のみの規約 + 変更前後の件数と既存部分の一致を受け入れ条件にする |
| version が 2 ファイルで食い違う | 低 | 中（インストール済みキャッシュが更新されない） | D2 で 1 タスク所有。受け入れ条件で同一性を明示検査 |
| 実測が `allow` の形が出る | 低 | 高（スコープが挙動修正へ波及） | D3 のエスカレーション経路 |
| JSON の構文破壊（カンマ・エスケープ） | 低 | 高（スイートが 1 件も動かない） | JSON としてパースできることとスイート全件 ok を受け入れ条件にする |
