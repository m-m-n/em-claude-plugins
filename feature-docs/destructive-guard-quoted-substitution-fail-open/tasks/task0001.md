## Design

### 追加する 8 形

対照となる裸形（引用符で囲んでいない双子）は、変更前のこのファイルの 165-168 行に
既に存在する。それぞれ「コマンド置換の直後に親参照付きパスが続く形」「置換が対象の
右側（末尾）に隣接する形」で、いずれも `deny` が期待値として固定されている。本タスク
は、その裸形を引用符で包んだ／着地先を変えた双子を追加する。

| # | 形 | 対照の裸形 |
|---|----|-----------|
| 1 | 二重引用符で対象全体を囲み、`$()` スペルの置換の直後に親参照 1 個と safe ルート名（scratch 系）が続く | 165 行 |
| 2 | 1 と同じ並びを単一引用符で囲んだ形 | 165 行 |
| 3 | バッククォートスペルの置換を二重引用符で囲み、直後に親参照付きパスが続く（両スペル対称性のバッククォート側） | 167 行 |
| 4 | 1 の着地先を `dist` に変えた形 | 165 行 |
| 5 | 1 の着地先を `node_modules` に変えた形 | 165 行 |
| 6 | 1 の着地先を `.cache` に変えた形 | 165 行 |
| 7 | 二重引用符の内側で、置換の**前**に実テキストが空白なしで密着する形（親参照 + safe ルート着地は維持） | 165 行 / 186 行 |
| 8 | 二重引用符の内側で、置換の**後ろ**に実テキストが空白なしで密着する形（同上） | 168 行 |

着地先に使うルート名は、既存ケースが safe ルートとして扱っている語彙から選ぶ
（IMPLEMENTATION.md D4）。実在パス・カレントディレクトリ・ネットワークに判定が依存
する文字列は使わない。

### 期待判定の決め方（FR2）

1. 候補のコマンド文字列 1 本につき、ランナーが 1 ケースに対して行うのと同じ呼び出し
   （Bash ツール入力形の JSON を標準入力でフックへ渡し、標準出力の判定を読む）を行い、
   判定を**観測**する。
2. 観測した判定をそのまま期待値として記録する。`deny` 以外でも `ask` は fail-closed 側
   （無人実行では deny に降格される）なので、理由をラベルに書いたうえでそのまま記録
   してよい。
3. 観測が `allow` になった形は記録しない。IMPLEMENTATION.md D3 のエスカレーションに
   従い、その形と観測値を計画逸脱として報告する。

### エントリ様式（FR5）

3 要素配列 `[期待する判定, ラベル, コマンド]`。ラベルは既存に揃えた日本語 1 行で、
「カテゴリ(判定カテゴリ): 説明」の形。説明には、引用符で囲んでも裸形と同じ判定になる
ことを検証している旨と、対照の裸形が持つ性質（置換の直後に親参照付きパスが続く／置換が
末尾に隣接する 等）を含める。追加位置は既存の裸形群の直後に隣接させ、対照関係が読んで
分かる並びにする。

### 触れないもの

判定層（`destructive-guard.py`）と実行層（`run-destructive-guard.py`）は凍結
（IMPLEMENTATION.md Layer Structure）。プラグイン version の更新は task0002 が所有する
（同 D2）ので、本タスクは version を含むファイルに触れない。

## Test Notes

- このタスクではケースエントリ自体がテストである。TDD の赤→緑は「観測 → 記録 →
  スイート実行」の順序で閉じる。順序を逆にして期待値を先に書くと FR2 を破るため、
  観測を先に行う。
- 追加直後にスイートを 1 回通し、追加分が ok、既存分も ok であることを 1 回の実行で
  確認する（既存分の巻き込み退行の検出）。
- スイートで FAIL が出たときは、期待値をスイートの出力に合わせて書き換えず、観測を
  取り直して原因（コマンド文字列の写し間違い・JSON エスケープの崩れ）を特定する。
- JSON のエスケープ（二重引用符・バックスラッシュ）が絡むため、編集後に必ずファイル全体が
  JSON としてパースできることを確認する。単一引用符形とバッククォート形は JSON 側の
  エスケープ規則と紛らわしいので、観測に使った文字列とファイルに書いた文字列が同一で
  あることを突き合わせる。
- 実行時間はケース数に比例してサブプロセス 1 本ずつ増える。ランナーの構造は変えない
  （NFR2）。
