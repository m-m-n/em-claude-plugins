## Design

### Root cause

The guard holds a module-level snapshot of the `em-review` entry captured
before that entry carried a `version` key, and asserts the live entry is
equal to it as a whole dictionary. The live entry now carries
`version: 0.5.7`, so the equality fails. Two properties make this a defect
rather than a detection:

1. **The mismatch is not a violation of what the guard protects.** The guard
   exists because the originating task (a different, already-merged feature)
   declared the em-review entry out of scope for its own edit. The em-review
   entry's `version` moving is not that task editing it — it is the
   repository rule in `.claude/rules/core-plugin-version-bump.md` requiring
   each plugin's version to advance whenever that plugin changes.
2. **The failure is permanent and grows.** Every future em-review bump
   re-breaks the same assertion, so no one-off snapshot refresh fixes the
   class. This feature's own diff does not touch the em-review entry, and
   the same test fails at the implement step's `base_commit`
   (`b49240996c198da1528b4b8d6265baab75a90931`), which is what makes the
   failure pre-existing rather than a regression this feature introduced.

### The repaired guard

The repository already contains the correct shape for this exact guard, in
`tests/test_rework_contract_drift_version_bump.py`
(`_assert_em_review_entry_matches`): identity fields pinned to literals, the
mutable `version` asserted by shape only, with negative proofs for both
halves. The same shape is adopted here — reproduced in this module rather
than imported from that one, because each test module in `tests/` stays
independently runnable (the convention this module's own docstring already
records for its `tests/test_plugin_version_parity.py` mirroring).

| Entry field | How it is asserted after the repair |
|---|---|
| `name`, `author`, `category`, `source` | equal to the pre-task literal, exactly |
| `description` | equal to the pre-task literal, exactly — an edit to the em-review description is precisely what this guard must still catch |
| `version` | present, a non-empty dotted-numeric string; never compared against a literal value |
| the key set as a whole | equal to exactly those five identity keys plus `version` — an added or removed key is still a detected modification |

The distinction the repair draws is between a field the repository rules
require to change over time (`version`) and every other field, which no rule
moves and whose change therefore remains a finding. Widening the guard past
that one field would trade a false alarm for a blind spot.

The repair is confined to the test module. The live registry is not edited:
deleting the entry's `version` key would satisfy the current assertion while
breaking the plugin-cache freshness rule and the nine sibling modules that
assert that key's presence.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The em-review entry guard in
      `tests/test_llm_led_review_user_docs.py` no longer compares the entry
      against a whole-entry snapshot that omits `version`. It asserts
      `name`, `description`, `author`, `category` and `source` equal to
      their pre-task literal values, and asserts the entry's key set equals
      exactly those five keys plus `version`.
- [ ] AC-2: The same guard asserts `version` by shape only — present, a
      string, and a dotted-numeric form — and no assertion in the module
      compares the em-review entry's `version` against a literal value. A
      positive proof over a synthetic entry carrying a different, higher
      version shows the matcher accepts it, which is what proves the shape
      assertion is not a literal one in disguise.
- [ ] AC-3: The guard's detection power is proven to survive, by negative
      proofs over synthetic entries (never by mutating the real registry
      file): an altered identity field (for example `source`) is rejected, a
      missing or non-dotted-numeric `version` is rejected, and an entry
      carrying an unexpected extra key is rejected.
- [ ] AC-4: The guard still runs against the live
      `.claude-plugin/marketplace.json` and is neither deleted nor disabled:
      a test class asserting the em-review entry's immutability is present
      and carries no `skip` / `expectedFailure` decorator, and the entry is
      located by its `name` field with a non-vacuity guard that fails when
      no em-review entry is found rather than passing on an empty lookup.
- [ ] AC-5: The module's docstring no longer states the em-review entry is
      asserted "byte-identical to before"; it states the repaired invariant
      (identity fields and key set pinned, `version` by shape) and why
      `version` is excepted, so the module does not document a rule it does
      not assert.
- [ ] AC-6: `python3 -m unittest discover -s tests` run from the repository
      root exits 0 with no failures and no errors, and
      `tests/test_llm_led_review_user_docs.py` imports only the standard
      library.

## Test Notes

- This task's deliverable IS a test module, so the TDD contract runs in the
  order the module's own assertions make available: first reproduce the
  reported failure by running the module unchanged and observing the single
  failing test, then add the AC-2 / AC-3 proofs over synthetic entries —
  which fail against the current whole-dict matcher — and only then replace
  the matcher until every one passes.
- AC-3's negative proofs and AC-2's positive proof operate on in-memory
  copies of the entry dictionary. Nothing in this task writes to
  `.claude-plugin/marketplace.json`, and no test may edit it as a fixture.
- AC-4's non-vacuity guard is the one that stops the repaired matcher from
  degenerating into a test that passes because it examined nothing. Assert
  it directly: a lookup against a marketplace document with no em-review
  entry must raise or fail, not return an empty mapping the matcher then
  finds unobjectionable.
- AC-6 is a whole-suite property this module cannot assert about itself
  without recursion; it is verified by running the command and recording the
  result in the implementer report, matching how the module's existing AC-7
  note already handles the same situation.
