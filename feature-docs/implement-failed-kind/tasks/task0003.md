# Task Plan: task0003 — Stop condition 3 branches on `failed_kind`, with a capped batch auto-resume

## Goal

`em-workflow/skills/develop/SKILL.md` Step B stops on an `implement`
`failed` only when `failed_kind` reads the decision-required value; on the
external-cause value in batch mode it instead resets `implement` to
`pending`, clears the field, counts the resume, commits that write set once,
and executes the phase — up to a defined cap.

## Requirements

FR6, FR7, FR8, FR2, NFR1, NFR4

## Scope

### Files to Create
- `tests/test_failed_kind_stop_condition.py`
  Document-invariant tests for the branch, the procedure, the cap and the
  unchanged neighbouring carve-outs.

### Files to Modify
- `em-workflow/skills/develop/SKILL.md`
  The stop-condition list item for condition 3, and a new Step B block
  stating the failed-kind branch and the auto-resume procedure.

## Design

This document is written in Japanese; keep it that way. Two edits.

**Edit 1 — the stop-condition list entry.** Stop condition 3's own list
item currently reads that a step whose status is `failed` or `needs_update`
stops the run, with a parenthetical pointing at Step B's precedence block.
Add a second pointer: for the `implement` step's `failed`, the firing
condition is narrowed by `failed_kind`, detailed in the new Step B block.
Keep the existing `needs_update` carve-out pointer intact — it is a
separate carve-out and this task does not touch it.

**Edit 2 — a new Step B block: the branch and the auto-resume.** Place it
alongside the existing exception blocks (the stop-condition-3 precedence
block and the batch verify-cap exception block), and state that it is
independent of both and changes neither. The block states, as an ordered
procedure evaluated at the moment Step B has identified `implement` as the
step to execute and read its status as `failed` (IMPLEMENTATION.md D4):

1. Read `failed_kind`. Its definition, its permitted values and its
   missing-value read rule are `references/workflow-schema.md`'s; cite that
   document and do not restate them.
2. Decision-required value → stop condition 3 fires exactly as before.
   Nothing below runs.
3. External-cause value in an interactive run → stop condition 3 fires
   (FR8: the auto-resume is batch-only). State this as an explicit
   non-change of the interactive behaviour.
4. External-cause value in a batch run → read the auto-resume record's two
   members from the `batch` block. Their key path, their meanings and the
   unset-read rule are `references/workflow-schema.md`'s; cite it. The
   `batch` block's own creation rule is `references/batch-mode.md`'s; cite
   it. Do not restate either.
5. When the performed count has reached the cap → the failure is treated as
   the decision-required case: stop condition 3 fires, and the report names
   the cap as the reason so the reader can tell this stop from an ordinary
   one. No workflow.yaml write is made on this branch.
6. Otherwise → one ordered workflow.yaml write set: `implement` `status`
   back to `pending`; `failed_kind` back to null (FR2 — the same write set
   that leaves `failed` clears the field); the performed count incremented
   by one. Commit that write set once with `commit-docs.sh` **before**
   executing the phase (NFR2: one write set, one commit, then the phase).
   Then execute the implement phase through Step B's normal sequence.

The block also states three non-changes, each in one sentence:

- The count is monotonic per feature and is never reset (it mirrors the
  existing rework counters recorded in the same block of workflow.yaml).
- The auto-resume is not a stop: it emits no batch terminal line, and it
  adds no new stop reason code (`references/batch-terminal-line.md` — cited,
  not restated).
- The auto-resume is not an `--once` phase boundary of its own; the
  boundary stays wherever the implement phase itself puts it.

Stop condition 3's other trigger (`needs_update`) and its behaviour for the
`review` and `verify` steps are unaffected — state this explicitly (SPEC
assumption A3), so the narrowing cannot be read as applying to every step.

## Test Notes

Document-invariant assertions in `tests/test_failed_kind_stop_condition.py`.
This document's Japanese prose hard-wraps without a space at the break
point, so markers must be matched after stripping whitespace entirely (the
`_strip_ws` convention in `tests/test_failed_items_category.py` and
`tests/test_develop_skill_rewiring.py`), never after collapsing to a single
space.

- Extract Step B by its own heading boundaries, and locate the new block by
  its bold-label anchor, so an assertion cannot accidentally match text in
  the verify or retrospect sections.
- AC-2 and AC-3 are the highest-value assertions: assert the ordering
  ("write set, then commit, then execute the phase") and the at-cap
  no-write statement independently, since a document that states the cap
  but not the ordering would still permit an unbounded resume loop.
- AC-8 is a presence check against the two existing blocks. Include the
  former block's exhaustiveness sentence and the latter's
  non-applicability bullet as separate assertions — those are the two
  statements an edit in this area is most likely to disturb.
- AC-10's detector must tolerate the branch-condition mentions AC-1 and
  AC-5 require. Base it on the definition-shaped artefacts, as in
  IMPLEMENTATION.md D7.
