# Task Plan: task0002 — The three terminal write paths carry `failed_kind`

## Goal

Every path in `em-workflow/references/implement-phase.md` that sets the
`implement` step's `status` to `failed` also carries `failed_kind` in that
same single write, with the classification pinned per path, and the
route-back write set clears the field when it moves the step off `failed`.

## Requirements

FR3, FR4, FR5, FR2, NFR1, NFR2, NFR4

## Scope

### Files to Create
- `tests/test_failed_kind_write_paths.py`
  Document-invariant tests for the three write paths and the route-back
  clear.

### Files to Modify
- `em-workflow/references/implement-phase.md`
  Step I.2.c: the abort-phase branch, the batch second-failure paragraph,
  the route-back gate-rejected terminal, and the route-back write set.

## Design

Four edits inside Step I.2.c, all of them additions to write descriptions
that already exist. The governing invariant is NFR2: each of the three
terminal paths currently states that "the terminal status write and its own
commit are the ONLY side effect". That sentence stays true — `failed_kind`
joins the same write; it never becomes a second write or a second commit.

**Edit 1 — abort phase, interactive entrance (FR3).** The abort-phase
option's write description gains the field. The value is the external-cause
value when the failing task's failure originates from a journal `failed`
event whose reason is `orphaned` (the event I.2.b step 1's orphan-recovery
exception records, already described earlier in this same document); the
decision-required value otherwise. State the determination as a property of
the already-reconciled failure the phase is holding, not as a new lookup
step — the orphaned-`launched` convergence paragraph at the head of I.2.c
already establishes that this information is present. The abort path's
"ONLY side effect" sentence stays unchanged.

**Edit 2 — abort phase, batch second-failure entrance (FR4).** The batch
paragraph at the end of I.2.c (the `implement.failed-task` behaviour) states
that its abort writes the decision-required value unconditionally, and
states explicitly that this holds even when the failure originated from an
orphaned journal event — i.e. this entrance overrides Edit 1's rule for
itself (IMPLEMENTATION.md D2, Precedence). Also state, as the reason this
is consistent rather than as a new rule, that the run's stop is unaffected
because `references/batch-terminal-line.md` already gives
`implement-second-failure` precedence over `stop-condition-3`; cite that
document rather than restating its precedence rule.

**Edit 3 — route-back gate rejected terminal (FR5).** The gate-rejected
path's single write gains the field, valued as the decision-required value
unconditionally. State the reason in one clause: the blocker is a
planning-side state (a `merged` or in-flight task), so an automatic resume
would meet the same gate again. The path's "no route-back write set, no
cleanup, no route-back commit — the terminal status write and its own commit
are the ONLY side effect" sentence stays unchanged.

**Edit 4 — route-back write set clears the field (FR2).** The
route-back-to-planning ordered write set already sets `create-plan` to
`needs_update`, sets `implement` back to `pending`, and resets the failed
tasks. It gains one more member: `failed_kind` returns to null in that same
write set, because the step is leaving `failed`. This adds nothing to the
commit sequence — the write set is already committed once, before cleanup.

**Citation discipline (NFR1, IMPLEMENTATION.md D7).** At the first point in
this document where `failed_kind` is used, cite
`references/workflow-schema.md` as the field's definition. Name individual
values only inside the "this path writes X" statements above; do not
enumerate both values as the permitted set, do not gloss their meanings,
and do not restate the missing-value read rule.

## Test Notes

Document-invariant assertions in `tests/test_failed_kind_write_paths.py`.
Extract Step I.2.c between its own heading and the next heading, then locate
each write path by an exact-wording anchor drawn from its existing commit
message string (the abort commit message, the gate-rejected commit message,
and the route-back commit message) — those strings are stable and unique, so
an assertion anchored on them will not drift onto a neighbouring paragraph.

- AC-5's negative proof is the important one: the whole NFR2 risk is that
  an implementer describes the field as an additional write. Assert the
  "ONLY side effect" sentences positively, and prove the matcher can fail.
- AC-6's detector needs to tolerate the legitimate value mentions AC-1 to
  AC-3 require. Base it on the definition-shaped artefacts — a
  both-values-together permitted-set enumeration, the meanings gloss, the
  missing-value rule — rather than on bare occurrences of either value.
- AC-7 is a presence check of the existing statements, since this task must
  not restructure the gate. Pick anchors from the gate's own wording (the
  two halves of the admissibility gate and the third conjunct).
