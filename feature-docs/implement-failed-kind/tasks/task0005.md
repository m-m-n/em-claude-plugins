# Task Plan: task0005 — Plugin version bump

## Goal

The em-workflow plugin version is raised past its pre-feature baseline in
both registries that must agree, so an installed copy picks up this
feature's protocol changes instead of serving a stale cache.

## Requirements

NFR3, NFR4

## Scope

### Files to Create
- `tests/test_failed_kind_version_bump.py`
  Tests for version parity, the past-baseline comparison, and the
  untouched sibling entry.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json`
  The plugin manifest's version field.
- `.claude-plugin/marketplace.json`
  The version field of the marketplace entry whose name is em-workflow.

## Design

The project rule (`.claude/rules/core-plugin-version-bump.md`) requires both
registries to carry the identical version, and requires the bump to ride in
the same change as the plugin content edit. Because tasks run fully in
parallel, this task is the single owner of both files (IMPLEMENTATION.md
D9) — no other task in this feature touches either.

Baseline at the start of this feature: both registries read `0.1.62`. This
feature is a behaviour change to existing protocol documents, so the bump is
a patch-level move on the `0.1.x` line — the pre-existing convention for
this repository, where nearly every change is patch-level.

The sibling `em-review` entry is independent and stays at `0.5.7`; versions
are per-plugin and moving one never moves the other.

Reporting note for the completion report: applying a plugin version bump
requires restarting Claude Code, because the installed copy is cached under
the version directory.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (NFR3): the plugin manifest's version and the em-workflow
      marketplace entry's version are the identical string.
- [ ] AC-2 (NFR3): that value parses as major.minor.patch, keeps
      major.minor at `0.1`, and has a patch component strictly greater than
      the baseline 62. The comparison is a numeric tuple comparison, never
      a whole-string comparison.
- [ ] AC-3 (NFR3): the `em-review` marketplace entry's version is unchanged
      at its pre-task value.
- [ ] AC-4: the marketplace entry is located by its name field, not by
      array index, and the lookup has a non-vacuity guard so a missing
      entry fails rather than silently passing.
- [ ] AC-5 (NFR4): `python3 -m unittest discover -s tests` passes with the
      new module present, and the new module imports only the standard
      library. Each matcher has a negative proof against synthetic data —
      one sample left at the baseline, one where the two registries
      disagree — plus a well-formedness guard showing the synthetic sample
      is itself parseable, so the proof exercises the comparison rather
      than a parse failure.

## Test Notes

Follow `tests/test_verify_rework_lineage_cap_version_bump.py` exactly in
structure: baseline held as a major/minor tuple plus a patch integer, a
version parser returning a null result rather than raising so a parse
failure is distinguishable from a comparison failure, and the sibling-entry
snapshot held as a module constant.

- The past-baseline matcher must not pin the exact new version string —
  that would go stale on the next unrelated bump. Pin major.minor and
  require the patch to be strictly greater.
- Note for the implementer: `tests/test_plugin_version_parity.py` carries a
  pre-existing failure unrelated to this feature — it pins the em-review
  entry as having no version key, while that entry does have one. It
  predates this task, is out of scope, and must not be "fixed" here; report
  it if the suite run surfaces it.

## Out of Scope

- Every protocol document this feature changes — task0001 through task0004
  own them. This task changes no Markdown.
- The em-review plugin's version, description or any other marketplace
  field.
- The plugin manifest's name or description.
- Fixing the pre-existing unrelated failure in the plugin version parity
  test module.
