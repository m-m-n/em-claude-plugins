# Task Plan: task0004 — Batch-mode and terminal-line documents follow the `failed_kind` branch

## Goal

`em-workflow/references/batch-mode.md` and
`em-workflow/references/batch-terminal-line.md` describe the run's stopping
behaviour accurately after the `failed_kind` branch exists, without adding
a stop reason code and without restating the field's definition.

## Requirements

FR10, NFR1, NFR4

## Scope

### Files to Create
- `tests/test_failed_kind_batch_docs.py`
  Document-invariant tests for the updated rows and for the unchanged
  stop-reason contract.

### Files to Modify
- `em-workflow/references/batch-mode.md`
  The failed-task row of the Non-packet gates table, and the bullet
  asserting that failure stops are unchanged.
- `em-workflow/references/batch-terminal-line.md`
  The needs-intervention reason code's Meaning cell, and the precedence
  paragraph that follows the stop-point coverage table.

## Design

Four edits, all of them narrowing existing descriptive text so it stays
true. No new row, no new code, no new gate.

**Edit 1 — the `implement.failed-task` row (batch-mode.md).** The row's
batch behaviour already says a second failure on the same task aborts the
phase by writing the `implement` step's `status` to `failed` and committing
exactly that write. Add that the same write also carries `failed_kind`,
valued as the decision-required value, and keep the row's existing
"Full detail" pointer to `references/implement-phase.md` Step I.2.c as the
place the rule itself lives. The row is a summary; it must not restate the
classification rule for the other two write paths.

**Edit 2 — the "failure stops are unchanged" bullet (batch-mode.md).** This
bullet currently asserts that batch mode never hides failures and that stuck
steps, YAML errors and post-cap failures still stop the run. It is now too
strong: an `implement` `failed` classified as the external-cause value does
not stop a batch run while the auto-resume is admissible. Narrow the bullet
so it stays true — the assertion becomes that batch mode removes
confirmations on the success path and never hides a failure that needs a
human, with the auto-resume named as a bounded, counted exception whose cap
returns control the same way. Cite `skills/develop/SKILL.md` for the branch
and the cap rather than restating them.

**Edit 3 — the `step_needs_intervention` Meaning cell
(batch-terminal-line.md).** The cell currently reads that a workflow step
reported `failed` or `needs_update`. Narrow it so the `implement` step's
`failed` counts only when `failed_kind` reads the decision-required value
(including the missing-value case, which reads that way by the schema's own
rule — cite, do not restate). The code itself, its `state` column and its
position in the closed set are unchanged.

**Edit 4 — the precedence paragraph after the coverage table
(batch-terminal-line.md).** That paragraph explains that three
phase-specific stop points can also match `stop-condition-3`, and that the
`stop-condition-3` row's meaning is restricted to `failed` / `needs_update`
states no phase-specific row covers. Extend that restriction sentence with
the `failed_kind` narrowing for the `implement` step, so the two
restrictions read as one coherent statement. The three phase-specific stop
points, the precedence rule itself and the coverage table's rows are
unchanged.

**What must not change.** The closed set of eleven stop reason codes stays
at eleven; no code is added, removed or renamed. The `stop-condition-3`
coverage row keeps its reason code and its source document. The infra
auto-resume is not a stop and therefore appears nowhere in the coverage
table (IMPLEMENTATION.md C5/D8).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR10): the `implement.failed-task` row states that the second
      failure's abort write also carries the decision-required
      `failed_kind` value, and keeps its existing pointer to
      `references/implement-phase.md` Step I.2.c as the rule's owner.
- [ ] AC-2 (FR10): the failure-stops bullet no longer asserts
      unconditionally that every failure stops the run; it names the
      bounded, counted auto-resume as the exception and cites
      `skills/develop/SKILL.md` for the branch and the cap.
- [ ] AC-3 (FR10): the `step_needs_intervention` Meaning cell states that
      an `implement` `failed` counts only when `failed_kind` reads the
      decision-required value, and cites `references/workflow-schema.md`
      for the missing-value case rather than restating the rule.
- [ ] AC-4 (FR10): the precedence paragraph's restriction sentence covers
      both restrictions on `stop-condition-3`'s meaning — the existing
      phase-specific-row one and the new `failed_kind` one.
- [ ] AC-5 (regression): the stop reason code table still contains exactly
      eleven codes, with the same names and the same `state` column values;
      the coverage table still maps `stop-condition-3` to
      `step_needs_intervention` with the develop skill as its source; and
      the precedence rule still names the same three phase-specific stop
      points. A negative proof shows each matcher fires against a synthetic
      copy with a code added, a code removed, or a mapping changed.
- [ ] AC-6 (NFR1): neither document enumerates the `failed_kind` values as
      a permitted set, glosses their meanings, or restates the
      missing-value read rule; both cite the owning document by
      repository-relative path where the field is used. A negative proof
      shows the detector fires against a synthetic restating copy.
- [ ] AC-7 (NFR4): `python3 -m unittest discover -s tests` passes with the
      new module present, and the new module imports only the standard
      library.

## Test Notes

Document-invariant assertions in `tests/test_failed_kind_batch_docs.py`.

- Locate table rows by their first-cell anchor text rather than by row
  index — neither table's row order is a contract.
- AC-5 is the regression backbone of this task: extract the reason-code
  table and assert the count and the ordered code names positionally, so
  both an addition and a removal fail. Do the same for the coverage table's
  `stop-condition-3` mapping.
- AC-2 needs care to avoid a vacuous assertion. Assert positively that the
  bullet names the exception and carries the citation, and assert that the
  unconditional phrasing that would now be false is gone — with a
  non-vacuity guard showing the "gone" matcher can find that phrasing in a
  synthetic copy of the original bullet.
- AC-6's detector is the same definition-shaped detector the other
  consuming tasks use (IMPLEMENTATION.md D7); it must tolerate the
  legitimate single-value mentions AC-1 and AC-3 require.
