# Task Plan: task0001 — `failed_kind` definition and the infra-resume record in the schema SSOT

## Goal

`em-workflow/references/workflow-schema.md` becomes the single owner of the
`implement` step's `failed_kind` field — its vocabulary, meanings,
required-ness, lifecycle and missing-value read rule — and of the `batch`
keys that record the infra auto-resume count and its cap.

## Requirements

FR1, FR2, FR7, FR9, NFR1, NFR4

## Scope

### Files to Create
- `tests/test_failed_kind_schema.py`
  Document-invariant tests for every statement this task adds to the schema
  document.

### Files to Modify
- `em-workflow/references/workflow-schema.md`
  Add the failed-kind definition section, point the implement step's entry
  in the Full structure block at it, and extend the batch block section with
  the infra auto-resume keys.

## Design

Three additions to one document, following the shape the document already
uses for `failed_items[].category` (a definition section owning a closed
vocabulary, plus a pointer from the Full structure block, plus a
compatibility paragraph).

**1. The `failed_kind` definition section.** A new section, placed
alongside the existing field-definition sections, stating all of:

- The field belongs to the `implement` step of `workflow`, and carries a
  closed two-value vocabulary: an external-cause value and a
  decision-required value. This section is the only place in the
  repository that enumerates the two values as the permitted set and the
  only place that glosses their meanings — external cause covers an
  implementer that was orphaned and harness failures; decision-required
  covers a failure of the implementation itself or one that needs the plan
  revisited.
- This document is the single owner of the field's meaning, its
  required-ness and its permitted values; every other document cites this
  section by repository-relative path instead of restating it
  (IMPLEMENTATION.md D7).
- The field is REQUIRED on every write that sets the `implement` step's
  `status` to `failed`. The three such write paths are owned by
  `references/implement-phase.md`; this section names their existence and
  cites that document, and does not restate which value each writes.
- **Lifecycle** (IMPLEMENTATION.md C4/D1): the field is set only by the
  same write that sets `status` to `failed`; it is held for exactly as
  long as that `failed` status; it is returned to null by the same write
  set that moves the step off `failed`. No separate write and no separate
  commit exists for the set or for the clear.
- **Missing-value compatibility**: an `implement` `failed` carrying no
  `failed_kind` reads as the decision-required value. No migration runs.
  This compatibility rule does not weaken the required-ness above for the
  write paths that are in scope. State this in the same shape the
  document's existing `failed_items[].category` pre-change compatibility
  paragraph takes.

**2. Full structure pointer.** The `implement` step's entry in the Full
structure YAML block gains a comment naming the field and pointing at the
new section, mirroring how the `verify` step's `failed_items` entry points
at its own section. The comment must not restate the vocabulary.

**3. The `batch` block's infra auto-resume keys** (IMPLEMENTATION.md C3).
Extend the existing `batch` block section (and the Full structure block's
`batch` mapping) with a nested record under the `batch` key whose path is
`batch.infra_resume`, carrying two member keys:

| Member | Meaning |
|---|---|
| `rounds` | How many infra-caused automatic resumes have already been performed for this feature. Monotonic; never reset. |
| `cap` | The permitted maximum number of such resumes. |

State the unset-read rule in the same shape the section's existing
retired-key paragraph uses: an absent `batch` block, an absent
`infra_resume` block, or an absent member key reads as `rounds` zero and
`cap` two. State that the judgment that consumes these keys — when `rounds`
is incremented, how the cap is compared, and what happens once it is
reached — is defined once in `skills/develop/SKILL.md` and is not restated
here, exactly as the section already does for `verify_rework`.

- [ ] AC-1 (FR1): the schema document contains a `failed_kind` section

      this document is the single owner of the field's meaning,

- [ ] AC-4 (FR9): the section states that an `implement` `failed` carrying

- [ ] AC-8 (NFR4): `python3 -m unittest discover -s tests` passes with the

## Test Notes

All criteria are document-invariant assertions in
`tests/test_failed_kind_schema.py`, following the structure of
`tests/test_failed_items_category.py`: the repository root is derived from
the module's own path, the section is extracted between its own heading and
the next heading, exact-wording markers are module constants matched after
whitespace normalisation, and each matcher has a negative proof against
synthetic text.

Edge cases worth explicit assertions:

- The vocabulary matcher must be positional (an ordered extraction of the
  enumerated values), so both an added value and a dropped value fail it.
- AC-4's compatibility assertion needs a non-vacuity companion showing the
  required-ness statement from AC-2 still stands in the same section — a
  compatibility paragraph that silently replaced the required-ness would
  otherwise pass.
- AC-5's unset-read assertion should read the two defaults independently,
  so a document stating only one of them fails.
- AC-7 must NOT be written as an absence check across the four consuming
  documents: those are other tasks' to write and they will legitimately
  name values. Assert instead that this task's own section exists at the
  cited path and that its heading text is stable enough to be cited.
