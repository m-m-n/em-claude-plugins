## Design

### The state the auto-resume actually leaves behind

The auto-resume write set sets `implement` to `pending`, clears
`failed_kind` and increments the resume count. It writes no `tasks.*` key,
and the terminal path that produced the `failed` (the implement phase's
abort branch) writes none either. So on re-entry the failing task is
`failed` and every other task is `merged`.

Three documents describe that moment and today they disagree:

| Document | What it says now | Why it is wrong for this route |
|---|---|---|
| implement phase, Step I.0's re-entry precondition | any non-fresh entry into `implement: pending` requires at least one `pending` task, else protocol error → ABORT | the auto-resume produces no `pending` task, so a resumed phase aborts immediately, leaves `implement: pending`, and repeats until the stuck-step stop fires — with the resume round already spent |
| rework synthesis, Invariant 1 | states unconditionally that `implement` never returns to `pending` without a rework task registered alongside | the auto-resume is not a rework transition and registers no task; as written the invariant makes the feature's own behaviour a violation |
| develop skill, auto-resume block | describes the write set only | a reader cannot tell whether omitting task state is deliberate, or what re-dispatches the failed task afterwards |

### The rule this task pins

1. **Entry routes.** Step I.0's precondition recognises three routes into
   `implement: pending`: a fresh first pass, a rework re-entry, and the
   develop skill's batch infra auto-resume (cited by repository-relative
   path, its own branch not restated).
2. **The auto-resume route's own satisfying condition.** At least one task
   whose reconciled state (the implement phase's own reconcile step) is
   `failed`. That is what the resumed phase has work to do about; a
   `pending` task is not required on this route.
3. **Convergence.** The resumed phase reaches its failure-handling branch
   through the ordinary reconcile, and that branch's existing behaviour —
   including the batch policy's one automatic retry per task and its
   second-failure abort — governs what happens next. This task states the
   convergence; it changes neither the retry policy nor the selection rule,
   and adds no new automatic restart of a failed task.
4. **Why the write set touches no task state.** Resetting `tasks.{T}.status`
   would make the task selectable as unlaunched by the launch step, under
   the recycled-task-id carve-out, and would restart it without passing
   through the failure-handling branch. The auto-resume deliberately does
   not do this; the develop skill says so in one sentence and cites the
   implement phase for what does handle the task.
5. **The unchanged failure.** A non-fresh entry with neither a `pending`
   task nor a task whose reconciled state is `failed` remains a protocol
   error with the same immediate ABORT and the same report. This carve-out
   widens the precondition for exactly one recognised route and for no
   other state.
6. **Invariant 1's scope.** The invariant governs rework-derived
   transitions (the transitions its own Section 10 defines). A sentence
   names the infra auto-resume as a transition outside that scope and
   points at Step I.0 for its precondition, so neither document has to
   restate the other.

### The route-back clear's reason

The route-back write set clears `failed_kind` "since the step is leaving
`failed`". That reason cannot hold at that point: the phase writes
`in_progress` unconditionally at its start, so the step already left
`failed` before the route-back write set is reached. The document must
instead name, in exactly one place, the write set that carries the
lifecycle clear when a phase is entered from `failed` — the phase-start
`in_progress` write — and state the route-back clause's own accurate role
(re-asserting null inside the same single write set, no extra write and no
extra commit), citing the lifecycle rule's owner rather than restating it.
The lifecycle rule itself is unchanged, so the schema document is not
touched by this task.

### The test module's anchor

The develop-skill module extracts its section by searching for the
auto-resume block's label from the start of the document. That label's first
occurrence is the pointer sentence inside stop condition 3, so the extracted
section is a superset that also contains the stop-condition item, the
precedence block and the verify-cap exception block. Every assertion over
it can pass on content that has moved elsewhere, or with the block's own
heading deleted. The extraction must start at the block's own heading
occurrence, and a guard must prove it: the extracted section contains
neither the stop-condition-3 item's opening text, nor the precedence block's
label, nor the verify-cap exception block's label.

## Test Notes

- All seven criteria are document invariants: read the document from the
  repository root computed from the test module's own path, hold exact
  wording markers as module constants, match after whitespace
  normalisation (these documents hard-wrap mid-phrase, including in
  Japanese without a break-point space).
- AC-5 is the one criterion whose failure mode is a passing test. Write its
  guard as an exclusion assertion over the extracted section, not as a
  presence assertion — a presence assertion passes on the superset too.
- The three neighbouring modules are edited only where a literal this task
  moves is pinned. Prefer adjusting the pinned literal over relaxing the
  assertion; a matcher that stops constraining anything is a regression in
  its own right.
- Non-vacuity: every new matcher gets a negative proof against synthetic
  text, and any matcher that could pass on absent input gets an explicit
  guard that the input was found.
