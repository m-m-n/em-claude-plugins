# Task Plan: task0001 — without_attribute tolerates an attribute absent from the start

## Goal

The test helper without_attribute in the tty-reaper test module runs its block
without raising when the target attribute is already absent, leaves the
attribute absent inside the block, and keeps its current behavior when the
attribute is present. Regression tests pin both cases.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `tests/test_codex_hook_tty_reaper.py` — fix the helper and add its regression tests

## Design

### Helper contract (name and parameters unchanged — FR4)

without_attribute(module, name) is a context manager over any object
`module` and an attribute name `name`.

- Precondition: none on whether `name` is present on `module`.
- Postcondition inside the block: `module` has no attribute `name`, in both
  the present-at-entry and absent-at-entry cases.
- Postcondition after the block (normal or exceptional exit):
  - present at entry: `name` holds the identical object it held before entry
    (identity, not equality);
  - absent at entry: `name` is still absent, and the helper performed no
    attribute deletion on entry and no attribute assignment on exit.
- An exception raised inside the block propagates to the caller unchanged
  (same exception object), after the post-block state above is established.

### Processing flow

1. On entry, look up `name` on `module` with a lookup default that is a
   private marker object unique to the helper, so that "absent" is
   distinguishable from every real value, including a present value of None.
2. If the lookup returned the marker, record "absent" and touch nothing.
3. Otherwise record the returned object and remove the attribute from
   `module`.
4. Run the block.
5. On every exit path: if step 3 ran, assign the recorded object back to
   `name`; if step 2 ran, do nothing. Do not suppress any exception from the
   block.

### Out-of-scope case (from SPEC.md Implementation Approach)

If the attribute was absent at entry and the block itself assigns `name`,
the helper's behavior after exit is unspecified; no caller does this, and no
test is written for it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1, FR2; TS-1): Entering the helper on a stand-in module that has
  no attribute `name` raises no AttributeError, and `name` is absent from the
  stand-in both inside the block and after leaving it.
- [ ] AC-2 (FR2; TS-1): On a stand-in target that records attribute deletions
  and assignments, a block over an absent attribute records zero deletions and
  zero assignments for `name`.
- [ ] AC-3 (FR1, FR2; TS-3): On a stand-in module without `name`, an exception
  raised inside the block propagates as the same exception object, and `name`
  is still absent after leaving the block.
- [ ] AC-4 (FR3; TS-2): On a stand-in module whose `name` holds a unique
  object, `name` is absent inside the block and the identical object is back
  on `name` after leaving it; the same holds when the block raises, and that
  exception propagates as the same exception object.
- [ ] AC-5 (FR1, FR5; TS-4): Nesting the helper twice on the os module's
  pidfd_open attribute raises no error in the inner use, and after both
  blocks exit the attribute is back in the state recorded before the outer
  block (identical object when it was present, absent when it was absent);
  the same holds for the signal module's pidfd_send_signal attribute.
- [ ] AC-6 (FR4; TS-5): The helper keeps its name and its two parameters
  (module, name), and the existing tests
  test_ac5_ts5_a_missing_pidfd_open_function_leaves_a_default_that_stops_nothing
  and
  test_ac5_ts5_a_missing_pidfd_send_signal_function_leaves_a_default_that_stops_nothing
  pass with their helper calls unmodified.
- [ ] AC-7 (NFR1, NFR2, NFR3; TS-6, TS-7): The new tests import only the
  standard library; `python3 -m unittest tests.test_codex_hook_tty_reaper`
  and `python3 -m unittest discover -s tests` both pass, including
  TestThisModule.test_ts14_module_imports_are_all_stdlib; no file other than
  the test module listed in Scope is changed.

## Test Notes

- TDD order: write the AC-1 and AC-5 tests first. Against the current helper
  both fail at block entry with AttributeError, which demonstrates that they
  detect the reported bug; then fix the helper until all criteria pass.
- AC-5 reproduces the missing-function condition on the repository's Linux
  Python, where both functions exist: the outer use removes the attribute, so
  the inner use starts with it absent. No non-Linux Python is needed.
- AC-5 mutates attributes of the real os and signal modules. Capture each
  attribute's original state before the outer block and register a test
  cleanup that restores it, so a failing helper cannot leave those modules
  altered for later tests.
- Stand-in targets (AC-1 to AC-4): a freshly created empty module object; for
  AC-4, place a unique object on it so identity can be asserted. For AC-2, a
  stand-in whose type records attribute deletions and assignments, built from
  the standard library only.
- Exception cases (AC-3, AC-4): raise an instance of a test-local exception
  class inside the block and assert that the caught exception is that same
  instance.
- Naming: name the new tests after the behavior they verify. The acN / tsN
  tokens in the existing test names follow an earlier feature's numbering;
  do not reuse them for this feature's TS-n IDs.
- Test conventions: the repository's test README referenced by SPEC.md NFR1.
