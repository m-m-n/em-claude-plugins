### Terms
- **Top-level chunk**: the chunk `statements()` takes off its pending stack
  first. This is the original command string, after its heredoc bodies are
  stripped out. Every chunk derived from it, at any depth, is not
  top-level: substitution and process-substitution bodies, unclosed
  command-form contents, heredoc bodies, and -c / eval / here-string
  payloads.
- **Single-quote candidate**: a span in the chunk's top-level span list
  that exists only because of the quote-agnostic scan. That scan runs
  `scan_structure()` with single quotes not honoured, so it also reports
  the lexer's substitution candidates inside single-quote and
  ANSI-C-quote regions. A span of a real substitution region, which the
  quote-aware scan also reports, is not a single-quote candidate. By the
  lexer's candidate rule, a candidate lies wholly inside one quote region.
- **Qualifying chunk**: a top-level chunk that meets all four conditions
  below.

### Conditions (FR2 (a)-(d))
A chunk qualifies only when each condition is decided true. A condition
that cannot be decided counts as false.

- **(a)** It is the top-level chunk.
- **(b)** Every statement of the chunk was lexed. None went through the
  parse-failure fallback.
- **(c)** No statement's command word is an execution word.
  - The command word is read from the statement's shaped words, after the
    same assignment and wrapper skip that `head()` applies.
  - The word is compared by its last path segment, so a path-qualified
    name (for example a shell named by its absolute system path) counts as
    the bare name.
  - Execution words are at least: the `SINK_WORD_RE` vocabulary, matched
    the way that pattern matches; eval; source; `.`; exec; xargs; find; su;
    ssh.
  - A statement executes when its skipped wrapper words include env's
    split-string option in any spelling (the existing env split-string
    detection).
  - When the command word is `builtin`, the statement is judged by the word
    that follows it.
  - Further words may be added (SPEC FR2 (c)). Each added word gets its own
    deny case under AC-2.
- **(d)** The command word is static and no override construct is present.
  - Every statement that has a command word has a static one: no
    substitution-derived token and no parameter expansion sits at
    command-word position.
  - No statement of the chunk holds a command-name override construct,
    meaning what `_overrides_command_name()` detects for a lexed
    statement.

A statement with no command word (an empty statement, grouping syntax
only, or assignments only) neither satisfies nor violates (c) and (d).

### Queueing rule
- In a qualifying chunk, the body of every top-level single-quote candidate
  is not pushed onto the pending stack.
- Everything else is queued exactly as before. That covers real
  substitution bodies, unclosed command forms, heredoc bodies and their
  substitutions, and payloads. In a chunk that does not qualify, it also
  covers the candidate bodies.
- **Invariant Q1**: a chunk that does not qualify sends the same entries to
  the pending stack, in the same order, as before the change. A qualifying
  chunk sends the same sequence minus the omitted bodies. The order is part
  of the behaviour, because processing order feeds run-global state: the
  command-name override flag, the deferred data-heredoc bodies and the
  registered marker positions. The decision must be available when the
  candidate bodies are queued, without breaking this invariant.
- **Invariant Q2 (FR3, TM-2)**: the following stay as they were before the
  change. Only whether a body is pushed differs.
  - The top-level span list.
  - Both marking passes.
  - The extension of the run-global substitution list, so that every marker
    index still names the right entry, including the index of an omitted
    body.
  - The registered marker positions.
  - The per-token unresolved and substitution-only flags.
- **Invariant Q3 (NFR2)**: `scan_budget` and `MAX_SHELL_PAYLOAD_EXPANSIONS`
  are unchanged. The qualification reads only what the chunk's existing
  lexing and statement walk already produce. It adds no scan of its own.

### Why the FR4 paths stay denied
- Unquoted and double-quoted substitutions, and substitutions in a heredoc
  body with an unquoted delimiter, are real substitution regions. They are
  never single-quote candidates.
- `bash -c`, `sh -c`, eval and here-string: the command word is an
  execution word, so (c) fails. The payload chunk is not top-level, so (a)
  fails there too.
- Text piped into a shell, or written to a file that a shell then runs:
  another statement of the same chunk has an execution word, so (c) fails.
- A candidate inside a process-substitution or command-substitution body:
  that body is a derived chunk, so (a) fails.

### Case conventions
- Format follows `.claude/rules/hook-tests.md`: three elements per case. No
  case of this task needs a fourth element.
- TS-1 to TS-17 copy the commands of SPEC.md's Test Scenarios exactly,
  including the sample integration-worktree path that SPEC uses.
- In each AC-2 case, `git branch -D example` is the only destructive text.
  It sits inside a single-quoted or ANSI-C-quoted substitution in the
  top-level command, so a deny can only come from the re-scan this task
  preserves.
- Labels are in Japanese, like the existing ones. Each starts with the
  feature name, then the TS-n ID, or for an AC-2 case the FR2 condition or
  execution word it pins.

  array.
