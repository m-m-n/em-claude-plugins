# Task Plan: task0001 — Close anonymous-function body groups on a bare closing brace with pending words

## Goal

string that also contains an anonymous-function body whose closing `}` has no
preceding `;`, without turning any currently silent input into a deny. Both

## Design

### Current behavior (the regression being fixed)

- Since the codex-guard-anon-brace-forms change, the guard opens a group at the
  `{` of an anonymous-function head (`function {`, `function () {`, `() {`).
- A `}` closes the innermost group only when the current simple command has no
  pending words. With words pending, the `}` is read as an ordinary word, the
  group never closes, the scan ends with a group still open, and the whole
  `-c` string is treated as undecidable and passed (silent).
- So `function { : }` (no `;` before `}`) hides every interactive launch in the
  same string, and `function { python3 -i }` is itself passed.

### Group attribute: within an anonymous-function body (NFR1)

- Every open-group record carries one boolean attribute, "within an
  anonymous-function body".
- It is fixed once, at the moment the group opens:
  1. true when the group being opened is an anonymous-function body (any of the
     three head forms);
  2. otherwise, true exactly when the innermost group open at that moment has
     the attribute true — this covers `{` groups, `(` groups and
     function-definition bodies alike, at any depth;
  3. false for a group opened at top level that is not an anonymous-function
     body.
- It is never recomputed and never derived by walking enclosing groups.
  Reading it at a `}` is constant time, so the whole scan stays linear in the
  input length.

### Closing rule for a standalone bare `}`

Precondition: the token is a standalone bare `}` — not quoted, escaped or
expanded, not part of a larger word, and not consumed as a redirect target
(FR4). Every other `}` keeps its current handling.

| Pending words in the current simple command | Innermost open group | Behavior |
|---|---|---|
| none | any | existing closing path, unchanged |
| some | anonymous-function body (FR1) | finalize, then close |
| some | `{` group — brace group or function-definition body — whose attribute is true (FR2) | finalize, then close |
| some | anything else: a `{` group whose attribute is false, a `(` group, or no open group (FR5) | unchanged: the `}` is an ordinary word |

"Finalize, then close" means:

1. Finalize the pending simple command as a command of the innermost group
   through the same path a `;` terminator uses — same verdict evaluation, same
   connection handling (SPEC as-1).
2. Close the innermost group through the existing group-close path.

Postcondition: for every input on which this rule fires, the verdict equals the
verdict of the same input with `;` inserted immediately before that `}`.

### Connection inheritance (FR3)

- Not reimplemented. Because step 1 reuses the `;` path and step 2 reuses the
  existing close path, a pipe into the group, an input redirect in the
  anonymous-function head, and an input redirect after the close reach the
  finalized command exactly as they reach a `;`-terminated command in the same
  group, including through nested groups.
- Words after a closed anonymous-function body are still read as that
  function's arguments (existing behavior).

### Fail-open stays as it is (NFR3)

- A string that still ends with a group open remains undecidable and is passed,
  as today. The change only makes previously undecidable strings decidable
  where FR1 or FR2 applies; groups outside every anonymous-function body (FR5)
  behave exactly as before.

### Module docstring (FR6)

Step 4 of the module docstring states three rules: the FR1 closing of an
anonymous-function body with words pending; the FR2 closing of a `{` group that
lies inside an anonymous-function body (any depth, `(` groups in between
allowed, function-definition bodies included); and the FR5 rule that a `{`
group outside every anonymous-function body does not close while words are
pending, leaving the string undecidable.

### Two copies (FR7)

Make the change in the em-workflow copy, then make the em-review copy
byte-identical to it within the same change.

### Constraints (NFR2, NFR4)

- Standard library only; no file, network or child-process access.
- No plugin version is changed.

  verdict deny or silent; the same table runs against both copies.
- SPEC as-4 makes only the three AC-1 commands mandatory `CASES` entries. AC-2

  too (or to an existing test class where that fits better).

  today, which reproduces the regression. The AC-3 and AC-4 silent cases pass
  today and must keep passing — they guard against new false denies.

  semicolon-inserted counterpart through both copies and asserts equal
  verdicts. List the counterparts explicitly in the test.
- AC-5 timing case belongs in the existing deep-input test class and reuses
  that class's time limit (and its depth, where it defines one).
- Optional edge cases: a function-definition body outside every anonymous
  function, with words pending before its `}`, stays undecidable (FR5); a
  function-definition body inside an anonymous-function body closes (FR2).
- Run the focused module command after each change and the full suite command
  before finishing.
