# Task Plan: task0001 — tests value and notes for a build or format command the cd prefix form does not cover

## Goal

The implementer's two instruction sources state what the report's `tests`
holds and what `notes` says when the approved string that the cd prefix form
does not cover is the build command or the format command. A new
document-test module checks those statements.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4, NFR5

## Scope

### Files to Create
- `tests/test_implementer_cd_prefix_build_format_docs.py` — document tests for the FR1-FR3 statements in both sections (FR5)

### Files to Modify
- `em-workflow/agents/implementer.md` — section "Step 3: Verify the worktree" only: add the build statement and the format statement
- `em-workflow/skills/worktree-task-workflow/SKILL.md` — section "Command execution gate (workflow.yaml strings)" only: add the same two statements

## Design

### Statements to add (in both sections)

Add two statements to each section. Each is its own sentence, and both are
kept apart from the existing test-command sentence (A3). In SKILL.md, they
are new bullets in the obligations list, placed after the test-command bullet
and before the deny bullet. In implementer.md, they go inside Step 3, either
at the end of the paragraph that holds the test-command sentence or in a new
paragraph right after it.

1. Build statement (FR1, FR3, TM-1): when the approved string that the cd
   prefix form does not cover is the build command (`project_commands.build`):
   - the build command is not run;
   - the report sets `tests: "fail"`;
   - `notes` says that the build command was not run because the cd prefix
     form does not cover it.
2. Format statement (FR2, FR3, TM-1): when that string is the format command
   (`project_commands.format`):
   - the format command is not run;
   - the report's `tests` follows the result of the test command;
   - not running the format command is not, on its own, a reason to set
     `tests: "fail"`;
   - `notes` says that the format command was not run because the cd prefix
     form does not cover it.

The new statements describe no other way to run the command: no alternative
form, no later run, no partial run (TM-1).

### What stays as it is (FR4, A1, A2)

- In both sections, these sentences and bullets stay unchanged:
  - the existing test-command sentence;
  - the operator sentence, the citation sentence and the handling sentence
    (not run with the cd prefix, not run without it, not rewritten or split);
  - in SKILL.md, the deny bullet and the Hard-refuse bullet.
- implementer.md Step 7 is not edited, so the report's JSON block keeps its
  field set. The `status` (merged / failed) handling is not changed.
- An empty build or format string means there is no such command (A4). The
  existing rule already says so, and the new statements do not restate it.
- When the test command is also not covered (A5), the existing test-command
  sentence already makes `tests` `"fail"`. Each command-specific statement
  already makes `notes` name the command that was not run. No extra sentence
  is needed.

### Document-test module

- Locating text: take each section by its heading text, "Step 3: Verify the
  worktree" in implementer.md and "Command execution gate" in SKILL.md. A
  section runs to the next heading of the same or a higher level. Headings
  inside fenced code are ignored. A missing heading raises, so an assertion
  never passes over an empty string. Never locate text by line number.
- Matching: normalize whitespace, split the section into blocks (a blank
  line or the start of a list item begins a block), then split blocks into
  sentences at a full stop followed by whitespace. Match each sentence on
  its own.
- Build matcher: accepts a sentence that contains `project_commands.build`,
  `tests: "fail"`, `notes`, "not run" and "does not cover".
- Format matcher: accepts a sentence that contains `project_commands.format`,
  `notes`, "not run" and "does not cover", and that both:
  - says `tests` follows the result of the test command;
  - says not running the format command does not, on its own, make `tests`
    "fail".

  It rejects a sentence that says the report sets `tests: "fail"` for the
  format case without that negation.
- Each matcher has at least one sentence it must accept and the forged
  sentences listed in AC-5 that it must reject.
- The module computes the repository root from its own path and imports only
  the standard library.

## Test Notes

  check the real documents; AC-4 and AC-5 check inline text.
- Write the AC-1 and AC-2 assertions before adding the sentences. With the
  sentences absent, they fail on both documents.
- The existing modules already assert AC-3 and AC-6. Their test IDs can be
  cited for those criteria.
- Model the section slicing and sentence splitting on
  `tests/test_implementer_cd_prefix_exclusion_docs.py`. Copy the approach
  into the new module; do not import that module.
- After each wording change, re-run the four modules named under "Wording
  constraints". Their exactly-one-sentence counts are the easiest thing to
  break by adding one sentence.
