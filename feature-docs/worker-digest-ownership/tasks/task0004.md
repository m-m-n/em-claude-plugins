# Task Plan: task0004 — worker digest stance and the stance check

## Goal

Every envelope worker that writes files and has no Bash carries, in its
agent prompt, citations of the two owner sections of the worker-side digest
stance; and the `worker_digest_stance` invariant check — which derives those
workers from the envelope's Applicability table and the agents' frontmatter —
fails when any of them loses the stance, is told to handle digests, or when
the derived set is empty. A validator test proves their path-only
`written_artifacts` are accepted.

## Design

### Digest stance citation (agent prompt side)

A target agent prompt contains two citations; each sits inside one paragraph
(a block delimited by blank lines; line breaks inside it do not matter):

- **(i)** the path token `references/contracts/worker-envelope.md` and the
  section name "`written_artifacts` reporting" — the worker lists paths only,
  digests are the orchestrator's;
- **(ii)** the path token `references/contracts/spec-writer-contract.md` and
  the section name "Who verifies `expect_digest`" — the worker never computes
  or re-verifies a digest and never returns `blocked` because it cannot
  compute one.

(i) and (ii) may share a paragraph. Placement and text:

- spec-writer.md: inside the existing "Do not compute or re-verify digests."
  bullet; its three pinned phrases ("Do not compute or re-verify digests.",
  "Never return `blocked` because you cannot compute a digest.",
  "`sha256: null`") stay intact.
- designer.md: the "Output" paragraph that already says "paths only — the
  orchestrator computes the digests" gains the section name for (i), plus a
  sentence for (ii).
- implementation-planner.md and rework-planner.md: one short paragraph in
  "## Output". In implementation-planner.md it must stay outside the
  `### 4.` step section (which must not contain `expect_digest`) and before
  `## Gate option vocabulary` (byte-pinned from that heading to the end of
  the file).

Each sentence states the stance by citation, phrased with negation or with
the orchestrator as the actor.

### Target-worker derivation helper

Contract: given a root, returns the sorted list of target worker names.

1. Read `em-workflow/references/contracts/worker-envelope.md`; take the
   "Applicability" section's table; from its `Applies` column take the first
   backticked name in each cell, dropping any trailing annotation such as
   `(new)` / `(revised)`.
2. For each name, read `em-workflow/agents/{name}.md`'s frontmatter `tools`
   list. Keep the worker when the list contains a file-writing tool (`Write`,
   `Edit`, `MultiEdit`, `NotebookEdit`) and no `Bash` entry in any form. A
   read-only worker (no writing tool) is dropped; so is a missing agent file
   (reported by the check as an offender).
3. No worker name is hard-coded anywhere.

### `worker_digest_stance` check

Pure function of the root; reads fixed paths only (IMPLEMENTATION.md
"Checker extension protocol"). Fails, naming the offender, when:

1. the derived set is empty — no envelope document, no Applicability table,
   no `Applies` names, or no name passes step 2 (TS8);
2. a target prompt lacks citation (i) or (ii);
3. a target prompt cites no `references/contracts/*-contract.md`, or a cited
   contract does not itself cite `references/contracts/worker-envelope.md`;
4. an owner stance sentence is absent (whitespace-normalized) from its
   section — "The worker does not compute digests" in worker-envelope.md's
   "`written_artifacts` reporting"; "A worker never returns `blocked` because
   it cannot compute a digest." in spec-writer-contract.md's "Who verifies
   `expect_digest`";
5. a target prompt, or a contract it cites, contains a worker-directed digest
   instruction.

**Worker-directed digest instruction** — a sentence (text whitespace-
normalized; split at sentence ends, including table cells and Japanese 「。」;
list markers and emphasis markers removed) for which all hold:

- it contains a digest term: `sha256`, `expect_digest`, or the standalone
  word digest(s) / hash — compound identifiers such as `input_digest`,
  `digest_inputs`, `base_input_digest`, `answers_digest`,
  `write_policy_digest`, `generation_digest`, `output_digest` do not count;
- it contains a computing or checking verb in any inflection: compute,
  recompute, calculate, hash, verify, re-verify, compare (or 計算 / 照合 /
  比較 / 検証);
- it is addressed to the worker: it starts with one of those verbs as an
  imperative (after dropping a leading clause that ends in a comma), or its
  subject is "the worker", "this worker", "this agent", "you", or the
  agent's own name;
- it carries no negation (not, never, no, n't, without, or しない / しません /
  行わない) and does not name the orchestrator (orchestrator / オーケストレーター).

The rule may be tightened by the implementer as long as every Acceptance
Criterion still holds; it must not depend on line-break positions.

### Synthetic-tree helper

Adds to `build_passing_repo`: an envelope document whose Applicability table
lists the fictional `stance-worker` (with an annotation) plus one read-only
fictional worker; their agent files (`stance-worker` with `Read, Write` and
both citations; the read-only one without a writing tool); a fictional
contract cited by `stance-worker` that cites the envelope; the two owner
stance sections; and a dispatch line for each fictional agent so
agent/dispatch parity passes.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1): spec-writer.md, designer.md, implementation-planner.md and
      rework-planner.md each carry citations (i) and (ii); spec-writer.md's
      three pinned phrases are intact; implementation-planner.md's new text
      is outside the `### 4.` section and before `## Gate option vocabulary`.
- [ ] AC-2 (FR6, TS1): the derivation helper returns a non-empty set for the
      real repository, equal to the `Applies` workers whose agent tools
      include a writing tool and exclude Bash (the read-only analyst is not
      in it); on synthetic trees it strips annotations, drops Bash-holding
      and write-less agents, and derives fictional names.
- [ ] AC-3 (FR6, TS1): `worker_digest_stance` passes on the real repository
      and fails on synthetic trees where one target prompt lacks (i), lacks
      (ii), cites no contract, cites a contract that does not cite the
      envelope, or where an owner stance sentence is removed — each failure
      names the offending worker or document.
- [ ] AC-4 (FR1, FR6, TS1): the check fails when a target prompt or a cited
      contract contains an imperative ("Before writing, compute the sha256 of
      each target and compare it with `expect_digest`.") or worker-subject
      ("The worker computes the digest of every written path.") digest
      instruction, and does not flag negated ("The worker does not compute
      digests."), orchestrator-attributed ("The orchestrator computes the
      sha256 …") or passive sentences.
- [ ] AC-5 (FR6, TS8): the check fails — never passes — when the derived set
      is empty: no envelope document, no Applicability table, a table without
      `Applies` names, or only Bash-holding / write-less agents.
- [ ] AC-6 (FR1, FR6, TS5): for every worker the helper derives from the real
      repository, its `references/fixtures/worker-result/{worker}/valid-completed`
      result with each `written_artifacts` entry's `sha256` set to `null`, and
      with `sha256` removed, is accepted by `validate-worker-output.py --kind
      worker-result` (exit 0); the derived set is non-empty, every derived
      worker has that fixture, and each run has at least one
      `written_artifacts` entry; a control variant whose entry has no `path`
      is rejected (exit 1).
- [ ] AC-7 (NFR1, NFR3): the existing checker tests pass (the CLI exit-0
      synthetic tree with this task's helper added, the single-traversal
      count, the repository-level run); the new and extended test code uses
      the standard library only, and the new test file contains no
      `subagent_type=` + quote + `em-workflow:` string.

## Test Notes

- AC-2 … AC-5 are unit tests in `tests/test_check_plugin_invariants.py`,
  each starting from a passing synthetic tree and breaking one thing; the
  real-repository cases call the functions on the repository root.
- AC-6 loads the checker module the way the existing checker tests do, calls
  the helper on the repository root, copies each fixture into a temporary
  directory, mutates the copy, and runs the validator as a child process
  exactly as the existing fixture-corpus runner runs that fixture directory
  (same auxiliary files). When a fixture's `written_artifacts` is empty, the
  test first adds one entry for a path the fixture's envelope `write_policy`
  covers, so neither variant is vacuous.
- The validator itself is not changed by this task (it already ignores the
  entry's `sha256`).
- Avoid dotted backtick spans after "gate id" phrases in synthetic or real
  prose (gate-ID coverage check).
