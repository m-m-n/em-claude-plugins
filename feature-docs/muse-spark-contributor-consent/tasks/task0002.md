# Task Plan: task0002 — contributor-consent skill in both plugins

## Goal

Deliver the only interactive path by which consent is granted or revoked: a
`contributor-consent` skill, present in both plugins, that probes for the LiteLLM
harness, presents exactly three mechanically collected facts, asks exactly one
question, and records or removes the consent through the guard CLI.

## Requirements

FR13, NFR3, NFR6

## Scope

### Files to Create
- `em-workflow/skills/contributor-consent/SKILL.md` — the skill document.
- `em-review/skills/contributor-consent/SKILL.md` — the same skill for the review
  plugin, differing only where it must name its own plugin or its own
  review-phase document.
- `tests/test_contributor_consent_skill.py` — structural test of both documents.

### Files to Modify

None. This task creates files only.

## Design

### Placement

The skill is a skill document, not a command file. No `commands/` file is added in
either plugin.

### Execution flow described by the document

1. **Availability probe.** Run the LiteLLM availability probe exactly as the
   owning plugin's review-phase document already defines it — reference that
   definition, do not restate or reimplement it (IMPLEMENTATION.md Open Questions,
   O2). When the probe is false, print exactly this line and exit, with no fact
   collection, no question, no store read and no store write:

   `vertex-review の LiteLLM ハーネスが見つからない。contributor ティアはこの環境では使えないため、同意の記録は不要。`

2. **Determine the current consent state** by invoking the guard CLI's `--list`
   for the current repository directory and branching on empty versus non-empty
   output. The skill never reads the store file itself; the CLI is its only route
   to the store (IMPLEMENTATION.md Shared Components, Guard CLI).

3. **Present the subject and the facts.** Print the subject of consent — the
   repository the derived project key stands for — then, after a blank line, the
   three facts as one explicitly labeled group, in this fixed order with these
   fixed labels:

   - `リモートの可視性` — public / private / internal / 取得できず
   - `ライセンス` — the license name as reported, or なし when the repository
     genuinely has none, or 取得できず
   - `コントリビューター` — あなたのみ / あなたを含む N 名 / 取得できず

   Facts are collected mechanically (repository metadata from the hosting CLI or an
   equivalent means, the license from the repository, the contributor count from
   the repository history). A fact that cannot be collected renders as 取得できず
   — never omitted, never guessed, never turned into a conversational follow-up
   question. The unpushed-commit state is not among the facts and is not shown.

   The subject line is the target of consent, not a fourth fact: the document
   introduces the three facts as their own labeled group (for example, a numbered
   list introduced as 提示する 3 つの事実) and describes the subject line
   separately. If a verifier still reads the subject line as a fourth fact, drop
   the subject line — the three facts are requirement-fixed and the subject line is
   not (IMPLEMENTATION.md Open Questions, O3).

4. **Ask exactly one question**, single-select, one question object, two options,
   with the wording chosen by the state determined in step 2:

   - Not yet consented — question: `このリポジトリの差分を muse-spark contributor ティアへ送ることに同意する?`;
     option 同意する (records this repository's key in the consent store, allowing
     the contributor tier in later reviews) and option 同意しない (records
     nothing; the contributor tier stays denied).
   - Already consented — question: `このリポジトリの contributor ティア同意は記録済み。どうする?`;
     option 維持する (leaves the record unchanged) and option 撤回する (deletes
     this repository's key; the contributor tier is denied again).

5. **Act on the answer.** The consenting option invokes the CLI's `--record` for
   the repository directory; the revoking option invokes `--remove`. The
   non-mutating option invokes nothing.

6. **Dismissal is the no-write branch.** If the user dismisses the question or
   answers nothing, take the non-mutating branch, print
   `同意ストアは変更していない。` and exit successfully without invoking the CLI.

### Constraints the document must satisfy

- The skill is run by a user in an interactive session. It is not invoked by the
  develop flow, and no develop-phase document references it.
- No document this task writes outside the skill itself may introduce a new
  occurrence of the interactive-question tool name in a develop-phase or
  review-phase document (IMPLEMENTATION.md Shared Components, Interactive-question
  budget). This task adds no such occurrence anywhere but inside the two new skill
  documents.
- The document collects no judgment material conversationally: exactly one round,
  and the facts inform the decision rather than gating it — the question is asked
  even when a fact could not be collected.
- Consent is per repository, and every worktree of a repository shares one entry;
  the document says so where it names the subject of consent.

### Register

Japanese, matching the register the guard's own messages settle on
(IMPLEMENTATION.md Conventions and Open Questions, O1). Identifiers stay verbatim
ASCII. No emoji, no decoration.

## Test Notes

- The whole task is verified structurally: the test parses each document's
  frontmatter and body and asserts the presence, count and distinctness of the
  described elements. Write the test first and let it drive the document's
  section structure.
- Make "exactly three facts" countable: assert the labeled group contains three
  entries and that the three fixed labels each appear once inside it. Assert the
  unpushed-commit wording is absent.
- Make "exactly one question round" countable: assert exactly one question
  construct is described and that each of the two state wordings offers exactly two
  options.
- Assert the not-installed line and the no-write line by exact string, since both
  are fixed content.
- Parameterize every assertion over both plugins so the two documents cannot drift.
- Cross-plugin reference check: assert that no develop-phase document in either
  plugin mentions the skill's directory name.

## Out of Scope

- Implementing the guard, the CLI, or the store (task0001 owns them).
- Changing any review registry or protocol document (task0003 owns them).
- Any version field (task0004 owns it).
- Automating consent: nothing in the develop or review flow may invoke this skill,
  and the skill must not offer a non-interactive mode.
- Storing any of the three facts anywhere — they are shown and discarded.
