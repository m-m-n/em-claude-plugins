# Task Plan: task0007 — quote-aware command recognition in the muse_guard classifier

## Goal

Rebuild the guard's command-recognition step so that shell quoting is honoured
**before** the command string is split into commands, and so that wrapper words and
nested shells are resolved to the command they actually run. A quoted separator must
no longer break a real contributor-tier invocation apart, and a quoted mention must
no longer be carved out as a standalone invocation.

## Provenance

- Source: verify, round 1. Failed items `TS-5`, `TS-6`, `TS-26`, `TS-27`.
- Single root cause: the recognizer splits the raw command string into segments
  **before** honouring shell quoting, so every one of the four scenarios fails on the
  same premise. The remedy is a change of mechanism (see IMPLEMENTATION.md D-H);
  adding more enumerated spellings was explicitly rejected by the rework gate.

## Requirements

FR1, FR4, FR5, FR10, NFR2, NFR4, NFR6

## Design

The store contract, the project-key contract, the deny-payload contract and the
plugin-slug rule are pinned in IMPLEMENTATION.md Shared Components and are NOT
changed here. Only the step answering "does this command string invoke the
contributor tier?" changes, and only in mechanism — its external contract is the
"Command recognition" row of IMPLEMENTATION.md Shared Components. The surrounding
decision flow keeps its current behavior, including the short circuit that returns
before project-key derivation and before the store read when the answer is "no".

### Why the current pipeline fails

The pipeline's first act is a regular-expression split of the raw string on
separator characters. That split cannot see quoting, so:

- a real invocation whose prompt argument is a quoted string containing a statement
  separator or a newline is cut into fragments, none of which still looks like an
  invocation (TS-5);
- a quoted string that merely contains invocation-looking text is cut into fragments,
  one of which looks exactly like an invocation, producing a misfire (TS-6);
- any spelling whose value carries a quote delimiter inherits both failures (TS-26);
- wrapper and nesting recognition, which consumes the same fragments, is applied to
  garbage inputs and additionally lacks the shapes the harness uses (TS-27).

Every later stage is therefore built on a premise that does not hold. The fix
replaces the premise, and the stages downstream are re-expressed as consumers of
tokens.

### Stage 0 — one quote-aware tokenization, first

The raw command string is tokenized once, by a real POSIX-shell tokenizer, before
anything else inspects it. Python's standard-library shell tokenizer is the expected
basis; a hand-rolled regular expression over the raw string is not acceptable for
this role. The tokenizer must be driven in its POSIX mode with the shell's own
metacharacter set, so that:

- single quotes, double quotes and backslash escapes are consumed as quoting, and
  the characters inside them are ordinary text;
- separators (statement separator, pipe, boolean operators, background, newline) are
  produced as their own tokens **only** when they occur outside quoting;
- a token records whether it came from a quoted region, because that determines
  whether it may later be re-examined as command text.

Tolerance is part of the contract: an unterminated quote, or any construct the
tokenizer refuses, must yield "cannot classify" — no exception escapes, no partial
result is used, and the guard falls back to no decision (NFR2).

### Stage 1 — here-document handling, expressed on the token stream

A here-document header is honoured only when it appears outside quoting, exactly as
today. Re-express that rule so it reads the quote state established by stage 0 rather
than performing an independent scan of the raw string:

- a genuine here-document's body is removed before classification, so a body that
  merely names the tier still produces no decision;
- a header-looking sequence inside a quoted region is not a header, so text that
  follows it stays visible to classification;
- stripping only ever removes text, so it can never produce a false deny; and no path
  classifies both the stripped and the unstripped text.

### Stage 2 — statements from tokens

Statements are formed by cutting the token stream at separator tokens. Because
separators only exist as tokens when they were unquoted, this stage cannot split
inside a quoted argument, and cannot fail to split at a real separator.

Command substitutions are extracted as statements in their own right, in addition to
the statement that contains them, and only from regions where a shell would expand
them: unquoted text and double-quoted text. A substitution-looking sequence inside a
single-quoted region is inert text and is not extracted.

### Stage 3 — resolving a statement's command word

Classification still requires a statement's command word to resolve to the codex
CLI. That restriction is load-bearing for the no-misfire floor — it is what keeps a
commit-message argument or a search pattern from being read as a model selection —
and it is preserved. What changes is that the command word is **resolved** rather
than read literally:

- **Environment assignments** leading a statement are stepped over.
- **Wrapper words**: a known wrapper word that prefixes another command is stepped
  through, and the wrapped command word becomes the statement's command word. The
  wrapper set must include, at minimum, the argument-list-expanding wrapper and the
  scheduling-priority wrapper named in the verify reproduction, alongside the wrappers
  already recognized.
- **Wrapper options that take a separate value**: for each recognized wrapper, the
  options that consume the following token as their value are known, so that value is
  stepped over instead of being mistaken for the wrapped command word. This is what
  makes a wrapper invoked with a numeric option resolve to the command behind it.
  An option token the wrapper's table does not describe stops resolution and leaves
  the statement unclassified (no decision) rather than guessing — fail open, and a
  documented residual.
- **Nested shells**: when the resolved command word is a shell, the argument that
  follows its command-string flag is treated as nested command text and re-entered at
  stage 0, recursively. The command-string flag must be recognized both as a
  standalone short option and when it is **bundled with other short options in one
  token**; a bundled cluster ending in the command-string flag selects the next token
  as the nested command text, and a cluster that does not contain the flag does not.
- Recursion is bounded at depth 2. Anything nested deeper is not classified and
  therefore yields no decision. The bound keeps the added work inside the latency
  budget; no stage introduces a subprocess or a file access.

### Stage 4 — model-selection matching

Unchanged in intent, re-expressed over tokens: for a statement whose resolved command
word is the codex CLI, the argument list is scanned for a model-selection argument.
The recognized shapes stay the table established previously — a short- or long-form
model flag whose value is the following token; a single token whose head up to the
first equals sign is that flag and whose tail is the value; a single token consisting
of the short-form flag with the value attached. Because quoting was consumed in stage
0, the "quoted equivalent" of each shape needs no separate row: the value arrives
already unquoted.

The value is compared to the contributor tier name by **exact equality**, never by
prefix, suffix or substring, so the superstring boundary holds in both directions.

### Both copies

The edit is applied identically to both plugin copies. The only permitted divergence
remains the plugin-slug constant. No shared module, helper package or generator is
introduced (FR1 / D-A).

## Test Notes

- Write the four verify reproductions as tests **first**, and confirm they fail
  against the current recognizer before changing it. Their exact shapes are:
  a contributor-tier invocation followed by a double-quoted prompt containing a
  semicolon (must deny); a text-printing command whose single-quoted argument contains
  separator-delimited invocation-looking text (must not decide); a shell invoked with a
  bundled short-option cluster ending in the command-string flag (must deny); the
  argument-list-expanding wrapper and the scheduling-priority wrapper, each with a
  separate-value numeric option before the command word (must deny).
- Keep the widening structured as two paired tables so a future shape is one row on
  each side: a deny table (shape → must deny) and a no-misfire table (shape → must not
  decide). Every row added to the deny table gets its counterpart. Existing floor rows
  are extended, never replaced or relaxed.
- The wrapper and nesting cases need both polarities inside the same construct — the
  wrapped invocation and the wrapped mention — because a fix that widens the command
  word without keeping the codex-CLI restriction passes the first and fails the second.
- Add at least one tokenizer-hostile case (unterminated quote) asserting no decision
  and a zero exit, so the tolerance clause is pinned behaviorally.
- The recursion bound is asserted behaviorally: a nesting one level past the bound
  yields no decision, and the whole set still runs well inside the registered timeout.
- Every case drives the same subprocess entry point the hook uses, is parameterized
  over both script copies, and points the store-path override under a temporary
  directory. No case reads or writes real user state.
- Do not touch existing cases that invoke a CLI command — those belong to the parallel
  CLI task (IMPLEMENTATION.md D-J).
