# Task Plan: task0006 — invocation-shape recognition in the muse_guard classifier

## Goal

Close the recognition gap between what the guard treats as a contributor-tier
invocation and what a real shell plus the codex CLI actually execute, so the deny
cannot be bypassed by a model-selection spelling, by nesting the invocation inside
a wrapper command, or by a quoted here-document header that erases the invocation
before classification — while the existing no-misfire floor stays exactly where it
is.

## Provenance

- Source: review, round 1.
- Origin findings (`origin_kind: review`):
  - `1170516129413bc5` (high, security) — unrecognized model-selection spellings.
  - `98df40b6ce96c809` (medium, security) — merged sibling of the above:
    unrecognized nested invocation contexts.
  - `e0fb5715d50c4b74` (medium, security) — quote-unaware here-document stripping
    deletes a real invocation before classification.

All three are one root cause — the recognition pipeline models a narrower command
grammar than the one that actually runs — and all three are constrained by the same
acceptance criterion (recognize every invocation shape without widening what counts
as a mention). The here-document fix and the command-substitution fix additionally
need the same quote-state scan over the raw command text, so they cannot be split
into independent worktrees.

## Design

The store contract, the project-key contract, the deny-payload contract and the
plugin-slug rule are pinned in IMPLEMENTATION.md Shared Components and are NOT
changed by this task. Only the step that answers "is this command an invocation of
the contributor tier?" changes. Every other stage of the hook decision flow keeps
its current behavior, including the short circuit that returns before project-key
derivation and before the store read when the answer is "no".

### The recognition pipeline, restated as four stages

1. **Pre-classification text handling.** Here-document bodies are removed from the
   raw command text before anything is split into statements or segments.
2. **Statement / segment splitting.** The remaining text is split into the
   individual commands a shell would run.
3. **Command-word resolution.** Each segment's own command word decides whether its
   arguments are even examined.
4. **Model-selection matching.** Only for a segment whose resolved command word is
   the codex CLI, the argument list is scanned for a model-selection argument whose
   value is the contributor tier.

The gap the findings describe is that stage 1 removes too much, stage 2 never looks
inside command substitutions or shell command-string arguments, stage 3 stops at the
literal command word, and stage 4 knows only two of the flag spellings.

### Stage 1 — quote-aware here-document stripping

A `<<WORD` sequence starts a here-document only when it occurs OUTSIDE any quoted
region. The stripper walks the raw text tracking single- and double-quote state and
honors a here-document header only in the unquoted state; a header-looking sequence
inside a quoted region is left alone, so text that follows it stays available to
classification.

Two behaviors this must preserve:

- A genuine here-document whose body merely names the contributor tier is still
  removed, so it still produces no decision. The cheaper mitigation of classifying
  both the stripped and the unstripped text is explicitly rejected: it would deny a
  genuine here-document body that mentions the model, which the no-misfire floor
  forbids.
- Stripping only ever removes text, so it can never cause a false deny; the fix
  changes what stays visible, never what a visible segment means.

### Stage 2 — command substitution as its own statement

The bodies of command substitutions — both the parenthesized form and the backtick
form — are extracted from the text and classified as statements in their own right,
in addition to the surrounding statement. Extraction happens on the quote-aware pass
of stage 1, which is why the two changes share one scan.

### Stage 3 — resolution through wrappers and shells

Classification still requires a segment's command word to resolve to the codex CLI:
that restriction is what keeps a commit-message argument or a search pattern from
being read as a model selection, and it is load-bearing for the no-misfire floor.
What changes is that the command word is RESOLVED rather than read literally:

- A wrapper word that prefixes another command (the existing wrapper set, extended
  with the argument-list-expanding wrapper named in the finding) is stepped through:
  the wrapped command word becomes the segment's command word.
- When the command word is a shell, the argument that follows its command-string
  flag is classified as its own command text, recursively.

Recursion is bounded at depth 2. Anything nested deeper is not classified and
therefore yields no decision (fail open, per the guard's error-handling policy). The
bound is what keeps the added work inside the latency budget: no new subprocess and
no new file access is introduced by any stage.

### Stage 4 — the model-selection flag table

Model selection is matched as a small table of argument shapes rather than two
hard-coded spellings:

- a short- or long-form model flag as one token, with the value as the FOLLOWING
  token;
- a single token whose head, up to the first equals sign, is the short- or long-form
  model flag and whose tail is the value;
- a single token consisting of the short-form flag with the value attached directly
  to it.

Each shape is recognized with the value bare, single-quoted and double-quoted. In
every shape the value is compared to the contributor tier name by EXACT equality
after quote removal — never by prefix, suffix or substring — so the superstring
boundary holds in both directions: the plain tier never matches the contributor
tier, and the contributor tier never matches the plain tier.

### Both copies

The edit is applied identically to both plugin copies. The only permitted divergence
remains the plugin-slug constant. No shared module, helper package or generator is
introduced (FR1 / D-A).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: With an absent or consent-free store, every model-selection shape in the
      table above denies from BOTH copies: long flag with a separate value, short and
      long flag joined by an equals sign, and short flag with the value attached — each
      with the value bare, single-quoted and double-quoted — in addition to the two
      spellings already recognized. Every comparison is exact equality against the
      contributor tier name. (TS-4, TS-5, TS-26)
- [ ] AC-2: The no-misfire floor is unchanged: a commit-message argument naming the
      tier, a text-search pattern argument naming it (including the short-flag form
      that collides with the model flag), quoted mentions, a here-document body that
      names it, plain `muse-spark` in every spelling, unrelated commands, a non-Bash
      payload, an empty command and unparseable input all still produce no decision
      from both copies. A model flag whose value equals the tier is an invocation ONLY
      when its segment's resolved command word is the codex CLI. (TS-3, TS-6, TS-7,
      TS-26)
- [ ] AC-3: Nested invocations are recognized: the invocation carried as a shell's
      command-string argument, inside a parenthesized command substitution, inside a
      backtick command substitution, and behind the argument-list-expanding wrapper
      all deny. The same constructs carrying only a mention (for example a
      commit-message argument inside a shell command string) produce no decision.
      Nesting deeper than the bound of two produces no decision rather than an error.
      (TS-27)
- [ ] AC-4: Here-document handling is quote-aware: a payload whose first line contains
      a here-document header inside a quoted string, whose second line is a real
      contributor-tier invocation and whose third line is the header word, denies. A
      genuine here-document whose body only mentions the tier still produces no
      decision, and a real invocation placed after a genuine here-document's terminator
      still denies. No path classifies both the stripped and the unstripped text.
      (TS-6, TS-28)
- [ ] AC-5: The two copies still differ in exactly one line, the plugin-slug constant;
      every new test case is parameterized over both copies; no shared module, helper
      package or generation script was added, and no file was added under either
      plugin's `hooks/tests/`. (TS-19, TS-17)
- [ ] AC-6: The guard's operating envelope is unchanged: no code path emits `allow` or
      `ask`; anything unclassifiable yields no decision; a non-invocation command still
      returns before the key-derivation subprocess and before the store read; the only
      subprocess launched is still that one git call; every new case completes well
      inside the registered timeout; the new tests live only in
      `tests/test_muse_guard.py`, import the standard library only, and
      `python3 -m unittest discover -s tests` passes. (TS-20, TS-21, TS-22, TS-24,
      TS-17)

## Test Notes

- Every new case is driven through the same subprocess entry point the hook uses and
  is parameterized over both script copies, matching the existing module's structure.
- Structure the widening as two paired tables so a future shape is one row on each
  side: a deny table (shape → must deny) and a no-misfire table (shape → must not
  decide). Every row added to the deny table gets its counterpart in the no-misfire
  table; the existing floor rows are extended, never replaced or relaxed.
- The wrapper / shell-nesting cases need both polarities in the same construct — the
  wrapped invocation and the wrapped mention — because a fix that widens the command
  word without keeping the codex-CLI restriction passes the first and fails the second.
- The quoted-here-document case belongs next to the existing genuine-here-document
  mention case, so the pair reads as one contrast.
- The recursion bound is asserted behaviorally: a nesting one level past the bound
  yields no decision, and the whole set still runs well inside the registered timeout.
- No case may read or write real user state; every case points the store-path override
  under a temporary directory, as the module already does.

- Emitting `allow` or `ask` under any condition.
