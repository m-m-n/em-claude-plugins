## Design

### Component responsibilities

`muse_guard.py` has two entry paths in one file, sharing the store reader and the
project-key derivation:

- **Hook path** (no CLI arguments): consumes the PreToolUse payload on standard
  input, emits either one deny object or nothing, always exits 0.
- **CLI path** (`--record` / `--remove` / `--list`): consumes arguments, mutates or
  inspects the store, prints a human line (or, for `--list`, a bare key), and is
  never reached from the hook path or from the workflow itself.

The store contract, the project-key contract, the CLI contract, the deny-payload
contract, the registration form and the plugin-slug rule are all pinned in
IMPLEMENTATION.md Shared Components — implement against those, do not re-derive
them.

### Hook decision flow

1. Read standard input. Unparseable input, a tool name other than the Bash tool, a
   missing command, or an empty command → no decision.
2. Classify the command string. If it is **not** an invocation of the contributor
   tier → no decision, returning before any project-key derivation and before any
   store access (this short-circuit is what keeps the guard far inside its
   registered timeout).
3. Derive the project key from the caller's working directory.
4. Read the store. Missing, unreadable, invalid, or wrong-shaped → treat as "no
   consent for any project"; never write, never repair.
5. Key present → no decision. Key absent → emit the deny object.

### Command classification rules

An **invocation** is the model-selection argument naming the contributor tier, in
every spelling the harness emits: the short flag followed by the value as a
separate word, and the long flag joined by an equals sign, each in bare, single-
quoted and double-quoted forms.

A **mention** is not an invocation and must never be denied: the identifier
appearing inside a quoted string that is not a model-selection value, as the
pattern argument of a text-search command, inside a here-document body, or inside
a commit-message argument.

Boundaries are honored in **both** directions: the plain tier name must never be
read as the contributor tier, and the contributor tier name must never be read as
the plain tier — neither is a substring match of the other for this purpose.

Anything the classifier cannot decide with confidence is not an invocation (fail
open).

### Message content

Two module-level constants, each a single line, with no value interpolated into
them.

- Human-facing reason — one sentence naming the model, naming the condition
  (consent for this repository is not recorded), and carrying no path, no project
  key, no store location and no remediation step:

  `muse-spark-contributor（contributor ティア）は、このリポジトリの同意が記録されていないため使用できない。`

- Agent-facing context — exactly three clauses in this order: what to do instead,
  who may grant consent and how, and the prohibition on the agent granting consent
  for itself:

  `回避策を探さず、reviewers.yaml の chain にある非 contributor の muse-spark エントリ、または他の chain エントリでレビューを続行する。同意はユーザーが対話セッションで /{plugin slug}:contributor-consent スキルを実行したときにだけ記録される。エージェント自身が muse_guard.py --record を実行して同意を代行してはならない。`

  `{plugin slug}` is the one permitted divergence between the two copies.

Before writing these, read the deny and ask messages the existing bash guard and
destructive guard emit (IMPLEMENTATION.md Open Questions, O1). If that family
writes in 敬体, convert both strings to 敬体 and keep the clause structure and
content exactly as above; otherwise keep plain form.

### CLI output content

- `--record`: `同意を記録した: <project key>`
- `--remove`, key present: `同意を削除した: <project key>`
- `--remove`, key absent: `同意は記録されていない: <project key>`
- `--list`: the project key alone, or nothing.
- Malformed store on a mutating command: `同意ストアの形式が不正: <store path>` on
  standard error, exit 1, nothing written. The store path appears in output only
  here.

### Registration

Add the entry to each plugin's PreToolUse / Bash group in the verbatim form and
timeout pinned in IMPLEMENTATION.md, ahead of the destructive guard entry so that
guard's blanket allow cannot terminate the decision first. The em-review file is
new and must satisfy the same well-formedness invariants the em-workflow file
already satisfies: plugin-root-relative verbatim command, per-script timeout, no
duplicate registration of one script under one event, referenced script present
and executable.

Both plugins installed means the guard fires twice for one command. Both copies
read the same store and reach the same decision, so the duplicate is a no-op.

- [ ] AC-1: Both copies exist, are executable, and differ in exactly one line —
      the plugin-slug constant. Both emit deny objects carrying exactly the four
      inner fields, with every string on a single line, and neither interpolates
      the command, the working directory, the project key, the store path or any
      store content into a message. (TS-19, TS-1)
- [ ] AC-2: With an absent or consent-free store, every enumerated contributor-tier
      invocation spelling produces a deny with exit 0 from **both** copies; the
      reason states the missing consent and the additional context directs the agent
      to a non-contributor entry. The store path still does not exist afterwards.
      (TS-1, TS-4, TS-5)
- [ ] AC-3: No decision (exit 0, empty stdout) is produced for: a plain
      `muse-spark` invocation in any spelling; a mere mention inside quotes, a

      unrelated command; a payload whose tool is not the Bash tool; an empty
      command; unparseable standard input; and the same invocation as AC-2 after

      the *other* plugin's copy. (TS-2, TS-3, TS-6, TS-7, TS-25)
- [ ] AC-4: The project key matches the existing bash guard's derivation rule:
      two worktrees of one repository share one consent entry (recorded from
      either, revoked from either, observed from both), and a non-repository
      directory reached through a symlink resolves to the same key as its real
      path. The store never holds two keys for one repository. (TS-9, TS-10)
- [ ] AC-5: A missing, unreadable, invalid-JSON, wrong-shaped, or
      directory-instead-of-file store makes every contributor-tier invocation deny
      and every other command undecided, and leaves the store byte-unchanged and

- [ ] AC-6: The CLI round trip holds: `--list` before consent prints nothing;

      no field beyond the version, the projects mapping, the key and its timestamp;
      the timestamp carries an explicit UTC offset; writes are atomic and create
      parent directories; a mutating command against a malformed store exits 1,
      writes nothing and does not rewrite the file; exactly one of the three
      commands is accepted at a time and argument misuse exits 2. (TS-11, TS-2)
- [ ] AC-7: `python3 -m unittest discover -s tests` collects and passes

      package; every case points the store-path override under a temporary
      directory and no case reads or writes real user state; neither plugin's
      `hooks/tests/` gained a file for this feature; the guard reaches no network

## Test Notes

- **Unit-level** (single process, no repository needed): command classification —
  invocation spellings, mentions, plain-tier commands, malformed payloads. Drive
  these through the same subprocess entry point the hook uses, so what is tested is
  the shipped path rather than an internal helper.
- **Integration-level** (temporary repository + temporary store): deny and pass-through
  behavior, worktree key sharing, symlinked non-repository directories, malformed
  store variants, the CLI round trip, and the cross-copy consent check (record
  through one plugin's copy, observe through the other's).
- Parameterize every behavioral case over both script copies; a case that passes
  for one copy and not the other is the failure mode this feature most needs to
  catch.
- The "no network" and "never `ask`" criteria are awkward for a behavioral test:
  satisfy them by inspecting the shipped source of both copies for
  network-capable imports and for the `ask` decision literal, and by asserting that
  the only subprocess the guard launches is the key-derivation git call.
- The latency criterion is asserted as a generous upper bound (well under the
  registered timeout) over a representative sample, not as a micro-benchmark.
- Structure the store-corruption cases as a table of store contents so a new
  corruption shape is one row.
