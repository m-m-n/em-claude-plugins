# Task Plan: task0009 — contributor-consent skill presents the command instead of running it

## Goal

Bring both plugins' `contributor-consent` skill in line with the amended FR13: the
skill inspects the current consent state, presents the three facts, asks exactly one
question, and then **hands the user the command line to run in their own terminal**
instead of recording or revoking consent itself.

## Provenance

- Source: create-spec amendment following the verify failure of `SC-8`. FR13 and AC-12
  now require the skill to present the mutating command rather than execute it, because
  the CLI refuses any write whose standard input is not an interactive terminal.
- The skill is the only surface a user touches; if it still described itself as
  performing the write, every run would end in a refusal the user did not expect.

## Requirements

FR13, NFR3, NFR6

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/skills/contributor-consent/SKILL.md` — the post-question steps: present
  the command, do not run it; and the wording that describes who performs the write.
- `em-review/skills/contributor-consent/SKILL.md` — the same change, with this
  plugin's own paths and namespace.
- `tests/test_contributor_consent_skill.py` — assertions for the presented-command
  shape and for the absence of any self-executed mutating command.

## Design

The Guard CLI contract and the Consent-write provenance boundary are pinned in
IMPLEMENTATION.md Shared Components. This task consumes them; it changes neither.

### What stays exactly as it is

- The skill is manually run by the user in an interactive session and is called by no
  develop-phase document.
- The availability probe runs first, exactly as each plugin's review-phase document
  defines it (IMPLEMENTATION.md O2). When it reports the harness absent, the skill
  prints its one plain "not installed" line and exits — no state read, no facts, no
  question, no command presented.
- The current consent state is read with the CLI's **read-only** command, which the
  skill may run itself: it lies outside the provenance boundary.
- Exactly three facts are presented — remote visibility, license, sole contributor —
  as one explicitly labeled group, in that fixed order with their fixed labels and
  their fixed value vocabulary, including the "could not be determined" value that is
  used instead of omitting or guessing a fact. The consent subject line stays above
  them, described as the subject of consent rather than as a fourth fact
  (IMPLEMENTATION.md O3). Unpushed-commit state is not presented.
- Exactly one question round, single-select, two options, with the wording chosen by
  the current state: a grant pair when no consent is recorded, a maintain / revoke pair
  when it is.
- Dismissal or no answer takes the non-mutating branch, prints the one line saying the
  store was not changed, and exits without presenting any command.

### What changes

1. **The skill never runs a mutating command.** Every step that would have invoked
   record or remove is replaced by presenting the exact command line for the user to
   run in their own terminal. The document must contain no procedure, no fallback and
   no retry that executes either mutating command.
2. **The presented command line** is shown after the answer, on its own line, ready to
   copy: the interpreter, the owning plugin's own guard script path, the chosen
   mutating flag, and the project-directory option carrying the same directory the
   subject line named. The grant answer presents the recording command; the revoke
   answer presents the removal command. Nothing else is presented.
3. **One short line of context accompanies it**, stating that the user runs it in their
   own terminal and that running it through the agent is refused because the write path
   requires an interactive terminal. It states the requirement, never a claim that the
   store cannot be written by other means (SPEC a12).
4. **The option descriptions are re-worded** so that the part naming who performs the
   write matches the new flow — the option leads to a command being presented, not to
   the key being written by the skill. The question count, the option count, the
   state-dependent split and the labels themselves are unchanged
   (IMPLEMENTATION.md O4).
5. **The skill ends after presenting.** It does not wait for the user to run the
   command, does not re-read the store to confirm, and does not re-ask.

### Both plugins

Both documents receive the same change. Each names its own plugin's script path and
its own slash-command namespace; nothing else differs between them. No `commands/`
file is added for either (repository rule: slash commands are skills).

## Test Notes

- The assertions are document assertions: locate each section by its heading or its
  fixed label and inspect the body, rather than matching the whole file against a
  literal.
- The "never runs a mutating command itself" property needs a negative assertion that
  cannot be satisfied by wording alone: assert that the mutating flags appear in the
  document only inside a presented-command context (the command line and the sentence
  introducing it) and never inside a step the skill performs. Pin the count of
  presented command lines per state so a later edit cannot quietly add an executed one.
- Assert the read-only command is still described as run by the skill, so the negative
  assertion above cannot be satisfied by removing all CLI use.
- Assert the question round count by counting the interactive-question tool name inside
  each skill document, and assert the option count per state.
- Cross-plugin equality is asserted structurally (same sections, same labels, same
  ordering), with the plugin-naming differences explicitly allowed.
- Both documents are checked in the same parameterized case so neither can drift.
