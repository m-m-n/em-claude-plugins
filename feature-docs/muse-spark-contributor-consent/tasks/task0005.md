# Task Plan: task0005 — pin the interactive-question budget of the develop and review paths

## Goal

Guarantee mechanically that this feature adds no interactive gate to the develop or
review paths of either plugin, by pinning the current per-file occurrence counts of
the interactive-question tool name and asserting that no file's count rises.

## Requirements

NFR3, NFR6

## Scope

### Files to Create
- `tests/test_muse_consent_no_new_questions.py` — the pinned baseline and the
  not-increased assertion.

### Files to Modify

None. This task creates one test module and changes nothing else.

## Design

This is the automated static equivalent of "run develop in a project that has not
consented and observe that no new question appears". Running develop is
deliberately not the verification method; the property is a property of the
documents that drive develop and review.

### What is measured

The occurrence count of the interactive-question tool's name inside each document
that drives the develop or review execution path in either plugin. That set is
enumerated at implementation time by walking both plugin trees' documents
(the references and skills directories) rather than by hand-listing paths, so a
document added later cannot slip out of the measurement.

### How it is pinned

- A literal table in the test maps each file that currently contains at least one
  occurrence to its count at the base revision. The table is written by reading the
  base revision, not by recomputing from the working tree at test time — a
  recomputed baseline would assert nothing.
- The assertion is directional: for every file in the table the current count must
  be **less than or equal to** the pinned count; for every document outside the
  table the current count must be zero. A removal elsewhere therefore does not turn
  the test red, while any addition does.
- One documented exclusion: the `contributor-consent` skill document in each
  plugin. That skill is the out-of-band consent path, it legitimately asks exactly
  one question, and it is reachable only when a user runs it in an interactive
  session. The exclusion is named explicitly in the test rather than implied by a
  pattern.

### What the failure means

A red result means some document on the develop or review path gained an
interactive question — the unattended-run guarantee is broken and the change that
added it has to be reworked, not the baseline raised.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The test enumerates the develop-path and review-path documents of both
      plugins by walking their document directories, so no such document is outside
      the measurement. (TS-15)
- [ ] AC-2: The baseline is a literal table of per-file counts in the test source,
      and no assertion derives its expected value from the same tree it checks.
      (TS-15)
- [ ] AC-3: The assertion fails when any measured file's count exceeds its pinned
      value, and fails when any measured file outside the table contains an
      occurrence; it passes when counts are unchanged or lower. Both directions are
      demonstrated by the test's own construction (for example, by asserting the
      comparison helper's behavior on synthetic counts). (TS-15)
- [ ] AC-4: The two `contributor-consent` skill documents are the only excluded
      files, and the exclusion is stated explicitly in the test source. (TS-15)
- [ ] AC-5: The module imports no third-party package and passes under
      `python3 -m unittest discover -s tests`. (TS-15, TS-24)

## Test Notes

- This task is a test module and nothing else; its acceptance criteria are
  properties of that module.
- Count occurrences of the tool name as plain substring matches over the file's
  text — a document mentioning it in prose still counts, which is the conservative
  direction.
- Assert the comparison logic itself on synthetic inputs so that a bug in the
  helper cannot make the whole suite vacuously green.
- The excluded skill documents may not exist yet in this worktree; treat their
  absence as acceptable and their presence as excluded, so the module passes both
  before and after the skill lands.

## Out of Scope

- Modifying any document to reduce its count — this task only measures.
- Running develop or review for real, in a worktree or otherwise.
- Covering questions asked by tools other than the interactive-question tool.
- Any production file in either plugin.
