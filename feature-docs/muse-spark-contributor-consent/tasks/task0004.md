# Task Plan: task0004 — version bump for both plugins

## Goal

Raise both plugins' versions in the same change that alters their contents, keeping
each plugin manifest and its marketplace entry in agreement, so installed caches
pick the new files up.

## Requirements

FR12, NFR6

## Scope

### Files to Create
- `tests/test_muse_consent_version_bump.py` — pins the post-bump version identity
  and the floor for this feature.

### Files to Modify
- `em-workflow/.claude-plugin/plugin.json` — raise the version field only.
- `em-review/.claude-plugin/plugin.json` — raise the version field only. Another
  task may touch a different field of this same file; do not reformat it and do
  not edit anything but the version.
- `.claude-plugin/marketplace.json` — raise both plugins' entries to the matching
  values; touch no other entry.

## Design

Both plugin trees change in this feature, so both versions move. The repository's
version-bump rule applies: two places per plugin, identical values, semantic
versioning, and the increment sized to the change. This feature adds new
capability without breaking existing behavior, so a minor-level increment is the
expected size; a patch-level increment is acceptable only if the reviewer of this
change agrees the addition is behavior-preserving. Either way, the new value must
be strictly greater than the base value for that plugin.

Base values this feature starts from: em-workflow at 0.1.69 and em-review at 0.5.7.
The bump is owned by this task alone — no other task edits a version field
(IMPLEMENTATION.md Cross-task Design Decisions, D-G).

Nothing else in the manifests changes here. If hook discovery requires the
em-review manifest to declare its new hooks file, that edit belongs to the task
that creates the hooks file, not to this one.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `em-workflow/.claude-plugin/plugin.json` and the em-workflow entry in
      `.claude-plugin/marketplace.json` carry the same version string, it parses as
      a semantic version, and it is strictly greater than 0.1.69. (TS-16)
- [ ] AC-2: `em-review/.claude-plugin/plugin.json` and the em-review entry in
      `.claude-plugin/marketplace.json` carry the same version string, it parses as
      a semantic version, and it is strictly greater than 0.5.7. (TS-16)
- [ ] AC-3: No field other than the version changed in the three edited files, and
      no other marketplace entry changed. (TS-16)
- [ ] AC-4: `tests/test_muse_consent_version_bump.py` asserts AC-1 through AC-3
      using version-ordered comparison rather than string comparison, imports no
      third-party package, and passes under `python3 -m unittest discover -s tests`.
      The pre-existing plugin-version parity test still passes. (TS-16, TS-24)

## Test Notes

- Compare versions component-wise as integers; a string comparison would call
  0.1.7 greater than 0.1.69.
- Read both plugin manifests and the marketplace file, and assert the pairing per
  plugin rather than asserting one global version.
- Keep the floor values (0.1.69, 0.5.7) as literals in the test: they are this
  feature's base revision, and a test that recomputes them from the working tree
  would assert nothing.
- If a repository-wide parity test already covers manifest-to-marketplace equality,
  the new module still asserts the floors, which that test cannot know about.

## Out of Scope

- Any content change in either plugin — this task only moves version numbers.
- Editing the em-review manifest's hooks declaration, if one turns out to be
  needed.
- Publishing, tagging, or cache invalidation steps outside the repository.
