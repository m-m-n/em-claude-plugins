# Task Plan: task0008 — consent-write provenance boundary on the guard CLI

## Goal

Make the consent store unwritable from an agent's ordinary Bash call path: the two
mutating CLI commands refuse to change the store unless standard input is an
interactive terminal, and the refusal happens before any store access at all. The
read-only command stays unaffected so the skill can still report the current state.

## Provenance

- Source: create-spec amendment following the verify failure of `SC-8`. The SPEC now
  states a second enforcement surface (FR7's provenance constraint, AC-13) and two new
  scenarios (TS-29, TS-30) that no existing task covers.
- The consent-write boundary this task establishes is the one SC-8 now asks to be
  verified by automated tests.

FR1, FR7, FR10, NFR5, NFR6

## Design

The store contract, the project-key contract and the Guard CLI contract are pinned in
IMPLEMENTATION.md Shared Components. This task adds exactly one precondition to that
CLI contract — the "Consent-write provenance boundary" row — and changes nothing else
about it: the same three mutually exclusive commands, the same required project
directory option, the same output lines, the same exit codes, the same atomic write,
the same refusal to repair a malformed store.

### The precondition

`--record` and `--remove` acquire one precondition: **the process's standard input is
an interactive terminal**. `--list` does not acquire it.

When the precondition fails:

- the command changes nothing — it does not create the store file, does not create its
  parent directories, does not update, delete or repair anything, and leaves an
  existing store byte-identical;
- it exits with a non-zero status;
- it writes to stderr one short Japanese line stating that the command must be run from
  an interactive terminal. The line carries no path, no project key and no store
  content, in keeping with the feature's no-input-echo convention.

### Ordering is part of the contract

The check is evaluated **before** project-key derivation and before any store access.
Two consequences follow and both are verifiable:

- a refused run launches no git subprocess and touches no file, so a refusal in a
  directory that is not a repository behaves identically to one inside a repository;
- a refused run against a non-existent store path leaves that path non-existent.

Placing the check after argument parsing (so that argument misuse still reports
argument misuse) and before everything else is the whole of the ordering requirement.

### What the boundary does and does not claim

The interactive-terminal test is a **provenance proxy**, not proof of human operation
(SPEC a12). It establishes that an agent's ordinary Bash call path cannot record
consent. It does not establish unbypassability: a sufficiently capable agent can
allocate a pseudo-terminal or write the store through another program. The refusal
message therefore states the requirement, never a claim of impossibility, and no
message or comment added by this task asserts that the store cannot be written by other
means.

### Effect on the existing CLI test cases

Every existing case that records or removes consent — the record-then-pass-through
case, the non-repository symlink case, the worktree-identity case and the CLI round
trip — currently drives the mutating command with an ordinary pipe for standard input
and will start failing. Each of those cases is updated to allocate a pseudo-terminal for
the child's standard input, using the standard library facility for that purpose; their
expectations are otherwise unchanged. Cases that call the read-only command keep an
ordinary pipe, which is itself part of what TS-30 asserts.

## Test Notes

- Write the refusal cases first: they are the ones that fail against the current script,
  and they are what SC-8 now asks to see verified.
- The refusal side needs an explicitly non-interactive standard input — an ordinary
  pipe from the parent — not merely an inherited one, so the case is deterministic
  under any runner.
- The success side needs a pseudo-terminal allocated by the standard library facility
  for that purpose. Read the child's output through the same channel and guard the case
  with a timeout so a hung child fails rather than hangs.
- Assert the no-write property two ways: the store path still does not exist in the
  absent-store case, and the file's bytes are identical in the existing-store case.
  Byte comparison, not a parsed comparison, is what pins "not repaired".
- Assert the ordering property behaviorally rather than by inspecting source: run a
  refusal with a project directory that is not a repository and confirm it behaves the
  same as inside one, which can only hold if key derivation never ran.
- Keep the new cases in their own test group with a distinctive name, so the parallel
  recognition task's additions and these cannot collide in the same region
  (IMPLEMENTATION.md D-J).
- Every case points the store-path override under a temporary directory; none resolves
  the real user store path.

## Out of Scope

  model-selection matching. Those belong to the parallel task and must not be touched
  here.
- The deny payload text, the hook registration, the store shape, the project-key
  derivation rule, and the malformed-store refusal behavior (all unchanged).
- The `contributor-consent` skill. Its rewrite to present the mutating command instead
  of running it is a separate task; this task only provides the CLI behavior that
  rewrite relies on.
- Any change to SPEC.md or REQUIREMENTS.md.
- Any version-field edit (IMPLEMENTATION.md D-G).
- Any attempt to make the boundary unbypassable — detecting pseudo-terminals,
  inspecting the parent process, or otherwise guessing at provenance. SPEC a12 accepts
  the residual; widening the check would add false refusals without closing it.
