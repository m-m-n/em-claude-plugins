# Task Plan: task0005 — Provider fallback chain inside the Codex wrapper

## Goal

`em-workflow/scripts/run_codex_exec.sh` survives a provider outage on its own:
it tries a three-entry provider chain in order, switching on a usage-limit
response and on a provider error, while every other failure surfaces unchanged
and no protocol document learns that any of this exists.

## Requirements

FR13, NFR4, NFR9

## Scope

### Files to Create

- `tests/test_codex_wrapper_provider_fallback.py` — subprocess-driven tests of the chain, driven against a stubbed command on PATH

### Files to Modify

- `em-workflow/scripts/run_codex_exec.sh` — the provider chain, its switch
  conditions and the fallback report line

## Design

**The chain.** Three entries in fixed order: the current default provider
first, then the second, then the third. Each entry is a named provider
configuration the script applies to its invocation of the underlying CLI; the
entries differ from one another in the arguments the script passes, so an
observer of the invocation can tell which entry is being attempted. The order,
the entry definitions and the switch conditions live in this script and nowhere
else (IMPLEMENTATION.md D3), so adding or reordering a provider needs no
protocol-document edit.

**Switch conditions.** Entry 1 hands over to entry 2 when its response is a
usage-limit response. Entry 2 hands over to entry 3 when its invocation reports
a provider error. Any other non-zero outcome — including the existing timeout
case with its diagnostic and its exit code — is NOT a switch condition: it
surfaces to the caller exactly as it does today, and the chain stops there.
When the last entry also fails, the caller sees that entry's outcome; the
wrapper never substitutes a synthetic success.

**Report line.** Per the Shared Components contract: on the first entry the
wrapper's output is byte-identical to today's, with no marker of any kind. When
and only when a later entry produced the answer, the wrapper writes exactly one
additional line to stderr, carrying a fixed prefix declared in the script's own
header comment, naming which entry answered. Nothing is ever added to stdout,
so existing consumers of the answer text are unaffected.

**Invocation surface.** The script's own argument surface does not change: the
mode argument, the working-directory flag, the output-schema flag and the
prompt keep their present form and order, because the reviewer agents' wrapper
invocation line is pinned byte-for-byte by an existing test. No new required
argument, no new environment variable requirement, no change to the
configuration file's parsed keys.

**Timeout.** Each attempt keeps the configured per-invocation timeout, so a
worst-case three-attempt run can take up to three times as long as a single
attempt. This is accepted, not mitigated (IMPLEMENTATION.md D3).

**Provider-name discipline.** Provider names appear in this script and in this
task's own test module only. The batch resolution document set — the six
documents IMPLEMENTATION.md C3 names — must contain none of them, and this
task's test asserts that property over exactly that six-document set, never
repository-wide: the review reviewer chains legitimately name providers
elsewhere and a wider assertion would fail against them.

**How the tests reach the script.** The test module runs the real script as a
subprocess with a stub executable placed first on PATH in a temporary
directory. The stub inspects the arguments it receives to decide which chain
entry is being attempted and replies accordingly: a usage-limit response for
entry 1, a provider error for entry 2, a success for entry 3. No network access
and no real provider are involved.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The wrapper tries the three chain entries in the fixed order, and
      the order, the entry definitions and the switch conditions exist only in
      this script. (FR13)
- [ ] AC-2: A usage-limit response from entry 1 causes entry 2 to be attempted,
      and a provider error from entry 2 causes entry 3 to be attempted;
      driven end to end through the stubbed command. (FR13)
- [ ] AC-3: A failure that is not a switch condition — including the timeout
      case with its existing diagnostic and exit code — surfaces to the caller
      unchanged, and no further entry is attempted. (FR13)
- [ ] AC-4: The script's argument surface is unchanged, asserted by the
      existing byte-for-byte invocation-line pin still passing untouched, and
      by a direct run in the invocation form the consultation procedure uses.
      (FR13)
- [ ] AC-5: On the first entry the wrapper emits no marker at all and its
      stdout is byte-identical to the stub's answer; when a later entry
      answered, exactly one additional line appears on stderr with the declared
      prefix, and stdout still carries only the answer. (FR13)
- [ ] AC-6: None of the six batch resolution documents contains a provider name
      or a description of usage-limit detection; the assertion is scoped to
      that document set and a negative proof shows it would fail on a forged
      sample. (NFR4)
- [ ] AC-7: The tests use a stubbed command on PATH, contact no network and no
      real provider, import only the standard library, and the full suite
      passes. (NFR9)

## Test Notes

Integration-style but hermetic: every assertion runs the real script against a
stub. Write the stub and the entry-1 success path first (it must reproduce
today's behaviour exactly), then the two switch cases, then the
non-switch-failure case.

Edge cases worth covering: the last entry failing (the caller sees that
entry's outcome, not a synthetic success); a usage-limit-shaped response
arriving from entry 2 rather than entry 1; and stdout cleanliness on the
fallback path.

TDD-awkward: the usage-limit response and the provider error are recognized
from the underlying CLI's output, so the stub's replies define what the script
must recognize. Fix those two shapes in the test module first and treat them as
the contract the script is written against.

## Out of Scope

- Any protocol document. The one sentence stating that the wrapper may answer
  from a fallback provider belongs to the resolution SSOT and is written by
  another task.
- Changing the wrapper's mode vocabulary, its sandbox flags, its reasoning
  effort handling or its configuration file's parsed keys.
- Any change to the reviewer agents or to their invocation line.
