# Task Plan: task0006 — Plugin version bump for both registries

## Goal

The em-workflow plugin manifest and the marketplace entry that points at it
carry the same new patch version, so an installed copy of the plugin actually
picks up this feature's changes instead of serving a stale cache.

## Requirements

FR23, NFR9

## Scope

### Files to Create

- `tests/test_batch_codex_autonomous_decisions_version_bump.py` — the version parity and past-baseline assertions for this feature

### Files to Modify

- `em-workflow/.claude-plugin/plugin.json` — the version field
- `.claude-plugin/marketplace.json` — the em-workflow entry's version field

## Design

This feature changes plugin content (protocol documents, one script, fixtures),
so the repository's version-bump rule applies: bump in the same change, in both
places, to the same value. The step is patch-level, per assumption A7 — this is
a behaviour correction and adds no new plugin surface. The pre-task baseline in
both registries is the same value; the new value keeps the major and minor
components and raises only the patch component.

Exactly one task owns these two files (IMPLEMENTATION.md C9), so the two
registries can never disagree through a parallel merge.

The test module follows the pattern the repository's existing version-bump
modules established:

1. Compare versions as a dot-separated numeric tuple, never as whole strings,
   so a future two-digit patch component still sorts correctly.
2. Locate the marketplace entry by its `name` field, never by array index, and
   guard the lookup so a missing entry fails instead of vacuously passing.
3. Pin the other plugin's marketplace entry at its pre-task value, so this
   bump is proved not to have moved it.
4. Prove each matcher against forged samples — one left at the baseline, one
   where the two registries disagree — with a well-formedness guard showing the
   forged sample itself parses.
5. Import only the standard library.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The plugin manifest's version parses as major.minor.patch, keeps
      the baseline major and minor, and has a patch strictly greater than the
      baseline patch. (FR23)
- [ ] AC-2: The marketplace entry for this plugin, looked up by name, carries
      exactly the same version string as the plugin manifest. (FR23)
- [ ] AC-3: The other plugin's marketplace entry version is unchanged from its
      pre-task value. (FR23)
- [ ] AC-4: The marketplace lookup fails loudly when the named entry is absent,
      proved against a forged sample, with a companion assertion showing the
      lookup succeeds when the name is present. (FR23)
- [ ] AC-5: Each matcher has a negative proof against forged data plus a
      well-formedness guard, the module imports only the standard library, and
      the full suite passes. (NFR9)

## Test Notes

Pure unit tests over two JSON files. Write the module first with the baseline
constants set to the current values and watch the past-baseline assertions
fail, then edit the two registries.

Edge case worth covering: a naive string comparison would order a two-digit
patch component wrongly, so assert on the parsed numeric tuple and include a
forged sample that would pass a string comparison but must fail the tuple one.

## Out of Scope

- Any other file's content, including the plugin descriptions in either
  registry.
- The other plugin's version.
- Regenerating or reinstalling the plugin cache; reporting that a restart is
  needed belongs to the run report, not to this task.
