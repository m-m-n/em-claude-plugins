# Task Plan: task0002 — Audit record and run-report coverage for the relaxed route

## Goal

Every resolution taken through the batch relaxed route leaves one batch audit
record whose writer, `question_id` rule and commit reach-point are stated in
`references/phase-state.md`, and appears both in `references/batch-mode.md`'s
run-report required contents and in its audit-item source map.

## Requirements

FR14, FR15, FR16, FR21, NFR1, NFR3, NFR4, NFR5, NFR9

## Scope

### Files to Create

None — this task modifies existing files only.

### Files to Modify

- `em-workflow/references/phase-state.md` — the Batch audit record file
  section gains the relaxed route as a writer, with its identifier rule, its
  source values and its commit reach-point
- `em-workflow/references/batch-mode.md` — the run-report required contents
  and the audit-item source map each gain the autonomous resolutions
- `tests/test_batch_quiet_output_audit_record_contract.py` — the writer-count

- `tests/test_phase_state_doc.py` — any assertion over the Batch audit record
  file section that the writer addition moves

## Design

This task owns the L2 half of the audit trail: where the record is defined and
where the report says it must be carried out. The route that produces the
record is stated elsewhere (IMPLEMENTATION.md layer L1) and is cited here by
path, never restated.

**phase-state.md — Batch audit record file.** The writers list gains one
entry for the batch relaxed route. The existing list is introduced by a
sentence naming how many writers there are; that count moves up by one and the
sentence is updated in place. The new entry states:

1. Which resolutions it covers — every resolution reached through the relaxed
   route, whether the mapping came from the consultation, from the Opus
   escalation, or from the minimum-side-effect fallthrough.
2. Its `question_id` rule — the question's own `question_id` when a worker
   packet exists; the gate's own `gate_id` when the gate was
   orchestrator-opened with no worker-minted identifier. Both conform to the
   `question_id` pattern `question-packet-schema.md` owns.
3. Its `source` values — drawn from the existing closed vocabulary:
   `batch-codex-consultation` when a suggestion mapped onto an option,
   `batch-safe-default` when the minimum-side-effect branch was taken.
4. Its `resolution_note` contents — per the Shared Components contract in
   IMPLEMENTATION.md: the gate, the option chosen, the options not chosen, the
   discussion's key points, whether Codex was consulted, whether a fallback
   provider answered, and whether the Opus escalation ran together with its
   reasoning.
5. Its commit reach-point — the record is appended at resolution time and
   committed by the enclosing phase step's next existing docs commit, the same
   reach-point the other in-step writers use. No new commit is created for it.

The record's per-field SHAPE does not change: no field is added, none is
removed, and the append-only rule stands. `packet_id` follows the existing rule
for the orchestrator-opened case.

**batch-mode.md — Reporting.** The required contents of a batch run's final
report gain one item: the autonomous fail-closed-route resolutions, each with
the gate, the option chosen, the options not chosen, the discussion's key
points, whether Codex was consulted, whether a fallback provider answered, and
whether the Opus escalation ran with its reasoning. The wording stays
provider-agnostic (IMPLEMENTATION.md C3).

**batch-mode.md — audit-item source map.** Exactly one row is added, pairing
the new report item with its persisted source: the feature's batch audit record
file, `records[]` / `records[].resolution_note`, with a path citation to
`references/phase-state.md`. Every other row is untouched, so the map keeps its
one-row-per-item property.

**Quiet output is untouched.** The suppression list, the marker line's prefix
and grammar, the terminal line's prefix and value sets, and the exceptions list
all stay exactly as they are (NFR5).

**Notion is out of scope.** em-workflow's obligation ends at the run report;
nothing in either document instructs any operation against an external service
(A6).

## Test Notes

Unit-level document pins only. Write the updated count assertions first and
observe them failing against the current documents before adding the prose, so
each count is verified to be load-bearing.

Edge case worth pinning: the `question_id` rule's two branches (worker packet
present vs orchestrator-opened gate) — assert both halves, since a single-branch
pin would pass on a document that mentions only one.

`tests/test_phase_state_doc.py` is listed because it asserts over the same
section and may hold a heading-adjacency or ordering assertion the writer
addition moves; if it turns out untouched, leave it unmodified.
