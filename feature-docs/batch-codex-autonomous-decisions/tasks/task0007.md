# Task Plan: task0007 — Make the wrapper's fallback entries resolvable and restore the chain

## Provenance

- Source: review, round 1
- Findings: `3af4ecb279d5fd40` (critical), `0c57632ebedaa31f` (high),
  `95ed359e6b7cc02b` (high)

All three sit on `em-workflow/scripts/run_codex_exec.sh` and its one test
module, and share a single root cause: the chain was implemented against a
placeholder contract. Entries 2 and 3 select provider names nothing defines,
and the switch conditions and the test stub disagree about which stream
carries the shapes that trigger a switch. Neither half can be fixed without
the other — changing the stream contract changes what the stub must emit, and
changing the entries changes what each attempt's invocation carries — so they
are one task.

## Requirements

FR13, NFR4, NFR7, NFR9

## Scope

### Files to Modify

- `em-workflow/scripts/run_codex_exec.sh` — the chain's entry definitions,
  the stream the switch conditions read, and the header comment that declares
  both
- `tests/test_codex_wrapper_provider_fallback.py` — the stub's response
  shapes and streams, the per-entry invocation assertions, and the
  spoofing/unconfigured negative proofs

## Design

**What is wrong today.** Entries 2 and 3 pass only a provider *selection*
(`model_provider="…"`) naming identifiers that exist nowhere: no provider
definition is passed, and the same invocation suppresses the user
configuration file that could otherwise supply one. Every switch therefore
lands on an undefined provider and can only fail. The test suite does not
catch this because the stub decides its identity by matching argument text
and never reads a provider definition. Separately, a round-1 auto-fix
narrowed both switch conditions to the attempt's stderr while the stub emits
both shapes on stdout, so under the module's own harness the chain never
advances: five of its tests fail on the integration branch today.

**Entry definitions must be self-sufficient.** Each non-primary entry's
invocation carries everything needed to reach that entry's provider — the
selection *and* the definition behind it (endpoint, wire protocol, auth key
source) and the model — so that the invocation does not depend on any
configuration source the same invocation suppresses. The chain's order is the
order the specification names: the primary entry unchanged, then the
Vertex-fronted model, then the Muse-fronted model.

**Where the definition comes from.** The wrapper does not invent a second
description of a deployment it does not own. The non-primary entries reuse
the environment contract the review chain already depends on — the same proxy
profile and auth environment variable `references/review-phase.md`'s harness
probe already checks for — and the script reads that contract at invocation
time rather than embedding endpoint knowledge of its own. What the script
*does* own, and states in its header comment, is which environment inputs the
non-primary entries require and what happens when they are absent.

**Fallback prerequisites absent.** When a switch condition fires but the
non-primary entry's environment prerequisites are not present, the wrapper
does not launch an invocation that can only fail: it stops the chain, leaves
the caller with the failing entry's own outcome and exit code, and writes one
stderr diagnostic saying the fallback entry was not configured. An operator
can then tell "the fallback was never available" from "the fallback was tried
and failed" — which is exactly the distinction the placeholder chain
destroyed.

**The stream contract.** A switch is decided only from output the underlying
CLI itself writes as a diagnostic, never from the model-generated reply text,
which quotes the reviewed repository and is attacker-influenceable. That
security property is not negotiable and is what the stderr-only rule exists
for; this task keeps it. What changes is that the contract stops being
implicit: the script's header comment declares which stream carries a switch
shape, and the test module's stub emits those shapes on that same stream, so
the harness and the script state one contract instead of two. The exit-code
gate is retained — a text match alone never switches, and a timeout's exit
code is never mistaken for either shape.

**Switch positions unchanged.** Entry 1 hands over on a usage-limit response;
entry 2 hands over on a provider error. Whether either condition should apply
at every non-terminal entry is a separate, unaccepted question and is not
decided here.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Each non-primary chain entry's invocation carries a resolvable
      provider definition — the selection plus the definition fields and the
      model behind it — and carries no flag that suppresses the source that
      definition depends on. Asserted per entry against the recorded
      invocation arguments, not against a provider name alone. (FR13)
- [ ] AC-2: The two non-primary entries resolve to distinct providers, in the
      order the specification names (primary, then the Vertex-fronted model,
      then the Muse-fronted model), asserted from the recorded invocation
      arguments of the second and third attempts. (FR13)
- [ ] AC-3: The script's header comment declares which stream carries a
      switch shape and which environment inputs the non-primary entries
      require; the test module's stub emits both switch shapes on that
      declared stream. (FR13, NFR4)
- [ ] AC-4: Driven end to end through the harness, a usage-limit response at
      entry 1 causes entry 2 to be attempted and a provider error at entry 2
      causes entry 3 to be attempted; entry 3's answer is the only content on
      stdout, and exactly one stderr line with the declared prefix names the
      answering entry. (FR13)
- [ ] AC-5: An attempt that fails with either switch shape present ONLY in
      the model-generated reply text never advances the chain — a negative
      proof that a repository or a model reply cannot force a provider
      switch. (NFR7)
- [ ] AC-6: When a switch condition fires but the non-primary entry's
      environment prerequisites are absent, no further invocation is
      attempted, the caller receives the failing entry's own exit code and
      output, and one stderr diagnostic states that the fallback entry was
      not configured. (FR13)
- [ ] AC-7: Non-switch outcomes are unchanged: the timeout keeps its existing
      diagnostic and exit code, an unrelated error surfaces verbatim and
      stops the chain, a provider error at entry 1 does not advance, and a
      usage-limit response at entry 2 does not advance. (FR13)
- [ ] AC-8: None of the six batch resolution documents names a provider or
      describes usage-limit detection, asserted over exactly that document
      set with a negative proof against a forged sample, and the assertion's
      marker list matches the identifiers the script actually uses. (NFR4)
- [ ] AC-9: `python3 -m unittest discover -s tests` exits 0, including every
      test in `tests/test_codex_wrapper_provider_fallback.py`; every pin this
      change invalidates is replaced at equal specificity rather than
      deleted. (NFR9)

## Test Notes

The module stays hermetic: the real script runs as a subprocess against a
stub executable placed first on PATH, with no network and no real provider.

Order of work: fix the stream contract first (declare the stream, move the
stub's shapes onto it) so the five currently failing tests turn green and the
chain is observably advancing again; only then change the entry definitions,
so an entry-definition regression cannot hide behind a chain that never
advances.

AC-1/AC-2 are argument-surface assertions over the stub's recorded
invocation log, one assertion per non-primary attempt. Assert the presence of
the definition fields, not a literal argument string, so the assertion does
not become a second copy of the script.

AC-5 needs a stub behaviour that writes a switch shape to the reply stream
while failing — distinct from the shapes on the declared diagnostic stream.
AC-6 needs the harness to control the environment prerequisites explicitly:
set them for the chain-advancing cases and unset them for AC-6, so neither
outcome depends on whatever the developer's machine happens to have.

Edge cases already covered by existing tests and to be kept: last-entry
failure surfaces that entry's outcome rather than a synthetic success; stdout
carries no earlier failed attempt's text; the primary path emits no marker at
all.

## Out of Scope

- Any protocol document. The documents state only that the wrapper may answer
  from a fallback provider; naming a provider there would break NFR4.
- Making the switch conditions apply at every non-terminal entry (the
  position-bound behaviour reported separately at medium severity).
- The wrapper's own argument surface — mode, working directory flag,
  output-schema flag, prompt — and the reviewer agents' invocation line.
- A further plugin version bump: this feature's bump is already past the
  pre-task baseline and its parity test still holds.
