## Design

**Fact 1 — which aborts survive.** The surviving-aborts enumeration currently
sweeps in "the Classification gate's step-3 origin-verification failures".
Step 3 structurally contains both directions, and direction 2 is explicitly
relaxed in batch, so a batch question whose bound-set category is `security`
is described as both aborting and taking the relaxed route. SPEC FR3 scopes
the survivor precisely: direction 1 only — an `origin_id` that is absent,
unresolvable, or not a member of the bound set. The enumeration is narrowed to
say exactly that. Direction 1's own final-and-non-overridable wording is
untouched, and so is direction 2's relaxation paragraph; only the enumeration
that names them from a distance changes.

**Fact 2 — where the batch direction-2 continuation is decided.** The same
routing fact — in batch, a routed question that trips direction 2 leaves the
Classification gate, joins the packet's batched consultation, and may reach
the fallback and `on_unanswered` from there — is presently narrated in the
Batch resolution sequence's step 2, in the Unlisted-gate fallback's step 3,
and again in the `block` branch. It is stated ONCE, at a single site, and the
other two cite that site. The `block` branch is reduced to what it owns: the
minimum-side-effect action it takes, plus pointers for the facts it does not
own (which questions were aborted upstream and by which rule, and which were
removed from the sequence by the routed arm). No statement of the two-mode
split is lost — it moves to one place and is cited from the others (NFR1,
IMPLEMENTATION.md C1).

**Fact 3 — what an autonomous decision's `source` says.** The escalation step
records every escalation decision as a consultation answer, while the
escalation also runs on the path where the availability probe reported the
wrapper unavailable and no consultation turn happened at all; the record then
asserts something false, which is exactly what an operator auditing an
unattended decision must be able to rely on (SPEC US5/FR14). The record shape
and its value mapping are `phase-state.md`'s subject, so the repair lands
there: its relaxed-route writer entry states the complete three-way mapping —
a mapping produced by the consultation, a decision made by the single
escalation, and the minimum-side-effect fallthrough — instead of covering only
two of the three paths it already claims to serve.

**The vocabulary stays closed at its present values.** No new `source` value
is minted. SPEC FR14 and the Database Schema table state this route's closed
vocabulary as the two existing values, and the schema document's vocabulary
list and the validator's constant are behaviourally frozen for this feature
(FR19, IMPLEMENTATION.md D5). What was missing is not a value but a complete
mapping plus an unambiguous note: `resolution_note` already must state whether
Codex was consulted, whether a fallback provider answered, and whether the
escalation ran with its reasoning (FR14), so the escalation case is
distinguishable in the record without widening the vocabulary. Accordingly the
writer entry defines its value for the escalation case in terms of the route
that produced the decision, never as a claim that Codex was consulted, and the
document carries no remaining sentence that defines the value in a way this
entry contradicts.

**Consistency direction.** `phase-state.md` owns the record shape and the
value mapping; `question-resolution.md` states the obligation to append and
cites that path (IMPLEMENTATION.md, Shared Components). The escalation step
therefore stops asserting a value that the mapping does not support, and
points at the mapping instead of restating it.

**Pin discipline.** Every sentence removed here is pinned by an exact
substring in at least one of the five test modules above. Each such pin is
replaced at equal specificity — a positive pin on the new wording plus a
negative proof that the superseded wording is gone — and every counting
assertion is updated to its new count. No pin is deleted (IMPLEMENTATION.md
C4, C5).

## Test Notes

All ten criteria are document-pin unit tests, run by the existing modules
listed in Scope. Work module by module in the order the facts are listed
above: each edit invalidates one or more exact substrings, so update the
pin in the same step as the sentence, never in a later pass.

The single-statement criterion (AC-3) needs a counting assertion, not a
presence assertion: a presence assertion passes on a document that states the
fact three times, which is the defect being fixed. Pair it with a positive pin
on the one statement site and citation pins at the two citing sites.

AC-7 and AC-8 are cross-document assertions and are the ones a single-document
pin cannot catch — assert the escalation case from both documents in one test
so a later edit to either side fails it.

Edge case worth a dedicated test: a batch question that trips direction 2
must be traceable, by reading the document alone, from the gate to the
consultation and to the fallback branch that resolves it, with no passage
claiming it aborts and none claiming it never arrives.
