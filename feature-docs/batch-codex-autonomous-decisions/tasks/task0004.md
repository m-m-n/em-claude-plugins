# Task Plan: task0004 — Packet-schema rationale, validator message, and the irreversibility fixture

## Goal

The `on_unanswered: block` constraint and the validator check behind it survive
byte-identical in behaviour with only their rationale reworded, and a
question-packet fixture carrying an assumptions entry declared irreversible is
accepted by the validator both directly and through the fixture-corpus sweep.

## Requirements

FR18, FR19, FR20, FR21, NFR1, NFR2, NFR8, NFR9

## Scope

### Files to Create

- `em-workflow/references/fixtures/question-packet/category-fail-closed/valid-irreversible-assumption-blocking/input.json` — a valid question packet whose assumptions entry names the question and declares the operation irreversible

### Files to Modify

- `em-workflow/references/question-packet-schema.md` — the rationale sentence
  after the constraint; the constraint itself stays verbatim
- `em-workflow/scripts/validate-worker-output.py` — the rejection message's
  parenthetical rationale only
- `tests/test_validate_worker_output.py` — the new fixture's direct assertion
  and the message-rationale pin

## Design

**question-packet-schema.md.** The sentence stating that a question whose
`category` is `spec-change`, `security` or `license` must carry
`on_unanswered: block` is kept word for word. Only the rationale around it is
reworded: the constraint no longer means "the batch run will abort", it means
that in batch `block` routes the question into the minimum-side-effect branch
rather than letting a worker choose `record_tbd` or `use_batch_policy` for it.
The existing path citation to `references/question-resolution.md` for the
resolution-time rule stays, and no condition of that rule is restated here
(IMPLEMENTATION.md C1). No `taskNNNN`-shaped identifier is introduced (C2).

**validate-worker-output.py.** The blocking-required category set and the
`on_unanswered != "block"` rejection are frozen (IMPLEMENTATION.md D5). The
only edit is the parenthetical rationale inside the rejection message, which
currently justifies the check by the batch abort; it is reworded to the reason
that survives — a worker must not be able to choose the non-blocking handling
for these categories. No accept/reject behaviour changes anywhere, and the
frozen gate-registry derivation is untouched (C8).

**The fixture.** A question-packet-kind fixture in the existing
`question-packet/category-fail-closed/` branch group (IMPLEMENTATION.md D4 —
every group must hold both a valid and an invalid case, and that group already
does). Its content:

1. One question, well-formed under the packet schema, whose `on_unanswered` is
   `block` and whose `category` is a value that does not by itself trigger the
   blocking-required check, so the fixture exercises the irreversibility
   declaration rather than the category rule.
2. One assumptions entry whose `related_question_ids` names that question,
   carrying an impact value from the validator's impact vocabulary and a
   reversibility declaration of boolean false.
3. Whatever envelope fields the question-packet fixture kind requires, matching
   the sibling fixtures in the same group.

Expected outcome: exit 0, both when the validator is run against the fixture
directly and when the corpus sweep runs it by directory-name convention.

## Test Notes

Two kinds: document pins for the schema document, and subprocess-driven
validator runs for the fixture. Write the fixture's direct-run assertion first
and watch it fail with a missing-path error before creating the fixture file.

Edge cases worth covering: the fixture must NOT rely on a category that already
forces `block`, or it would pass for the wrong reason — assert that the
question's category is outside the blocking-required set. The negative side is
already covered by the group's existing invalid case; do not weaken it.

TDD-awkward: the message-rationale pin asserts on an error string. Pin a stable
fragment of the new rationale, not the whole message, so unrelated formatting
does not make it brittle.

## Out of Scope

- Any behavioural change to the validator, including the blocking-required
  category set, the rejection condition and the gate-registry derivation.
- The resolution-time rule itself; this task only cites it.
- Adding a new fixture branch group or changing any existing fixture.
