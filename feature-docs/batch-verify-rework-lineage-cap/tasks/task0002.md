# Task Plan: task0002 — cap 到達走行の継続（停止条件・Step C 実行条件・終端行）

## Goal

verify が cap 到達により `failed` のままである batch 走行が、Step B の停止条件
に捕まらず retrospect と Step C（完了処理）まで到達し、worktree 掃除と終了報告
を経て、機械可読な終端行として報告される状態にする。

## Design

### 1. batch 専用の独立条項（FR7 / IMPLEMENTATION.md D4）

既存の自動再エントリ carve-out（「フェーズプロトコルが自動再エントリのために
設定した `needs_update`」限定で、対象遷移を「厳密に次の 2 つ」と網羅的に宣言
しているブロック）には**一切触れない**。代わりに batch 専用の独立条項を新設
する。

新条項が定めること:

1. 適用条件 — batch モードであり、かつ verify が系譜 cap または hard cap の
   到達により `failed` であること。この 2 つが揃ったときにのみ適用される。
2. 停止条件 3（ある step の status が `failed` なら停止）に対する例外 — この
   `failed` を停止理由にしない。
3. 停止条件 1（全 step が `completed` でないとターンを終えられない）に対する
   例外 — verify がこの理由で `failed` のままであっても、retrospect の完了後に
   Step C へ進み、走行を完了させてよい。
4. 非適用の明示 — 上記以外の理由による `failed`（implement の失敗、review の
   失敗、cap 未到達の verify 失敗）には適用されない。interactive にも適用され
   ない。
5. `verify.status` は `failed` のままであり、別 status も `deferred` も導入
   しないこと。

配置の制約（既存テストを壊さないため）:

- 新条項は既存 carve-out ブロックの**外側**に置く。既存テストは carve-out
  ブロックを「停止条件 3 との優先関係」ラベルから「create-plan が
  `in_progress` を経ない理由」ラベルまでの範囲として切り出し、その範囲に
  対して非存在アサーションを持つため、範囲内への追記は既存テストを壊し得る。
- 条件 3 の箇条書き（「ターンを終わらせていい唯一の条件」の 3 番）は、既存
  テストが「`create-plan` という語を含まない」「停止条件 3 の優先関係ラベルを
  参照している」ことを固定している。追記する場合はこの 2 性質を保つ。
- 既存テストモジュール `tests/test_develop_skill_rewiring.py` は本タスクの
  `files` に含まれない。同モジュールを無改変のまま通すことが本タスクの受け入れ
  条件である。

### 2. Step C の実行条件（FR6）

Step C の実行条件は見出し文字列そのものに埋め込まれている（現行:「全 step
completed — design のみ skipped 可 — 時のみ」）。この条件を、cap 到達により
verify が `failed` のままである場合も Step C に入れる形へ書き換える。書き換え
は見出し行の変更を伴う。

- 新しい見出し文字列は本タスクが確定する。確定した文字列を SKILL.md の見出し
  行と、2 つのテストモジュールの見出し定数の計 3 箇所に**一字一句同一**で
  反映する（IMPLEMENTATION.md の Shared Components）。
- 見出し以外の Step C 本文（手順 1 の三択、手順 2 の worktree 掃除、手順 3 の
  終了報告）は本タスクでは変更しない。手順 1 の推奨デフォルトの条件付き変更は
  task0004 の担当。
- Step C に入った走行では、`verify.status` が `failed` であっても手順 2 の
  `git worktree remove` と手順 3 の終了報告が通常どおり行われる。この点は
  既存の本文で既に成立しているため、追加の記述は不要（実行条件だけが障害
  だった）。

### 3. cap 到達走行の終端行（FR11 / IMPLEMENTATION.md D5）

「## バッチ終端行」節に、cap 到達走行の終端状態を明記する。

- `state=stopped` / `step=verify` / `reason=verify_rework_cap_reached`。
- `detail` には「Step C まで到達し、worktree 掃除と終了報告は完了した」旨を
  含める。
- 通常完了の終端状態（`state=completed`）は使わない。外部サービスが cap 到達
  走行を成功と誤判定しないため。
- 終端行は 1 走行につき 1 行。cap 到達走行では Step C の完了報告の直後に
  出力する。
- `references/batch-terminal-line.md` は**変更しない**。同ドキュメントは
  stop point `verify-rework-cap` を reason code `verify_rework_cap_reached` に
  既に束ねており、その stop point の所有ドキュメントは SKILL.md であるため、
  SKILL.md 側の記述だけで整合する。
- 既存の「## バッチ終端行」節の記述（対象の列挙、非終端ターンで行を出さない
  規則、出力直前に SSOT を Read する指示）は保持する。既存テストはこの節に
  対して存在アサーションのみを持つため、追記は安全。

## Test Notes

- TS6（Step C 実行条件）: 新しい見出し文字列が SKILL.md に存在すること、旧
  見出し文字列が存在しないこと、そして 2 つのテストモジュールの定数が新見出し
  と一致することを検査する。定数の一致検査はテキスト比較で行い、対象モジュール
  を import しない（import すると、そのモジュールのテストが二重に走る）。
- TS15（停止条件・終端行）: 新条項の存在と、その適用条件（batch かつ cap 到達
  による `failed`）が両方述べられていることを検査する。既存 carve-out ブロック
  の範囲を切り出し、そこに新条項の語が入り込んでいないことを非存在アサーション
  で確かめる（配置の制約を機械的に固定する）。
- 終端行の検査は「## バッチ終端行」節を切り出して行う。`reason` の値は
  `references/batch-terminal-line.md` が定義するコードと同じ文字列であること
  だけを確かめ、同ドキュメントの内容自体はアサートしない（変更しないファイル
  に対する不要な結合を避ける）。
- TDD 上の注意: AC-5 は既存モジュールの定数を書き換えるまで赤にならない。
  先に新しい見出し文字列を決め、テスト側の期待値として書いてから SKILL.md と
  既存定数を更新する順で進める。
- エッジケース: `--once` を併用した走行では終端行を出すターンが Step C の
  ターンになる。本タスクは「cap 到達走行の終端状態は `step=verify`」とだけ
  述べ、`--once` 併用時のターン割りには言及しない（IMPLEMENTATION.md の
  Open Questions 参照）。
