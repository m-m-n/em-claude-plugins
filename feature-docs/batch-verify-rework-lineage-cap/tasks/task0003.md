# Task Plan: task0003 — retrospect への失敗項目の引き渡しと follow_up_drafts

## Goal

verify の失敗項目と証拠が retrospect.yaml に構造付きで引き渡され、cap 到達時に
未解決で残った項目が `follow_up_drafts` として機械可読な定型で出力される状態に
する。外部サービスへの引き継ぎを自動化可能にすることが目的。

## Requirements

FR4, FR5, NFR6, NFR3, NFR4, NFR5

  （TS4 / TS5 / TS13 と負の証明）

### Files to Modify

  自動・承認不要）」節のみ。retrospect.yaml のスキーマ例と、その周辺の説明文

## Design

### 1. `signals.verification_failures` の構造確定（FR4）

現行の retrospect.yaml スキーマ例では `verification_failures` がキーのみで
下位構造を持たない。verify フェーズの `failed_items` をそのまま載せる形で構造を
確定させる。

- 各項目は verify が workflow.yaml に記録した `failed_items` の要素をそのまま
  写す。項目が持つフィールドの定義元は `references/workflow-schema.md` の
  `failed_items` の記述であり、ここで再定義しない（`category` の閉じた語彙も
  同様に参照にとどめる）。
- 検証の証拠（ビルド・フォーマット・非 race 実行等の結果）が同じ項目から読み
  取れることを、スキーマ例の周辺の説明文で述べる。
- 他の `signals.*` キー（`review_critical_high`、`conflict_reworks`、
  `file_prediction_misses`、`discretionary_perspectives`、`declined_findings`）
  と `lessons_candidates` は現行のまま保持する。

### 2. `follow_up_drafts` の新設（FR5 / IMPLEMENTATION.md D6）

retrospect.yaml のトップレベルに `follow_up_drafts` を新設する。

| フィールド | 内容 |
|---|---|
| `origin_kind` | 由来の種別。対の意味は `references/rework-task-synthesis.md` Invariant 6 が定義済みのものをそのまま使う |
| `origin_id` | 由来の識別子。同上 |
| `title` | 1 行の要約 |
| `body` | 再現手順・証拠・該当箇所 |

生成母集団（本フィーチャーで確定した仮定）:

- **cap 到達時点で未解決の `failed_items` 全件**を母集団とする。系譜 cap に
  触れた ID かどうかで絞り込まない。
- 絞り込まない理由をスキーマ例の周辺で 1 行述べる必要はないが、母集団が
  「未解決の `failed_items` 全件」であることは明記する（絞り込みの解釈が
  後から入り込まないようにするため）。
- cap 到達が起きていない走行（verify が `completed`）では母集団が空になり、
  `follow_up_drafts` は空リストになる。

`origin_kind` / `origin_id` の対は Invariant 6 を**参照**するだけで、値の
一覧や意味をこの節に書き写さない（`references/rework-task-synthesis.md` は
NFR2 により変更禁止であり、その定義を複製すると SSOT が二重化する）。

### 3. 未信頼入力扱いの引き継ぎ（NFR6）

`title` / `body` は `failed_items` と VERIFICATION.md のシナリオ本文から生成
される。verify フェーズが既にこれらの入力に課している未信頼入力扱いを、
retrospect 側の出力にも引き継ぐ。

- `references/contracts/worker-envelope.md` の Untrusted-Input Handling 節が
  定義する扱いに従う旨を参照として書く（扱いの内容を書き写さない）。
- 外部サービスへ命令として解釈され得る形で出力しないことを明記する。
- retrospect フェーズが「機械的に書き出す軽量ステップ」であり、スキル・ルール
  表への反映を行わないという現行の性質は変えない。

## Test Notes

- 検査対象は SKILL.md の retrospect 節のみ。節は見出し行で切り出す。終端側の
  境界に Step C の見出しを使うと task0002 の見出し変更で境界が動くため、
  **境界には Step C 見出しの完全一致を使わない**（例: レベル 2 見出しの出現
  そのものを終端に使う、あるいは節の先頭からの固定長ではなく次の `\n## ` を
  探す）。これは worktree 独立性のために必要な配慮。
- TS4 / TS5 はスキーマ例（コードフェンス内の YAML）に対するテキストアサーション
  になる。キーの存在と入れ子の深さが読み取れる形で検査する。
- TS13（NFR6）は節全体に対するアサーション。参照先のドキュメント名と
  Untrusted-Input Handling という節名の両方が現れることを確かめる。
- 負の証明: `verification_failures:` の直後に下位構造が無い旧形と、
  `follow_up_drafts` が存在しない旧形の合成テキストを用意し、matcher が
  それらを通さないことを確かめる。
- 本タスクは他タスクが書く記述（cap の判定本文、停止条件の条項、Step C の
  実行条件）にアサートしない。cap の数値も書かない（NFR1 の定義元は SKILL.md
  の verify フェーズ節であり、retrospect 節ではない）。
