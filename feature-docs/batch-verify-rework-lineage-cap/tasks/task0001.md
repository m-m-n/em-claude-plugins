# Task Plan: task0001 — verify rework の系譜カウント cap と batch ブロック構造

## Goal

batch モードの verify 自動 rework 上限を、固定回数から「失敗項目 ID の系譜
ごとの再発回数（系譜 cap）+ グローバル hard cap」の二段構えに変え、cap 到達時
は停止せず `verify.status: failed` のまま retrospect へ進む形にする。あわせて
判定に必要な履歴を持てるよう workflow.yaml の `batch` ブロック構造を更新する。

## Design

### 1. cap 判定モデル（SKILL.md verify フェーズ節に置く定義本文）

batch モードの verify 失敗時、自動 rework を回すかどうかを次の 2 つの独立した
判定で決める。どちらか一方でも到達していれば cap 到達とする。

| 判定 | 数える対象 | 上限 | 検出したいもの |
|---|---|---|---|
| 系譜 cap | `batch.verify_rework.failed_id_counts` が保持する、failed item ID ごとの累積出現回数 | 1（同一 ID が 2 回目の `failed_items` に現れた時点で到達） | 同じ問題が直らないこと |
| hard cap | `batch.verify_rework.rounds`（rework 実行ラウンド数） | 3 | 新しい問題が湧き続けること |

カウントの更新規則:

1. verify ラウンドが `failed_items` を確定させる。
2. そのラウンドの `failed_items` に現れた**全 ID** について累積出現回数を 1
   増やす（1 回目のラウンドも含む — SPEC の前提 a2）。
3. rework を実行するラウンド数を 1 増やす。
4. 上表の 2 判定を独立に評価する。
5. どちらも未到達なら従来どおり rework-planner を dispatch して implement /
   verify を `pending` に戻す。到達していれば rework を回さない。

「過去ラウンドの `failed_items` に現れなかった新規 ID は新規予算を得る」という
性質は、累積出現回数が 1 の ID が系譜 cap に触れないことから導かれる。この性質
自体も定義本文に明記する（検証カバレッジ強化で新しく見つかった欠陥を握り潰さ
ないことが本フィーチャーの目的であるため）。

### 2. cap 到達時の帰結（FR3）

cap 到達時は走行を停止しない。`verify.status` は `failed` のまま、次のフェーズ
（retrospect）へ進む。残った `failed_items` に `deferred` を与えない（review の
defer は「リスク受容の記録」だが、verify の defer は「検証の偽装」になるため）。
旧文言「`failed` のまま報告して停止」はこの節から消える。

停止条件との整合そのもの（停止条件 1 / 3 の例外条項）は task0002 の担当であり、
本タスクは verify フェーズ節の中で「停止せず retrospect へ進む」と述べるに
とどめる。停止条件の条文を本タスクで書かない。

### 3. cap 定義の SSOT 単一化（NFR1 / IMPLEMENTATION.md D1）

- 定義本文（値・数え方・独立評価・cap 到達時の帰結）は SKILL.md「verify
  フェーズ」節にのみ置く。
- `batch-mode.md` の `verify.failed` 行は「系譜 cap と hard cap による自動
  rework、cap 到達時は `failed` のまま retrospect へ進む」旨と Full detail の
  参照だけを書き、**cap の数値を書かない**。同行の他の要素（ゲート名、
  interactive 側の三択の記述、Full detail の参照先）は現状の形を保つ。
- `workflow-schema.md` の batch ブロックは構造（キーとその意味）だけを書き、
  cap の値と判定規則を書かない。

### 4. batch ブロック構造（FR8）

`workflow-schema.md` の batch ブロックを次の構造に更新する。

| キー | 内容 |
|---|---|
| `review_rework_count` | 据え置き（FR10 により review 側は変更しない） |
| `verify_rework.rounds` | verify 自動 rework のラウンド数 |
| `verify_rework.failed_id_counts` | failed item ID ごとの累積出現回数（ID をキーとする写像） |

- 旧キー `verify_rework_count` の記述は消える。
- ブロックの説明コメント（現行「Rework counters ONLY」）を、履歴を保持する
  構造であることに合わせて書き換える。ただし「このブロックは batch モードの
  有効化には使わない（有効化は `--batch` フラグの役割）」という現行の趣旨は
  残す。
- 旧キーを持つ既存 workflow.yaml の扱い（IMPLEMENTATION.md D7）を 1 行で
  述べる: 移行は行わず、新構造のキーが無い場合は未計上（ラウンド数 0 / 出現
  回数は空）として扱い、旧キーは無視する。
- `batch-mode.md` の「## workflow.yaml `batch` ブロック」節も同じ構造を示す。
  ただし構造の定義元は `workflow-schema.md` であり、`batch-mode.md` 側は
  その参照にとどめる。

### 5. 既存テストの更新（IMPLEMENTATION.md D8）

次の 2 つの既存テストは、本タスクが書き換える旧文言をそのまま pin している。
新しい文言に合わせて更新する。更新後も「旧文言に戻ったら落ちる」性質を保つ
（単に削除しない）。

- `tests/test_develop_skill_rewiring.py` の、verify フェーズ節に旧カウンタ
  文言が残っていることを確かめているテスト
- `tests/test_batch_quiet_output_skill_wiring.py` の、verify フェーズ節の
  rework cap 文言が非改変であることを確かめているテスト

どちらのモジュールでも、上記以外のクラス・定数・アサーションには触れない。
とくに `tests/test_develop_skill_rewiring.py` の停止条件 3 carve-out 検査
クラスと、`tests/test_batch_quiet_output_skill_wiring.py` の Step C 見出し
定数は他タスクの所有物であり、本タスクは変更しない。

### 6. テスト隔離（IMPLEMENTATION.md D2）

本タスクの新規テストは、本タスクが変更する 3 つのドキュメント（SKILL.md /
batch-mode.md / workflow-schema.md）に対してのみアサートする。他タスクが書く
予定の記述（Step C の実行条件、retrospect.yaml の `follow_up_drafts`、停止条件
の独立条項、終端行）にはアサートしない。

## Test Notes

- TS1 / TS2 / TS3 は SKILL.md と `batch-mode.md` に対する文言アサーション。
  セクションは既存モジュールと同じく見出し文字列で切り出す。verify フェーズ節
  の終端に retrospect 節の見出しを使うと、他タスクが retrospect 節を書き換えた
  ときに境界が動く可能性があるため、切り出しは見出し**行**そのものを境界に
  使い、節の中身に依存しない。
- TS7 は `workflow-schema.md` の batch ブロックに対する構造アサーション。
  旧キーの不在は全文に対する絶対の非存在ではなく、batch ブロック内での不在
  として検査する（同ファイルの他の箇所で歴史的経緯に触れる可能性を残す）。
- TS12（NFR1）は 3 ファイルにまたがるが、3 ファイルとも本タスクが所有するため
  worktree 内で完結する。`batch-mode.md` には review 側の cap 1 の記述が残る
  ため、matcher は verify の cap を指す文脈に限定する（例: `verify_rework` /
  「系譜」「hard cap」という語の近傍でのみ数値を検出する）。
- 負の証明: 旧文言（固定回数カウンタで cap 1 とする表現）を含む合成テキストを
  作り、TS1 / TS3 の matcher がそれを通さないことを確かめる。
- 既存 2 モジュールの更新は「アサーション対象の文字列の差し替え」であり、
  クラス構造を変えない。差し替え後にモジュール単体で実行し、setUpClass の
  セクション切り出しが例外を出さないことを確認する。
