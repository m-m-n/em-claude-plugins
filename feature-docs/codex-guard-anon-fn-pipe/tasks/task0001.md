# Task Plan: task0001 — Pin the piped and head-redirected anonymous function body in CASES

## Goal

The CASES table of the codex-hook-interactive-guard contract tests pins, for
both hook copies, that a pipe or a stdin redirect in the head of a zsh
anonymous function `function () { ...; }` connects its body: a program-less
`python3` in that body passes silently, and an explicit `python3 -i` there is
still denied. The hook copies change only if one of the new entries fails on
the current code.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `tests/test_codex_hook_interactive_guard.py` — three entries added to the CASES table (FR4)
- `em-workflow/scripts/codex-hook-interactive-guard.py` — changed only if a new entry fails on the current code (FR5)
- `em-review/scripts/codex-hook-interactive-guard.py` — the same change as the em-workflow copy, byte-identical to it (NFR1)

## Design

The shared contracts (the CASES entry shape, the hook copies' output
contract) and the conventions are in IMPLEMENTATION.md; this section does not
restate them.

### The three entries

1. Expected `silent`. Command string the hook receives:
   `zsh -c 'printf "print(1)\n" | function () { python3; }'`.
   Placement: the section of the three zsh anonymous-function forms, beside
   the existing silent entry for `zsh -c 'echo x | function () { python3; }'`.
2. Expected `deny`. Command string the hook receives:
   `zsh -c 'printf "print(1)\n" | function () { python3 -i; }'`.
   Placement: beside entry 1.
3. Expected `silent`. Command string the hook receives:
   `zsh -c 'function < /dev/null () { python3; }'`.
   Placement: the section of the stdin redirect read in the head of an
   anonymous function, beside the existing silent entry for
   `zsh -c 'function < /dev/null { python3; }'`.

- In entries 1 and 2, `\n` is two characters: a backslash and `n`. The
  source literal escapes the inner double quotes and that backslash as SPEC
  "File Structure" shows, so the string the hook receives matches the list
  above exactly.
- Each label is Japanese and names the form the entry pins: the pipe from
  printf into `function ()` connecting the body, an explicit `-i` in that
  body still being denied, and the stdin redirect between `function` and
  `()` connecting the body. The wording is free (SPEC A3).
- Inserting the entries shifts which entries the every-twelfth sample picks;
  that changes no verdict and needs no adjustment.

### Expected behavior of the current code

The planner read the current parser. When the `(` of the empty `()` opens,
the parser reads the head's pending pipe and any stdin redirect read in the
head before the head words are ended, keeps them on that `(` group, and hands
them to the brace body that follows the `()`. So all three entries are
expected to pass with no hook change (SPEC A1).

### Decision flow

1. Add the three entries.
2. Run `python3 -m unittest tests.test_codex_hook_interactive_guard`.
3. All entries pass on both copies: the task is done and neither hook copy is
   modified.
4. A new entry fails: change the em-workflow copy so that the head of an
   anonymous function (the simple command up to the body) passes its pipe
   connection, and a stdin redirect read in it, to the body and to the groups
   nested in the body, and to nothing else. Copy the result byte for byte to
   the em-review copy in the same commit. Keep the module docstring and the
   group description in step with the behavior, so the documentation markers
   the test file checks still hold. Then rerun step 2 and the project test
   command.

### Constraints on a hook change (step 4 only)

- The connection reaches the anonymous body alone: not the `(` group of the
  `()`, not a command after the separator that ends the arguments, not a
  brace group that is no anonymous body. A redirect other than stdin
  connects nothing. An explicit `-i` in a connected body stays denied. The
  existing deny entries pin these limits (THREAT-MODEL.md TM-1).
- The parse stays linear in the length of the command string; the existing
  deep-input tests stay unchanged and pass.
- The guard keeps using the standard library only and touches no file,
  network connection or child process.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: CASES holds a `silent` entry whose command string is exactly `zsh -c 'printf "print(1)\n" | function () { python3; }'` (with `\n` as a backslash and `n`), and for it each hook copy exits 0 with empty standard output and standard error. (FR1, FR4)
- [ ] AC-2: CASES holds a `deny` entry whose command string is exactly `zsh -c 'printf "print(1)\n" | function () { python3 -i; }'`, and for it each hook copy exits 0 with empty standard error and prints one object whose permissionDecision is `deny`. (FR2, FR4)
- [ ] AC-3: CASES holds a `silent` entry whose command string is exactly `zsh -c 'function < /dev/null () { python3; }'`, and for it each hook copy exits 0 with empty standard output and standard error. (FR3, FR4)
- [ ] AC-4: The three entries carry Japanese labels and sit in the sections the Design names; `test_cases_are_unique` and `test_cases_hold_both_a_deny_and_a_silent_case` pass. (FR4)
- [ ] AC-5: Every CASES entry present at the base revision `ceefe2b5` (SPEC AC6) remains with its expected verdict, label and command unchanged, and no import is added to the test file: the test file's diff consists only of added CASES lines. (NFR2, NFR3)
- [ ] AC-6: If AC-1 to AC-3 pass on the unmodified hook copies, neither copy is modified; otherwise both copies change in the same commit. Either way `TestCopies.test_the_two_copies_are_byte_identical` passes, and no plugin.json or marketplace.json version field changes. (FR5, NFR1, NFR4)
- [ ] AC-7 (TM-1): `python3 -m unittest tests.test_codex_hook_interactive_guard` passes in full on both copies, and so does the project test command `python3 em-workflow/hooks/tests/run-destructive-guard.py && python3 -m unittest discover -s tests`. When a hook copy was changed, this includes every pre-existing deny entry that bounds the anonymous-body connection (a launch after the separator that ends the arguments, a non-stdin redirect in the head, a brace group that is no anonymous body) and the new piped `-i` entry, so no program-less or `-i` launch outside a connected anonymous body passes the guard.

## Test Notes

- AC-1 to AC-3 are exercised by `TestCasesTable.test_cases_run_against_both_copies`,
  which runs every CASES entry against both copies; AC-4 by the two table
  checks it names; AC-6 by `TestCopies`; AC-5 and the version-field part of
  AC-6 by a diff review.
- The entries are written first. The current code is expected to pass them
  at once (Design, "Expected behavior of the current code"), so the first run
  may already be green: the entries are a regression pin, not a red-to-green
  cycle. A red run sends the task into step 4 of the decision flow.
- To check AC-1 and AC-2, compare the string the source literal evaluates to
  with the Design list; a real newline in place of the backslash and `n`
  changes the input without changing the verdict, so a passing run alone does
  not catch it.

- Editing `.claude/rules/hook-tests.md` or any other document.
