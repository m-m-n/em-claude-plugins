# Task Plan: task0006 — Feature-docs correction entry script and removal patch validation

## Goal

A new `feature-docs-entry.py` decides at a re-run whether a failed implement
is corrected by removing feature-docs paths from the plan. The validator
checks and applies a `tasks_patch.feature_docs_removals` patch, sharing one
implementation of the conditions with the script.

## Requirements

## Design

Work against IMPLEMENTATION.md D6 and D7 and the feature-docs path predicate.

### Validator

1. **Shape** (`feature-docs-removal-shape`). This runs in the structural
   check of `tasks_patch`, whether or not `--dry-run-apply` is given. The
   field must be a non-empty list of mappings with exactly `task_id` and
   `path` (strings), on `replace_planning` only. Each `task_id` must be in
   `carried_task_ids`, pairs must be unique, and `path_corrections` must be
   absent.
2. **Precondition function.** One function takes the workflow, the
   removals and the journal's last events, and returns the errors of these
   conditions:
   - `-in-flight`: any task with status `in_progress` or last event
     `launched`;
   - `-merged`: a target whose status or last event is `merged`;
   - `-path`: the path is not a feature-docs path or is not in the target's
     `files`;
   - `-empty-files`: the target's `files` would be empty after removing
     every feature-docs path named for it.
   The entry script calls this same function.
3. **Dry-run-apply.**
   - The permission comes first. The correction entry (`create-plan`
     `completed`, `implement` `failed`) admits the patch. Any other state
     yields `feature-docs-removal-not-permitted`.
   - On the correction entry, a `failed` task is permitted and an
     `in_progress` task is not, the same as the existing correction entry of
     the final-path correction.
   - Then the precondition function runs, then the limits
     (`-limits`: `step_patches` and `entries` must be empty, and
     `requirements_patch` null or without entries).
   - Then the in-memory application: every occurrence of `path` is removed
     from the target's `files`, and `notes` is set to null.
   - Then `-incomplete`: a task not `merged` still holds a feature-docs path.
   - Then the plan agreement: each target's plan Files sections must equal
     its corrected `files` (`task-plan-files-mismatch`).
   - Without `--workflow`, `--journal` or `--feature-dir` the run is an
     execution error (exit 2).
   - The Re-planning path's carry-over and mandatory-preserve checks still
     apply.
4. **Application** in the apply path used by the orchestrator. Carried
   records are copied verbatim, then the removals are applied, the same
   order as path corrections.
5. **Unchanged.** A `replace_all` without the field behaves exactly as
   before.

### Entry script

`feature-docs-entry.py` follows `report-name-entry.py`'s structure:

- the same four arguments;
- sibling loading of the validator and of `report-name-entry.py`;
- one JSON object on stdout with exactly the keys of D6;
- exit 0 for `none`, `dispatch` and `blocked`;
- exit 2 for an execution error, with a one-line stderr message and no
  traceback.

The judgment is D6:

- The failed-task and unmerged-task selection is the one in
  `report-name-entry.py`, reused rather than re-implemented.
- The blocking conditions come from the validator's precondition function.
- `final_path_remaining` comes from the validator's report-name violation
  finder, applied to the failed tasks' files with their feature-docs paths
  removed. It is computed only on `dispatch`, so the base commit is needed
  only then.

`report-name-entry.py` itself is not changed, and its output key set stays
as its tests pin it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS-6): With `implement` `failed`, the script returns `dispatch` when one failed unmerged task's `files` holds `feature-docs/call-end-history/THREAT-MODEL.md`, a second unmerged task that has not failed holds `feature-docs/other/NOTES.md`, and a merged task holds a third feature-docs path. In that case:
  - `targets` lists the first two, in workflow order and then file order, each with `task_id`, `path` and `failed_journal_line`;
  - the merged task's path is not listed;
  - a target path that exists at the base commit is still listed.
- [ ] AC-2 (TS-7): The script does not return `dispatch` in these cases:
  - `none` when `implement` is not `failed`;
  - `none` when only merged tasks hold feature-docs paths;
  - `blocked`, naming the condition, when a task is `in_progress` or its last journal event is `launched`;
  - `blocked`, naming the task, when a target's `files` would become empty;
  - `blocked` when a target's last journal event is `merged`.
- [ ] AC-3: The output keys are exactly `entry`, `targets`, `errors` and `final_path_remaining`, and the exit code is 0 for all three outcomes. `final_path_remaining` is true on `dispatch` only when a failed task still holds a report-name violation after removal; it is false otherwise. `report-name-entry.py`'s tests pass unchanged.
- [ ] AC-4 (TS-9): Each of these exits 2 with a stderr message and no traceback:
  - a `--workflow` file that is invalid YAML;
  - one that is not a mapping;
  - an unreadable journal;
  - a missing argument.
  A `files` value that is not a list reads as no files, and non-string elements are skipped.
- [ ] AC-5 (TM-4): Each condition code is produced by its failing case and absent from the passing case: `feature-docs-removal-shape`, `-not-permitted` (the Initial-planning and Re-planning states), `-in-flight`, `-merged`, `-path`, `-empty-files`, `-incomplete` and `-limits`. A `failed` target is accepted and an `in_progress` task is rejected.
- [ ] AC-6 (TS-8, TM-4): Applying a valid patch under `--dry-run-apply` behaves as follows:
  - every occurrence of the path leaves the target's `files`;
  - the target's `notes` becomes null, and its other fields are unchanged;
  - merged tasks' records are byte-for-byte the same as before;
  - a target plan whose Files section still lists the path yields `task-plan-files-mismatch`;
  - the run without `--journal` exits 2.
- [ ] AC-7: `python3 -m unittest discover -s tests` passes, and the refreshed byte pin carries a comment naming this task.

  plans.
- Compare merged records as parsed mappings and assert equality.
- Never use timing-dependent or load-generating setups.
