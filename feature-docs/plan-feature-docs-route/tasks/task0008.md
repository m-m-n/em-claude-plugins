## Design

Work against IMPLEMENTATION.md D6, D8 and D9.

### develop SKILL.md, `## Step A.6: failed からの入口`

The heading, its place between Step A.5 and Step B, and every phrase pinned
by `tests/test_failed_entry_develop_docs.py` stay. The section is written in
Japanese like the rest of the skill.

1. The opening paragraph also names the feature-docs correction, the
   removal of `feature-docs` paths from `files`, as a correction this entry
   decides.
2. After the not-failed check, the steps run in this order:
   - capture the integration tip as today;
   - run `${CLAUDE_PLUGIN_ROOT}/scripts/feature-docs-entry.py` with the same
     four arguments;
   - only then run the existing `report-name-entry.py` step.
   Each script owns its judgment, which is cited, not restated. The output
   keys of the new script are named the same way the existing step names
   `report-name-entry.py`'s keys.
3. Both judgments are evaluated in one Step A.6 evaluation, and neither
   result skips the evaluation of the other (A4).
4. On `dispatch`, the new step runs section 13's feature-docs correction
   subsection. The existing sentences (`failed_kind`, interactive and batch,
   no new `gate_id` and no user question) cover both judgments.
5. The restoration list stays. A new paragraph splits it per D9:
   - task-level items are written for each correction's targets
     (`violations` for the final-path correction, `targets` for the
     feature-docs correction), with that correction's patch, in one Write and
     one commit after its artifact commit;
   - step-level items (`implement` and `failed_kind`) go into the Write of
     the last correction, and only when no judgment is unresolved;
   - the feature-docs correction is last when `final_path_remaining` is
     false; otherwise the final-path judgment runs next on a freshly
     captured tip;
   - when that judgment returns `none`, the step-level items are written
     alone in one Write and one commit.
6. An unresolved judgment (`blocked`, a non-zero exit, or no validated
   patch) changes nothing in `workflow.yaml` for that judgment, so Step B's
   stop condition 3 fires. The stop report names the failed conditions of
   every unresolved judgment, read from `errors`.
7. The untouched-items paragraph (worktrees, branches, merged tasks,
   uncommitted changes) covers both corrections.
