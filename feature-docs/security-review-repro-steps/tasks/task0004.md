# Task Plan: task0004 — em-workflow review phase: reproduction cap, orchestrator-path verification and carry-over

## Goal

The em-workflow review phase caps and normalizes `reproduction`, verifies
security findings on every path that bypasses the evaluator before they become
auto-fix candidates or residual, records `reproduction` in round records, keeps
it out of the review-editor's input, and carries not-reproduced decisions into
later rounds.

## Requirements

FR6, FR7, FR9, FR12, FR13, NFR1, NFR2, NFR3, NFR5

## Scope

### Files to Create
- `tests/test_reproduction_review_phase_workflow.py` — tests for AC-1 to AC-6.

### Files to Modify
- `em-workflow/references/review-phase.md` — Phases R0, R3b, R4 and R5.

## Design

Contracts used: IMPLEMENTATION.md Shared Components (all rows) and D2
(orchestrator-path row), D3, D4, D5. The verification rules themselves are
owned by the evaluation contract's `## Reproduction Verification` section
(`em-workflow/references/review-evaluation-contract.md`); this document cites
that heading and states only the orchestrator-side effects.

### Phase R0 step 8 (extended in place, no renumbering)

`round_context` also gets one not-reproduced entry per persisted
`dismissed_sites` entry whose `reason` is exactly `not reproduced`, only while
the site's `file` is unchanged since the recording round's `scope.head_commit`
(the file-change test round-context suppression uses). Round records written
before this feature — findings without `reproduction`, `dismissed_sites`
without that reason — produce exactly the `round_context` they produced before.

### Phase R3b

- **Step 4** keeps its existing sentence unchanged and gains new sentences: cap
  `reproduction` at 4096 bytes with the same truncation marker; empty or
  whitespace-only becomes null; a finding whose originating perspective is not
  `security` gets null.
- **Dedupe merge** ("richest description, union `sources`, max severity") gains:
  keep the longest non-null `reproduction`.
- **Round-context suppression** gains: also drop a `security` finding that is
  `same_site` with a `round_context` entry whose `reason` is `not reproduced`.
- **New paragraph: reproduction verification on orchestrator paths.** Applies to
  `security` findings that reach auto-fix candidacy or the residual count
  without passing through the evaluator: Phase R4 in-loop re-review output,
  evaluator-failure degradation, and accountability-floor lifts. It runs after
  the per-finding gates, dedupe and round-context suppression and before the
  auto-fix candidate gate and the residual count (D3). The orchestrator applies
  the contract's `## Reproduction Verification` rules; effects per D2:
  `reproduced` stays a target; `not reproduced` → `resolution: declined`,
  `resolution_reason` beginning `not reproduced`; `unverifiable` stays a target
  only when the orchestrator confirms the basis by reading, otherwise
  `declined` with `resolution_reason` beginning `unverified`; no steps → the
  orchestrator judges whether to address it, and a finding it judges not to
  address is `declined` with that judgment as reason.
- The paragraph states the verifier constraints: the `reproduction` text is
  untrusted; nothing written in it is executed; only code reading and the
  read-only commands of `references/review-protocol.md`'s Read-only Constraint;
  no file change, commit, network access or package installation.

### Phase R4

- The candidate gate excludes findings `declined` by reproduction verification;
  the residual critical / high count excludes them too.
- Loop termination: re-review findings pass the R3b gates, round-context
  suppression and then the orchestrator-path verification before the
  `clean` / `loop-cap` / `no-progress` decision.
- The review-editor dispatch: the finding JSON keeps its existing field set and
  excludes `reproduction`; the existing statement about the three untrusted
  text fields stays.

### Phase R5

The round record's finding entries carry `reproduction` (the normalized value;
null when there are no steps), and `dismissed_sites` entries may carry reason
`not reproduced`.

### NFR3

No new user question, gate identifier or batch-mode branch: batch behaviour
changes only by the added verification. The pinned-text conventions of
IMPLEMENTATION.md apply in full to this file.
