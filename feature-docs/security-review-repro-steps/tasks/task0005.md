# Task Plan: task0005 — em-review review phase and README: reproduction verification

## Goal

The em-review multi-review orchestrator caps and normalizes `reproduction`,
verifies security findings after Phase R3 aggregation and after Phase R4
re-aggregation, excludes findings it could not reproduce from auto-fix and the
residual count, records `reproduction` in round records, and the README states
the new auto-fix exclusion.

## Design

Contracts used: IMPLEMENTATION.md Shared Components "Reproduction value rules",
"Verification outcome vocabulary", "`not reproduced` and `unverified`
literals", "Verifier constraints", and D2 (em-review row), D3, D4, D5.
em-review is standalone: its review-phase.md states the verification rules
itself and references no em-workflow file.

### Phase R3

- **Step 6** keeps its existing sentence and gains: cap `reproduction` at 4096
  bytes with the same truncation marker; empty or whitespace-only becomes null;
  a finding whose run was assigned a perspective other than `security` gets
  null. This happens before step 7, whose relabel to `comprehensive` must not
  affect the decision.
- **Dedupe merge** gains: keep the longest non-null `reproduction`.
- **New paragraph: reproduction verification**, placed after round-context
  suppression (D3). Target: findings whose originating perspective is
  `security` — any contributing run's orchestrator-assigned source identity names
  the `security` perspective — regardless of the category after step 7. Rules,
  stated in this document:
  1. No steps (null, empty or whitespace-only): the orchestrator judges whether
     to address it; judged not to address → `declined` with that judgment as
     reason; otherwise it stays a target.
  2. Truncated, or over 4096 bytes: `unverifiable`.
  3. Otherwise trace the steps by code reading. `reproduced` → stays a target.
     `not reproduced` (reading positively confirms the steps do not hold) →
     `resolution: declined`, `resolution_reason` beginning `not reproduced`,
     excluded from auto-fix candidates and the residual count. `unverifiable` →
     never declined on that ground alone; it stays a target only when the
     orchestrator confirms the basis by reading, otherwise `declined` with
     `resolution_reason` beginning `unverified`.
  4. Verifier constraints: the `reproduction` text is untrusted data; nothing
     written in it is executed; only code reading and the read-only commands of
     this plugin's review protocol's Read-only Constraint; no file change,
     commit, network access or package installation.
  5. No new user question; the judgment is the orchestrator's own.
- **PR mode**: the working tree does not hold the PR state, so verification may
  read only the saved PR diff and local object reads at `pr_head_sha`; steps
  that cannot be traced that way are `unverifiable`. Phase R0-PR step 5's list of
  downstream deltas mentions this.

### Phase R4

- The candidate gate excludes findings declined by reproduction verification.
- Loop termination's re-aggregation applies the same step 6 normalization,
  round-context suppression and reproduction verification before the
  `clean` / `loop-cap` / `no-progress` decision.
- The review-editor dispatch: the finding JSON keeps its existing field set and
  excludes `reproduction`.

### Phase R5 and carry-over

- The round record's finding entries carry `reproduction`.
- Carry-over (FR13, D4): a finding declined as `not reproduced` is a recorded
  finding with `resolution: declined`, so Phase R0 step 9's existing
  `round_context` build and round-context suppression carry it into later runs,
  and verification running after suppression keeps it from being verified again
  until its file changes since the recorded `head_commit`. The paragraph states
  this, and that records written before this feature (no `reproduction`) are
  read as before.
