# Task Plan: task0001 — script that resolves deferred findings on verify pass

## Goal

A new script, `em-workflow/scripts/resolve-verified-findings.py`, checks the
orchestrator's mapping against `workflow.yaml` and the latest review round
record and rewrites only eligible deferred spec findings to `fixed` with
provenance, so that `merge-preflight.py` treats them as resolved.

## Requirements

FR4, FR5, FR7, FR8, FR11, NFR1, NFR3, NFR5, NFR6

## Scope

### Files to Create
- `em-workflow/scripts/resolve-verified-findings.py` — the script; its
  command-line contract is IMPLEMENTATION.md C2
- `tests/test_resolve_verified_findings.py` — tests for every Acceptance
  Criterion below

### Files to Modify

## Design

Contracts used, not restated here: IMPLEMENTATION.md C1 (verify-step
fields), C2 (command line, eligibility, exit postconditions, stdout
summary), C3 (mapping file), C4 (rewritten finding shape), C5 (token
format), C6 (latest-round selection).

### Processing flow

1. Check the arguments. A missing argument gives `invalid-arguments`; a
   `--verified-commit` that is not 40 or 64 lowercase hexadecimal characters
   gives `invalid-commit`.
2. Read `DIR/workflow.yaml` with safe load. It is structurally valid when the
   top level is a mapping, `workflow` is a list, exactly one element has id
   `verify` and is a mapping, `result` is absent, null, `pass` or `fail`,
   `round` is absent or an integer of 0 or more (a boolean is not an
   integer), and `passed_ids` is absent or a list of C5 tokens. Otherwise:
   `invalid-workflow`.
3. Read the mapping file as JSON. It is structurally valid when the top
   level is an object, every value is an array, and every array element is a
   string. Otherwise: `invalid-mapping`.
4. Select the latest round record per C6. When none exists:
   `missing-round-record`. Read it with safe load. It is structurally valid
   when the top level is a mapping, the findings list (under the key
   `em-workflow/references/review-phase.md` defines for the round record) is
   a list, and every element is a mapping. Otherwise:
   `invalid-round-record`.
5. A document carrying a YAML tag that would construct a language-native
   object is refused by safe load; that refusal is the structural error of
   the file it occurs in (`invalid-workflow` or `invalid-round-record`).
6. Every check above finishes before any write. On any failure: print one
   stderr line holding only the error code, exit non-zero, write nothing,
   print nothing on stdout.
7. When `result` is not `pass`, or `round` is 0: exit 0 without writing; the
   summary has an empty `fixed` list and counts every entry in
   `not_applied`.
8. For each entry in mapping order, apply the C2 eligibility conditions. A
   finding is located by its `stable_id` string; a finding whose `stable_id`
   is not a string never matches; an entry that matches zero findings or
   more than one finding is not applied.
9. Rewrite each eligible finding in memory per C4.
10. When at least one finding was rewritten, replace the latest round record
    as a whole in one step, so that an interruption never leaves a
    half-written record and no temporary file remains after the run. Write it
    without language-specific tags, with key order preserved and non-ASCII
    text kept as it is.
11. Print the C2 summary on stdout and exit 0.

The error codes form a fixed set: `invalid-arguments`, `invalid-commit`,
`invalid-workflow`, `invalid-mapping`, `missing-round-record`,
`invalid-round-record`.

### Constraints

- `em-workflow/scripts/merge-preflight.py` and `tests/test_merge_preflight.py`
  are read, never modified (FR11, NFR3). Read `check_review_findings` to
  reproduce the C6 selection rule and the `resolution` vocabulary.
- Of a finding, the script reads only `stable_id`, `resolution`, `severity`,
  `category` and `resolution_reason` (the last only to carry it over). It
  never reads SPEC.md, VERIFICATION.md or finding text to decide anything.
- stdout and stderr carry only the structured values C2 lists: stable_ids
  that conform to C5 and exist in the record, IDs that are members of
  `passed_ids`, round numbers, counts and error codes (NFR1, TM-6).
- Follow the sibling scripts in `em-workflow/scripts/` for the file header,
  the interpreter line and the executable bit.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS-1; SPEC AC1, AC2, AC9; TM-7): Fixture: a temporary git
  repository whose integration branch holds a feature `workflow.yaml` with
  verify `result: pass`, `round: 2` and `passed_ids` containing one criterion
  ID, and a latest round record with one finding of resolution `deferred`,
  severity `high` and category `spec`. Before the script runs,
  `merge-preflight.py` on the committed branch returns `unresolved_findings`
  naming that finding's stable_id. After the script runs with a mapping of
  that stable_id to that ID and `workflow.yaml` and the round record are
  committed in one commit that contains both paths, the finding has
  `resolution: fixed`, a `resolution_reason` equal to the C4 sentence for
  round 2 and that ID, and a `verify_resolution` with exactly the five C4
  keys holding 2, the given verified commit, the ID list, `deferred` and the
  previous reason; and `merge-preflight.py` returns outcome `proceed`.
- [ ] AC-2 (TS-2; SPEC AC3; FR4, FR8; TM-3): With one latest round record
  holding a deferred spec/high finding absent from the mapping, a deferred
  security/high finding mapped to a passed ID, deferred spec/high findings
  mapped respectively to an ID of an excluded requirement, to an unevaluated
  ID and to an unknown ID (none of them in `passed_ids`), a deferred
  spec/medium finding mapped to a passed ID, plus a mapping entry with an
  empty list and a mapping key that matches no finding: the script exits 0,
  every one of those findings keeps all its values, `not_applied` counts
  every entry, and `merge-preflight.py` on the committed state returns
  `unresolved_findings`.
- [ ] AC-3 (TS-3; SPEC AC4; FR8): With an otherwise eligible fixture whose
  verify result is `fail` (and separately: result null; `round` 0), the
  script exits 0 and the round record is byte-identical to before.
- [ ] AC-4 (TS-4; SPEC AC5; FR8): Findings of resolution `unresolved`,
  `fixed` and `declined` in the latest round, mapped to passed IDs, keep all
  their values. With round1 and round2 records where round2 is the latest, a
  deferred spec/high finding of round1 mapped to a passed ID leaves the
  round1 file byte-identical.
- [ ] AC-5 (TS-5; SPEC AC6; FR7): Running the script twice with the same
  inputs leaves the round record byte-identical to its state after the first
  run, and the second run's summary has an empty `fixed` list. A finding
  already `fixed` with a `verify_resolution` of the same verify round is not
  touched.
- [ ] AC-6 (TS-6; SPEC AC7; TM-5): For each structurally broken input — a
  mapping that is not JSON, a mapping whose top level is an array, a mapping
  element that is not a string; a round record that is not YAML, a findings
  value that is not a list; a `workflow.yaml` that is not YAML, a missing
  verify step, a `round` that is a string, a negative `round`, a
  `passed_ids` that is not a list, a `passed_ids` element that breaks C5; a
  malformed verified commit; no round record at all — the exit status is
  non-zero, stdout is empty, and every file under the fixture's feature
  directory is byte-identical with no file added.
- [ ] AC-7 (TS-10; NFR1, NFR6; TM-4, TM-5, TM-6): (a) A round record, and
  separately a `workflow.yaml`, carrying a YAML tag that would construct a
  language-native object makes the script exit non-zero and write nothing.
  (b) With one sentinel instruction-like string placed in a finding's
  free-text fields, in its `resolution_reason`, as a mapping key and as a
  mapping ID, neither stdout nor stderr contains the sentinel, on a
  successful run and on a failing run. (c) After a successful rewrite, the
  latest round record is the only file of the fixture repository whose bytes
  changed, and no file was added.
- [ ] AC-8 (TS-8, TS-12; SPEC AC10; FR11, NFR3): `python3 -m unittest
  discover -s tests` passes, and this task's change touches neither
  `em-workflow/scripts/merge-preflight.py` nor `tests/test_merge_preflight.py`.

## Test Notes

- Every criterion is an integration-style test that runs the script as a
  subprocess with the running interpreter against a fixture built in a
  temporary directory.
- AC-1 and AC-2 need `merge-preflight.py` to pass its other checks; build the
  fixture repository and invoke the preflight the way
  `tests/test_merge_preflight.py` does (read it, do not modify it; copying
  its fixture setup into the new module is fine). AC-1's "before" assertion
  is what makes SPEC AC9 hold: the same fixture fails the preflight without
  the script.
- Byte identity: read file bytes before and after. "No file added": compare
  the fixture tree's file listing before and after.
- AC-7 (b): use a sentinel that cannot appear in any structured value, and
  check the captured stdout and stderr text.
