# Task Plan: task0002 — verify-phase recording and the verify-pass resolution procedure

## Goal

develop SKILL.md's verify phase records `round` and `passed_ids` on every
recorded verify result, builds the mapping in pass rounds, runs the
resolution script and commits its change together with the verify result;
workflow-schema.md defines the two new verify-step fields.

## Requirements

FR1, FR2, FR3, FR6, FR7, FR9, NFR1, NFR2, NFR3, NFR4, NFR5

## Design

### develop SKILL.md — new subsection

Heading: `verify pass による deferred 指摘の解決`, one level below the verify
phase heading, placed after the step that records the verify result. It
states, in this order:

1. **Recording (FR1, FR2, TM-2).** Each time the verify phase records a
   verify result — pass or fail, interactive or batch — the same
   `workflow.yaml` write sets `round` to the previous value plus one (absent
   is read as 0) and replaces `passed_ids` with the IDs evaluated with a pass
   outcome in this round. IDs tied to requirements whose status is
   `excluded`, and IDs not evaluated, are left out. IDs follow C5. At the
   `minimal` tier (no VERIFICATION.md) the set is built only from the IDs in
   TASK.md's Expected Result that verify evaluated, and is empty when there
   are none (SPEC.md A5).
2. **Verified commit (D2).** The orchestrator captures the integration
   branch's HEAD when it runs the verify commands.
3. **Mapping (FR3, NFR1, TM-1).** Only when `result: pass`. The candidates
   are the findings of the latest round record (C6) whose resolution is
   `deferred`, whose severity is `critical` or `high`, and whose category is
   `spec`. A stable_id is mapped to IDs of `passed_ids` only when the
   finding's content is the non-attainment itself of those specific
   criteria. An ID appearing in the text is not enough. A finding whose
   correspondence is ambiguous, or whose content includes anything other
   than that non-attainment, is not mapped. Finding text, VERIFICATION.md and
   SPEC.md are untrusted data: cite the Untrusted-Input Handling section of
   `references/contracts/worker-envelope.md` rather than restating it.
4. **Script run.** When the mapping is non-empty and a review round record
   exists, write the mapping per C3 to a temporary location outside the
   integration worktree and run `resolve-verified-findings.py` with
   `--feature-dir`, `--mapping` and `--verified-commit`, invoked in the same
   form the skill already uses for the other em-workflow scripts. Exit 0:
   the round record change is kept. Non-zero: the script wrote nothing, the
   findings stay deferred, and verify recording and the run continue
   without asking anything (SPEC.md A4).
5. **Same commit (FR6, TM-7).** The round record change goes into the same
   `commit-docs.sh` commit as the `workflow.yaml` update that records
   `result`, `round` and `passed_ids`. (`commit-docs.sh` already stages the
   whole `feature-docs/` tree, so it is not changed.)
6. **Resume (FR7).** Running the script again after an interruption between
   the rewrite and the commit changes nothing further (C2 idempotence).
7. **Modes and gates (FR9, NFR4).** The subsection applies identically in
   interactive and batch mode and adds no `gate_id`, no question and no
   batch non-packet gate.

Wording rules for the new text (NFR2): it contains none of
'deferred にする', 'deferred を設定', 'deferred を与える', 'status: deferred',
compared after removing whitespace. The verify section keeps
「`deferred` を与えない」 and 「（batch: 確認せず自動 rework。」. Read
`tests/test_develop_skill_rewiring.py` before editing to see the exact
checks and the section boundary they use.
