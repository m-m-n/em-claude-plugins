# Task Plan: task0001 — Judge heredoc body rescans by each heredoc's own destination

## Goal

destructive-guard.py stops denying a command just because a heredoc body it
does not execute contains `git reset --hard`. It still denies whenever that
body reaches, or may reach, a shell sink. The fix ships with regression
cases and the em-workflow patch version bump.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, FR7, FR8, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify
- `em-workflow/hooks/destructive-guard.py` — heredoc extraction for several operators per line, and a per-heredoc rescan decision by destination
- `em-workflow/hooks/tests/destructive-guard-cases.json` — new allow and deny expectation cases (added before the guard is modified)
- `em-workflow/.claude-plugin/plugin.json` — em-workflow version raised at the patch position

## Design

Cross-task context lives in IMPLEMENTATION.md: D1 (single-task
decomposition), D2 (the batch-resolved interpretation of FR5) and the
version-bump convention. Everything below is local to this task.

### Terms

- **Heredoc operator**: exactly what the guard recognises as one today. That
  covers `<<` and `<<-`, a bare or quoted word-character delimiter, and the
  here-string exclusion. The recognition rule itself does not change.
- **Host statement**: the statement that contains a heredoc's operator.
  When the operator sits inside a command substitution (either spelling,
  quoted or not), the host statement is the statement inside that
  substitution's body.
- **Enclosing statement**: a statement that contains the command
  substitution holding the host statement. With nested substitutions, every
  level outward counts, up to the outermost.
- **Pipeline**: a run of statements joined by a pipe separator (`|` or
  `|&`, including when newlines follow it). `||`, `&&`, `;`, `&` and a bare
  newline end it.
- **Command word**: what `head()` returns for a statement's shaped words.
  That is the basename of the first word left after the existing
  assignment / wrapper / grouping / reserved-word skip. Reuse the existing
  shaping as-is. Do not change `head()`, `WRAPPERS` or
  `WRAPPER_VALUE_FLAGS`, because failed-run-cleanup-guard.py mirrors them
  and that file is out of scope.
- **Sink word**: a command word whose basename begins with one of the
  entries sh, bash, zsh, dash, ksh, python, python followed by one digit,
  perl, ruby, node. The character right after the entry must be the end of
  the word or a non-word character.
  - Qualify: `bash`, `/bin/sh`, `python3`, `python3.12`.
  - Do not qualify: `run_codex_exec.sh`, `shellcheck`, `nodemon`.
  - This is exactly the set of words for which the current SHELL_SINK
    expression matches starting at the word's first character. Keep one
    source for the vocabulary, so the word-level test and the chunk-wide
    fallback cannot drift apart.
- **Data command**: a command word on this closed list. Each command treats
  its standard input and its arguments as data and never runs them as a
  program:
  - `:` `cat` `tee` `head` `tail` `wc` `uniq` `cut` `tr` `grep` `diff`
    `jq` `read` `echo` `printf` `git` `gh`
  - `sed`, `awk`, `sort` and `rg` are deliberately absent, because each can
    take a program from its input or run a program named in an option.
  - The list is part of this task's contract, and review judges any change
    to it.

### Component 1: heredoc extraction (replaces the single-pattern strip)

- **Input**: one chunk of text.
- **Output**:
  - The chunk with heredoc bodies removed.
  - An ordered list of heredoc records. Each record holds the body text and
    enough information to find its operator in the stripped chunk, and from
    the operator its host statement and enclosing statements.
- **Postconditions**:
  1. For a line with exactly one operator, the stripped chunk and the body
     are identical to what the current strip produces. The operator line is
     kept; the body lines and the delimiter line are removed.
  2. For a line with several operators, the operators consume body lines in
     left-to-right order. The first body runs up to the first operator's
     delimiter line, the next starts on the line after that delimiter line,
     and so on. No second operator is swallowed as the tail of the first
     operator's line.
  3. An operator whose delimiter line never appears in the remaining text
     consumes nothing, and its would-be body stays in the chunk. This is
     the current handling. The operators after it on the same line still
     consume in order.
  4. Text after the last consumed delimiter line stays in the chunk
     unchanged, and later stages check it as commands (FR4).
  5. Cost stays proportional to input size. Consumption only moves forward,
     and an unterminated operator does not trigger a fresh search of the
     rest of the input once per operator (NFR3, TM-5).

### Component 2: destination decision (per heredoc record)

Each heredoc gets exactly one outcome, evaluated in this order.

1. **sink-bound** when any of the following holds.
   - (i) The host statement's command word is a sink word.
   - (ii) A statement later in the host statement's pipeline has a sink
     command word.
   - (iii) An enclosing statement's command word is a sink word, or a
     statement later in an enclosing statement's pipeline has a sink
     command word. For example, `echo "$(cat <<'EOF' ... EOF)" | bash` is
     sink-bound.
2. **undeterminable** when it is not sink-bound and any of the following
   holds. This is FR5 as resolved in IMPLEMENTATION.md D2.
   - The chunk after heredoc removal takes `lex_segments()`'s parse-failure
     path. The same applies to a substitution body that has to be lexed to
     find the host statement.
   - The host statement has no command word of its own, because the
     operator is attached to a compound command's closer (`}`, `)`, `done`,
     `fi`, `esac`).
   - The host command word is statically unknown, because a command
     substitution sits in command position.
   - The host command word is neither a sink word nor a data command. This
     includes execution-prefix commands outside `WRAPPERS` (`timeout`,
     `exec`, `stdbuf`, `setsid`, `xargs` and the like) and any other
     command or script.
   - An enclosing statement's command word is neither a sink word nor a data
     command, including a statically unknown one or none at all. The
     exception is an enclosing statement made only of variable
     assignments: there the substitution sits in an assignment value, and
     its output is only stored. For example,
     `timeout 10 bash -c "$(cat <<'EOF' ... EOF)"` is undeterminable.
   - The host statement or an enclosing statement contains a process
     substitution (`<(...)` or `>(...)`), because its inner command can
     consume the body. Examples: `tee >(bash)` and `cat > >(bash)`.
3. **data** otherwise. At that point the host command word is a data command,
   and every enclosing statement is either a data command or
   assignment-only.

For a heredoc inside a command substitution, the decision is made while the
chunk that holds the enclosing statement is being processed. It must be made
before that substitution's body is queued as a chunk of its own, because the
association with the enclosing statement is lost at that point.

### Component 3: rescan decision (inside `statements()`)

This replaces the current rule, "any sink word anywhere in the chunk".

- A **sink-bound** body goes back on the rescan queue.
- An **undeterminable** body goes back on the queue only when the stripped
  chunk matches the current chunk-wide SHELL_SINK test. This is the current
  conservative behaviour, applied to that heredoc only (FR5, TM-3).
- A **data** body is never queued, even when another heredoc in the same
  chunk falls back (TS-25).
- A blank body is never queued, as today.

After this decision the chunk continues through the existing stages
unchanged: substitution collection, lexing, shaping, payload extraction and
the checks.

### Behaviour that must not change

- The chunk-wide `check_pipe_to_shell()`.
- Here-string handling and `-c` / `eval` payload handling.
- Every check function called from `main()`.
- `hooks.json`.
- The runner script.

### Expectation cases (added first, FR6)

Add each case in the existing `[expected verdict, label, command]` shape.
Labels follow the existing style: Japanese, naming the shape and whether it
guards against a false positive or pins detection.

In the list below, ` / ` separates the lines of one command; each ` / ` is a
newline in the JSON string. Each line is shown verbatim inside a code span.
IDs refer to VERIFICATION.md.

- TS-1 (allow): `cat > /tmp/p.txt <<'EOF'` / ``Some prose mentioning `git reset --hard` inside a documentation quote.`` / `EOF` / `echo done`
- TS-2 (allow): `S=/tmp/x && cat > $S/prompt.md <<'EOF'` / ``Step I.2.a には `git reset --hard` の記述が無い`` / `EOF` / `em-workflow/scripts/run_codex_exec.sh readonly "$(cat $S/prompt.md)"`
- TS-3 (allow): `python3 x.py; cat > /tmp/p <<'EOF'` / `git reset --hard HEAD` / `EOF`
- TS-4 (allow): `cat > /tmp/a <<'A' ; cat > /tmp/b <<'B'` / `first` / `A` / `git reset --hard HEAD` / `B`
- TS-5 (deny): `bash <<'EOF'` / `git reset --hard HEAD` / `EOF`
- TS-6 (deny): `cat <<'EOF' | bash` / `git reset --hard HEAD` / `EOF`
- TS-7 (deny): `sudo bash <<'EOF'` / `git reset --hard HEAD` / `EOF`
- TS-8 (deny): `/bin/sh <<'EOF'` / `git reset --hard HEAD` / `EOF`
- TS-9 (deny): `cat > /tmp/a <<'A' ; bash <<'B'` / `first` / `A` / `git reset --hard HEAD` / `B`
- TS-10 (deny): `cat > /tmp/p <<'EOF'` / `x` / `EOF` / `git reset --hard HEAD`

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR6): Before destructive-guard.py is modified, `em-workflow/hooks/tests/destructive-guard-cases.json` gains one case for each scenario under "Expectation cases": TS-1 to TS-13, TS-15 to TS-17, and TS-21 to TS-27.
  - Each case uses the existing three-element shape and carries the expected verdict listed there.
  - Each case reproduces the command exactly, newlines included.
  - The suite result against the unmodified guard is recorded, and at least one new allow case fails in it (red). The expected failures are TS-2, TS-3, TS-4 and TS-25.
- [ ] AC-2 (FR1 (i), FR2; TM-1): Whether a body is rescanned follows the host command word.
  - A body is not rescanned when its host command word is a data command and it is neither sink-bound nor undeterminable. TS-1, TS-2 and TS-3 are allowed, including when another statement in the same chunk carries `python3`, `bash` or a `.sh`-suffixed word as its command word or as an argument.
  - A body whose host command word is a sink word is rescanned. TS-5 (bare), TS-7 (behind a wrapper), TS-8 (absolute path), TS-16 (versioned spelling) and the existing case "bash ヒアドキュメントは実行" are denied.
- [ ] AC-3 (FR1 (ii), (iii); TM-1): A body is rescanned when a sink is downstream of it or encloses it.
  - A later stage of its host statement's pipeline has a sink command word: TS-6 is denied.
  - An enclosing statement's command word is a sink word, or a later stage of an enclosing statement's pipeline has one: TS-13 and TS-23 are denied.
  - The same substitution under a data enclosing statement with no sink downstream stays data: TS-24 is allowed.
- [ ] AC-4 (FR3, FR4; TM-1, TM-2): With several heredoc operators on one line, each body is consumed in operator order, up to its own delimiter line, and is judged on its own destination.
  - TS-4 is allowed and TS-9 is denied.
  - A statement after the last delimiter line is still checked as a command: TS-10 is denied.
- [ ] AC-5 (FR5; TM-3): An undeterminable destination falls back to the current chunk-wide sink match, for that heredoc only.
  - These are denied: TS-15 (the chunk fails to lex), TS-17 (the operator is attached to a compound command's closer), TS-21 and TS-22 (an execution prefix on the host statement), TS-26 (an execution prefix on the enclosing statement) and TS-27 (a process substitution).
  - TS-25 is allowed: the fallback for its undeterminable heredoc does not spill onto the data heredoc on the same line.
- [ ] AC-6 (FR7; TM-4): Existing verdicts are preserved.
  - TS-11 and TS-12 are allowed.
  - `python3 em-workflow/hooks/tests/run-destructive-guard.py` reports every case passing.
  - Compared with the base revision, the cases file only gains entries. No pre-existing entry is removed, and none has its expected verdict, label or command changed.
- [ ] AC-7 (FR8): The version is raised by exactly one patch step.
  - The em-workflow `version` in `em-workflow/.claude-plugin/plugin.json` equals the value at the commit's parent with the patch position raised by one.
  - The em-workflow entry in `.claude-plugin/marketplace.json` carries the same value.

## Test Notes

- **Where the tests run**: AC-1 to AC-6 are exercised through the cases
  file and the unchanged runner. The runner executes the guard as a
  subprocess with a real hook payload. NFR4 allows no new test file, so do
  not add a unittest module.
- **TDD order**:
  1. Add every listed case.
  2. Run the suite against the unmodified guard and record which new cases
     fail.
  3. Change the guard until the whole suite passes.
  4. Commit all `em-workflow/` changes, including the version bump,
     together. The plugin-version guard rejects any `em-workflow/` commit
     without a bump.
- **Recommended extra cases**: add these only if they hold under the rules
  above. They never replace a listed case.
  - `cat <<'EOF' | sudo bash` with a reset body: deny.
  - `cat <<'EOF' | grep x` with a reset body: allow.
  - The pipe-then-newline shape, where `cat <<'EOF' |` ends the line and
    `bash` follows the delimiter line: deny.
  - `bash scripts/check.sh && git commit -F - <<'EOF'` with a message that
    mentions `git reset --hard`: allow. git is a data command, even though
    the chunk contains a sink word.
  - `bash scripts/check.sh && git commit -m "$(cat <<'EOF' ... EOF)"` with a
    message that mentions `git reset --hard`: allow. The enclosing
    statement is a data command.
  - `x="$(cat <<'EOF' ... EOF)"` with a reset body: allow. The enclosing
    statement is assignment-only.
  - A `<<-` heredoc with a tab-indented delimiter, aimed at `cat`: allow.
- **Stress measurement (AC-8)**:
  1. Generate two inputs outside the repository: one of about 2,000 lines
     and one of twice that. Each line opens two or three heredoc operators
     aimed at a data command. Some have delimiter lines and some are never
     terminated.
  2. Feed each input to the guard as a hook payload and time it.
  3. Record the timings. Do not commit the generator (NFR4).
- **Inspection**: the change-set and import clauses of AC-7 and AC-8 are
  checked by inspecting the diff against the base revision.

## Out of Scope

- failed-run-cleanup-guard.py's and muse_guard.py's own heredoc handling.
- Changes to `head()`, `WRAPPERS` or `WRAPPER_VALUE_FLAGS`. Execution
  prefixes are handled only through the undeterminable outcome above, never
  by widening `WRAPPERS`.
- Resolving what an execution prefix, an unknown command, or a program-
  running option of a listed data command actually does. That would need
  per-command argument parsing.
- Command substitutions inside an unquoted heredoc body.
- A body written to a file and later run by another statement.
- The current handling stays for these cases:
  - unterminated heredocs
  - delimiters containing non-word characters
  - a `<<` inside quotes being read as an operator
- Any change to `hooks.json` or the runner script.
