## Goal

Make every failure path of the implement phase's I.2.c route-back protocol end
in a state the workflow can leave — no permanently unlaunchable task id, and
no plan whose only exit is abort — and re-ground I.2.a's unreachability

## Design

Read IMPLEMENTATION.md first: decisions D1–D7, the Conventions (wording bans
and test-module discipline) and the pinned-literal registry govern every edit
below and are not restated here.

### Site A — I.2.c: the third gate conjunct (FR1, FR2 → D1)

Add to the route-back admissibility gate one further conjunct beside its two
existing halves: route-back is inadmissible while any task's journal last
event is `merged`. Required properties of the added text:

1. It names the journal's last-event-per-task replay as its source and states
   that it holds independently of the ancestor verification the `merged`
   half's second source requires — i.e. it blocks the case where the journal
   reports `merged` but that claim fails verification, which neither existing
   half sees.
2. It gives the reason in one clause: the launch guard denies a launch whose
   journal last event is `merged`, so a renumbered task id inheriting such an
   event could never be launched. The launch guard's rule is cited from its
   owning site in Supporting cast, never restated.
3. It states the narrowing this produces: of the two terminal journal last
   events the surviving precondition sentence names, only the failed one
   leaves a recycled id launchable.
4. It cites, before the gate-rejected marker sentence, that a task the journal
   reports in-flight whose worktree and branch are gone is handled by Site C's
   recovery in I.2.b step 1 — a citation only, no journal mechanics.

Both existing halves keep their present wording and their two-source shape.

### Site B — I.2.a: replace the falsified premise (FR2 → D2)

The unreachability paragraph's premise beginning "Because route-back proceeds
only when no task is `merged` under either source" is replaced by a premise
resting on Site A's conjunct: route-back proceeds only when no task's journal
last event is `merged`, read from the journal directly, so the justification
survives a failing ancestor check. The paragraph's conclusion — the retired-id
inheritance invariant and the failed-only scoping of the carve-out — is
retained verbatim, as is the in-flight sentence and the unreachability slice's
opening and closing anchors (pinned-literal registry).

### Site C — I.2.b step 1: the existence check's effect and the recovery (FR3, FR4 → D3, D4)

Give the "worktree/branch existence for tasks the journal claims are in-flight"
check a stated outcome, in I.2.b (where journal mechanics may be described):

1. Failure condition: the task's journal last event is `launched` while
   neither the task worktree nor the task branch exists.
2. Effect of failure: it does not reclassify the task on its own — the
   last-event rule owned by I.2.a stays authoritative and is cited, not
   restated — it triggers the recovery below and the task is named in the
   phase report.
3. Recovery: the wake phase stops that task's recorded agent through the
   harness stop tool; the stop-tool recorder, cited from its owning bullet in
   Supporting cast, records the task's terminal failed event; the next replay
   reconciles the task as failed, so it reaches the normal failed handling
   where retry and route-back are both available.
4. Residual: when the stopped agent cannot be resolved to that task, the
   journal is unchanged, the task stays in-flight, the route-back gate blocks,
   and the phase takes the existing gate-rejected terminal with the task named
   in the report.
5. The recovery runs during the wake-phase reconcile, hence before the I.2.c
   user-facing menu is offered.

## Test Notes

All criteria map to unit-level document-contract assertions in the two named
modules, plus one aggregate integration run.

- Work test-first: add or update each matcher so it fails against the document
  as it currently reads, capture the pre-change sample it will be proven
  against at that same moment, then write the prose until it passes. A matcher
  that is green before the corresponding edit proves nothing.
- Slice before asserting. Section slices used by the existing modules are the
  I.2.a / I.2.b / I.2.c / Supporting cast boundaries; anchor new assertions on
  the narrowest slice that makes the claim, so a phrase surviving elsewhere in
  the document cannot satisfy a claim about a specific branch. Where a matcher
  slices between anchors, its negative proof shows the slice cannot be formed
  on the pre-change sample rather than asserting token absence.
- Scenario mapping: AC-1 → TS-1; AC-3 → TS-2; AC-2 → TS-3; AC-5 → TS-4;
  AC-6 → TS-5 and TS-6; AC-7 → TS-7 and the aggregate run; AC-4 → TS-8.
- Edge cases worth an explicit assertion: a task with no journal event at all
  still never blocks route-back; a journal `merged` that fails the ancestor
  check blocks route-back under the new conjunct; a stale launched state
  reaches the recovery rather than the abort-only path; the residual
  unresolvable-agent case is stated.
- TDD-awkward: AC-4's "no hook file modified" is a property of the diff, not
  of the document — verify it by inspecting the change set rather than adding
  a committed checker, and record that in the test record file.
- Run the FULL suite from the repository root after each edit site, not only
  the two named modules: modules outside the declared change set are the pins
  that catch an accidental rewrite of an immutable literal.
