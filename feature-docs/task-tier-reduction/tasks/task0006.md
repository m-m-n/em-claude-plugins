# Task Plan: task0006 — tier transcription, the task document, and tier-aware create-plan preconditions

## Goal

Transcribe the persisted tier decision into the workflow file when create-spec
builds it, define the task document that replaces the spec document at the
most-reducing tier, and relax the create-plan preconditions so a reduced run
is not rejected for missing documents it was never supposed to produce.

## Requirements

FR10, FR15, FR16, FR18, NFR7

## Scope

### Files to Create

- `em-workflow/references/templates/task-document.md` — the task document template with exactly two sections
- `tests/test_tier_phase_preconditions.py` — conformance tests for the transcription, the template and the relaxed preconditions

### Files to Modify

- `em-workflow/references/phases/create-spec-phase.md` — transcribe the persisted tier into the workflow file; produce the task document instead of the spec document at the most-reducing tier
- `em-workflow/references/phases/create-plan-phase.md` — make the preconditions tier-aware and state the single-task shape the most-reducing tier produces

## Design

**Transcription.** When create-spec builds the workflow file, the
orchestrator reads the persisted tier record and writes the tier and the
decision block into it, in the same write that builds the file. The
single-writer rule is unchanged: the worker proposes nothing here, the
orchestrator writes. After this point the workflow file is the value read;
a later re-transcription on resume may raise the tier and must never lower
it. The persisted record's fields are cited from the phase-state document,
not restated.

**Artifacts per tier at create-spec.** At the middle tier the requirements
document is not produced. At the most-reducing tier the spec document is not
produced either; a task document takes its place. Which artifacts each tier
subtracts is cited from the develop skill's reduction table, never restated
here.

**Task document template.** Exactly two sections: the change being made, and
the expected result. Nothing else — no requirement identifiers, no scenarios,
no assumptions block. The template file follows the existing templates'
conventions in the same directory.

**Create-plan preconditions.** Three preconditions currently assume a full
run: that both the requirements document and the spec document exist, and
that the workflow file's requirement map agrees with the spec's identifier
set. They become tier-aware. At the middle tier the requirements document may
be absent. At the most-reducing tier the spec document may be absent too,
with the task document named as the planner's input in its place, and an
empty requirement map is a legitimate state rather than a mismatch.

**The single-task shape.** The most-reducing tier still registers one real
task entry pointing at the task document. Subtracting the task split is not
subtracting the task record: the entry carries execution status and branch,
and task completion is defined by the merge into the integration branch. The
create-plan document states this explicitly, so nobody later reads "no task
split" as "no task". The entry still carries every mandatory field, including
its complexity value, and its requirement list may be empty.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: the create-spec protocol states that the orchestrator reads the
      persisted tier record and writes the tier and the decision block in the
      same write that builds the workflow file, and that a later
      re-transcription may raise but never lower the tier (TS-8).
- [ ] AC-2: the create-spec protocol states which artifacts are not produced
      at the middle and most-reducing tiers by citing the develop skill's
      reduction table, and restates no subtraction list of its own.
- [ ] AC-3: `em-workflow/references/templates/task-document.md` exists and
      contains exactly two sections — the change and the expected result —
      with no third section heading of the same level.
- [ ] AC-4: the create-plan preconditions admit an absent requirements
      document at the middle tier, and an absent spec document plus an empty
      requirement map at the most-reducing tier, naming the task document as
      the planner's input in that case (TS-6).
- [ ] AC-5: the create-plan protocol states that the most-reducing tier still
      registers exactly one task entry pointing at the task document, that the
      entry carries every mandatory field including complexity, and that its
      requirement list may be empty.
- [ ] AC-6: a planning patch built from that shape — an empty requirement map
      in the workflow file and an empty requirement list on the single task —
      passes `em-workflow/scripts/validate-worker-output.py` without changes
      to that script (TS-6).
- [ ] AC-7: `tests/test_tier_phase_preconditions.py` asserts AC-1 through
      AC-6, is discovered by `python3 -m unittest discover -s tests`, imports
      only standard-library modules, and pairs each matcher with a negative
      proof and a non-vacuity guard.

## Test Notes

- AC-6 is the one behavioural test in this task: build the minimal patch and
  run the validator against it the way the existing validator tests invoke it,
  then assert no error is reported. Its negative proof forges a patch missing
  the complexity field and confirms the validator does reject that.
- The two-section assertion for the template must be exact in both directions:
  a missing section and an extra one both fail.
- AC-2's "restates no subtraction list" is an absence check; its negative
  proof forges a copy that does restate one.
- Edge case worth covering: an empty requirement map written as an empty
  mapping and an empty requirement list written as an empty list are distinct
  YAML shapes, and both appear in the same document. Cover both.
- The transcription assertion should pin the single-writer wording so a future
  edit cannot quietly let a worker write these fields.
