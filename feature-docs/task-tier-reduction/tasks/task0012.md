## Goal

Make the deterministic evaluator honour the fail-safe principle it
declares: rows are interpreted from their declared threshold members rather
than from hardcoded identifiers and duplicated literals, out-of-range and
non-finite observations resolve to the tier that removes nothing, and the
disagreement rule between the two decision readings lives in the evaluator
instead of only in prose.

## Design

**The fail-open path.** Row selection branches on the row identifier
strings the current table happens to use, and each branch re-states the
table's numeric floors as its own defaults. Two consequences: renaming or
removing a member in the rules file silently reverts to a stale literal
instead of failing safe, and a row whose identifier matches neither branch
is returned unconditionally the moment it is reached — so a new conditional
row inserted above the removes-nothing row is adopted with its conditions
never evaluated, in the reducing direction.

**Row interpretation becomes data-driven.** A row is read for the threshold
members it declares, not for its identifier, and the code carries no numeric
default for any of them:

- a row declaring no threshold member at all is the unconditional
  fallthrough — the only row that may be returned without a comparison;
- a row declaring at least one threshold member matches only when every
  declared member has a corresponding observation that is present, numeric,
  finite, within the closed unit interval, and satisfies the comparison;
- a declared member whose observation is absent, non-numeric, non-finite or
  out of range makes the row not match, and evaluation continues to the next
  row — never to an unconditional return.

The correspondence between a declared threshold member and the observation
it constrains stays exactly the correspondence the rules file already
expresses (a first-bucket floor, a clarity floor, and a floor on the sum of
the first two buckets); what changes is that the evaluator derives which
comparisons to run from the row's own declared members.

**Range and finiteness.** Probability and clarity observations are accepted
only when finite and within the closed unit interval. An observation outside
that set is not merely a non-match: the result is the tier that removes
nothing, with a reason naming the offending member — a malformed score must
never buy a lighter tier. The result is serialized so that a non-finite
value can never reach the output at all, since a downstream strict parser
rejects such a token. The process still exits zero on every input and never
prompts.

**The two readings.** The procedure collects two readings of the judgement
skill — one from the task description alone, one with the pre-survey
estimate merged in — and the rule "if they disagree, fall to the tier that
removes nothing" currently lives only in prose, outside the one
deterministic component on the path. The evaluator's input contract is
extended to accept both readings in a single invocation, each with its own
basis label and its own observed score, and it returns the tier that removes
nothing whenever the two readings evaluate to different tiers. A single
reading remains accepted, so the availability fallback (the pre-survey
being unusable) needs no separate shape. The revised contract is pinned in
IMPLEMENTATION.md Shared Components — task0013 makes the document side cite
it rather than restating the rule.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: No row identifier literal and no threshold numeric literal
      appears in the evaluator; every floor it compares against is read from
      the rules table.
- [ ] AC-2: A row declaring at least one threshold member is never returned
      without its declared comparisons being evaluated, including when its
      identifier is unrecognized; only a row declaring no threshold member
      is an unconditional fallthrough.
- [ ] AC-3: A declared threshold member whose observation is absent or
      non-numeric makes that row not match and evaluation continues to the
      next row; when no row matches and no unconditional row exists, the
      result is the tier that removes nothing.
- [ ] AC-4: An observation that is non-finite or outside the closed unit
      interval yields the tier that removes nothing with a reason naming the
      offending member — in particular, neither the most-reducing nor the
      middle tier is reachable with such an observation.
- [ ] AC-5: No non-finite token can appear in the emitted result, and the
      process exits zero for every input including the malformed ones above.
- [ ] AC-6: The evaluator accepts two readings in one invocation and returns
      the tier that removes nothing when they evaluate to different tiers;
      a single reading is still accepted and behaves as it does today.
- [ ] AC-7: The existing threshold and fallback behaviour is unchanged for
      well-formed input — the three threshold cases and every
      availability combination resolve exactly as they do today — and
      `python3 -m unittest discover -s tests` reports no failure that is not
      already present at the integration branch's base commit.

## Test Notes

The evaluator is loaded and called directly, as the existing module already
does, so no subprocess is required except for the serialization check in
AC-5, which needs the emitted bytes.

Cases worth pinning explicitly: a rules table carrying an unrecognized row
identifier that declares thresholds, placed above the unconditional row
(AC-2's fail-open regression, with the pre-change code as the negative
proof); a rules table whose threshold member has been renamed, which must
make the row not match rather than fall back to a literal (AC-1); the
out-of-range and non-finite pairs the review reproduced (AC-4); and two
readings that resolve to different tiers (AC-6). The three threshold cases
and the availability combinations already covered stay as regression
assertions (AC-7).
