## Design

**The gap.** The rework planner's index declares, per task, either scenarios
already covered by the verification document or scenarios it says are new.
The validator proves the "new" claim by diffing that document against a
baseline copy, and treats a declared new scenario with no baseline as a hard
error. At the most-reducing tier the document does not exist at all, so the
question is whether that is an error, a route that cannot be reached, or a
case with its own rule.

**The decision to document.** Two routes into rework exist: an upgrade, which
recreates the missing documents before any rework planning happens, and a
direct rework without an upgrade. The rework path's documents must state which
of the two applies at the most-reducing tier, and state the outcome plainly
enough that the validator has one behaviour to implement. The behaviour chosen
must be fail-closed: an unverifiable novelty claim is rejected, never
silently accepted, which is the property the existing baseline rule already
protects.

**Validator change, minimally.** The script currently distinguishes "no
baseline directory supplied" from "baseline supplied". The absent-document
case is a third situation and gets an explicit outcome and an error message
that names it, rather than falling through into one of the first two by
accident. Nothing else in the script changes; in particular the task-entry
validation stays exactly as it is, because the empty requirement list it
already accepts is what the most-reducing tier relies on.

**Version bump.** This task is the only writer of both manifests for this
feature. The two values must be equal and strictly greater than the
pre-change value under per-component numeric comparison. The concrete target
is the next **minor** value on the current line, as NFR4 requires for a
feature addition. The twenty-two existing modules that pin the major/minor
pair as a named durable invariant are in this task's file set and are
rewritten to assert the property NFR4 actually cares about — both manifests
equal, and strictly greater than the pre-change value under per-component
numeric comparison — instead of a literal pair that blocks every future
legitimate minor bump. IMPLEMENTATION.md Resolved Questions records the
decision and its basis.

**Other plugin untouched.** The marketplace entry for the other plugin keeps
its name, author, category and source, and its version is asserted by shape
only.

## Test Notes

- AC-3 and AC-4 are behavioural: call the validator the way the existing
  validator tests do, with a synthetic result declaring a new scenario and no
  verification document present, and assert the specific error. AC-4's case
  asserts the absence of an error for the empty requirement list.
- The version modules follow the established pattern in `tests/`: a pinned
  pre-change baseline constant, per-component numeric comparison, an entry
  lookup by name rather than by array position, and the string-comparison trap
  case.
- Before choosing the bump value, run the whole suite once with the intended
  value in place. If a module outside this task's file set fails purely
  because of the version change, that is a plan deviation to report, and it
  is the signal that the open question in IMPLEMENTATION.md needs answering
  before proceeding.
- Edge case: the pre-change baseline constant must be captured from the base
  commit, not assumed, since sibling features may have moved it.
