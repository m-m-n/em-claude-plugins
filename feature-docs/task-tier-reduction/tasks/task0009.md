# Task Plan: task0009 — secure the integration worktree before the tier record is persisted

## Goal

Make the tier decision's persistence step reachable on the new-feature route:
Step A secures the integration branch/worktree before it writes and commits
the tier record, and exactly one of the two documents that can create that
worktree is named as its creator, with the other stated as a reuser.

## Design

**The defect.** Step A's worktree-securing step is scoped to existing
features only, while the tier-decision procedure's final step writes
`feature-docs/{feature}/phase-state/tier.yaml` inside the integration
worktree and commits it with `commit-docs.sh`. On the new-feature route no
worktree and no branch exist at that moment, and `create-spec-phase.md`
section 3 is what creates them — after the tier decision has already had to
persist itself. The persistence step therefore cannot complete, which in an
unattended run stops the run before create-spec begins (NFR6).

**The ordering this task fixes.** Inside the tier-decision procedure the
securing of the integration branch/worktree sits *after* the no-work stop
check and *before* the persistence step:

1. reuse a persisted decision if one exists (unchanged — on the routes where
   a worktree already exists);
2. the two external invocations (unchanged);
3. the no-work stop (unchanged) — a run that stops here has created no
   branch and no worktree, so the cheapest outcome stays the cheapest;
4. the two readings and the evaluation (unchanged);
5. **secure the integration branch/worktree** when it is not already
   present, using the same quoted-argument form Step A's existing
   re-materialization step uses;
6. persist the record into that worktree and commit it.

**Ownership between the two documents.** `create-spec-phase.md` section 3
currently instructs the phase to create the worktree immediately after the
feature name is fixed. It is reworded so that the phase *reuses* the
worktree Step A secured, and creates one only when entered by a caller that
did not come through Step A. The two documents together state one ordering,
and neither leaves the reader with two unordered creation claims.

**What is not changed.** The decision still happens in Step A, before any
create-spec cost is paid; the persisted-decision reuse on resume is
unchanged; the record's field set is unchanged (that record's shape belongs
to task0013); no new `gate_id` and no user question appear on this path.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: In `skills/develop/SKILL.md`, the integration branch/worktree is
      secured on the new-feature route and on the bootstrap-incomplete route
      before the tier-decision procedure's persistence step, and the

- [ ] AC-4: No sentence in either document claims unconditional creation of
      the integration worktree at a point that contradicts AC-1's ordering;
      a repository-wide read of both documents yields exactly one ordering.
- [ ] AC-5: `tests/test_tier_worktree_bootstrap.py` asserts AC-1 through AC-4
      against the raw text of both documents, and every matcher is paired

      ordering, plus a non-vacuity guard.
- [ ] AC-6: `python3 -m unittest discover -s tests` reports no failure that
      is not already present at the integration branch's base commit.

## Test Notes

All criteria are document-conformance assertions over raw file text, in the
style the existing `tests/test_tier_*.py` modules already use. The negative
proof for AC-1/AC-2 is a forged copy of the Step A text with the securing
step placed after the persistence step (and a second forgery placing it
before the no-work stop), both of which the matchers must reject. The
module imports standard-library modules only (NFR7).

The ordering assertion is positional, not keyword-presence: comparing the
byte offset of the securing step against the offsets of the no-work stop and
the persistence step inside the tier-decision section is what makes AC-1 and
AC-2 fail on the pre-change text rather than passing vacuously.
