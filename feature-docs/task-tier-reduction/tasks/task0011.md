## Goal

Make an upgrade actually re-run the phases it claims to re-run: the
procedure persists the re-entry and re-planning authorization the create-spec
and create-plan entry conditions require, the `reduced`→`full` branch
re-runs create-spec so the requirements document exists before design and
create-plan, the two subtracted documents are attributed to the phases that
own them, and the automatic-re-entry carve-out and the pinned test
assertions agree with the resulting state machine.

## Design

**Three defects with one root cause.** The upgrade procedure declares
transitions whose enabling conditions it never establishes:

1. It sets create-spec (and, in the round-1 text, create-plan) to the
   re-entry status, but the exclusion that keeps stop condition 3 from
   firing on that status requires an unconsumed authorization record in
   `phase-state/rework.yaml`, and the re-planning `replace_all` that a
   create-plan re-entry needs requires that same record carrying an unspent
   re-planning authorization. A plain run at a reduced tier has no such
   record, so neither re-entry is admitted.
2. The `reduced`→`full` branch re-runs design and create-plan but not
   create-spec, so the requirements document — which create-spec's writer
   produces — is never created. The planner's entry condition permits its
   absence only at the `reduced` tier, so the post-upgrade re-entry at
   `full` violates the condition it just became subject to.
3. The same branch attributes both missing documents to the design step's
   skip. Only one of them belongs to design's neighbourhood at all: the
   requirements document is subtracted by create-spec, the implementation
   plan by create-plan. That misattribution is what produced defect 2.

**The authorization record.** The upgrade writes the existing
`phase-state/rework.yaml` authorization record rather than inventing a
second one, and the existing vocabulary already fits: the two upgrade
triggers are a critical review finding and a failed verification, which are
exactly the two `origin_kind` values, with `origin_id` being the finding's
stable identifier or the failed item's identifier. The record is written
with its interruption reason, its origin pair, the commit it was recorded
at, unconsumed, and with the re-planning authorization granted — and it is
written and committed *before* any step status is set, so an interruption
between the two leaves a record that permits the re-entry rather than a
status the entry conditions reject. `phase-state.md` gains the tier-upgrade
procedure as a second writer of that record alongside rework's spec-change
transition; no field and no vocabulary value is added.

**The `reduced`→`full` ordering.** create-spec first (producing the
requirements document), then design, then create-plan. Each of the three is
named with the document it restores, and the attribution sentence states
that the requirements document is create-spec's subtraction and the
implementation plan create-plan's.

**The carve-out.** The enumeration's tier-upgrade entry is widened to cover
both re-entries the upgrade performs — create-spec and create-plan — rather
than a fourth entry being appended, because the first entry's create-plan
case is deliberately scoped to the implement phase's route-back and must
stay that way. The enumeration's stated count and the number of listed
transitions therefore stay equal, and the `--once` phase-boundary table's
automatic-re-entry row names the same transition.

**The pinned tests.** Two existing modules assert the pre-round-1 wording
and fail against the current text. They are updated to the state machine
this task settles, not to whatever the current text happens to say: each
updated assertion is re-derived from the criteria below.

## Test Notes

AC-1's ordering is the one criterion that a keyword-presence assertion would
pass vacuously: the test compares the byte offset of the record-writing
sentence against the offsets of the status-setting sentences within each
branch, and the negative proof is a forged sample with the two swapped.

AC-5's count assertion extracts the listed transitions and the stated count
from the same paragraph and compares them, so that a future edit adding a
transition without touching the count fails. AC-4's negative proof is the
current text, which attributes both documents to the design skip.

`tests/test_tier_decision_step_a.py` is this task's file for the duration of
the rework round; task0013's assertions go into its own new module so the
two do not contend for it.
