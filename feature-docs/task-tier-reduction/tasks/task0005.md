# Task Plan: task0005 — tier reductions, skipped discipline and upgrade in the develop loop

## Goal

Teach the develop orchestrator what each tier removes, let it pass over a
skipped step outside the design step instead of treating it as a broken file,
and define upgrading as returning skipped steps to pending.

## Requirements

FR3, FR9, FR10, FR11, FR12, FR19, FR21, NFR2, NFR3, NFR6, NFR7

## Scope

### Files to Create

- `tests/test_tier_reduction_develop_loop.py` — conformance tests for the reduction table, the skipped discipline and the upgrade procedure

### Files to Modify

- `em-workflow/skills/develop/SKILL.md` — add the reduction table; amend the turn-ending conditions, the Step B discipline, the Step C entry condition and the phase-boundary table for non-design skipped steps; add the upgrade procedure and extend the automatic-re-entry carve-out enumeration

## Design

**Region ownership.** IMPLEMENTATION.md D3 splits the develop skill between
task0003 and this task and the split is binding. This task owns the
turn-ending conditions list at the top of the file, the Step B status
discipline and phase table, the automatic-re-entry carve-out enumeration, the
Step C entry condition and its heading, the phase-boundary table, and the new
reduction and upgrade sections. It does not touch Step A or the retrospect
section.

**Reduction table.** One table, owned here, listing per tier what is
subtracted and what every tier keeps. The middle tier subtracts the
requirements document, the implementation plan and the design step. The
most-reducing tier additionally subtracts the spec document — replaced by the
task document, whose shape belongs to a template this task cites rather than
defines — the task split, the verification document, and task-level
parallelism. Every tier keeps the whole existing test suite, the Step 0
git-setup gate, and the integration worktree.

**Parallelism, precisely.** Subtracting parallelism means running a single
task in a single task worktree. The integration worktree is not subtracted in
any tier, because the workflow file and every feature document live only
there and the later phases depend on that placement. No sentence anywhere may
read as subtracting it.

**Skipped discipline.** Four places currently assume the skipped status
belongs to the design step alone: the first turn-ending condition, the Step B
sentence that treats a non-design skipped status as a file error, the Step C
entry condition and its heading, and the phase-boundary table's row for an
ordinary step. All four are rewritten so a step skipped by a tier is passed
over normally while its skip reason stays mandatory. The design step's own
create-spec-decided skip stays described.

**New turn-ending condition.** One entry is added to the conditions list for
the stop point task0003 triggers, named by its hyphenated form. The
underscored reason code is never written into this file. Before adding the
entry, search the repository for any assertion that pins the number of
conditions in this list; if one exists, it is part of this task's change.

**Upgrade.** Upgrading is expressed only as skipped becoming pending. No new
status value is introduced. The triggers are a critical review finding and a
failed verification. Downgrading is forbidden. Because the most-reducing tier
produced a task document through a create-spec step that reads completed, the
upgrade procedure includes re-running that completed step so the spec document
comes into existence. The automatic-re-entry carve-out currently enumerates
exactly two transitions and declares that enumeration exhaustive; it becomes
three, and the exhaustiveness sentence is updated to match the new count.

**Review selection untouched.** No tier-conditional branch is added to review
perspective selection anywhere in this file. That is what keeps the baseline
perspective set — the security perspective included — structurally
unreachable by this feature.
