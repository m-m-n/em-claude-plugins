# Task Plan: task0004 — the no-work stop reason code and its pinned assertions

## Goal

Add one stop reason code and its coverage row to the terminal-result
contract, and update every existing test that pins the size of that closed
set, so the suite stays green and the negative proofs keep working.

## Requirements

FR7, FR8, FR22, NFR3, NFR6, NFR7

## Scope

- `tests/test_no_work_required_stop.py` — tests for the new row, the coverage row, and a result carrying the new code

### Files to Modify

- `tests/test_structured_result_consumer_constraints.py` — regression confirmation; expected to need no edit

## Design

**The new code.** One row is added to the closed reason-code set, named for
the condition "the pre-survey reported that no work remains". The existing
completion code is not reused: it means the run reached the final workflow
step, so reusing it would distort that meaning. The row's applicable state is
the stopped state, matching every other row.

**Set-size prose.** The contract states the set's size in words in at least
two places — the field-value description and the section heading paragraph —
and counts a reserved consumer-only value separately. Every such sentence is
updated consistently, including the sentence explaining that exactly one
documented value has no stop point.

**Coverage row.** One row is added to the stop-point coverage table, mapping
the hyphenated stop point to the new code and naming the develop skill as the
specifying document. The precedence paragraph is examined: the new stop point
occurs before any workflow step exists, so it collides with none of the
generic rows, and the paragraph's list of colliding stop points is left
unchanged. If the paragraph turns out to need a sentence, it gets one.

**Responsibility boundary untouched.** The section stating that em-workflow
performs no operation against the external task-management service is not
edited at all. This is asserted, not merely intended.

**Existing pinned assertions.** Three modules pin the set's size or its exact
membership. Each is updated so the new code is part of the expected value,
while every existing negative proof — an added code detected, a removed code
detected, a changed mapping detected — keeps firing. Two further modules
derive the set from the owning table and are expected to follow
automatically; they are inside this task's declared file set so that a
surprise there is handled here rather than reported as a deviation.

**Single-source discipline.** The code literal is added only to the owning
contract. It is not written into the batch-mode document or the develop
skill, which point at the contract instead; this is the split the existing
modules already check mechanically.

## Test Notes

- Start by running the whole suite and recording which modules fail purely
  because of the count change. That set is the authoritative work list; the
  three modules named above are the predicted members, and anything else that
  appears is handled here rather than deferred.
- The byte-identical assertion for the responsibility-boundary section needs
  its pre-change text captured before the edit, then compared — capture it
  from the base commit, not from memory.
- The set-size prose is written in words, not digits, in at least one place.
  A search for the digit form alone will miss it; search for both.
- The pre-existing negative proofs must not be weakened to accommodate the new
  row. Prove this by running each forged-sample case and confirming it still
  raises.
- Edge case: the contract says exactly one documented value has no stop point.
  Adding a stop point for the new code must not change that statement's truth,
  and a test asserts it directly.
