## Design

**The two defects.** Both live in one section of one document and share a
root cause: the section's prose drifted away from wording that task0003's
Acceptance Criteria pinned and that `tests/test_tier_decision_step_a.py`
asserts.

- Item 4 states the first reading as a `decision_basis` identifier followed
  by a parenthetical gloss, so the required wording "1 回目はタスク記述のみを
  基準に" is split by the identifier and is no longer a contiguous run of
  characters. No information is missing — only the word order changed.
- Item 6 enumerates three individual unusable cases (the judgement skill
  unusable, the pre-survey unusable, the two readings disagreeing) and stops
  there. It carries no clause for a state the fallback table does not
  resolve at all. This is a missing rule, not a wording mismatch: without it
  an unknown or malformed availability state has no stated outcome.

**Item 4 — word order restored, identifiers kept.** The sentence is
reordered so the first basis is introduced by the required contiguous
phrase, with the `decision_basis` identifier attached to it rather than
inserted inside it. Both identifiers (`description_only` /
`description_plus_code`) remain present and remain attributed to
`tier-rules.yaml`'s `decision_basis` values — the identifier vocabulary
task0013 unified is not re-opened here, and no new identifier is coined. The
second reading keeps stating that the pre-survey estimate is merged into the
judgement skill's state, and the item keeps stating that both readings are
recorded, with their basis labels and observed values, as the decision's
bases.

**Item 6 — the catch-all added, the enumeration kept.** The three existing
cases stay exactly as they are, including the rule that any non-zero exit
status of the judgement skill counts as "judgement skill unusable" and the
citation that hands disagreement resolution to the evaluator's input
contract. One sentence is added stating that any other condition the
fallback table does not resolve likewise takes the tier that removes
nothing. The clause is the section's fail-closed floor: it names no row of
the fallback table and adds no new case to it, so `tier-rules.yaml` stays
the availability SSOT.

**Constraints the edit must not break.** The section restates no threshold
literal (the probability figures, the expectation comparison, the
probability-function notation, the expectation member name); it reproduces
no sentence from either external skill, while continuing to name the
readonly Codex wrapper and the judgement skill with its two JSON switches by
path; and it never names the raw Codex subcommand as an invocation route.
Every one of these is already true today and must remain true after the
edit — these are the properties the surrounding assertions in the same test
module pin.

**Region.** Only items 4 and 6 of `### tier 決定` change. Items 1, 2, 3, 5,
7 and 8 of that section, the turn-ending conditions list, Step A's other
text, Step B, Step C and the retrospect section are all untouched, so
IMPLEMENTATION.md D3 / D3a's region split is respected rather than
renegotiated.

## Test Notes

- The TDD contract is already written: the two named tests exist and fail
  today. The implementer runs them FIRST to observe both failures, edits the
  document, and re-runs until both pass. No new test module is created —
  adding one would duplicate assertions the pinning module already owns.
- AC-3 is covered by the sibling assertions in the same module
  (`test_no_threshold_value_restated`,
  `test_no_external_skill_sentence_reproduced_text_overlap`,
  `test_real_section_never_mentions_raw_codex_subcommand`,
  `test_named_external_skills_by_path_structurally`). They pass today, so
  their job here is regression detection: a wording change that breaks one
  of them is a failure of this task, not a pre-existing failure.
- The matchers compare with all whitespace stripped, so a required phrase may
  cross a hard wrap — but it must not be interrupted by any non-whitespace
  character. That distinction is the whole of TS-13's failure and is the one
  thing to verify by re-running rather than by eye.
- AC-4 is verified from the change's own diff: the diff touches exactly the
  two items and nothing else in the file.
