# Task Plan: task0002 — entry script targets every violating task

## Goal

When a failed task holds a violation, the entry returns every violating task that
is not merged, so correcting that list passes the validator and implementation
can resume.

## Requirements

FR4, FR8, NFR2, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `em-workflow/scripts/report-name-entry.py` — the widened violation list in judge, and the module docstring
- `tests/test_report_name_entry.py` — recurrence test and the FR4 cases

## Design

`judge` decides in two steps.

1. The `none` decision is unchanged: the violations of the failed tasks alone. No
   violation there returns `none`, whatever other tasks hold.
2. Otherwise `violations` is recomputed over every task whose status is not
   `merged`, in the order of the workflow's task mapping, and conditions 1 to 3 are
   judged on that whole list.

The helpers listed under Shared Components in IMPLEMENTATION.md are called as they
are. `failed_tasks` and the exit codes do not change.

An element for a task with no failed journal event carries `failed_journal_line:
null`, which the existing lookup already gives. The module docstring states the two
steps and the null line.

- [ ] AC-1: With a failed task and an unstarted task each holding a new report-artifact name, the entry returns `dispatch` listing both in task then file order, with a null `failed_journal_line` for the unstarted task (TS-7).
- [ ] AC-2: A failed task with no violation beside a pending task with one still returns `none`.
- [ ] AC-3: A merged task holding a name is not listed. An unstarted task whose last journal event is `merged` returns `blocked` with `path-correction-merged`, and an unstarted task whose name is a directory at the base commit returns `blocked` with `path-correction-old-path` (TS-7).
