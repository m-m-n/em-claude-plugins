## Design

Renders design-input.md 5.11.1, 5.11.2 and 5.11.5. The script is a command-line program, not a library, and the orchestrator judges it by exit code alone.

**Interface**: the five `--kind` values, the mandatory `--worker` and `--input`, and the auxiliary arguments for packet, answers, workflow, registries, phase-state, input envelope, digest source, feature directory, baseline directory and dry-run application. `--input-envelope` is mandatory for `--kind worker-result` for every worker, and its omission is an execution error rather than a validation failure. Inputs may be JSON or YAML.

**Exit codes**: 0 pass, 1 validation failure with machine-readable detail on stdout, 2 execution error including an unavailable PyYAML, whose message names PyYAML explicitly.

**Deliberate non-goal**: no JSON Schema evaluator. Rules are expressed directly, because a partial Schema implementation would diverge subtly on reference resolution, combinator semantics, formats and defaults.

**Validation content**: structural checks (required keys, types, enums, identifier patterns, size limits, per-status exclusivity, answer-mode consistency); cross-reference checks (answer options and modes against their questions, skills and domains against their registries, requirements against workflow.yaml, task files against the task plan's file sections, preserve paths against the permitted vocabulary and the per-operation mandatory sets, rework coverage against the verification index and the baseline diff, and the token yaml/html co-occurrence rule); and, under dry-run application, the digest and blob anchors, all expected values, the `replace_all` permission conditions, the append constraints, the post-application structure and preserve invariance.

**Markdown parsing** is limited to the four existing structural markers, using the existing template structures without introducing new markers. Path extraction from the file sections takes exactly one backticked token per bullet, treating zero or multiple as a validation error, and ignores HTML comments and fenced blocks. The shared-contract check is explicitly an approximation — multiple tasks declaring the same file require the shared-components heading to exist — and the script's own documentation says so.

**Mode dispatch**: for requirements-analyst the script branches on `analysis_mode` taken from the input envelope, verifies `mode_echo` agreement, and applies that mode's payload exclusivity; a missing or mismatched `mode_echo` is a validation failure.

**Fixtures** cover, per `--kind`, at least one case for every branch in the coverage table, with valid cases expected to exit 0 and invalid cases expected to exit 1. Fixture files carry enough naming structure for the test to know the expected outcome, the kind and the worker without a separate manifest.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `em-workflow/scripts/validate-worker-output.py` accepts all five `--kind` values and all auxiliary arguments listed in design-input.md 5.11.1, and rejects an unknown kind as an execution error.
- [ ] AC-2: The script exits 0 for valid input, 1 for validation failure with machine-readable detail on stdout, and 2 for execution errors; an unavailable PyYAML exits 2 with a message naming PyYAML.
- [ ] AC-3: Omitting `--input-envelope` with `--kind worker-result` exits 2 for every worker.
- [ ] AC-4: A requirements-analyst result whose `mode_echo` is missing, or disagrees with the envelope's `analysis_mode`, fails validation; a `design_system_detection` result containing full-mode payload keys fails validation.
- [ ] AC-5: Under `--dry-run-apply`, a stale digest or blob anchor, a mismatched `expected`, a duplicate patch identifier, a `replace_all` proposed after implementation has started, and an `append_rework` missing the mandatory preserve path are each rejected.
- [ ] AC-6: `em-workflow/references/fixtures/` contains at least one valid and one invalid fixture for every branch in the coverage table of design-input.md 5.11.5, including the two analyst modes separately.
- [ ] AC-7: `tests/test_validate_worker_output.py` runs every fixture and asserts exit code 0 for valid fixtures and 1 for invalid fixtures under `python3 -m unittest discover -s tests`.

## Test Notes

The tests are the primary artifact of this task and are written first. Structure them as: one test method per acceptance criterion for the interface and exit-code behaviour, plus a data-driven test that discovers every fixture file and asserts its expected exit code from its naming convention. Add a coverage test that parses the branch table from design-input.md and asserts each branch has at least one fixture, so an added branch fails until a fixture exists.

Simulate the missing-PyYAML case by invoking the script as a subprocess with an import environment where the module cannot be found, rather than by editing the script.

Edge cases worth covering: a bullet in a task plan's file section carrying zero or two backticked tokens; a symlink-valued path in `written_artifacts`; an `extend_only` target whose YAML contains an alias or merge key, which must be reported as uncomparable rather than silently accepted.

TDD-awkward area: the dry-run application needs a workflow.yaml to apply against. Handle it with small synthetic workflow files built in temporary directories rather than by depending on this feature's own workflow.yaml.
