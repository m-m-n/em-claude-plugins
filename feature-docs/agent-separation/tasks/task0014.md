## Design

Renders the automated verification table of design-input.md 9.1. The script takes a repository root as an argument, runs a set of independent checks, and reports machine-readable results, exiting 0 when all pass, 1 when any check fails, and 2 on an execution error.

Checks implemented:

- **Agent/dispatch parity**: the set of agent definition basenames under the plugin's agents directory equals the set of subagent-type identifiers referenced anywhere in the repository. A definition that is never dispatched, and a dispatch of a definition that does not exist, both fail.
- **Stale references**: the removed create-spec agent's name and the inline-execution phrase do not occur, with an allowance for this feature's own design and planning documents, which quote them historically.
- **Gate identifier coverage**: every gate identifier appearing in the phase protocols and the develop skill has an entry in the batch policy file, and the policy file contains no identifier that appears nowhere, with the one documented intentional exception excluded from both directions.
- **Domains vocabulary parity**: the vocabulary in the review rules registry equals the set described in the plan-writing skill.
- **Forbidden heading**: no agent definition contains the task-assignment heading that the queue hooks treat as a fallback.
- **Fixture branch coverage**: every branch named in the fixture coverage table has at least one fixture file.
- **Digest reproducibility**: computing the input digest twice over the same inputs yields the same value; the check builds its own small input set rather than depending on a live feature.

Each check is a separate function taking a root path, so the unit tests can build a synthetic directory tree in a temporary directory containing exactly the files a given check inspects, exercise both the passing and failing branch, and assert the reported outcome. This is what makes the task implementable in isolation, since no task worktree contains the fully integrated repository.

The script's output names each check, its outcome, and for failures the specific offending items, because it is read by a human during the verify phase.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `em-workflow/scripts/check-plugin-invariants.py` accepts a repository root argument and exits 0 when all checks pass, 1 when any check fails, and 2 on an execution error.

- [ ] AC-4: The agent/dispatch parity check fails both for an undispatched definition and for a dispatch of a missing definition.

- [ ] AC-7: The digest reproducibility check computes its value twice over a self-constructed input set and compares them.

## Test Notes

Tests are written first and are the main deliverable alongside the script. For each check, build a temporary tree containing the minimum files that check reads, in a passing arrangement and in at least one failing arrangement, then assert the function's outcome and the reported offenders.

Keep the synthetic trees small and explicit; do not copy the real plugin directory, because doing so would couple these tests to the merge order of sibling tasks.

Edge cases worth covering: an agents directory containing a non-Markdown file; a subagent-type reference appearing inside a fenced code block, which should still count as a reference; a gate identifier that differs only by case; and a fixtures directory with a file whose name does not follow the expected convention.

TDD-awkward area: the digest reproducibility check depends on the normalization rules owned by another document. Handle it by having the check consume an explicit input mapping rather than discovering files itself, so its behaviour is fully determined by its argument.
