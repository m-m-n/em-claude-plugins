# Task Plan: task0006 — create-spec 側 worker 契約（analyst / spec-writer）

## Goal

Define the input/output contracts for the two workers that replace the current create-spec agent: requirements-analyst and spec-writer.

## Requirements

FR4, FR5

## Scope

### Files to Create
- `em-workflow/references/contracts/analyst-contract.md` — requirements-analyst input/output contract

- `tests/test_worker_contracts_create_spec.py` — analyst / spec-writer 契約の構造アサーション

### Files to Modify

(none)

## Design

Both documents extend the common envelope by reference (`references/contracts/worker-envelope.md`) and add only worker-specific content.

**analyst-contract.md** renders design-input.md 5.4.1 and the analyst rows of 5.0 R1. It states:

- The worker's responsibility: project context inspection, requirement clarification candidates, command and license detection, design-step recommendation, and design-system candidate detection. It performs no file writes, no commits, no branch or worktree operations and never asks the user.
- The additional inputs: `analysis_mode`, `analysis_scope`, `task_description`, `known_feature_name`.
- The `analysis_snapshot` payload returned with `needs_user_input`, field by field.
- The `completed` payload for `analysis_mode: full`.
- The lightweight `design_system_detection` mode: it ignores `analysis_scope`, returns only design-system candidates, may return only three of the six statuses, never returns a question packet, and must not include the full-mode payload keys.
- The `digest_inputs` set for each mode, and the rule that the orchestrator resolves all globs and the worker reads nothing outside `resolved_input_paths`.
- The `mode_echo` requirement.
- The design-system candidate categories the analyst reports, with the explicit statement that it detects and classifies candidates but does not decide the project's `kind`.
- The exclusivity assumption for the integration worktree during dispatch.

**spec-writer-contract.md** renders design-input.md 5.4.2. It states:

- The responsibility: produce REQUIREMENTS.md and SPEC.md from the analyst's resolved requirements; never write workflow.yaml; never return a question packet.
- The additional inputs: `requirements_analysis` and the two template paths.
- The full path-level `write_policy` model: the six actions with their `expect_digest` requirements and the worker behaviour each mandates; the protection split between `targets` (existing-file protection, mandatory enumeration) and `allowed_write_roots` (directories where new files may be created); the rule that enumerating a file in `targets` is itself the permission for that file; the reason `regenerate` needs no user approval and its `source` field; the reason `replace_authorized` still verifies the digest; and the `extend_only` key-comparison rule with its blocked cases.
- How the orchestrator chooses each target's action before dispatch, including the digest-mismatch branch and its gate.
- The `completed` payload (`spec_index`, `assumptions_written`).
- The post-conditions: requirement ID pattern and uniqueness, index/document agreement, mandatory `tbd_reason`, and the prohibition on inventing requirements or assumptions the analyst did not produce.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: `analyst-contract.md` exists, references the common envelope by path, and documents `analysis_mode`, `analysis_scope`, `task_description` and `known_feature_name`.
- [ ] AC-2: The analyst contract documents the `analysis_snapshot` fields and the full-mode `completed` payload from design-input.md 5.4.1.
- [ ] AC-3: The analyst contract documents the `design_system_detection` mode with its payload exclusivity, its restricted status set and its `digest_inputs`, and states that the analyst detects candidates without deciding `kind`.
- [ ] AC-4: `spec-writer-contract.md` exists, references the common envelope by path, and documents all six `write_policy` actions with their `expect_digest` requirement and worker behaviour.
- [ ] AC-5: The spec-writer contract states the protection split between `targets` and `allowed_write_roots`, including that an existing file not enumerated in `targets` may not be modified even under an allowed root.
- [ ] AC-6: The spec-writer contract documents the `completed` payload and all four post-conditions, including the prohibition on inventing requirements.
- [ ] AC-7: Neither contract restates the common envelope's fields or the question packet schema; both reference them by path.
