# Task Plan: task0004 — rework 合成 SSOT と implement / review 参照の修正

## Goal

Create the single source of truth for rework task synthesis and fix the real bug where returning `implement` to `pending` with no pending task leaves the implement phase with nothing to launch.

## Requirements

FR1, FR2

## Scope

### Files to Create
- `em-workflow/references/rework-task-synthesis.md` — the rework synthesis contract shared by all four routes
- `tests/test_rework_synthesis_contract.py` — rework SSOT と 2 参照元の構造アサーション

### Files to Modify
- `em-workflow/references/implement-phase.md` — add the rework re-entry precondition requiring at least one pending task
- `em-workflow/references/review-phase.md` — point both the interactive and batch rework branches at the new SSOT and document the `needs_rework` update ordering

## Design

**rework-task-synthesis.md** renders design-input.md 5.10 with the coverage rules from 5.4.4. It is organised as: purpose; applicable modes (the four routes); inputs; grouping rules; task ID allocation; task plan requirements; metadata derivation; verification coverage rules; related document updates; workflow state transition; invariants; validation; execution adapter. Key content:

- The document's subject is the contract the synthesis result must satisfy, not who writes the prose, so the contract survives a change of executing worker.
- Grouping does not map one file to one task; findings sharing a cause, a contract or an acceptance criterion become one task, using the normal decomposition rules from the plan-writing skill.
- The document update scope: task plans always created; VERIFICATION.md per the coverage rules; IMPLEMENTATION.md only when a new shared contract arises; SPEC.md and REQUIREMENTS.md never.
- The coverage declaration requiring `covered_by_existing` or `new_scenarios` to be non-empty for every rework task, with the four validation checks.
- The state transition ordering: for review-sourced rework, the orchestrator writes `needs_rework` and the review status first, then dispatches, then validates and applies the patch, with the implement transition carried inside that patch; verify-sourced rework starts from the dispatch step because `needs_rework` is review-specific.
- The eleven invariants, notably that a pending rework task must exist before `implement` returns to `pending`, that `base_commit` is preserved, and that synthesis rules do not differ between interactive and batch.
- A reference to the execution adapter (the rework-planner contract) without restating it.

**implement-phase.md** gains a precondition, placed where the phase's entry conditions are stated, saying that re-entering implement for rework requires at least one task whose status is `pending`; entering with every task `merged` is a protocol error that must abort with a report rather than idling. The `completed_at_commit` semantics are not changed.

**review-phase.md** replaces the thin interactive completion-gate wording and the batch branch with references to the new SSOT, and states the `needs_rework` update ordering explicitly.
