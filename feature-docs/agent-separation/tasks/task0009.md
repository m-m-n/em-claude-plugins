# Task Plan: task0009 — 新規 worker 定義 3 件（analyst / spec-writer / rework-planner）

## Goal

Create the three new Task-dispatched agent definitions that carry out investigation, document authoring and rework planning under the new contracts.

## Requirements

FR20, FR21, FR23, NFR7

## Scope

### Files to Create
- `em-workflow/agents/requirements-analyst.md` — investigation and question-generation worker
- `em-workflow/agents/spec-writer.md` — REQUIREMENTS.md and SPEC.md authoring worker
- `em-workflow/agents/rework-planner.md` — additional-task planning worker for review and verify rework
- `tests/test_new_worker_agents.py` — 新規 worker 定義の frontmatter と規律アサーション

### Files to Modify

(none)

## Design

Each file is an agent definition in the existing repository style: YAML frontmatter with `name`, `description`, `model`, `effort`, `tools` and optional `skills`, followed by the prompt body. The body states the worker's responsibility, points at its contract document for the input/output shape, and encodes the discipline the contract requires.

Common body content for all three:

- The worker is dispatched by the orchestrator; it never asks the user and has no AskUserQuestion tool.
- workflow.yaml is read-only; the worker never commits.
- The final output is a single structured object conforming to the common envelope, whose contract path is given.
- The worker reads only the paths supplied in the envelope and in `resolved_input_paths`, and performs no discovery of its own.
- No completion report may contain next-step guidance, matching the existing corpus convention.
- The prompt must not contain a `# Task assignment` heading (NFR7), because the queue hooks use that block as a fallback when the subagent type is absent.

Worker-specific content:

- **requirements-analyst**: tools are read-only plus shell for inspection; the two `analysis_mode` values with their differing scope and payload; the categories it inspects; the rule that it reports design-system candidates without deciding the project's `kind`; the requirement to echo its mode; and the guidance that unresolved points become questions rather than assumptions.
- **spec-writer**: tools include write access; it renders the two documents from the supplied templates and the analyst's resolved requirements; it never invents requirements or assumptions the analyst did not produce; it honours the write policy's per-path action and returns `blocked` when a digest disagrees; it returns no question packet.
- **rework-planner**: tools are read plus write for plan documents; it plans only additional tasks and never rewrites the existing plan; it applies the normal decomposition rules to grouping; it emits the coverage declaration and the shared-contract rationale; it returns a question rather than tasks when a specification change is required; and it proposes a workflow patch instead of writing workflow.yaml.

Model and effort selection follows the existing corpus: analysis- and planning-heavy workers use the stronger model with high effort; the authoring worker matches the effort of the document work it replaces.

## Test Notes

Write `tests/test_new_worker_agents.py` asserting, per file: the frontmatter parses as YAML and contains the required keys; `AskUserQuestion` is absent from `tools`; the contract path string appears in the body; the read-only, no-commit and no-discovery sentences are present; and no line matches the forbidden task-assignment heading.

Add a shared assertion helper covering the three common rules so a fourth worker added later is trivially checkable.

Edge case: frontmatter that parses but omits `effort` or `model` must fail, since those only take effect under Task dispatch and their absence would silently downgrade the worker.
