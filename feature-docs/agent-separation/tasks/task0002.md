# Task Plan: task0002 — workflow patch 契約

## Goal

Define the restricted patch format through which workers propose workflow.yaml changes, together with the rules that govern its atomic application.

## Requirements

FR12

## Scope

### Files to Create
- `em-workflow/references/workflow-patch.md` — the workflow patch format, permitted operations and application rules
- `tests/test_workflow_patch_doc.py` — patch 契約ドキュメントの構造アサーション

### Files to Modify

(none)

## Design

Renders design-input.md 5.5 (including 5.5.1 through 5.5.6). The document states:

- Why generic RFC 6902 JSON Patch is not adopted: arbitrary JSON Pointer writes break the state machine's ownership boundary, and array-index addressing is fragile against step reordering.
- The common fields and their requirement status, including `base_input_digest` and `base_workflow_blob` as the staleness anchors and the `patch_id` identifier pattern.
- The two operations and the matrix binding each to its `tasks_patch` mode, its permitted `step_patches` targets and its issuing worker.
- `tasks_patch`: atomic upsert of whole task entries (never partial, so the mandatory metadata set is never left incomplete), the `expected_next_task_id` requirement for `append`, the `provenance` block for rework entries, and the permission conditions for `replace_all`.
- `requirements_patch`: the `merge_entries` mode and the closed set of permitted `set` operations.
- `step_patches`: addressing by `step_id` rather than array index, with `status` as the only settable field, and the statement that `base_commit` and `completed_at_commit` are orchestrator-owned.
- `preserve`: the permitted path vocabulary, the per-operation mandatory sets, and the recommendation for `append_rework`.
- The sixteen application rules in order, ending with single-write application and the rule R2 commit sequence.
- That `project` and the review summary block are not patchable by workers.
- That the `domains` vocabulary SSOT is `references/review-rules.yaml`.
