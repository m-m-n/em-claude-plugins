# Task Plan: task0023 — 検証スクリプトの gate 束縛と型ガード

## Goal

Bind gate identifiers to the worker, phase, category and options permitted for them, extend the type guards to every structure the validator walks, and stop two checks from silently degrading.

## Requirements

FR9, FR10, FR11, NFR4, NFR8

## Scope

### Files to Modify
- `em-workflow/scripts/validate-worker-output.py` — gate registry, type guards, baseline requirement, per-worker payload rule
- `em-workflow/references/fixtures/` — invalid fixtures pinning each fix
- `tests/test_validate_worker_output.py`

## Design

Findings addressed: `bs2` (validator half), `bs9`, `bs10` (validator half), and the validator side of `bs1`. Read `feature-docs/agent-separation/reviews/round2.yaml` first; `bs2` and `bs9` each record an exact reproduction.

**Gate binding.** A gate identifier is currently only checked for non-emptiness, so a worker can attach a permissive listed identifier to a sensitive question and have batch resolution auto-select its option. Both spoofs in `bs2` were reproduced through this script and exited 0. Introduce a registry keyed by gate identifier giving the permitted emitting worker, phase, category and option identifiers, and reject a packet that does not match. Derive the registry from what already exists rather than inventing a second source of truth — the policy file declares the identifiers, and each gate's originating contract states its worker and phase.

**Type guards.** The guard added last round reached only the written-artifact normalizer. A task patch entry whose value is a string, and a worker-run list containing a string, both raise and exit 1 with empty output, breaking the documented contract that exit 1 carries machine-readable detail. Guard every element of the patch entries, step patches, preserve list, worker runs, patches, packets, answers and resolved-input cache. Then wrap the top-level dispatch so an unexpected exception exits 2 with a message on standard error, leaving exit 1 always accompanied by JSON.

**Baseline requirement.** The rework coverage check degrades silently without a baseline directory: it falls back to "the identifier exists in the current document", which the rework planner itself wrote. Make the validator error when new scenarios are declared and no baseline was supplied, rather than accepting a claim it cannot verify.

**The payload prohibition on the awaiting-input status.** The design settles this and neither side of the collision needs a new exception. Its status table forbids artifacts, a patch and a blocking reason on the awaiting-input status — it does not forbid a payload — and its analyst section defines that status's payload explicitly. The forbidden-payload entry for that one status was added during implementation and is not design-backed. Drop the payload prohibition for the awaiting-input status only, leaving it in place for the other non-completed statuses, and add a fixture in which the analyst returns its interim snapshot alongside a question packet. task0024 makes the matching correction to the envelope contract's table; both sides must end up saying the same thing.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Both reproduced gate spoofs are rejected, and a packet whose gate identifier, category, worker, phase or option set does not match the registry fails validation.
- [ ] AC-2: The registry derives its content from the existing declarations rather than restating them.
- [ ] AC-3: A malformed element in the patch entries, step patches, preserve list, worker runs, patches, packets, answers or resolved-input cache produces a machine-readable error, never a traceback.
- [ ] AC-4: An unexpected exception exits 2 with a message; exit 1 always carries JSON on standard output.
- [ ] AC-5: Declaring new scenarios without a baseline directory is an error rather than a silent degradation.
- [ ] AC-6: An analyst result carrying its interim snapshot alongside the awaiting-input status validates, while the payload prohibition still holds for the other non-completed statuses.
- [ ] AC-7: Each fix above has at least one invalid fixture, and every fixture still resolves to its expected exit code.

## Test Notes

Turn the two reproductions in the round record into failing tests before touching the script. For AC-6, coordinate the fixture with task0024's contract wording; if that task lands first its contract is authoritative, and if this one lands first leave the fixture in place for it to match.
