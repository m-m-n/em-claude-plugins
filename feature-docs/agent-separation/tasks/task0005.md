# Task Plan: task0005 — question 解決規則と batch policies

## Goal

Define the shared interactive/batch question resolution procedure, create the gate-ID-based batch policy SSOT, and reduce `batch-mode.md` to the decisions that are not expressed as question packets.

## Requirements

FR15, FR16, FR24, NFR4

## Scope

### Files to Create
- `em-workflow/references/question-resolution.md` — shared packet resolution procedure for interactive and batch
- `em-workflow/references/batch-policies.yaml` — gate-ID-based batch decision SSOT
- `tests/test_batch_policies.py` — gate policy の集合一致アサーション
- `tests/test_question_resolution_doc.py` — 解決規則ドキュメントの構造アサーション

### Files to Modify
- `em-workflow/references/batch-mode.md` — remove the migrated content, retain the non-packet decisions, and reference the two new documents

## Design

**question-resolution.md** renders design-input.md 5.9. It states:

- Deduplication, applied in the given order: identical question IDs are the same question and a changed body after answering is a worker protocol violation; `supersedes` obsoletes the prior question; matching gate, evidence target and affected workflow field marks a duplicate candidate; the orchestrator does not judge meaning from prose differences but re-dispatches asking the worker to reuse stable IDs; answered questions are never re-presented, and invalidating an answer requires a new question ID with `supersedes`.
- The stable priority sort: blocking first, then priority, then the category order, then question ID; `depends_on` defers a question until its dependency is answered.
- Presentation limits: at most three questions per AskUserQuestion call and at most four options per question, while a packet may carry up to thirty-two questions.
- The batch resolution sequence, including that an option ID absent from the question's options is a protocol error and label matching is forbidden as a substitute.
- The unlisted-gate fallback with its numbered steps, the Codex consultation with its untrusted-output caveat, the mapping attempt, the `on_unanswered` branches, and the fail-closed rule: a merely preferential choice on a success path takes the minimum-side-effect option, while specification change, security, licensing and irreversible operations abort. The document states plainly that this replaces the current continue-on-success-path rule and is an intentional behaviour change.
- The requirement to record the decision basis in `resolution_note` and the run report.

**batch-policies.yaml** contains the `gate_policies` map covering exactly the gates expressed as question packets, with the actions and option IDs from design-input.md 5.9, and header comments stating its scope, that `rework.spec-change` is intentionally absent so it falls through to the abort path, and the meaning of `preserve_and_reuse` and `on_unavailable: abort`.

**batch-mode.md** keeps the decisions that never pass through a question packet (git-setup failure, feature selection, review diff-size gate, command-approval hook fallback and similar), removes the rework synthesis body and the Codex fallback detail, and references `rework-task-synthesis.md`, `question-resolution.md` and `batch-policies.yaml` in their place. The union of the retained decisions and the policy file must still cover every gate the current decision table covers.
